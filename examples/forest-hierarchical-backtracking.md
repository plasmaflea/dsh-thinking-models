# 示例：🌳 林状分层分类回溯法（林状图／回溯法）

> 技能 id：`forest-hierarchical-backtracking`
> 本示例演示 v2 的两条关键改动：**轴必须生成（时序），不得列举**；**禁止删枝，只挂起（含恢复条件）**。

## 输入

> 我们的 CI 每天随机失败 3~5 次，重跑就过。根源在哪？

## 产物

```
[🌳 林状图] 选择理由：问的是「根源」。轴取「一次 CI 运行的必经阶段」——一步必然发生且只发生
     一次，所以完备性由流程保证，不靠灵感列举。

轴（生成源：时序）
  ┌──────────────────────┬───────────────────────────────────┬──────────┐
  │ 阶段                 │ 该格故障的可观测症状              │ 判定     │
  ├──────────────────────┼───────────────────────────────────┼──────────┤
  │ ① 触发与领取         │ 同一 commit 两次运行结论不同      │ 不是根   │
  │ ② 环境准备（镜像/缓存）│ 时快时慢、偶发缺包或版本漂移    │ 共因     │
  │ ③ 依赖安装（registry）│ 日志里出现 retry / 超时         │ 次要     │
  │ ④ 构建               │ 产物 hash 两次不一致              │ 不是根   │
  │ ⑤ 测试执行           │ 失败用例不固定、重跑即过          │ **主因** │
  │ ⑥ 上报与聚合         │ 超时判定的边界抖动                │ 次要     │
  └──────────────────────┴───────────────────────────────────┴──────────┘

逐格回溯
  ① 不是根：两次运行同一个 commit，两侧输入相同 ⇒ 差异必须发生在后面
  ② 共因：缓存目录跨 job 复用 ⇒ 上一 job 的残留物进入下一 job（这是"非确定性"的放大器）
  ③ 次要：有 retry 但最终成功率高 ⇒ 影响的是时长，不是成败
  ④ 不是根：产物 hash 稳定 ⇒ 构建是确定性的，锅不在编译
  ⑤ 主因：失败用例不固定 + 重跑即过 = 非确定性被执行的并行结构放大
  ⑥ 次要：聚合只看期望耗时，卡在临界点的 job 被误判

汇合层（多根合并）
  ⑤ 主因 ∧ ② 共因 收束到同一句：CI 从未被当作"有非确定性输入的实验装置"来设计——
  既没有隔离共享状态，也没有给信号加可信度指标。

候选根排序（Share × Lever ÷ Cost）
  ┌────────────────────┬────────┬──────────┬──────────┬────────┐
  │ 候选根             │ Share  │ Lever    │ Cost     │ 优先   │
  ├────────────────────┼────────┼──────────┼──────────┼────────┤
  │ 共享工作目录/端口   │ 主因   │ 改配置   │ 半天     │ 1      │
  │ 缓存跨 job 复用     │ 共因   │ 改配置   │ 半天     │ 1      │
  │ 时间/随机种子未固定 │ 次要   │ 改代码   │ 1 天     │ 2      │
  │ 并行 job 资源竞争   │ 次要   │ 改容量   │ 一笔采购 │ 3      │
  │ 超时判定阈值        │ 次要   │ 改配置   │ 1 小时   │ 2      │
  └────────────────────┴────────┴──────────┴──────────┴────────┘

挂起表（分支／判定／依据／恢复条件）
  ┌──────────────┬────────┬────────────────────────────────┬──────────────────────────────┐
  │ 网络抖动     │ 不是根 │ 历史监控在失败时段无告警       │ 失败时刻与网络告警重合率 > 30% │
  │ 硬件故障     │ 不是根 │ 同机其他流水线同期稳定         │ 同机其他流水线同时失败        │
  │ 代码缺陷     │ 不是根 │ 重跑即过，与逻辑确定性相悖     │ 某用例连续 5 次稳定失败       │
  │ 镜像仓库故障 │ 不是根 │ 无 pull 失败的明确日志         │ 出现 429/5xx 且集中同一时段   │
  │ 构建工具 bug │ 不是根 │ 产物 hash 两次一致             │ 产物 hash 出现两次不一致      │
  └──────────────┴────────┴────────────────────────────────┴──────────────────────────────┘
  ⚠️ 「挂起」不等于「没想过」：每条都带恢复条件，任一条件成立就重启该枝。

结论（从根解决，而非治症状）
  1) 隔离非确定性：每 job 独立工作目录 + 独立端口 + 固定随机种子与时间
  2) 给信号加可信度：同一 commit 排 3 次，报 flaky 率而不是单一红绿
  3) 治理：flaky 用例进独立队列，阻断其进入主干门禁
```

## 为什么这样比直接回答好

| | 直接回答 | 林状图（v2） |
|---|---|---|
| 结构 | 一段推理 | 按必经阶段生成的 6 格 + 逐格判定 |
| 完备性 | 靠想到什么说什么 | 由流程保证：漏格一眼可见（**全空列判据**） |
| 失败定位 | 「答案错了」 | 哪一格错，其余格仍成立 |
| 排除项 | 无记录 | 5 条挂起**带恢复条件**，可被人复核、可在新证据下重启 |
| 排序依据 | 挑一个最像的原因 | `Share × Lever ÷ Cost`，可被质疑的是权重而不是直觉 |
| 结论来源 | 单根 | 多根汇合，对应三个动作 |

## 轴是怎么生成的（可复制）

| 问题 | 生成源 | 轴 |
|---|---|---|
| Windows 服务启动即退 | 时序 | SCM 注册 → 令牌/窗口站 → PE 加载器 → `DllMain` → 注入与钩子 → 就绪检查 → 受限令牌/完整性 |
| CI 随机失败 | 时序 | 触发 → 环境准备 → 依赖安装 → 构建 → 测试执行 → 上报 |
| 留存低 | 时序 + 证据来源 | 认知 → 获取 → 激活 → 习惯 → 留存 → 召回；× 自埋点/第三方/定性 |
| 收入上不去 | 恒等式 | `收入 = 流量 × 转化率 × 单价`，每因子再切 提升/稳定/风险 |
| 请求变慢 | 时序 + 并发 | 接入 → 鉴权 → 业务 → 存储 → 回包；× 单次耗时/并发退化 |
| 估算工期 | 恒等式 | `人日 = 人数 × 工期 × 效率`，再按模块拆 WBS |

**不合格的轴**（都是"列举式"，会被这张表一眼看穿）：权限/环境/DLL/杀软/配置；新用户/老用户/某渠道；前端/后端/数据库/网络。
