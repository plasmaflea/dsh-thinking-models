# 示例：🌳 林状分层分类回溯法（林状图／回溯法）

> 技能 id：`forest-hierarchical-backtracking`

## 输入

> 我们的 CI 每天随机失败 3~5 次，重跑就过。根源在哪？

## 产物

```
[🌳 林状图] 选择理由：问的是「根源」，且至少有三个正交维度（背景现象 / 能力链 / 问题机制）。
     用单根树会跨维度跳跃，所以拆成三棵独立子树并行回溯，最后在汇合层合并。

维度一〈背景现象：他到底想解决什么〉
  随机失败 → 重跑即过 → 不是功能性错误
  → 用户真正痛的是"信号不可信"：CI 红不再意味着代码坏
  → 根：信任成本，不是时间成本。
  ⚠️ 若把这一维换成"CI 太慢"，方向会立刻跑偏——这一维决定后面两维的判据。

维度二〈能力链：它为什么能发生〉
  非确定性（必要）
    └ 时序竞争（必要）
        ├ 容器复用：同一工作目录、同一端口（充分）
        ├ 外部依赖：时间、随机种子、外部服务限流（充分）
        └ 资源竞争：并行 job 抢 CPU/IO，卡在超时临界（充分）
  → 根：非确定性来源没有被隔离，而不是"测试写得不好"。

维度三〈问题本身的机制〉
  3~5 次/天且重跑即过 → 失败率低但稳定存在
  → 指向系统性缺陷，不是偶发硬件
  → 根：缺少对不确定性来源的显式枚举与治理。

汇合层（三根合并）
  三棵树收束于同一点：CI 从未被当作"有非确定性输入的实验装置"来设计，
  所以既没有隔离，也没有可信度指标。→ 三个根治动作其实是一个动作的三个面。

无关边（被排除分支 + 剪枝理由）
  - 网络抖动 ⊥ ：历史监控无对应时段异常 → 剪枝
  - 硬件故障 ⊥ ：同机其他流水线稳定 → 剪枝
  - 代码缺陷 ⊥ ：重跑即过与代码逻辑相悖 → 剪枝

结论（从根解决，而非治症状）
  1) 隔离不确定性：每 job 独立容器 + 固定随机种子 + 时间冻结
  2) 给信号加可信度：同一 commit 排 3 次，报 flaky 率而不是单一红绿
  3) 治理：flaky 用例进独立队列，阻断其进入主干门禁
```

## 为什么这样比直接回答好

| | 直接回答 | 林状图 |
|---|---|---|
| 结构 | 一段推理 | 三棵可独立推翻的子树 |
| 失败定位 | 「答案错了」 | 哪一维错，其余两维仍成立 |
| 排除项 | 无记录 | 三条 `⊥` 边留档，可被人复核 |
| 结论来源 | 挑一个最像的原因 | 多根汇合，对应三个动作 |

**负边的作用**：`网络抖动 ⊥` 这类断言，直接回答永远不会写——因为它看起来「没价值」。但它恰恰是「我想过并排除了」的唯一证据。
