# 示例：林状分层分类回溯法

## 输入

> 我们的 CI 每天随机失败 3~5 次，重跑就过。根源在哪？

## 产物

```
[🌳 林状图] 选择理由：问的是「根源」，且至少有三个正交维度（为什么要管 / 为什么能发生 / 问题本身的机制），
     用单根树会跨维度跳跃，所以拆成多棵独立子树并行回溯。

维度一（背景现象：他到底想解决什么）
  随机失败 → 重跑即过 → 不是功能性错误 → 用户真正痛的是"信号不可信"，
  即 CI 红不再意味着代码坏。→ 根：信任成本，不是时间成本。

维度二（能力链：它为什么能发生）
  非确定性 → 时序竞争 → 共享可变状态
    ├─ 容器复用（同一工作目录、同一端口）
    ├─ 外部依赖（时间、随机种子、外部服务限流）
    └─ 资源竞争（并行 job 抢 CPU/IO，超时临界）
  → 根：非确定性来源没有被隔离，而不是"测试写得不好"。

维度三（问题本身的机制）
  3~5 次/天、重跑即过 → 失败率低但稳定存在 → 提示系统性缺陷而非偶发硬件问题。
  → 根：缺少对不确定性来源的显式枚举与治理。

汇合层（三根合并）
  三棵树在同一个点上收束：CI 从未被当作"有非确定性输入的实验装置"来设计，
  所以既没有隔离，也没有可信度指标。

被排除分支
  - 网络抖动：历史监控无对应时段异常，剪枝。
  - 硬件故障：同机其他流水线稳定，剪枝。
  - 代码缺陷：重跑即过与代码逻辑相悖，剪枝。

结论（从根解决）
  1) 隔离不确定性来源：每 job 独立容器 + 固定随机种子 + 时间冻结；
  2) 给信号加可信度：同一 commit 排 3 次，报告 flaky 率而不是单一红绿；
  3) 治理：把 flaky 用例进单独队列，阻断其进入主干门禁。
```

## 为什么这样比直接回答好

- 三棵树各自独立，任何一棵被推翻不影响其他两棵（失败可定位）
- 「被排除分支」把剪枝理由留档，别人能复核你是不是漏了
- 结论是从多个根汇合出来的动作，而不是拍一个最像的原因
