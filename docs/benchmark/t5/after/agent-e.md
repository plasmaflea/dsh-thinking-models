# 支付成功率 98.2% → 96.9%（−1.3pp）根因回溯

**[🌳 林状图／回溯法]** 选择理由：问「根源在哪」＝因果深度问题，不是选项广度（网状图）也不是数量关系（公式图）。且四个候选原因已摆在题面，本轮真正要做的不是"再想原因"，而是判断**哪一个是根、哪几个只是症状**——这正是「个例根必须挂在类根下」＋「禁止删除、只许挂起」两条例要解决的。

## L0 类别判定

**类别：软件类（分布式请求路径 ＋ 观测结构）。**
判据：①可复现性来自代码/配置/环境姿态——CDN 切换＝环境姿态变更、v3.4＝代码变更，两者都满足；②失败是确定性的或由确定性竞争导致——超时、排队、阈值触发都是「给定输入与时序下的确定结果」，不是随机位翻转。

**已排除的大类：硬件故障。** 依据：无 CRC/ECC 类校验症状、无跨软件随机性、症状严格与「变更时点 ＋ 链路」绑定。

**不能排除、必须显式保留的三类：**
- **网络类**——CDN 全量切换本身就是链路变更；分层可达性数据缺失，无法排除。
- **组织与流程类**——三家团队各自"我们这边没有异常"，这是口径与职责边界问题，不是技术结论。
- **权限/账号类**：基本排除（失败按"哪一类请求"分布，而非"哪一个账号"），但风控的 IP／设备信誉判定与它相邻，保留观察。

## L2 逐层回溯

### 轴（生成式，不是列举）

生成源取**恒等式**：一次支付的成功率是多跳存活率之积

```
SR = Π_i (1 − f_i)          ΔSR ≈ − Σ_i f_i   （f 小时）
```

于是「请求的每一跳」就是天然的一格——格子由必经路径机械生成。每格必须能说出自己的**专属症状**（三判据：正交／可生成／可观测）。

| 格 | 这一跳在管什么 | 该格故障的专属症状 | 本题对得上的观察 |
|---|---|---|---|
| **G1** 客户端→边缘 | DNS／TLS／证书链／SDK 网络栈 | 分段客户端失败率；按 OS／机型／App 版本分层 | App 失败率 > Web |
| **G2** 边缘→源站（回源） | B 的回源路由、跨境链路、连接复用 | 回源延迟分位数、回源失败率；按 POP／地理分层 | 海外 > 国内；"厂商说无异常" |
| **G3** 网关／接入 | 超时阈值、限流、连接池、排队 | 网关超时率、排队时长、连接池饱和度 | 网关超时率上升 |
| **G4** 后端调用链 | v3.4 的两个同步调用、新下游容量 | 各调用段 p99；新下游 QPS／p99／连接数 | （无细分，只有"发了 v3.4"） |
| **G5** 风控决策 | 规则**输入**（IP／设备／地理／频次）→ 放行/拒绝 | **拒绝原因码（reason_code）分布** | 0.8% → 1.1% |
| **G6** 支付渠道／下游 | 银行／渠道成功率 | 分渠道成功率 | 无数据（空白点） |

**跨格的两个放大器**（不是格，是因子：它们不自己产出症状，只放大各格的 f）：
- **A1 流量密度 +40%**：排队等待近似 ∝ ρ/(1−ρ)。在 ρ 的高区，+40% 流量能把 p99 抬数倍（M/M/1 量级关系，此处不代入具体数）。
- **A2 串行跳数 +1**：`f_total = 1−(1−f1)(1−f2) ≈ f1+f2`，且两跳**共用同一超时预算与同一连接池**。加一跳不是"加一次查询"，而是**加一个失败域 ＋ 加一次超时预算消耗 ＋ 加一份连接持有时间**。

### 关键一步：把 ④ 从「原因」改判为「探针」

题面把「风控拒绝率上升」列为第 ④ 件事，还特意强调"规则没动过"。这是本题第一个陷阱：

- **规则没动 ≠ 决策没变。** 风控输出是 `f(规则, 输入特征)`。规则是常量，**输入才是变量**。
- 这两周唯一改变了风控**输入**的，恰好就是 ① 和 ③：CDN 全量切 B 会改变源站看到的**客户端 IP（XFF 链增减、B 的自家 IP 段、地理归属判定）**、**UA／头字段／设备指纹（UTDID 等）的保真度**；流量 +40% 会改变**同 IP／同设备请求密度**，让"高频"类阈值在规则完全不变的情况下更易触发。
- 所以 ④ 不是与 ① 并列的第四个原因，而是 **①（和 ③）的一个传感器**：拒绝率上升，是"请求身份信息在新边缘下失真"的最便宜的读数。

这一改判同时消掉一个正交性矛盾：如果主因是纯后端的 v3.4，风控**没有理由拒绝得更多**（后端慢会变成超时，不会变成"拒绝"）。拒绝率上升这件事，**必须**由"输入变了"或"密度变了"解释——二者都指向 ① 和 ③。

### 用四个观察做互斥（这一步不可跳过）

- **App > Web、海外 > 国内，是「跨度差」。** 后端（v3.4）是全部客户端、全部地区共享的同一套服务：纯后端退化应让失败率**各处同比例**上升。出现客户端与地区的跨度差，说明至少有一个原因作用在 **G1/G2（客户端与链路）**，不在业务层。
  → 推论：**v3.4 至多是共因或放大器，不可能是唯一主因。** 这条单靠逻辑就能排掉一个候选。
- **海外 > 国内 ＋ 网关超时率上升**：后端同构，国界差异只能来自**边缘到源站的路径**（B 的海外 POP→源站跨境回源质量、IP 归属误判）或**区域客户端差异**。这是 ① 的指纹。
- **"厂商说我们这边没有异常"不构成证据。** CDN 厂商的"无异常"通常只指它自己的边缘侧指标（5xx、缓存命中、可用性）。**回源延迟、跨境链路、TLS 握手与连接复用率、XFF 传递正确性，根本不在那张报表里。** 口径不覆盖 ≠ 没问题。这是第二个陷阱：把"对方自证"当成"已排除"。
- **网关超时率是观测口径，不是原因。** 它把 G2（回源慢）、G3（自己排队）、G4（后端慢）三类"慢"加总成一个数。它上升只说明"某处慢"，**不定位任何一格**。把它当原因读，只会得到"网关有问题"这种不可执行的结论。

### 类根（面对整个大类）

> **成功率是逐跳存活率的乘积，而观测只有聚合指标、没有请求级归因；于是当多个变更同时落在不同跳上时，"损失分布在哪几跳"在结构上不可回答——下降能被看见，却不可能被定位。**

这条类根有必然性，不依赖本次细节：只要同时满足（a）成功率是乘积、（b）只有聚合值、（c）变更期不止一个跳被动过，则"哪一跳掉的"**必定不可判**。本次三条全中（① 动 G1/G2/G5 的输入，② 动 G4，③ 动所有格的 ρ）。**这才是"两周了还查不出根"的真正根**——不是没人努力，是系统没有能回答这个问题的结构。

### 个例根（挂在类根之下，不是并列清单）

> **母因：CDN 从 A 全量切到 B，同时改变了两个东西——「请求的身份保真度」（源站看到的客户端 IP／设备标识／地理归属）与「回源路径质量」（尤其跨境）。v3.4 的串行加跳与 40% 流量，把这条已经变脆的链路推过了超时悬崖。风控拒绝率上升是母因的读数，不是独立原因。**

机制分解（按 Share 从大到小）：

- **M1 身份失真 → 风控误拒（G5 ← G1/G2）**：B 的 XFF 链多一层或少一层、B 的出口 IP 段未进风控 IP 库与源站白名单、geo 库把 B 的边缘 IP 判成"数据中心 IP"或错判国家、App 的设备指纹经新边缘后丢失或漂移 → 风控在"信息不全"时倾向拒绝（风控的默认降级策略几乎总是"拒"）→ 拒绝率 +0.3pp，且 App（指纹链路更长）与海外（IP 归属更难）更严重。
  **这是唯一能做到「三个观察合一」的机制**（拒绝率↑ ＋ App>Web ＋ 海外>国内）→ Share 最高。
- **M2 串行加跳 × 流量密度 → 越过超时悬崖（G3/G4）**：v3.4 拆成两个同步调用，`f ≈ f1+f2`，两跳共用超时与连接池；新增"查询"的下游此前从没见过大促 QPS，容量与连接数都没做过对应评估。40% 流量在高 ρ 区把排队放大数倍。两者是**交互项，不是加法**：单独任一项可能都不越阈值，叠加就整段超时。附带的恶性循环：**超时 → 重试 → 同一支付意图重复投递 → 幂等/锁冲突 → 从"慢"变成"确定性错"**。
- **M3 回源与跨境路径（G2）**：B 在海外区域的 POP 覆盖／回源专线不如 A，连接复用率下降 → 建连次数上升 → 边缘到源延迟与超时上升。**这一条独占地解释"海外 > 国内"**。
- **M4 测量层假象（不是故障，但必须先扣掉）**：App／海外的失败率基线本来就高于 Web／国内；大促期间流量结构变化（App 占比、海外占比上升）会让**聚合成功率自己往下挪**（Simpson 型 mix shift）。所以"App 失败率高于 Web"这句话，在没做分组加权之前**不能当证据用**。

**算术约束（题面数据能算的部分）**：
- 风控拒绝 0.8% → 1.1%，直接贡献 **+0.3pp**，占 1.30pp 的 **23%**。（前提：拒绝被计入失败。若"成功率"定义为技术/接口成功率而不含风控拒绝，则这 0.3pp 不是可加项，而是与失败同源的分叉——见 ⚠️1）
- 剩余 **≈1.0pp 没有任何一个直接数字支撑**。题面只说"网关超时率上升"，没给幅度。这 1.0pp 要在 M2（超时/重试）、M3（回源）、M4（mix shift）、G6（渠道，无数据）之间分配，而现有聚合数据**在数学上无法定这个分配**。
- 这就是"没有原始日志"的真实代价：不是少了一份日志，是**少了一个可解的方程组**。

## L3 双根

### 处置根（修本次，按 Cost 排序）

1. **用形状代替日志（Cost ≈ 一次取数，杠杆最高）**：把已有的**日／小时粒度**成功率曲线按四个事件时点对齐。三类变更的时间形状天然不同——CDN 全量切换＝**阶跃**（瞬间一步到位）；v3.4 发版＝**阶跃且可分组**（灰度期新旧版本并存）；大促＝**斜坡**（随流量渐升）。形状一对齐，主因基本落定。**这是现有数据里还没被榨过的最后一块结构。**
2. **用现存对照组做差分，而不是下钻日志**：未切 CDN 的区域／运营商、v3.4 灰度期的老版本实例、App vs Web、同一批用户的非峰时 vs 峰时——这些都是**已经存在的自然实验**。无日志时的归因不靠 trace，靠**对照**。
3. **调风控拒绝的原因码（reason_code）分布**：这是现有聚合数据里**唯一带语义**的维度，也几乎是最便宜的一步。若拒绝集中在 IP 信誉／地理／设备指纹／高频类规则 → M1 基本坐实；且能立刻区分"身份失真"（按 IP/设备类规则聚集）与"密度触发"（按频次类规则聚集）。
4. **单独验 v3.4 的"加一个查询"**：取该新下游在变更前后的 QPS、p99、连接数、连接池饱和度。若它的 p99 在流量上来后抬升数倍 → M2 坐实，"只是加了一个查询"被推翻。
5. **对 CDN B 改口径要数**：不要问"有没有异常"，直接指定要回源延迟分位数、回源失败率、跨境链路、TLS 握手与连接复用率、XFF 传递校验。口径对齐之后，"无异常"才有意义。
6. **（最后手段）小流量灰度回切 A**：最强的因果检验，Cost 中等；当 1／3／4 都做不出区分时使用。

### 消解根（灭这一类）

> 给请求路径装上**逐跳归因结构**：`request_id` 从客户端贯穿到渠道，边缘／回源／网关／每一段后端调用／风控各自产出「到达数、成功数、耗时分布」，配 1% 头部采样原始日志，并把**分阶段成功率**做成常驻看板——而不是只有一个总成功率。

- **不可发生判据**：若当时采用它，则任一多变更叠加期的下降都能在小时级被拆成"哪几跳各掉了多少"，本类问题（聚合指标下，多变更期不可归因）**在结构上不可能发生**——不是"更容易查"，而是**问题本身不成立**。
- **可执行首边**：先只做**分阶段计数**，不引全链路 trace、不引新系统：网关注入一个 request_id 并透传，G1/G2/G3/G4/G5 各打一对「到／成」计数，输出一张「逐跳存活率」表。一支小队、几个工程日可落地。
- **成本量级**：**中**。工程量：小几个工程师周（透传 ＋ 五处打点 ＋ 看板）；存储：1% 采样日志，按当前流量是可接受量级；真正的瓶颈是**组织成本**——需要 CDN 厂商回传其边缘侧采样日志（跨公司）。

## L4 迁移出口

消解根产生的新问题清单（**本次问题降级为其中第 1 项**）：

1. **[本次问题] 多变更叠加期的成功率下降不可归因** → 降级为"逐跳归因缺失"的一个实例。
2. **数据与口径**：分阶段成功率的分子/分母必须全局统一（含"风控拒绝算不算失败"）——否则五处打点会产出五套口径，比没有更糟。
3. **运行开销**：request_id 透传 ＋ 1% 采样会带来可测的延迟与存储成本，需要预算与降级开关。
4. **可观测性落点**：边缘（第三方）与源站（自有）日志的 join 键与时钟对齐——跨公司时钟偏差会让"哪一跳慢"算错，这是最容易埋雷的一处。
5. **凭据与权限**：CDN 厂商侧日志导出的鉴权与合规（海外流量涉及数据出境）。
6. **组织能力**：三家团队共用一个"逐跳存活率"口径，等于把"各自自证无异常"的结构换成"共同对一张表负责"——**这是流程变更，不是技术变更**，也是这条迁移路径上最容易失败的一项。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| v3.4「只是加了一个查询」＝无害 | 不是无害；判为放大器／共因，不是唯一主因 | 纯后端退化应各处同比例，无法解释 App>Web、海外>国内 的跨度差 | 若失败集中在调用该查询的那一段、且灰度期老版本成功率显著高于新版本，则升为主因 |
| CDN B 边缘侧「无异常」＝已排除 | **未排除**；厂商口径不覆盖回源与跨境 | "无异常"通常只指其边缘 5xx／缓存／可用性 | 拿到 B 的回源延迟分位数、回源失败率、跨境链路数据，且口径与本问题对齐 |
| 流量 +40% 是独立主因 | 判为放大器（因子），非根 | 流量是斜坡、变更是阶跃，形状可分离 | 若失败率曲线与流量曲线同形且与变更时点无关，则升为主因 |
| 风控**规则**变更 | 排除 | 题面明示规则未动 | 若配置/代码 diff 显示阈值改动，或规则依赖的特征/模型版本有静默更新 |
| 风控**模型/特征平台**静默更新 | **挂起**（"规则没动" ≠ "决策没变"） | 未验证模型版本与特征版本 | 查模型/特征版本号与发布记录 |
| 支付渠道侧（银行/渠道成功率） | 挂起（无任何数据） | 题面未给渠道指标 | 取分渠道成功率与渠道侧超时 |
| App>Web 由 App 自身导致（版本／机型／OS 信任链） | 挂起 | 旧 Android 对 B 的证书链／根证书不兼容也能产出同一现象，与 M1 同症状 | 按 App 版本／OS 版本分组成功率；若集中在旧 OS 则升为主因 |
| 聚合值下的 mix shift（Simpson） | 观测层根，先扣 | 流量结构变化本身就能移动聚合成功率 | 分组加权后重算总成功率；若加权后差异消失则确认 |
| 重试 → 重复投递 → 幂等/锁冲突 | 挂起（树外分支 `data-consistency`） | 两跳同步 ＋ 超时重试必然提高重复提交概率，但无数据 | 查重复请求率、幂等冲突计数、分布式锁失败计数 |
| 网络类（`network` 节点未建，`v2` 候选） | **树外分支，未排除** | 本题主嫌之一，但树里没有该节点 | 分层可达性数据（POP→源站握手／丢包／重传） |
| 组织与流程类（`org-process` 未建，`v2` 候选） | **树外分支，未排除**；可能是"为什么两周定位不了"的根 | 三家各自"无异常"＝各自用自己口径自证 | 三家指标合并到同一张逐跳表后重判 |
| 硬件类 | 排除 | 无 CRC/ECC、无跨软件随机性、症状与变更时点绑定 | 出现随机性症状或校验错误 |
| 权限/账号类 | 基本排除 | 失败按"哪类请求"而非"哪个账号"分布 | 出现账号特异失败 |

## 结论（三句话）

1. **根源不在四选一，而在那个结构性变更上**：CDN 从 A 全量切到 B，同时改变了「源站看到的请求身份」（客户端 IP／XFF／设备指纹／地理判定 → 风控误拒）与「回源路径质量」（尤其跨境）；v3.4 的串行加跳与 40% 流量是把它推过超时悬崖的放大器。**风控拒绝率上升是母因的读数，不是独立原因。**
2. **再往上一层，真正的类根是观测结构**：成功率是逐跳存活率的乘积，而系统只留聚合指标、没有请求级归因，所以"1.3pp 分散在哪几跳"在数学上就是不可解的——**这才是两周定位不了的根**。
3. **下一步不需要日志也能推进**：先用「曲线事件形状对齐（阶跃 vs 斜坡）＋ 现存对照组差分 ＋ 风控 reason_code 分布」三招把 M1／M2／M3 撕开；同时把「逐跳存活率」作为消解根的第一条可执行边落地。

## ⚠️ 异常 / 矛盾 / 空白

1. **「成功率」的定义未给**（分子/分母是什么：页面 PV→支付成功？接口成功率？含不含风控拒绝？）。若风控拒绝**不**计入成功率，则 ④ 的 +0.3pp 不是可直接相加项，M1 的份额要重算。**这是全题最关键的定义空白，必须在取任何数之前钉死。**
2. **1.0pp 没有任何直接数字**：题面对"网关超时率上升"没给幅度。已知可观测的只有 0.3pp（占 23%），余下 1.0pp（占 77%）在现有数据下不可分配——不是没查到，是**现有聚合数据不足以构成可解的方程组**。
3. **矛盾点**：题面把 ④ 与 ① 并列陈述（"风控规则没动过"），但拒绝率上升**需要**由输入或密度变化解释，而这两周只有 ① 和 ③ 动过它们。把 ④ 当独立原因，就永远解释不了它与 ① 的耦合。
4. **「厂商说没有异常」与「海外失败率更高」并置**不是矛盾，是口径差——需要先对齐口径，否则两句话都不能用。
5. **空白**：无 v3.4 的分段耗时、无分渠道成功率、无 App 版本/OS 分组、无风控 reason_code 分布、无日/小时级时间序列。前四项任何一项都能单独推翻或坐实一个候选根。
6. **树外分支 3 个**（`network` / `org-process` / `data-consistency`）已登记进挂起表。建议升 `v2`：新增 `network` 节点，理由——本题主嫌落在该支，而现有树只有单进程启动失败视角，覆盖不到跨跳请求路径。

## 💡 灵感备注

- 一个反问能替代大量分析：**"如果当时只切了 CDN、没发 v3.4、也没大促，成功率会掉多少？"** 以及反过来 **"如果 CDN 没切，只发 v3.4 ＋ 大促，会不会掉？"** 这两个反事实若能从任何灰度／区域／时段数据里近似读出，排序立刻收敛。
- 本题的元教训：**"我们这边没有异常"是口径陈述，不是事实陈述。** 三家各自无异常而整体退化，正是"每跳都正常、乘积不正常"的典型——这类问题只有把测量粒度下沉到「跳」，才有答案。
