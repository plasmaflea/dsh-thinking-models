# 支付成功率 98.2% → 96.9%：根源在哪

## 结论先行（三句话）

1. **跌幅不是一个原因造成的，是两个结构性变更在同一段同步串行链路上乘性叠加**：v3.4 把 1 次同步往返变成 2 次串行往返（失败率≈翻倍、时延预算相加、上游超时阈值未重算）；CDN 全量切 B 同时改掉了「跨境链路质量」与「客户端特征透传语义」。前者吃掉了约 1.0 pt，后者直接制造了风控那 0.3 pt 与 App／海外的超额跌幅。+40% 流量是**放大器**，不是根。
2. **四个已观测现象是同一张图上的三个切片，不是四个问题。** App>Web、海外>国内 同时指向「时延预算 + 端侧特征采集」，而不是业务逻辑——业务逻辑 bug 不会挑端类型和国别。
3. **两周没定位的根不在技术，在观测结构**：只有聚合成功率、没有原始样本，而每个依赖方都用自己的（对它有利的）聚合口径自证无异常。技术根与认知根要分开报。

## L0 类别判定

**类别**：分布式链路的「成功率—时延」退化（外部依赖变更 + 链路拓扑变更，叠加在一条同步串行路径上）。
**判据**：跌幅可按端／地域／时间／依赖方切片区分；症状随链路与流量变化，不随单一代码路径变化；同一份程序在不同接入路径下行为不同（命中 `software` 节点判据 1 的「环境姿态」分支）。
**已排除的大类**：硬件故障（无随机位翻转／校验错误症状，跌幅有明确时间断点）；权限账号类（拒绝只集中在风控环节且与规则命中无关）。
**树外分支**（本树未建，登记进挂起表，不静默丢弃）：`network`、`data-consistency`、`org-process`。

## L2 层 1：用恒等式切「跌幅只可能来自三处」

成功率 = 1 − [ P(网关超时/系统失败) + P(风控拒绝) + P(下游失败) ]

任一跌幅在这条恒等式上只有三条入口，正交、可生成、各有专属症状：

| 格 | 机制 | 该格故障的可观测症状 |
|---|---|---|
| ①真实恶化 | 某个因子在**同一批切片内**确实变大 | 切片内成功率下降，且该因子占比同步上升（本次：超时率↑、风控拒绝率↑） |
| ②结构漂移（mix／辛普森） | 各切片成功率不变，但低成功率切片的**权重**变大 | 总跌幅 > 各切片跌幅的加权；把 mix 固定回两周前后跌幅显著收窄 |
| ③口径／分母变化 | 「成功」的定义或分母变了 | 旧口径无法复算；同一用户请求被计成两次（v3.4 双调用正有此风险） |

**判定**：本次 ① 是主账（两个因子占比**同时**上升，纯 ②③ 不会出现因子占比上升）；② 必须减掉（+40% 大促必然改变 mix，它制造伪跌幅）；③ 必须查（若 v3.4 使成功率分母从「用户请求」变成「后端请求」，则存在天然下跌而用户无感）。

## L2 层 2：用必经时序切「变更落在哪一格」

轴由支付请求的必经步骤机械生成（一步一格），每格写专属症状：

| 格 | 该格故障的可观测症状 | 落入本格的变更 |
|---|---|---|
| S1 端侧/客户端 | 只有某端、某端版本跌 | App 的 SDK、证书 pinning、DNS 缓存、长连接预热 → App 专属退化 |
| S2 接入/边缘（CDN） | 按地域/运营商分层的 RTT 与丢包上涨；真实客户端 IP 与头部透传失真 | **① 全量切 B** |
| S3 网关 | 超时率、429/5xx、队列深度上升 | **③ 流量 +40%** + 下游变慢的回压 |
| S4 风控 | 拒绝**原因码分布**变化，「信息缺失／兜底」类命中占比上升 | **④ 规则未动但输入与分母变了** |
| S5 后端业务 | 单请求延迟从 L 变 L1+L2，P99 相加；单请求失败率从 p 变 ≈2p | **② v3.4 双同步调用** |
| S6 下游支付/清算 | 渠道侧成功率与错误码 | 无变更声明（待验） |

**关键结构**：四个变更全部落在 S2/S3/S4/S5，而 **S2 与 S5 是相邻串联**——CDN 增加的那部分往返与 v3.4 增加的那一跳，落进**同一个**时延预算里相加，而不是各自被预算独立吸收。这就是「四个局部无损的变更叠加出一次不可归因跌幅」的物理位置。

**全空格判据**：S1、S6 有症状但非主因（见挂起表条目），六格非全空，不构成换轴。

## L2 → 类根

**类根：在一条 P99 敏感、超时阈值固定、多团队并行变更的同步串行链路上，没有任何一方对「整条链路的总时延预算与总失败预算」负责。**

只要这个结构在，任何一组「各自都没错」的变更都能叠加出一次无法归因的跌幅——这就是「类」在什么结构条件下必然可能发生。

个例根（挂在类根之下，三者乘性，不是并列清单）：

- **个例根 α（主因·结构）**：v3.4 把一个同步往返拆成两个**串行**往返。失败率 p → 1−(1−p)² ≈ 2p；时延 L → L1+L2；且上游超时阈值、重试次数没有重算 ⇒ 尾延迟必然击穿固定预算。对「只是加了一个查询」的反驳：在同步链路上加一次外部调用不是 +1 个查询，是 **+1 个 RTT + 1 个独立失败点 + 1 份对下游的负载**。
- **个例根 β（主因·触发与差异化）**：CDN A→B 全量切换同时改了两样东西——**链路**（海外节点覆盖、跨境回源路径、丢包与 RTT）与**语义**（X-Forwarded-For 链、边缘 IP、UA/设备特征、TLS 指纹的透传方式）。语义变化正好命中风控：拒绝率是「规则 × 输入分布 × 分母结构」的函数，规则是常量，所以拒绝率上升只可能来自**输入分布**或**分母结构**——fail-closed 的风控把「取不到特征」直接变成「拒绝」。
- **放大器 γ（非根）**：+40% 流量把利用率 ρ 推向饱和，排队延迟按 ~1/(1−ρ) 非线性上升；同时把 mix 推向高失败切片（大促新客、海外、App 占比上升）；超时→无退避重试→流量再放大，构成正反馈。γ 不改变单请求失败的结构概率，它只放大 α 和 β。

## 判别性推理：为什么这样切，而不是别的原因

1. **App>Web、海外>国内 是排除「业务逻辑 bug」的判别证据。** 业务逻辑错（那条 SQL 写错、字段映射错）与端类型、国别无关，会**均匀**打穿所有切片。差距出现 ⇒ 真正起作用的是与「网络距离」和「端侧环境」相关的量：RTT 预算与特征采集。由此可粗分解：**Web×国内 切片的跌幅 ≈ 纯 α 效应；App／海外 超出它的部分 ≈ β 效应。**
2. **「风控规则没动」不是免责，是定位钥匙。** 规则不变而拒绝率 +0.3 pt，变量只能在这三处：① 特征缺失/失真（CDN 头部透传）→ 兜底拒绝；② 分母结构变化（大促新客/海外/新设备本身高危）→ 同一规则命中更多；③ 风控自身调用被拖慢 → 超时后默认拒绝。三者都**能在规则未改的前提下发生**，且 ②③ 还能同时解释 App/海外偏高。
3. **「厂商没有异常」与「后端只是加了一个查询」是同一类错误：用对自己有利的聚合口径证明局部无损。** 厂商 SLA 口径里不含「头部字段透传正确率」「跨境回源质量」「App SDK 兼容」；且**全量切换没有对照组**，它即使造成差异也测不出来。后端的「加一个查询」在 P50 上看不见，杀伤全在 P99。
4. **1.3 pt 的账必须能对上。** 风控拒单 +0.3 pt 是可直接相加项；剩下约 1.0 pt 若全部由 α 解释，则要求单次外部调用失败率从 ≈0.5% 翻到 ≈1.0%——与「网关超时率上升」同量级，**自洽**。若 v3.4 之前外部调用失败率本就 <0.2%，1.0 pt 就装不进 α，权重必须挪给 β（海外/App 的链路退化）。**这条数量级检验就是分离 α 与 β 权重的判据，也是唯一缺的基线数据。**

## L3 双根

### 处置根（修本次，按 Share×Lever÷Cost 排序）

1. **让 v3.4 第二跳并行化或异步化，并给它独立超时与熔断**（Lever：改架构｜Cost：一次灰度）。同一次灰度顺带完成归因：5% 流量看超时率是否回到基线——这是全题最便宜的实验。
2. **CDN B 按「地域 × 端」分层灰度回切 5~10%**，只盯两个数：风控拒绝原因码里「信息缺失/兜底」占比、海外 App 的网关超时率。**回切即归因，不需要原始日志。**
3. **补齐 +40% 对应的容量与限流/指数退避**（Lever：改配置｜Cost：一次扩容）：把 ρ 压回 0.7 以下，切断「超时→重试→更超时」的正反馈。
4. **用切片级分子/分母做辛普森分解（Kitagawa 分解）**：固定两周前的 mix，用今天各切片的成功率加权，得「纯恶化」；与总跌幅的差 = mix 漂移的伪跌幅。**不需要原始请求日志，只要各切片的成功数与总数还在。**

### 消解根（灭这一类）

**条件**：支付链路引入显式的「同步跳数预算 + 端到端时延/失败预算」契约；任何外部依赖变更（CDN／风控／下游）必须携带「头部与特征透传契约测试」与「全链路压测」才允许全量；成功率必须按（端 × 地域 × 依赖方 × 链路版本）四维常驻切片，并保留可加总的分子分母。

- **不可发生判据**：若当时采用，α 会在「跳数预算超限」处被拦下（v3.4 无法以串行方式上线）；β 会在「透传契约测试」处被拦下（头部失真不允许全量）；γ 会被「全链路压测 + 容量随流量同比例」吸收；「聚合口径下无法归因」被四维切片消掉。此时「多团队各自局部无损、却叠加出无法归因的跌幅」**在结构上不可能发生**，而不只是变少见。
- **可执行首边**：本周在发布门禁里加一条「支付链路端到端 P99 + 同步跳数」检查（从一次压测开始，可以很小）。
- **成本量级**：跳数预算 + 压测门禁 ≈ 人月级；四维切片埋点 ≈ 周级（指标系统已有分子分母，主要是加维度标签）；透传契约回归用例集 ≈ 周级。相对一次大促丢掉 1.3 pt 成功率的 GMV 量级，投入低一个数量级。
- **诚实交代**：消解根本不修本次跌幅，它把本次问题降级为「链路预算治理」清单里的一项。

## L4 迁移出口

1. **可观测性**：从聚合单值迁到四维切片 + 可加总分子分母；迁移前必须先冻结「成功」的定义（重试算不算、双调用怎么计）。
2. **依赖治理**：CDN／风控／下游的 SLA 口径必须包含「语义正确性」项（透传、特征完整性），否则「我们这边没有异常」永远成立。
3. **发布工程**：同步跳数预算、端到端时延门禁、大促期链路级变更冻结窗口。
4. **组织能力**：需要一个对整条链路总预算负责的跨团队角色／值班，否则类根不动。

→ **本次问题降级为第 3 项「发布工程—同步跳数预算」的一个违规实例。**

## 结论

根源是**结构的**：一条 P99 敏感、超时阈值固定、多团队并行变更的同步串行链路上，没有人对「总时延预算与总失败预算」负责。具体到本次——**α**：v3.4 把 1 个同步往返变成 2 个串行往返（失败率≈翻倍、时延相加、超时阈值未重算），是主因与放大器；**β**：CDN 全量切 B 同时改掉跨境链路质量与客户端特征透传语义，直接造出 0.3 pt 风控拒单与 App/海外的超额跌幅，是触发与差异化来源；**γ**：+40% 流量与无退避重试把它们非线性放大，并把 mix 推向高失败切片。

**要先做两件最便宜的事就能定量分离二者：v3.4 第二跳并行化灰度 + CDN 按地域/端分层回切。** 这两次实验各自带回一个数，α 与 β 的权重就定了——不需要原始日志，也不需要任何一方承认自己有异常。

## ⚠️ 异常 / 矛盾 / 空白

- **最大缺口**：「全量切 CDN」与「v3.4 发版」的**先后顺序与时间差**未给。若 v3.4 先上线且当时跌幅很小，β 是主因；若 CDN 切换当天就有小台阶、v3.4 后台阶变大，则是「β 铺路 + α 放大」。这两条断点的时间差是全题最重要的缺失量，建议优先补齐。
- 1.3 pt 的账只能用「外部调用失败率翻倍」配平 α 的 1.0 pt；v3.4 之前的外部失败率基线缺失，这是 α/β 权重分配的唯一数字缺口。
- 「风控拒绝率」与「成功率」的分母是否同源未说明：若前者以「网关受理请求」为分母、后者以「客户端发起请求」为分母，两者不可直接相减，0.3 pt 的可加性存疑（这不影响定性，但影响账目闭合）。
- 「大促流量 +40%」与「容量是否同比例扩容」未说明。若已扩容，γ 降为次要放大器；若未扩容，γ 可能是被低估的主因之一。

## ✅ 验证

按题面要求不采集任何本机/线上数据，本节只做两条**内部自洽性检验**：
1. 账目闭合：风控拒单 0.3 pt + 超时/失败 ≈1.0 pt = 1.3 pt，无剩余项。
2. 量级自洽：双调用使失败率 ≈2p，要产生 1.0 pt 需 p≈0.5%，与「网关超时率上升」同量级，无矛盾。若实测基线 p<0.2%，则本模型须把权重从 α 移到 β。

## 💡 灵感备注

- 这类事故的标准陷阱是「四个变更里挑一个凶手」。真正的判据不是谁看起来更可疑，而是**哪个变更落在时延预算的乘法项上**——加在串行链路上的一跳，永远不是加法。
- 一条比任何指标都便宜的通用判据：**若跌幅按「端 × 地域」分层后不齐，根在链路与特征采集；若齐，根在业务逻辑与下游。** 这一条能在一小时内决定调查方向。
