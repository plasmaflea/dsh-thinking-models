# 支付成功率 98.2% → 96.9%：根源定位

**[🌳 林状图]｜选择理由：** 问句是「根源在哪」，未知在**因果深度**而非选项广度，走回溯法。四个变更事件在时间上共线，且两个当事方各自给出「我这边没问题」的自证——这是典型的「症状全在漏斗末端、原因不可分辨」局面，正需要分层回溯把末端读数还原成跳级定位。

---

## L0 类别判定

**类别：** 主类 `software`（分布式支付链路）。判据：失败由代码/配置/边缘姿态决定，可复现，不来自物理介质。
**已排除：** 硬件故障（跌幅跨渠道跨地域同向、无校验错误类症状）、权限/账号体系（无 ACL/令牌类特有失败）。
**标为共类、不排除（只在汇合层合并）：** `network`（CDN 切边、海外段）、`org-process`（观测纪律、发布纪律、两方各自自证）。理由见挂起表。

## 选轴（生成式）

轴由**恒等式 + 必经时序**生成，不靠联想：

> 一次支付成功 ⇔ 链路上**每一跳**都在时延预算内返回成功且判定为放行。
> 各跳失败率远小于 1 时，**总失败率 ≈ Σ 各跳失败率**（这就是恒等式右边要切的因子）。

七跳（必经时序，一格不可省）：

| 跳 | 该跳在管什么 | 该跳故障的可观测症状 |
|---|---|---|
| H1 客户端→边缘 | DNS/TLS 握手/证书链/OCSP/静态资源与指纹 SDK | 客户端错误率高、按机型/系统版本/运营商分层陡增、**App 高于 Web** |
| H2 边缘→源站 | 回源成功率、连接复用、**头传递语义**（真实客户端 IP、UA、设备指纹头、cookie 域） | 回源 5xx/超时；风控侧看到「设备未知/地理不一致」；边缘自身大盘仍正常 |
| H3 网关/接入 | 限流、超时阈值、连接池/线程池 | **网关超时率上升**（这是读数，不是原因） |
| H4 业务编排 | v3.4 的两个同步调用、下游扇出、N+1 | p99 抬升而 p50 稳定；下游 QPS 翻倍；超时集中在慢请求 |
| H5 风控 | 同步决策调用、规则、**输入信号质量** | 拒绝率上升而**规则未变**；拒绝原因分布单向偏移 |
| H6 支付通道 | 收单行/卡组织/3DS 挑战、SCA 强制 | 海外>国内、按卡组织/发卡行分层陡增、拒绝码来自通道侧 |
| H7 结果回写与呈现 | 回调幂等、客户端轮询超时、重试 | 资金成功但页面显示失败；同单多次尝试（重试放大） |

正交性检验：H1 的症状（按客户端栈分层）不能解释 H4 的症状（p99 对两端等价），反之亦然；H6 的失败带通道侧拒绝码。三判据齐。

## L2 逐层回溯

### 第 0 层（先拆数字，否则「1.3 个点」没有定义）

- 失败率 1.8% → 3.1%，**+1.3pp，相对 +72%**；叠加 +40% 流量后，**失败事件绝对量 ×2.41**（1.8 → 4.34）。
- 风控拒绝 0.8% → 1.1%（+0.3pp）→ **最多解释跌幅的 23%**。
- 扣掉风控后的非风控失败：**1.0% → 2.0%，正好翻倍**。→ **跌幅的 77% 必须在超时/边缘/客户端/通道一侧，风控不是主项。**
- ⚠️ 这里有一处必须先证伪的口径污染：+40% 大促流量必然改变人群结构（新用户、海外、低端机、首次支付占比）。若各场景成功率都不变、只是权重变了，总体成功率照样掉——**Simpson 型虚假跌幅**。所以在做任何归因之前，「同比人群」重算必须先行（见处置根 T0）。未做这步之前，1.3pp 里有多少是「效率下降」本身未定义。

### 第 1 层（把四个「上升」还原成跳级）

用户手上已有的四项观测——网关超时率↑、风控拒绝率↑、App>Web、海外>国内——**没有一项是原因，全部是读数**：

- **网关超时率↑ → 落在 H3，但 H3 是报警器**：超时是所有上游（H1/H2/H4/H5/H6）变慢的总和。H3 只会告诉你「预算被吃光了」，不会告诉你谁吃的。
- **风控拒绝率↑ 而规则未变 → 落在 H5，且这是「输出」不是「输入」**：风控引擎是输入的纯函数。规则常量 + 输出分布偏移 ⇒ **输入分布或输入质量变了**。只有三个来源：流量结构变了（H5 的输入人群）、信号质量变差（H2 的头/指纹传递）、或有人来打（攻击流量）。**「风控拒绝率上升」不是独立原因，它必然归属于 H2、H4 之外的一条通道。**
- **App>Web** → 这是全题**判别力最强的一条**，见下。
- **海外>国内** → 判别力弱：H1（POP 距离/国际链路）、H2（回源）、H6（国际卡组织/SCA）三者都预测这一现象，无法区分。

### 第 2 层（正交切分：App>Web 免费砍掉一半候选）

> **v3.4 的第二个同步调用对 App 和 Web 是同一段后端代码，产生相同的时延增量。一个两端等价的变更，在数学上不可能产生 App 与 Web 的差异。**

因此：**后端 v3.4 单独不可能是唯一根**，主因链上**必须**存在「客户端侧 / 客户端到边缘 / 客户端特有调用序列」这一段——也就是 **CDN 切边（H1/H2）必须被算作参与者**，或 App 特有链路（App 每单多打接口、依赖指纹 SDK）在放大它。这是不花钱就能做的一次逻辑排除，直接决定了「CDN 说没异常」这句话在本案里最不可信。

反过来，**海外>国内**无法做同样的排除（三者同向预测），所以它是共因证据，不是定位证据。

### 第 3 层（三个变更如何汇合到同一处）

三者不是相加，而是**同时推进同一个数：贴着超时阈值 T 的请求密度**。

**超时阈值模型（决定量级，不是精确值）：** 令 `P_timeout = P(L > T)`，v3.4 把时延变为 `L' = L + d`，则
`ΔP ≈ f(T) · d`（f 为时延分布在 T 处的密度）。
若网关超时阈值本就压在 p99 附近（工程上极常见），尾部密度约 **0.5%/100ms**，则 **d ≈ 100ms 就产生 ≈0.5pp，d ≈ 200ms 就吃掉全部 1.0pp 缺口**。
→ **「只是加了一个查询」在阈值附近是乘性伤害：它不需要任何 bug，也不需要功能出错，单靠加性时延就能吃掉全部跌幅。** 这是本题最反直觉、也最常被两边团队同时漏掉的一点。

**队列放大模型（决定为什么是 1.3pp 而不是 0.3pp）：**
- 排队时延按 `ρ/(1−ρ)` 增长。原 ρ=0.6 → 流量 ×1.4 → ρ=0.84，等待时间放大约 **3.5×**；若原 ρ=0.7 → ρ=0.98，放大 **≈21×**。
- **+40% 流量在高利用率系统上不是 1.4 倍问题，是尾部延迟数十倍问题。** 它把 v3.4 那点加性时延的伤害从「几个 bp」放大到「一个点」。
- **重试正反馈**：超时 → 客户端/SDK 重试 → 每个重试同样携带两个同步调用 → 负载再涨（r=10% 时有效负载 +11%）→ 更多超时。这是 1.3pp 大于线性估算的第三个来源，也解释了「大促期间尾延迟为什么非线性塌陷」。

**汇合结论：** v3.4 提供了「推」、+40% 流量提供了「增益」、CDN 切边提供了「路径变差 + 信号损伤」、大促提供了「人群分母」。四者叠在同一条已经贴阈值的串行链路上——**所以 1.3pp 不是四个原因的加和，而是一个瓶颈被三方同时顶穿。**

### 类根（往上一层）

**类根：** 当一个系统的**尾延迟预算已经贴近超时阈值**、且**多个变更在同一时间窗内叠加进同一条串行链路**、同时**没有任何按维度可归因的证据**——这一组合必然产出「跌幅可见、归因不可行」的事件。三者缺一，问题不会以这种形态出现：有余量则加性时延无害；单变量变更则归因显然；有分层证据则四者立即可分。
**这就是为什么本案的根源不在「谁是元凶」，而在「这套系统在结构上不允许你找出元凶」。**

个例根挂在类根之下：

1. **v3.4 第二同步调用（主项贡献者）** — 唯一能单独量级覆盖 1.0pp 缺口的单一因素。
2. **+40% 流量（放大器，决定幅度）** — 抬高利用率，把加性时延的伤害乘性放大；重试构成正反馈。
3. **CDN A→B（必须存在的参与者）** — App>Web 无法被后端解释，所以这一段必然在因果链上；同时它是「规则未变而拒绝率上升」的最优解释（H2 头传递语义与客户端信号质量受损），也是海外>国内的最简解释。
4. **大促人群结构变化（分母污染，可能已吞掉相当份额）** — 最先量化，因为它决定其余三项各自还剩多少可解释空间。

**不是原因的：** 风控规则（未变）、网关超时（读数）、风控拒绝率（输出的读数）。

## L3 双根

### 处置根（修本次）：用「降价排除」替代「找元凶」，按成本从 0 起

按 `Share × Lever ÷ Cost` 排序，先做四个**零成本**的，再做两个**一次变更**的：

- **T0（成本≈0，且必须最先）：人群同质化重算。** 用两周前的分渠道/分地域权重，给**当前**的分场景成功率加权，看「同权重成功率」是否仍降 1.3pp。
  - 若仍降 ≥1.0pp → mix 被排除，是真实效率下降，继续 T1。
  - 若只剩 0.3–0.5pp → **1.3pp 里大半是人群结构变化，整个追凶方向要改**：问题从「链路变慢」变成「新增低基线人群（海外/低端机/首次支付）占比上升」。这一步不做，后面全部推断都建在未定义的分母上。
- **T1（成本≈0，判别力全题最强）：风控拒绝的「原因分布」。** 拒绝原因码直方图是**聚合指标，不是原始请求日志**——也就是说，这是「没有原始日志」条件下唯一仍然可用的高信息探针。分三叉：
  - 集中在「设备指纹缺失 / 设备 ID 不匹配 / IP 与地理不一致 / UA 异常」→ **H2 边缘信号传递被破坏 → CDN 切边实证**，且同时解释 App>Web（App 更依赖客户端指纹 SDK）。
  - 集中在「同卡多试 / 频次超限 / 代理 IP / 名单命中」→ **攻击或羊毛党**，与大促相关，与 v3.4、CDN 无关。
  - 各规则同比例平摊上升 → **人群结构（T0）或评分整体漂移**。
- **T2（成本≈0）：App/Web 内部对照。** 若 Web 基本持平、只有 App 掉，则同一条后端链路上 v3.4 不可能是主因，主因锁定在「客户端→边缘」段。**免费的正交检验。**
- **T3（成本≈0）：拐点形态判别。** 把 CDN 切点、v3.4 发布点、大促流量爬升点三个时刻对齐**小时级**失败率曲线（聚合指标本来就有时间维度——「没有原始日志」不等于「没有时间序列」）。
  - **阶跃且与某点严格重合** → 开关型因素（CDN 或 v3.4）。
  - **斜坡且随流量走** → 容量/队列型（R2 主导）。
  形态比数值更便宜也更难伪造。
- **T4（成本一次变更，唯一干净归因动作）：双 CDN 定向分流 1–5%。** 只把**海外**或只把 **App** 切回 A。海外失败率回落 → CDN 系主因被证实。这是四个候选里唯一能做成对照实验的。
- **T5（成本一次变更）：v3.4 第二调用的「半拆」。** 1% 流量走「并行化 / 给第二调用加 deadline / 临时关闭」分支，对比网关超时率；或离线注入 `d` 压测看 p99 是否越阈。回落即为实证。

### 消解根（灭这一类）：让「看得见跌幅、说不出原因」在结构上不可能

不是加监控看板，而是让**归因所需的证据在变更发生时就已存在**：

1. 每个请求贯穿 **trace id**（一次失败能还原成七跳里的具体一跳，而不是一个 500）。
2. **失败原因码按 hop 枚举**，强制带 beat（H1…H7），跨团队统一口径——这一条即使没有原始日志也能定位下次同类问题。
3. **1% 全字段分层采样**（按渠道/地域分层，不是纯哈希采样），替代「全量原始日志」（后者成本不可行）。
4. **指标预置维度**：渠道 × 地域 × 边缘节点 × 服务版本 × 各下游耗时分位——而不是只有一个总成功率。
5. **单变量发布 + 金丝雀 + 毒性指标自动回滚**；任何新增**同步** hop 必须从父请求既有 deadline 预算里扣（deadline 传播），并在压测门禁里过「p99 不越阈」。

- **不可发生判据：** 若两周前这五条已在，1.3pp 的跌幅会在**数小时内**被定位到唯一因素——甚至 v3.4 在灰度阶段就被金丝雀按「网关超时率」自动回滚，「多变更并发 + 零原始证据 + 两个厂商各自自证清白」这个局面在结构上不成立。这是消解而非缓解：它不只让本类问题变少见，而是让「不可归因」这一状态不可能存在。
- **可执行首边：** 在支付链路入口中间件里加 trace id 与**按跳枚举**的失败原因码，不动业务逻辑，约一天工程量。这是唯一一条今天就能落地、且直接消灭「下次还是查不出来」的边。
- **成本量级：** 单季度工程量级，不是换架构。存储增量 ≈ 全量的 1%（1% 采样）；在支付链路日请求 10^5–10^7 量级时，1.3pp 的效应量在 1% 采样下达到统计显著所需时间以**小时**计。主要成本在**组织**（失败码统一口径、发布纪律、跨团队认账），不在钱。

## L4 迁移出口（消解根指向观测与发布结构的改造，故必填）

1. **高基数维度爆炸**：渠道×地域×边缘×版本×分位一旦预置，指标基数会失控 → 需要基数治理与预聚合策略。
2. **采样代表性偏差**：纯哈希采样会系统性低估长尾客户端（正是海外/低端机这一群）→ 必须分层采样，否则新体系在最需要它的地方失效。
3. **PII 与合规**：支付链路采样日志含卡信息/设备标识，需脱敏与分域存储，合规成本真实存在。
4. **deadline 传播会暴露历史欠账**：一开传播，原本「能过」的慢下游会开始报错，等于把隐藏问题一次性翻出来 → 需分批推进并预留治理窗口。
5. **双 CDN 常态化**：切边不再是一次性项目而是持续能力，需要一致性测试与按地域/渠道灰度切流的常备手段。
6. → **本次问题降级为其中一项：** 「观测与归因能力缺失」——具体落在第 2 项（采样代表性）与第 1 项（基数治理）上；本次的 1.3pp 只是它的一个症状实例。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 硬件/物理介质 | 非根 | 跌幅跨渠道跨地域同向；无校验错误、无温度/负载相关随机性 | 出现跨进程随机失败、CRC/ECC 类错误、同程序时快时慢无规律 |
| 风控规则本身 | 非根 | 规则未变；且 +0.3pp 最多占跌幅 23% | 拒绝原因分布显示某条规则被新数据大量命中，且该规则存在未申报的热更新（阈值/名单库） |
| 网关超时率上升 | 非根（读数） | H3 是所有上游变慢的总和，无定位能力 | 若各下游耗时分位均未变化而仅网关侧超时上升 → 才反转为网关自身（连接池/限流参数）问题 |
| 风控拒绝率上升 | 非根（输出） | 风控是输入的纯函数，规则常量 + 输出偏移 ⇒ 输入变 | 若拒绝原因分布显示纯评分漂移且 H2 头传递经核验完好 → 独立为 H5 自身问题 |
| **CDN 厂商「我们这边没异常」** | 不可采信（自证） | 它只能看到边缘 5xx/回源/自身 POP；看不到客户端端到端（App TLS/证书链/OCSP）、看不到转发出去的**头与信号质量**、看不到其到源站/风控的 RTT 变化 | 提供三项外部可核验数据：头传递合规性（XFF/UA/指纹头原样性）、海外 POP 的 RTT 分位、客户端 TLS 握手失败率。任一不达标，自证即失效 |
| **后端「v3.4 只是加了一个查询」** | 不成立（加性思维） | 阈值附近加性时延 → 乘性失败率（`ΔP ≈ f(T)·d`）；同步调用消耗父请求预算，只在 p99 显形，单机 p50 压测看不见 | 注入压测证明 `d` 对 p99 无影响（即尾部密度在 T 处极低）→ 才可降为次要 |
| App>Web 差异 | 已用于排除 | 后端等价的变更不能产生两端差异 | 若 App 与 Web 走完全不同的后端端点且 App 端点独有第二调用 → 差异可由 v3.4 解释，本排除作废 |
| 海外>国内 差异 | 不能用于定位 | H1/H2/H6 三者同向预测，无判别力 | 拿到按地域的「最慢一跳」分解后，才具判别力 |
| **支付通道/收单行/卡组织/3DS·SCA（树外分支）** | 挂起（不可排除） | 海外>国内 也可由国际卡通道与 SCA 强制挑战解释；大促期间发卡行限流是常见独立原因；且该因素**不在用户列出的四件事里** | 按卡组织/收单行/3DS 结果码切分失败率；若通道侧拒绝码占比上升则升为主因之一 |
| **攻击/撞库/羊毛党（大促期）** | 挂起 | 可同时抬高拒绝率与网关负载，形成与本案同形的信号 | 拒绝原因分布集中在频次/同卡多试/代理 IP；请求频次与设备重复度高 |
| **人群结构 mix（Simpson 型虚假跌幅）** | 必须先量化 | +40% 流量必然改变人群权重；同权重重算未做前「1.3pp」含义未定义 | 同权重重算后仍降 ≥1.0pp → mix 排除 |
| v3.4 的隐性回归（N+1、连接池耗尽、连接复用退化、重试风暴） | 挂起 | 与 v3.4 同源，现有证据不可分 | v3.4 灰度回切实验中失败率回落 |
| 大促扩容是否到位 | 挂起 | 决定 R2 的 ρ 落在 0.6 还是 0.7 之后——两者的放大倍数差 6 倍 | 拿到大促前后各下游的利用率与连接池占用时序 |
| `network` 节点（树外，v2 候选） | 登记 | 现有树只有 software / win-service，本次主体在边缘与回源段 | 待 `network` 节点建成并核查后回填 |
| `org-process` 节点（树外，v2 候选） | 登记 | 「无原始日志 + 两方各自自证」属组织观测纪律，software 六子层覆盖不到 | 待建成后回填；本轮的消解根即其雏形 |
| `win-service` 节点 | 不适用 | 无进程初始化/加载器类症状 | 若后续发现服务启动失败则重启本支 |

## 结论

**根源不是一个，是一个结构 + 一条主链。**

结构层（真正的根）：**尾延迟预算已经贴着网关超时阈值 + 四类变更在同一两周内叠加进同一条串行链路 + 全链路没有任何按维度可归因的原始证据。** 前两条决定了「一定会掉」，第三条决定了「一定查不出来」。这也是为什么两边团队都能诚实地说「我这没问题」而问题依然存在——**他们的自证在结构上就是不可证伪的**：CDN 只看得到自己边缘的 5xx，看不到客户端端到端与头传递；后端用「只加了一个查询」做加性推理，而阈值附近的加性时延是乘性伤害。

主链（本次机制）：**v3.4 的第二个同步调用把时延加性推进尾部窗口（能量级覆盖全部 1.0pp 缺口，无需任何 bug）→ +40% 流量把利用率推高、排队按 ρ/(1−ρ) 超线性放大、超时触发重试构成正反馈（把 0.3pp 放大成 1.3pp）→ CDN 切边同时恶化客户端/海外路径与头传递语义（这是 App>Web 无法被后端解释的唯一出路，也是「规则没变而拒绝率升」的最优解释）→ 大促人群结构变化污染了分母本身。风控规则不是原因，风控拒绝率和网关超时率都不是原因——它们是读数。**

三句话版本：
1. **别找元凶，先做四个零成本判别**——同人群重算（是不是假的 1.3pp）、风控拒绝**原因分布**（是不是边缘信号损伤或有人在打）、App/Web 内部对照（v3.4 已被逻辑排除为主因）、拐点形态（阶跃=开关型，斜坡=容量型）。
2. **主项大概率是 v3.4 加的那一跳，放大器是 40% 流量，CDN 切边必然在因果链上**（App>Web 这条免费证据已经把后端单独为根的可能性砍掉）；风控拒绝率上升是结果，不是原因。
3. **真正的根是归因能力缺失**：trace id + 按跳枚举的失败原因码 + 1% 分层采样 + 预置维度 + 单变量发布与 deadline 传播。这些不做，下一次换一批事件，会得到一模一样的一场会议。

## ⚠️ 异常 / 矛盾 / 空白

1. **「没有原始请求日志」与「有一堆聚合指标」并存**——说明有指标采集但无请求级证据。**聚合指标本身有时间维度与拒绝原因维度**，这两者都不属于「原始请求日志」，却足以完成第 1 步判别。这是本案最大的信息浪费。
2. **「风控规则没动过但拒绝率升」被当成第四个独立事件**——它不是事件，它是另外三个事件的**输出**。把它当平行原因，是本案最容易走偏的一步。
3. **App>Web 与「后端只加了个查询」在同一套叙述里互相矛盾**——两端等价的变更不可能产生两端差异。这个矛盾目前被「所有指标都是聚合的」这句话掩盖了。
4. **海外>国内 被当作定位证据使用，实际无判别力**（边缘/回源/通道三者同向）。
5. **空白：支付通道侧（收单行/卡组织/3DS）完全没有出现在已查清单里**，而它是最能独立解释「海外失败率高」的一项，且大促期发卡行限流是行业常态。这是一个未登记的候选。
6. **空白：扩容是否到位未知**——ρ 从 0.6 到 0.7，队列放大倍数相差约 6 倍，这个参数决定「流量是共因还是主因」。
