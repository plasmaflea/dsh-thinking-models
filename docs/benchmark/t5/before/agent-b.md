# 支付成功率 98.2% → 96.9%：根源判断

## 结论

主因是 **v3.4 把一次支付请求拆成两个串行同步调用**。它把单次请求的"超时暴露"从 1 次变成 2 次，把尾部延迟从单段分布变成两段分布的叠加；在固定超时阈值下，与超时相关的失败率**近似翻倍**，贡献约 **1.0 个百分点**（占 1.3 个点总跌幅的约 3/4）。

次因是风控拒绝率 +0.3 个点，但它**不是"规则变严"**。规则没动，说明变的是**输入或分母**：大促流量结构变化（新客、海外、App、单设备多笔占比上升）让同一套规则命中更多；同时 CDN A→B 很可能改变了后端看到的**客户端 IP / 地域信号**（回源 IP、X-Forwarded-For 透传、GeoIP 库），造成以海外为主的假拒绝。

CDN 切换和 40% 流量增长是**放大器与混杂项**，不是独立主因：它们抬高延迟、把系统推进排队与超时的非线性区，并改变流量构成。**"CDN 厂商说没异常"和"v3.4 只是加了一个查询"可以同时为真，却与上述结论不矛盾**——前者只看自己的边缘指标，看不到端到端支付成功率；后者恰恰就是问题本身：在关键路径上加一个同步调用，从来不是"只是"。

---

## 一、先把 1.3 个点拆开：最硬的信号是"非风控失败恰好翻倍"

失败率 1.8% → 3.1%（相对上升 72%）。风控拒绝 0.8% → 1.1%。若风控拒绝计入失败，则**非风控失败** 1.0% → 2.0%，**正好乘 2**。

什么变更会把一个失败率精确乘以 2？两个**独立**的超时机会：

    P(整体超时) = 1 − (1 − p)² ≈ 2p      （p 为单次调用超时概率）

p≈1% 时 1−(1−p)² = 1.99%，与 2p 的误差只有 0.01 个点。v3.4"一次请求拆成两个同步调用"正好提供这个结构：

- 若网关超时**按调用**计 → 失败概率 ≈ 2p；
- 若网关超时**按端到端**计 → 两段延迟串行相加、方差相加（σ²→2σ²，尾部标准差 ×√2），而超时由尾部决定，所以超时率的涨幅会**大于**平均延迟的涨幅。

两种口径下结论一致：**串行化把尾部推向阈值**。反过来看另外三个变量——40% 流量能把超时推高，但涨幅取决于利用率落在排队曲线的哪一段，很难正好落在 2.00×；CDN 切换改变握手与路由，通常表现为连接类错误和延迟整体平移，也不天然给出干净的 2×。**只有"调用次数从 1 变 2"天然给出 2×。**

必须说明边界：上面的等式是**高度自洽，不是证明**。非风控失败里还混着银行拒付、3DS 失败、客户端错误，真实 p 小于 1%，翻倍项会小于 1.0 个点，差额由流量/CDN 抬升的延迟补齐。但归因方向不受影响。

## 二、"App > Web、海外 > 国内"是超时机制的指纹

- **App**：无线侧 RTT 抖动大、切网/弱网、前后台切换、SDK 重试，尾部本来就长。超时是尾部敏感型失败，对 App 的惩罚天然更大。
- **海外**：跨境 RTT、CDN B 的海外回源路由、TLS 握手往返次数，单次超时概率 p 本来就高；串行化后 1−(1−p)² 在 p 大时绝对增量更大（p=5% 时是 9.75%，增量是国内的数倍）。
- **国内/Web**：p 小，同样翻倍后绝对增量小，所以看起来"没事"。

风控假阳性也会造成海外偏高（GeoIP 误判），但它解释不了"App > Web"这么整齐的梯度——App 和 Web 的 IP 归属通常一致，差异在链路质量。**两个梯度同时出现，说明至少两个机制在叠加**：超时解释 App/海外，信号失真解释海外/风控。

## 三、风控那 0.3 个点：规则没变，变的是喂给规则的输入

规则不变而拒绝率上升 37.5%，只有三种可能，且会在数据里留下不同指纹：

1. **人群变了（暴露变化）**：大促 +40% 流量不是均匀的，通常新客、海外、App、单设备多笔（velocity）占比上升，同一套规则命中率自然上升。这是正确行为，不是 bug。
2. **信号坏了（假阳性）**：CDN B 若不透传真实客户端 IP、或用不同回源网段/GeoIP 库，风控会看到"机房 IP、共享出口、地域不符"，直接触发高风险规则。指纹是**海外集中，且被拒样本的 IP 落在 CDN B 回源段/机房 ASN、IP 归属地与申报地域矛盾**。
3. **评估口径变了**：如果 v3.4 新增的那个"查询"本身就是风控/画像类调用，它可能扩大了风控的评估覆盖（以前不查的场景现在查了），或改了传入上下文（设备指纹、session 丢失）。规则一个字没改，拒绝率的分子分母却都变了——这是"指标口径随发版漂移"的经典陷阱。

第 3 条应当先查：**先确认这两个指标的分母在 v3.4 前后是否还是同一个东西**。如果"网关超时率"从"每请求"变成"每上游调用"，它上升是算术必然，不是劣化。

## 四、CDN 与 40% 流量：放大器，不是主犯

- **CDN**：厂商的"无异常"只覆盖它自己的边缘可用性、5xx、缓存命中，**看不到端到端支付成功率**。一次"健康"的 CDN 切换完全可以：抬高海外回源 RTT、改变 TLS 会话复用率、改变客户端 IP 透传、把流量导到不同出口 ASN。它的作用通过**延迟**（喂给超时）和**信号**（喂给风控）间接体现，而不是自己报错。所以"厂商说没异常"只说明"不是 CDN 的可用性故障"，不构成排除。
- **40% 流量**：在接近饱和的链路上，利用率上升会让排队延迟**超线性**增长，固定超时阈值把延迟增长直接翻译成超时增长。再叠加客户端/网关重试——串行化已经把每次请求的失败机会翻倍，重试又把流量再放大一轮，形成"超时→重试→更拥塞→更多超时"的正反馈。这就是为什么 40% 流量能撬动 1.3 个点，而不是按比例撬动 0.5 个点。

## 五、聚合数据还留了一个必须排除的解释：结构性漂移（Simpson）

全部指标聚合，意味着**整体成功率下降不等于任何一段变差**。如果大促把流量结构推向低成功率的段（海外、App、新客），整体会掉，而每个分群的失败率纹丝不动——这和"真实劣化"在聚合曲线上长得一模一样。

好消息是他们**已有 App/Web、海外/国内的分群失败率**，现在就能做**直接标准化**——用两周前的分群流量权重，加权两周后的分群失败率：

    成功率_标准化 = Σ wᵢ(旧) × 成功率ᵢ(新)

- 标准化后仍 ≈96.9% → 真实劣化，按第一、二节归因；
- 回到 ≈98.2% → 跌幅主要是结构漂移，要修的是流量结构而非某个 bug；
- 落在中间 → 差额就是 mix 与 regression 的比例。

这一步不需要任何原始日志，只需要已有的聚合分群数据。

## 六、所以"根源"分三层

- **直接根因（可修复、贡献最大）**：v3.4 在支付关键路径上引入**串行同步依赖**，且没有为新增依赖单独设超时/降级/并行化。失败概率对串行依赖近似**相加**，延迟对串行依赖是**方差叠加**，而超时只看尾部——"加一个查询"在数学上等于"把超时暴露翻倍"。
- **触发与放大**：CDN A→B 改变了延迟分布与客户端 IP/地域信号；大促 40% 流量把系统推进排队非线性区并改变人群结构。三者不是相加，是在阈值附近**相乘**。
- **元根因（为什么两周定不了位）**：只有聚合指标、无原始请求日志、无端到端 trace、无"版本 × CDN × 平台 × 地域 × 时间"的交叉维度；每个团队都在用自己的局部指标自证清白，而局部指标全是真的。**观测粒度低于故障粒度，这才是这次事故真正的"根源"。**

## 七、不补日志也能做的判定（按性价比排序）

1. **日级成功率曲线对齐四次变更的时间点**：变更不同日，台阶位置直接指认主犯；同日则看台阶陡度（CDN 切换是阶跃，流量是渐进，发版是发布窗口内的阶跃）。
2. **确认两个指标的分母/口径在 v3.4 前后是否一致**（每请求 vs 每调用、风控评估覆盖范围）。
3. **直接标准化**（第五节），先分清 mix 与 regression。
4. **查 CDN B 的真实客户端 IP 透传**：被拒样本的 IP 是否落在 CDN B 回源段/机房 ASN、GeoIP 与申报地域是否矛盾。这一条能一次判定风控是"真严"还是"看错了"。
5. **拿 v3.4 单调用版本对比延迟分布**：若双调用 P99 ≈ 两倍单调用（或尾部质量显著右移），超时翻倍机制即被证实。
6. 若还有灰度/分批切换窗口，直接用 A/B 对照——这是唯一能干净分离 CDN 与 v3.4 的机会。

## 一句话

根源不在"谁有异常"，而在于：**支付关键路径被改成串行双调用，恰好撞上 CDN 切换抬高的尾部延迟和 40% 流量带来的拥塞，延迟被放大成超时（约 1.0 个点）；同时 CDN 改变或稀释了风控赖以判断的 IP 与地域信号（约 0.3 个点）。而全聚合、无原始日志的观测体系让这三件事无法分离，于是每家都能拿出真实数据证明"我没问题"。**
