# 支付成功率 98.2% → 96.9%：根源在哪

## 0. 结论先说

**技术根因（最可能）**：v3.4 把支付主链路从"一次同步调用"改成"两次**串行**同步调用"，在没有任何延迟预算、失败域预算、容量预算的前提下新增了一个串行依赖。大促 +40% 流量把这条链路推过了延迟拐点，**网关超时率上升就是最直接的证据**（超时是延迟的函数，不是网络错误的函数）。超时再触发重试，重试同时放大分母和负载，形成正反馈——这解释了为什么是"两周内缓慢流血"而不是一次干净的事故。

**风控拒绝率 0.8% → 1.1% 是结果，不是原因。** 规则没动而拒绝率涨，只有两种可能：① 进来的人变了（大促新客 / 海外用户 / 首单用户没有历史，本来就该被拒更多）；② 喂给风控的**输入信号变了**（v3.4 新增的那个"查询"就是特征查询，一超时特征就缺失，风控 fail-closed 走保守默认）。两种都指向"上游变了"，而不是"策略变了"。

**CDN 全量切换是同一时间窗里的放大器，不是主因。** 它为每个请求多加一拍（新 POP、新 peering、新 TLS 握手、HTTP/2-3 支持度、证书链），在 App（DNS 长缓存、超时更短、可能证书固定）和海外（跨境 RTT 本来就贴着超时预算）上**最先击穿预算**——这恰好解释"App 比 Web 差、海外比国内差"。但请注意：**这两条不能用来指认 CDN**，因为如果机制是"延迟增量吃掉了余量"，那么"App 和海外先失败"是这个机制的必然预测，跟延迟增量来自 CDN 还是来自 v3.4 无关。它们是**同向证据，不是区分证据**。

**组织性根因（真正让这个问题谈不拢的那个）**：四个变更叠在一个流量峰值窗口上，而唯一观测手段是聚合指标、且没有请求级关联。四个变量完全共线（同一时间、同一群人、同一批流量），任何归因都只能是叙事而不是证据。这就是为什么两个团队都能**真诚地**说没问题——厂商的仪表盘看的是它自己的可用性/5xx/缓存命中，后端的仪表盘看的是自己的错误率；**你要的那个量（端到端 p99 与跨跳归属）不在任何一方的 SLO 里**。

**一句话**：根因不是"某一次变更"，而是"在峰值窗口把四个变更叠在一起，其中一个吃掉了支付链路的延迟与失败余量，而系统完全没有能力在请求粒度上证明是谁吃掉的"。

## 1. 先把数字翻译成可比较的量

- 成功率 98.2% → 96.9%，即失败率 **1.8% → 3.1%**，**相对恶化 +72%**。这个幅度远大于"1.3 个点"给人的直觉，不能用"正常波动"解释。
- 风控拒绝 0.8% → 1.1%，**+0.3pp（相对 +37.5%）**，占 1.3pp 的 **23%**。
- 剩下 **≈1.0pp**（相对 +56%）必须由超时 / 网络 / 后端解释。
- 流量 +40%：如果系统原本只有约 15% 的容量余量，利用率被推过 0.9 之后，排队延迟是**超线性**上升的（ρ=0.85→0.95，队列等待时间可以涨到 3 倍以上）。也就是说：**40% 的流量增长，足以在一条已经贴着超时阈值的链路上造成 50% 以上的相对失败增长**，而不需要任何新 bug。

**先确认两个口径，否则上面这笔账算错**：
1. **被风控拒绝的请求，算不算进"失败"？算不算进分母？** 如果算，则 0.3pp 是"算术"，剩下 1.0pp 才是"系统退化"；如果不算，则风控信号是正交的另一条线，1.3pp 全部在别处，而拒绝率上升是同一个上游变化的第二个症状。
2. **分母是"请求/尝试"还是"用户/订单"？重试算一次还是两次？** 这是本题最容易被忽略、也最可能直接改答案的一条：如果改成"用户 N 次内成功"，很有可能只掉 0.2~0.4pp。那说明相当一部分"下降"是**重试把尝试数放大了**造成的观感，而不是真实用户付不了款。

## 2. 五条"已经看过的"信号，哪些有定位力

| 信号 | 定位力 | 为什么 |
|---|---|---|
| 网关超时率上升 | **强** | 超时是延迟的尾部。这是唯一一条能把 ①②③ 串进同一个机制的信号：多一跳同步调用（+延迟、+失败域）、流量 +40%（排队延迟非线性）、换 CDN（+RTT/TLS）。它几乎排除"纯业务逻辑 bug"——逻辑 bug 给的是错误码，不是超时。 |
| 风控拒绝率上升 | **弱（是症状）** | 规则没变而比例变了 ⇒ 变量在"人"和"输入"上，不在"策略"上。 |
| App 失败率 > Web | **弱，且是陷阱** | 移动网络 RTT 更高、客户端超时更短、可能证书固定——这个差值在大促前大概率就存在。**跨段比较绝对值不能归因，只能同段对比自身基线（DiD）**。正确问题是"各段各自退化了多少"，不是"谁更差"。 |
| 海外失败率 > 国内 | **弱，且是陷阱** | 同上。跨境 RTT、支付方式、3DS 流程本来就更差。 |
| 厂商说"没异常" / 后端说"只是加了一个查询" | **无效（不可证伪）** | 两句都在各自 SLO 里为真，且都不覆盖你要的量。厂商"无异常"= 边缘 5xx / 可用性 / 缓存命中正常，**不包含客户端侧 RTT 尾部、跨境 peering、TLS 握手时间**；后端"只是加了一个查询"恰恰是最可疑的一句——**一个同步关键路径上的新依赖从来不是"只是"**：可用性相乘（0.999×0.999）、p99 相加、新超时源、新连接池、新缓存失效面。 |

## 3. 机制链（最可能的因果路径）

1. v3.4 在支付关键路径上插入第二个串行同步调用 → 单请求 p99 抬升 Δt，并新增一个独立失败域。
2. 大促流量 +40%，且新增流量多为冷用户（冷缓存、冷连接池、冷特征）→ 下游利用率越过拐点 → Δt 被非线性放大。
3. 尾延迟击穿网关/客户端的固定超时阈值 → **网关超时率上升**、客户端侧失败上升。
4. 超时触发网关/App SDK 重试 → ① 成功率分母被放大（同一批用户，指标更差）② 重试继续加压，回到第 2 步，**正反馈**。这解释了"两周缓慢下滑"的斜率。
5. 那条新增查询如果同时是风控的特征来源 → 超时 = 特征缺失 → 风控 fail-closed → 拒绝率 0.8%→1.1%。**规则确实没改，改的是喂进去的东西。**
6. CDN 切换在每个请求上再加一拍 RTT 与一次新握手，压缩了本已变薄的预算；App 与海外是**预算最薄**的两端，于是最先失败——不是因为 CDN"坏了"，而是因为它把余量拿走的那部分正好是它们仅剩的。

**"两周缓降"这个形状本身就是证据**：CDN 配置错误和代码逻辑 bug 都是**台阶**（切流/发版那一刻跳一下）；而两周内随流量一起爬升的斜坡，是**容量/资源/重试型正反馈**的特征（连接池耗尽、线程池排队、缓存冷启动、数据量增长导致索引退化）。请先确认它是斜坡还是台阶——这一条不需要任何原始日志，只需要 14 天的**天级/小时级**曲线，而且它能一次性砍掉一半的假设。

## 4. 为什么用现有数据永远定不了案

- 四个变量共线：同一时间窗、同一批流量、无请求级关联 ⇒ 只能做加法叙事，不能做减法归因。
- **平均值看不见尾部**：成功率、超时率如果是整体比率/均值，p99 的退化会被 p50 淹没。而超时 100% 是尾部事件。
- 分母口径不明（见 §1），"1.3pp"里有多少是算术变动没人说得清。
- 每方只测自己的 SLO：CDN 测边缘可用性，后端测自身错误率，**没有人测"端到端一次支付由哪一跳贡献了多少延迟"**。这就是为什么"都正常"和"成功率掉了"可以同时为真。

## 5. 不依赖原始业务日志也能定案的最小动作（按性价比排序）

1. **用灰度窗口做自然实验（最高性价比）**：v3.4 几乎不可能原子全量发布。查发布记录里新旧版本并存的时段，把成功率按 `backend_version` 切一刀：
   - 灰度期新旧版本**同幅下降** ⇒ 排除 v3.4，矛头转向 CDN / 容量；
   - 只有 v3.4 下降、旧版本平 ⇒ 定案，10 分钟结束。
   这一步只需要发布时刻表 + 两条曲线，不需要一条原始日志。
2. **变化点分析**：14 天按小时画成功率 + 超时率，把 ①②③ 的时刻标上去。看台阶在哪一刻：
   - 台阶在切流时刻 → CDN；
   - 台阶在发版时刻 → v3.4；
   - 与流量曲线同形的斜坡 → 容量；
   - 三步都不是、只有大促开始那一刻起跳 → 人群结构。
   四种形状不同，肉眼可分。
3. **同段 DiD（差分中的差分）**：`App/Web × 国内/海外 × 新客/老客 × 支付方式 × ISP/POP`，每格对自己的基线求差。
   - 退化**集中在**某些格子（如海外 × App × 某 ISP/POP）→ 指向 CDN 路由；
   - 所有格子**均匀**退化约 1.0pp → 指向全局路径（后端/网关）；
   - 老客不动、只有新客掉 → 是人群结构 + 冷启动，不是系统坏了。
4. **先去找接入层日志**：业务侧原始请求日志没了，但网关 / Nginx / ALB / APM 的访问日志通常还在（一般保留 7~30 天），里面通常有 `client_ip`、`UA`、`upstream_response_time`、`status`、`request_id`。这一层足以重建"App/Web × 国内/海外 × ISP"的交叉切片，还能把 p99 拆成"网关排队 / 第一跳 / 第二跳 / 回程"——**第二个同步调用会在"第二跳"这一列上自己暴露出来**。先去确认这一层是否真的不存在：它决定你是"能定案"还是"只能叙事"。
5. **向厂商要指定切片，而不是问"有没有异常"**：要"本域名过去 14 天，按国家 × POP 的 p99 TLS 握手时间、TTFB、5xx 率"。他们的"无异常"是对**全舰队**说的，你要的是**你那一条路由**的尾部分布。同理向后端要 APM 的按版本事务曲线。
6. **一次只动一个变量的回滚实验**：把 5% 流量切回 CDN A（或回滚 v3.4 的一小批），看成功率是否回弹。20 分钟出结论，比继续开会便宜得多。**千万别同时动两个。**
7. **验风控**：把被拒请求按"落到了哪个分支"计数（正常评分 vs 特征缺失/超时降级）。若大量落在缺失分支 ⇒ 证明是 fail-closed，不是人群变化，同时反证 v3.4 的新查询在关键路径上。

## 6. 我可能错在哪（可证伪点）

| 假设 | 预测的切片特征 | 预测的时间形状 | 什么能推翻它 |
|---|---|---|---|
| **v3.4 串行调用**（主假设） | 全机型、全地域**均匀**退化 | 发版时刻台阶，之后随流量放大 | 灰度期旧版本同幅下降 ⇒ 推翻 |
| **CDN B** | 集中在特定 POP/ISP/国家；国内 Web 基本不动；握手/TLS 类失败突出 | 切流时刻台阶 | 国内 Web 与海外同步等幅下降 ⇒ 推翻 |
| **容量/延迟拐点** | 与流量曲线同形；p99 先动、p50 后动；各段均匀 | 两周斜坡 | 流量回落后**不自愈** ⇒ 需要另有解释（数据增长/泄漏/配置） |
| **人群结构**（非系统退化） | 老客成功率不变，新客/海外占比上升 | 与新增流量同形 | 老客成功率也同步下降 ⇒ 推翻 |
| **风控 fail-closed** | 拒绝集中在"特征缺失/超时降级"分支 | 随新查询延迟同步上升 | 拒绝集中在正常评分分支 ⇒ 是人群变化而非依赖降级 |

**最可能的替代解释**：如果变化点分析显示台阶精确落在切流那一刻，且 DiD 显示国内 Web 纹丝不动，那么 CDN 才是主因、v3.4 清白——但那时超时→重试的正反馈仍然成立，只是从"主因"降为"放大器"。所以无论哪种，**超时与重试这条链都要先掐掉**（给新增调用设独立超时与熔断、网关对支付接口禁用无脑重试、给重试加退避与次数上限），因为它是唯一会让"1.3pp 自己长大"的机制。

## 7. 落地建议（按顺序）

1. **今天**：确认口径（拒绝是否计入、重试是否计入），把成功率同时算成"请求成功率"和"用户 N 次内成功率"两个版本，看 1.3pp 缩水多少。这一步可能直接把问题缩小一半。
2. **今天**：拉 14 天小时级曲线 + 发布/切流时刻表，做变化点分析，判断台阶还是斜坡。
3. **24 小时内**：拿到 `backend_version` 维度的成功率（灰度自然实验）+ 接入层日志的交叉切片。
4. **结构性修复**：给新增的同步调用独立超时、熔断、异步化或批量合并（支付链路不允许"只是加一个查询"）；风控对特征缺失必须显式 fail-open 或降级评分，而不是静默变严；网关对非幂等的支付请求禁止自动重试。
5. **长期**：`request_id` 全链路贯穿、按跳耗时的 p50/p90/p99 看板、大促前变更冻结与灰度门禁、以及"一次只上一个变更"。这次的真正教训是：**四个变更叠在一个峰值上，等于主动放弃了归因能力。**
