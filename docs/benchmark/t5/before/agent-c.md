# 支付成功率 98.2% → 96.9% 归因

## 结论（先给判断）

根源不是四个并列的原因，而是 **② × ③ 的乘积**：v3.4 把支付主链路从「1 次串行远程调用」改成「2 次同步调用」，在一周内把这条链路的串行服务时间、连接/线程占用时长、以及"超时抽签次数"都放大约一倍；同期 +40% 的大促流量把系统利用率推过了排队拐点，于是**「变慢」以非线性方式转成了「超时」**。①CDN 被「App 失败率高于 Web」这个方向证伪；④风控拒绝率上升不是规则问题，而是大促人群结构漂移 + 超时后被 fail-closed 记成拒绝，它是症状，不是原因。

我的下注（不互斥，允许叠加）：

| 假设 | 权重 | 一句话 |
|---|---|---|
| H1 v3.4 双同步调用 × 流量拐点 | ~65% | 串行依赖翻倍把 ρ 推过 1，延迟→超时的相变 |
| H2 海外方向 CDN B 边缘覆盖劣化 | ~15% | 唯一还能替 CDN 说话的证据，需交叉表判定 |
| H3 纯人群结构漂移（Simpson） | ~15% | 新客/跨境/App 占比上升，群体内成功率其实没变 |
| H4 其他共享依赖劣化 | ~5% | 兜底 |

**H1 + H3 很可能同时成立**：前者解释 1.0pp 的工程退化，后者解释那 0.3pp 的风控拒绝。

## 一、先把 1.3pp 拆开（算术层面，这步不做后面全是猜）

- 成功率 98.2% → 96.9%，等价于**失败率 1.8% → 3.1%**，相对恶化 **+72%**。这不是"1.3 个点"这种听上去温和的量级，而是失败量翻了将近一倍。
- 风控拒绝 0.8% → 1.1%，吃掉 **0.3pp（23%）**。
- 剩下 **1.0pp（77%）** 必须由非风控的失败解释——「网关超时率上升」正好落在这一格。
- **前提校验**：0.3 与 1.0 必须同源（同一时间窗、同一分母、风控拒绝是否计入失败）。口径不一致时这个拆解直接作废。

一个量级上很漂亮的吻合：**新增一个串行依赖，它自身的失败/超时率只要 ≈1%，就足以解释那 1.0pp**，完全不需要出现"大故障"或"某个服务挂掉"。

## 二、四条「已看过的证据」，两条指向 v3.4，两条是假线索

这是本题最容易踩的坑：**四条观测是同一个原因的并发症状，彼此不独立**。把它们当成四个证据，等于把同一个原因数了四遍。

**① 网关超时率上升 —— 是结果，不是原因，而且在替真正的现场背锅。**
网关的超时阈值是固定的。后端 P99 抬高后，请求在网关→服务的排队等待里被提前掐断，**被超时截断的请求不会在后端留下慢日志**。这正好解释了为什么后端团队能真诚地说「v3.4 只是加了一个查询、我们服务没异常」：他们在看自己服务的 SLO 和平均耗时，而伤害发生在他们看不见的排队等待和客户端一侧。**用平均耗时自证清白，是典型的用均值掩盖尾部。**

**② App 失败率高于 Web —— 这条反向排除 CDN，正向锁定延迟。**
CDN 服务的是静态资源，Web 端对 CDN 的依赖远高于原生 App。如果 CDN B 有问题，**应该是 Web 更差**，实际相反。同时 App 的客户端超时更短、弱网更差，**对延迟抬升最敏感**——延迟一涨，App 第一个被打穿。所以这条不是"一个原因"，它是 H1 的放大器证据。

**③ 海外失败率高于国内 —— 同样是 H1 的放大器，不是独立原因。**
跨境 RTT 本身就高（+150~300ms），再多一次完整 RTT，受害最重的必然是海外。**加一个同步调用 = 海外多付一次跨境往返 + 多一次超时抽签**。
唯一还需要替 CDN 保留的可能性：**CDN B 的海外边缘覆盖确实可能劣化**。但这需要 device × geo 交叉表才能和 ② 分开——而交叉表恰恰是聚合指标没有的东西（如果"海外"和"App"人群高度重叠，②③ 其实是同一条证据）。

**④ 风控规则没动、拒绝率却涨 —— 规则不变 ≠ 拒绝率不变。**
拒绝率 = f(规则, 人群分布, 上游失败时的降级行为)。两个候选机制：
- **(a) 人群漂移**：大促拉来的新客、低 history、跨境用户打分天然偏高。**这是策略按设计生效，属于 mix shift，不是故障**，也不该算进工程退化预算。
- **(b) fail-closed 记账**：风控调用超时 → 按策略拒绝 → 在报表上被记成「风控拒绝」。**于是同一批失败在「网关超时」和「风控拒绝」两个桶里各记了一次**。
- 还有个放大器：v3.4 多占一份连接/线程/DB 连接池，连接池耗尽会拖慢同进程的其他出向调用，**包括风控调用**。一个原因，四个症状。

判定方法很便宜：看被拒请求的 **reason code 分布**和**新客占比随时间的变化**。reason code 全是超时类 → (b)；新客占比同步抬升 → (a)。

**关于两句"我们这边没问题"**：CDN 厂商只看得到自己的 5xx，看不到回源、跨境劣化、以及特定 ASN/运营商的边缘节点退化；后端只看得到自己进程内的耗时。两句都是真话，但都是**在自己看不见伤害的口径下说的真话**，不能作为证据使用。

## 三、机制：为什么"只加了一个查询"能吃掉 1pp

四条独立成立、互相叠加的机制，任何一条单独都不致命，合起来正好 1pp 量级：

1. **可用性相乘**：原来 1 个串行依赖，现在 2 个。可用性从 `A` 变成 `A₁×A₂`。两条 99% 的依赖串起来就是 98.01%——**单是这一步就凭空造出 ≈1pp 的失败**，与我们拆出来的残差严丝合缝。
2. **超时抽签次数翻倍**：原来单次超时概率 p，现在 `1-(1-p)² ≈ 2p`。**容量完全不变，超时率也近似翻倍。**
3. **排队论相变（这是把 1pp 变成"掉得莫名其妙"的关键）**：ρ = λ·S。λ 被 +40% 流量抬到 1.4×，S 因串行化抬到约 2×，**ρ 变成约 2.8×**。原来 ρ≈0.5–0.6 很安全，现在越过 1；利用率一旦 >1，延迟从"随负载线性"变成"垂直墙"，**超时率是阶跃式爆发的**。这解释了最迷惑人的现象：没有任何单个变更看起来像能造成故障，但成功率就是掉了，而且**掉得不均匀**。
4. **重试正反馈**：客户端/网关自动重试 × 延迟上升 = 放大回路，把 1.3pp 变成自持的。

**两个必须强调的推论**：
- **均值不重要，P99 才是唯一变量**。新增查询"平均只加 20ms"完全可能同时"P99 加 800ms"——存储层的锁竞争、连接池排队、buffer pool 命中率下降在流量 +40% 后都会让尾部变肥。超时只由尾部决定。
- **②和③是乘法关系，不是加法关系**。+40% 流量单独一般吃不掉 1.3pp，**除非系统已经在拐点边缘**；而把它推到拐点边缘的正是 v3.4。**v3.4 是制造脆弱性的那个变更，大促是扣动扳机的那个事件。** 这也说明为什么两边团队都"无辜"：谁都只看到自己那一半。

## 四、为什么现在还归不了因（这是方法论上的真根源）

- **用聚合率做因果归因，在信息上不可解。** 1.3pp 是个标量，四个候选原因是四维；标量无法反解四维。
- **Simpson 悖论**：两周内流量结构变了（新客/跨境/App 占比上升），**整体成功率下降完全可以与每个分群成功率不变同时成立**。很可能有一大块"退化"根本不是退化。
- **"没有留存原始请求日志"这个前提八成是错的。** 至少四份数据几乎必然存在：网关/Nginx/LB 的 access log、APM 的 span、CDN 边缘日志、客户端埋点/RUM。缺的不是数据，是 **request_id 没打通**。
- 附带一句：把"网关超时""风控拒绝""App 更差""海外更差"当成四条独立线索并列，会导致**同时去修四个地方**——这是这类事故最常见的二次伤害。

## 五、今天就能做的判定（不需要原始日志，按性价比排序）

1. **时间序列拐点归因（零成本，最强判据）**。三个变更各有自己的时间戳：CDN 切换时刻、v3.4 发版时刻、大促起量时刻。把成功率画成小时级曲线：
   - 掉点**与流量峰值同步、全天呈"峰谷差拉大"** → 容量/排队，H1 成立；
   - **在发版时刻出现阶跃、之后不回** → H1 成立且是代码问题；
   - **在 CDN 切换时刻阶跃、与流量无关** → H2 翻案。
   同时看 **App/Web 失败率比值、海外/国内失败率比值随时间的走势**——比值不变而绝对值涨 = 全局延迟问题；比值恶化 = 分段问题。
2. **分群交叉表剥离 mix shift**：device × geo × 新老客 × App 版本 × 上游耗时区间。看**同群内部**的失败率还剩多少没解释。剩得越少，H3 权重越高。
3. **v3.4 灰度回滚 10%**（保留 CDN B、保留全量大促流量）：成功率回到基线即锁定 v3.4。**这是唯一能同时控制住 ②③、只动一个变量的对照实验**，比任何分析都硬。
4. **CDN B 单独回切 5% 流量**（不动后端）：Web 侧无变化即彻底排除 CDN。
5. **网关补一条埋点**：超时请求的 upstream_response_time 分布，以及超时后是否 fail-closed 打到了风控——用来合并 ④ 的两个桶。

---

## 六、一句话

**根源不在 CDN，也不在风控规则，而在 v3.4 把支付主链路从 1 次串行远程调用变成 2 次——它同时把可用性相乘、把超时抽签次数翻倍、把排队利用率乘以 2.8；大促 +40% 的流量在同一时间窗内把系统推过了排队拐点，于是「变慢」相变成「超时」，再被网关阈值和 fail-closed 的风控放大成报表上的「网关超时上升 + 风控拒绝上升」；而 0.3pp 的风控拒绝上升主要是大促人群结构漂移，属于策略按设计生效。1.3pp = 一个新引入的延迟放大 × 一次容量拐点 × 一次人群结构漂移，不是四个独立故障。**
