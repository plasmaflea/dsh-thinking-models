# 支付成功率 98.2% → 96.9%：根源判断

## 结论（先给答案）

根因不是 CDN、不是风控、也不是「大促流量大」，而是 **v3.4 把「一次请求」改成「两次串行同步调用」** —— 它在三个维度上同时对同一件事做了 ×2：超时预算、失败概率、后端并发占用。这两周恰好又叠加了 CDN 全量切换（抬高 RTT 尾部，尤其跨境/海外）和大促 +40% 流量（把并发需求推到约 2.8 倍）。三者作用在**同一个变量**上（每次请求占用的时延与后端资源），所以是**乘性叠加**，不是三个独立小毛病相加，最终在超时阈值处被截断，表现为 1.3 个百分点。

风控拒绝率从 0.8% 升到 1.1% 不是独立病根，它是伪信号（被评分的人群结构变了）或共犯（超时/降级被 fail-closed 记成了「拒绝」）。CDN 和流量是**放大器**，不是起源。

---

## 一、先把账算对：分母比归因更优先

- 成功率 98.2% → 96.9%，对应失败率 **1.8% → 3.1%**，相对涨幅 **+72%**。1.3 是绝对百分点，但业务痛感是失败量多了七成。
- 归因之前必须先确认：这两个数字是不是同一个分母。v3.4 把 1 次请求拆成 2 个同步调用后，如果成功率仍按「用户请求」算、失败却按「调用」记（或反过来），或者网关把拆分后的两条调用各记一笔，「成功率」这个指标的计数单位就已经变了。**1.3pp 里可能有一部分是口径漂移，不是真实损失。** 这是在没有原始日志时最容易被骗的一处。
- 假设口径可比，先做一次粗分解：
  - 风控拒绝 0.8% → 1.1%，对应 **+0.3pp**；
  - 余下 **+1.0pp** 是技术失败，即技术失败率大约从 1.0% 翻到 2.0%。
  - 这个「翻倍」与「调用数从 1 变 2、串行复合失败概率 1−(1−p)² ≈ 2p」在数量级上严丝合缝。**这是本案最硬的一条算术线索。**

## 二、用症状指纹做排除法

| 候选原因 | 网关超时↑ | 风控拒绝↑（规则未动） | App > Web | 海外 > 国内 |
|---|---|---|---|---|
| CDN B 质量回退 | 仅回源路径可能 | 不能解释 | ✗ 应两端同等受影响 | 可能 |
| **v3.4 双同步调用** | ✓ 直接 | ✓ 若新增调用在风控/降级链上 | ✓ 移动网络 RTT 长 | ✓ 跨境 RTT 长 |
| +40% 流量 | ✓ 排队 | 不能解释 | ✗ 负载是全局的 | ✗ |
| 大促人群结构变化 | ✗ | ✓ | 可能 | ✓ |
| 风控规则变更 | — | 前提已排除 | — | — |

读法：

- **只有一个原因的指纹能同时覆盖四列：v3.4 的串行化。** 它能解释「谁在失败」—— 恰好是 RTT 最长的两端（App 与海外）。CDN 和流量都解释不了这个偏斜：纯 CDN 回退对 App/Web 是一视同仁的；纯流量压力是按流量份额分布的，不会刚好挑中移动端和跨境用户。
- **「网关超时」这个指标本身已经把病灶定位在后端链路。** 网关是服务端，它超时说明请求已经进来了、是网关等下游等不到。客户端到边缘那一段出问题会表现为客户端失败或边缘 5xx，不是网关超时。所以 CDN 顶多在「回源放大」这条间接路径上有份，不是主因。
- **风控规则没动而拒绝率涨 0.3pp，逻辑上只有两种可能**：一是被评分的人群变了（大促新客、新设备、海外流量、羊毛与欺诈攻击在大促集中出现）；二是风控的判定被链路上的超时/降级污染了（fail-closed 把「判不了」记成了「拒绝」）。两种都不支持「风控是病根」，而且第二种会把技术失败洗白成风控拒绝，正好污染账本。

## 三、机制：为什么是「乘 2」而不是「加一点」

三个维度同时翻倍：

1. **超时预算**：原来一次 RTT 要在 T 内完成，现在两次串行 RTT 要在同一个 T 内完成。单次超时概率 p 时，串行复合失败概率 ≈ 2p。超时阈值一个字没改，但它从「尾部保险」变成了「日常截断」。
2. **失败面**：多一个同步依赖 = 多一个会超时、会降级、会返回脏数据的环节。后端说「v3.4 只是加了一个查询」—— 这句话本身就是问题清单：加一个同步查询，在功能上是多一个字段，在可靠性上是多一个故障点，在延迟上是多一段 p99，在容量上是多一份并发占用。**规则没动 ≠ 决策没变**；把一个新的查询接进决策链，等于事实上改动了策略面。
3. **并发占用**：按 Little's law，单个请求占用后端资源的时间翻倍、到达率又 +40%，所需并发 ≈ 1.4 × 2 = **2.8 倍**。连接池 / 线程池 / 下游配额如果没有同步扩容，排队时延就会在尾部爆炸 —— 而尾部永远是 RTT 最长的那批请求先死，正好是 App 和海外用户。

这也解释了「为什么偏偏是现在」：任何一个变更单独上线，可能都还留在水位线以下；两个变更作用在同一个资源上，才会在超时线上被截断。

## 四、为什么两个团队都能自证清白（这本身是根因的一半）

- **CDN 厂商的「我们这边没有异常」是对它自己的 KPI 负责**：边缘可用性、5xx 率、带宽。全量切换没有对照组，切换后缓存是冷的，大促峰值第一次打上去时命中率低 → 回源放大 → 源站网关的负载与时延被抬高。这些都不会出现在厂商的异常面板里，因为在它的视角，它在正常服务、正常回源。
- **后端的「只是加了一个查询」是自证清白的典型句式**：它描述的是代码 diff，不是系统行为。
- 真正的根因就落在这两句话的缝隙里 —— **端到端延迟**。而你们只有聚合指标、没有请求级留痕、也没有灰度对照组，于是任何一方都能用自己口径的数据证明自己没错。技术根因是串行化，**组织根因是「同期叠加变更 + 无对照组 + 无请求级证据」**，两者是同一个事故的两半。

## 五、置信度，以及什么能推翻我

置信度：机制层面**高**；量级拆分层面**中**。

以下任一成立，我就改指向 CDN 的跨境路径：

- 失败率按 RTT / 网络类型 / 国家分桶后，不随 RTT 单调上升，或与超时阈值无关；
- 超时集中发生在第 1 个调用，而不是新增的第 2 个调用；
- 摘掉第 2 个调用（灰度或回滚）后，失败率不回到 98.2% 附近。

## 六、怎么证实（顺带止血，因为大促还在跑）

1. **先止血再归因**：按 user_id / POP 灰度 1% 流量回退到单调用，看成功率是否回到 98.2%。这是唯一同时能验证因果和止损的动作，对比时务必同国家、同网络类型分桶。
2. **向前埋三个维度**（不必回溯历史，从今天开始采就够）：调用序号（call_1 / call_2）的 p99 与超时计数；RTT 分桶（国内/海外 × App/Web × 网络类型）的成功率；被记为「风控拒绝」的请求里风控调用的返回码分布——用来把「真拒绝」和「超时/异常 fail-closed」拆开。
3. **向 CDN 要曲线，不要结论**：分国家、分运营商的 p99 RTT、TLS 握手耗时、回源时延、缓存命中率，而不是一句「无异常」。
4. **对齐成功率口径**：请求数、调用数、订单数三个分母各算一遍，确认 1.3pp 里有没有口径伪降。

## 七、一句话给老板

不是 CDN 坏了，也不是风控变严了。是我们把一个请求的延迟预算和后端占用都翻了一倍，同时换了 CDN、又撞上大促 40% 的增量——三个变化作用在同一个变量上，相乘之后在超时线上被截断。先回滚第二个同步调用止血，再补请求级埋点，否则下次还是只能听两个团队各自说「我这边没问题」。
