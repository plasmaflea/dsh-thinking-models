# 支付成功率 98.2% → 96.9%：根源归因

## 结论（先给判断）

根源不是这四件事里的任何一件，而是**一条原本就贴着超时阈值的延迟预算被吃掉了余量**。其中最可能的直接肇事者是 **v3.4 新增的第二个同步调用**：它把一个查询的耗时叠加进了串行链路，抬高的是 p99 而不是 p50；随后 **+40% 的大促流量把这个尾部问题变成容量问题**，越过超时悬崖。

**风控拒绝率从 0.8% 升到 1.1% 不是原因，是下游产物**：超时引发客户端重试与网关"失败关闭"，重复请求被速度类规则误判、风险调用超时被计为拒绝。

**CDN 全量切换是同时发生的混淆变量**，它单独只能解释"海外失败率高于国内"，无法解释"App 高于 Web"和风控拒绝率上升。

但必须说清楚一句话：**以现有这批纯聚合指标，1.3 个点无法被唯一分解**。下文的判断是"证据强度最高的假设"，不是已证实的结论——好在它的可判别性很高，两条曲线或一次回滚就能定案。

## 一、先把 1.3 个点做减法：风控解释不了这件事

| 指标 | 两周前 | 现在 | 变化 |
|---|---|---|---|
| 成功率 | 98.2% | 96.9% | −1.3pp |
| 总失败率 | 1.8% | 3.1% | +1.3pp（相对 +72%） |
| 风控拒绝率 | 0.8% | 1.1% | +0.3pp |
| **非风控失败率（残差）** | **1.0%** | **2.0%** | **+1.0pp（翻倍）** |

两个直接推论：

1. **风控最多只能解释 0.3/1.3 ≈ 23% 的跌幅。** 剩下 1.0pp、也就是 77%，必须由别的东西解释。任何把根源归给风控的说法，在算术上就站不住。
2. **非风控失败率恰好翻倍，而流量只涨了 1.4 倍。** 换算成失败"次数"是 2.0×1.4/1.0 ≈ **2.8 倍**。失败量随负载**超线性**增长——这是典型的"撞到某个硬上限"（超时、连接池、线程池、下游限流）的特征，而不是某个因素按比例变差。按比例变差的故障会让失败率跟着流量线性走。

所以问题被锁定了：**有 1 个点来自"超时/容量"这一族，而不是来自策略或规则**。风控那 0.3pp 反而更像这条链的副产品（见第三节）。

## 二、用"故障签名"做排除法

| 候选 | 能解释 | 不能解释 | 判定 |
|---|---|---|---|
| **v3.4 双同步调用** | ①网关超时↑（串行链路 p99 抬升）②App>Web（App SDK 超时更短+自动重试，先越线）③海外>国内（跨境 RTT 更高，同一条延迟增量把更多请求推过阈值）④风控拒绝↑（重试→重复请求→速度规则误触发；风险调用超时→失败关闭计为拒绝） | 无 | **四项全中，最强嫌疑** |
| **流量 +40%** | 放大以上一切 | 无法单独造成拒绝率上升，也无法单独造成 App/Web 分化（同地区内不该有客户端差异） | 必要条件/放大器，不是起因 |
| **CDN A→B 全量切换** | 海外>国内（PoP 覆盖、回源路径、TLS 握手/会话复用、HTTP/2、边缘→回源超时阈值漂移） | 解释不了 App>Web；解释不了风控拒绝率上升 | 只解释 1 项，且是**混淆变量** |
| **风控规则** | 规则没动 | 规则没动 ≠ 行为没动（见第三节） | 结果，不是原因 |

**为什么"两个团队都在说真话"：** CDN 厂商说"我们这边没有异常"，指的是他们自己的边缘指标——他们的监控里看不到我们回源变慢了；后端团队说"v3.4 只是加了一个查询"，也是真话——**一个没有覆盖索引、或者跨服务的查询，在高并发下足以让 p99 变成原来的 2～3 倍**。两个诚实的人指向相反方向，这恰恰是"没有原始日志、只有聚合值"造成的僵局。而且 `一次请求拆成两个同步调用` 的真实代价不只是那条查询的耗时：它同时把每个请求的**下游连接占用时长**翻倍，等效吞吐减半。1.4 倍流量压在约 0.6 倍的等效容量上，负载比接近 2.3 倍。

一个容易被忽略的交互项：**如果 CDN B 的边缘→回源超时默认值比 A 短**，那么"v3.4 让回源变慢"这件事会被 B 更早地翻译成 5xx。此时根源是"两者相乘"——单独换 CDN 或单独发版都不会掉这么多。这也是我最想验证的第二假设。

## 三、风控拒绝率为什么会在规则不变时上升

规则没动，但**输入分布动了**，有三条互相独立又同向的机制：

1. **重试放大**：超时后 App/SDK 自动重发，同一用户在秒级发出多个相同请求，速度类/频次类规则看到的是"短时间高频"，判定为异常。规则没变，被它看到的东西变了。
2. **失败关闭**：网关或风控客户端在调用超时/熔断时走保守分支直接拒绝，这条在监控里落在"风控拒绝"的口径下，但它其实是**超时的伪装**。这会自动把"超时"的一部分搬进"风控拒绝"的桶里——两个指标同时上升，正是这个机制的特征。
3. **大促混量变化**：新客占比、设备指纹新鲜度、地区分布都变了，同样的规则对不同的流量构成给出不同的分数。

所以"网关超时率上升 + 风控拒绝率上升"这两个"独立"观察，很可能是**同一件事的两个出口**。把它们当成两个独立故障去分头排查，是这次归因最容易走偏的地方。

## 四、还有两个"观察"本身可能是假的

这是纯聚合数据最危险的地方，必须点明：

1. **App>Web 与 海外>国内 可能是同一个人群偏斜（辛普森悖论）。** 如果 App 装机量在海外占比显著更高，那么"App 失败率高于 Web"完全可以由"海外失败率高"解释；控制地区之后 App 的劣势可能消失，反之亦然。没有分层数据，这两个百分点不能算两个证据，只能算一个。
2. **成功率的度量口径可能被重试污染。** 如果分母按"请求"计，而客户端会自动重试，那么"一次失败 + 一次成功"= 2 个请求里 1 个成功 = 50%，而用户的**实际支付体验是成功的**。重试风暴会机械地压低请求级成功率，而订单级成功率没变。**必须先确认：这个 98.2%→96.9% 是请求级还是支付意图级。** 如果是请求级，1.3 个点里有一部分是度量幻觉，真实跌幅可能小于看起来的。

## 五、没有原始日志，怎么把它定死

关键认知：**你不需要原始请求日志，你需要的是"失败原因的分类维度"和"一次可控的开关实验"。** 缺的是分类，不是字节。

1. **失败原因码对账（最便宜、最可能一击命中）。** 原始 payload 没留，但状态码/原因码/网关指标通常还在。把 1.3pp 拆成：网关 504/超时、风控 403、客户端超时、TLS/连接错误、业务错误。如果残差那 1.0pp 主要是 504 和客户端超时 → 延迟路径定案；如果主要是 403 → 才轮到风控。
2. **看时间序列的"形状"，而不是数值。** 四件事的时间点不同：
   - 阶跃点精确落在发版日、之后平台期 → v3.4；
   - 阶跃点精确落在切换日 → CDN；
   - 促销开始前平、开始后持续**爬升**且不回落到新平台 → 容量/饱和。
   日粒度的拐点判别不需要任何原始日志，这是本题最被低估的线索。
3. **把标签切开看。** 聚合指标通常带 CDN PoP/地区、App 版本、后端实例、API 版本等维度，只是没人切过。如果 v3.4 是灰度/分批上的，就存在**天然对照组**；如果有按 PoP 的失败率，海外那部分立刻能分辨是"所有 PoP 一致变差"（后端问题）还是"特定 PoP 变差"（CDN 问题）。
4. **双因子现场实验（最快的因果证据）。** 两个开关独立拨动：5% 流量回 v3.3；一个地区回切 CDN A。四种组合看失败率，一次就能把主因和交互项分开。这是可控的，比继续看板子便宜得多。
5. **不要问 CDN 厂商"有没有异常"，要两条曲线。** 要"边缘 TTFB"和"边缘→回源耗时"分开的时间序列：边缘平、回源涨 → 后端；回源平、边缘涨 → CDN；两条都平但 5xx 涨 → 配置/超时阈值漂移。
6. **p99 vs 失败率画在一张图上，看是不是悬崖。** 如果是阈值型（过了某条线失败率陡升），那么"平均延迟只涨了一点"和"成功率掉了 1.3 个点"就不矛盾——这正是聚合均值掩盖 p99 的经典形态。

## 六、置信度排序与一句话根源

- v3.4 串行调用导致延迟回归，被 +40% 流量放大 → **主因（高置信）**
- CDN B 的超时/回源配置漂移作为交互项 → 次因（中置信，且与主因相乘）
- CDN 独立故障 → 低置信（解释不了 App>Web 与风控）
- 纯流量 → 不是原因，是放大器
- 风控规则 → 不是原因，是重试与失败关闭的出口

**一句话根源：** 系统的延迟余量本来就薄，v3.4 新增的第二个同步调用把 p99 推过了超时线，大促流量把这个尾部问题放大成容量问题，超时又通过客户端重试和"失败关闭"二次转成了风控拒绝与额外的负载；CDN 全量切换是同期发生、主要污染"海外"这一维度的混淆变量。

**但真正可复发的根源在组织层：** 全量 CDN 切换、发版、大促三件事压进同一个时间窗，没有灰度、没有 canary、没有失败原因分类、没有原始日志——这让**任何**一次故障都变得不可归因。下次不必是 v3.4。修完这次的延迟问题之后，该补的是三样东西：失败原因码的分类指标、按维度（地区/客户端/版本/PoP）可切的指标、以及能独立拨动的发布与路由开关。
