## 1 L0 类别判定

**软件类**（`software`）。
**判据**：失败由代码/配置/环境姿态确定性决定，且能被归因到某个外部输入的时序——本次已在等价副本上以「并发数 → 失败数」的确定性函数复现（见 §4），满足。
**已排除的大类**：
- **硬件**：无校验错误；失败率是并发的确定性函数（N=9→1 条、12→4、16→8、20→12），不是随机抖动。
- **网络链路**：同一客户端、同一请求「刷新一下就好」，`/api/items` 与 `/api/upload` 失败率**完全相同**（都是 8 成功 / 12 失败），与链路和路径无关。
- **权限/账号**：全程无 401/403，同一请求重试即成功。
- **组织流程**：能解释「为什么一周没人管」，不能解释 502 本身；挂起（见挂起表）。

## 2 L1 树实例化

`树 = knowledge-tree/software · v1 · 核查 2026-10-18`（子层轴：lifecycle／init／dependency／quota／concurrency／config）。
**本次判为不适用的节点**：`win-service`（L1，服务形态初始化失败——与本例无关）；`lifecycle`／`init`／`dependency` 三子层（进程从不死、不重启，200 与 502 在同进程内交替出现，故不是启动期或依赖期问题）。
**命中子层**：`quota`（资源配额：后端并发槽位）＋ `concurrency`（时序：排队时延 vs 调用方超时）。
**树外分支（须登记，不许静默丢弃）**：现有六子层里没有「调用方超时预算 × 被调用方容量」这一支，`quota` 只管配额值、`concurrency` 只管锁与竞态。登记 `v2 候选`：`software.quota.timeout-budget`（调用方超时预算与被调用方容量的耦合），理由：本类是它的首个实例，且用现有两支描述都会漏掉「两个上限互不推导」这个关键结构。另：`network` 是待建节点，本次判为不适用但已进挂起表。

## 3 L2 逐层回溯（轴＝必经时序，7 格）

轴由「一个请求从发起到判定结束」的必经步骤机械生成，不用联想列举。每格必须写出该格故障时的**专属可观测症状**：

| 格 | 必经步骤 | 该格故障的可观测症状 | 本次实测 | 判定 |
|---|---|---|---|---|
| G1 | 客户端发出请求（含 body 大小/协议） | nginx 直回 **413**，请求不进上游 | 5MiB、12MiB POST 均 200 | 空 |
| G2 | 代理接收并缓冲 body（`client_body_buffer_size`／`client_max_body_size`） | 同为 413，access.log 该条 **无** `$upstream_*` | 副本无任何 body 限额 | 空 |
| G3 | 代理建连到上游（connect） | `connect() failed` / 502，且 `$upstream_status` 为空、`$upstream_connect_time` 大 | 502 文本是 `upstream timeout after 800ms`，不是 ECONNREFUSED | 空 |
| G4 | **上游排队等槽位** | 成功请求时延呈**整数倍服务时间的阶梯**；失败数随并发线性增长 | 时延阶梯 320 / 634 / 830ms；N=9→1、12→4、16→8、20→12 条 502 | **非空** |
| G5 | 上游处理业务（逻辑/SQL 慢） | 单请求（串行）时延就已超过阈值 | N=1 时 320ms；N=4 时 319–321ms（与单请求一致） | 空：处理本身不慢 |
| G6 | 响应回传 | 200 的头已发出后连接断开（客户端侧 truncated） | 502 都是完整的网关响应体 | 空 |
| G7 | **代理判定完成/放弃** | 失败时延**钉在超时值**上，与负载无关 | 502 的时延全部落在 823–835ms，而超时设置是 800ms | **非空** |

G4 ＋ G7 汇合 ⇒ **个例根**：

> 代理的固定超时预算（`lab-t1/front.js:11  UPSTREAM_TIMEOUT = 800`）小于后端在忙时的排队时延（`lab-t1/upstream.js:5-6  DELAY = 300` 与 `MAX_ACTIVE = 4`）；当在飞请求数超过代理能容忍的轮数时，代理在请求真正被处理之前就 destroy 掉上游连接，把「慢」翻译成「坏」，于是 502。

**量化定位（可直接抄进你的容量估算）**：

```
代理可容忍的在飞请求数  N_max = ⌊T_proxy / T_service⌋ × N_slot
                            = ⌊800ms / 300ms⌋ × 4 = 2 × 4 = 8
失败数 = max(0, N − N_max)
```

⇒ **类根**：任何「固定超时的调用方」＋「有限并发槽位、无排队上限、无背压的被调用方」的组合，只要负载使在飞请求数超过 `⌊T_超时 / T_单请求⌋ × N_槽位`，网关类错误就必然发生。根不落在「4m 还是 10m」这种具体数值上，而落在**两个互不推导的常量**上：超时预算是猜的（谁也没算过它对应多少并发），容量是硬的（槽位 4 / 连接池大小）。中间没有任何一层把二者联系起来——没有队列语义、没有上限、没有背压。

## 4 实测证据（等价副本，一次性对照实验）

只跑客户端压测脚本，未启动任何新服务进程，只碰 127.0.0.1:19300。

| 并发 N | 目标路径 | 200 | 502 | 时延 min/p50/max (ms) | 与 `max(0, N−8)` 是否吻合 |
|---|---|---|---|---|---|
| 1 | /api/items | 1 | 0 | 320 / 320 / 320 | ✓ |
| 4 | /api/items | 4 | 0 | 319 / 320 / 321 | ✓ |
| 8 | /api/items | 8 | 0 | 327 / 634 / 635 | ✓ |
| 9 | /api/items | 8 | **1** | 329 / 637 / 823 | ✓ |
| 12 | /api/items | 8 | **4** | 327 / 636 / 823 | ✓ |
| 16 | /api/items | 8 | **8** | 324 / 830 / 831 | ✓ |
| 20 | /api/items | 8 | **12** | 327 / 834 / 835 | ✓ |
| 20 | **/api/upload** | 8 | **12** | 327 / 823 / 823 | ✓（路径无关） |
| POST 5MiB | /api/upload | **200** | 0 | — | body 大小无关 |
| POST 12MiB | /api/upload | **200** | 0 | — | body 大小无关 |

三条独立结论：
1. **失败数精确等于 `N − 8`**，而 8 恰是 `⌊800/300⌋ × 4`。这个吻合不可能由「body 太大」解释，只能由「超时预算 ÷ 单请求时延 × 槽位数」解释。
2. **失败时延钉在 800ms 墙钟上**（823–835ms），而成功请求的时延是 300ms 的整数倍阶梯（320 / 634 / 830）——这正是「排队」而非「处理慢」的指纹。
3. **换成 `/api/upload` 结果一模一样，5MiB/12MiB 的 body 直接被放行**——所以这条链路上根本不存在「4MB 拦不拦得住」的问题。

## 5 L3 双根

### 处置根（修本次）
1. 把代理侧超时从「常量」改成「由后端忙时 P99（含排队）推出的函数」：`proxy_read_timeout` / `proxy_connect_timeout`（对应 `front.js:11` 的 800ms）≥ 忙时上游 P99 × 2，并**同时**给后端槽位加排队上限，超额立即 `503 + Retry-After`，不要沉默排队。
2. `client_max_body_size` 该改还是改（10m），但要说清它修的是 **413**、不是 502；它与 502 是两条互不相干的链。
3. 补一条 access.log 字段：`$upstream_status $upstream_response_time $upstream_connect_time $request_time`——没有这四个字段，你永远分不清「代理放弃」和「上游返回错误」。

### 消解根（灭这一类）
**让「慢」不再等于「坏」**：在每一对（调用方超时，被调用方容量）之间插入队列语义与背压，并从可观测性上把「超时」与「真故障」分成两类信号。

- **不可发生判据**：若当时采用它——代理超时由后端 P99 反推得出、后端对超额请求返回 `503 + Retry-After`、客户端按退避重试、access.log 记 `$upstream_status`——那么忙时负载上升只会表现为**延迟上升 + 明确 503 + 排队**，502 这一整类在结构上不可能发生，因为链路上再没有任何一处把「排队」编码成「坏网关」。
- **可执行首边**：不改代码、不下线——加一个 `log_format` 把上面四个变量打进 access.log，同一小时内把 `proxy_read_timeout` 由现值临时提到 5s 跑一个忙时峰。一条配置 + 一条 reload，约 1 人时。
- **成本量级**：首边 1 人时 / 0 架构变更；完整背压（排队上限 + 503 + 客户端指数退避 + 幂等键）≈ 1–3 人日；改造成按 location 分池分超时 ≈ 3–5 人日。**不给量级的换架构建议不可决策，所以只给到量级为止**，精确值交给公式图（不在此轮）。

## 7 L4 迁移出口

消解根指向「把超时预算与容量通过公式耦合起来」，必然带出下面这串问题，本次 502 降级为其中一项：

1. **容量规划**：用 Little's law 反推槽位数与超时预算，并把压测基线（N_max）写进配置变更的验收条件。
2. **重试语义**：503 + Retry-After、客户端指数退避＋抖动、上传接口的幂等键（否则重试会制造重复数据）。
3. **可观测性**：`$upstream_*` 四字段、超时率与 P99 看板、把「502 且 `$upstream_status` 为空」单独分型告警。
4. **长请求与大文件上传**：上传与普通 API 共用同一套超时，是下一次同类事故的温床——按 location 分池、分超时。
5. **组织**：「一天十几次、刷新就好」这类事件如何进入 SLO 而不是进不了工单——值班阈值口径。
→ **本次问题降级为第 3) 项的一个子项**（可观测性把「偶发 502」变成可归因事件），并与第 1) 项直接相关；它不是独立的根因问题，而是「容量与超时未耦合」这个更大问题在这条链路上的一个投影。

## 9 线上验证方法（不下线，四步，成本递增）

1. **`nginx -T` 全量 dump**（不要只看主配置）：确认 `/api/upload` 的 **location** 分支上生效的 `client_max_body_size` 到底是多少。若它是 1m（Nginx 默认）或任何 < 4194304 的值，就解释了「日志值恰好等于你听说的 4m」这个巧合——**location 覆盖是这类误读的标准成因**。
2. **给 502 分型**：加 `log_format` 记 `$upstream_status $upstream_response_time $upstream_connect_time $request_time`。
   - 若 502 的 `$upstream_status` 为 `-`、`$upstream_response_time` 贴着 `proxy_read_timeout` 的值 ⇒ **代理主动放弃**，与本次复现同机制，根在「超时预算 < 忙时 P99」。
   - 若 `$upstream_status` 有值 ⇒ 是上游真的返回了 5xx，另一条链，另起一次回溯。
   - 顺便数一下同期 **413** 的条数：它才是 body 限额该负责的那部分流量。
3. **反证 body 假设**：临时把 `client_max_body_size` 提到 10m，观察同一时段的 502 数。**若不变** ⇒ 与 body 无关（预期结果），同时 413 数应下降。这一步比任何论证都便宜。
4. **反证超时假设**：把 `proxy_read_timeout` 由现值提到 5s + 给后端加排队上限/快速失败，同一忙时段 502 应降到 0。代价要提前说清：**卡住的请求会变慢、连接占用变多**——所以「调大超时」不能单独做，必须与容量/背压同批上线，否则你只是把 502 换成了长尾延迟。

## 结论

三句话：

1. **你的猜测不对，方向还相反**：那条 error.log 产出的是 **413**（Nginx 自己答复，请求根本不进上游），而 access.log 里是 502——两者不是同一个请求，只是落在同一个忙时段；而且日志里 4194304 与「4m」**数值相等**，在 Nginx「严格大于才打印」的判据下，这反而证明生效限额**小于** 4194304，你说的「只写了 4m」不是生效值。把 4m 改成 10m 会放更多大请求进来、让单请求占槽更久，**排队更深，502 只会更多**。
2. **真正的根**：代理的固定超时预算（800ms）与后端的并发槽位（4 个 × 300ms）之间没有任何容量公式联系，也没有队列上限和背压。可容忍并发 `⌊800/300⌋ × 4 = 8`；一旦白天在飞请求数超过 8，多出来的每一条都必然在 800ms 被代理 destroy 成 502——**502 不是上游坏了，是代理替上游的排队买了单**。副本上失败数精确等于 `N − 8`（9→1、12→4、16→8、20→12），换成 `/api/upload` 结果不变，5MiB/12MiB 的 body 照样 200。
3. **怎么验**：`nginx -T` 查生效 body 限额（顺手证伪你的猜测）＋ access.log 加 `$upstream_status/$upstream_response_time` 给 502 分型（`upstream_status` 为空且 `response_time` ≈ `proxy_read_timeout` ⇒ 代理超时，实锤）＋ 临时提 `proxy_read_timeout` 到 5s 看 502 归零。三步都不下线，首步 1 人时。

## ⚠️ 异常 / 矛盾 / 空白

1. **题面自带矛盾**：你说 access.log 里对应条目「都是 502」，又说 error.log 里刷得最多的是 `client intended to send too large body`——这两句在机制上不能同时成立（该 error 只会产出 413）。请按 §9 第 2 步把两条日志按请求/时间戳对齐，多半会发现它们是**两个不同的事件流**。
2. **数值巧合**：4194304（＝4MiB 整）既是「日志值」又恰好是「你听说的限额」。这种「日志值恰等于限额」在 Nginx 上通常意味着**打印该行的 location 生效限额比它更小**，而不是相等。
3. **缺失信息**（决定线上是否与副本同机制，必须先补）：真实的 `proxy_read_timeout`／`proxy_send_timeout` 现值、后端连接池/并发槽位大小、忙时上游 P99、502 条目的 `$upstream_response_time`。这四项任缺其一，结论只能停在「高度可能」。
4. **副本与线上的差异**（不要过度外推）：副本的 `/api/upload` 完全不落地 body（5MiB/12MiB 都是瞬间 200），线上上传要落盘/入库，单请求占槽时间会随文件大小增长。这意味着线上同一个 502 机制里，**大文件是放大器而不是根**——4m→10m 恰好会把这个放大器调大。

## 💡 灵感备注

这个故障的形状值得记住：**两个各自都合理的常量（800ms 超时、4 个槽位）凑在一起，就变出了一个硬阈值 8**。所有「白天忙时偶尔、刷新就好」的线上现象，第一反应都该去算这个阈值，而不是去读 error.log 里刷得最多的那行——**刷得最多的错和造成事故的错，往往不是同一行**。
