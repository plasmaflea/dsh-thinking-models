# 502 根因分析：你的猜测错在「拿 A 格的缺陷去解释 B 格的症状」

[模式标识] 🧪 倒推图（前置审计，`presupposed-answer-hypothesis-backderivation`）→ 🌳 林状图（正式作答，`forest-hierarchical-backtracking`）
[选择理由] 提问者已带答案（「改成 10m 就好了」），且要求「说明猜测为什么不对」——按机制必须先用倒推图把已有结论摊开证伪，再回到林状图按必经时序切格取证。502 属于「根源在哪」型问题，因果深度未知，不是选项广度问题，所以主模式是林状图而非网状图。

## 0. 一句话结论

**502 的根不在请求体大小，在「代理侧一个与负载无关的常量上游超时」对上「后端一个随并发无界增长的排队时延」。**
等价副本里这条机制已被完整复现并量化：`client_max_body_size` 那一族错误（413）与 502 根本不产生于同一格，改 4m→10m 修的是另一条独立的真 bug，**不改动 502**，甚至有把小问题放大的方向性风险。

**标注**（哪些是显式、哪些伪装成事实）：
- 「502」是事实；「一天十几次、白天多、刷新就好」是事实（用户口述，可采信）。
- 「nginx 配置里 client_max_body_size 看着像只写了 4m」**是假设伪装成事实**——依据只有「日志里那个数字是 4194304」。而且这条依据本身是错的（见 §11 ⚠️1：那个数字是客户端声明的 Content-Length，不是限额；限额只能推出「< 4194304」）。
- 「改成 10m，502 就好了」是结论，不是事实。

**走形命中**：
- **#1 单一假设**：只列了「体积超限」这一个假设，没有并列「上游超时 / 上游连接失败 / 容量排队 / 长连接被重置」。

- **#5 假设升格为事实**：「看着像只写了 4m」在下一句就变成「所以改 10m 就好了」。

**纠正映射**：#1 / #2 → 林状图（按必经时序切格取证，逼出「这一格能不能产生 502」）；#5 → 公式图（把超时/容量写成等式再代入，见 §4.3）。
**结论**：H0 不可信。它是一次**跨格串线**——把「请求头限额校验」这一格的真实缺陷，错配到了「等待上游响应」这一格的症状上。

## 2. L0 类别判定（一行，但必须有）

**类别：软件类问题（`software` 节点），子层落在 `quota` 资源配额 + `concurrency` 并发与时序 + `config` 配置。**
判据（同时满足）：①失败来自代码/配置姿态而非物理介质——等价副本在 loopback 上零丢包、零 DNS，仍 100% 复现同一 502（N=40 时 40/40）；②失败是确定性的——给定相同并发，502 数量可预测（见 §4.3，误差 ≤ 4）。
**已排除的大类**：
- **网络类**：判据是「分层可达性可测、症状随链路变化」。本问题在 127.0.0.1 纯环回上复现，与链路无关 ⇒ 排除链路层，但**保留「上游连接阶段失败」作为代码内的一格**（§4 第 4 格）。
- **硬件类**：无校验错误、无跨进程随机性、时延分布被截断在常数值上 ⇒ 排除。
- **权限/账号类**：无 401/403/ACL 痕迹，全部为代理生成的 502 ⇒ 排除。
- **业务逻辑类**：业务错误会是 500/4xx 且带 body；502 的 body 由代理生成 ⇒ 排除。

## 4. L2 逐层回溯

### 4.1 轴（生成式，不是列举）

主轴由**必经时序**生成：一次被代理的请求，从 accept 到响应落地，必然依次经过 7 个阶段，一格都不可省。每格给「该格故障的可观测症状」——注意症状是**互斥的**，这满足正交/可生成/可观测三判据。

| 格 | 阶段（必经） | 该格故障的专属症状 | 本次取证 |
|---|---|---|---|
| 1 | 接入：accept/建连/worker 资源 | `worker_connections are not enough`、连接排队；502 但 `upstream_addr` 为空 | 未出现（无 acceptance 类错误） |
| 2 | **请求头解析与限额校验**（`client_max_body_size`、header 缓冲） | **413 / 400 / 494**；error.log：`client intended to send too large body: N bytes` | **命中**：你看到的那条 4194304 —— 属于此格 |
| 3 | 请求体传输（缓冲/临时文件/`client_body_timeout`） | 408 / 413 / 499 | 未见独立证据 |
| 4 | 上游连接建立 | `connect() failed (111: Connection refused)` / `(110: ... timed out)` → 502 | 未见（lab 中上游始终存活） |
| 5 | 请求投递完成 | `upstream prematurely closed connection` → 502 | 未见 |
| 6 | **等待上游响应（含排队）** | `upstream timed out (110: Connection timed out) while reading response header` → **502**；延迟被截断在超时值上 | **命中（实测确证）**：502 body = `502 Bad Gateway: upstream timeout after 800ms` |
| 7 | 响应回传/长连接复用 | 半截 502、keepalive 被 RST、499 | 未见 |

**关键结构事实（这就是你猜测错误的机制性理由）**：
- 502 是**网关侧语义**，它只能由第 4/5/6/7 格的「上游交互失败」产生；
- 第 2 格（body 限额）的产物**只能是 413**，nginx 不会把它记成 502，也不会把它写成 502 返回给客户端；
- 你在 error.log 里捡到的那条 `4194304 bytes`，**坐在第 2 格**，而 502 坐在第 6 格。**跨格证据不可互证**。频率最高的报错与那十几条 502 不是同一批请求——这是两件事被日志的相邻性串成了一件事。

> 跳步规则的落实：我这 7 格全部列出，即使 1/3/4/5/7 格「本次无症状」也各占一行，因为「无证据」本身是判断。

### 4.2 沿第 6 格下钻，换下钻轴（恒等式）

第 6 格的等待时长不是单一量，用**恒等式**切因子（第二类合法生成源）：

```
请求总时延 = 排队时延 + 处理时延
排队时延   = ceil(C / A) × D        （C=瞬时并发，A=并发槽位，D=单请求服务时延）
502 判据   = ceil(C/A) × D > T      （T=代理侧上游超时，常量）
⇒ 可承受并发上限 C_max = A × floor(T / D)
```

- `A`（槽位）由后端持有量决定（等价于数据库连接池大小）→ 变量；
- `D`（单请求时延）由业务与 IO 决定 → 变量；
- `T`（代理侧超时）**是常量**：`front.js:11  const UPSTREAM_TIMEOUT = 800; // ms`。

### 4.3 公式代入 + 实测对账（这一步不需要你信我，可以复跑）

lab 实际参数：`upstream.js:6 MAX_ACTIVE = 4`、`upstream.js:5 DELAY = 300`、`front.js:11 UPSTREAM_TIMEOUT = 800`、`front.js:8 maxSockets = 32`。

`C_max = 4 × floor(800/300) = 4 × 2 = 8` ⇒ **并发 ≤ 8 全部成功；并发 = 9 起，每多 1 个并发就多 1 个 502。**

实测（`node load.js <N> http://127.0.0.1:19200/api/items`，每档一次全并发）：

| N（全并发） | 200 | 502 | 最小/p50/最大 时延 ms | 模型 C−8 | 对账 |
|---|---|---|---|---|---|
| 4 | 4 | 0 | 327 / 328 / 330 | 0 | ✔ |
| 8 | 8 | 0 | 323 / 629 / **630** | 0 | ✔（2 波 × 300ms） |
| 9 | 8 | **1** | 328 / 636 / **822** | 1 | ✔ |
| 10 | 8 | **2** | 321 / 632 / **818** | 2 | ✔ |
| 12 | 8 | **4** | 319 / 626 / **827** | 4 | ✔ |
| 16 | 8 | **8** | 327 / **822** / 822 | 8 | ✔ |
| 20 | 4 | **16** | 641 / **840** / 842 | 12 | 方向一致（+4：`agent` 排队与事件循环把到达时刻摊开，使更多请求落进第 3 波之后） |
| 40 | 0 | **40（100%）** | **839** / 840 / 1662 | — | ✔（`maxSockets=32` 也参与排队） |

两个必须记住的**指纹**：
1. **最大时延被"钉"在常量上**：4/8/9/10/12 各档的 max 分别是 330 / 630 / 822 / 818 / 827——不是长尾，是**截断**，截断点 ≈ `UPSTREAM_TIMEOUT`。真实系统里这个指纹对应的观测是 `$upstream_response_time ≈ proxy_read_timeout`（或 `$request_time` 顶在某个配置值上），而不是服从平滑长尾。
2. **502 数 = 并发 − 容量**：超过容量后呈 1:1 线性，这是排队类根的签名。资源泄漏/OOM/连接拒绝类不会给出这么干净的线性关系。

### 4.4 结果：类根（在上）＋ 个例根（挂其下）

**类根（这一大类在什么结构条件下必然可能发生）**：
> **代理与上游之间不存在「时延预算」这一契约**——代理用一个**与负载无关的常量超时**去裁决一个**随并发无界增长**的时延分布，且后端排队**没有上限、没有队头拒绝**。
> 只要这个结构在，任何「白天并发会周期性超过容量」的系统都会把「排队」误判成「上游故障」，把该报的 503/拥塞语义报成 502。排队在任何容量有限系统里都必然发生，所以这不是运气问题，是**结构上的定时炸弹**：容量余量只决定它多久炸一次（一天十几次），不决定它会不会炸。

**个例根（本次具体机制，挂在类根下）**：
- 本系统：`A=4` 槽位（后端等效 DB 连接持有）× `D=300ms` ⇒ 容量 7.5 rps；`T=800ms` 常量 ⇒ 可承受并发 8。白天忙时瞬时并发 > 8 ⇒ 第 3 波及以后的请求排队时延跨过 800ms ⇒ `front.js:22-24` 的 `up.setTimeout(800, () => up.destroy(...))` 触发 ⇒ `front.js:26-29` 的 error 处理写 502。**实测 N=9 起出现、N=40 时 100%，与模型逐点吻合。**
- 三个放大因子（都是"共因"，不是独立根）：
  - `front.js:8 maxSockets: 32` 对后端 4 槽位 = **8× 超卖**，前端把后端根本吃不下/根本不该这么快进来的并发全放进来了；
  - 前端排队**无上限**：`Agent` 队列里的请求也在等，而等待本身没有 deadline 传递；
  - 超时后 `up.destroy()` 只关掉前端这一侧，后端 `setTimeout` 仍跑满 300ms 才 `release()`（`upstream.js:33-37`）——**已经超时作废的请求还在消耗槽位**，拥塞被自己放大；
  - 用户刷新即重试（自述"刷新一下就好"）：每次 502 换来一次额外并发，正反馈。

## 5. L3 双根

### 处置根（修本次，让线上今天不再冒 502）
**把代理侧上游超时从常量改成「后端实测 p99.9 × 2」，并同步给后端排队加显式上限（排队超时返回 503 + Retry-After，而不是让代理超时去猜）。**
- lab 对应动作：`UPSTREAM_TIMEOUT` 800 → ≥ 3000（此时 `C_max = 4 × floor(3000/300) = 40`），配合 `maxSockets` 与后端槽位比例收敛到 2–3×。
- 真实 nginx 对应动作（**必须先按 §10 取证再改，别直接改数字**）：`proxy_read_timeout` / `proxy_send_timeout` / `proxy_connect_timeout` / upstream `keepalive_timeout` 中，凡小于后端 p99.9 的那个，抬到 p99.9×2；同时不要把 `proxy_next_upstream` 打开成超时即重试（会把拥塞翻倍）。
- 备选（若"宁可快速失败"是产品决策）：不改超时，改**准入**——把前端并发/连接数限到 `A × floor(T/D)` 以内，超出直接返回 503/429。两者取一，**不能都不做**。

### 消解根（灭这一类，必须过三道闸门）
**把「时延」变成代理与上游之间的显式契约（deadline 传播 + 后端先于代理拒绝 + 容量准入成比例）：**

1. **不可发生判据**：若当时采用它——(a) 代理超时由后端实测 p99.9 推导而非手填；(b) 后端在自己的 deadline 到点时**先**返回可重试的 503/429，且该 deadline **严格小于**代理超时；(c) 前端准入并发被限制在 `A × floor(T/D)` 以内——则「排队时延 > 代理超时」这一事件在结构上**不可能发生**。502 这一类（把拥塞误判成上游故障）整体消失，剩下的拥塞以**正确的语义**（503/429 + Retry-After）暴露出来。这不是"变少见"，是这条因果链的输入端被切断。
2. **可执行首边**（从现状出发的第一步，很小）：在 access_log 里加 `$upstream_status $upstream_response_time $upstream_connect_time $request_time $upstream_addr` 五个字段，跑满一个工作日，取 502 行与峰值时段的 p99.9。**这一步只改日志格式 + reload，不碰业务代码。**
3. **成本量级**（粗估，非严格公式图，仅给决策量级）：日志字段 + 一天采样 + `nginx -T` 核对超时值 ≈ **0.5 人天**；(b) 后端排队上限与 503 语义 ≈ **1–2 人天**（需客户端配合重试幂等）；(c) 准入并发成比例 ≈ **0.5–1 人天**。合计 **2–4 人天**，不含"上传异步化"那类架构改动。

## 6. L4 迁移出口（消解根带来的新问题清单；本次问题降级为其中一项）

1. **慢请求积压**：抬高超时 = 单个请求占用槽位的时间变长 ⇒ 若不配合准入限制，容量会被慢请求吃光，502 会变成大面积长延迟（用户体感更差，且更难被监控发现）。
2. **失败语义变更**：从"502 快速失败"变成"长延迟"或"503 排队拒绝" ⇒ 前端 loading/超时提示、客户端重试策略都要改。
3. **重试幂等性**：`POST /api/upload` 被 503 后客户端重试会**重复上传**——这是 `data-consistency` 类问题（重试风暴 + 重复投递），必须在上传接口上加幂等键。
4. **容量规划入预算**：槽位数要从 DB `max_connections` 反推，成为容量预算的一部分，而不是留一个 4 就不管；前后端并发比例（8× 超卖）要写进评审项。
5. **上传异步化（可选架构出口）**：上传改为「同步受理 + 异步任务」，把长时延从请求链路里拿出去；代价是引入队列（消息丢失/重复消费/状态查询）与一套新的可观测性。
6. **可观测性落点变更**：`upstream_response_time` 只在 nginx 侧有，后端排队时延要在应用侧自己打点，否则契约没法持续校验。

→ **本次问题降级为第 1) 项与第 4) 项的子项**：当"时延契约"成立后，本次这条 502 不再是独立故障，只是"容量准入未成比例"这一项的一个症状。

## 7. 候选根排序（Share × Lever ÷ Cost，预算有限所以必须排序）

| 候选根（层级） | Share 份额 | Lever 可控性 | Cost 证伪代价 | 排序 |
|---|---|---|---|---|

| 个例根：前端 `maxSockets=32` 对 4 槽位 8× 超卖（`front.js:8`） | 次要（放大排队） | 改配置 | 一次压测 | **4** |

## 9. 结论：你的猜测为什么不对（三条，按杀伤力排序）

1. **状态码语义不同格，证据跨格不可互证。** `client_max_body_size` 违例，nginx 的产物是 **413**（access.log 记 413，error.log 记 `client intended to send too large body`），它**没有任何路径**变成 502。502 只由上游交互失败产生（`upstream timed out` / `connect() failed` / `prematurely closed`）。你捡到的那条日志坐在「请求头校验」格，502 坐在「等待上游响应」格。**改限额不会让 502 少一条。**
2. **证据的分布形状和体积假说相反、和排队假说一致。** 体积违例是**确定性**的：同一个超限请求重试 100 次还是 413；而你明确说「用户刷新一下就好」——这只有**瞬态拥塞**能解释（刷新时排队已被消化）。另外「一天十几次、几乎都在白天忙时」是**负载相关**分布；体积违例会与上传发生量成比例，且数量级应该与 error.log 里那类报错的频次**相当**（你说它"刷得最多"，那可能是几百条/天，而 502 只有十几条/天——**两者数量差一个数量级，不可能是同源**）。
3. **在等价副本里，体积假说被直接打成了反例。** 对 127.0.0.1:19200 发 1KB / 4MiB / 5MiB / 9MiB 的 `POST /api/upload`：**全部 200，耗时 307–315ms，无 413 无 502**。而把并发从 8 抬到 9，502 立刻出现，且响应体自报 `upstream timeout after 800ms`。同一套副本，一条路走不通、另一条路 100% 走得通。
4. **方向性风险（额外一条，不属于"为什么不对"但要说）**：把 4m 改成 10m 会让 4–10MB 的上传真正进入后端链路，单请求占用槽位的时间变长、上传路径在后端的处理更重 ⇒ 按 §4.2 的恒等式，`D` 变大 ⇒ 排队时延变大 ⇒ **502 会变多**。修一个 413 的动作，可能是在给 502 加油。这不是说不要改（该改，见 §11⚠️2），而是**必须先修 502 的根，再放开限额**。

## 10. ✅ 验证方法（在真实系统上怎么定死，5 步，每步都有可执行命令/字段）

0. **先做算术，不碰配置**：`C_max = A × floor(T/D)`。把后端连接池/并发槽位 `A`、单请求时延 `D`、代理侧超时 `T` 三个数写下来，就能算出「并发超过多少必然 502」。三者任一拿不到，说明取证还没开始。
1. **给 nginx 加 correlated 日志**（只改格式 + reload）：
   ```
   log_format up '$remote_addr $time_iso8601 "$request" $status '
                 'urt=$upstream_response_time uct=$upstream_connect_time '
                 'us=$upstream_status ua=$upstream_addr rt=$request_time';
   ```
   然后：`grep ' 502 ' access.log | awk '{print $NF}' | sort -n | tail -20`
   - 若 `urt` 全部 ≈ 某个配置值（或 `rt` 顶在常量上）⇒ **确诊第 6 格超时**（对应 §4.3 的"截断指纹"）；
   - 若 `urt` 为 `-` 或 `uct` 很大 ⇒ 落在第 4 格（连接阶段），处置改为查后端存活性/backlog，而不是调 read timeout。
2. **按时间对齐，不按频率对齐**：取那十几条 502 的时间戳（精确到秒），`grep -n '10:22:4[0-9]' error.log`，看**同一秒**里出现的是哪一类错误。预期看到 `upstream timed out (110: Connection timed out) while reading response header from upstream`。**不要再用"刷得最多的报错"当线索**——在这个场景里频率排序是反向线索。
3. **看 502 的 URI 分布**：`grep ' 502 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn`。若 `/api/items` 等只读接口也有 502 ⇒ 与上传体积彻底无关（这一步 1 分钟，是否定你猜测最快的实证）。
4. **叠加负载曲线**：把 502 时间点与同一分钟的 QPS / 上游并发数叠在一张图上。预期 502 只出现在并发峰值。若 502 在低谷也出现 ⇒ 排队假说降级，转去查第 4/5 格（连接失败/后端重启）。
5. **复现（本机已完成，可复跑）**：
   ```
   node "D:\DeepSeek-levelup\lab-t1\load.js" 8  "http://127.0.0.1:19200/api/items"   # 8/8 全 200
   node "D:\DeepSeek-levelup\lab-t1\load.js" 9  "http://127.0.0.1:19200/api/items"   # 8×200 + 1×502
   node "D:\DeepSeek-levelup\lab-t1\load.js" 40 "http://127.0.0.1:19200/api/items"   # 0×200 + 40×502
   ```
   502 的响应体原文：`502 Bad Gateway: upstream timeout after 800ms`——它自己就是根因声明。

**验证目的论**：上面 1–4 步的判据是**互斥**的（`urt≈常量` / `urt='-'` / `prematurely closed` / 低谷也出现），所以任一条命中就排除其余；不要"感觉像"，要让 `$upstream_response_time` 的分布形状替你裁决。

## 11. ⚠️ 异常 / 矛盾 / 空白（必须报）

1. **⚠️ 那条日志里的 4194304 不是"限额"，是客户端声明的字节数。** nginx 的报文是 `client intended to send too large body: %O bytes`，`%O` 是**本次请求的 Content-Length**。你从这个数字反推"限额是 4m"是**锚定**：唯一能推出的是「限额 < 4194304」。更狠的是——nginx 的判定是**严格大于**（`content_length_n > client_max_body_size`），4194304 恰好等于 4m=4194304，**若生效限额真是 4m，这条请求根本不该被拒**。所以「看着像只写了 4m」这句本身就要打问号：真实生效值很可能小于 4MiB（典型是没被覆盖的默认值 1m，或 4m 写在别的 `server`/`location` 块里、或改写后没 reload）。**验证**：`nginx -T | grep -n -i client_max_body_size`，再按 `/api/upload` 的 location 匹配顺序确认**生效**的那一条。
2. **⚠️ 上传限额本身是真 bug，但它是另一条问题。** 业务限额 10MB 而实际拒绝 < 4MiB，意味着 4MB 左右的上传现在就在失败（413，用户侧可能表现成"上传失败/重试"）。请**单独**修它（改 `client_max_body_size 10m` 并确认生效块 + reload），但不要把它和 502 混成一个工单——混在一起会导致下一次复盘再次串线。
3. **⚠️ 数据空白：你没有给出** ① 502 的 URI 分布（是否含非上传接口）；② 真实系统的 `proxy_read_timeout` / `proxy_connect_timeout` / upstream `keepalive` 配置值；③ 后端连接池大小与单请求 p50/p99。这三项缺任意一项，上述归因在真实系统里只能算**高置信度推断**，不能算确诊。
4. **⚠️ 等价副本没有复现 413。** `front.js` 里没有等价的 body 限额逻辑，5MB/9MB 直接透传并返回 200。这本身就是一条证据：这份"等价副本"的等价性**只覆盖超时这条链**——副本的作者把哪个机制当成根，看副本模拟了什么就知道。真实系统里 413 那一支需要另外用 nginx 复现（`curl --data-binary @big.file`）。
5. **⚠️ 副本的数值不可直接搬到线上。** lab 的「4 槽位 / 300ms / 800ms」是缩小模型，线上真实值必须用 §10 的 `$upstream_response_time` 分布重新测；`C_max = A × floor(T/D)` 这个**结构**可搬，**数字**不可搬。
6. **⚠️ 一处我没能实测的断言**：修好超时后 502 会归零——因为改动需要重启服务进程，而本轮明确禁止启动新进程/占用端口。所以我给的是模型（`C_max` 从 8 → 40）与截断指纹，不是实测。若需要，可在获准重启后复跑同一组 N 验证。

## 12. 💡 灵感备注

- **"刷得最多的报错"在 SRE 场景里是最危险的线索选择器**：错误频率与故障因果是两套排序。正确的选择器是「与故障行同 request / 同秒」，其次是「与故障同状态码族」。这条可以沉成一个检查项：任何 5xx 复盘的第一步都必须是"按 request 对齐"，而不是"按 error.log 排序"。
- **延迟被钉在常量上是常量超时的指纹**：p99 ≈ 配置值，且 p999 不再增长，说明你不是在观测系统，你是在观测你的超时设置。这个信号在 Grafana 上非常好看（"p99 很稳"），极其容易被误读成"后端很稳定"。
- **"刷新一下就好"是一条被严重低估的判据**：它几乎唯一地指向瞬态。凡是"重试即成功"的故障，先怀疑拥塞/时序/缓存，再怀疑数据与配置。
- **同一个根可以同时解释两个 bug 的"改善"**：改超时会同时让 502 变少、让 413 的相对比例上升——这种"两个指标一起动"的假象，正是下一次串线的温床。修 502 与修 413 必须分两个工单、两次验证。
