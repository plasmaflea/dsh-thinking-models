## 先判你的猜测：4m → 10m 治不了 502

先把它钉死，因为它会污染后面所有回溯：

| # | 你的猜测要求什么 | 实际事实 | 判定 |
|---|---|---|---|
| 1 | body 超限能产出 502 | `client intended to send too large body` 是 nginx **413 Request Entity Too Large** 的伴生日志；nginx 从不因 body 超限返回 502（502 的定义是"与上游通信失败"） | ✗ 错误码不对 |
| 2 | 症状该与时间无关 | 限额是**确定性阈值**：>4MB 必失败、<4MB 必成功，与白天/夜里无关 | ✗ 与"忙时集中、一天十几次"不相容 |
| 3 | 刷新不该有用 | 静态阈值刷新一万次也一样失败；"刷新就好"要求一个**随负载/时序变化**的量 | ✗ 与"自愈"不相容 |
| 4 | 502 的 request 应是 `POST /api/upload` | 你只贴了 413 那条的日志上下文；`*48213` 是那条 413 的连接 id，**不是** 502 那条的连接 id | ✗ 未验证，且大概率不是 |
| 5 | 量级应吻合 | 若 502 由 body 超限产生，502 次数必须 ≈ 413 次数；而 413 因为存在 4~10MB 的常态化上传，量级远超"一天十几次" | ✗ 数量级矛盾 |
| 6 | — | 实测：本 lab **没有任何 body 限制**，5x1024x1024 字节 POST 顺序发 → `200`（319ms） | ✗ 直接反证 |

**4m/10m 不一致是真 bug，但它是另一类**：4~10MB 的上传会稳定吃 413。该修（改 `client_max_body_size 10m;` 或把产品限额降到 4m），但修完 502 一次都不会少。
你踩的是「**按日志刷屏量排序**」这个陷阱：413 是常态化高频错误，502 是一天十几次的低频错误，二者在同一份 error.log 里交错，刷得最多的那行天然不是 502 的成因。

## L2 逐层回溯

### 选轴（生成式：必经时序）

一个被代理的请求必然依次穿过 5 个环节，一格一步，不可省：

| 格 | 必经环节（为什么必然存在） | 该格故障的**专属**症状 |
|---|---|---|
| 格1 | 客户端 → 代理：建连、读请求行/头/体 | **413/400/499**；error.log `client intended to send too large body`、`client sent invalid ...` |
| 格2 | 代理 → 上游：建连（含 DNS/端口） | **502** + `connect() failed (111: Connection refused)`；**全量**失败、与并发无关、持续到修复 |
| 格3 | 上游处理：内部槽位/队列/下游依赖 | 延迟随并发**单调上升**并越过某条阈值；忙时集中；刷新即恢复 |
| 格4 | 上游 → 代理：响应返回/连接复用 | **502** + `upstream prematurely closed connection` / `recv() failed (104)`；或 **504** + `upstream timed out ... while reading response header` |
| 格5 | 代理 → 客户端：回写 | **499**、`client closed connection`；由慢客户端/大响应触发 |

三判据自检：**正交**（格1 只出 4xx，格2/3/4 出 5xx 但错误行互不相同）、**可生成**（时序一句话说明）、**可观测**（每格有专属 error.log 行）。

### 逐格回溯

- **格1 → 命中但产出码不对**：`...too large body: 4194304 bytes` 精确等于 4MiB，说明确有 4m 限额、且被拒的是刚好到界的 body，产出 **413**。它解释不了 access.log 里的 502。
  → 判定：**不是 502 的根**；作为独立问题（413 类）挂起，见挂起表第 1 行。
- **格2 → 不符**：建连失败是"全量、持续、与并发无关"，与"一天十几次、刷新就好"方向相反。挂起。
- **格3 → 命中**：忙时集中、并发相关、请求级自愈——三者同时满足。
- **格4 → 命中**：502 是"代理没拿到一个合法响应"，其触发条件正是格3 的排队时间跨过代理侧写下的**常量**时间预算。格3 是"排队变长"，格4 是"预算被击穿"，它们是同一结构的两个断点。
- **格5 → 不符**：499 不会进 access.log 的 502 计数。

### 定量判据（恒等式，用于把"命中"变成"必然"）

单请求完成时间与超时预算构成一条硬判据：

```
T_complete(N) = ceil(N / S) · D      (S = 上游并发槽位, D = 单请求耗时)
502  ⟺  T_complete(N) > T_budget
⟹ 502 起始并发  N_crit = floor(T_budget / D) · S + 1
⟹ 上游吞吐上限  μ = S / D
```

本 lab 代入 `S=4, D=300ms, T_budget=800ms`（`upstream.js:5-6`、`front.js:11`）：
`N_crit = floor(800/300)·4 + 1 = 2·4+1 = 9`，`μ = 13.3 req/s`。

**实测阶梯扫描（全部是零 body 的 `GET /api/items`，`node load.js N http://127.0.0.1:19100/api/items 1`）**：

| N | 200 | 502 | 预测 200 = min(N, 8) | 预测 502 = max(0, N−8) | 吻合 |
|---|---|---|---|---|---|
| 1 | 1 | 0 | 1 | 0 | ✓ |
| 2 | 2 | 0 | 2 | 0 | ✓ |
| 4 | 4 | 0 | 4 | 0 | ✓ |
| 6 | 6 | 0 | 6 | 0 | ✓ |
| 8 | 8 | 0 | 8 | 0 | ✓ |
| **9** | 8 | **1** | 8 | 1 | ✓ **拐点** |
| 10 | 8 | 2 | 8 | 2 | ✓ |
| 12 | 8 | 4 | 8 | 4 | ✓ |
| 16 | 8 | 8 | 8 | 8 | ✓ |
| 20 | 8 | 12 | 8 | 12 | ✓ |
| 24 | 4 | 20 | 8 | 16 | ✗（请求到达被摊开，实际可用"波次"少于 ceil(N/4)；方向一致） |

502 的采样原文：`502 Bad Gateway: upstream timeout after 800ms`（`front.js:23-28` 把上游超时 destroy 后统一转 502）。
对照组：N=2 连打 5 轮 → 10 次全 200，延迟锁死 307~316ms（单波次，永不可达 800ms 预算）。

### 类根 → 个例根

**类根（这一类在什么结构条件下必然可能发生）**：
> **代理层把一个"与负载相关的真实完成时间分布"，用一条静态常量（超时预算 / 池大小 / 限额）去代理；并且上游满载时是"无界排队"而不是"立即背压"。**
> 于是任何一个有限的超时预算都必然在某个并发处被击穿——排队时间随利用率 ρ→1 发散，而预算不动。表现出来的就是：504/502 间歇出现、集中在忙时、单请求重试即好、与任何具体业务逻辑无关。

这一类不依赖 node/nginx/具体数字：换任何代理 + 任何有槽位的后端，只要"有限预算 × 无界排队"，同一个 502 就会长出来。

**个例根（本次具体机制，挂在类根下）**：
1. **（本 lab 已证实，主因）超时预算 < 第 3 波排队完成时间**：上游只允许 4 个并发（`MAX_ACTIVE=4`，模拟持有 DB 连接），单请求 300ms；第 9 个并发起落入第 3 波，完成时刻 900ms > 800ms 预算 → 被 `up.destroy()` → 502。刷新只是让请求落回第 1/2 波。
2. **（线上待证实，同类的另一断点）预算与连接复用语义错配**：若 nginx `upstream { keepalive }` 的 `keepalive_timeout`（默认 75s）大于 Node 侧 `server.keepAliveTimeout`（默认 5s），池里会存在"上游已关、nginx 以为还活着"的连接，复用时得 `upstream prematurely closed connection ...` → 502。同理，若上传等重活把后端槽位占满，队列时间超过 `proxy_read_timeout` → 502/504。

⚠️ 这就是本案真正的空白：**你贴的那几行日志里，没有一行是 502 那条请求自己的 upstream 错误行。** 类根已经确定，个例根只能在 (1)/(2) 之间用下面 ✅ 验证 三招判别。

## L3 双根

**处置根（修本次）**
1. 先别改 `client_max_body_size`（那是治 413 的）——先给 502 那条请求**配对**：拿 access.log 里每个 502 的 `*connection id`（或加 `$connection`）去 error.log grep 同一 id，取它自己那行 `upstream` 错误。
2. 按错误行分流处置：
   - `upstream timed out ... while reading response header` / `recv() timed out` → 抬高 `proxy_read_timeout`（或上游超时）到 **p99.9 完成时间之上**，并同时加背压（见消解根）；只抬超时会把 502 换成"慢"。
   - `upstream prematurely closed connection` → 对齐 keepalive：`upstream` 的 `keepalive_timeout` ≤ 上游 `keepAliveTimeout`，或直接对该 upstream 关掉复用。
   - `connect() failed` → 查上游存活/端口，与 body 无关。
3. 上传类大 body 单独修：`client_max_body_size 10m;`（与 10MB 业务限额一致），或把产品限额改成 4m——二选一，别两头不一致。

**消解根（灭这一类）**
> **把代理层的超时/池大小/限额，从手写常量改成"由上游实测完成时间分布 + 拐点压测推导出的预算"，并让上游满载时走显式背压（快速 503/限流）而不是无界排队。**

- **① 不可发生判据**：若 `T_budget ≥ 目标并发下的 p99.9 完成时间`，**且**上游槽位满时立即返回 503/被 `limit_conn`/`limit_req` 挡在门外而不是继续排队——则"排队击穿超时 → 502"在**结构上不可能发生**：任何超预算的时刻都会先以可观测的背压（503 计数、限流日志）出现，502 不再是一个泄露负载的信号。注意只抬超时**不满足**本判据（只是把击穿点推远，仍是"无量纲的常量 vs 无界的排队"）。
- **② 可执行首边**：在 access.log 的 `log_format` 里加上 `$upstream_status $upstream_response_time $request_time $upstream_connect_time $upstream_header_time $request_length`（只加字段，零业务变更），然后在低峰窗口对一个只读接口做阶梯并发压测，画出 p50/p99 与首个 502 的并发拐点。**这一步是只读的，0 人日风险。**
- **③ 成本量级**：日志字段+拐点压测 ≈ 0.5 人日；`proxy_read_timeout`/keepalive 对齐 = 一行配置 + 一次 reload（分钟级）；`limit_conn`/`limit_req` 或扩后端槽位 ≈ 1–3 人日；上传通道分流（直传对象存储）≈ 1–2 周，单独排期。

## L4 迁移出口

消解根把问题从"调一个参数"提到"代理层与服务层的容量契约"，因此必须连带解决：

1. **上游容量与下游连接配比**：单实例并发槽位 `MAX_ACTIVE` ↔ DB 连接池上限 ↔ 代理 `maxSockets`，三者现在是三个互不知情的常量（本 lab 即 `upstream.js:6` 的 4 与 `front.js:8` 的 32）。
2. **超时/重试语义**：502/504 是否可重试、请求是否幂等、`proxy_next_upstream` 在单上游下等于没有重试。
3. **背压与限流**：`limit_conn`/`limit_req`、队列上限、503 语义与 429 语义的区分。
4. **可观测性**：`$upstream_*` 变量、慢请求采样、以 connection id 贯穿 access/error 两本日志的关联能力。
5. **重活隔离**：10MB 上传与 JSON API 不该抢同一个后端槽位（格外的热路径隔离）。

→ **本次问题降级为第 4 项（可观测性）＋第 1 项（容量配比）里的一个具体动作**：它本来就不是"一条配置写错了"，而是"没人知道 p99 是多少、拐点在哪、满载时该表现成什么"。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| `client_max_body_size` 4m vs 10MB 不一致 | **真 bug，但不是 502 的根** | nginx 该错误行必然产出 413；实测 lab 无 body 限制时 5MB POST 得 200 | 若 access.log 里 502 那条的 `request` 恰为 `POST /api/upload` 且 `$request_length > 4194304`，则需把"上游在读 body 阶段被重置"单列一格重判（注意此时更可能仍是 413/499 而非 502） |
| 格1 的 413 族（4~10MB 上传失败） | 成立，独立问题 | 4MiB = 4m 精确边界 | 改 `client_max_body_size` 或改产品限额后复查 413 计数归零 |
| 格2 代理→上游建连失败 | 不是 502 的根 | 建连失败是全量且持续的，与"一天十几次/刷新即好"方向相反 | 若 error.log 出现 `connect() failed (111)` 且同时刻 200 归零 → 重新纳入 |
| 上游 keepalive 空闲竞态 | 高度可疑，待判 | `common` 502 形态，忙时连接周转快会放大命中率 | 若 502 行是 `upstream prematurely closed connection` → 升为主因 |
| `proxy_read_timeout` 超时（应出 504） | 待判 | nginx 默认把该路径记成 504，而 access.log 是 502，二者不等价 | 若同 request 同时出现 504/502 混合 → 说明存在两条断点 |
| `worker_connections`/`somaxconn` 打满 | 待判 | 会产生 502/499 混杂且伴随 accept 报错 | 若 error.log 出现 `worker_connections are not enough` / `too many open files` → 纳入 |
| 上游 OOM/重启/GC 停顿 | 待判 | 会同时打出 502 与连接重置 | 若上游进程启动时间戳落在 502 窗口内 → 纳入 |
| DNS/resolver（`proxy_pass` 用域名） | 不是本类 | 只在 reload 后失败且**全量**失败，不随忙时 | 若 502 集中在 reload 之后 → 重新纳入 |
| `lifecycle / init / dependency` 三子层 | 本次不适用 | 服务在跑，200 大量返回 | 若 502 伴随进程消失/端口未监听 → 重新纳入 |
| 树外分支 `capacity-contract` | 登记 v2 候选 | 现有六子层是单进程视角，缺"进程间时间预算契约" | 出现第二个"预算 vs 分布"类故障时合并建设 |
| 树外分支 `hot-path-isolation` | 登记 v2 候选 | 大 body 上传挤占 API 槽位是独立成因 | 若确认 502 的相邻请求均为上传 → 并入主因 |

## 结论

1. **你的猜测不对，而且不对得很有信息量**：`client intended to send too large body` 是 **413** 的伴生日志，nginx 不会因此返回 502；4MB 限额是确定性阈值，无法产生"忙时集中、一天十几次、刷新即好"这三种时间特征。改 `client_max_body_size` 只会消掉 413（该改，独立改），**502 一次都不会少**。
2. **真正的根（类）**：代理层用静态常量（超时预算 / 连接池 / 限额）去代理一个随负载变化的完成时间分布，同时上游满载是无界排队而非背压。有限的预算必然在某个并发处被击穿——这是结构性的，不是"某条配置写错了"。
3. **本次的机制（个例）**：`502 ⟺ ceil(N/S)·D > T_budget`，即 `N_crit = floor(T_budget/D)·S + 1`。lab 里 `S=4, D=300ms, T_budget=800ms → N_crit=9`，实测 N=8 全 200、N=9 起出现 502 并随 N 线性增多（N=20 时 12/20 失败），与公式逐格吻合；对照组 N=2 连打 5 轮 0 次 502，且 5MB POST 顺序发返回 200（证明与 body 无关）。线上把 800ms 换成 `proxy_read_timeout`、`D` 换成上传/重活的阻塞时长、`S` 换成后端槽位，同一个式子直接可用。
4. **真正的验证方法**（三步，成本≈0.5 人日）：
   - ① `log_format` 加 `$upstream_status $upstream_response_time $request_time $upstream_connect_time $upstream_header_time $request_length $connection`；
   - ② 拿 502 那条的 connection id 去 error.log grep 出**它自己**的 upstream 错误行（不是刷屏最多的那行）；
   - ③ 对只读接口做阶梯并发压测，找出 502 起始并发 **拐点**，与 `floor(T_budget/D)·S + 1` 对照。若实测拐点 ≈ 公式值 → 根即确认；若 502 与并发无关而只在空闲后首次请求出现 → 改判因果②（keepalive 竞态）。
5. 修的顺序：**先取证（只读）→ 再对齐超时/keepalive → 再加背压与容量规划 → 最后（独立地）修 body 限额**。

## ⚠️ 异常/矛盾/空白

- ⚠️ **日志缺口（最关键）**：你贴的 error.log 片段里没有任何一条属于 502 请求自己的 upstream 错误行；`*48213` 是那条 413 的连接 id。缺这一行，个例根只能在两种断点间二选一。补它比任何配置改动都值钱。
- ⚠️ **数量级矛盾**：若 502 真来自 4MB 限额，502 次数必须与 413 次数同量级；你说 502 只有"一天十几次"，而 4~10MB 上传若在常态化发生，413 必然远多于此。二者不同源。
- ⚠️ **N=24 偏离模型**：预测 8/16，实测 4/20。原因是 24 个连接的建连与到达被摊开，前端收到请求的时刻不再整齐，可用"波次"少于 `ceil(N/4)`。含义：真实系统的 502 比模型**更糟**，公式只能当乐观下界用；也说明"按并发估算容量"必须用实测拐点，不能只做纸面计算。
- ⚠️ **502 ≠ 504**：nginx 的 `proxy_read_timeout` 超时通常记 504，而 access.log 是 502。这说明线上可能不止一条断点（超时 + 连接重置），或者上游（node）先关了连接。别把"超时"当成唯一解释。
- 空白：线上 `S`、`D`、`T_budget` 三个值我一个都不知道，只给了可测的公式与取证路径——不编造。

## 💡 灵感备注

- 这类问题的通用指纹是三个同现：**"忙时集中 + 单请求自愈 + 错误码属 5xx"**。命中这三个，几乎可以直接跳到"预算 vs 排队"，不必先看业务逻辑。
- 排查日志时按"刷屏量"取因果关系，是最常见的确认偏误入口：**高频错误解释的是高频问题，不解释低频问题**。正确做法是按 connection id / trace id 做**同请求配对**，而不是按时间窗口做**同区间并置**。
- `N_crit = floor(T_budget/D)·S + 1` 可以当容量规划的准入门槛：把它写进发布检查，超时预算与后端槽位一起标定，"间歇 502"这一类就变成发布期可算的数字。
