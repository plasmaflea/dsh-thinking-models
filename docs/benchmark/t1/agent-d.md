# 502 的根：不是 body 限额，是「网关放弃上游」的预算与上游容量之间没有任何契约

## L0 类别判定

**类别**：`software`（软件配置/并发/配额类）——判据：故障可由等价副本的代码与配置复现（lab-t1 复现成功），失败是确定性竞争的结果（同样的并发数必得同样的 502 比例），与物理介质无关。
**已排除**：硬件故障（无 CRC/ECC、重启后行为不随机器变化）；权限/账号体系（症状不随主体变化）；组织流程（技术链路已能精确复现，无需引入人为因素）；纯网络链路问题（同机 127.0.0.1 回环上即可复现，排除了链路质量）。网络**不作为大类排除**，而是作为未建节点登记（见挂起表「树外分支」）。

## L1 树实例化

## L2 逐层回溯

### 选轴（生成式，非列举）

轴由**一次请求穿过网关的必经时序**生成——任何反向代理架构下这六格必然存在，一格不可省：

| 格 | 必经环节 | 该格故障的可观测症状 |
|---|---|---|
| 格1 | 客户端 → 网关：请求行/请求头解析 | 400 / 408 / 414 / 494；`client sent invalid ...` |
| 格2 | **请求体接收与体积限额校验**（client_max_body_size） | **413** + `client intended to send too large body`；或 `a client request body is buffered to a temporary file` |
| 格3 | 上游选址与连接建立（DNS / upstream / connect） | **502** + `no live upstreams` / `connect() failed (111)` / `host not found in upstream` / `upstream timed out (110) while connecting` |
| 格4 | **上游排队/取用并发槽位**（连接池、DB 池、keepalive 池） | 延迟阶梯式上抬；**502/504** + `upstream timed out (110) while reading response header from upstream`；等价副本中为 `upstream timeout after 800ms` |
| 格5 | 上游处理与响应头返回（上游崩溃/响应非法） | **502** + `upstream prematurely closed connection` / `upstream sent invalid header` / `recv() failed (104)` |
| 格6 | 响应回传客户端（客户端先断） | 499 / `client closed connection`；此时状态码已定，**不会变成 502** |

**三判据核对**：正交——格2 的失败发生在网关自己拒绝、根本没连上游；格4 的失败必然已经连上上游。**单字段判据：`$upstream_addr` 为 `-` ⇒ 格2；非 `-` ⇒ 格3/4/5。** 可生成——请求必经这六步，无一步可省。可观测——每格有专属日志字样，不重叠。

### 逐格回溯

- **格1**：无对应日志，空。判「此处无贡献」。
- **格2**：**有症状但症状类型不对**。`client intended to send too large body: 4194304 bytes` 这条 line 的归属是 **413 Request Entity Too Large**，因为它是 nginx 在客户端 body 尚未转给上游时自行拒绝的路径：`$upstream_addr = "-"`、请求计数 `*48213` 那条在 access.log 里同一时刻应是 413 而非 502。**全空列判据的反向用法**：格2 已有症状而 502 仍在发生 ⇒ 格2 解释不了 502，必须继续往格4/5 看。这就是提问者猜测的落点，也是它错位的地方。
- **格3**：若命中，502 会伴随 connect 类字样；提问者未给出，副本中也无（服务在监听）。留挂起。
- **格4**：**命中**。等价副本里同一现象精确复现，且成因可写成闭式：

```
成功请求数 = min(N, floor(T_timeout / Δ) × S)
失败请求数 = max(0, N − floor(T_timeout / Δ) × S)
T_timeout = 800ms（front.js:11 的手写常量 UPSTREAM_TIMEOUT）
Δ = 300ms（upstream.js:5 单请求处理耗时 DELAY）
S = 4（upstream.js:6 同时处理的槽位数 MAX_ACTIVE，模拟后端持有的 DB 连接）
⇒ floor(800/300) = 2 波 × 4 槽 = 8；N > 8 时，第 9 个及以后必然 502
```

实测（`node load.js N http://127.0.0.1:19400/api/items`，全部实跑）：

| 并发 N | 200 | 502 | 延迟 p50 / max (ms) |
|---|---|---|---|
| 4 | 4 | 0 | 318 / 319 |
| 8 | 8 | 0 | 621 / 637 |
| 9 | 8 | **1** | 629 / 813 |
| 12 | 8 | **4** | 639 / 826 |
| 16 | 8 | **8** | 833 / 836 |
| 32 | 8 | **24** | 832 / 834 |

四个 N>8 的点全部落在 `min(N,8)` 上，误差 0——这不是「并发高了就坏」的模糊现象，而是**超时预算被两波排队吃光**的确定性结果（第 3 波起 900ms > 800ms）。
- **格5**：副本无「上游崩溃/响应非法」症状（无 restart、无 `prematurely closed`），502 又与并发阈值严格吻合 ⇒ 判非本次根，挂起。
- **格6**：空。

### 放大因子（个例根的另一半）

front.js:22-24 用 `up.destroy(new Error('upstream timeout after 800ms'))` 放弃等待，但**这个放弃不会撤销上游已经排进队列的工作**（upstream.js:12-19 的 `queue` 里已 resolve 的等待者继续占槽 300ms）。于是超时的死请求继续消耗槽位，形成**积压自放大**。实测两连击：

| 场景 | 结果 |
|---|---|
| 32 并发突发**刚结束**，立刻发 1 个请求 | **502**，814ms（排在死请求后面） |
| 同上，等 3 秒再发 1 个请求 | **200**，312ms |

这就是「**用户刷新一下就好**」的机制：不是修好了，是积压排空了。

### 类根

> **这一类（网关在高负载下随机返回 5xx 且自愈）的结构条件：网关「放弃上游」的判据（超时预算）与上游的真实服务能力（并发槽位 × 单请求耗时 × 允许排队深度）之间没有任何契约，且网关侧的并发上界远大于上游上界——超订 8 倍（front.js:8 `maxSockets: 32` vs upstream.js:6 `MAX_ACTIVE: 4`），既无背压也无快速失败。**

**个例根（挂其下）**：本系统里超时被写成 `800ms` 这个手写常量，而上游 4 槽 × 300ms 的第三波就已经 900ms；`maxSockets=32` 让 32 个请求同时压在一台只有 4 个槽的上游上；超时即 destroy 却不传播取消，死请求继续占槽。三者相乘 ⇒ 任何瞬时并发 > 8 的秒级窗口里，第 9 个之后的请求必然 502，突发结束后还有约 1.8s（24 个死请求 × 300ms ÷ 4 槽）的残留窗口。

### 为什么「改 10m」不是根（逐条证伪，不只一条）

1. **状态码类别错配**：`client intended to send too large body` 的输家是 **413**，不是 502。502 的定义是「网关没能从上游拿到合法响应」，413 是「网关没打算把请求交给上游」。两者的请求集合由构造互斥（`$upstream_addr` 为 `-` vs 非 `-`）。
2. **日志相邻 ≠ 因果相邻**：提问者取的是「error.log 里刷得最多的那条」，这是**频次最高的错误**，不是**502 对应的错误**。真正的 502 伴生行（格3/4/5 任一）从未被拿出来——这是本题最大的证据缺口。
3. **确定性矛盾（不用碰服务器就能证伪）**：体积限额的失败对**同一请求是确定性的**——同一个 4MB 文件重传，永远 413，刷新一万次也一样失败。而现象是「刷新一下就好」＋「几乎都落在白天忙的时候」⇒ 决定成败的是**当时的排队状态**，不是 body 大小。
4. **等价副本反证**：lab-t1 里根本没有 body 限额这道闸门，**4MB POST /api/upload 实测返回 200**（不是 413）。也就是说副本里「用户的修法」根本无处可改，而 502 照样按上表精确出现。把 `4m` 改成 `10m` 在任何一条实验里都不会让 502 少一个。
5. **方向还可能有害**：10MB 的 body 在 `proxy_request_buffering on` 下要落临时文件、占用更多 worker 连接与磁盘 IO，上游侧也要多花时间读 body——在「排队已经吃掉超时预算」的系统里，放宽体积只会让 格4 更紧张。
6. **但它是另一个真 bug**：应用限额 10MB 与 nginx 实际 4m 不一致，会让 4–10MB 的上传稳定失败（且报错语义是 413，用户会看到「上传失败」而不是「502」）。必须修，只是**修的是另一格**。注意提问者说「看着像只写了 4m」——这是**未验证**的（见 ⚠️）。

## L3 双根

**处置根（修本次）**——让超时预算与并发上界由上游容量派生，而不是拍常量：

1. 网关侧并发上界压到上游槽位量级：`maxSockets` 32 → ≤ 4（等价于 nginx 侧把 upstream keepalive 池/worker 连接数与后端连接池对齐）。这一行改动就能把「排队深度无界」变成「排队深度有界」。
2. 超时值改为实测派生：`UPSTREAM_TIMEOUT ≥ p99(处理耗时) × (1 + 允许排队深度)`，本副本即 `300ms × 允许深度`；要么给足（≥ 2.4s 覆盖 32 并发），要么反向——**把排队变成显式的 503 + Retry-After 快速失败**，不占着连接干等。
3. 超时即取消：`up.destroy()` 时同步通知上游（或上游在写响应前检查 `req.aborted`），让死请求立刻释放槽位，消除积压自放大。

**消解根（灭这一类）**：把「网关放弃上游」的条件从**手写常量**改为**由容量与实测派生的契约**——即网关侧并发上界 ≤ 上游并发上界、超时预算 ≥ 实测 p99 × 允许排队深度、放弃时传播取消，且放弃原因按类分桶可观测。

- **① 不可发生判据**：若当时采用它，则「负载在容量余量之内时随机 502」在结构上不可能发生——同一时刻要么得到 200，要么在真正超容时得到显式的 503/限流，而不是概率性的 502。注意：这不是「变少见」，因为该结构下**不存在「排到了但被网关提前放弃」这一状态**——排队深度一旦被上界约束，超时预算就恒大于最坏排队延迟。
- **② 可执行首边**（很小）：在 access.log 的 log_format 里加 `$upstream_response_time $upstream_addr`（先能看见），同时把 `maxSockets` 压到 4 跑一次同样的压测。一小时内的改动。
- **③ 成本量级**：上面第 1、2 条＝**小时级**配置改动；第 3 条（取消传播 + 排队超时/处理超时分离）＝**人日级**代码改动；引入独立背压/限流层＝**人日级**。全部远低于「换掉 nginx」的周级。

## L4 迁移出口

消解根指向「把容量契约与取消语义显式化」，迁移必然带出这些问题：

1. **可观测性**：502 必须按原因分桶（upstream_timeout / connect_refused / prematurely_closed / upstream_reset），且与 413 类日志分表——**本次误判的直接原因就是「按频次看错误日志」**。首件交付物：一张「502 按原因 × 分钟」的图，与 QPS 曲线同屏。
2. **配置管理**：超时值、并发上界、连接池大小三类数字必须成对出现（改一个必须核另一个），禁止手写魔数；`client_max_body_size` 与应用 10MB 限额的一致性要做启动校验/CI 断言，不靠肉眼 `看着像`。
3. **容量规划**：上游槽位（DB 连接池、worker 并发、keepalive 池）升级为一等公民，纳入扩容剧本；扩容时同步改网关侧上界。
4. **客户端契约**：413 与 502 的语义要在 API 层区分（413 给明确的「文件过大 + 上限值」文案与错误码），避免用户把「上传失败」和「服务故障」混成一类投诉。
5. **组织能力**：值班 SOP 第一条从「看 error.log 刷得最多的那条」改为「先看 502 行的 `$upstream_addr` 与 `$upstream_response_time`」。
6. **树外分支（待登记节点）**：`software v2 候选 —— 新增第七子层 gateway/网关语义层（超时预算 / 背压 / 取消传播）`。理由：本次类根落在 `quota × concurrency × config` 三个子层的交叉处，任何单一子层都容纳不下它，属结构性空档；不升版就必然出现「树里没这一格 → 静默丢弃」的剪枝借口。另：索引里 `network` 节点仍是「待建候选」，本次用到了「超时形态」这一类判据，需补核查。

→ **本次问题降级为上面第 1 项（可观测性）与第 3 项（容量规划）的子项**：一旦「排队延迟 p99 与超时预算」成了同屏指标，「再补一条 body 限额就能修 502」这种误判在流程上就不会发生。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|

## 结论

1. **你的猜测不对**，不对在两个层面：**状态码类别**（`client intended to send too large body` 的输家是 413，不是 502；它对应的请求压根没交给上游）与**存在性**（体积限额的失败是确定性的，同一个文件重传必败，刷新不可能好；而你的现象是自愈的）。
2. **这个「最高的错误频次」是被挑出来的**：你取的是 error.log 里刷得最多的那条，而不是与 502 同一请求的那条。真正的 502 伴生行（`upstream timed out` / `connect() failed` / `prematurely closed`）你还没贴出来——这是本题唯一的证据缺口。
3. **真正的根（类）**：网关「放弃上游」的判据（超时预算）与上游真实容量（并发槽位 × 单请求耗时）之间没有任何契约，且网关侧并发上界超订 8 倍、超时不传播取消。**个例**：800ms 常量 < 上游第 3 波排队 900ms，`maxSockets=32` 把 32 个请求同时压到 4 个槽上，`min(N,8)` 之外全灭；超时后死请求继续占槽，突发结束还有约 1.8s 残留窗口——「刷新一下就好」就是这 1.8s。
4. **4m → 10m 仍然要改**，因为它是另一个真 bug（4–10MB 上传稳定 413，且用户会被误导成「服务挂了」），但它对 502 的贡献是**零**，改完 502 一个都不会少。
5. **生产侧验证（按代价从低到高，前两步就能定案）**：
   - ① 单字段判据：access.log 加上 `$upstream_addr $upstream_response_time`。body-size 那类行的 `$upstream_addr` 必为 `-`；502 行的必为后端地址。**两者的请求集合由构造互斥**，一眼分家。
   - ② 三个数字：`grep -c 'client intended to send too large body' error.log`、access.log 里 413 的条数、access.log 里 502 的条数。若第一个 ≈ 第二个、而第三个自成一列 ⇒ 该 error line 已被 413 全额消费，不可能是 502 的成因。
   - ③ `grep -E 'upstream timed out|no live upstreams|connect\(\) failed|prematurely closed|recv\(\) failed' error.log` 按分钟聚合，与 access.log 的 502 分钟对齐；命中的字样决定落在格3/4/5 的哪一格。
   - ④ 只改超时与并发上界（把 upstream 侧池子对齐、`proxy_read_timeout` 由实测 p99 派生），**不改 body 限额**，观察 502 频次；同时用「临时把上传端点摘出该 upstream」做反向对照——若 502 依旧，上传彻底出局。
   - ⑤ 生产侧要拿的两个数：502 分钟的 QPS 峰值、以及上游延迟 p99。若 502 全部落在峰值分钟且 p99 逼近超时值，本结论在生产上同样成立。
6. **副本侧已经复现**（不是推测）：改 `maxSockets` 到 4 或把超时抬到 ≥ 2.4s，即可让 `min(N,8)` 的天花板消失——这是给根做的单变量对照，比改 body 限额的实验成本还低。

## ⚠️ 异常 / 矛盾 / 空白

- ⚠️ **最大的空白**：提问者没给出与 502 同一请求的 error.log 行。`upstream timed out` / `connect() failed` / `prematurely closed` / `no live upstreams` 一个字都没出现——现在这一层是「按最可能的类根推断 + 副本复现」，生产侧仍需第 ⑤ 步坐实。
- ⚠️ **矛盾**：「看着像只写了 4m」是目测，未用 `nginx -T` 验证，也没说明该指令在 http/server/location 哪一层。若某个 location 有 10m 覆盖，那连 413 都没有发生过。
- ⚠️ **空白**：`4194304 bytes` 恰好等于 4 MiB 整——说明客户端发的 body 正好压线或超线（很可能是分片/整文件边界）。若生产上 4MB 上传占比很低，这条日志刷得最多反而说明**采样窗口是「出故障时顺手翻日志」的窗口**，不是全量窗口，会系统性放大偶发高频错误的存在感。
- ⚠️ **副本与生产的一处不等价**：副本的超时落在网关自己身上（502），而真实 nginx 里「连接阶段超时」是 502、「读响应头超时」是 504。因此生产上若看到成对出现 502/504，同属类根 A/B，结论不变；但**不能**用「我看到的是 502 不是 504」来推翻本结论。
- ⚠️ **副本仍有一个 env 未核**：19400 端口的实例是通过 `FRONT_PORT` 起的，其余几对实例走默认 18080。这不影响结论（源码常量相同，且 800ms 的报错文本直接来自 front.js:11/23）。

## 💡 灵感备注

这次误判的**形态**比结论更值钱：**「按频次取错误日志」把低成本的错误候选送上了第一位**。份额为零的候选只要 Cost 足够小（看一眼日志），在 `Share × Lever ÷ Cost` 里就能挤掉份额唯一的正确候选——因为「份额为零」在排序里乘出来是零，但人的注意力不这么算。工程上的对策只有一条：**先按「同一条请求」把日志 join 起来**（`$request_id` 或时间戳+请求计数），再谈频次。任何「高频错误 ⇒ 它是根」的推理，都应该先被这条 join 打断一次。
