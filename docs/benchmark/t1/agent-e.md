## L0 类别判定

**类别**：软件问题 · `concurrency`（并发与时序）＋ `quota`（资源配额）两子层的交叉，具体形态是「过载被误报为故障」的容量契约缺失。
**判据**：故障可复现且可归因于确定性时序（并发数越过阈值即 502，数量精确可算），失败现象是请求**已经到达**后端却由代理单方面裁断，与物理介质无关。
**已排除**：hardware（无随机/跨机征象，症状与并发强相关）；network（全链路 127.0.0.1 精确复现）；权限/账号（无 ACL/令牌相关症状）；组织流程（技术层已有确定性复现，不落在这一支）。

## L2 逐层回溯（轴 = 一次请求穿越系统的必经时序，7 格不可省）

| # | 轴格（必经步骤） | 该格故障的可观测症状 | 本例判定 |
|---|---|---|---|
| 1 | 客户端 → 代理：建连/头部 | 连接重置、TLS 失败、客户端侧 4xx | 无症状 |
| 2 | 代理 body 准入（`client_max_body_size`） | **413** + error.log `client intended to send too large body` | ✅ 命中，但产出 413，不是 502 |
| 3 | 代理 → 上游建连（连接池、DNS、端口） | 502 + `connect() failed` / `ECONNREFUSED` | 无症状（同突发内 200 与 502 交错，上游一直活着） |
| 4 | 上游准入（并发槽位 / 排队等待） | **排队时延无上限且不表达** → 沉默、直到代理超时 | ✅ 命中，本例真正的时序瓶颈 |
| 5 | 上游计算（300ms/请求） | 无异常，p50 稳定 308ms | 无症状 |
| 6 | 上游 → 代理回响应头 | **502 `upstream timeout after 800ms`**（响应未在预算内到达） | ✅ 命中，即 502 的直接产生点 |
| 7 | 代理 → 客户端写回 | 客户端断开、写失败（会掩盖 502 的真实来源） | 无症状 |

全空列判据检查：**不是全空**——格 2 有症状但产出码不同（413），格 4/6 有症状且产出 502，坐标轴成立。

**量化（不等式写死，先定判据再谈修）**：上游槽位 `S=4`，单请求 `T_s=300ms`，代理等待预算 `T_to=800ms`。位置 p 的请求完成于 `⌈p/S⌉·T_s`，502 ⟺ `⌈p/S⌉·T_s > T_to` ⟹ `⌈p/4⌉ ≥ 3` ⟹ `p ≥ 9`。即

- 临界并发 `K* = S·(⌈T_to/T_s⌉ − 1) + 1 = 4·(3−1)+1 = 9`
- 502 条数 `= max(0, K − 8)`

**根因链**：
代理侧 `front.js:11 UPSTREAM_TIMEOUT = 800`（把「等响应」当成「上游是否故障」的判据）
→ 上游 `upstream.js:6 MAX_ACTIVE = 4`（有界容量）＋ `upstream.js:9 const queue = []`（**无界队列、无排队超时、饱和不表达**）
→ 代理 `front.js:8 agent = new http.Agent({keepAlive:true, maxSockets:32})` 允许一次放行 32 条并发，是槽位的 **8 倍**
→ 代理自己制造的最坏排队 `(32/4 − 1)·300 = 2100ms`，是它自己愿意等待的 `800ms` 的 **2.6 倍**
→ 白天并发峰值一到 9，第三波（900ms）越线，被代理单方面判死 → 502；刷新即好，因为刷新时队列已消化、单请求独享槽位。

**→ 类根**：系统缺少「饱和」的显式表达——后端的有界容量与排队状态既不能告知代理、也无法告知客户端，代理只能用固定超时去**猜**上游是否活着，于是「过载」被系统性地误报成「网关故障」。任何「固定超时 + 无界排队」的组合都必然把过载转成 502；这不是这台机器坏了，是这一结构在过载下必然输出 502。（与知识树 `software` 的类根同构：**本该由上游自己掌握的「我是否饱和」的判断权，被外部机制代持了**。）

　└ **个例根（本次）**：`UPSTREAM_TIMEOUT=800ms` 小于「`maxSockets 32 ÷ 槽位 4 × 300ms` 的最坏排队 2100ms」，且线上对应的 `proxy_read_timeout` 若被调小到同一量级，则白天并发 ≥9 的每一次尖峰都会稳定产出 `K−8` 条 502。个例根是类根的一个实例，不是平行清单。

## L3 双根

**处置根（修本次）**

1. 把代理的「上游响应等待预算」与自身放行的并发量对齐：本环境等价动作是把 `front.js:11` 的 `800` 提到 `≥2100ms`（工程上取 5000ms）；线上等价项是核对 `proxy_read_timeout` / `proxy_connect_timeout`（nginx 默认 60s，**若线上被动过，这本身就是最大嫌疑**）。
2. 把 `maxSockets` 从 32 降到 ≤4（或给上游加队列上限），让代理不再制造自己等不起的排队。
3. `client_max_body_size 4m → 10m` **照做**，但明确它的收益是「4–10MB 上传不再 413」，**不是**「502 消失」。

**消解根（灭这一类）**：让「饱和」由上游自己说出来，代理不再代持这个判断——上游槽位耗尽时**立即快速失败**（`503 + Retry-After`），代理只把真实断连/真实无响应判为 502；并且并发上限、超时预算、body 限额由**同一份容量参数**派生，不允许三个数各自拍脑袋。

- **不可发生判据**：若上游在槽位耗尽时立即回 503（带 Retry-After），且代理的超时预算由 `maxSockets × 单请求最坏耗时` 反推得出，则「排队被误报成 502」在结构上不可能发生——同类现象只会表现为「可预期的 503 + 客户端退避」。注意：**单纯把 800ms 调大不满足这条判据**（只是把 9 抬到 25，过载仍在、误报仍在），所以它只能进处置根，不能进消解根。这一条是本次双根分开的关键。
- **可执行首边**（从现状出发的第一步，很小）：在 `upstream.js` 的 `acquire()` 上加排队预算——`await Promise.race([acquire(), sleep(500).then(() => { throw new Error('queue budget exceeded') })])`，超预算直接 `res.writeHead(503, {'retry-after': '1'})`。约 10 行。
- **成本量级**：源码改动 ≤20 行 + 一次配置对齐 + 一次压测验证，人时 < 半天；不换架构、不迁数据。定量留给 📐 公式图，这里只给量级。

## L4 迁移出口

消解根**不指向换环境/换架构**（它指向「把控制权交还上游」这一层结构改动），所以本轮 L4 记「不触发强制迁移」；但一旦把容量契约上收到统一入口（nginx 或 API 网关）统一实施，会产生下列新问题，必须一并成立：

1. **参数派生**：`worker_connections` / `limit_conn` / `proxy_read_timeout` / `maxSockets` / `client_max_body_size` 必须由同一份容量模型算出，改任何一个都要过同一次评审；
2. **状态码语义重划**：502（真故障）／503+Retry-After（饱和）／429（限流）三种语义，前后端与客户端 SDK 都要按新语义退避；
3. **可观测性**：新增「排队时延」与「槽位占用率」两个指标，让饱和在监控上可见，而不是只能在 502 里被发现；
4. **客户端契约**：`POST /api/upload` 的幂等性（能否安全重试），否则快速失败会变成重复上传；
5. **组织能力**：值班手册不再把「改大一个配置」当止血手段。

→ **本次问题降级为**：上述第 1 项「参数派生」下的一个实例。

## 结论（三句话）

1. **你的猜测不对，而且不只差一个数值**：`client_max_body_size` 超限在 nginx 里产出的是 **413**，裁断发生在「请求体准入」那一格，此时 upstream 还没被选中，所以它在结构上**产生不了 502**。那条 error.log 是真的（4194304 = 4MiB，`4m` 确实生效），但它的产物是那批上传的 413，不是 502。
2. **真正的根**：代理用固定的 `800ms`「等上游响应」预算冒充「上游是否故障」的判据，而上游是「4 个槽位 + 无限排队 + 饱和不表达」。白天并发一过 **9**（`4·(⌈800/300⌉−1)+1`），第三波请求要等 900ms > 800ms，被代理单方面判死 → 502；刷新即好，因为刷新时队列已消化。这同时解释了「偶尔」「白天多」「刷新即好」三条现象，而 body 一条都解释不了。
3. **该改什么**：`client_max_body_size 10m` 照做（修 4–10MB 上传的 413，另案）；修 502 要做的是两件事——先把 `proxy_read_timeout`/`maxSockets` 与上游真实容量对齐（处置），再让上游槽位耗尽时自己回 `503 + Retry-After`（消解），否则这类「过载伪装成网关故障」会随流量增长按 `K−8` 线性回来。

502 的耗时 `p50=831ms`（贴着 800ms 超时线），成功请求 `min=308ms`（= 上游单请求 300ms）。502 文案即 `502 Bad Gateway: upstream timeout after 800ms`。

**B. 持续中等并发（模拟白天忙时）**：`load.js 10 ... 5` → 每轮稳定 `8×200 + 2×502`，累计 `40×200 + 10×502`（20% 失败率）。这就是「一天十几次、只在忙时」的生成机制：**均匀、可预测、随峰值出现次数累加**，不是随机故障。

**C. body × 并发 2×2（决定性证据：body 不是变量，并发才是）**

| 并发 | body | 结果 | 耗时 |
|---|---|---|---|
| 1 | 6MB | **200** | 328ms |
| 1 | **10MB** | **200** | 322ms |
| 20 | 100KB | 200×8 + **502×12** | 848ms |
| 20 | 6MB | **502×20** | 1032ms |

并发 1 时 10MB（等于业务限额）上传成功 → 说明「大 body 本身」不产生 502；并发 20 时 100KB 也照样 12 条 502 → 说明 502 与 body 大小无关。body 大只是把单请求拖慢、把排队时延推得更高（同机制内的放大器，不是根）。

**D. 反证 keepalive 死连接**：空闲 8s 后单发 3 次 → 200 / 315ms、200 / 310ms、200 / 309ms。挂起表中该行据此判非根。

**E. 线上验证方法（按成本从低到高，建议做前两项就够定性）**

1. **connection id 对齐**（一次 grep，最高性价比）：取 access.log 里一条 `status=502` 的行，拿到它的 `*NNNNN`，在 error.log 里 grep 该 id。若得到 `upstream timed out (110: Connection timed out) while reading response header from upstream` → 就是本例机制；若得到 `connect() failed` → 上游真挂了（另一支）；若确实得到 body 过大那行 → 才需要回退到 body 假设（但那时状态码应为 413）。
2. **`$upstream_response_time` 分布**：502 的该值应聚在 `proxy_read_timeout` 附近；同时看成功请求的 p99 是否也贴着超时线——「p99 紧贴超时线 + 502 也贴在同一处」是过载误报的指纹。
3. **并发阶梯二分**：用压测在 8/9/12/16/24 五档各打一轮，看 502 是否呈 `K−8` 型阶跃而不是随 body 变化。
4. **单一变量对照**：临时只把 `proxy_read_timeout` 调到 5s（其余不动），若 502 消失且 p99 抬到 2s 量级 → 过载误报确证；若 502 不减 → 回挂起表第 3/5 行。
5. **补两个指标**：上游排队时延、槽位占用率。饱和应该在监控里可见，而不是只能在 502 里被发现。

## ⚠️ 异常/矛盾/空白

1. **最强的自相矛盾**：题面说 502，日志给的却是 body 超限条目。`413` 与 `502` 不可能由同一条请求路径产生——这一条本身就该让人停手，而不是去改配置。
2. **502 与上传的绑定只存在于日志文本，不存在于机制**：可复现环境里 502 出在零 body 的 `GET /api/items` 上，与上传接口无关。真实系统很可能也是「上传只是白天高峰的一部分流量」，被当成了相关。
3. **高并发段模型失准**：`K=16` 实测 11 条 502（模型 12），`K=20` 两次跑分别 12 与 19。已定位的偏差来源未确认，挂起为「代理侧 backpressure / agent socket 行为叠加」，不影响 `K∈[9,15]` 的精确匹配与结论。
4. **线上真实超时值未核**：nginx `proxy_read_timeout` 默认 60s。若线上从未被调小，则本例的 800ms 只是 lab 的等价物——机制不变，但「阈值 9」要按线上真实值重算：`K* = S·(⌈T_to/T_s⌉−1)+1`。这是唯一的数值依赖，必须在线核对。
5. **`4m` 与「业务 10MB」不一致是独立的一颗雷**：4–10MB 的上传现在会稳定 413（用户看到的是上传失败），只是它返回 413 不返回 502，所以从没被和投诉连起来。修它是对的，但别指望它治 502。

## 💡 灵感备注

这个 502 的恶劣之处在于它把**过载伪装成了故障**：监控上看到的是「网关不稳定」，于是所有人往代理/网络/换机器方向查，而真正缺的是后端「快速失败」的能力。第二个反常识点：body 限额配错（4m vs 10MB）和 502 这两件事在同一时段同时发生、又都出现在 error.log 里，制造了一个几乎无法靠肉眼识别的混杂——**唯一能拆开它们的动作是 connection id 对齐**，而这一步只需要一次 grep。
