## 结论

**约 300–380 人日，中位数 ≈ 330 人日**（不含实时多人协同、不含数据库视图、不含 AI）。

对照团队容量：3 人 × 6 个月 ≈ 每人 126 工作日 = **378 人日毛容量**，扣除休假、会议、上下文切换（系数 0.8）后 **有效容量 ≈ 300 人日**。

也就是说：**工作量和容量基本持平，没有缓冲。** 6 个月 3 人做得出来，但前提是范围卡得很死 + 编辑器不自己造轮子。任何一项“顺便加一下”都会直接穿透到延期。

## 估算口径（先对齐这 5 条，否则数字没意义）

| 假设 | 取值 |
|---|---|
| 人员水平 | 3 人均为熟手（3–5 年+），无招聘、无新人 ramp |
| 时间 | 6 个月 × 21 工作日 ≈ 126 人日/人，总计 378 |

## 工作分解（WBS）

### 前端 ≈ 130–160 人日

| 模块 | 人日 | 说明 |
|---|---|---|
| 编辑器内核 | 30–45 | 块树数据模型、选区/光标跨块移动、Enter 分块 / Backspace 合并块 / Tab 层级、粘贴解析 |
| 块类型（8–10 种） | 18–25 | 段落、H1–H3、有序/无序/todo、引用、代码块、分割线、图片 |
| 行内富文本 | 8–12 | 加粗/斜体/行内代码/链接 |
| Slash 菜单 + 悬浮工具栏 + 拖拽手柄 | 12–18 | Notion 的“手感”主要靠这块，容易被低估 |
| Undo/Redo | 4–8 | 用编辑器库自带可压到 4 |
| 页面侧边栏 + CRUD + 面包屑 + 嵌套 | 12–18 | 树形拖拽排序比想象中麻烦 |
| 自动保存 / 草稿 / 冲突提示（前端侧） | 6–10 | 防抖 + 重试 + 离线态 |
| 搜索 UI、导出入口 | 4–6 | |
| 响应式 / 窄屏可用 | 5–8 | 可直接砍掉 |
| 联调、bug、性能打磨 | 20–30 | 按经验值，不要省 |

> **关键文档/决策点**：编辑器内核占前端工作量 30% 以上。用 Tiptap / ProseMirror / Lexical 起步可把它压到 30 人日左右；自己写 block tree + selection(selection mapping) 引擎会多出 **40–60 人日**，且大概率踩坑。这是整个估算里**最大的一个杠杆**，第 1 周就要定。

### 后端 ≈ 85–105 人日

| 模块 | 人日 |
|---|---|
| 数据模型（workspace/page/block/user/permission）+ 迁移 | 8–12 |
| 认证鉴权（邀请、分享链接、角色） | 12–18 |
| Page/Block API（批量 diff 保存、排序、事务） | 18–25 |
| 自动保存 / 版本 / 乐观锁冲突 | 10–15 |

| 全文搜索（Postgres FTS 足够） | 6–10 |
| 导出 Markdown / HTML | 5–8 |
| 基础设施（部署、CI、监控、备份） | 10–15 |

### 产品 & 设计 ≈ 25–40 人日
需求与范围定义 8–12、线框/交互原型 8–12、视觉与规范（用成熟 UI 库压缩）6–10、早期用户测试 4–8。

### 测试与发布 ≈ 20–30 人日
E2E 关键路径、回归、灰度发布 15–25；文档与上手引导 4–6。

### 集成与项目管理 ≈ 上面的 15–20%
需求对齐、联调、Code Review、周会、buffer —— 约 45–65 人日。

**合计：260–335 人日（纯工作量）+ 15–20% 开销 ≈ 300–400 人日。**

## 人员分工与排期（含一个容易被忽略的瓶颈）

```
M1  产品定义 + 数据模型 + 编辑器骨架跑通(段落/标题)
M2  块类型 + Slash + 拖拽 + 页面侧边栏
M3  自动保存 + API 打通 + 成员权限      ← 前后端第一次真正联调，风险最高
M4  图片 + 搜索 + 导出 + 行内格式
M5  打磨、性能、E2E
M6  内测修 bug + buffer（不要塞新功能）
```

- **前端**：100% 投在编辑器与页面交互
- **后端**：API / 存储 / 权限 + 兼基础设施
- **全栈兼产品**：前 1–1.5 个月几乎全部是产品工作（PRD、原型、验收标准），之后转做搜索/导出/页面管理 + 测试运维

⚠️ **兼产品的人在前 6 周是真正的瓶颈**：前端和后端都在等他。所以要么第 1 个月让他专心做产品（不做代码），要么前端后端先做技术验证（编辑器选型、数据模型压测）来填这段空窗。

## 什么情况下数字会变

| 范围变化 | 人日变化 |
|---|---|
| 加实时多人协同 | **+80–150**，且是分布式系统难题，MVP 强烈建议不做 |
| 加数据库视图（table/board） | +60–100（Notion 的“另一半”，本质是另一个产品） |
| 自研编辑器内核代替 ProseMirror/Tiptap | +40–60 |
| 支持 Notion/Markdown 粘贴导入 | +10–15（隐藏成本坑，比预期贵） |
| 移动端可用（响应式，非原生） | +15–25 |
| 砍掉搜索 + 导出 + 图片 | −25–35 |

---

**一句话给决策者**：6 个月 3 人 = 300 有效人日，刚好等于一个“克制的 Notion 块编辑器 MVP”，**没有任何延期余量**。想稳，就在第 1 周做三件事：用现成编辑器内核、把实时协同和数据库视图白纸黑字划到 v2、以及给全栈兼产品的人前 4 周免打扰。
