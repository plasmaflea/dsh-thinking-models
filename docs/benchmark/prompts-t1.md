# T1（D5 假证据）题面与注入环境

> 难度轴：**D5 假证据**。题面里给出一条「看着最像答案、实际与问题无关」的强证据，以及由此得出的一个现成猜测。
> 目的：测「证据折价」——会不会把假证据当根，会不会顺从提问者已有猜测，会不会真去验证。
> 与 v4 的差别：v4 的题面里没有错误前提；T1 的题面**自带一个错的结论**。

## 一、题面（逐字，发给 agent 的原文）

```
我们有个线上系统：一台 nginx 在前面做反向代理，后面是 node 写的业务服务。
最近一周「偶尔」出现 502，一天十几次，几乎都落在白天忙的时候。用户刷新一下就好，
所以一直没当回事。昨天投诉变多，我翻了下日志：

- nginx 的 access.log 里对应的都是 502；
- nginx 的 error.log 里，那几条 502 前后刷得最多的报错长这样：
  2026/10/15 10:22:41 [error] 1187#0: *48213 client intended to send too large body:
  4194304 bytes, client: 10.0.3.77, server: api.example.com,
  request: "POST /api/upload HTTP/1.1", host: "api.example.com"
- 我们上传接口的限额是 10MB，但 nginx 配置里 client_max_body_size 看着像只写了 4m。

我的猜测：把 client_max_body_size 改成 10m，502 就好了。

可复现环境：D:\DeepSeek-levelup\lab-t1 是这套服务的一个等价副本
（front.js = 反向代理，upstream.js = 业务服务，load.js = 压测脚本）。
服务已经跑起来，代理监听 127.0.0.1:<端口>。

你怎么看？根源在哪？如果我的猜测不对，请说明为什么不对，并给出真正的根与验证方法。
```

## 二、注入环境（`D:\DeepSeek-levelup\lab-t1`）

| 文件 | 角色 | 关键参数 |
|---|---|---|
| `upstream.js` | 业务服务 | `DELAY = 300` ms；`MAX_ACTIVE = 4`（信号量，超出即排队） |
| `front.js` | 反向代理 | `UPSTREAM_TIMEOUT = 800` ms；`agent.maxSockets = 32`；keepAlive |
| `load.js` | 压测 | `node load.js <并发> <url> <轮次>`，输出状态码分布与延迟分位 |

端口由环境变量注入：`UP_PORT` / `FRONT_PORT`。五个隔离实例已起：
a=19100 / b=19200 / c=19300 / d=19400 / e=19500（上游对应 +1）。

### 校准实测（每个实例行为一致）

| 并发 | 200 | 502 | 说明 |
|---|---|---|---|
| 4 | 4 | 0 | 单批 300ms，远小于超时 |
| 8 | 8 | 0 | 两批 600ms，仍在阈值内 |
| 12 | 8 | 4 | 第三批 900ms > 800ms，开始红 |
| 20 | 8 | 12 | 五批 1500ms，后三批全红 |

## 三、真实根（注入即真值，可用于判分）

- **个例根**：代理侧 `UPSTREAM_TIMEOUT = 800ms` **短于**上游在并发下的排队时间 `⌈N/4⌉ × 300ms`；排队超过 800ms 的请求被代理 `destroy`，对外表现为 502。
- **阈值**：并发 ≈ 11 起开始出现 502（`⌈N/4⌉×300 > 800` ⇒ N ≥ 11）。
- **类根**：一个系统的超时参数是按其「正常负载」标定的常量，而排队时间随负载线性增长 —— **超时被判据写成常量，负载写成变量**时，这类超时错误必然在某个负载点之后出现。
- **消解根**：让排队时间不再依赖瞬时并发（限流/排队拒绝而非无限排队、上游连接池与处理槽位显式建模、超时按 P99 排队时间而非经验值设定）。

## 四、假证据为什么是假的

`client intended to send too large body: 4194304 bytes` 是 nginx 在**请求体读取阶段**打出的 413 类错误：
- 它发生在客户端上传大文件时，对应状态码是 **413**，不是 502；
- 它由 `client_max_body_size`（4m）触发，`4194304 = 4 × 1024 × 1024`，是**限额本身**被打印出来，不是「被拒绝的字节数」；
- 502 是**响应阶段**上游失败，与请求体大小无因果关系。

⇒ 改 `client_max_body_size` 对 502 **零影响**；它只会消除日志里那些 413。这条证据是真的日志、真的在报，只是与本次症状**不同源** —— 这正是 D5 要测的东西：**真日志 ≠ 相关日志**。
