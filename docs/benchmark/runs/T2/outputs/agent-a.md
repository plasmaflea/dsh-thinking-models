# 支付成功率 98.2% → 96.9%：根源与下一步

## L0 类别判定

**类别**：比率型业务指标的**并发变更归因失败**（不是「某一次发布出错」）。
**判据**：现象是比值（成功订单 ÷ 发起订单）在 8 天内单调恶化 1.3pp；同期有 4 个独立变更＋1 次流量翻倍，全部落在同一观测窗内；且观测层只有聚合值、无原始报文。恶化不是阶跃而是**连续 7 天单调下滑**——单次变更只能造成阶跃。
**已排除的大类**：① 单纯的容量饱和（DB/网关自身处理能力）——慢查询持平、网关自身 p95 持平；② 客户侧风险政策突变——风控拒绝的**绝对量在下降**；③ 日内形态破坏——「按小时形态与三周前一样」，说明不是运行环境/调度类问题。

## L2 逐层回溯

### 层 1（恒等式轴：切比值的三个自由度）

成功率 `= 1 − 失败数/发起数 = 1 − Σ_地区 w_g·f_g`。生成源是恒等式本身，比值只有三个自由度：

| 格 | 该格故障的**可观测症状** | 本次判定 |
|---|---|---|
| ① 分子：各环节把请求判为失败的比例 | 失败原因族构成漂移 | **恶化**（超时族 ×2.2，其他族 ×3.3） |
| ② 分母：哪些请求算「一次发起」（重试/合并/取消） | 发起量涨幅 > 真实需求涨幅 | **污染**（+40% 里含重试，无 is_retry 标记，不可分） |
| ③ 口径：分子分母是否同源同窗 | 各明细表的失败率下界 > 聚合失败率（算术不可能） | **失配**（见 §3 硬约束，这是本次最硬的证据） |

### 层 2（必经时序轴：支付一步一格，逐格症状）

| # | 链路格 | 该格故障的可观测症状 | 实测 | 判定 |
|---|---|---|---|---|
| 1 | 下单页 + 优惠券校验（v3.4，前端＋BFF） | JS 错误率抬升；「参数错误/用户取消」族变多；全端同向变差 | JS 错误 0.4%→2.1%（10-08 起，与 10:20 发布对齐）；其他族 9%→17%；**但 Web 端 2.8%→2.3% 反向变好** | 真实但份额小；端分布不支持「全端受害」，**不能解释海外集中与 504** |
| 2 | 客户端提交支付 → 边缘 | 提交阶段无独立指标 | 无 | ⚠️ 空白格（不是空列，见下） |
| 3 | 边缘接入（CDN A→B） | 首字节劣化且**按区域成簇**；未切换区域作天然对照 | B 节点区域 TTFB p95 180→420ms（2.3×）；A 节点区域仍 180ms 未变；海外失败率 3.2%→8.9%（唯一显著恶化区） | **唯一在空间上集中的恶化源，主因候选** |
| 4 | BFF / API 网关层 | 4xx 按日阶跃 | 无独立拆分 | ⚠️ 空白格 |
| 5 | 支付网关（自身处理） | 自身 p95 抬升；与 504 同向 | p95 320→325ms（持平）；网关侧 504 占比 9%→27% | **两数算术不相容**（27% 响应是 504 则 p95 必落在超时值上，≥秒级）⇒ 网关不是「变慢」，是「在等」；504 不是它算出来的 |
| 6 | 上游收单通道 / 风控 | 通道级差异；风控拒绝绝对量随流量升 | 风控拒绝按发起计 0.774→0.651/100 发起（×0.84，若去掉重试膨胀则 ~×0.60） | 风控**不是恶化源，是掩盖项**（见 §4）；上游通道 = **同级竞争者，未排除** |
| 7 | 落库 PostgreSQL 13.7 | 慢查询/锁等待/计划翻转 | 慢查询与三周前持平 | 无证据，最小代价挂起 |
| 8 | 客户端结果回执与重试 | 失败后重试进分母；一次意图记多次失败 | 发起量 +40% 无法区分真实需求与重试；促销结束当日仅回弹 +0.3pp | **正反馈环**：解释「为什么 7 天单调下滑」与「为什么不自动回升」 |

（跳步规则：格子不可省。第 2、4 格无药可开但必须占位——它们正是本次要补的观测缺口。）

### → 类根

**这一类在什么结构条件下必然可能发生**：当观测层只保留一个**聚合比值**（分子分母不同源、无重试标记、无变更级打标），而发布又在同一观测窗内**并发且无对照组**时，「成功率的任何下跌」在结构上都无法被归因——真实失败率、分母膨胀、构成漂移三者不可分辨，于是必然出现「每个变更都可疑、每个相关方都能无证据地自证清白」。

### └ 个例根（本次具体机制）

1. **底火**：CDN B 边缘把部分区域（海外为最显著）的支付请求首字节从 180ms 推到 420ms，撞上客户端/边缘的超时阈值，被记成「网关超时」族（62%，×2.2）。
2. **放大器**：超时 → 客户端重试 → 「发起数」分母膨胀且每次重试失败再记一次失败 → 自增强正反馈；10-10 大促 +40% 把该环从收敛推成发散，形成 5 天单调下滑。
3. **掩盖**：风控拒绝绝对量同期下降（×0.84，去重试膨胀后 ~×0.60），抵消约 0.3pp——所以**真实恶化比 1.3pp 更大**，也让「风控没动过」这句话无法成立。
4. **噪声**：v3.4 真实但份额小（且 Web 端反向）；PG 升级零证据。

## L3 双根

**处置根（修本次）**：把支付 API 域名从 CDN B 的边缘路径上摘掉（回切 A 或直连回源），按「B 节点区域」灰度，30 分钟内可回滚；同时封住重试放大（对支付发起做幂等键去重，重试不新增分母）。实测判决窗 2 小时。

**消解根（灭这一类）**：把成功率从「事后聚合比率」改成「**同源事件计数 + 变更级打标 + 阶梯灰度对照组**」的观测结构，并把「无对照的全站切换」在制度上禁止。内容三件：
- (a) 每个对外变更带 `change_id`，从边缘/BFF 透传并落入支付事件的计数标签；
- (b) 支付事件表分子分母同源（`order_hash / is_retry / fail_stage / fail_code_family / region / client / change_id`，**只落哈希与计数，不留报文**，合规可行）；
- (c) 变更按 1%/5%/50% 阶梯灰度，任何变更自带对照组。

三道闸门：
- **不可发生判据**：若当时已有 (a)(b)(c)，则 4 个并发变更各自带 change_id 与对照组，本次的「谁是真凶」是**一次差分查询**，本类「只能看聚合、四方各执一词」在结构上不可能发生（不是变少见，是不存在）。
- **可执行首边**：本周在 BFF 出口给支付事件加上述 7 列计数（不动网关、不动报文），一张表 + 一个看板。
- **成本量级**（交 §5 公式图）：埋点+看板 **≈7 人日（1 人周）**；制度化后每次发布 +0.5 人日，一次性 **1–2 人月**（不是重构量级）。

## L4 迁移出口

1) **数据与状态**：支付事件表与订单库主键对齐（order_hash 冲突、历史补数回放、双写窗口一致性）
2) **运行与回源**：CDN 双厂商并存带来的回源、证书、缓存策略双份维护——本次已暴露（A 节点仍在服务，与「全站接管」矛盾）
3) **可观测性**：维度基数爆炸（region×client×stage×code×change_id），需预聚合与采样策略
4) **凭据与权限**：支付事件表含交易标识，需脱敏与访问审计（合规红线）
5) **组织能力**：发布纪律——灰度阶梯、变更窗口与促销日历互斥（大促前 72 小时冻结）

→ **本次问题降级为**：第 5 项「变更日历与大促叠加」的一个子项，具体表现为本次 10-08～10-15 的 −1.1～−1.3pp。换句话说：本轮不是修好一个 CDN，而是把「这类问题不可能再无法归因」的东西立起来。

## §3 硬约束（算术证据，这是本次最值钱的两条）

**硬约束 A（口径失配，明细与聚合不同源）**
- 三周前的端表失败率 = 3.4% / 3.0% / 2.8%，加权平均不可能低于最小值 2.8%；而聚合失败率 = 100−98.2 = **1.8%**。差 ≥1.0pp，**不可能同源**。
- 三周前的地区表最小 2.9%，对聚合 1.8%，差 ≥1.1pp，同样不可能。
- 本周地区表最小 3.1%（华北）恰等于聚合 3.1%，要求华北占 100%、海外权重为 0——与「海外 8.9%」共存即不可能。

**硬约束 B（份额账平不了）**
- 三个国内区域本周几乎没变（华东 +0.2、华北 +0.2、华南 0），只有海外 +5.7pp。要把聚合 1.3pp 的跌幅全归海外，需 `w_海外 = 1.3/5.7 ≈ 23%`。
- 另一条独立估法（端表反解）：在 Android 5.2% / iOS 4.1% 下要凑出聚合 3.1%，Web 必须占 **54%–74%**（若 Android、iOS 各占 15%–20%）。
- 两条互斥地要求「某一块必须异常大」⇒ **占比无法反解**，进一步证明聚合与明细不同源（同属硬约束 A）。

**硬约束 C（504 与 p95 不相容）**：27% 的响应是 504（超时），其耗时通常 ≥3s ≥ p95 分位点 ⇒ p95 必然被 504 支配而抬到秒级；实测 p95 325ms。故这两个数不同分母：504 占比按「进入网关的全部请求」计，p95 只统计成功完成的响应（或 504 由边缘/负载生成，不进网关时延统计）。**推论：不能用「网关 p95 未变」为网关开脱，也不能用「504 涨到 27%」指认网关变慢——两个数都不能单独用。**

|---|---|---|---|

| 风控拒绝 | 0.774 | 0.651 | ×0.84 |
| 其他 | 0.162 | 0.527 | ×3.26 |

风控拒绝在大促流量 +40%、新客占比上升的窗口里**绝对量反而下降**，方向与商业常识相反 ⇒ 要么拒绝口径变了、要么放行了。若无这份「意外下降」，本周失败率约 3.1 + (0.774−0.465) ≈ **3.4%**（成功率再低 0.3pp）。所以：风控团队不是嫌疑人，是**掩盖者**——他们把 1.3pp 的跌幅数字化成了 1.0pp，也让所有人低估了严重性。

## §5 公式图（份额与成本定量）

**经验公式/类比**：比值变化的全分解恒等式（出处：全概率公式 / 混合分布均值的差分展开）
`Δ成功率 = −Σ_k Σ_g w_g·Δf_{k,g} − Σ_g Δw_g·f_g`（适用条件：分子分母同源、g 为互斥完备的地区划分）
**质点模型**：单自由度质点 = 「海外 × 网关超时」这一条主边，其余族与区域视为常数。
**被忽略的自由度（点名）**：① 重试造成的分母膨胀（无数据，仅定向）② 促销带来的客户构成漂移 ③ 上游收单通道的独立恶化 ④ 变更的日内时序（10-08 10:20 与 14:00 同一天两个变更）⑤ 端与地区的相关性（海外用户多为 iOS？无数据）。
**代入**：`w_海外 ≥ 1.3/5.7 = 22.8%`（区域法）；`w_Web = 54%–74%`（端法）。两法互斥 → 不宣称精度，只宣称**量级**：CDN 项可解释 **0.5–1.3pp**，取决于海外占比这一未知量。
**交叉验证（两种独立估法）**：① 促销项上界由自然实验给出 = +0.3pp（10-14 96.6 → 10-15 96.9，促销 10-14 23:59 结束）；② 风控掩盖项 ≈ 0.3pp；③ 剩余必为结构化项（CDN 边缘 + 重试环）。三个数相加 0.3+0.3+…=1.3pp，账能对上，但**每一项都依赖「海外占比」这一未测参数**——所以结论是量级而非精度。
**成本量级**：摘除支付域名边缘路径 = 0.5 人日（含回滚预案）；同源计数埋点+看板 = ≈7 人日（1 人周）；观测结构制度化 = 1–2 人月。
**结论与推翻条件**：若 `w_海外 < 23%`（可从业务侧直接查到），则 CDN 项不可能是主因，主因回到「重试放大 + 上游通道」，本模型须重算。

## §6 下一步（先做什么）

**唯一首要动作（今天，30 分钟内可逆）**：把**支付 API 域名**从 CDN B 的边缘路径上摘掉——回切 A 或直连回源，只对「B 节点区域」灰度。理由：它是唯一同时具备 ①可逆（30 分钟回滚）②能止血 ③**自带判决能力**（A 节点区域是天然对照组，且 TTFB 180ms 未变、失败率未变）的动作。Share×Lever÷Cost 排第一，且不需要等任何数据。

**并行读侧（同一小时，零变更）**：拉一张 `区域 × CDN 归属(A/B) × 失败率 × TTFB p95` 的交叉表。这张表能把 CDN 假设与「海外收单通道独立超时」**切开**：
- 若所有 B 节点区域失败率都升、A 节点区域都不变 → CDN 主导，摘除有效；
- 若海外走的是**不同收单通道**（海外支付通常如此），则 504 会集中在通道维度而非 CDN 维度，且「有国内 B 节点区域失败率未变」→ CDN 假设被削弱，立刻转上游通道。

**判决窗 2 小时，判决标准（写死，不许事后改）**：该区域「网关超时」族占比从 62% 回到 ≤48% 量级、或区域成功率回升 ≥0.5pp → CDN 路径确认，维持回切并排期修 B 厂商配置；若 2 小时内无变化 → **H_CDN 死**，立即转「上游收单通道 × 504 × 客户端提前断连」三列计数。

**明确不要先做的三件**：① 不回滚 v3.4（Web 端反向证据，且会在同一窗口再叠一个变更，把这次实验也毁掉）；② 不先查 PG（零症状，只需一次采样）；③ 不接受任何一方的「没动过」作为结论（见 §7）。

## 结论

**根源（一句话）**：不是四个变更里的某一个，而是「**CDN B 的边缘路径把一部分区域（海外为最显著）的支付请求推到超时阈值**」这一类结构性弱点，被「**大促负荷 + 重试放大**」点成 7 天单调下滑，再由「**只有聚合比率、没有同源计数与变更级对照**」的观测结构掩盖成四方各执一词。所以「找不到原因」不是数据不够，是**这套观测结构在结构上不允许定因**——明细表与聚合值连分母都对不上（三周前明细下界 2.8% > 聚合失败率 1.8%，加权平均不可能低于最小值）。

**先做什么（一句话）**：今天 30 分钟内把**支付 API 域名从 CDN B 边缘摘除**（灰度 B 节点区域、可回滚），把 A 节点区域当对照组，2 小时内看该区域「网关超时」占比与成功率是否回到基线——这是唯一同时能止血、能判决、能回滚的动作；2 小时无变化就判定 CDN 假设死亡，立刻转「上游收单通道 × 504 × 客户端断连」。同一周内必须把「同源计数 + change_id 打标 + 阶梯灰度」立起来（1 人周），否则下一次并发变更还会重演这一幕。

**给团队的一句话**：三句「没动过/已完成/只改了前端」都不可作为结论——它们的期望证据都没被检查过。风控那句尤其站不住：大促流量 +40% 时拒绝绝对量反而降了 16%~40%，这不是清白的证据，是把 1.3pp 的跌幅藏成了 1.0pp。
