# 支付成功率 98.2%→96.9% 的根源与第一步

## L0 类别判定

**类别**：`软件` 节点下的**配置与状态变更（config）＋网络/边缘（network，待建）复合支** —— 具体形态是「比值型聚合指标在分层未拆 + 变更渐进生效的情况下发生的比例型劣化」。

**判据**：①劣化可被绑定到一组确定的可复现的配置/拓扑变更（不是物理介质、不是随机）；②失败是系统性的、可被同一机制按比例解释，而非位翻转式随机。
**已排除的大类**：硬件（无症状跨进程随机、无 CRC/ECC 线索）｜权限账号（无 ACL/令牌类症状，且失败率按地域/端分层而非按账号）｜组织流程（**暂列排除，但见挂起表第 13 行：三方说法全部无证据，一旦证实"变更未按流程灰度"则本类回填**）。

## L1 树实例化

`树 = software · v1 · 核查 2026-10-18`（工作区无 `knowledge-tree/`，读技能目录 `tree/index.md`）

**本次适用的子层**：`config`（CDN 全站接管、PG 小版本升级＝配置与状态变更）｜`quota`（大促 +40% 量＝容量/排队，仅作放大器）｜`concurrency`（重试风暴→分母灌水，见横切格）。

**本次判为不适用的子层（留档判断，非静默跳过）**：
- `lifecycle`／`init`／`dependency`：本次无进程起不来、无加载器退出码、无 DLL/符号错误码族；服务整体在跑。
- 子树 `win-service`：Windows 服务形态，与支付链路无关。

**树外分支 / 待建节点登记**：
- `network`（索引中已列 v2 候选，**本次正好命中**）→ 本次必须使用，故**升格为 `network · v2 候选`**，理由：本次核心证据是分层可达性与超时形态（TTFB p95、504 占比、按地区/按端差异），现有 `software` 节点无一格承载它。
- **新增 `observability-attribution · v2 候选`**，理由：`software` 判据要求"可复现性来自代码/配置"，但本次的**主症是"无法归因"本身**——原始报文不留存、只剩聚合、缺链路侧维度。这一类（变更与劣化无法配对）在现有树里没有节点，若不给它一个位置，消解根就无处落地。

## L2 逐层回溯（轴＝恒等式生成，非列举）

**选轴依据（生成源：恒等式）**：`支付成功率 = Π(各环节通过率) × 分母修正`，环节顺序由**必经时序**机械给出（一笔支付必须依次穿过这六格，少一格就付不出去）。故轴是：

> 客户端提交 → 边缘/网络 → 网关受理 → 风控放行 → 后端落单 → 异步回调确认 ＋ 两个横切格（分母口径、结构 mix）

每格写出"该格故障的可观测症状"，逐格判定。**无空列**，故轴成立（不走换轴程序）。

| 格 | 该格故障的症状 | 本次判定（Share） | 证据 |
|---|---|---|---|
| 1 客户端提交（下单页/JS/优惠券校验） | JS 错误率↑、按端差异、参数错误族↑ | **次要** | JS 错误 0.4%→2.1%（×5.25）确有；但 **Web 失败率 2.8%→2.3% 反向**，且不解释 504 |
| 2 边缘/网络（CDN B） | TTFB p95↑、按地区与按端集中、504↑、日形态不变 | **主因（待一次灰度证伪）** | TTFB 180→**420 ms（×2.33）**，且**仍走 A 的区域仍是 180 ms**；海外 3.2%→8.9%（×2.78）；Android ×1.53、iOS ×1.37 而 Web ×0.82 |
| 3 网关受理 | 网关 p95↑、渠道错误码 | **无** | 网关 p95 320→325 ms（+1.6%），处理时间没变 |
| 4 风控放行 | 风控拒绝**绝对量**↑ | **无（且方向相反）** | 绝对量 −4%~−9%（见下方归一化） |
| 5 后端/DB 落单 | 慢查询、BFF 5xx | **无** | DB 慢查询与三周前持平（PG 升级因此被排除） |
| 6 异步回调/落地 | 网关超时族与"最终成功"的差集、对账差异 | **未观测（重大空白）** | 无任何对账数据——见 ⚠️ 第 5 条 |
| 横切 A 分母口径 | 人均发起次数、同订单多次发起 | **未观测** | v3.4＋超时都会诱发重试，机械拉低成功率 |
| 横切 B 结构 mix | 各格倍数 vs 总体倍数的背离（Simpson） | **共因** | 海外/App 的倍数远高于总体 ×1.72，说明劣化是**集中的**，不是均匀的 |

### 关键一步：把"占比"折回"绝对量"（这张表的数据陷阱）

团队最容易读错的是 3.1 表：风控拒绝占比 43%→21%，看着像"风控放松了"；网关超时 48%→62%，看着像"只多了 14 个点"。实际把占比乘回总失败率（98.2%→96.9%，失败率 1.8%→3.1%），以"三周前失败量 = 100 单位"归一化：

| 原因族 | 三周前（绝对） | 本周（绝对） | 倍数 | 占**增量**比重 |
|---|---|---|---|---|
| 网关超时 | 48.0 | **106.8** | **×2.23** | **+81%** |
| 风控拒绝 | 43.0 | 36.2 | ×0.84 | **−9%（改善项）** |
| 其他（取消/余额/参数） | 9.0 | 29.3 | ×3.26 | +28% |
| 合计 | 100 | 172.3 | ×1.72 | 100% |

（用最差日 96.6% 重算，结论不变：网关超时占增量 78%，风控 −4%，其他 +26%。）

**读法**：**增量里 78–81% 是网关超时；风控在绝对量上是下降的，它是被"分母变大"挤低了占比，不是变严格**——风控团队"没动过规则"的说法与数据一致，不该再被追问。而且风控绝对量下降与 504 上升是同一件事的两面：请求在到达风控之前就被截断了，所以**流水线前端（边缘）故障会同时表现为"超时↑ + 风控↓"**，这是可检验的内部一致性，不是两个独立事实。

### 时间线的三因子分解（决定"根"落在哪）

| 窗口 | 成功率 | 相对 98.2% |
|---|---|---|
| 10-05~10-07（基线） | 98.2–98.3% | — |
| 10-08~10-09（当日两变更，**促销前**） | 98.0 / 97.9% | **−0.3 pp** |
| 10-10~10-14（促销期） | 97.6→96.6% | −0.6 → **−1.6 pp** |
| 10-15（促销已结束） | 96.9% | **−1.3 pp** |

三个必须同时被解释的事实：
1. **起于 10-08，且是单调渐变而非阶跃**（一个 14:00 的 DNS/配置切换不会在 7 天里一天降一点）；
2. **促销结束只回收 0.3 pp，仍比促销前差 1.0 pp** → 有一个**不可逆的、持续推进的**分量；
3. **"按小时形态与三周前一样"**（只有水平位移，没有形状变化）→ 若为容量/排队型劣化，峰值时段应变陡；形态不变更像**"每个请求有一个恒定的概率被路由到坏路径"的比例型劣化**。

能一次解释这三条的机制只有一类：**坏路径的占比在单调上升**。而 4 节里"仍走 A 节点的区域 180 ms"这一行，正好证明 **10-08 号称"全站接管"的切换其实没有完成**——存在仍在 A 上的流量（这是一个白送的对照组！）。DNS TTL、App 的长连接/DNS 缓存、海外 ISP 缓存，让"流量从 A 漂移到 B"本身就是一个以天为单位的爬坡过程。

### 汇合到类根

> **类根（这一类在什么结构条件下必然可能发生）**：**当"劣化的观测维度"只存在于结果侧（原因族/端/地区），而"劣化的产生维度"在链路侧（哪个 CDN POP、哪个回源状态、哪个客户端版本），同时变更的生效是渐进的（DNS/长连接/灰度和上架）而指标是日粒度聚合时——任何候选根都能在同一天找到一片支持它的切片，于是归因只能靠"形状猜"，而形状对多个候选并不互斥。**"原始报文不留存"这条合规约束把这个结构缺陷钉死：它删掉的正是能一票定案的那个维度。

> └ **个例根（本次具体机制，挂在类根之下）**：**10-08 14:00 切到 CDN 厂商 B 后，B 的边缘/回源表现劣化（TTFB p95 ×2.33，504 占比 9%→27%），把支付请求推过超时阈值；而流量并未真正"全站"切完，A→B 的漂移在 7 天里持续推进（解释单调爬坡），大促 +40% 加深了坏 POP 上的排队深度（解释促销期加速与结束后只回收 0.3 pp）。**
> 　具体链条：`B 边缘 TTFB↑ → 跨境/移动弱网路径先破（海外 ×2.78、Android ×1.53）→ 支付请求超时/被边缘 504 → 未达风控（风控绝对量 −9%）→ 用户重试（分母灌水）→ 成功率机械性再降`

**这个个例根的可证伪点（写在这里，是为了让它将来能被推翻，而不是被保住）**：若按 POP 拆解发现 B 的"坏 POP"承载 <2% 流量、或按客户端版本拆解发现新版用户失败率是旧版的 ≥3 倍、或 504 被证明由第三方渠道返回而非我方边缘——三条任一成立，则个例根降级，v3.4/渠道侧升格。

## L3 双根

**处置根（修本次）**：**把 API 域名（只 API，不动静态资源）按 POP 灰度回切到 A，优先海外与移动路径**；同时把 v3.4 的 JS 错误（2.1%）作为独立缺陷单修复（它污染"其他"族，会让后续归因继续失真）。

**消解根（灭这一类）**：把"变更—劣化无法配对"这一结构条件拆掉——**给所有链路指标加两个低基数维度（`cdn_pop`、`edge_status`），并把"全站接管类变更必须带灰度分组 + 预注册回退判据"写进变更流程。**

- **① 不可发生判据**：若 10-08 14:00 的切换是"按 POP 灰度 + 指标带 POP/回源状态标签 + 自动回退判据"，那么**这一次根本不会演变成两周悬案**：2 小时内单个 POP 的 TTFB/504 就会把环节直接指出来并触发回退，不需要任何事后归因；而且"渐变型劣化只能猜形状"这一类在结构上不可能发生（不是变少见，是不会发生）。判据成立。
- **② 可执行首边**：今天就在支付域的 **5% 流量**上给现有指标管道加这两个标签（只计数、不留报文，合规内），不改采集范围、不引第三方。这是最小可执行的一步。
- **③ 成本量级**：工程量 **1–2 人日**；指标基数按 `pop(归并到 ~20 个大区) × status(6 值)` ≈ **120 series/接口**，存储增量量级 **<5%**（精确数字交 📐 公式图：series 数 × 采样间隔 × 保留期）。不需采购、不需停机。

## L4 迁移出口（因消解根产生的新问题，本次问题降级为其中一项）

1. **指标基数与成本**：`cdn_pop` 若不归并会 series 爆炸，需要用大区聚合而非原始 POP（成本量级需 📐 定量）。
2. **合规边界**：计数可留、报文不留——加标签这件事必须让合规确认边界，否则埋点本身越界（这是本次"只能猜"的成因，别让修复动作再踩一次）。
3. **告警与 SLO 重算**：从"全局成功率 <95% 报警"改为"按端/按 POP 的 SLO + 环比漂移报警"，否则下一次劣化仍然在全局均值里被稀释（本次全局只掉了 1.3 pp，但海外已经是 8.9%）。
4. **变更流程**：全站接管类变更强制"灰度分组 + 预注册判据 + 自动回退"，值班 SOP 同步。
5. **双 CDN 运维能力**：A/B 并存、按 POP 定向、DNS 权重治理——能力不建立，"回切"这个动作下次也做不快。
6. **分母治理**：重试/重复提交的去重口径，防止成功率被灌水掩盖真实改善。

→ **本次问题降级为**：第 3 项（SLO 重算）与第 4 项（变更流程）的**输入样本**——即"一次未被观测维度拦截的变更事故"，而不是一个需要英雄式排查的孤立事件。

## 结论

1. **根源（主因）**：10-08 下午切到 CDN 厂商 B 后，B 的边缘/回源性能劣化——TTFB p95 **180 ms → 420 ms（×2.33）**，网关侧 504 占其响应 **9% → 27%（×3）**。它把支付请求推过超时阈值，失败增量里 **78–81% 是"网关超时"**；而风控绝对拒绝量 **−9%**（不是变严，是被分母挤低了占比，且更可能是请求在到达它之前就被截断）、网关自身 p95 只 +1.6%、DB 慢查询持平——这三条被数据直接排除，PG 升级与风控规则都不该再占用排查预算。
2. **为什么"两周不回升"**：劣化是**比例型**的（每个请求有恒定概率命中坏路径），所以按小时形态不变、峰值不额外恶化；而 10-08 号称"全站接管"其实**没切完**（指标里仍有区域走 A，且 A 侧仍是 180 ms 的完好对照），A→B 的流量漂移以天为单位推进，于是日均值一天降一点。大促 +40% 是**放大器不是根**：促销结束只回收 0.3 pp，仍比促销前差 1.0 pp。
