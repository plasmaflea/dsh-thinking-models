# 支付成功率 98.2% → 96.9%：根源与首动作

**[🌳 林状图／回溯法] [选择理由]** 问题是「掉了两周没回升，根源是什么」，属追根因；手上是 4 项叠加变更 + 只有聚合指标，未知在**因果深度**（哪一跳坏了），不在选项广度也不在数量关系（数量关系只用于验证，见汇合层）→ 林状图。交付前先做一次负边审计：团队的三条说法（风控"没动过"、B 厂商"无异常"、后端"没碰支付链路"）都是**无自证能力的否定**，而"风控拒绝占比 43%→21%"是最容易被误读成"风控放松→风险升高"的辛普森陷阱（占比下降 ≠ 绝对量上升）。这两处在 L2 层6 与挂起表里逐条处置，不单独开 🧪 倒推图。

---

## L0 类别判定

- **类别**：网络／接入链路类（树内**待建候选节点** `network`）。
- **判据**：增量失败中 81% 是「网关超时」族；同一指标在两个 CDN 节点集合上同期对照 420ms vs 180ms（2.33×，A 节点侧 1.00× 未变）；失败率按地区切分出 5.7pp 极差（海外 8.9% vs 华南 3.3%，三周前为 3.2%）。这三条正是 `software` 节点**排除表第 2 行「网络问题」**的判据（分层可达性可测、症状随链路变化；典型症状＝超时、连接被重置、DNS 解析失败）。
- **已排除的大类**：数据库／存储（慢查询与三周前持平）；业务代码回归为主因（发布必为台阶，观测是 7 天斜坡；且 Web 端失败率**反而改善** 2.8%→2.3%）；风控策略（拒绝绝对量下降 16%，方向相反）；硬件（无 CRC/跨进程随机性、无温度负载相关）；纯容量（网关 p95 325ms vs 320ms 持平）。
- **维度声明**：因果链只走技术跳；「变更隔离／流程」维度**不在 L2 上跳**，只在汇合层与 L3 消解根合并（禁止跨维度边）。

## L1 树实例化

- `树 = software · v1 · 核查 2026-10-18` → **命中其排除项（网络问题）**，故本次**不在** `software` 的六个子层（lifecycle／init／dependency／quota／concurrency／config）上切轴；`win-service` 节点不适用（非 Windows 服务形态、无进程初始化症状）。
- **本次判为不适用的节点（留档）**：`software` 六子层全部（失败不发生在应用能打日志之前，而发生在它之后的网络跳上）；`win-service` 全部。
- **新节点登记**：`network` → **v2 候选**。理由：本次需要的判据（症状随链路/节点集合变化、分层可达性可测、**「慢超时」与「快速失败」必须分开判**）在现有树里没有承载节点；按规则不静默绕过。
- **轴选择（生成式，非列举）**：**支付请求的必经跳**。一次「发起支付」必须依次穿过 7 个跳才可能成功，少一跳到不了成功 ⇒ 轴可生成；每格有专属症状（TTFB／回源 5xx／业务错误码／网关状态码／渠道码／DB 等待／客户端 JS 错误）⇒ 正交；症状均可从现有或一日内可取的数据读出 ⇒ 可观测。

## L2 逐层回溯（7 跳 + 汇合层）

**层1 客户端（App/H5 发起、SDK 超时与重试）**
症状：分端失败率倍数、JS 错误率。实测：Android 3.4%→5.2%（**×1.53**）、iOS 3.0%→4.1%（×1.37）、**Web 2.8%→2.3%（×0.82，改善）**；下单页 JS 错误 0.4%→2.1%（×5.25，10-08 起）。
判定：**不是根，是放大器**——短超时＋重试把接入层的 420ms 与快速 504 翻译成客户端口中的"网关超时"。Web 反向改善，说明 v3.4 的前端改造本身没把支付打坏。

**层2 接入层（DNS／TLS／CDN 边缘；B 全站接管含 API 域名）**
症状：TTFB p95、同指标跨节点集合对照、分地区极差。实测：**B 节点 TTFB p95 420ms；仍走 A 节点的区域 180ms 未变（2.33× vs 1.00×，自带对照组）**；海外 3.2%→8.9%（**×2.78**），国内三区几乎不动（×1.06／×1.07／×1.00）。
判定：**命中，主因所在跳。**

**层3 边缘→回源（BFF 入口、连接复用）**
症状：回源 5xx／连接拒绝／回源 RT。实测：**无此层指标（数据空白）**。
判定：挂起（挂起表第 4 行）。方向上与层2 同因，不独立成根。

**层4 BFF 业务（v3.4：下单页样式 + 优惠券校验重写）**
症状：业务错误码族、下单页 JS 错误、Web 失败率。实测：Web 失败率下降；「其他」族（用户取消/余额不足/参数错误）绝对量 1.62→5.27 每千次（**+3.65**）；JS 错误 ×5.25。
判定：**不是主因**（代码发布不可能产生 7 天线性斜坡；Web 反向改善），但可能贡献「其他」族的一部分（券校验→参数错误；页面慢+JS 错误→用户取消）。Share＝次要，需按错误码切片定案。

**层5 支付网关 API（我方→网关）**
症状：网关 p95、504 占其响应比、超时族绝对量。实测：p95 325ms vs 320ms（**×1.02，平**）；**504 占其响应 9%→27%（×3.0）**；超时族绝对量 8.64→19.22 每千次（**×2.22，占增量 81%**）。
判定：这是**故障被观测到的落点，不是病因**。关键推论：27% 的响应是 504，而 p95 仍 325ms ⇒ 这 27% 不是"等到超时才失败"，而是**在 p95 之内返回的快速失败** ⇒ 病因在"连不上／路由／回源"一侧，不在"渠道算得慢"（后者必然把 p95 推过超时阈值）。

**层6 网关→渠道（银行／卡组织／风控）**
症状：风控拒绝占比与绝对量、渠道错误码。实测：风控拒绝占失败 43%→21%，但**绝对量 7.74→6.51 每千次（−16%，是下降）**。
判定：**不是根，且方向相反**——风控"没动过"的说法与数据一致。更可能的机制是**失败前移**：请求死在层2／层5 就不再抵达风控，风控拒绝被机械性稀释。渠道侧无数据 → 挂起。

**层7 数据库（PG 13.6→13.7、连接池、慢查询）**
症状：慢查询数、连接等待、DB 相关错误码。实测：慢查询（>1s）与三周前持平。
判定：**阴性，排除。** 13.7 是安全/小版本修正，且不在"快速失败的 504"这条因果链上。

**汇合层（恒等式：失败率 = Σ 各跳失败贡献；单位＝每 1000 次发起）**
+13.0 失败／千次 = 网关超时 **+10.58（81%）** + 其他 **+3.65（28%）** + 风控 **−1.23（−9%）**（分解闭合到 1.3pp，见 ✅ 验证）。
七跳中**只有层2 有独立劣化证据**（自带 A/B 对照、与"快速 504"方向一致、与海外/分端形态一致）⇒ 增量主体归层2。
**形态证据（本轮最关键的一条）**：日序列 98.2→98.0→97.9→97.6→97.4→97.0→96.8→96.6，**7 天近似线性 −0.23pp/日，没有台阶**。一次性代码发布必然产生台阶（10:20 之后所有流量即新版本，最迟一个缓存周期到位），**不可能**生成 7 天线性斜坡 ⇒ v3.4 在形态上被排除为主因。能生成斜坡的机制必须随时间累积：CDN 切流后 DNS TTL／运营商 LocalDNS 缓存／客户端 SDK 内置兜底 IP／长连接逐级过期，B 的实际覆盖占比逐日上升——这正是斜坡生成器。
10-15 回升 +0.3pp 与大促 10-14 23:59 结束吻合 ⇒ 负载因素上界约 0.3pp（≤23% 增量）：**大促是放大器，不是主因**（弱证据：仅一日，需复核）。

## 类根（这一类在什么结构条件下必然可能发生）

**支付链路的可用性没有按 SLO 分级隔离：它被并入了与自身无关的全局接入层变更的爆炸半径（"全站接管，含 API 域名"），而失败链路上只有聚合指标、没有逐跳证据——于是同一窗口内的多项变更无法被任何一个反证区分，同形态事故必然重演"每一方都说自己没动、数据也自洽不了"的局面。**

```
└ 个例根：CDN B 接管 API 域名后，接入层对移动/海外路径劣化（TTFB 2.33×、快速 504 3.0× 占其响应 27%），
   经客户端短超时与重试放大为"网关超时"，占增量 81%；呈逐日爬坡＝切流残留（非一次性回归）。
   ├ 放大器：大促 +40% 压低超时/重试余量（≈0.3pp / ≤23%）
   └ 次要贡献：v3.4 券校验与页面（"其他"族 +3.65/千次，方向与 JS 错误 ×5.25 一致，待错误码切片定案）
```

## L3 双根

**处置根（修本次，48h 内）**
1. 把**支付 API 域名**从 B 的接管清单撤出、指回 A 或直连源站；**把这一步做成实验**：灰度 5% → 25% → 100%，每档 ≥12h，指标＝网关超时/千次发起、504 占比、海外失败率。**静态资源留在 B**（那是唯一真正吃到收益的部分）。
2. 并行取两个「一日切片」（不加埋点、只改查询）：①按**边缘节点归属 A/B × 端 × 地区 × 错误码**切成功率与超时率；②把「其他」族按错误码拆开（参数错误 vs 用户取消），决定 v3.4 的功能开关动不动。
3. **不要整体回滚 v3.4**：形态上它不是主因，且 Web 端指标改善，整体回滚白扔收益。
4. 大促余量：与 App 组核对支付 SDK 的当前超时/重试值，在 504 快速失败场景下把"重试放大"限到 1 次（重试预算模型交 📐 公式图定量，本轮不给数）。

**消解根（灭这一类）**
**支付／资金链路的接入面永不进入任何全局变更的生效集合**（API 域名专用回源、独立证书与 DNS 段、不进"全站接管"清单），并让每次失败带「跳」标记（client／edge／origin／gateway／channel）。
- **不可发生判据**：若 API 域名不在任何 CDN 全站接管／边缘规则／WAF 变更的生效集合内，则厂商切换、节点劣化、边缘配置变更在结构上**无法**改变支付请求的接入路径与 TTFB ⇒ 本次这条"接入层变更 → 网关超时激增 → 成功率下滑"的因果链断裂，而不是"变少见"。
- **可执行首边**：一条配置——`pay-api` 子域 CNAME 从 B 改回 A 的专用回源（关闭该域名的 CDN 缓存与边缘改写），灰度 5% 流量、观察 48h。1 人 × 半天。
- **成本量级**：首边 **0.5–1 人日**（配置+DNS+证书与回源带宽核对+灰度观测）；之后边际成本 ≈ 0（API 本就不吃 CDN 缓存收益）；配套逐跳埋点 **3–5 人周**（量级估算，细算交 📐 公式图）。

**候选根排序（Share × Lever ÷ Cost；类根在上，个例根在下）**

| 排序 | 候选根（层级） | Share | Lever | Cost（＝预算） | 首验动作 |
|---|---|---|---|---|---|
| 1 | **类根**：支付链路未与全局接入层变更隔离（B 接管 API 域名） | 唯一／主因（增量 81%） | 改配置 | 一条 CNAME + 一次取数，≤1 人日 | 边缘节点 A/B 分组成功率 |

| 3 | 个例：v3.4（券校验 → 参数错误；页面慢/JS 错误 → 用户取消） | 次要（≤28%，含在"其他"族） | 改配置（开关） | 一次取数 + 一次开关 | 按错误码切片 |

## L4 迁移出口

1. **接入拓扑**：API 专用回源、证书/SNI、海外就近节点与跨境链路由谁负责。
2. **可观测性**：逐跳耗时与状态码直方图；合规下**只留分段耗时+错误码聚合、不留原始报文**即可满足归因（这条同时回答了"报文不留存就不能定位"的困境）。
3. **变更管理**：按 SLO 分级爆炸半径；支付相关变更与基础设施变更**不同窗**；支付链路强制金丝雀＋回滚演练。
4. **容量与重试预算**：峰值下"重试放大系数 vs 超时预算"的定量模型（交 📐 公式图）。
5. **客户端契约**：App SDK 超时/重试/兜底 IP/DNS 缓存策略纳入变更评审。

→ **本次问题降级为第 1 项里的一个条目**（支付 API 域名退出 CDN 全站接管），外加第 3 项的一条规则。

## [结论]

1. **根源**：不是"某一次发布把代码改坏了"，而是**支付链路的可用性被并入了与它无关的全局接入层变更的爆炸半径**——CDN 从 A 切到 B 且"全站接管含 API 域名"后，移动/海外路径的接入层劣化（TTFB 2.33×、快速 504 占其响应 27%），被客户端短超时与重试翻译成"网关超时"，占失败增量的 **81%**；斜坡形态（7 天 −0.23pp/日、无台阶）证明它是**逐日扩散的切流残留**而非一次性回归。v3.4 至多贡献「其他」族的次要部分（≤28%，待错误码切片），PG 13.7 与风控规则**数据上已经排除**（慢查询持平；风控拒绝绝对量反降 16%）。大促是放大器（≤23%，仅 0.3pp），不是主因。
2. **最该警惕的不是这 1.3pp，而是它被重试掩盖了**：网关 504 已达 27%，而失败只 3.1%，说明约 9 成 504 被重试救回；一旦峰值把重试预算耗尽，会是断崖而不是缓降。
3. **接下来先做什么（按序）**：①今天内取两个一日切片（边缘节点 A/B 分组成功率；「其他」族错误码拆分）——零成本、当天出结论；②把支付 API 域名从 B 撤出并灰度 5%，48h 读回弹（这既是止血也是判定性实验），静态资源留 B；③同时与 App 组核 SDK 超时/重试值，峰值前把重试放大限到 1 次；④不要整体回滚 v3.4；⑤止血后按 L4 第 1、3 项把"支付 API 域名永不进全站接管"落成规则——这才是让这一类不再发生的那一步。
