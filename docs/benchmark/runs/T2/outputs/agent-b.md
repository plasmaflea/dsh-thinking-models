[🌳 林状图] 选择理由：问句是「根源是什么」+「接下来先做什么」，且四个变更同期叠加、原始报文不留存——这是**因果深度未知**的问题（不是选项广度、也不是数量关系），唯一能定位的维度是「必须发生时序」与「恒等式分解」。故用林状图／回溯法：先用恒等式把 1.3 个百分点的降幅拆干净，再用支付链路的必经时序选轴，最后给出处置根（修本次）与消解根（灭这一类）。

## L0 类别判定

**类别**：分布式支付链路「端到端成功率」结构性下降，主支落 `software`（配置/依赖/并发姿态）+ 明显外溢到尚未建节点的 `network` 支。
**判据**：①可复现性来自代码/配置/环境姿态而非物理介质——同一地区、同一端稳定地变差，且与 10-08 14:00 的切换对齐；②失败是确定性竞争导致——不是随机位翻转，而是「某一跳的延迟 vs 客户端超时阈值」的确定性比较。
**已排除的大类**：硬件故障（无 CRC/ECC/重传迹象，症状按地区稳定分簇而非跨进程随机）；权限/账号体系（App 与 Web 共用同一账号与风控体系，二者却方向相反）；纯组织流程（是加重项，非首因，但进入类根）；随机故障（时序单调，不像噪声）。

## L2 逐层回溯

### 先做恒等式分解（不是选轴，是把降幅拆干净）

成功率 `S = 1 − Σ(失败族 i 的占比 × 该族绝对发生率)`。用 `3.1 按失败原因`的比例乘总失败率（1.8% → 3.1%）还原绝对值：

| 失败族 | 三周前（×1.8%） | 本周（×3.1%） | Δ（pp） | 占 1.3pp 降幅 |
|---|---|---|---|---|
| 网关超时 | 0.864% | 1.922% | **+1.058** | **81%** |
| 风控拒绝 | 0.774% | 0.651% | −0.123 | −9% |
| 其他（取消/余额/参数） | 0.162% | 0.527% | +0.365 | +28% |
| 合计 | 1.800% | 3.100% | **+1.300** | 100%（闭合） |

三条立即成立的结论：
1. **风控不是原因**。它占失败的比例从 43% 掉到 21%，是因为**分母从 1.8% 涨到 3.1%**；它的绝对拒绝量其实**下降**了 0.12pp。风控团队说「规则没动过」与数据一致。
2. **增量几乎全是「超时」**（+1.06pp / 81%，相对涨幅 +122%）。任何解释必须能解释「为什么是超时」。
3. 「其他」族 +0.365pp（28%）**没有任何变更能解释**——这是一个空位，见挂起表 H8。

### 再选轴：按一笔支付的必经时序（生成式，非列举）

生成源＝必经时序：一笔支付从「点击」到「结果回写」必然经过这些跳，每一跳都必须存在，故每一格必然存在（可裁链，不可裁格）。

| 格 | 为什么这格必然存在 | 本次在该格看到什么 | 判定 |
|---|---|---|---|
| **S0 客户端**（点击、JS、超时阈值、重试） | 支付必须由客户端发起 | 下单页 JS 错误 0.4%→2.1%（10-08 起）；App 失败率 3.4→5.2 / 3.0→4.1，**Web 反而 2.8→2.3 改善** | 有症状，但**方向与 Web 相反** ⇒ 客户端差异是「放大器」，不是全量根源 |
| **S1 边缘分发/域名路由**（DNS、TLS、静态资源、API 域名） | 客户端必须先解析、握手、取到 API 入口 | B 节点区域 TTFB p95 180→**420ms（2.33×）**；**仍走 A 节点的区域 180→180，未变**；海外失败率 3.2→**8.9%**；且「全站接管」与「仍走 A 节点的区域」并存 | **唯一同时具备「处置组/对照组分离 + 地区选择性 + 时间对齐 10-08 14:00」的格** ⇒ 主支 |
| **S2 我方接入层/BFF**（下单、优惠券校验重写） | 客户端不直连支付网关，必有接入层 | **无任何指标（观测空白）**；可反推：若此格为根，Web 与国内应同幅恶化，事实相反 | **不可观测 ⇒ 只能挂起，不能判无罪**（这是关键区分） |
| **S3 支付网关**（受理、超时、504） | 必须有一方受理支付请求 | API p95 325ms vs 320ms（**持平**）；但网关侧 504 占其响应 9%→**27%（3×）**；「网关超时」占失败 62% | 网关**自身处理时延未变** ⇒ 超时点不在网关处理器，而在「到网关之前」或「网关的上游」；62% 的「网关超时」是**记账科目，不是故障地点** |
| **S4 通道/风控/银行** | 真实资金侧必然存在 | 风控拒绝绝对量 0.774%→0.651%，下降 | 无新增症状 |
| **S5 数据层（PG、订单库）** | 订单与幂等必须落库 | 慢查询（>1s）与三周前持平 | 无症状 |
| **S6 结果回写/幂等/对账** | 支付结果必须回写，且对账要对得上 | 无数据；「其他」族 +0.365pp 未解释 | 空白 ⇒ 见 H8 |
| **S7 容量（横切乘数，不占格）** | 任何链路都有容量上限，是乘数不是环节 | 发起量 +40%（10-10~10-14）；504 3×；10-10 起斜坡；**10-15 促销结束即 +0.3pp 回升** | 乘数/放大器；**解释不了 10-08 的 step**（step 在促销之前） |

**全空列判据**：S2/S5/S6 空，但 S0/S1/S3 有症状 ⇒ 坐标系可用，不换轴。但必须点明：**S2/S6 的「空」是未测量，不是无故障**。把「没量」当成「无罪」，正是本次两周定不了位的直接机制。

### 沿时序回溯到类根

- **层1（哪一格的状态在 10-08 14:00 后被改变？）** → S1。四个变更里只有一个的作用面正好是「整层替换」：CDN 由 A 全量接管到 B，且**含 API 域名**。v3.4 只动前端与优惠券校验（S0+S2）、PG 只动 S5、促销只动 S7 的乘数。
- **层2（为什么一次边缘替换能变成 1.3pp 的端到端损失？）** → 因为缺了四道缓冲：① API 域名与静态资源同域同边缘，边缘劣化直接进入支付链路；② 客户端超时阈值短于新边缘的 p99（420ms 的 TTFB 加握手后轻易打穿移动端短超时）；③ 超时后的重试没有退避与幂等约束，把「慢」放大成「失败」并推高发起量；④ **失败分类只记「哪一族」不记「哪一跳」**，于是 62% 的最大族无法定位到人。
- **层3（为什么两周还在猜？）** → 因为**变更按组件发布、指标按结果聚合、放行无对照组**，三者同时成立。三个被怀疑的变更都能被数据独立否掉或降级（PG→慢查询持平；v3.4→Web 改善；风控→绝对量下降），唯独「整体接管一层」的那一个不能被否掉——**不是因为它最可疑，而是因为它是唯一没有对照组的**。

→ **类根**：**支付成功率的结构性下降，发生在「一整层被全量替换」与「观测与放行仍按单组件粒度」同时成立的结构条件下。** 在这个结构里，任何一次全量替换都必然把一个本可在 2 小时内定位的问题，变成一场跨团队、无休止的归因争论；而且被替换的那一层越「基础设施」，越无法被证伪（三方都能自证清白）。
  - └ **个例根（本次具体机制）**：CDN 厂商 B 在海外/部分 PoP 的回源链路劣化（TTFB 180→420ms，2.33×；A 节点区域维持 180ms 未变）→ 打穿原生 App 的短超时 → 客户端侧超时被归入「网关超时」科目；10-10 起 +40% 发起量（其中含重试放大）把网关侧 504 从 9% 推到 27%，形成**两段式下降**：10-08 的台阶（约 −0.3~0.4pp，促销前已在）＋ 10-10 后的斜坡（约 −0.7pp，负载乘数）；10-15 促销结束即回升 +0.3pp，与斜坡部分属负载乘数一致，也说明**还剩约 −0.4pp 的台阶没走**——那正是 CDN 那一段。

## L3 双根

### 处置根（修本次）

**先回切边缘，再修放大器，全程不碰 v3.4 与 PG。**
1. 分钟级可逆：把**海外/App 的 API 域名**从 B 切回 A（或切到 B 的其他 PoP），**只切 API 域名、不切静态资源**（静态资源慢只影响体验，不动它才能让「JS 错误 2.1%」与「支付失败」解耦，避免第二次混淆）。可回切时间目标 < 15 分钟。
2. 并行修放大器：客户端指数退避 + 幂等键（禁止无幂等重试）；给支付受理链路单独做容量护栏（限流 + 排队），因为下一次大促还会来。
3. 独立修 v3.4 的 JS 错误（0.4%→2.1% 是真问题），但**与支付成功率分开立项跟踪**——它没有转化为支付失败（Web 反而改善），混在一起只会再次污染归因。

### 消解根（灭这一类）

**把发布/切换的单位从「组件」改成「可对照的切片」，并把失败记账从「哪一族」改成「哪一跳」。**
- **不可发生判据**：若当时采用它，则 10-08 14:00 的切换落地后 2 小时内，海外 B 组与国内 A 组的 TTFB、成功率、失败跳并排出现在同一张看板上，回切决策在小时级完成——本次这种「四个变更叠两周、三方各自清白、62% 的失败族指向不了任何一跳」的**结构不可能发生**（不是「变少见」）。
- **可执行首边**：① 把现有四维交叉表（地区 × 节点组 × 端 × 失败族/错误码 × 是否重试）按天回补，**分母一并回补**；② 在任何「接管一整层」的发布单里强制增加一栏「对照切片」（同一切口下 A/B 两侧各自的成功率与失败跳），不填不予放行。
- **成本量级**：回补报表 ≈ 1 人日（数据在数仓里，只是没切）；切换流程改造 ≈ 1~2 周；客户端超时预算下发（服务端下发超时 + 重试契约）≈ 3~5 人日。量级与「再猜两周」的机会成本相比可忽略。

## L4 迁移出口

1) **可观测性迁移**：失败族 → **失败跳（hop）+ 状态码 × 耗时 × 是否重试**。注意合规约束：原始报文不留存，因此这些标签必须在**聚合之前**就打进指标（只含标签与计数，不含报文内容）——这是「不留报文」前提下唯一可行的替代方案，也正好绕开合规。
2) **口径迁移**：日成功率改为「点值 + 分层加权」双口径，禁止把滚动均值当点值用；各维分母（发起量占比）必须随指标一起发布。
3) **变更纪律迁移**：CDN/网关/DNS 这类「接管一整层」的变更统一纳入分级发布（金丝雀 → 地域切片 → 全量），并要求可回切时间 < 15 min。
4) **组织能力迁移**：风控/后端/CDN 厂商的「我没动 / 无异常」必须带**对照口径**才算证据；建立「变更 → 指标切片 → 预期方向」台账，每次变更自带验证条件。
5) **客户端契约迁移**：超时与重试策略由服务端下发，禁止各端自行拍阈值。

→ **本次问题降级为第 1) 与第 3) 两项下的一个症状**：它不再是「一次神秘的 1.3pp 下降」，而是「缺少 hop 级记账 + 缺少对照放行」这条结构性缺陷的第一个案例。

## 结论

1. **根源不是一个变更，而是一个结构**：「一整层被全量替换（CDN 全站接管含 API 域名）」遇上「指标按结果聚合、失败只记族不记跳、放行无对照组」，于是四个变更里唯一无对照组的那一个无法被证伪，两周都停在猜——这是**类根**；本次的**个例根**是 B 厂商在海外/部分 PoP 的回源链路劣化（TTFB 2.33×）打穿原生 App 短超时，再被 +40% 量与大促放大成 504 三倍，形成「10-08 台阶 −0.3~0.4pp ＋ 10-10 后斜坡 −0.7pp」的两段式下降，10-15 结束大促回升 0.3pp 只走掉了斜坡那一段。
2. **今天先做的一件事**：出一条按 **地区 × 边缘节点组（A/B）× 端 × 失败码/是否重试** 的四维交叉成功率（附各自分母），对比 10-07 / 10-12 / 10-13。它同时验证三件事——CDN 假设、构成效应、口径分母——成本是一条查询、零风险，且**验证即处置**：若「仍走 A 节点的区域」确实是没掉的那批，就立刻把海外/App 的 **API 域名**回切 A（只切 API、不切静态资源），15 分钟内可逆。
3. **同时（不依赖上一步）**修放大器：客户端指数退避 + 幂等键 + 支付受理链路限流/扩容。不要先回滚 v3.4（Web 反而改善，回滚会同时动两个变量且方向不对），不要先怀疑 PG（慢查询已否），也不要把「厂商说无异常」当证据（它给的是它自己的口径）。
