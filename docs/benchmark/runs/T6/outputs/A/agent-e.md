# 订单服务三现象定位：一个类根，五个投影洞

[🌳 林状图] [选择理由：题目问的就是「根源到底是一个还是几个」，未知在**因果深度**而不是选项广度，必须走林状分层回溯；且我怀疑三个认领人各自抓到的是「个例根」而非「类根」，需要把个例根挂到类根下面才能回答"分头修行不行"。]

> 一句话答案放在最前面，因为它决定后面怎么读：
> **不是三个 bug，也不是一个 bug。是一个"缺席者"（请求作用域边界）+ 它缺席后留下的五个洞。「库存对不上」有三个独立来源，其中两个不在任何人的认领清单里 —— 所以分头修必漏。**

## L0 类别判定

**类别：`software` 类中的「运行时请求处理路径的状态一致性」子域**（判据：①同一份 `service.js` 在同一台机器上确定性复现，压测三轮结果逐字节一致；②失败由确定性时序竞争导致，每一次都能归因到某段 `await` 的让出点，没有随机位翻转）。

**已排除的大类**：硬件故障（无 CRC/ECC、无温度负载相关、重启即归零）、网络问题（客户端与服务端同在 `127.0.0.1` 回环，无链路变量；504 精确落在 200ms 且只对单一 SKU）、权限/账号体系（无 ACL/令牌/服务账户变量，同一用户同一命令结果稳定）、组织流程（争论尚未发生，三个技术现象已全部可由代码单独复现）。

## L2 逐层回溯

### 选轴（生成式，不是列举）

**轴 = 一次 `/pay` 请求从进入到响应的必经时序**（生成源：必经时序，一步一格）。为什么必然存在：任何订单服务都必须「先知道要买什么 → 判断有没有货 → 把货占住 → 对下游承诺 → 留痕 → 决定回什么码 → 决定这些状态活多久」。七步缺一，服务就不成立。

正交性 / 可生成性 / 可观测性三判据逐格校验（见下表「格的独立性」列）。

### 七格 + 逐格症状 + 逐格判定

| 格 | 必经步骤 | 代码位置 | 该格故障的可观测症状 | 本轮观测到了吗 |
|---|---|---|---|---|
| **G1** | 准入与输入契约（sku/qty 解析与校验） | `service.js:96-97` | 非法数量被接受：负数量返库存、0 免费下单、非数字把库存写成 NaN 并**永久**废掉该 SKU | ✅ 实测命中（见 E8） |
| **G2** | 可用量判定读 | `service.js:52,54` | 判定基于过期快照；并发下 409 一个都不出 | ✅ 16 并发 SKU_C：`e409=0`，16 单全 200 |
| **G3** | 库存提交写 | `service.js:57-58` | 无锁递减，跌穿 0 成负数 | ✅ SKU_C 7 → **-9** |
| **G4** | 下游预留 / 事务边界 | `service.js:35-49,67` | 客户端预算 < 依赖真实延迟 → 该 SKU 100% 超时，与并发无关 | ✅ SKU_B 8/8 全 504，延迟 221ms |

**格的独立性（正交性证据，这是"一个还是几个"的判据）**：

- G2/G3 的竞态**不能**解释 G4 的 504 —— 串行 1 个请求也 504（E5）。
- G4 的错配**不能**解释 G5 的累积 —— 把 timeout 改 500 后 504 全消，listeners 照样 +8（E6）。
- G5 的泄漏**不能**解释 G2/G3 的超卖 —— 串行跑 7 单，`ok=28` 已经放大 4×，但库存 7→0 完全正确（E4）。
- G6 的白扣**不能**解释 G2/G3 —— 并发=1 时 SKU_B 失败仍扣 1 件（E5），SKU_C 却不超卖（E4）。
- G1 的校验缺失**不能**解释题面三现象（题面压测 qty 恒为 1、sku 合法），但它能**单独**把任意 SKU 永久打穿（E8）。

四格各自有专属症状、互不解释 → 正交成立，所以**"只有一个根"的说法是错的**。

### → 类根

> **类根：这份代码里不存在"请求作用域"这个边界。**
>
> 所有跨请求可变状态（`stock` / `audit` / `stats` / `auditTrail`）都是模块级全局量，因此四件事同时缺失：**没有所有权**（谁注册的副作用谁负责释放）、**没有原子性**（读—改写之间可以被 `await` 拆开）、**没有事务边界**（预留失败必须回滚，但这里扣减已经提交）、**没有输入契约**（非法请求也能进临界区）。
>
> 这一类在什么结构条件下必然可能发生：**只要"请求级副作用 + 跨请求可变状态"共用同一个进程级容器，且中间存在任何 `await`，这一整类问题就是必然而非偶发。**

**个例根挂在类根之下（是子节点，不是平行清单）**：

```
类根：请求作用域边界缺席
├── 个例根 A（G2+G3）TOCTOU：判定读 remain 快照，扣减读 stock[sku] 实时值，中间 await sleep(3)
│     └ 症状：SKU_C 16 单全 200、库存 -9、e409=0；串行则 7 成 9 拒、库存 0（正确）
├── 个例根 B（G4）超时预算错配：DB_CLIENT_TIMEOUT_MS=200 < SKU_B 真实耗时 300
│     └ 症状：SKU_B 100% 504/E_DB_TIMEOUT，延迟恒 221ms；改 500 即全 200（E6）
├── 个例根 C（G5）请求级注册 + 进程级持有 + emit 广播扇出
│     └ 症状：auditListeners=请求数（永不减）、rss 线性涨、ok = Σ(emit 时刻存活监听器数)
├── 个例根 D（G3 先于 G4 + G6 无补偿）★无人认领
│     └ 症状：504 订单照扣库存（8 单 → 8 件蒸发），且串行也发生 → 与并发无关
└── 个例根 E（G1）qty 无校验 ★无人认领
      └ 症状：qty=-100 返库存（500→600）、qty=0 免费成功、qty=abc 把库存写成 NaN 后
              该 SKU 永久 200 且 remain 恒 null（无限卖，库存保护彻底失效）
```

### 为什么"分头修"一定漏 —— 反事实推演 + 实测边界

| 谁修什么 | 修完之后 | 仍然存在 | 实测依据 |
|---|---|---|---|
| **甲** 给库存加锁/串行化 | SKU_C 不再 -9 | D 白扣、E 打穿、C 泄漏全在 | E4：串行=正确，但同环境 SKU_B 单请求仍白扣（E5） |
| **乙** 把 timeout 200→400 | SKU_B 恢复 200 OK | A 超卖、C 泄漏在；依赖再慢时 504 回来并继续白扣 | E6：8/8 变 200；E7：timeout=500 但依赖=1000 时 4/4 又 504 且库存 40→36 |
| **丙** 改 `audit.once` / 就地计数 | `ok` 数对了、内存斜率下降 | A、B、D、E 完全不动 | E6：改 timeout 不影响 listeners；E4：串行下 `ok` 也放大（28 vs 7） |
| **无人认领** | —— | **D + E**：题面"库存对不上"有一半来自 D，E 能一行 URL 永久废掉库存 | E5 / E8 |

更狠的一层：三个洞之间有**正反馈**。`audit.on` 注册发生在 `dbReserve` **之前**（`service.js:62` 早于 `:67`），所以**失败请求也在漏内存**；而 A 的超卖让更多请求活到 `emit`，`ok` 爆炸更快。三个人分别修，各自的指标都会变绿，但把三条曲线叠起来会看到同样的斜率仍在 —— 只有**同一组判据同时回归**才能防假通过。

## L3 双根

### 处置根（修本次，五件事必须成组上线）

1. **G1**：`const qty = Number(...)` 后强制 `Number.isInteger(qty) && qty > 0`，否则 400；`sku` 白名单。
2. **G2+G3 合并成同步临界区**：判定与扣减之间**不得出现任何 `await`** ——`if (stock[sku] < qty) throw 409; stock[sku] -= qty;` 连写成一段。Node 单线程的同步段天然原子，这就够；多副本才需要行锁/乐观版本号。
3. **G3 与 G4 的顺序**：扣减必须在 `dbReserve` 成功之后；若坚持"先扣后预留"，则 catch 里必须 `stock[sku] += qty` 补偿，且补偿本身要幂等。
4. **G5**：删掉每请求 `audit.on`，`stats.ok++` 就地执行；`auditTrail` 改环形缓冲（有界）；`/health` 去掉 `auditListeners` 这种会随请求数变化的业务字段。
5. **G6**：catch 分支必须满足"状态码 ↔ 库存影响"一一对应（504/500 一律不改变库存）。

### 消解根（灭这一类）：给请求路径建立显式 **Request Scope** + 显式共享资源契约

- 每个请求一个 `scope` 对象，持有本请求一切可变量（预留量、计量、审计项、超时预算、已提交标记）；
- 跨请求共享的只能是**显式声明**的资源，且必须带并发控制（DB 行锁 / 乐观版本号 / per-SKU 串行队列）；
- 生命周期：scope 里注册的一切副作用随 scope 在 `finally` 统一提交或回滚；
- 输入契约在 scope 建立**之前**校验完，非法请求连 scope 都不建；
- 超时预算随 scope 与依赖 SLA 一起声明，禁止散落的模块级常量（`DB_CLIENT_TIMEOUT_MS=200` 与 `DB_SLOW_QUERY_MS=300` 本来就是同一件事被写成了两个互不认识的常量）。

**三道闸门**：

1. **不可发生判据**：若当时有 scope 边界，则 (a) 读改写不可能被 `await` 拆开（同一 scope 内的同步临界区）；(b) 预留失败必然经 `finally` 回滚（库存在 scope 内）；(c) 请求级副作用不可能被进程级持有（scope 回收即回收）；(d) 非法 qty 进不来（契约在 scope 之前）；(e) 超时预算与依赖 SLA 必须同处声明，200<300 的错配不可能被写出来。→ 四个洞在**结构上不可能形成**，而不只是变少见。对照：**只把 timeout 调大不满足这条判据** —— 它只是让 504 变少见，E7 已经实测证明依赖一慢失败就带着白扣回来。
2. **可执行首边（很小，半天）**：在 `handlePay` 里加 `const scope = { sku, qty, committed: false }` + `try { ... } finally { if (!scope.committed) rollback(scope) }`，先把"回滚"这条边打通；同时把 `stats.ok++` 从监听器搬到就地执行。这一小步就能同时关掉 D 和 C。
3. **成本量级**（量级交给 📐 定，此处只给量级）：单进程内改造 **0.5–1 人日**；库存真源迁到 DB/Redis 事务+行锁 **1–3 人日** + 一次数据修正窗口；观测口径重定义 **0.5 人日**；per-SKU 队列的 QPS 上限需确认 —— 当前 p50 62–70ms 由 `sleep(3)` + `dbReserve(40ms)` 支配，同步临界区不会成为瓶颈。

## L4 迁移出口（消解根指向"作用域 + 显式共享资源"带来的新问题）

1. **数据与状态**：库存真源离开进程内存 → 需要一致性校验脚本与影子读；已污染数据必须先修（现在 SKU_C=-9、SKU_A 已是 `NaN`→`null`）。
2. **运行与自启**：多副本后进程内 `stats`/`auditTrail` 不再是全局真值 → `/health` 从"业务真值"降级为"存活探针"，指标落集中式。
3. **可观测性**：`ok` / `e504` / `auditListeners` 口径全部重定义（`ok` 必须等于显式提交次数；`total` 不应把 `/health` 自己算进去 —— 现在算了，见挂起表第 6 条）。
4. **凭据与权限模型**：DB/Redis 连接串、超时预算、池大小进入配置与部署环境，不再硬编码。
5. **组织能力**：验收必须是一条"同时校验四件事"的流水线 —— 库存恒等式（Σ成功 qty = 初始库存 − 当前库存）、状态码分布、`rss` 斜率、`ok` 与成功请求数一致。缺了它，三个人分头修仍然会各自"通过"。

→ **本次问题降级为：第 3 项（观测口径）与第 1 项（库存真源）的子项** —— 即"三个现象"只是"缺请求作用域 + 缺集中式观测口径"这个更大问题的一个子项，不是三个独立工程。

## 候选根排序（Share × Lever ÷ Cost，上下级结构）

| 层级 | 根 | Share（能解释多少已观测现象） | Lever | Cost | 序 | 动作 |
|---|---|---|---|---|---|---|
| **类根** | 请求作用域边界缺席 | **唯一**（能解释全部 5 个洞、7 格症状） | 改架构 | 0.5–1 人日 | — | 用同一组判据验收，不单独"修" |
| 个例根 | **B** G4 超时预算 200<300 | 唯一（504 全灭） | 改配置 | 一次压测 | **1** | 必须与 D **同批**上线 |
| 个例根 | **D** G3 先提交 + G6 无补偿 | 主因（库存对不上的第二来源） | 改代码 | 一次压测 | **2** | 与 B 同批；单修 B 会把白扣藏起来 |
| 个例根 | **A** G2/G3 TOCTOU | 主因（超卖 -9） | 改代码 | 一次压测 | **3** | 同步临界区，一行合并 |
| 个例根 | **C** G5 泄漏 + 扇出 | 唯一（内存 + 计数） | 改代码 | 一次压测 | **4** | `on`→就地计数 + 有界 trail |
| 个例根 | **E** G1 qty 无校验 | 次要（题面未暴露，但能永久废掉库存） | 改代码 | 一次压测 | **5** | 不许省；否则前四个修完仍能被一行 URL 打穿 |

> 排序的预算含义：五条的 Cost 都是"一次压测"，所以序由 Share×Lever 决定。**但 1 与 2 之间没有排序，只有绑定** —— 因为 B 一旦单独修好，D 造成的库存蒸发就从"504 现象"里隐身了（失败率归零，没人再去看库存差），这是最危险的一步。

## 挂起表（分支｜判定｜依据｜恢复条件）

| # | 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|---|
| 1 | 硬件/内存介质故障 | 挂起（非根） | `rss` 增长与 `listeners × 64KiB` 严格同斜率；重启归零；无随机性 | 重启后零请求也涨，或同镜像跨机斜率不同 |
| 2 | 网络/回环问题 | 挂起（非根） | 同在 `127.0.0.1`；504 精确落在 200ms 且只对 SKU_B；改 timeout 即消 | 换远端 DB 后 504 分布改变 |
| 3 | GC 压力导致 504 | 挂起（非根） | 串行单请求、堆仅 49MB 时也 504；`rss` 87MB 时 SKU_A 仍全 200 | 并发下 504 率显著高于串行 |
| 4 | 409 判定逻辑本身写错 | 挂起（非根） | 串行 16 次得 7×200 + 9×409、库存归 0，判定本身正确 | 串行也超卖 |
| 5 | qty 被放大（>1）导致 -9 | 挂起（非根） | 压测固定 qty=1，7−16=−9 恰等于 16×1 | 日志出现 qty≠1 的订单 |
| 6 | `stats.total` 把 `/health` 自身计入 | 挂起（是缺陷，但非三现象之根） | E1 中 `total=19` = 16 pay + 3 health | 一旦要计算成功率就必须先修 |
| 7 | `Promise.race` 超时后未取消 `work`（僵尸查询）——**树外分支** | 挂起 | 本实现里 `work` 只是 `sleep` 后置 `finished`，无副作用；真 DB 客户端等价于"超时了查询还在服务端跑"，连接/游标累积 | 接入真 DB 客户端时必须核查 cancel 语义 |
| 8 | 知识树 `request-path`（请求作用域轴）——**树外分支** | 登记 **v2 候选** | `software.md` 六层是启动期轴，缺运行时请求链 | 待新节点落库后回填 L1 |
| 9 | 三个现象来自三个独立子系统（配置漂移等） | 挂起（非根） | 全部现象在单文件单进程内可确定性复现 | 出现只在某环境下才复现的分片症状 |
| 10 | 压测脚本重复统计 `ok` | 挂起（非根） | `load.js` 每请求只 `push` 一次 `results`；`ok` 由服务端给出；扇出定律在串行下也成立（28 vs 7） | 出现客户端侧计数与服务端不一致 |

---

## 结论

1. **一个还是几个**：**一个类根（请求作用域边界缺席）+ 五个投影洞**。类根是"这一大类在什么结构条件下才可能发生"的答案：只要"请求级副作用 + 跨请求可变状态"共用同一个进程级容器、且中间存在 `await`，这一类问题就是必然而非偶发。
2. **三现象归因**：超卖 ← A（并发 TOCTOU）；504 ← B（超时预算错配）；内存 + 计数 ← C（请求级注册 / 进程级持有 / `emit` 广播）。**但"库存对不上"有三个来源：A、D（失败不还库存）、E（qty 无校验）** —— D 与 E 不在任何人的认领清单里，这是"分头修"必漏的实质所在。
3. **定位顺序**（这才是本题真正的交付）：先建一条**同时校验四件事**的压测（库存恒等式 / 状态码分布 / `rss` 斜率 / `ok` 与成功数一致），再按 **B+D 同批 → A → C → E** 修。理由：任一根单独修都能让自己那条指标变绿，而 D 会在 B 修好后彻底隐身；只有同组判据同时回归，才能否掉假通过。

## ⚠️ 异常 / 矛盾 / 空白

1. **⚠️ 题面"成功计数大一个数量级"是个低估**：它不是固定倍数 bug，而是**二次增长的扇出效应**。16 请求时是 16×（256 vs 16），16 轮后是 **283×**（146946 vs ~518）。若按"一个数量级"去修（除以 10 之类），必然修错。
2. **⚠️ 题面"48MB → 89MB"我复现到 87MB**（534 listeners），差 2MB 属 GC 时机与轮次差异；按 64KiB/监听器 + `auditTrail` 二次增长核算，89MB 约对应 550–650 个已付请求。基线 48MB 精确吻合。
3. **⚠️ 一个容易误导的"半正确"写法**：`remain` 用**快照**判定（`service.js:52`），扣减却用**实时值**（`service.js:58`）。两份读不同源 —— 正因如此，16 并发的结果才是显性的 **−9**；若两处都用快照，结果会是"库存显示 6、实际卖了 16"（隐性 lost update），更难查。**这份代码是在"恰好把它暴露出来"的那一侧**，改动时别把这一点改成一个更隐蔽的 bug。
4. **⚠️ 空白**：题面未说明 504 的 SKU 是哪个（我从 `service.js:36` 的 `SKU_B` 特例推定，实测吻合）；也未说明压测的 `qty` 是否恒为 1（我按 1 复现，−9 恰等于 7−16）。若实际压测用了 `qty>1`，超卖量级会不同，但机制不变。
5. **⚠️ 无人认领的第四个洞**：`audit.on` 注册发生在 `dbReserve` **之前**，所以 504 失败的请求同样注册监听器、同样漏 64KiB（E2：8 个失败请求让 listeners 16→24）。修 C 的人如果只看成功路径，会漏掉这一半。

## 💡 灵感备注

- **一条恒等式就能验收全部修复**：`Σ(成功订单 qty) == 初始库存 − 当前库存`。当前 −9 违反；而且**任何单点修复都无法让这条等式对那批 504 请求成立** —— 这比"看三张指标图"更难被糊弄。
- `/health` 业主已经把 `auditListeners` 和 `maxListeners` 一起吐出来了，这是留在案发现场的哨兵。定位的第一步不该是读代码，而是压测后看**这个字段的每请求斜率**：`+1/请求 = 泄漏`，一格就能定性。
- 一个更便宜的消解首边：`stats.ok` 不必依赖事件总线 —— 从 `auditTrail.length` 或 `paidCount` 直接推导，可立刻让计数正确且顺手把这个泄漏源拔掉。
- 这条类根可以外推成一句通用判据：**只要你在一个进程级容器上，为"请求级"的东西 `on()` 了却从不 `off()`，或者为"请求级"的扣减了却在失败路径上从不补偿 —— 那么你缺的不是两个 bug，是一个作用域。**
