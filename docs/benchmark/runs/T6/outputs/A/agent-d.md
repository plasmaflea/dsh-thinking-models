### → 类根

**类根（结构条件）**：**每个请求被当成一个「没有作用域、没有提交点、没有所有权」的开区间**——状态、副作用、资源三者都没有明确的「进入 / 提交 / 释放」边界。

许可关系（必要条件的说法）：只要这个结构条件在，(i) 读到过期的值（③）、(ii) 提交不该提交的副作用（⑤）、(iii) 资源跨请求存活（⑦）、(iv) 计量无锚点（⑥）就都是**结构上必然可能**的；反过来，补上其中任何**单一**格，另外三格**都不会消失**（正交验证：修好 504 不会让 -9 变小，修好 -9 不会让 RSS 变平，修好 RSS 不会让 ok 变准）。

### └ 个例根（挂在类根下，非平行清单）

- **G1「库存对不上」＝ 3 个独立机制**：1-a 校验式缺 qty 维度（`<=0` 应为 `< qty`，且 qty 必须为正整数）｜1-b 参数域无校验（负数把库存加回去、0 元单也成交）｜1-c check-then-act 跨 await（并发窗口内全部通过校验）。**题面 -9 的主因是 1-c，但 1-a/1-b 在 qty>1 或恶意入参下独立成立**。
- **G2「某 SKU 全 504」＝ 1 个机制**：客户端超时预算（200ms）与依赖真实耗时（300ms）是两个各自独立的常量，彼此不知道对方存在。单点、确定性、与并发无关。
- **G3「内存涨 + ok 放大」＝ 2 个机制**：3-b 监听器泄漏（资源无所有权）｜3-a 计数口径把「监听器被调用次数」当成「请求成功数」。
- **X1「失败照样扣库存 + 失败请求污染成功计数」（无人认领）**：⑤ 的缺回滚 + ⑦ 的失败路径同样泄漏（`:62` 注册早于 `:67` 抛错）。**这是三个症状之间的真实耦合**，也正是「一人一件」分工会永久漏掉的东西。

## L3 双根

### 处置根（修本次，四处）

1. **`service.js:52-58` 收成一个不跨 await 的单一写入口**（同时灭 1-a/1-b/1-c）：
   `function tryReserve(sku, qty){ if(!Number.isInteger(qty)||qty<=0) throw mkErr(400,'E_BAD_QTY'); const r=stock[sku]; if(r===undefined) throw mkErr(400,'E_NO_SKU'); if(r<qty) throw mkErr(409,'E_NO_STOCK'); stock[sku]=r-qty; return {sku,qty}; }` —— 把 `await sleep(3)` 移出临界区。
2. **`service.js:19` 与 `:36` 合成单点预算**：超时上限由「依赖自己声明的耗时上限」生成（`DB_SLOW_QUERY_MS + 余量`），而不是另写一个独立常量。
3. **`service.js:58`/`:67` 加提交边界**：先预留拿 token → `dbReserve` 成功才 commit → 任何 throw 路径在 `finally` 里 rollback 归还（灭 X1）。
4. **`service.js:62-65` 给监听器加所有权**：`audit.once('paid', ...)` 或 `try/finally` 里 `audit.removeListener`；`stats.ok++` 只在「提交成功」处自增一次；`ctx` 与监听器同生命周期（灭 3-a/3-b）。

**预期（可用同一压测验收）**：SKU_C `16×32` → `{200:7, 409:25}`、stock=0；SKU_A `16×320` → `ok=320`、`auditListeners=0`、RSS 稳定在 ~50MB；SKU_B `16×32` → `{200:32}`、stock 40→8（**这次是对的，因为真的成交了**）。

### 消解根（灭这一类）

**把「请求作用域」变成结构强制**，四条不可发生判据：

① **状态写入只允许经过单一写入口，且该入口不得跨 await**（必要时加版本号/CAS），使「读过之后再写」在代码结构上不可表达 → ③ 类不可能。
② **副作用一律「预留-提交-回滚」三段式**，任何 throw 路径都经过 `finally` 的补偿 → ⑤ 类不可能（失败不可能留下已提交副作用）。
③ **超时预算由依赖声明的耗时上限生成，单一来源**，禁止两处独立常量 → ④ 类不可能。
④ **所有全局注册（`emitter.on`/timer/socket）返回 disposable，由请求作用域自动释放**（`AsyncLocalStorage` 或 `try/finally`），未释放即测试失败；计数只在「提交成功」处自增一次 → ⑦⑥ 类不可能。

**三道闸门**
- *不可发生判据*：四条各自把对应格的问题变成「结构上不可表达」，而不只是「更少见」——例如 ② 之后，「失败请求扣了库存」没有可写的代码路径，因为库存的 commit 只挂在成功分支上。
- *可执行首边*（最小第一步，本轮就能验）：在 `service.js` 里新增 `tryReserve(sku, qty)`，把 `:52-58` 的读-判-写整体搬进去并删掉中间的 `await sleep(3)`；重跑 `conc=1` 与 `conc=16` 两档，若 -9 与 -3 同时消失，则 ①② 两格已闭合。约 10 行。
- *成本量级*（粗量级，**未走 📐 公式图，仅量级**）：①②④ 是 `service.js` 单文件内的结构性改动，**小时级～1 人日**；③ 需把「依赖耗时上限」变成声明式配置，**小时级**。若进一步引入真实 DB 事务/幂等键，则升到**天级**——但那属于 L4-1。

## L4 迁移出口

消解根指向「代码结构强制」，并非换环境；仍列后续问题清单，避免把「不解决具体问题」当策略：

1. **状态外部化**：现在 `stock` 是进程内对象，重启即回滚。多实例部署时每实例各卖 7 件，超卖会以「实例数倍」放大。→ 迁到 DB/Redis 后，「预留-提交-回滚」必须变成事务或幂等键，需要**数据迁移与一致性校验**。
2. **多实例语义**：`stock` 与 `audit` 都是实例级状态，需外部化 + 幂等键（否则 ④ 的 disposable 只解决单进程内存）。
3. **可观测性重定义**：`/health` 的 `ok` 必须重定义为「已提交成功」，并把 `auditListeners==0`、`Δrss/请求≈0` 做成 CI 断言（否则 3-a 会以别的形式回来）；`stats.total` 不应把 `/health` 计入。
4. **组织能力**：**把「一人一件症状」的分诊换成「一格一人（准入/依赖与提交/记账/资源）」的分工**——本次 X1 就是分诊粒度的直接代价，它既不在「库存」名下，也不在「504」名下。

→ **本次问题降级为**：上述 1) 的子项——「库存状态外部化之后的事务边界」。

| 树外分支 `observability-metrics` | 树无节点（`v2 候选`） | `stats.ok` 语义错位；`stats.total` 把 `/health` 计入（实测 323 对 320） | 同上 |
| 「并发度是否是唯一开关」 | **已验证为正交判据** | conc=1 → 7 单/0；conc=4 → 8 单/-1；conc=16 → 16 单/-9 | 若某 SKU 在 conc=1 下仍超卖，则叠加了 G1-a/G1-b |
| 多实例部署下的行为 | 未验证（推演） | 本实验全程单进程，`stock` 为进程内对象 | 起 2 个实例同压 → 超卖按实例数放大 |

## 结论

**三个症状＝三个互不解释的缺陷族，但只有一个类根；而且这个类根已经长出了没人认领的第四个症状。**

1. **是不是一个根？** 机制上**不是**：G1（库存对不上，含 3 个独立机制）、G2（全 504，1 个常量矛盾）、G3（内存涨+ok 放大，2 个机制）**互相不能解释对方**——修好 504 不会让 -9 变小，修好 -9 不会让 RSS 变平，修好 RSS 不会让 ok 变准。三人分头修的技术判断没错。
2. **但根源也确实是同一个**：三者都由「请求是一个没有作用域、没有提交点、没有所有权的开区间」这一条结构条件许可，所以它们是**同一个类根下的 5 个决策缺陷**，不是 5 个巧合。
3. **所以分头修仍然会漏**：类根已经产出 **X1 = 失败请求照样扣库存（32 个 504 扣掉 32 件，0 成交）+ 失败请求污染成功计数（2 次成功被记成 67）**。这条既不在「库存」名下也不在「504」名下——**按症状认领是分类错误，不是分工错误**。正确分诊轴是「请求时序格」：准入 / 依赖与提交 / 记账 / 资源，一格一人，且每格必须给出自己的专属症状。
4. **顺序由成本决定**：先 30 秒的 G2 与 1 分钟的 G1-a（消噪声）→ 用并发阶梯 + 单请求对照把 G1-c / G1-b / X1 分离 → 用 `/health` 的 `auditListeners` 与 `ok` 两个字段锁死 G3 → 再做结构性收敛（消解根四条）。**G2 与 X1 必须同批修并配一条「注入依赖失败」的守护测试**，否则修完 504 会让 X1 永久隐形。

## ⚠️ 异常/矛盾/空白

1. **题面低估了计数失真**：说「大了一个数量级」，实测是 **170×**（320 真实成功 → 54480），且是 **O(n²) 而非 O(n)**——它是「Σ 监听器数」，会随压测时长平方级恶化。
2. **`stats.total` 口径脏**：把 `/health` 自己也算进去了（实测 total=323 对 320 单成交），任何以 total 为分母的成功率都会偏低。
3. **`dbReserve` 的超时语义本身不成立**：`Promise.race([work, guard])` 里 `guard` 在 200ms 抛错，而 `work` 仍在 300ms 才置 `finished=true` 并**无人等待**。真实系统里这就是「服务端已完成、客户端以为失败」的不一致源；本题被进程内 `stock` 掩盖了，但它是 L4-1 的种子。
4. **已有告警从未被读取**：`MaxListenersExceededWarning` 在第一个 10 请求后就出现在 stderr，属于「已经告诉你答案但没人看」的典型。
5. **本报告的 L4-1/L4-2 是推演，未实测**：全程单进程，未验证多实例下超卖按实例数放大。

## 💡 灵感备注

「三个独立 bug 共用一个类根，而类根已经长出清单外的症状」是**按症状认领**这种分诊方式的结构性缺陷：认领清单只能覆盖「已经被人看见的现象」，而类根产生的是「还没被人看见的现象」。更好的分诊轴与本次回溯轴同构——按请求必经时序分格，一格一人，并把「该格故障的可观测症状」写成验收条件。这样 X1 会作为「提交边界」格的自有症状被主动发现，而不是等下一次事故。
