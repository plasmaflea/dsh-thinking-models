# 订单服务压测三症状：根源是一个还是几个？

**[🌳 林状图／回溯法]** 选择理由：提问形式是「根源在哪」「到底一个还是几个」——未知在**因果深度**而非选项广度，必须先定因果骨架再谈分工。三件现象表面互不相干，正是「先分头修」的典型误判入口，所以要把它们放回同一条必经时序上切片。

---

## L0 类别判定

**类别**：`software`（软件类）。
**判据**（两条同时满足）：
1. 可复现性来自代码/配置，不来自物理介质——同一份 `service.js` 在我这台机器上三件现象全部确定性复现（见文末 ✅）；
2. 失败是确定性的或由确定性竞争导致——#1 由 `await sleep(3)`（service.js:57）这个固定让出点触发，16 并发下 100% 命中，4 并发下按窗口比例命中；#2 是**纯确定性的常量倒挂**（200 < 300），串行也 100% 复现。
**已排除的大类**：硬件故障（无 CRC/ECC、非随机、同机可复现）；网络问题（全走 127.0.0.1 回环，504 由进程内 `sleep(300)` 与 `race(200)` 造成，与链路无关）；权限/账号体系（无 ACL 类症状）；组织与流程（见挂起表第 4 行——它是放大器，不是成因）。

## L1 树实例化

- 本次**命中**三个子层：`concurrency`（竞态）、`quota`（监听器/内存配额）、`config`（超时常量与下游耗时）。⚠️ 注意：它们命中在同一份进程、同一条请求路径上，是**同一次压测暴露的三个格子**，不是三套独立系统。
- 本次**判为不适用**：`lifecycle`（进程由前台 `node` 启动，从未猝死、`listen` 成功）；`init`（无「死在日志第一行之前」，启动即打印 1 行并 accept）；`dependency`（无缺失/版本/位数错误码族）；`win-service`（L1 节点，只管 Windows 服务形态的初始化失败，本例是前台进程）。
- ⚠️ **树外分支**：树 v1 给 `software` 挂的类根是「某个本该由应用掌握的控制权被外部机制代持」——**本例不适用**：控制权完全在应用自己手里，塌的是**应用内部的配对契约**。已登记 `v2 候选`（见挂起表第 7 行），不静默丢弃。

## L2 逐层回溯

### 层1：轴 = 单次请求的必经时序（生成源：必经时序，一步一格）

为什么这个轴是可生成的：一个 HTTP 请求在服务端**必然**按「进入路由 → 读共享状态并判定 → 提交写共享状态 → 等待下游 → 登记副作用/占用资源 → 响应或抛错 → 回收」走完，任何一步都删不掉。七格全有专属症状、互不解释（正交），且无一格为空（非全空列，坐标系有效）。

| 格 | 该格职责 | 落点 | 该格故障的可观测症状 | 本仓库实测 |
|---|---|---|---|---|
| G1 入口与计量 | 计 `stats.total` | service.js:80 | 计数口径混入探针流量 | `total=34` 而压测只发 32 单（多了 2 次 `/health`） |
| G2 读取与判定 | 读 `stock[sku]`、判 `<=0` 抛 409 | service.js:52-54 | 判定结果在提交时已过期 | 16 并发全部读到 `remain=7`，全部判通过 |
| **G3 提交/写共享状态** | `stock[sku] = stock[sku] - qty` | service.js:57-58（`await sleep(3)` 是间隙） | 卖出数 > 库存数、库存为负 | SKU_C 7 件卖出 16 单 → **-9**；SKU_A 180 件又卖出 182 单 → **-2** |
| **G4 等待下游** | `await dbReserve()` → `Promise.race([work, guard])` | service.js:67 → 35-49，常量在 18-19 | 某 SKU 100% 504，换 SKU 又正常 | SKU_B 32/32 = 504，串行 4/4 = 504；`DB_CLIENT_TIMEOUT_MS=200 < DB_SLOW_QUERY_MS=300` |
| **G5 登记副作用/占资源** | `Buffer.alloc(64*1024)` + `audit.on('paid', …)` | service.js:61-65 | 监听器数 = 累计请求数，Node 自报泄漏 | `auditListeners=550`，stderr 出现 `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 paid listeners added` |
| **G6 响应/失败路径** | catch 各分支 | service.js:100-110 | 失败请求仍改变了共享状态 | SKU_B 32 次全 504、成功 0，库存却 40→**8** |
| **G7 回收** | （**代码里不存在这一格**） | 无 `audit.off`／无 `ctx` 释放 | 计数按监听器数倍增 + RSS 单调涨 | `ok=156536` vs 实际成功 518（**302×**）；RSS **48 → 89MB** |

> G7 是「缺格」而非「空格」：按生成判据它必然存在，代码里根本没有它——**这个缺失本身就是发现**，不是我这套坐标的漏洞。

### 层2：每格往上问「这一格缺了什么必要条件」

| 格 | 缺的必要条件 | 失效机制（个例根候选） |
|---|---|---|
| G3 | 「检查即承诺」：判定与提交必须原子 | 读判(52-54)与写(58)之间让出事件循环(57) → TOCTOU |
| G4 | 「超时预算 ≥ 下游 P99」 | 两个独立常量没人校验谁大；`guard`(200ms) 必在 `work`(300ms) 前结算 |
| G5+G7 | 「登记必有对应注销」 | `on` 有 `off` 的配对，只写了前半；64KB Buffer 被闭包永久持有 |
| G6 | 「扣减与补偿成对」 | 扣减(58)在等下游(67)之前，失败路径不回滚 |
| G1 | 「计量点必须在路径判定之后」 | `total++` 写在 `/health` 分支之前 |

### 层3：再往上问「为什么四格会同时缺同一类东西」

→ **类根：应用在请求处理路径上，每一对「配对操作」都只实现了前一半，且没有任何结构强制后一半存在。**
四对：检查↔提交、登记↔注销、扣减↔补偿、超时预算↔下游 SLA。它们落在时序上相邻的四格，所以一次压测同时爆开，看起来像三件无关的事。

```
类根（配对契约缺失，结构层）
├ 个例根① G3  TOCTOU：service.js:57 的 await 让出，读判与写分离
├ 个例根② G4  超时预算倒挂：DB_CLIENT_TIMEOUT_MS=200(18) < DB_SLOW_QUERY_MS=300(19)
├ 个例根③ G5+G7 监听器只登记不注销：audit.on(62) 无 off，ctx=64KB(61) 被闭包持有
├ 个例根④ G6  失败不补偿：扣减(58) 早于下游(67)，504 路径照样扣库存
└ 个例根⑤ G1  计量口径（次要）：total++ 在路径判定之前(80)
```

**注意个例根③是一个机制的两个症状**——`stats.ok` 放大与 RSS 上涨不是两件事：每请求多一个监听器，emit 时被全部触发（放大），闭包里的 64KB 永不被回收（内存）。这一件若拆给两个人修，必然互相甩锅。

### 直接回答「根源到底是一个还是几个」

分两个层，两个答案都对，且**不能只给一个**：

- **机制层：4 个，不是 3 个。** 三个表面现象背后有四个独立失效机制（上表①②③④）。现象 1（超卖）本身是**两个机制叠加**：① 让 16 个请求同时越过判定（主因），④ 让「失败的单也扣库存」，于是 SKU_B 全 504 时库存照样掉。现象 3 反而**只有一个**机制（③ 的两个面）。
- **结构层：1 个类根。** 四个机制是同一条「配对契约缺失」在四个相邻格子上的独立塌方。

所以「三个人各自认领、分头修自己那摊」错在三处：
1. **现象 1 一个人修不完**——只修 ① 不修 ④，SKU_B 的库存仍会被 504 吃掉（实测：32 次失败、库存 40→8）。
2. **现象 3 拆成两个人会各修一半**——内存与计数同源，只有把 `on` 改成 `once`/补 `finally` 才同时消失（实测：改一个词后 `ok` 恰等于成功数、`listenerCount` 归零）。
3. **观测工具本身在故障域内**——`stats.ok` 就是被放大的那一个。**先修 G3/G4 而不先修 G5/G7，你无法验证修完是否成功，因为验收判据（成功率）自己在说谎。**

## L3 双根

### 处置根（修本次，最小面，全部经实测验证）

| # | 动作 | 落点 | 实测效果 |
|---|---|---|---|
| 1 | `audit.on` → `audit.once`；`Buffer.alloc` 移出闭包或改 `try/finally` 释放 | service.js:61-65 | 32 单成功 → `ok=32`（精确等于成功数）、`auditListeners` 回到 0、`auditTrailLen=32` |
| 2 | `DB_CLIENT_TIMEOUT_MS` 提到 > 300（如 800），或把 `dbReserve` 的慢路径改为异步确权 | service.js:18 | SKU_B 由 32/32 失败 → **32/32 成功** |
| 3 | 扣减后置到下游确认之后；或 catch 里 `stock[sku] += qty` 回滚 | service.js:58/67 | 修掉「504 仍扣库存」（本轮未单独跑消融，见挂起表第 10 行） |
| 4 | 把 `await sleep(3)` 移到扣减之后（单进程单线程下即原子）；真实实现用 per-SKU 版本号 CAS 或串行队列 | service.js:57 | SKU_C 由 **-9 → 0**，16 并发下 7×200 + 25×409 |
| 5 | `stats.total++` 移到 `/health` 分支之后 | service.js:80 | `total` 回归等于业务请求数 |

> 处置根 ≠ 消解根：上面 5 条都只让**这几个具体洞**消失，下一对配对还会塌。

### 消解根（灭这一类）

**把「配对」从纪律变成结构——让只写一半在物理上写不出来。**

三道闸门：

1. **不可发生判据**（若当时采用它，本类问题结构上不可能发生，不只是变少见）：
   - ① 请求级副作用只能经 `withRequestScope()` 登记，作用域退出自动注销——**没有裸 `emitter.on` 可写** ⇒ G5/G7 类不可能发生；
   - ② 所有超时/配额常量必须由单一 SLA 声明派生，并在 `listen` 之前 `assert(timeout > sla.p95)`，断言失败进程起不来 ⇒ G4 类不可能发生；
   - ③ 扣减只允许发生在「下游已确认」之后（单向依赖：库存写是下游确认的下游），不存在「先扣后补」代码路径 ⇒ G3+G6 类不可能发生。
2. **可执行首边**（从现状出发的第一步，可以很小）：把 `handlePay` 的 service.js:61-65 四行包进 `try/finally` 并改成 `once`，同时在 `listen` 前加一行 `assert(DB_CLIENT_TIMEOUT_MS > DB_SLOW_QUERY_MS)`——半天内可完成。
3. **成本量级**（量级，形式定量交 📐 公式图）：本文件内改动 = **人时级**（约 15 行 + 4 条回归用例）；把库存搬到外部原子存储 = **人日级**；把超时治理收进统一 client 封装 = **周级**（见 L4）。

## L4 迁移出口

消解根 ③ 若真做（扣减只能发生在下游确认之后），等于把库存状态搬出进程，本次问题随之降级。后续问题清单：

1. **数据与状态**：库存成为外部状态 → 一致性/事务边界、幂等键、超卖补偿与对账。
2. **运行与自启**：进程内 `EventEmitter` 审计 → 外部日志/队列，落点、投递语义与重试策略全变。
3. **可观测性**：`stats.ok` 口径须重定义（服务端成功 / 下游成功 / 客户端可见成功三者不再相等），`/health` 增加 `listenerCount` 与 RSS 的阈值告警。
4. **凭据与权限模型**：真实 DB 客户端连接池与凭据接入。
5. **组织能力**：code review 增加「配对检查」清单（每个 `on`/`alloc`/`- qty`/timeout 常量都要指出它的另一半在哪）。

→ **本次问题降级为第 1 项的子项**：「扣减必须原子且与下游结果一致」。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 硬件故障 | 挂起（非根） | 无 CRC/ECC；同机可复现；非随机 | 若换等价机器症状变化/消失，本行复活 |
| 网络问题 | 挂起（非根） | 全走回环；504 由进程内 `sleep(300)` 对 `race(200)` 造成，与链路无关 | 若接真实远端库且 p50 明显变化，本行复活 |
| 权限/账号体系 | 挂起（非根） | 无 ACL/令牌类症状 | 接入真实 DB 后出现 auth 错误则复活 |
| 组织流程（三人分头修） | 挂起为**共因，不是根** | 它是放大器不是成因：这 4 处缺陷在任何分工方式下都存在于代码里 | 若同一份代码在单人维护下仍反复出现同组缺陷，本行升格为根 |
| `lifecycle`/`init`/`dependency` 三子层 | 挂起（不适用） | 进程 `listen` 成功、无崩溃、无依赖错误码族 | 出现无堆栈猝死或加载失败则复活 |
| `win-service` 节点 | 挂起（不适用） | 前台 `node` 进程，无 SCM 代持生命周期 | 迁到 Windows 服务形态则复活 |
| **树外分支**：树 v1 的 `software` 类根（「控制权被外部机制代持」） | 挂起 + 登记 `v2 候选` | 本例控制权在应用自己手里，塌的是内部配对契约；树缺「内部契约完整性」这一支 | 若发现某外部机制强制了这些写法（如框架模板）则复活，并据此补 v2 节点 |
| 压测脚本 `load.js` 自身缺陷 | 挂起（非根） | `load.js` 只发请求、不碰库存；其 `byStatus`/`byCode` 与服务端 `e409/e504` 计数一致 | 换压测器结果不同则复活 |
| `qty` 参数无上界/无负数校验（负数可反向加库存） | 挂起（**未爆但同类根下的下一个洞**） | `load.js` 恒发 `qty=1`，`Number('1')` 正常；service.js:97 未校验 | 参数变为外部可控（真实订单 API）即复活为高危根 |
| G6 补偿缺失（单独消融未跑） | 挂起（证据为共因观察，非单变量实验） | 已观测「32 次全 504 仍扣 32 件」，但未做「只修 G6」的消融 | 需一次单变量实验补齐（见 ⚠️ 第 2 条） |
| 409 分支之后的二次竞争（`remain<=0` 判定同样非原子） | 挂起为 G3 子项 | 与 G3 同一机制，不构成独立根 | 无需恢复条件（并入 G3） |
| `/health` 计入 `stats.total` | 判定为**次要根**（已列入处置根第 5 条） | `total=34` vs 32 单 | 若口径被要求 `total == 业务请求数` 则升级为必修 |

## 结论

**一个类根，四个机制，三件现象——而「三个人一人一件」在任何分配方式下都会漏。**

- 现象 1（库存 -9）＝ G3 竞态（主因）× G6 无补偿（它让别的 SKU 也在掉库存）。7 件卖 16 单，超卖 9 件，与 `-9` 精确吻合。
- 现象 2（某 SKU 全 504）＝ G4 的两个常量倒挂：`DB_CLIENT_TIMEOUT_MS=200` 小于 `DB_SLOW_QUERY_MS=300`，`guard` 必先于 `work` 结算。与并发无关，串行 4/4 也全 504。
- 现象 3（内存涨 + 计数放大）＝ G5+G7 **同一个**机制：每请求注册一个永不注销的监听器并持有 64KB Buffer。放大倍数不是固定一个数量级，而是 `Σ(每次 emit 时的监听器数)`——16 并发 16 单时 `ok=256/16=16×`，跑 320 单后 `ok=156536/518≈302×`，**随累计请求数二次增长**。
- 修的顺序：先 G5/G7（把尺子修正），再 G4+G6 同批（同一条失败路径），再 G3，最后类根。反过来做，你会用一个自己在说谎的成功率去验收。

```
             ok=56 = 已有 4 个泄漏监听器×7 次 emit(28) + 1+2+…+7(28) ← 放大公式逐项命中
```
**三处单变量消融**（复制到 `%TEMP%` 打补丁，不动仓库原文件，每次 fresh 进程）：

| 消融 | 改动 | 结果 |
|---|---|---|
| A | 注释掉 service.js:57 `await sleep(3)` | SKU_C 16 并发下 `{"200":7,"409":25}`，`stock=0` — **无超卖** ⇒ 该行是超卖的充分必要条件 |
| B | `DB_CLIENT_TIMEOUT_MS` 200→800 | SKU_B `{"200":32}` 全成功，`stock 40→8` 正常扣减 ⇒ 504 唯一因是常量倒挂 |
| C | `audit.on` → `audit.once` | SKU_A 32 单全成功，`ok=32`（=成功数）、`auditListeners=0`、`auditTrailLen=32` ⇒ 放大与内存同源于「只登记不注销」 |

B 组 `ok=768` 也精确等于 `16×16 + 16×32`（两批各 16 次 emit，emit 时监听器分别为 16/32），逐项对上放大机制。

## ⚠️ 异常/矛盾/空白

1. ⚠️ **「大了一个数量级」是严重低估**。`ok` 不是成功数的固定倍数，而是 `Σ(每次 emit 时的监听器数)`，随累计请求数**二次增长**：16 单时 16×，336 单时约 211×，518 单时 302×。任何用 `ok/total` 做验收的结论都会随时间漂移，必须换口径。
2. ⚠️ **G6（失败不补偿）缺一条单变量消融**。我只能用「全 504 仍扣 32 件」这个共因观察证明它存在，未做「只修 G6、其余不动」的实验。已入挂起表，不冒充已验证。
3. ⚠️ **错误码分布会骗人**。超卖之后库存为负，后续请求全部 409——`e409` 上升看起来像「库存保护/限流生效」，实际是超卖后的残局。只看错误率的人会以为系统在自我限流。
4. ⚠️ **504 没有任何日志行**。`service.js` 全文件无一处 `console.error`，504 只留下一个 `stats.e504` 计数，事后无法从日志取证是哪个 SKU、等了多久。可观测性与 G5/G7 属同一类缺口。
5. ⚠️ **`qty` 无校验**（service.js:97）：`qty=-1` 会**增加**库存，`qty=1e9` 会一次打穿。当前压测恒发 1 所以未暴露，但它是同一类根下的下一个洞。
6. ⚠️ **树 v1 覆盖不到本例的类根**。`software` 节点的类根讲「控制权被外部代持」，本例是「应用内部配对契约缺失」，两者正交。已登记 `v2 候选`（新增子层 `contract`：成对操作的完整性），不静默降级。

## 💡 灵感备注

- 三件现象同时爆开不是巧合，是**同一个压测旋钮同时拧过了三个阈值**：并发数（开 G3）、慢 SKU 混入（开 G4）、累计请求数（开 G5/G7）。这解释了为什么「分头修 + 单发单测」永远看不到超卖——单发请求时 G3 的窗口宽度是 0。
- 判别「一个还是几个」的可操作手法：**做单变量消融**。若某处改动只消掉一个症状 ⇒ 该格独立；若一个改动同时消掉两个症状 ⇒ 那两个症状同源（本例 C 组同时消掉放大与内存）。这比争论「是不是一个 bug」便宜得多。
- 「先修尺子」可以抽象成一条通用顺序：**当故障域覆盖了观测代码时，观测代码优先修**。否则后续所有验证都在用坏掉的尺子量。
- 类根写成「配对契约」的好处：它给出一张可执行的 review 清单（每个 `on`/`alloc`/`- qty`/timeout 常量都必须指出另一半在哪），而「注意并发安全」这种类根给不出任何 checklist。
