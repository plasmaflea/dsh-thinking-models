# 订单服务三症并发：根源是几个？—— 林状分层分类回溯

**一句话结论**：不是三个可以分头认领的摊子，也不是一个根。**机制上是 3 条相互独立的缺陷链（可拆出 5 个缺陷点），结构上是 2 个类根 + 1 个配置常量**；而这 2 个类根又出自同一笔架构欠账——**代码里没有"所有权与生命周期"这一层**（库存谁拥有、在哪个边界内改；请求级对象活多久、谁释放）。三件事里有两件共根（内存涨 + 成功计数虚高是同一个监听器泄漏），而 504 与库存对不上在**后果**上耦合（`D:\DeepSeek-levelup\lab-t6\service.js:67` 的预留失败后无补偿，实测 32 单全 504 却扣掉 32 件库存）。所以"分头修"必然互相打脸，正确切法是**按结构边界切两刀，而不是按现象切三刀**。

## L0 类别判定

**类别：`software` —— 运行时数据一致性与资源所有权缺陷（判据：① 三症状在同一份代码上确定性复现，同一输入同一结果；② 全部由代码/常量决定，换机器不影响；③ 精确可算——成功计数 256／28／54568 分别精确等于 Σ(当时监听器数)，超卖数精确等于并发通过闸门的请求数）｜已排除：硬件（无随机性、无校验错误）、网络（全程 127.0.0.1，504 的服务端文案为 `query timeout after 200ms` 由 `service.js:43` 自造）、权限/账号（单进程无权限调用，未知 SKU 正确返回 400 `E_NO_SKU`）、组织与流程（技术缺陷已具名到行，人的分工不是本次因）。**

补一句：本问题是**运行时**取向，而非知识树 `software.md` 类根所描述的**初始化**取向（"控制权被外部机制代持"）。这不是树错，是树在该节点上只长了"进程起不来"这一支；运行时这一支登记为树外分支 + v2 候选，见挂起表。

## L2 逐层回溯

### 层 1（轴：单次下单请求的必经时序 —— 生成式，一步一格）

轴为何可生成：任何"校验前置＋扣减落账＋下游预留＋结果编码"的写请求，都必须按此顺序经过这些步骤，一步不可跳。每格都写了"该格故障的可观测症状"，全部实测定格，无一空格。

| 格 | 该步为何必然存在 | 本次代码位置 | 该格故障的可观测症状（实测） | 判定 |
|---|---|---|---|---|
| ① 前置校验 | 任何写操作必须先判合法性，否则可能写坏 | `service.js:52-54`：`const remain = stock[sku]` → `if (remain === undefined) 400` → `if (remain <= 0) 409` | `POST /pay?sku=SKU_C&qty=100` 返回 `{"ok":true,"result":{"taken":100,"remain":-93}}`，库存 7→**-93**，**单请求、非并发**即穿透 | 缺陷（校验缺 `qty <= remain`） |
| ② 让出事件循环 | 只要处理链里有任何 `await`，就必然存在一个"状态已读、尚未写"的悬挂窗口 | `service.js:57`：`await sleep(3)`（注释自陈"查库存与扣减之间让出一次事件循环"） | 该格自身无独立症状；它是 ③ 的窗口放大器：并发=16 时 16 个请求全部挤进此窗口 | 放大器（非根，但是判据要点） |

### 层 2（↑ 归并：7 格 → 3 条结构条件）

**类根 A —— 一致性类：一次请求的"读-判-写-预留"横跨了挂起点，却没有任何原子边界包裹它，且 commit 之后可能失败的步骤没有补偿边。**
- 在什么结构条件下这一类必然可能发生：只要"判据取自快照、写入作用于当前值"且两者之间有 `await`，超卖就不是概率事件而是**并发度的确定性函数**（本例并发 16 ⇒ 必然卖 16 件）；只要"落账早于预留"，预留失败就必然留下已落账的库存。
- └ 个例根 A1（现象 1 的主机制）：`service.js:52` 读 `remain` 与 `service.js:58` 写 `stock[sku]` 之间夹 `service.js:57` 的 `await sleep(3)`，闸门判的是 `remain`，写入用的是 `stock[sku]`，于是 7 件库存被 16 个通过闸门的请求各减 1 → **-9**。
- └ 个例根 A2（现象 1 的第二条边）：`service.js:54` 只判 `remain <= 0`，不判 `qty <= remain`，所以 `qty=100` 无需并发即打到 **-93**。这条边独立存在，加锁也修不掉。
- └ 个例根 A3（现象 2 的"白扣"部分）：`service.js:67` 的 `dbReserve` 抛错后，`service.js:101-110` 的 catch 不回滚 `:58` 的扣减 → SKU_B 32 单全 504 却 40→8。

**类根 B —— 所有权/生命周期类：进程级长生命周期容器被当成请求级状态的宿主；注册无注销，计数在被广播的回调里累加。**
- 结构条件：`const audit = new EventEmitter()`（`service.js:15`，"进程级、长期存活"）＋ `stats`（`:21`）＋ `auditTrail`（`:22`）是进程级；而 `ctx`、一次成功的"计数动作"是请求级。一旦请求级对象挂到进程级容器上且不摘除，**内存与计数就都变成请求数的函数**——两类症状共根，不是两个 bug。
- └ 个例根 B1（现象 3 内存）：监听器闭包持有 64KB `ctx`，`on` 无对应 `off`，请求结束对象仍可达 → rss 单调涨（320 单 ≈ +26MB ≈ 81KB/单），且 `auditTrail` 也按同样倍数膨胀（54568 条 vs 应有 320 条）。
- └ 个例根 B2（现象 3 计数）：`stats.ok++` 位于 `emit` 的**整个监听器集合**里，一次 `emit` 会触发当时**全部** N 个监听器，故一次成功被记 N 次。因此 `ok` 不是"多了一个数量级"，而是**随请求数线性放大的系统偏差**：实测 16×、4×、170.5× 三个倍率对应三种监听器增长节奏（批量并发 16 个一起注册 → 16×；串行 1 个 1 个注册 → 三角数；跨 4 轮累积 320 个 → 170×）。
- 关键旁证：`SKU_B` 32 单全失败（`ok` 增量 0），`auditListeners` 仍从 0 涨到 32 —— 泄漏发生在**失败路径**上（`:62` 的注册在 `:67` 的 `await` 之前），所以"把失败的请求干掉"并不能止住泄漏。

**类根 C —— 配置类：等待上限是单一全局常量，与实际按查询分化的成本解耦；且该 race 并不取消下游工作。**
- 结构条件：超时的"时长"与"语义"两件事被压进同一个 `Promise.race`，而 race 只是**放弃等待**，不是**取消执行**。
- └ 个例根 C1（现象 2 的直接机制）：`DB_CLIENT_TIMEOUT_MS=200`（`:18`）< `DB_SLOW_QUERY_MS=300`（`:19`），且 `service.js:36` 让成本按 SKU 分化 → SKU_B 的 504 是**结构性必然**，与负载无关（串行亦 504）。
- └ 个例根 C2（把 C 与 A 焊在一起的边）：`service.js:38-40` 的 `work` 在 200ms 判超时后仍继续跑，300ms 时把 `finished` 置真 —— 即"客户端被告知失败，服务端实际完成"。这条边正是 A3"失败却扣减"的上游放大器：**超时语义误用 × 无补偿边 = 静默丢库存**。

**元层（回答"一个还是几个"）：A 与 B 都在违背同一条更抽象的结构约束——"每个共享可变状态都该有一个明确的所有者与一个明确的存活边界"，代码里没有任何一处表达它。C 是唯一与这条约束无关的独立常量错误。**

## L3 双根

### 处置根（修本次，最小动作集，按序上，缺一步就有残留）

1. **把 ①→③ 圈进同步原子段**：`handlePay` 内 `检查 + 扣减` 改为在同一次同步执行里完成（消除 `:57` 的 `await sleep(3)` 跨段），或对同 SKU 加串行闸（进程内 mutex / 按 sku 的 Promise 队列）。→ 直击 A1。
2. **补 `qty` 校验**：`if (!Number.isInteger(qty) || qty <= 0 || qty > remain) throw mkErr(409, 'E_NO_STOCK')`。→ 直击 A2（加锁修不掉的那条边）。
3. **把落账挪到预留之后，或给预留失败加补偿边**：`dbReserve` 成功后才写 `stock[sku]`；若必须在前后分两步，则 catch 里 `stock[sku] += qty`。→ 直击 A3。
4. **超时改为按成本分化 + 只作熔断不作取消**：`DB_CLIENT_TIMEOUT_MS` 提到 ≥ 2× 最慢查询（如 1000ms），并要求下游支持幂等键；`race` 输掉后必须真的 `abort` 或落补偿。→ 直击 C1、C2。
5. **监听器 `on`→`once`，并在 `finally` 里 `off`；两条路径都清**。→ 直击 B1。
6. **把 `stats.ok++` 从广播回调挪到 `handlePay` 的返回处**（`send(res,200,…)` 前）。→ 直击 B2（注意：口径要重定义——`ok` 必须是"回包 200 的次数"，与监听器数彻底解耦）。

### 消解根（灭这一类）

**条件：给共享可变状态引入"所有者 + 原子边界 + 补偿边"三件套；并规定"任何请求级对象的存活期不得超过该请求，注册必须带归属与释放"。**

- **不可发生判据**（若当时采用，本类问题在结构上不可能发生，而非变罕见）：
  - 有原子边界 ⇒ "判据用快照、写入用当前值"这种写法**无处安放**（判与写之间不存在可插入 `await` 的位置），超卖不是变小概率而是没有发生的位置。
  - commit 严格在可能失败的步骤之后（或失败必补偿）⇒ "失败却扣减"不成立。
  - 计数由返回值单点聚合而非广播累加 ⇒ 计数与"有多少监听器"彻底解耦，加多少监听器都不会污染 `ok`。
  - 注册与请求同生命周期且有归属清理 ⇒ 监听器数与请求数**不可能**单调相关，内存不随请求数单调增长。
  - 超时表达为"成本分档 + 可取消 + 幂等" ⇒ 慢 SKU 不允许存在"必然 504"的结构位置。
- **可执行首边**（很小，从现状出发第一步）：在 `handlePay` 外面套一个按 sku 的串行闸（~10 行），同时把 `service.js:62` 的 `audit.on` 改成 `audit.once`，并把 `stats.ok++` 移出回调。这三处不依赖任何重构，改完可立刻回归复测。
- **成本量级**：单进程内落地 ≈ 15–30 行改动 + 一次 4 轮压测回归（分钟级）；若上多实例，一致性必须落到存储层条件更新，成本跳到"一次数据层改造"（见 L4-4）。

## L4 迁移出口

消解根指向"给状态设所有权与原子边界 + 请求级对象不跨请求存活"的结构改造，会带出以下新问题；**本次问题被降级为其中一项**：

1. **存储与一致性语义**：进程内 map → 带条件更新的持久层（`UPDATE stock SET qty = qty - ? WHERE sku = ? AND qty >= ?`，靠影响行数判定，而非先 SELECT 再写）。需补幂等键（`request_id`）以支撑重试。
2. **超时与取消语义**：客户端等待上限 ≠ 服务端取消。需要"下游可取消 + 失败可补偿 + 重试幂等"三件一起设计，否则只是把 504 换成慢失败。
3. **可观测性口径重定义**：`stats.ok/total` 从广播累加改为返回值聚合后，历史看板与告警阈值全部要重算（`total` 现状还含 `/health` 自身，实测 `total=35` = 32 pay + 3 health，口径本就脏）；并新增 `auditListeners`／堆外内存的告警线。
4. **并发模型随扩容失效**：进程内 mutex 只在单实例成立。**本次问题降级为 L4-4 的一项**——扩容到多实例后，超卖会在存储层复现，届时处置手段是条件更新＋事务，而不是加锁。
5. **组织与值班**：`/health` 的 `ok` 被污染会持续误导排障方向（这次就误导成"成功量很大"）。需要一条"计数与请求数偏离即告警"的元监控。

| 硬件故障（位翻转/内存校验） | ⊥ 不是根 | 三症状确定性复现；`ok` 精确等于 Σ(当时监听器数)（256 / 28 / 54568），超卖数精确等于通过闸门的请求数（16 / -9） | 出现同输入随机结果、或 rss 抖动与 `auditListeners` 解耦 |
| 网络问题 | ⊥ 不是根 | 全程 `127.0.0.1`；504 的 `message` 是服务端 `service.js:43` 自造的 `query timeout after 200ms`，属应用层语义 | 出现 `ECONNRESET`/DNS 失败/连接超时且响应体无该文案 |
| 权限/账号体系 | ⊥ 不是根 | 单进程无 ACL 调用；未知 SKU 正确返回 400 `E_NO_SKU` | 出现 `EACCES`/服务账户特有差异 |
| 事件循环被阻塞导致"看起来超时" | ⊥ 不是根 | SKU_B **并发=1 也 4/4 504**、`p50≈217ms`≈200ms 上限；同期 SKU_A 同并发 200×80 全 200、`p50=62ms`。若是阻塞，SKU_A 应同样退化 | 若串行下也超时且查询实际成本 < 上限 |
| `load.js` 客户端自身的缺陷 | ⊥ 对现象 2 不是根 | `load.js` 与 SKU 无关（只拼 query 串），换 SKU 即正常；客户端 timeout 是 15000ms，远未触发 | 出现 `status:0`／`client timeout` 主导 |
| GC 抖动或堆上限 | ⊥ 非主因 | rss 在 4 轮之间**单调不回**（55→61→69→74），且与 `auditListeners` 严格同步；泄漏源已定位到 `:61` 的 64KB 闭包 | 出现 rss 回落或 OOM 崩溃 |
| 真实数据库连接池耗尽 | ⊥ 挂起（当前不可证） | 代码里没有真实 DB，`dbReserve` 是 `sleep` 模拟，不存在池；本机无法取证 | 接真实 DB 后按同一脚本重测，若 504 数量与池大小相关则恢复此分支 |
| 「三个现象同源，一个修复能全解」 | ⊥ 不是根（假说被实测否掉） | 只修 B（`on`→`once`）后 504 仍全灭（C 独立）、超卖仍发生（A 独立）；只修 C（timeout 调大）后 SKU_B 变全 200，但**并发下 SKU_B 也会超卖**，且"失败扣减"路径仍在（A3） | 若任一单点修复能同时消掉三类症状（现有 6 条实测均为否） |
| `stats.ok` 只是"多算了一点" | ⊥ 不是根，是 B2 的症状 | 16 倍/4 倍/170.5 倍三档比例全部由当时的监听器数决定，是可推算的系统偏差，不是噪声 | 若倍率不随请求数变化 |
| **树外分支**：知识树无"运行时数据一致性／资源所有权"判据 | 登记树外 | `software.md` 六子层面向"进程初始化失败"；`quota` 有"配额更小"但无"注册不注销"判据，`concurrency` 有"依赖未声明"但无"读-判-写跨挂起点"判据 | 树升 v2 后本行可并入 `ownership` 子层 |
| **v2 候选节点**：新增 `ownership`（所有权与生命周期）子层 | 登记候选 | 本次 2 个类根全部落在它上面，现有六层无法表达"这段代码拥有此状态多久" | 该子层建成并核查后，本次回溯可升为 v2 实例化 |

## 结论

1. **不是一个根，也不是三个能分头修的根。** 精确表述：**3 条独立缺陷链（竞态/无补偿、监听器泄漏/计数错位、超时常量失配），收敛为 2 个类根 + 1 个配置常量。**
2. **三件现象里两件共根**：内存 48→74MB 与 `ok` 虚高是**同一个** `service.js:62` 的"每请求 `audit.on` 且不注销、计数在广播回调里累加"——同一段代码既留住了 64KB `ctx`，又让一次成功被记 N 次。把它们派给两个人修，两个人会改同一行。
3. **现象 2 与现象 1 在后果上耦合**：504 的直接根是 `200 < 300` 的常量失配（串行也必死），但它之所以吃掉库存，是因为 `service.js:67` 失败后没有回滚 `service.js:58`。**只修 504 的人会把"白扣"从高频路径变成低频路径，而不是消灭它。**
4. **现象 1 还有一条加锁修不掉的边**：`qty` 未与 `remain` 比较，`qty=100` 单请求把 7 打到 -93。加锁的人会以为修完了。
5. **因此正确的分工是按结构边界切，不是按现象切**：①「状态一致性 + 补偿边」（含超时常量与取消语义，必须同批上）②「资源所有权与计数口径」（监听器生命周期 + 统计聚合点）。两刀互不重叠、可并行、各自可独立回归。
6. **根源往上还有一层**：两个类根都在违背同一条结构约束——共享可变状态缺少"所有者 + 原子边界 + 存活边界"。这才是"灭这一类"的入口，也是"一人一件"这种分工方式必然失败的原因：现象是症状的分布，不是缺陷的分布。

## ⚠️ 异常/矛盾/空白

1. **⚠️ `service.js:18-19` 把两个本该联动的常量写成了互不相干的字面量**：`DB_CLIENT_TIMEOUT_MS=200` 与 `DB_SLOW_QUERY_MS=300`，且 300 只对 `SKU_B` 生效（`:36` 三元表达式）。任何"新增一个 join 较多的 SKU"的动作都会静默复制这次事故。建议：成本与上限同源（如 `timeout = 3 * p99Cost[sku]`），并加启动自检"上限 < 已知最慢成本就拒绝启动"。
2. **⚠️ `dbReserve` 的 `Promise.race` 只放弃等待、不取消工作**（`:38-48`）：超时后 `work` 继续跑到 300ms 并置 `finished=true`。这意味着"服务端实际成功、客户端看到 504"是常态，一旦有重试就会重复扣减。这是比 504 本身更危险的一层，题面未提。
3. **⚠️ `/health` 会污染它自己上报的计数**：`stats.total++` 在路由分发之前（`:80`），所以 `total` 含 `/health` 请求（实测 `total=35` = 32 pay + 3 health）。体检接口改自己的指标，任何用它算成功率的人都会算错。
4. **⚠️ 计数偏差不是"一个数量级"而是随规模放大的系统偏差**：16 单时 16×、320 单时 170×。把它当"多算了一点"会低估严重性——它会让容量评估、成功率 SLI、告警阈值全部失效。建议把"计数与请求数偏离"本身做成一条元告警。
5. **空白：无法判定真实 DB 侧行为**。`dbReserve` 是 `sleep` 模拟，本次给不出"接真实 DB 后 504 是否还全灭/连接池是否耗尽"的结论，已登记挂起（恢复条件：接真实 DB 后按同一脚本重测）。
6. **空白：多实例部署下的超卖未验证**。进程内加锁只在单实例成立，扩容后必然复现——这一点是推断而非实测，已放入 L4-4 并标为"降级项"。

## 💡 灵感备注

- **给"分头修"团队的实测反驳弹药**：把表 ③（32 单 504 却扣 32 件）和表 ⑥（qty=100 → -93）甩出来，就足以说明"库存对不上"这一个现象背后至少有两条**不同**的边，而 504 那条边只能由"库存组"修——所以按现象分工会把同一行代码派给两个人。
- **这个 case 是一件很好的"三类症状 = 两条边"的教学样本**：泄漏（内存）与错算（计数）通常被当成两件事，但这里它们共用 `audit.on(...)` 那一行——**同一行代码既留住了对象，又复制了写入**。判据是"症状比例是否由同一个计数（监听器数）解释"，本例三个倍率 16/4/170.5 全部由此解释，故共根成立。
- 若要做成可复用的排查动作：`/health` 里已经暴露了 `auditListeners`、`auditTrailLen`、`rssMb` 三个字段——**`auditTrailLen / 实际成功数` 的比值就是"共根"的指纹**（应恒为 1；实测 16、4、170.5），这一个比值将来能一秒判掉"内存与计数是不是同一个 bug"。
