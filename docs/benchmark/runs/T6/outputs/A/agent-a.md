## L0 类别判定

**类别**：软件类（单进程内的确定性缺陷）。判据：①失败来自代码/配置姿态而非物理介质——同一份程序在同一台机上逐次复现，`SKU_C conc=16` 每次都得 `-9`；②失败确定性可归因——`SKU_B` 的 504 在 `conc=1` 时同样发生（实测 T4），不含随机成分。
**已排除的大类**：硬件（无数值抖动、每次复现同一整数）、网络（全 `127.0.0.1` loopback，无链路变量）、权限/账号（服务无鉴权）、组织流程（纯技术手段即可复现全部三症状，无需人的决策介入）。

## L2 逐层回溯（轴=单条支付请求的必经时序，一步一格）

轴由「必经时序」生成，不是列举：一条 `/pay` 请求**必须**依次穿过"接入→校验→提交→登记→预留→记账"，跳过任何一格请求都拿不到 200。

| 格 | 必经阶段（代码位） | 该格职责 | 该格故障的可观测症状 | 本次判定 |
|---|---|---|---|---|
| G1 | 接入解析 `service.js:78-97`（`stats.total++`、取 sku/qty） | 计量与取值 | 总数与实际请求数不符（`/health` 也被计入） | 次要偏差，非本次三症状 |
| G2 | 库存校验读 `service.js:52-54`（`const remain = stock[sku]`） | 只读判定 | 单独看永不出错 | **空（本格正确）** |
| G3 | 库存提交写 `service.js:57-58`（`await sleep(3)` → `stock[sku] = stock[sku] - qty`） | 原子扣减 | 成功数 > 库存，库存为负 | **症状 1：超卖 −9** |
| G4 | 审计登记 `service.js:61-65`（`Buffer.alloc(64*1024)` + `audit.on('paid', …)`） | 注册必须成对注销 | `auditListeners` 只增不减、超 `maxListeners`、`MaxListenersExceededWarning`、rss 随请求数线性涨 | **症状 3（内存部分）** |
| G5 | 下游预留 `service.js:35-49,67`（300ms 依赖 vs 200ms guard） | 依赖在预算内返回 | 某 SKU 全量 504，且**失败订单仍然扣了库存** | **症状 2：504** |
| G6 | 结果记账 `service.js:62-68`（`audit.emit('paid')` → 广播到 N 个监听器） | 一次请求记一次 | `stats.ok` 远大于实际成功数，且呈 `Σ_{i=1..N} i` | **症状 3（计数部分）** |

**轴的三判据自检**：
- **正交（有实测背书，不是口头声明）**：`conc=1` 分离实验（实测 T3）——G3 空（7 单卖 7 件，库存精确归 0，**超卖消失**），但 G6 仍非空（`stats.ok=28`，而成功只有 7）。两格互不解释对方的症状，故不是同一根。
- **可生成**：每一步都是请求的必经阶段，说不出"为什么这格必然存在"就无法跳过。
- **可观测**：每格症状在 `/health` 或 stderr 里有专属字段（`stock` / `auditListeners` / `stats.ok` / `e504`）。
- **全空列判据未触发**：G3/G4/G5/G6 均非空，轴有效，不需换轴重切。

**→ 类根**：**请求级副作用对进程级／共享状态没有所有权**。一条请求对共享状态做了四种写（扣库存、注册监听器、跨 await 依赖、累加计数），但**四种写都没有"成对"的对端**：检查不对应原子提交（G3）、预留不对应补偿（G5）、注册不对应注销（G4）、记账不对应单次语义（G6）。于是每一次"写"都可能在并发或生命周期上裂开——**这一大类在这个结构条件下必然可能发生，与具体哪个 SKU、哪个字段无关。**

**└ 个例根（三条，挂在类根下，不是平行清单）**
- **R1＝G3：检查-提交跨 `await` 的丢更新。** `remain` 在 `service.js:52` 读，`stock[sku]` 在 `service.js:58` 重读重写，中间 `await sleep(3)` 让出事件循环。并发请求全部读到同一个 `remain=7>0` 通过校验，随后各自执行 `stock -= 1`（写是串行的），于是 16 个请求扣 16 次 → `7-16 = -9`。**卖出的 16 单一字不差等于并发数 16，这是丢更新的指纹。**
- **R2＝G5：超时预算与依赖延迟硬错配 + 无补偿。** `DB_CLIENT_TIMEOUT_MS=200` 而 `DB_SLOW_QUERY_MS=300`（`service.js:18-19`），`Promise.race` 的 guard 必然先落地并抛 `ETIMEDOUT`。同时扣库存发生在 `dbReserve` **之前**且失败不回滚，于是 SKU_B **0 成功却扣掉全部库存**（实测 40→8 / 40→35）。
- **R3＝G4+G6：每请求注册、永不注销的监听器；计数器做成广播语义。** `audit.on('paid', …)` 在请求里注册，进程级 `audit` 长活，闭包各持有 64KB `Buffer`，从不 `off`/`removeListener` → 内存线性涨且不可被 GC 回收。同一监听器里 `stats.ok++`，而 `audit.emit('paid')` 会触发**当时已注册的全部 N 个监听器**，所以第 N 次成功把 ok 加了约 N 次 → `ok ≈ Σ i = O(N²)`。

## L3 双根

### 处置根（修本次）——三处，彼此不冲突，可以分头做，但必须补齐第 4 项
1. **G3**：把"读-判-写"收进单条无 `await` 间隙的同步临界区（`if (stock[sku] >= qty) stock[sku] -= qty; else throw 409`，并把 `await sleep(3)` 移到扣减之后或删除）；生产形态用条件更新 `UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?` 判 `affectedRows`。
2. **G5**：超时预算按依赖实测 p99 给（实测 SKU_B 218–231ms、join 路径 300ms → 设 ≥800ms 而非 200ms），**并且**把扣库存移到预留成功之后（或失败时 `+qty` 补偿）。只调常量不够——错配消失了，"失败仍扣库存"还在。
3. **G4+G6**：`audit.on` 改为模块级注册一次；或直接删掉事件总线，用 `stats.ok++` 普通计数；删 `Buffer.alloc(64*1024)`。**`setMaxListeners(n)` 不是修复**，它只消掉 warning，泄漏与计数膨胀都还在。
4. **无人认领的第 4 项**：失败订单仍扣库存（SKU_B 40→8，0 成功）。三人分头修会各自认为"这不是我的"——它同时属于 G3 与 G5 的边界，必须显式指派。

### 消解根（灭这一类）
**契约：一条请求的每个副作用必须与其所有权成对——检查↔原子提交 / 预留↔补偿 / 注册↔注销 / 记账↔单次。**

- **① 不可发生判据**：若当时采用该契约，则 (a) 无间隙条件更新 ⇒ 丢更新不可能；(b) 补偿存在 ⇒ 失败请求不可能吃掉库存；(c) 注销配对 ⇒ 进程内 listener 不积累，且计数不再被 N 倍广播。**四类问题在结构上不可能发生，不是"变少见"。**
- **② 可执行首边**：`service.js` 单文件 <30 行改造——把 `stock` 访问换成 `updateIf(sku, qty)`、`audit.on` 移出 `handlePay`、`DB_CLIENT_TIMEOUT_MS` 按 SKU 配置；同时在 CI 加一条回归：`seed stock=7, conc=16`，断言 `stock >= 0 && stats.ok === sold`。这条断言一次抓住 R1 与 R3。
- **③ 成本量级**：见下 📐 公式图——**天级（≈2.5–3 人日）**；若库存扣减必须下推 DB 且现有 schema 无条件更新，则升到 **1 周**。

## L4 迁移出口（消解根指向"副作用所有权契约"，上生产要一并处理）

1. **数据与状态**：原子扣减下推 DB（条件更新／乐观锁版本号）、幂等键防重试重复扣减。
2. **运行与自启**：连接池与超时预算同 SLA 对账（或依赖侧提供真实延迟指标，而非代码里的魔法常量）。
3. **可观测性**：计数改为 request-scoped counter 暴露 `/metrics`；**禁止把事件广播当计数器**；`MaxListenersExceededWarning` 升为 SLO 级告警。
4. **凭据与权限**：本次无变化（服务无鉴权，若要暴露公网需另立）。
5. **组织能力**：值班与故障归口从"按 SKU／按人"改为"按请求路径的副作用阶段（G1–G6）"——否则下一次仍是三个人各认领一件、第 4 项无人认领。

→ **本次问题降级为**：上面第 1 项「数据与状态：原子扣减 + 幂等键」的一个子项。

## 📐 成本量级（公式图，只为 L3 ③ 供数）

**经验公式/出处**：`T ≈ (N_edit × t_edit + N_case × t_case) / P`。出处：COCOMO II 的规模-工作量幂律在"单文件、<100 行改动、团队已熟悉代码库"区间退化为线性，故此处取线性近似；**适用条件**：无跨团队排期、无 DB 迁移、单人可独立验证。
**质点模型**：只保留"改动点数"一个自由度（3 个彼此独立的副作用点：G3 库存提交／G5 超时预算／G4+G6 审计注册），砍掉的自由度见下。
**代入**：`N_edit=3`，`t_edit≈0.5 人日/点`（含自测）⇒ 1.5 人日；`N_case=1` 回归用例（seed stock=7, conc=16，断言 `stock>=0 && ok===sold`）⇒ 1 人日；`P=1`；合计 **≈2.5 人日**。
**迭代/交叉验证**：第二独立估法——按"小缺陷中位修复时间 0.5–2 人日/个 × 3 个"⇒ 2.5–6 人日。两法同量级（**天级**），故报量级不报精度。
**结论**：天级（≈3 人日，误差 1–6 人日）。**假设被推翻的条件**：①若库存扣减须下推 DB 且现 schema 无条件更新／版本号 ⇒ +3–5 人日（迁移+灰度），升到 **1 周**；②若已多实例部署，需分布式锁或幂等表 ⇒ 再 +1 周。
**被切掉的自由度（无关项）**：压测机网络与 `load.js` 客户端计时、Node 版本与 GC 参数、`/health` 自身污染 `stats.total`、25 个 409 的分布细节、`auditTrail.push` 的数组开销（≈2MB，比监听器持有的 33.5MB 低一个量级，不单独立项）。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 三症状＝同一个 bug | **不是**（至少两个独立机制） | `conc=1` 分离实验：超卖消失（7 单=7 件），但 `stats.ok=28≠7` 仍在 | 若存在单点改动同时消除两者，则恢复该判定 |
| 三症状＝三个完全独立的问题 | **不是**（同挂一个类根） | 四条写共享同一结构缺陷：无原子提交／无补偿／无注销／无单次记账 | 若某条的修复逻辑与另两条无共同契约，则恢复 |
| 超卖只发生在 SKU_C | **不是** | SKU_A 从 180 压到 **−12**（192 成功 > 180 库存）；只要 `stock < 并发` 就复现 | 若同一并发下 `stock ≫ 并发` 仍超卖，则恢复（说明另有根） |

| 内存涨是 GC 未及时回收 | **不是**（真泄漏） | 监听器闭包持有 64KB `Buffer` 且永不 `off`，引用链挂在进程级 emitter 上，GC 不可达回收；`rss` 与 `auditListeners` 同步线性增 | 若手动 `global.gc()` 后 rss 回落至 48MB 基线，则恢复 |

| **树外分支**：幂等／重试重复扣减（`data-consistency`，v2 候选） | **挂起** | 树 v1 无此节点；本次未引入重试路径 | 一旦网关重试或客户端重放上线，须建 v2 节点后复核 |

| `win-service` 分支（进程初始化失败） | 本次不适用，折叠 | 进程已起、能返回 504 与 `/health` | 若故障形态变为"无堆栈猝死"则恢复 |

## 结论

**不是一个，也不是三个——是「一个类根 + 三条个例根」。**

1. **团队的三分法在"病因"上是对的，在"归口"上是错的。** 三条个例根确实彼此独立（`conc=1` 实验证明超卖与计数膨胀至少是两个机制），所以分头修不会互相破坏——这正是三个人各认领一件能成立的唯一部分。
2. **但它漏了一整个面**：失败订单仍扣库存（SKU_B 0 成功扣掉 32 件）不属于任何一个人的摊子；而"SKU_C 特有"是假象——SKU_A 被打到 180 以下时同样超卖到 −12。
3. **共同的类根是：请求级副作用对共享状态没有所有权**——扣库存无原子提交、预留无补偿、注册无注销、记账无单次语义。四种"写"都没有对端，因此任何一个格子都会在并发或生命周期上裂开。这才是"压测时三件事同时爆发"的原因：高并发同时把这四条无主写全部放大。
4. **先修哪个**：按 Share×Lever÷Cost，先动 `DB_CLIENT_TIMEOUT_MS`（一个常量，解释 100% 的 504），再收 `check-and-act` 的 `await` 间隙，最后改 `audit.on`（一条改动同时吃内存与计数两个症状）。三处合计约 **3 人日**；要真正消解这一类，得立"副作用所有权"契约并在 CI 里放一条 `stock>=0 && ok===sold` 的断言。
5. **对题面数字的复核**：`7-16=-9` 与"卖 16 单"完全吻合，反证并发数就是 16；`48MB→89MB` 与实测 `48→90MB` 吻合，对应约 500 个泄漏监听器（524×64KB=33.5MB）。这两个数字说明题面观测是真的，不是误读。

## [⚠️ 异常/矛盾/空白]

1. **⚠️ 题面「成功计数大了一个数量级」是低估。** 实测它不是常数倍而是 **O(N²)**：16 次成功时 `ok=256`（16×，恰好 `16²`，所以看着像"一个数量级"），320 次成功时 `ok=58787`（184×），512 次成功时 `ok=145064`（283×）。**建议**：不要按"除以 10 修正"处理，它是二次增长，压得越久错得越离谱——这会让容量规划与 SLO 全线失真。
2. **⚠️ 题面「库存变成 −9 且卖 16 单」反证并发数恰为 16**（`7−16=−9`）。若线上并发调过，这两个数字会同步变，是天然的并发探针。**建议**：把它写成回归断言。
3. **⚠️ 空白：失败订单扣库存无人认领**（SKU_B 40→8，0 成功）。三个人分头修会各自认定"不是我的摊子"。**建议**：显式指派给 G3∪G5 的交界，否则修完 504 后 SKU_B 仍会被静默吃空库存。
4. **⚠️ `stats.total` 把 `/health` 也计入**（32 请求后 `total=35`）。任何"按 total 对账"的核对都会每轮多 3。**建议**：`/health` 不计入业务总数，或拆到独立的 metrics 命名空间。
5. **⚠️ 空白：`load.js` 的 `latencyMs` 含客户端排队**，T2 的 p50=219ms 已经是服务端 200ms guard 的地板值，不要再拿它去推断 DB 真实延迟。真实延迟只能从服务端拿（当前服务端**根本没有打点**，`DB_SLOW_QUERY_MS` 是硬编码常量而非测量值）。**建议**：先把依赖延迟变成指标，再谈超时预算。
6. **⚠️ 树外分支**：`data-consistency`（幂等/重复扣减/顺序）在知识树 v1 里无节点，本次被迫挂起。**建议**：登记 `v2 候选` 并补齐"幂等键、至少一次投递、失败补偿"三个子判据，否则同类问题下一轮还会落不到格子里。

## [💡 灵感备注]

- `MaxListenersExceededWarning` 是全场**唯一不需要压测就能看到的信号**：只要 11 个请求它就报警。把它当 SLO 级告警，这三件事里最贵的那个（内存泄漏）在预发就能被抓到。
- `/health` 已经把 `auditListeners`／`maxListeners`／`auditTrailLen`／`rssMb` 四个量全暴露出来了——作者显然是"想让你看这里"。反过来说，这四个量在任何 code review 里都该被当成"你在担心什么"的自白书：一个健康检查接口主动吐出监听器数量，通常意味着它已经在泄漏了。
- 三个症状里最危险的不是超卖，而是 `stats.ok` 变 O(N²)：超卖会被业务方当天抓出来，**而一个持续偏大的成功计数会让所有容量规划和 SLO 都不要基于它做决策**——它错的方向是"看起来更健康"。
