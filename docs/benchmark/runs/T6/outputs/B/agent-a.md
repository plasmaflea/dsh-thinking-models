# 订单服务三连故障定位：是三个根源，不是一个

## 结论先行

**三个根源，不是三个人的三摊事——三个人分头修是错的排队顺序。**

题面的三个现象对应 `lab-t6/service.js` 里三个**互不相关**的缺陷，但它们不是"一个根源的三个表现"：

| 现象 | 根因 | 所在位置 | 依赖并发？ | 依赖 SKU？ |
|---|---|---|---|---|
| 库存 -9、卖出 16 单 | 检查与扣减之间有 `await` 让出事件循环，读-判-写非原子（lost update / TOCTOU） | `service.js:52-58` | **是**（并发 1 时完全正常） | 否 |
| 某 SKU 全量 504 | 客户端超时 200ms < 该 SKU 实际查询 300ms，硬编码的单一超时打不过数据相关的查询代价 | `service.js:18-19, 36-48` | **否**（并发 1 也 100% 失败） | **是**（只有 SKU_B） |
| 内存 48→89MB + ok 计数虚高 | 每请求注册一个永不注销的 `audit.on('paid')` 闭包，并闭包命中持有 64KB Buffer | `service.js:61-65` | 是（量级问题，不是存在性问题） | 否 |

关键点：**现象 3 是两个信号、一个根因**（内存涨和 ok 虚高是同一行代码的两张脸），而现象 1、2 各自独立。所以真实的清点是：**3 个现象 ↔ 3 个根因 ↔ 4 个信号**，谁也不是谁的结果。

三个缺陷共享的只是同一个"设计味道"：**这条链上没有任何一步有"归属与生命周期边界"**——扣库存没有事务边界（失败不回滚）、DB 调用没有按操作定预算、监听器没有释放点。这是同一种思维缺失，但不是同一个 bug，修掉任一个对另外两个**零改善**（下面用实验证明）。

## 一、复现：先把三个现象钉死

环境：端口 19105，`$env:PORT='19105'; node service.js`。

### 1. 库存：并发 16 / 32 请求 SKU_C（库存 7）

```
byStatus={"200":16,"409":16}
byCode={"OK":16,"E_NO_STOCK":16}
health after: {"stock":{"SKU_A":500,"SKU_B":40,"SKU_C":-9},"stats":{"total":35,"ok":256,...},
               "auditListeners":16,"maxListeners":10,"auditTrailLen":256,"rssMb":51}
```

7 − 16 = −9，与题面完全一致：**第一批 16 个请求全都读到了 `remain=7`**，`service.js:54` 的 `if (remain <= 0)` 一次都没拦住；第二批 16 个请求读到 −9 才拿到 409。

### 2. 对照组：同样的 SKU_C，并发 1 / 16 请求（新进程）

```
byStatus={"200":7,"409":9}
health after: {"stock":{...,"SKU_C":0},"stats":{"ok":28,...},"auditListeners":7}
```

**串行时严丝合缝卖出 7 单、剩 0、9 个 409**。这一组对照把根因从"业务逻辑写错"排除掉，锁定在并发交叠上——`service.js:57` 的 `await sleep(3)` 就是那个让出点。

### 3. 504：SKU_B

```
并发 16 / 32 请求: byStatus={"504":32} byCode={"E_DB_TIMEOUT":32}
  latencyMs p50=215 p90=217   message: "query timeout after 200ms"
并发 1  / 3 请求 : byStatus={"504":3}    ← 单线程也全灭
stock SKU_B: 40 -> 8 (32 个失败请求扣掉 32 件)
```

并发 1 也 100% 失败 ⇒ **与压力无关，是确定性配置错误**；p50=215ms ≈ 200ms 超时 + 开销，说明每个请求都是"卡在超时上"而不是"被压垮"。同一进程里 SKU_A 320 请求 200:320 全成功（p50=62ms），正是题面说的"换成别的 SKU 就正常"。

### 4. 内存与计数：SKU_A 并发 16 / 320 请求

```
byStatus={"200":320}
health after: {"stats":{"ok":57162,...},"auditListeners":327,"maxListeners":10,
               "auditTrailLen":57162,"rssMb":75}
stderr: (node:20068) MaxListenersExceededWarning: Possible EventEmitter memory leak
        detected. 11 paid listeners added to [EventEmitter]. MaxListeners is 10.
```

**真实成功 320 次，`stats.ok` 报 57162 —— 虚高 178 倍**（"大一个数量级"的量级还会随压测规模放大）。RSS 49→75MB，约 320×64KB=20MB 的净留存，与题面 48→89MB 同形。

## 二、机制的精确拆解

### 根因 A：库存扣减是"读-判-写"，中间隔着 `await`（`service.js:51-58`）

```js
const remain = stock[sku];              // L52 读
if (remain === undefined) ...           // L53
if (remain <= 0) throw mkErr(409, ...)  // L54 判
await sleep(3);                         // L57 ← 让出事件循环，16 个协程在这里排队
stock[sku] = stock[sku] - qty;          // L58 写（基于已被别人改过的值）
```

Node 单线程不等于"不会并发"，`await` 就是显式的抢先点。16 个请求在 L57 全部挂起时，**每个都揣着过期的 `remain=7` 快照**，恢复后 16 次无条件扣减。这不是"扣错了数"，是**没有判据的扣减**：L58 用的是新值 `stock[sku]`，而准入用的是旧值 `remain`，两者之间没有任何保护。

顺带一个更隐蔽的次生问题：L58 的扣减发生在 L67 的 `dbReserve` **之前**，且失败路径没有补偿。所以 SKU_B 那 32 个 504 请求**每单都真实扣了库存却没成交**（40→8）。如果线上对这些 504 做重试，就是双重扣减——这是比"超卖"更贵的那种账。

### 根因 B：单一固定超时 vs 数据相关的查询代价（`service.js:18-19, 35-48`）

```js
const DB_CLIENT_TIMEOUT_MS = 200; // L18 全局唯一超时
const DB_SLOW_QUERY_MS = 300;     // L19
const cost = sku === 'SKU_B' ? DB_SLOW_QUERY_MS : 40;  // L36
const guard = sleep(DB_CLIENT_TIMEOUT_MS).then(() => { if (!finished) throw ETIMEDOUT });
await Promise.race([work, guard]);                     // L48
```

SKU_B 需要一次 join（300ms），客户端只肯等 200ms ⇒ **按构造必然超时**，100% 失败率。而且超时被映射成 `504`（`service.js:102-104`），语义上是指网关超时，实际是**服务端自己的客户端预算配错了**——`/health` 里已经把 `dbClientTimeoutMs: 200` 摆在明面上，这就是自证。

注意 `Promise.race` 只抛弃了等待，**没有取消工作**：work 在 300ms 仍会跑完。所以"超时报失败"的服务端其实已经把活干了（本文件里扣减在更早的 L58）。这就是超时类故障里最经典的账不平来源。

### 根因 C：每请求注册监听器 + 闭包持有大对象（`service.js:60-65`）

```js
const ctx = Buffer.alloc(64 * 1024, 7);   // L61 每请求 64KB
audit.on('paid', () => {                  // L62 注册，永不 off，也不是 once
  stats.ok++;                             // L63
  auditTrail.push(ctx.length);            // L64 闭包命中 → ctx 被永久引用
});
```

两个后果是**同一个根因的两次展开**：

1. **监听器线性增长** ⇒ 每次 `audit.emit('paid')`（L68）会**扇出到历史上所有请求注册的监听器**。因此 `stats.ok` 不是"成功次数"，而是"累计成功事件 × 当时存量监听器"，全程是**超线性/二次**的。串行 7 次成功时 ok=28，正是 1+2+…+7=28，这是判定"扇出"而非"多计一次"的铁证；并发 16 时全部注册完毕后互相扇出，ok=16×16=256。
2. **64KB Buffer 被闭包永久引用 + `auditTrail` 无界增长** ⇒ RSS 线性上涨且**永不回落**。`auditTrail.push(ctx.length)` 本身还是个逻辑错误：审计轨迹里存的是"缓冲区长度 65536"，不是任何可审计内容，等于**审计日志被写成了垃圾且无界**。

`MaxListenersExceededWarning` 是最省事的定位入口——它在第 11 个请求就把答案打印到 stderr 了。

### 另外两个"读数不可信"的细节

- `/health` 自己也会 `stats.total++`（L80），所以 `total` 永远比真实业务请求多（32 次业务 + 3 次 health = 35）。
- 失败请求同样会泄漏监听器但不会 `ok++`（L68 在 L67 之后，抛错就跳过 emit）。于是 ok 的失真倍数取决于**流量构成**：混入失败流量后，同样的成功数会得到不同的 ok 值。这让 ok 连"可换算的常数倍数"都不是，**不能用于任何容量/成功率判断**。

## 三、独立性验证：分别只修一处，另外两处毫无改善

把 `service.js` 复制三份，各只打一个补丁（补丁写在 `%TEMP%`，未改动 `lab-t6` 原文件）：

- **F1** 只修泄漏：删掉 L61-65，改为模块级单个 `audit.on('paid', ...)`
- **F2** 只修竞态：把 L52-58 改成"检查与扣减之间不再 `await`"，原子完成
- **F3** 只修超时：`DB_CLIENT_TIMEOUT_MS = 500`

每个变体各跑 `SKU_C 16×32` + `SKU_B 8×8`：

| 变体 | SKU_C 结果 | ok 计数（真实成功数） | SKU_B 结果 | 泄漏 |
|---|---|---|---|---|
| 原始 | 200:16 / 409:16，**stock −9** | **256**（16，虚高 16×） | **504:8** | listeners 16，RSS 涨 |
| **F1 只修泄漏** | 200:16 / 409:16，**stock −9** | **16**（16，✅ 正确） | **504:8**，stock 40→32 白扣 | listeners 1，✅ 不涨 |
| **F2 只修竞态** | 200:7 / 409:25，**stock 0** ✅ | **49**（7，虚高 7×） | **504:8** | listeners 7→15 ❌ |
| **F3 只修超时** | 200:16 / 409:16，**stock −9** | **256**（16，虚高 16×） | **200:8** ✅ | listeners 16→24 ❌ |

读法（这就是回答"一个还是几个"的实验证据）：

- F1 把 ok 从 256 校正到 16、RSS 止涨，但**库存照旧 −9、SKU_B 照旧 100% 504**。
- F2 把库存修到 0、只卖 7 单，但 **ok 照旧虚高（49 vs 7）、SKU_B 照旧 504、监听器照旧涨到 15**。
- F3 让 SKU_B 全成功，但**库存照旧 −9、ok 照旧 256**；而且此时 SKU_B 扣掉的 8 件才是"真成交"——反过来证明原始状态下那 32 件是纯白扣。

**三个补丁两两正交，没有任何一个附带修好另一个。** 这就是"三个根源"的判决性证据。

## 四、为什么"三个人分头修"会翻车

1. **分工的切法错了，会修出互相掩盖的假象。** 修超时的人（F3）一动，SKU_B 的成功请求开始 emit，ok 立刻从 256 跳到 448——内存/计数那条线会以为"是我修坏的"，两边互相甩锅。反过来修泄漏的人（F1）把 ok 修对了，压测报告里成功率突然变正常，容易被误判为"库存问题也一起好了"（实际 F1 的 stock 仍是 −9）。
2. **他们共用的那台仪表本身是坏的。** 三个人都靠 `/health` 判定进展，而 `/health` 的 `stats.ok`、`auditTrailLen`、`rssMb` 里前两个已经被根因 C 污染。**必须先修 C（或至少改用真实计数）再谈验收**，否则后面所有"修好了"都是自证。
3. **根因 B 是"静默扣款"，不属于任何一摊。** 504 那条线只管把超时调大就能"修好"，但那 32 件白扣的库存不会自己回来；库存那条线看到 −9 只会去补锁，不会想到其中一部分是失败订单造成的。这正是需要**一个人看全局账**的理由：`成交数 × qty + 剩余 = 初始`这一条恒等式，是唯一能同时抓住 A 和 B 的判据（原始状态：16+(-9)=7 恰好成立，所以只看这条等式甚至会误判"账是平的"，必须同时满足"失败单不扣库存"才闭合）。

**建议的排查/修复顺序（一次性做完，别分三摊）：**

1. 先修 C 的**可观测性部分**（哪怕临时）：`audit` 改为模块级单监听，`stats.ok` 直接在 `send(res,200)` 处自增，`auditTrail` 加环形上限。否则后面无法验收。
2. 再修 A：把 `remain` 的读-判-写做成同步原子段（去掉 L57 的 `await`，或改成 `if (stock[sku] < qty) throw 409; stock[sku] -= qty;`，Node 单线程下无 await 即原子）；跨进程则要行锁/`UPDATE ... WHERE stock >= qty` 的条件更新/预占+确认两阶段。
3. 再修 B：超时按操作定预算（`timeout > 该查询 p99`），不要一个常量打天下；`ETIMEDOUT` 语义改成 503/504 + 幂等键，超时后必须走**确认/回滚**而不是假设失败；扣减要放到 DB 事务里，不要用本地内存先扣。
4. 最后清理生命周期：`audit.once(...)` 或显式移除，绝不把请求级大对象捕获进进程级监听器；每请求 64KB 的 `Buffer` 在本例中根本没被使用，属于纯浪费。

## 五、附：这次定位的顺手手法（下次可复用）

1. **先做并发对照**：同一接口 `conc=1` 与 `conc=16` 各跑一遍。串行对、并发错 ⇒ 一定是交叠/原子性问题；串行也错 ⇒ 配置或逻辑错。这一刀就把 A 和 B 分开了（本节 §1 vs §2、§3）。
2. **看 stderr 的 `MaxListenersExceededWarning`**：EventEmitter 泄漏永远是自报家门的，别去猜内存快照。
3. **让计数器自证**：观察 ok 在"串行 n 次成功"后是否等于 n(n+1)/2。二次增长 ⇒ 扇出型泄漏，不是重复计数。
4. **算恒等式**：`初始库存 − Σ成功 = 剩余` 且在**失败单不应扣减**的前提下才算闭合。原始状态这条式子恰好平（16−7=−9），只看它会被骗，必须叠加"失败单是否扣库存"这一维。
5. **拿 `/health` 的 `dbClientTimeoutMs` 与压测延迟 p50 对照**：p50≈超时值（215 vs 200）就是超时配置问题的指纹；p50≈后端真实耗时则是容量问题。

## 一句话回答

**三个根源**：库存的读-判-写非原子（A）、单一超时预算小于某 SKU 的真实查询代价（B）、请求级 EventEmitter 监听器与 64KB Buffer 永不释放（C，它同时造成了内存涨和 ok 计数虚高）。三个补丁两两正交，实验已逐个验证；三个人可以并行**改代码**，但必须由一个人先修好仪表、再按 C→A→B 的顺序验收，否则会互相制造假象。
