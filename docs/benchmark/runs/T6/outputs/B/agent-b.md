# 订单服务压测三症状定位报告

## 0. 结论（先给判断）

**根因是三个独立缺陷，不是一个。** 但它们**只有一个共同的病因模式**，而且其中**两处存在实测的交叉污染**——所以"三个人分头认领一件、各自去修自己那摊"这个分工方式是错的。

| # | 症状 | 根因 | 代码位置 | 一句话机制 |
|---|------|------|----------|-----------|
| 1 | SKU_C 7 件卖 16 单，库存 -9 | 检查与扣减之间让出事件循环（TOCTOU），且扣减先于确认、失败无补偿 | `lab-t6/service.js:52-58` | 16 个请求都在 `await sleep(3)` 之前读到 `remain=7`，之后各自无条件 `-1` → `7-16 = -9` |
| 2 | SKU_B 全 504，换 SKU 正常 | 客户端超时预算(200ms)小于该 SKU 的实际查询耗时(300ms) | `lab-t6/service.js:18-19` + `:35-48` | `Promise.race` 的 guard 在 200ms 就抛 `ETIMEDOUT`，而 `SKU_B` 的查询要 300ms → 必然超时，与负载无关 |
| 3 | 内存 48→89MB，成功计数大一个数量级 | 每个请求都 `audit.on('paid', ...)` 注册一个监听器且永不注销；`emit` 时触发**全部历史监听器** | `lab-t6/service.js:61-68` | 监听器闭包持有 64KB 的 `ctx` → 真泄漏；每次成功 `emit` 把 N 个历史监听器全跑一遍 → `stats.ok` 被放大 O(N²) |

三处缺陷**互不解释**：我用三个最小场景把它们分别单独复现了（下节表格 B2 / A1 / D1），修好任何一处，另两处症状原样存在。所以是三个都要改。

但它们确实共享同一个病因模式：**进程级共享状态（`stock`、`audit`）被并发请求无所有权地读写**，缺三样东西——
- 缺**原子性**（库存的检查→扣减）；
- 缺**失败补偿**（扣减在确认之前，504 路径不回滚）；
- 缺**生命周期**（监听器注册了不注销）。

还有一个必须点出来的组织性错误：**症状 2 是症状 1 和症状 3 的污染源**（见第 4 节实测），所以 1 和 2 不能分给两个人各修。

## 1. 我是怎么定位的（方法先于结论）

三个症状同时出现，最大的陷阱是**假设"同时出现 = 同一根因"或"三个问题 = 三件独立的事"**。我的做法是：**先做单症状隔离复现，再做交叉实验**——判断依据不是"哪个症状先出现"，而是"**哪个症状能在其他两个都不成立的最小场景里单独复现**"。

另外，这份代码的 `/health`（`lab-t6/service.js:82-93`）已经把自证材料全吐出来了，不需要外部监控：
- `auditListeners` / `maxListeners`（`:86-87`）：监听器累积的直接读数；
- `auditTrailLen`（`:88`）：和 `ok` 同源，可以互相验证；
- `rssMb`（`:89`）：内存；
- `dbClientTimeoutMs`（`:91`）：超时预算，和 `SKU_B` 的实际耗时对照就能立刻看出矛盾。

实验矩阵（全部在端口 19106 上跑，每个场景都是全新进程，跑完即 kill）：

| 实验 | 场景 | 关键结果 | 证明了什么 |
|------|------|----------|-----------|
| A1 | SKU_B，**并发 1，总共 1 个请求** | `504 E_DB_TIMEOUT`，220ms，`SKU_B 40→39`，`listeners=1` | 504 与并发/负载**无关**，单请求必现；且失败请求**已经扣了库存** |
| A2 | 紧接 A1 再发 1 个 SKU_A 成功 | `ok 0→2`，`listeners 1→2` | 1 次成功让 `ok` 涨 2 —— 历史监听器被连带触发 |
| B1 | SKU_C，**并发 1**，16 个请求 | `7×200, 9×409`，`stock=0` | 业务逻辑本身是对的，串行时完全正确 |
| B2 | SKU_C，**并发 16**，16 个请求 | `16×200`，`stock=-9`，`ok=256` | 超卖**纯由并发竞争**造成，精确复现题面的 -9 |
| C1 | SKU_A，并发 16，320 请求 | `ok=54861`，`listeners=320`，`rss 48→74MB`，等待后**不回落** | 计数放大 ~171×；内存随监听器线性增长且不回收 |
| C2 | SKU_A，并发 16，640 请求 | `505×200, 135×409`，`SKU_A 500→-5`，`ok=133293`，`rss 48→87MB` | 内存量级对上题面的 48→89MB；**SKU_A 自己也会被超卖** |
| D1 | SKU_B，并发 4，**20 个请求（全部 504）** | `SKU_B 40→20`，`ok=0`，`listeners=20`，`rss 48→51MB` | 20 单全部失败，却**静默吃掉 20 件库存** |
| D2 | 紧接 D1 发 1 个 SKU_A 成功 | `ok 0→21` | 1 次成功让计数涨 21（20 个僵尸监听器 + 自己） |

| E | 同一进程内连跑 4 批(各 100，并发 16) | p50 恒为 62ms、p99 62-74ms、**零 504**；`ok 5905→21960→48016→84095` | 监听器从 100 涨到 400，**延迟完全不退化** → 泄漏不是 504 的成因 |
| F | SKU_B 重试 45 次（并发 8） | `40×504, 5×409`，`SKU_B 40→0`，`ok=0` | 持续重试会把"504 的 SKU"变成"售罄的 SKU"，库存永久蒸发 |
| R1/R2/R3 | 机制微复现（见第 3 节） | R1 独立复现 `-9`；R3 证明 `on` vs `once` | 三处缺陷各自的最小充分条件 |

## 2. 逐一分析

### 症状 1：超卖，根源是 TOCTOU + 先扣后确认

```js
// lab-t6/service.js:51-58
async function handlePay(sku, qty) {
  const remain = stock[sku];                    // :52  读快照
  if (remain === undefined) throw mkErr(400, 'E_NO_SKU');
  if (remain <= 0) throw mkErr(409, 'E_NO_STOCK');  // :54  判在快照上
  await sleep(3);                               // :57  ← 让出事件循环，临界区被撕开
  stock[sku] = stock[sku] - qty;                // :58  无条件扣，不看最新值
```

`remain` 是**请求进入时的快照**，第 57 行的 `await` 把"检查"和"扣减"劈成两个事件循环 tick。16 个并发请求全部在第 57 行之前读到 `remain=7`，全部通过第 54 行，然后 16 次 `-1` 依次落地：`7 - 16 = -9`。

注意第 58 行用的是 `stock[sku]` 的最新值，但**扣减本身没有任何条件**（不是"如果还够就扣"），所以即使扣到负数也不会有人拦。

**为什么这不是"业务逻辑写错"**：B1 并发 1 时 `7×200 / 9×409 / stock=0`，完全正确。B2 只把并发改成 16，同样的代码就 -9。**这是并发缺陷，不是逻辑缺陷**——所以任何"改判断条件 / 加 if"的修法都无效，必须动临界区。

**为什么与另两个症状无关**：代码顺序上 `:52-58` 在 `:61`（监听器注册）和 `:67`（数据库调用）之前，超卖在它们之前就已经发生。B2 里 `e504=0`，照样 -9。

### 症状 2：SKU_B 全 504，是超时预算配置错误，不是数据库慢

```js
const DB_CLIENT_TIMEOUT_MS = 200; // :18 客户端等待上限
const DB_SLOW_QUERY_MS     = 300; // :19 SKU_B 需要一次 join，实际耗时更长

async function dbReserve(sku, qty) {
  const cost = sku === 'SKU_B' ? DB_SLOW_QUERY_MS : 40;  // :36
  let finished = false;
  const work  = sleep(cost).then(() => { finished = true; });          // :38  300ms
  const guard = sleep(DB_CLIENT_TIMEOUT_MS).then(() => {               // :41  200ms
    if (!finished) { const e = new Error('query timeout after ' + DB_CLIENT_TIMEOUT_MS + 'ms'); e.code = 'ETIMEDOUT'; throw e; }
  });
  await Promise.race([work, guard]);                                   // :48  谁先到谁赢
}
```

`SKU_B` 需要 300ms，客户端只等 200ms → `guard` 永远先赢 → 100% 超时。**200 < 300 是常量之间的硬矛盾，与并发数、机器负载、数据库健康度全都无关**。所以"换成别的 SKU 就正常"——其它 SKU 是 40ms，离 200ms 有 5 倍余量。

压测里的取证特征很干净：**p50 = p90 = p99 = max = 220ms，零方差**（A1、D1、F 三次都是 217-220ms）。延迟被死死钉在"客户端超时值 + 一点开销"上，这几乎总是**超时预算与真实耗时错配**，而不是资源竞争或下游故障——竞争会给出抖动的分布。

**这里还有一个更危险的问题，比 504 本身严重**：

```js
stock[sku] = stock[sku] - qty;   // :58  先扣了
...
await dbReserve(sku, qty);       // :67  后确认，抛异常
audit.emit('paid', sku);         // :68  永远到不了
```

`:58` 的扣减在 `:67` 之前，`catch`（`:101-105`）里**没有任何回滚**。所以每个 504 都永久吃掉一件库存。D1 实测：20 个请求全部 504，**零成功，`SKU_B` 从 40 掉到 20**——20 件货凭空蒸发，账上没有一笔成功订单。F 更狠：重试 45 次后 `SKU_B` 从 40 掉到 0，然后开始返回 409。**"某个 SKU 全 504"在重试压力下会自动演变成"某个 SKU 卖光了"**，运维看到的现象会从"超时"变成"缺货"，进一步误导排查方向。

还有一处：`Promise.race` 超时**不会取消 `work`**。`:38` 的查询在 200ms 后仍会跑完（`finished` 标志只阻止 guard 抛错，不中断任何东西）。换成真实数据库，这就是"客户端已经报失败、服务端写入随后落地"——超时后结果未知，**简单重试会造成重复扣减**。这个坑必须靠幂等键解决，不能靠调大超时。

### 症状 3：内存泄漏 + 计数放大，同一个根因的两个出口

```js
// lab-t6/service.js:60-68
const ctx = Buffer.alloc(64 * 1024, 7);   // :61  每个请求 64KB
audit.on('paid', () => {                  // :62  ← 每请求注册一个，永不 off
  stats.ok++;                             // :63
  auditTrail.push(ctx.length);            // :64  闭包持有 ctx
});
await dbReserve(sku, qty);
audit.emit('paid', sku);                  // :68  ← 触发全部历史监听器
```

`audit` 是**进程级、长期存活**的事件总线（`:14-15` 注释就写了），却被当成 per-request 订阅来用。后果是两个：

**(a) 内存泄漏。** 每个请求新增一个监听器，闭包捕获 64KB 的 `ctx`（`:61`），监听器永不注销 → 这些 Buffer 永远不可回收。实测线性关系：

- C1：320 个监听器，`rss 48→74MB`（+26MB），320×64KB = 20.5MB；
- C2：505 个监听器，`rss 48→87MB`（+39MB），505×64KB = 32.3MB；
- D1：20 个监听器，`rss 48→51MB`（+3MB）。

差额是分配器开销和碎片，**斜率稳定在 ~64-80KB/监听器**，与"一个 ctx 一条命"完全吻合。而且**压测结束后等待 4 秒 RSS 不回落**（C1、C2 都验证了 `t+2s`/`t+4s` 恒定），说明是**被引用的活对象**，不是待回收的垃圾——真泄漏。题面的 48→89MB 对应大约 500-600 个成功请求，量级对得上。

顺带还有第二个小泄漏：`auditTrail`（`:22`）只 push 不设上限。

**(b) 计数放大。** `stats.ok++` 写在监听器**内部**（`:63`），而 `emit`（`:68`）会触发**当时全部**已注册监听器。第 N 次成功时，N 个监听器全部执行 → `ok` 的增量为 N，累计 `ok = 1+2+…+N`（串行时，B1：7 次成功 → `ok=28`），并发时更接近 `N×N`（B2：16 次成功 → `ok=256`；C1：320 次 → `ok=54861`；C2：505 次 → `ok=133293`）。

所以题面说"大了一个数量级"其实是**保守**的：`ok/实际` 这个倍率本身就是累积请求数的函数（E 实验里 100/200/300/400 个监听器时，增量分别是 5905/16055/26056/36079），跑到 505 个时已经放大 **264 倍**。

**验证三者同源**：`auditTrailLen` 和 `ok` 的读数**永远相等**（C1 都是 54861，C2 都是 133293，D2 都是 21）。因为 `:63` 和 `:64` 在同一个监听器里同步执行。这条自洽性说明 `auditTrail` 也一起被污染了——**审计轨迹同样不能用来对账**，它和 `ok` 错得一模一样。

**为什么不是"打点写错位置"**：如果只把 `stats.ok++` 挪出监听器（改成 `handlePay` 成功后加一），计数会变对，但**泄漏一点没修**。反之 `on` → `once` 一处就能同时修好两者。这是症状 3 内部最重要的分辨：**它有两个出口，但只有一个入口（`:62`）**。

## 3. 三个机制的最小复现（把它们彻底分开）

为了排除"三个症状互相引起"的可能，我把三处机制各自剥出来单独跑，都只保留最小充分条件：

```js
// R1：检查与扣减之间 await 一次，就足以复现超卖
const stock = { C: 7 };
async function pay() {
  if (stock.C <= 0) return "409";
  await new Promise(r => setTimeout(r, 3));   // 对应 service.js:57
  stock.C -= 1;                               // 对应 service.js:58
  return "200";
}
// 并发 16 → 200数量=16, stock.C=-9        ← 与题面的 -9 完全一致

// R2：超时预算 200ms vs 查询 300ms
// SKU_A cost=40ms  -> 200 OK
// SKU_B cost=300ms -> 504 query timeout after 200ms

// R3：on vs once（5 次真实成功）
// on   : ok=15, 残留 listener=5     ← 三角数 1+2+3+4+5，且泄漏
// once : ok=5,  残留 listener=0     ← 正确，且不泄漏
```

R1 用 15 行代码独立复现出 `-9`，全程没有数据库、没有监听器、没有 `emit`——超卖与另外两个症状无关，这一点是硬证据。

## 4. 交叉污染：为什么"分头修"会出问题

这一段是我认为这道题最关键的部分。三个症状虽然各自独立，但**症状 2 的代码路径位于另两个症状的污染源位置**：

**污染 1：2 → 1（504 也在吃库存）**
D1 实测：20 个 SKU_B 请求全部 504，`ok=0`，但 `SKU_B` 从 40 掉到 20。原因是 `:58` 扣减在前、`:67` 确认在后、`catch` 无回滚。
→ 于是：**只修症状 1 的人如果只盯着 SKU_C 的并发加锁，SKU_B 的静默丢库存会原样留着**。而且他修完 SKU_C 复测通过，会认为"库存问题已解决"。这是最典型的"分头修导致漏修"。

**污染 2：2 → 3（504 也在埋雷）**
D1 里 20 个失败请求留下了 20 个永远不 `emit` 的监听器（`listeners=20`，`ok=0`）。随后 D2 只发 **1 个成功请求**，`ok` 从 0 跳到 **21**——20 个僵尸监听器借别人的 `emit` 全部复活。
→ 于是：**只修症状 3 的人如果按"每次成功应该 +1"去验证，会发现怎么修都对不上**，因为他不知道历史失败请求也在贡献放大系数。他必须先知道症状 2 的存在才能写出正确的验证用例。

**反向不成立（我验证了）：3 不导致 2，也不导致 1**
E 实验：同一进程内监听器从 100 涨到 400，p50 稳定在 62ms，p99 62-74ms，**一个 504 都没有**。`emit` 的扇出成本（几百次自增 + 数组 push）远不足以把 40ms 的查询推到 200ms 以上。所以**不能**把超卖或超时归咎于内存泄漏——这个方向我先排除了，否则会把结论带偏成"一处泄漏引起三处故障"。

**净结论**：
- 症状 1、2、3 各自独立可复现 → **三个缺陷，不是一个**；
- 但它们共享一个病因模式（进程级共享状态无所有权管理）→ **不是一个可以分别甩出去的三个"模块问题"**；
- 2 是 1 和 3 的**上游污染源** → **1 和 2 必须同一次修、同一个人负责**，因为"扣减时机 + 失败补偿"是同一份契约的两面。

## 5. 修复建议（含"不要做什么"）

按"先止血、再治本"排序，并标注为什么这个顺序：

**P0 — 症状 2 的超时与补偿（先做，因为它既是对外故障又是另两个的污染源）**
1. `DB_CLIENT_TIMEOUT_MS` 必须**大于最慢 SKU 的实际耗时**（300ms），按 SLO 取 3-5 倍余量，例如 1000ms。更好的做法是把"客户端超时"和"业务耗时"解耦，不要用一个全局常量卡所有 SKU。
2. **超时必须显式建模为"结果未知"**，不能用简单重试兜底：`Promise.race`（`:48`）不取消 `work`，200ms 后查询仍在跑，服务端可能已经写入。建议加幂等键（orderId），超时后用同一幂等键查询真实结果，再决定补偿还是置成功。
3. **把"扣减"改成"预留 + 提交/释放"两步**（见 P1），让 504 路径能释放预留。这一条同时是症状 1 的修复基础。

**P1 — 症状 1 的原子性与补偿**
4. 把"检查库存"和"扣减库存"放进**同一个同步临界区**：删掉 `:57` 的 `await sleep(3)`，或者用按 SKU 串行化的队列/锁把临界区包起来。Node 单线程下，只要两行之间没有 `await`，就是原子的。
5. 扣减**不能无条件**：改成 `if (stock[sku] < qty) throw 409; stock[sku] -= qty;`，且必须读最新值。
6. **扣减与订单状态同事务提交**：预占 `reserved`，成功才转 `sold`，失败/超时释放回 `available`。这是唯一能同时挡住症状 1 和"504 吃库存"的结构性修法。
7. 断言不变量：库存单调不增、且 `available + reserved + sold == total`，压测后自动校验。

**P2 — 症状 3 的监听器生命周期**
8. `:62` 的 `audit.on` 改成 `audit.once`，或者在 `emit` 之后 `audit.off('paid', handler)`（用命名函数，别用匿名箭头）。**一处修改同时治好泄漏和计数放大**（R3 已证：`once` → `ok=5, listeners=0`）。
9. `:61` 的 `Buffer.alloc(64 * 1024, 7)` 不要每个请求分配；它是"模拟业务上下文"的话，用完即弃，别让监听器闭包捕获它。
10. 计数不要放在"会被历史监听器重复执行"的位置：`stats.ok++` 应放在 `handlePay` 成功返回处（或 `emit` 之外的确定路径），让一次成功只加一次。
11. `auditTrail` 设上限（环形缓冲/采样），否则它是第二个无界增长点。
12. 加一条告警：`audit.listenerCount('paid')` 持续增长或 > `maxListeners` 就报；同时把 `MaxListenersExceededWarning`（压测里已经打出来了）当 P2 级别告警而不是当噪音。

**不要做的事**
- 不要用 `audit.setMaxListeners(10000)` 消警告——那是把体温计砸了，监听器和 64KB Buffer 一个都不会少。
- 不要把 `stats.total` 当 QPS 分母：它在 `:80` 无条件自增，连 `/health` 都算进去了（B1 之前的 `total=2` 就是 health 探活）。这个计数器同样不能用来对账。
- 不要在"重试 504"上加自动重试：F 实验已证明每重试一次就永久损失一件库存，重试会加速把 SKU 打成售罄。
- 不要相信 `ok` 和 `auditTrail` 任何一个去对账，它们错得一模一样（`ok == auditTrailLen` 恒成立）。目前唯一可信的计数器反而是 `stats.e504`（`:103` 在 `catch` 里自增，不经过 `emit` 扇出）——F 实验里 40/40 准确。

## 6. 一句话回答"一个还是几个"

**三个独立缺陷，一个共同病因，两处交叉污染。**

- 若问"要不要分头修"：**不要**。1 和 2 必须合流（扣减时机与失败补偿是同一份契约），3 需要知道 2 的存在才能写出正确的验证。
- 若问"最该先修哪个"：**2**。它不只是 100% 失败的那个 SKU，它还在无声地扣库存（2→1）、无声地埋僵尸监听器（2→3）。
- 若问"团队吵架谁对"：三个人**都对但也都不完整**——每人指到的都是真缺陷，但没人指到"失败路径不补偿"和"进程级状态当 per-request 用"这两个真正的结构性病因。
