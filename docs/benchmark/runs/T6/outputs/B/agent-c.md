# 订单服务压测三连崩：定位过程与根因判定

> 结论先说：**三件事是三个彼此独立的根因，不是一个 bug 的三个表象**——而且都已在 `lab-t6` 里用「一次只改一个变量」的最小实验做成了反事实矩阵（修好任意一个，另外两个原样存在）。同时还存在**第四处没人认领的缺陷**（扣减早于占库、失败不回滚），它才是"账修不平"的那一半原因。
> 但**"分头去修"这个分工仍然是错的**：三处现象是按 SKU **互相遮蔽**的，压测报告里每张截图都只说了三分之一的真话；`/health` 自身给出的三个数字（`stats.ok`、`rssMb`、`stats.total`）全部不可作为对账口径。所以正确的做法是：**一个人先把不变量立起来，再按"不变量归属"而不是"现象归属"分工。**

---

## 0. 我在现场做了什么（可复现）

环境：端口 **19107**，原始代码未改动。

```
$env:PORT='19107'; node service.js          # 原版
$env:PORT='19107'; node load.js 16 32 SKU_C
```

| # | 实验 | 命令 | 目的 |
|---|---|---|---|
| 1 | 原版·SKU_C 并发 | `node load.js 16 32 SKU_C` | 复现超卖 |
| 2 | 原版·SKU_C 串行（对照） | `node load.js 1 8 SKU_C` | 证明超卖**只**由并发触发 |
| 3 | 原版·SKU_B 串行（对照） | `node load.js 1 4 SKU_B` | 证明 504**与并发无关**，是常量不匹配 |
| 4 | 原版·SKU_A 大流量 | `node load.js 16 320 SKU_A` ×2 + 空闲 4s | 内存与计数放大 |

## 1. 先别读代码：用 `/health` 的三个**不变量**判断"这是几个问题"

三件事看起来毫不相干，但一份正确的订单服务必须同时满足三条硬不变量。原版 `/health` 一次就把三条全破了：

```json
{"stock":{"SKU_A":-3,"SKU_B":37,"SKU_C":-9},
 "stats":{"total":645,"ok":132166,"e409":137,"e504":3},
 "auditListeners":503,"maxListeners":10,"auditTrailLen":132166,
 "rssMb":86}
```

| 不变量 | 含义 | 原版实测 | 破的地方 |
|---|---|---|---|
| **I1** `stock[sku] >= 0` | 库存只会被"成功且已占库"的单消耗 | `SKU_C=-9`、`SKU_A=-3` | 超卖 |
| **I2** `stats.ok <= stats.total` | 成功数不可能超过请求数 | `ok=132166 > total=645`（**约 205 倍**） | 计数口径错 |
| **I3** `auditListeners` 有界且不随时间单调上涨 | 进程级对象的生命周期归谁管 | `16 → 320 → 503`，只涨不跌 | 对象泄漏 |

三条不变量分别落在**三条互不相交的代码路径**上（扣减临界区 / 成功记账 / 监听器生命周期）。这不是"一个 bug 三个面具"，而更像"同一个纪律缺了三处"：**共享可变状态没有归属**。要确认这个判断，就得把三个现象分别压到 0 负荷的极端条件下——只要有一个在 0 负荷下仍然 100% 复现，它就绝对不可能是并发 bug 的副产物。

这一步很关键，因为团队吵架的根源正是"现象按 SKU 分区"：

| 现象 | 只在哪个 SKU 上看得见 | 因为 |
|---|---|---|
| 超卖 −9 | SKU_C（库存 7，并发 16） | 只有"库存小于并发数"时才溢出 |
| 全量 504 | SKU_B（唯一需要 join 的慢 SKU） | 只有它的单次耗时越过超时常数 |
| 内存涨 + 计数虚高 | SKU_A（量大且全部成功） | 只有大批成功单才会把 `ok` 放大；失败单只漏内存不涨计数 |

**所以三个人各自的截图都是真的，但都不完整。** 谁都没有看到全局，于是每人手里都是一个"独立的小 bug"。

## 2. 根因一（现象①：库存 −9）：`await` 把"检查—扣减"劈成了两段

`service.js:51-58`：

```js
const remain = stock[sku];          // 52  读
if (remain === undefined) throw mkErr(400, 'E_NO_SKU');
if (remain <= 0) throw mkErr(409, 'E_NO_STOCK');   // 54  判
await sleep(3);                     // 57  ← 让出事件循环，临界区在此断开
stock[sku] = stock[sku] - qty;      // 58  写（无条件覆盖，不是原子 CAS）
```

`52` 读、`54` 判、`57` 让出、`58` 写：这是教科书的 **TOCTOU（check-then-act）**。16 个并发请求全在 `57` 处让出，因此**每一个都读到了同一份快照 `7`**，全部通过 `remain <= 0` 检查，然后各自执行 `7-1` 的覆盖写。7 件库存卖了 16 单 → `7 - 16 = -9`。

注意 `58` 还叠加了第二个错：它是 `stock[sku] - qty` 的**整值覆盖**，而不是"读取时的值 + 条件更新"。即使把 `sleep(3)` 删掉，只要两个请求之间还有任何抢占点，覆盖写依然会丢更新。

**证据（原版，16 并发 / 32 请求）：**

```
byStatus={"200":16,"409":16}     elapsedMs=67  p50=61
stock: SKU_C 7 → -9              auditListeners=16
stats.ok=256（真实成功 16 单 → 16 倍）
```

`node probe-c.js SKU_C 16` 把 16 个响应体全打出来，**16 个全是 `200 {"ok":true,...,"remain":-9}`**：

```
 0: 200 {"ok":true,"result":{"sku":"SKU_C","taken":1,"remain":-9}}
 ...
15: 200 {"ok":true,"result":{"sku":"SKU_C","taken":1,"remain":-9}}
```

两个细节值得记：
- **超卖是以 HTTP 200 成交的**，调用方完全无法感知；`remain:-9` 还被当成"扣减后的真实余量"返回给客户端。
- 16 个响应里 `remain` 全是 `-9`（都是事后读的终值），连"每单扣完后余 6、5、4…"的因果次序都丢了。

**对照实验（把并发降到 1，其它全不变）：**

```
node load.js 1 8 SKU_C
byStatus={"200":7,"409":1}    stock: SKU_C 7 → 0    stats.ok=28（真实 7 单 → 4 倍）
```

7 件卖 7 单、第 8 单被 409 挡住、库存恰好 `0`。**超卖 100% 由并发触发，与超时、监听器无关。** 这一条同时把现象①从"另外两件事"里彻底剥离出来。

## 3. 根因二（现象②：某 SKU 全 504）：一个全局超时常量对不过一个 SKU 级的固定成本

`service.js:18-19` + `35-48`：

```js
const DB_CLIENT_TIMEOUT_MS = 200;   // 18  客户端等待上限（全局唯一）
const DB_SLOW_QUERY_MS   = 300;     // 19  SKU_B 要一次 join，实际耗时更长

const cost = sku === 'SKU_B' ? DB_SLOW_QUERY_MS : 40;   // 36
const work  = sleep(cost).then(() => { finished = true; });
const guard = sleep(DB_CLIENT_TIMEOUT_MS).then(() => {   // 41
  if (!finished) { ... e.code = 'ETIMEDOUT'; throw e; }
});
await Promise.race([work, guard]);                       // 48
```

`300 > 200` 是一个**与负载完全无关的常量不等式**：SKU_B 的单次"占库"固定要 300ms，而等待上限固定 200ms，所以 SKU_B **必然 100% 超时**，SKU_A/C 的 40ms 则永远安全。这不是"慢查询把连接池打满"那种负载型故障，而是一个**永远不会自愈的配置错配**——这也是为什么它只打一个 SKU，换 SKU 就"正常"。

**证据（原版，串行 1 并发 4 请求——把负载彻底摘掉）：**

```
node load.js 1 4 SKU_B
byStatus={"504":4}  byCode={"E_DB_TIMEOUT":4}   elapsedMs=878  p50=217  max=231
sample: 504 {"ok":false,"code":"E_DB_TIMEOUT","message":"query timeout after 200ms"}
```

串行、零竞争、四个全挂，p50 恰好 217ms（≈200ms 的 guard），错误信息直接点名 `after 200ms`。**与并发无关，与另外两件事无关。**

**这里藏着第四处缺陷（没人认领的那一处）：** 看它跑完后的健康检查：

```
stock: SKU_B 40 → 36     ← 4 单全部失败（504）
auditListeners=4, ok=0, auditTrailLen=0
```

**4 单全部返回失败，库存却实打实少了 4 件。** 因为 `service.js:58` 的扣减发生在 `67` 的 `await dbReserve()` **之前**，失败路径既不回滚、也没有补偿事务：

```js
stock[sku] = stock[sku] - qty;   // 58  先扣（且已对客户端不可逆）
const ctx = Buffer.alloc(64 * 1024, 7);
audit.on('paid', () => { ... });  // 62-65  先注册监听器
await dbReserve(sku, qty);        // 67  后占库 —— 这里会抛 ETIMEDOUT
audit.emit('paid', sku);          // 68  超时就永远走不到这一行
return { sku, taken: qty, remain: stock[sku] };
```

失败路径一次性亏三样：**库存白扣 1 件 + 泄漏一个 64KB 监听器 + 审计轨迹缺一条**（`ok=0`、`trail=0`，说明这一单在账上从未存在过）。这解释了为什么"修好了 504 之后账还是不平"——504 只是让这个洞暴露得更彻底的那只手，洞本身是"扣减与占库不在同一事务、且无补偿"。

顺带一条同路径的隐患：`dbReserve` 超时只是**客户端放弃等待**，`work` 的 300ms 定时器仍在跑完，也就是说"你已经告诉用户失败、数据库那边占库却真的发生了"；重试就会双扣。这里没有幂等键。

## 4. 根因三（现象③：内存 48→89MB 且成功计数大一个数量级）：进程级 `EventEmitter` 每请求注册、从不摘除

`service.js:14-15` + `61-68`：

```js
const audit = new EventEmitter();          // 14  进程级、长期存活
...
const ctx = Buffer.alloc(64 * 1024, 7);    // 61  每请求 64KB
audit.on('paid', () => {                   // 62  ← 每请求 on，永不 off
  stats.ok++;                              // 63
  auditTrail.push(ctx.length);             // 64  闭包持有 ctx
});
await dbReserve(sku, qty);
audit.emit('paid', sku);                   // 68  一次 emit 触发**全部历史监听器**
```

一个错误长出两个完全不同的症状，这就是"内存涨"和"计数虚高"其实是同一处代码的原因：

**(a) 计数虚高不是"多加了几次"，而是二次放大。** `ok` 的自增写在监听器体内，而 `emit` 会调用**累计注册过的所有**监听器。第 n 次 emit 时若存活 k 个监听器，就加 k。于是 `stats.ok = Σ(每次 emit 时刻存活的监听器数)`，量级是 `O(c·n)`～`O(n²/2)`，**不是** `O(n)`。这就是"大一个数量级"的来源，而且**放大倍数随并发度和总单量增长**，压得越狠越离谱：

| 场景 | 真实成功 | `stats.ok` | `auditTrailLen` | 放大 |
|---|---|---|---|---|
| SKU_C 串行 8 请求 | 7 | 28 | 28 | **4×**（=7·8/2，三角数） |
| SKU_C 16 并发 16 成功 | 16 | 256 | 256 | **16×**（16 个监听器全在首次 emit 前注册完，16×16） |
| SKU_A 16 并发 320 成功 | 320 | 54784 | 54784 | **171×** |
| SKU_A 累计 503 成功 | 503 | 132166 | 132166 | **263×** |

注意 `stats.ok` 最终 **`132166 > stats.total = 645`**。一个正确实现里这个不等式不可能成立——所以**这张 `/health` 从第一次压测起就不能作为对账口径**，包括它给的 `stats.total`（`80` 行的 `stats.total++` 在 `/health` 分支之前，连探活请求也计进去了）。

**(b) 内存涨是闭包把 64KB 焊在进程级对象上。** `ctx` 被监听器闭包引用，监听器挂在永不销毁的 `audit` 上，所以 64KB × 成功单数**不可回收**。实测：

```
rss: 48MB（空载）→ 74MB（320 单）→ 70MB → 86MB（再 320 单，其中 183 成功）
空闲 4 秒后仍然 86MB —— 不回落（GC 拿不回来）
```

`48 → 89MB` 与题面吻合（约 640 单 × 64KB ≈ 40MB）。**`rssMb` 是滞后指标**：它在泄漏过程中还从 74 掉到过 70，光看它会以为"自愈了"。**唯一的单调可信指标是 `auditListeners`：16 → 320 → 503，只涨不跌**，而 `maxListeners:10` 就在旁边做对照。Node 自己早就报警了（我这次运行的 stderr 里也复现了同一行）：

```
(node:22152) MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
11 paid listeners added to [EventEmitter]. MaxListeners is 10.
Use emitter.setMaxListeners() to increase limit
```

**失败路径是这条泄漏里最阴的一支：** 前面 SKU_B 的 4 个 504 留下 `auditListeners=4 / ok=0 / trail=0`——**监听器注册在 `62`，`emit` 在 `68`，超时直接跳过了 `68`**。于是全量失败的 SKU_B 每个请求漏 64KB、却一毛钱都不进 `ok`。这正好解释了题面的错配："内存一路涨"和"计数虚高一个数量级"根本不是同一个 SKU 提供的：**内存主要来自失败的 SKU_B + 成功的 SKU_A，计数虚高只来自成功的 SKU_A**。两句话拼在一起，谁也对不上账。

## 5. 判定"一个还是几个"：反事实矩阵

光靠读代码说"三处独立"是不算数的——`await` 与并发、事件循环、泄漏都可能互相诱发。所以我做了三个**只改一行/一处**的分支，各自单独跑：

| 变体（其它一行不动） | 现象① 库存 | 现象② SKU_B | 现象③ 内存 / 计数 |
|---|---|---|---|
| **原版** `service.js` | `SKU_C -9`（16 全 200） | `4/4 504` | `503 单 → rss 86MB、ok=132166(263×)、listeners 503` |
| **只修①** `agent-c-lock.js`（按 SKU 串行化临界区） | ✅ **修好**：`7×200 + 25×409`，库存停在 `0` | ❌ `3/3 504`，库存还白扣 3 件 | ❌ `ok=44` / 真实 7 单（6.3×），listeners 10 |
| **只修②** `agent-c-timeout.js`（`200 → 400ms`） | ❌ 仍 `-9`（16 全 200） | ✅ **修好**：`4×200`，p50 328ms | ❌ `ok=330` / 真实 20 单（16.5×） |
| **只修③** `agent-c-leak.js`（监听器只在启动时注册一次） | ❌ 仍 `-9`（16 全 200） | ❌ `3/3 504` | ✅ **修好**：`ok=336` = 真实 336 单（**分毫不差**），`listeners=1`，`rss 52MB` |

矩阵是干净的对角线：**每一处修复只关掉自己那一列，另外两列原样保留。** 这就是"三个独立根因"的硬证据，也是我唯一认可的证据形式——不是"我觉得它们没关系"，而是"关掉一个，另外两个还在"。

顺带得到两个有意思的旁证：
- `只修②` 后 SKU_B 的 p50 是 **328ms**，比 `DB_SLOW_QUERY_MS=300` 还高——说明 200ms 的等待上限连"正常的一次 join"都装不下，它本来就不可能是靠调并发能解决的问题。
- `只修③` 后 `ok` 精确等于成功数，且 `rss` 只从 48 涨到 52（320 单），泄漏量级也从"每单 64KB 永久驻留"变成"随请求回收"。

**最终判定：**
- **机制层面：三个独立根因**（三段不相交的代码路径、三种不同的错误类型：缺原子性 / 常量错配 / 缺生命周期管理），**外加第四处没人认领**（`58` 的扣减早于 `67` 的占库，失败不回滚、无补偿、无幂等），以及相邻的 `qty` 未校验（见第 6 节）。**所以三份 patch 是必须的，谁也不能替谁修。**
- **认知层面：一个共同的元根因**——**共享的可变状态没有所有者**：`stock` 谁都能读改写、`audit` 谁都能挂监听器、超时常量对 SKU 级成本没有约束；再加上 `/health` 把**派生量**（监听器触发次数、瞬时 RSS）当成了业务指标，导致三个现象互相遮蔽。
- **协作层面：分头"修"可以，分头"查"不行。** 三个人各自的结论单独看都是对的（超卖=并发、504=超时、泄漏=监听器），但拼在一起会漏掉第 4 处、也会得出"修完就好了"的错误判断。正确顺序是：**先立不变量（一次调查），再并行打三个补丁（三次修复），最后用不变量验收。**

## 6. 顺手打出来的第四个和第五个洞（属于"库存对不上"这一族，别漏）

修完上面三处，账**仍然**不平，所以必须把这两条也写进工单：

1. **失败不回滚 / 无幂等**（`58` 早于 `67`）：已实测 SKU_B `40 → 37` 而三单全 504。真实系统里这是"资损"而非"bug"：用户收到失败、库存却真扣了、DB 侧的占库在 300ms 后照样落地、重试再扣一次。
2. **`qty` 完全没校验**（`96-97`，`Number(...)` 直通）：

```
POST /pay?sku=SKU_C&qty=-1000  →  200 {"taken":-1000,"remain":1007}     ← 负数直接加库存
POST /pay?sku=SKU_A&qty=abc    →  200 {"taken":null,"remain":null}       ← stock 变 NaN
之后 /health: {"stock":{"SKU_A":null,...}}                              ← 该 SKU 永久中毒
```

`NaN <= 0` 恒为 `false`，所以中毒的 SKU **每次下单都会通过检查**、且 `NaN - 1 = NaN` 永远不变——**一个坏请求就能把某个 SKU 变成无限库存**。这条同样是"库存对不上"，但与并发无关，且任何一次线上脏调用都会永久生效，优先级不低于前三件。

## 7. 如果我只能留一段话给团队

> 别按"现象"认领，按"不变量"认领。
> 1. **先停机再对账之前，先把三条不变量写下来并断言**：`stock >= 0`、`ok <= total`、`listeners` 不随请求单调增长。它们今天全破，说明这是"三处无人把守的不变量"，不是"三个偶发"。**`/health` 里的 `ok` 和 `rssMb` 从此禁止出现在任何对账或容量结论里**（一个 `ok=132166 > total=645`，一个在泄漏中还会回落）。可信的只有 `auditListeners`。
> 2. **用"把负荷降到 0"来分离根因**，这一步 5 分钟就能吵完：串行跑 SKU_C 库存不再溢（→ 超卖是并发）；串行跑 SKU_B 依然全 504（→ 504 是常量）；320 单全成功依然 rss +26MB、ok 放大 171×（→ 泄漏与失败无关）。三个对照一做，谁也不用量谁的截图。
> 3. **再跑反事实**：关掉一处，另外两处必须还在。这是"几个根因"唯一能过硬的判据。
> 4. 按这个顺序修，别并行开工：**先①**（超卖是资损，且在持续发生）→ **再④**（失败不回滚 + `qty` 校验，同样是资损，且第 4 处会被前三条的修复"看起来已经好了"掩盖）→ **再②**（改 `DB_CLIENT_TIMEOUT_MS` 到 > 单次预期、或按 SKU 分别配置，并把超时与取消/补偿一起做）→ **最后③**（监听器改启动时注册一次；`ctx` 不要挂在长生命周期对象上；`auditTrail` 要重算/清理历史脏数据）。**注意顺序：先修①④再修②，否则修完②只会让 SKU_B 的库存洞从"暴露"变成"静默"。**
