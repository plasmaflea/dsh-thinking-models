## L2 逐层回溯

### 轴（生成式，不是列举式）

任何「有副作用的写请求」必然经过：**接入 → 读共享态 → 判定 → 让出/排队 → 写共享态 → 注册副作用 → 调依赖 → 结算回写**。八格不可省（跳步可省、格子不可省），每格必须有专属症状，哪怕写「此处无症状」。

| 格 | 该格在管什么（必经理由） | 代码锚点 | 本次专属症状 | 判定 |
|---|---|---|---|---|
| G1 接入与计数 | 请求进闸，任何服务都要数 | `service.js:80` `stats.total++` | `/health` 也被计入 `total`（26 vs 实际 pay 21） | 无症状级偏差（可观测性噪声，不是根） |
| G2 读共享态 | 要扣减必须先读 | `service.js:52` `const remain = stock[sku]` | 读本身无副作用 | **此处无症状**（读不单独致病） |
| G3 判定 | 有剩余才能卖 | `service.js:53-54` `E_NO_SKU` / `E_NO_STOCK` | 判定读的是**快照**，不是提交时的真值 | 判定无原子性 → 挂在类根下 |
| G4 让出/排队 | 单线程 JS 的每次 `await` 都是可插入窗口 | `service.js:57` `await sleep(3)` | **超卖的唯一窗口**：16 并发全部读到 `remain=7` 且全部通过判定 | **必要条件**（无并发则 0 超卖，实测） |
| G5 写共享态 | 唯一应发生「提交」的地方 | `service.js:58` `stock[sku] = stock[sku] - qty` | 无条件写、无 CAS、无事务；写到 `-9` 也不报错 | 类根的直接载体 |
| G6 注册副作用 | 记账/审计 | `service.js:61-65` `Buffer.alloc(64*1024,7)` + `audit.on('paid',…)` | **监听器只增不减、每个还钉住 64KB**；`stats.ok++` 写在监听器里 → 一次 emit 触发全部历史监听器 | 类根的第二载体（无所有权、无回收） |
| G7 调依赖 | 真扣库 | `service.js:18-19,41-48` `guard` 200ms vs `SKU_B` cost 300ms | `SKU_B` 100% 504 `E_DB_TIMEOUT`；且**扣减已在 G5 提交、失败不回滚** | 触发根（预算错配）+ 被类根放大 |
| G8 结算/回写 | 成功才该结算 | `service.js:67-68` `await dbReserve()` 之后才 `audit.emit` | 成功路径正常；失败路径直接跳走，G5 的写入永久生效 | 缺回滚/补偿点 |

### 因果边（必须标明必要/充分）

```
G4（并发插入窗口）  --必要条件-->  R1 超卖（还额外需要 remain>0 通过 G3，故非充分）
G5（无条件写、无 CAS）--必要且充分-->  负库存可以被持久化到 -9 而不报错
G7（timeout 200ms < SKU_B cost 300ms）--充分条件-->  R2 100% 504
G5 提交先于 G7 成功  --充分条件-->  504 也扣库存（失败已扣，且无回滚）
     └── 这条边使 R2 成为 R1 的放大器：不是"另一个 bug"，是把 R1 的账做得更烂
G6（监听器无 owner、无 off）--充分条件-->  R3a 计数膨胀（emit 扇出到全部历史监听器）
G6（同上，每个监听器钉住 64KB ctx）--充分条件-->  R3b RSS 上涨
     └── R3a 与 R3b 是同一个节点的两个后果，不是两个根
```

### 回溯到根

**→ 类根（这一类在什么结构条件下必然可能发生）**
请求处理链**没有唯一提交点，也没有副作用的所有权**：每个请求直接对进程级共享对象做「读—判—写」，且把不可逆的副作用（扣库存、注册监听器）放在依赖调用成功**之前**、放在任何可回收的作用域**之外**。只要这个结构在，`remain` 的读与写之间必然存在他人插入窗口，失败路径必然留下已提交的写入，副作用必然只增不减 → 超卖、失败已扣、内存与计数一起膨胀，是**同一个结构条件的三个投影**，不是三次巧合。

**└ 个例根（挂在类根下，按机制分，不按人分）**

- **R1 超卖（-9）**：`G3` 用快照判定 + `G4` 让出窗口 + `G5` 无条件写。实测把并发降到 1，同一份代码 **0 超卖**（7 单成、9 单 409、库存落 0）→ 证明超卖是 TOCTOU，不是「库存表算错」。
- **R2 `SKU_B` 全 504**：客户端等待上限 `DB_CLIENT_TIMEOUT_MS = 200` 小于 `SKU_B` 需要的 join 成本 `DB_SLOW_QUERY_MS = 300`（`service.js:18-19`），`guard` 在 200ms 抛 `ETIMEDOUT`，被 `service.js:102-104` 映射成 504。确定性 100% 失败，p50 实测 223ms ≈ guard 预算。**它的触发根与类根无关**（属 `config`/`dependency` 子层：超时预算由手写常数给出，不是由被调方 p100 成本生成）；类根只负责把它从"一次失败"升级成"一次失败 + 一次不可回滚的扣减"。
- **R3 内存涨 + 计数放大**：`service.js:61-65` 每个请求 `audit.on('paid', …)` 注册一个新监听器且从不 `off`，监听器闭包钉住 `Buffer.alloc(64*1024)`；`stats.ok++` 在监听器体内 → 一次 `emit` 触发**全部历史**监听器，计数变成 O(n²) 的扇出计数。实测 16 并发同批 → `ok=256`（16×16，**比真实成功数大 16 倍**）；大流量段 `ok=70381` vs 真实 320（**220 倍**）；`auditListeners` 单调 0→16→48→368，stderr 真实吐出 `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 paid listeners added to [EventEmitter]. MaxListeners is 10.`，RSS 48→51→53→74MB。

## L3 双根

### 处置根（修本次，三处都要动，但一次改完）

1. **库存**：把 `G3+G5` 合成一条条件更新（`UPDATE stock SET qty=qty-? WHERE sku=? AND qty>=?`，以影响行数决定 200/409），删掉 `await sleep(3)` 这个可插入窗口。
2. **依赖**：`SKU_B` 类慢查询的超时预算必须 > 其 p100 成本（200ms→按被调方 SLA 生成，而非拍常数）；失败路径补回滚/补偿，`dbReserve` 的 `work` 要真取消。
3. **审计**：`audit.on` 改为**进程启动时注册一次**的单例监听器，请求只带 `ctx`（`ctx` 在 `finally` 里释放）；`stats.ok` 直接计数，不再由 emit 扇出来算。

### 消解根（灭这一类）

**让「共享可变状态」在结构上只经由一个提交点被修改，并让副作用成为有 owner、可回收的请求局部对象**——即：(a) 状态修改一律走条件更新/事务边界（compare-and-set），(b) 副作用在提交之后注册且由 `finally` 释放，(c) 依赖调用的超时预算由被调方 SLA 生成。

- **不可发生判据**：若当时采用该结构，则「超卖」与「失败已扣」在结构上**不可能发生**——要出现它们，必须先额外写出一个 bug；而「监听器只增不减」失去载体（不存在每请求注册的长期监听器）。这不是让问题变少见，是让格子空掉。
- **可执行首边**：改 `handlePay` 一处——把 `stock` 的读-判-写换成一条条件更新函数（本进程内先同步实现即可），并删掉 `service.js:57` 的 `await sleep(3)`。
- **成本量级**：单文件约 30 行改动 + 1 个事务边界；回归成本 = 一次 3 分钟压测（具体人日与回归矩阵交公式图定量，本图只给量级）。

## L4 迁移出口（因消解根产生的新问题）

1. **数据与状态**：已污染的账要回滚——`SKU_C=-9`（16 单卖出 7 件）、`SKU_B` 40→8 而 **0 单成功**（32 单失败已扣）；需要按流水对账，并引入幂等键（`requestId`）才能安全重放。
2. **运行与自启**：库存从进程内存搬到 DB/Redis；一旦多实例，原子扣减必须换成分布式 CAS/乐观锁，单进程锁不再成立。
3. **可观测性**：`stats.ok` 语义变了（不再等于监听器调用数），`/health` 的 `total` 仍混入探活请求；需新增 `ok/attempt` 比值、`auditListeners` 阈值告警、慢查询分 SKU 直方图。
4. **凭据与权限模型**：DB 客户端超时/连接池参数从代码常量挪进配置中心并纳入评审。
5. **组织能力**：值班需能一眼区分「过载/竞争失败」与「配置预算失败」，否则同类事故仍会被拆给三个人。

→ **本次问题降级为**：第 1 项（数据回滚）与第 3 项（计数语义重建）的子项；即"三个人分头修"这个现场，降级成"一次结构性改造的收尾。

## 结论

1. **不是一个故障，也不是三个故障，是"一个结构类根 + 一个被它放大的预算错配"**——两棵树：`请求链无提交点/副作用无 owner`（root of R1、R3，并把 R2 的伤害放大）、`客户端超时预算 200ms < SKU_B 查询成本 300ms`（root of R2 的触发）。它们**共因于同一个汇合层**：不可逆副作用在依赖成功之前提交。
2. **直接回答"根源一个还是几个"**：从修复动作看是 **2 个根**（三处代码，其中 R1/R3 同根）；从发生学看是 **1 个结构 + 1 个配置**。三个人分头修的错不在分工，在于**把同一个结构缺陷的两个投影当成两件独立故障**，于是任何一个人单独修完，另外两个症状都还在。
3. **最刺眼的证据链**（一句话能钉死）：同一份代码，`SKU_C` 并发 16 → 卖 16 单库存 `-9`，并发 1 → 卖 7 单库存 `0`；`SKU_B` 并发 1、5 单**全失败**，库存却从 40 掉到 35；`ok` 从 16 成功报到 `256`，因为它在 16 个历史监听器里各加了一次。
4. **先动哪一刀**：`service.js:52-58` 的读-判-写换成条件更新，同时删 `service.js:57` 的 `await sleep(3)`（一次改动同时断掉超卖与"失败已扣"）；再改超时预算与单例审计监听器。修完必须回滚已污染的 `SKU_C=-9` 与 `SKU_B=8`。
