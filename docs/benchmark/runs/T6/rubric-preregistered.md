# T6 预注册口径 · 三真根并列（带注入真值）

写定时间：发题之前。跑完不许改判定式。

## 题面（逐字，A/B 两组完全一致）

> 我们内部的一个订单服务，压测时同时出了三件事，团队已经吵起来了：
> 1. 库存对不上——总共才 7 件的 SKU_C，压测跑完卖了 16 单，库存变成 -9。
> 2. 有一个 SKU 的订单全部失败，返回 504；换成别的 SKU 就正常。
> 3. 进程内存一路涨（48MB → 89MB），而且 `/health` 里的成功计数比实际成功请求数大了一个数量级。
> 三个人各自认领一件，说要分头去修自己那摊。你怎么定位？根源到底是一个还是几个？
>
> 代码在 `D:\DeepSeek-levelup\lab-t6`（`service.js` + `load.js`），可以读、可以起服务、可以自己压测。

## 注入的真值（三根，互不覆盖）

| id | 真根 | 代码位置 | 判别证据 |
|---|---|---|---|
| **R1** | 竞态：查库存（读 `remain`）→ `await sleep(3)` → 扣减，读-改-写非原子 | `handlePay` 开头 | 并发 > 库存时 `stock.SKU_C` 变负（实测 −9），`E_NO_STOCK` 只在第二次读时才触发 |
| **R2** | 配置：DB 客户端超时 200ms < SKU_B 查询耗时 300ms | `DB_CLIENT_TIMEOUT_MS` / `DB_SLOW_QUERY_MS` / `dbReserve` | SKU_B 全 504（64/64），且**扣减发生在预留之前** ⇒ 库存掉了但订单失败（丢货） |
| **R3** | 泄漏：`handlePay` 每次 `audit.on('paid', …)` 注册监听器且从不移除，并捕获 64KB Buffer | `handlePay` 中段 | `auditListeners` 线性增长（0→516），`stats.ok` 按监听器数重复累加（实测 145342 vs 实际 500），rss 48→89MB |

三者**独立**：修好任一个，另两个的症状仍在。

## 判定项

| id | 项 | 判据 |
|---|---|---|
| H1 | 真根召回（0–3） | 逐根判定：是否点出「读-改-写非原子/竞态」(R1)、「超时阈值 < 查询耗时」(R2)、「监听器只加不减」(R3)。同义表述算命中；只说"有并发问题"不说机制不算 |
| H2 | 并列声明 | 是否明确「这是三个独立根并存，不是同一个根」，且**每根给独立证据**（不是一句话带过） |
| H3 | 区分实验 | 是否给出能把三支分辨开的观测/实验（如：单线程压测看 R1 是否消失、换 SKU 看 504、看 listenerCount 曲线），而不是"先修一个再看" |
| H4 | 误并惩罚 | 是否把三件事强行归因到单一根（如"都是内存导致"、"都是并发"），或说"修了 A 就都好了" |
| H5 | 修复独立性 | 是否指出三个修复互不覆盖（修一个，另两个症状仍在） |

## 判定规则（预注册）

1. **主判定 = H1 的平均召回根数 + H2 命中份数**。这是唯一能给出真值的题（真根由作者注入、可执行复现）。
2. H4 每命中 1 份记 −1 根（从 H1 里扣），因为"误并"是本轮要测的核心缺陷。
3. H3/H5 单独报告，不计入主判定。
4. A 组（装技能）/ B 组（无技能）各 5 份，**同一题面逐字**，同机不同端口，互不可见。
5. 不报答对率，只报"召回根数分布 + 并列声明份数 + 误并份数"。
