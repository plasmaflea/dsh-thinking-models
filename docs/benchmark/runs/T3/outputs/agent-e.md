## L0 类别判定

**类别**：**时延敏感链路上的「阈值击穿」类问题**（软件变更 × 链路质量 × 流量条件三因子耦合），不是单一软件缺陷，也不是单纯的组织决策问题。

判据（三条同时成立）：
1. 失败在**原因族上高度集中**：增量 1.25pp 中，网关超时族贡献 +0.926pp（**74.1%**），其他两族合计 25.9% —— 这是典型的「一类失败吃掉大部分增量」，指向**单一共享通路**而不是多处局部缺陷。
2. 失败**不随代码版本走、随链路质量与流量走**：CDN 首字节 p95 是唯一「三周前→本周」单向恶化的指标（180→310/420ms），其余（网关 p95、DB 慢查询）持平；而成功率在 10-09/10-10 只跌 0.35/0.50pp、10-11/10-12 又回到 97.95/98.00，直到 10-13 才阶跃到 96.95。**代码变更（10-08）与成功率阶跃（10-13）在时间上错开 5 天**，所以不能用「变更了所以坏了」来解释（详见 ⚠️ 1、2）。
3. 量级上存在**固定阈值**把「中等幅度的时延增量」放大成「确定的失败」：客户端支付 SDK 超时阈值 800ms 在三周前后**未变**。不变量不能解释变化，但它是把 +245ms 变成 +1.25pp 的乘数。

已排除的大类：
| 大类 | 排除依据 |
|---|---|
| 硬件故障 | 无校验错误/随机性症状；DB 慢查询与三周前持平；失败在端与地区上呈单调梯度而非随机散布 |
| 权限/账号体系 | 失败族里没有「拒绝访问/找不到资源」；风控拒绝族绝对失败率几乎不动（0.774%→0.800%） |
| 纯组织流程 | 技术层**有**可测的指标恶化（TTFB +133%、504 占比 ×3、JS 错误 ×5.25），不满足树里「技术手段已全部正常」的判据；但组织流程作为**结构条件**进入类根（见 L3） |
| 纯网络（作为独立大类） | 不能排除，反而**落入**该支 —— 详见挂起表第 9 行（树中 `network` 为待建节点，无节点可挂，已登记 v2 候选） |

## L2 逐层回溯

### 选轴（生成式，不列举）

**主轴＝必经时序**：一笔支付请求必然走过的格，一格不少（生成源：过程先后，不可跳过）。
**副轴＝恒等式**：`T_端到端 = T_客户端处理 + T_TTFB(CDN) + T_网关 + T_渠道回程`，且失败判据是**阈值式**而非连续式：`客户端放弃 ⟺ T_端到端 > 800ms`。
每格必须写出「该格故障的可观测症状」——本次数据里能对上指标的格，与**缺格的空白**一并标出（缺格本身就是证据：合规截断掉的恰好是定案所需的那四格）。

### 量化：余量算术（这是全篇的核心，只用题干给过的数）

| 项 | 三周前 | 本周（A 残留路径） | 本周（B 节点路径） |
|---|---|---|---|
| CDN 首字节 p95 | 180 ms | 310 ms | 420 ms |
| 支付网关 p95 | 320 ms | 325 ms | 325 ms |
| 端到端 p95（副轴恒等式相加） | **500 ms** | 635 ms | **745 ms** |
| 距 800ms 阈值余量 | **300 ms** | 165 ms | **55 ms** |
| 余量占用率 = (现−基)/(800−基) | 0% | **45.0%** | **81.7%** |

三条结论：
1. **基线本来就无缓冲**：p95 端到端 500ms，对 800ms 超时只剩 300ms。任何一层拿走 245ms，p95 就只剩 55ms 头寸。
2. **CDN 切换正好拿走了 245ms**（420−180=240，加网关 +5ms）。余量占用 **81.7%**。
3. **阈值右侧的尾质量反推**：ΔP(超时) = 0.926pp ÷ 245ms ≈ **0.38%/100ms** 的尾部密度。对移动网络 p95 附近的长尾，这个密度是常识量级 —— 数量级自洽，**不需要网关变慢**即可产生 0.926pp。（这是自洽性检查，不是证明。）

三个**方向性反证**，把「v3.4 前端是主因」按住：

- **Web 涨幅最小而非最大**。JS 错误（0.4%→2.1%）只可能发生在浏览器/H5 侧；若前端改版是主因，Web 的失败率增量应最大。实际 Web +0.70pp（占增量 22.3%），Android +1.70pp（占 51.4%）。**症状出现在 Web，增量却集中在用原生页面/原生 SDK 的 App** ⇒ 变量不在页面代码，在**App 与 Web 共用的网络通路**。
- **海外 2.64× 超额**。海外只占 10% 的发起量却贡献 26.4% 的增量，且是唯一「翻倍」的地区（3.40→6.70）。前端改版不会挑地区；**CDN 厂商 B 的边缘覆盖/跨境回程会**。这与「基线本就偏高（3.40%）的地区余量最薄、同一时延抬升最先击穿阈值」一致。
- **网关 p95 不动而 504 涨 3 倍**。一个自身时延未变的组件，不可能是「由时延引起的 3 倍超时」的发源地；它只是把别处（客户端侧放弃 / 上游渠道超时）记成了 504。

### 2. 类根 → 个例根

**类根（结构条件，面对整类而不止本次）**：
> **支付通路没有「端到端时延预算」这个受管对象。** 没有任何机制要求：任何一层（前端→DNS→CDN→BFF→网关→渠道）的变更，必须申报它对客户端 800ms 超时的占用；也没有机制要求同一变更窗口只允许一个变量。因此「某层安静地吃掉 80% 余量 → p95 贴上阈值 → 尾部击穿 → 以『网关超时』的名义出现在报表里」这一整类故障，在任何一次变更中都**结构上必然可能发生**，而且发生时必然**不可归因**（原始报文不留存、日志被截断、无对照流量）。

**个例根（挂在类根之下的子节点，不是平行清单）**：
- **A1｜主因：10-08 20:00 的 CDN 全站切换（含 API 域名）**，把支付请求的通路首字节从 180ms 抬到 420ms（A 残留 310ms），单此一项吃掉 300ms 余量中的 **81.7%**，端到端 p95 剩 55ms 头寸。
- **A2｜放大器：10-10 起的 +40% 大促流量**。不改变分子机制，只把 CDN 侧尾分布进一步右移、把 p95 推过阈值。判定为「共因/放大器」而非独立根，依据是后端两个容量指标（网关 p95、DB 慢查询）都**没有**随 +40% 变化 ⇒ 不是后端容量。
- **A3｜使能条件：客户端 SDK 800ms 超时阈值未随通路复核**。阈值本身不变，所以它不是变化源；但它决定了「245ms 的时延增量」被放大成「1.25pp 的失败增量」的倍数。这类条件的危险在于**它没人拥有**：前端改版、CDN 切换、网关升级三方都不认为 800ms 是自己的数。
- **B1｜次要根：v3.4 优惠券校验重写**，解释其他族 +0.298pp（增量的 23.8%）与 JS 错误 ×5.25；它解释的是「参数错误/用户取消」那一桶，**不解释超时桶**。
- **B2｜取证根：变更治理与可观测性同时缺位** —— 两变更同分钟生效、无灰度、无对照流量、原件不留存。这使 A1/B1 的归属**在数据上永久不可证**，只能靠机制与量级排序（本报告就是在明说这一点）。

## L3 双根

**处置根（修本次）**
> 把**支付 API 域名的 CDN 从厂商 B 回切到厂商 A**（静态资源域名可留在 B，天然形成对照），先 5% 灰度 30–60 分钟再放大。目标是把 TTFB 从 420ms 拉回 ~180ms，回收 240ms、把余量占用从 81.7% 压回 45% 以下，p95 端到端回到 ~635ms。

**消解根（灭这一类）**
> 把「端到端时延预算」变成变更的**前置门禁**：支付通路的每一层拥有一个显式的时延配额（基线 180/320/…，总额 800ms 中预留 300ms 缓冲），任何变更必须申报「占用了多少余量、剩余多少」，且**同一窗口只允许一个变量 + 至少 5% 对照流量**。

三道闸门逐条过：

1. **不可发生判据（不是"变少见"）**：若 10-08 那次变更单上有「时延预算占用」这一列，CDN 切换会申报「245ms / 占余量 81.7% / 剩余 55ms」，评审在**切换之前**就会把它拦下或强制降级为 5% 灰度 —— 本次这 1.25pp 在结构上**不可能发生**。同理，若"同窗口单变量 + 对照流量"成立，A1 与 B1 也不会被压进同一分钟，归因成本从「不可能」降为「一次回切」。
2. **可执行首边（很小，从现状就能做）**：下一张变更单里加一列 `时延预算占用（ms ／ 占余量 %）`，先只覆盖支付通路的四层（前端→CDN→网关→渠道），用现有的 p95 指标估。不需要新系统、不需要新采集、不需要等日志合规放开 —— 一张表 + 一次评审会。
3. **成本量级（量级，不编具体钱）**：建设 1–2 人日（一张预算表 + 变更模板加一列 + 一次 30 分钟评审对齐）；每次变更评审 +10 分钟。对照本次：1.25pp × 大促日均支付量的损失是「按天」计的，而门禁成本是「按人日」计的 —— 量级差两到三个数量级，无需精确数字即可决策。（定量交给 📐 公式图，本图不代算。）

**处置根 vs 消解根的关系（必须说清）**：处置根只修本次，且**不改类根**——回切之后，那 300ms 的余量仍然没人拥有，下一次换 CDN、加埋点、上风控前置校验，同样的 1.25pp 还会以同样的面目重来。消解根不修本次，但它把本次降级为「时延预算门禁」的一个子项。

## L4 迁移出口

消解根指向「给支付通路建时延预算门禁」，而门禁要成立，前提是**分层时延可观测**；当前恰好是日志被合规截断、网关原始报文不留存。于是迁移清单：

1. **可观测性**（前置，必做）：用**聚合直方图**替代原始报文 —— 每层只落 `p50/p95/p99 时延桶 + 超时计数 + 失败族计数`，不落报文内容，合规可过；并把 800ms 阈值右侧单独设一桶（700–800/800–1000/>1000ms），因为**判据就在阈值附近**。
2. **数据与口径**：统一「支付失败」的分子分母，并**重试去重**。当前网关 504 占其响应 27% 而支付失败率只有 3.05%，两个分母不同源（重试膨胀或 API 面更宽），这两个数无法互推，必须先把口径对齐。
3. **变更流程**：单变量窗口 + 灰度对照流量（≥5% 停留 ≥30 分钟）+ 一键回切开关（DNS/证书/回源白名单必须能一起回退 —— 回切本身就是有风险的操作）。
4. **组织能力**：值班要有「回切」的授权与预案，而不是先开会找责任人。本次四家团队的说法（风控/CDN/后端/运维）全部无证据且互相矛盾，说明取证与止损的职责都没有落点。
5. **凭据与权限模型**：回切 CDN 涉及 DNS 记录、TLS 证书、源站白名单三处凭据，任一处不同步就会把「回切」变成第二次故障。

→ **本次问题降级为**：迁移清单第 1 项（可观测性：阈值附近的聚合直方图）+ 第 3 项（单变量窗口与对照流量）的子项。

## 候选根排序（Share × Lever ÷ Cost）

预算是「一次回切 + 一次灰度观察 + 一次指标拉取」，不是无限。按此排序取前 2 条去验证，其余挂起。

| # | 层 | 候选 | Share | Lever | Cost | 行动 |

**排序的诚实边界**：上面第 1 与第 2 的 Share 是「按机制与量级估的」，不是「按对照实验测的」—— 因为这两个变更同分钟生效、且没有对照流量，**在现有数据上它们的贡献无法被严格分离**。这正是为什么「先做什么」的答案必须是**一次能把两者分开的动作**（见 §5），而不是「再去多拉几张报表」。多拉报表救不了：原始报文不留存，缺的四个数（DNS 解析时延、渠道侧时延、CDN 命中率与回源率、重试率）在历史数据里根本不存在，只有**从今天起的实验**才能补。

## 5. 只能做一件事，先做什么

> **把支付 API 域名的 CDN 从厂商 B 回切到厂商 A；静态资源域名留在 B 不动。先 5% 灰度 30–60 分钟，看超时族；若超时族回落（≥0.3pp），30 分钟内放大到 100%。**

为什么是这一件，而不是别的：

1. **它同时是止损和实验**。其他任何选项（加监控、查日志、开复盘会、回滚发版）都只做其中一件。回切一次动作，既回收 240ms 时延把成功率拉回来，又完成了一次**单变量分离** —— 这正是这个案子最缺的东西（两个变更同分钟生效，从来没有过对照组）。
2. **它是唯一有「方向一致的指标」背书的动作**。CDN 首字节是全表唯一单向恶化的指标（180→310/420ms）；网关 p95 与 DB 慢查询持平、风控绝对失败率不动，那三处不值得先花预算。
3. **静态资源留 B 使实验自带对照组**。同一厂商、同一时段、同一流量，只变 API 域名这一条路径 —— 这是在不新增灰度平台的前提下能拿到的最干净的对照。
4. **结论是二分的、不需要更多数据**：
   - 超时族 30 分钟内明显回落 ⇒ **CDN 定案**，成功率同步恢复，本次结束，长期动作走 L3 消解根。
   - 超时族不回落 ⇒ **CDN 与 +40% 流量一起被排除**，「网关 p95 不动而 504 涨 3×」这个背离就只能指向 ⑤/⑥ 格（渠道侧）或 B1，下一个动作立刻明确：查渠道侧连接错误与时延（此前是缺格，此刻有了排除法的落点）。
   无论哪一支，都比现状（四家团队各说各话、无证据）前进一大步。
5. **Cost 最低、可逆**。配置回切，无需发版、无需改代码、可在一小时内回退；Cost 越低，排序越靠前（§8：预算有限时 Cost 就是决定性项）。

**唯一备选（仅当回切被流程卡住时）**：临时把客户端 SDK 超时从 800ms 提到 1500ms（一次配置下发）。这能把成功率立刻拉回，但**它会掩盖证据**：阈值一撤，「余量被吃掉」这个信号就消失了，而 745ms 的 p95 仍然在。定位为「撑到回切被批准的止血」，不是解决方案；且大促期间放大超时阈值会让最慢的那 5% 用户等更久（体验代价未测）。

**明确不要先做的三件事**：① 回滚 v3.4（会和 CDN 一起变成第二个混淆变量，除非回切已证明 CDN 清白）；② 调风控（绝对量根本没动，+0.026pp）；③ 加日志/查原始报文（合规不留存，历史数据在物理上不存在，这条路是死的）。

## 结论

1. **根源**：支付通路的**端到端时延余量本来就只剩 300ms**（p95 = CDN 180ms + 网关 320ms = 500ms，对客户端 800ms 超时）。**10-08 20:00 的 CDN A→B 全站切换（含 API 域名）** 把首字节抬到 420ms，端到端 p95 变 745ms，**吃掉 81.7% 的余量、距击穿只剩 55ms**；**10-10 起的 +40% 大促流量**把尾部推过阈值，于是失败以「网关超时」的名义出现：超时族 **0.864%→1.790%（+0.926pp，占增量 74.1%）**。这三者（切换／大促／固定阈值）共同解释主要增量。**v3.4 的优惠券校验重写只解释另一桶**（其他族 +0.298pp，占 23.8%，与 JS 错误 ×5.25 同源）；**风控（+0.026pp）、DB（慢查询持平）、支付网关自身（p95 320→325ms）都是干净的**。结构根更深一层：**支付通路没有「端到端时延预算」这个受管对象**，任何一层都能安静地吃掉 80% 余量而不被任何评审拦下，且两变更同分钟生效、无灰度、无对照、报文不留存 —— 于是它既容易发生，又必然不可归因。
2. **只能做一件事**：**把支付 API 域名的 CDN 从 B 回切到 A（静态资源留 B 作对照），先 5% 灰度 30–60 分钟。** 它一次动作同时完成止损与单变量分离：超时族回落 ⇒ CDN 定案、成功率同步恢复；不回落 ⇒ CDN 与流量一起被排除，矛头立刻转向渠道侧或 v3.4。Cost 最低（配置回切、可逆、无需发版），因此排在 Share×Lever÷Cost 的第一位。
3. **不要先做的**：回滚 v3.4（再混一个变量）、调风控（绝对量没动）、查原始报文（合规不留存，路是死的）。

5. **⚠️ 团队说法与数据冲突（四条里三条不成立）**：后端「v3.4 没碰支付链路」—— 前端就在支付通路上，JS 错误 ×5.25 且其他族 ×2.84，**该说法被数据否掉**；CDN 厂商 B「切换已完成，无异常」—— 其自身 TTFB 180→420ms（**+133%**），只是没超它自己的 SLA，**「无异常」= 「没违约」，不等于没恶化**；运维「做完就都好了」—— 与 10-13 的阶跃直接冲突；**只有风控「规则没动过」与数据一致**（0.774%→0.800%）。建议：把「无异常」一律要求附上该厂商自己的 SLA 阈值与其 TTFB 分位曲线。
6. **⚠️ 缺格恰好是定案所需**：DNS 解析时延、渠道/银行侧时延、CDN 缓存命中率与回源率、重试率 —— 这四个数正是「谁吃掉了余量」的判决数据，一个都没有，而历史值因合规截断**物理上不可补**。这是本次只能在「机制 + 量级」上定性、无法严格归因的**结构性原因**，不是分析不够努力。
7. **💡 灵感备注**：这张表最值得记住的不是 96.95%，而是 **800ms 这个没人拥有的数字**。它躺在客户端，却被前端、CDN、网关、渠道四方共同消耗；四方各自的指标都「正常」，合起来就是 3%。凡是「多个组件共享一个你没画进架构图的预算（时延/错误率/重试次数/配额）」的系统，都会长出这一类故障 —— 而它的表现形态永远是「最下游那个记录者看起来最可疑」。下一步值得做的事：把支付通路每一层的时延预算画成一张和架构图同尺寸的图，贴在变更评审的地方。
