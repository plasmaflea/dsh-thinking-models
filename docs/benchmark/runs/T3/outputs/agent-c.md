L2 逐层回溯

**轴的选择（生成式，不列举）**：取**恒等式**——一次支付成功是若干必要条件之积，且客户端可观测时延是各段的**和**：

```
P(支付成功) = P(页面/客户端可用) × P(链路可达且及时) × P(网关在预算内返回)
            × P(渠道成功) × P(风控放行) × P(账户状态正常)
客户端观测时延 ≡ CDN TTFB + 网关处理 + 回程   <   SDK 超时阈值 800ms
```

「积」的每一项都必然存在（少一项交易就不成立），「和」的每一段都必然串行——所以格子是被等号右边机械生成的，不是联想的。逐格填症状：

| 格（必要条件） | 该格故障的可观测症状 | 本题读数 | 判定 |

**层1（预算恒等式，段1=CDN）**
180 + 320 = **500ms**，阈值 800ms → 余量 **300ms**
420 + 325 = **745ms**，阈值 800ms → 余量 **55ms**
→ 余量被吃掉 245ms／300ms ＝ **82%**，p95 已达阈值的 **93.1%**。
关键验证：**总时延 p95 的平移量（+245ms）≈ CDN 段的平移量（+240ms）**。若这 240ms 与网关处理并行、或能被重试/连接复用吸收，总 p95 不会整段平移。整段平移 ⇒ 该延迟**串行叠加在客户端关键路径上，且无任何吸收**。这是「CDN 换轨 → 客户端超时」这条边的硬证据，不是相关性。

**层2（客户端阈值，硬 800ms 未变，data.md:79）**
阈值未变 ⇒ 没有自适应退避、没有降级页面 ⇒ 分布整体右移直接变成失败。端维度指纹支持这一机制而不支持「页面加载失败」：
Android 2.20%→3.90%（**+77.3%**）＞ iOS 2.00%→3.50%（**+75.0%**）＞ Web 1.30%→2.00%（**+53.8%**）。
若根因是「下单页改版把页面搞坏」，占比最高的 Web（40%，且 JS 错误主要发生在它身上）应当最差；实际 Web 最好。App 最差，正是因为它的 SDK 超时是**不可退避的硬阈值且无降级页**。
（加权自检：0.38×3.90 + 0.22×3.50 + 0.40×2.00 = 3.052% ≈ 3.05% ✓；地区 0.45×2.5+0.25×2.7+0.20×2.9+0.10×6.7 = 3.050% ✓ —— 两张表内部自洽，说明切分本身是可信的）

**层3（失败原因族，把 1.25pp 拆开）**
网关超时 0.864%→**1.790%**（+0.926pp，相对 **+107%**，占总增量 **74.1%**）
风控拒绝 0.774%→**0.800%**（+0.026pp，**2.1%**）
其他（取消/余额不足/参数错误）0.162%→**0.460%**（+0.298pp，**23.8%**）
合计 1.800→3.050（+1.250pp）✓
→ 风控「占比从 43% 掉到 26%」是**分母效应**（0.774/1.800=43%，0.800/3.050=26.2%），绝对量只涨 3.4%。这既排除了风控收紧，也说明风控团队那句「没动过」不必采信也不必反驳——它不是变量。

**层4（渠道/容量）**
网关自身 p95 只涨 1.6%（320→325），但 504 占其响应比 **9%→27%（×3）**。504 是网关对**上游渠道**的超时语义，不是网关自己慢 ⇒ 第二段预算（网关→渠道）也在被侵蚀。大促 +40%（10-10 00:00 起，data.md:37）是这一段唯一的候选侵蚀源。

**层5（时序，最容易被跳过的一格）**
10-05～10-08：98.05～98.20（切换前基线，均值 ≈98.16）
10-09～10-12：97.85 / 97.70 / 97.95 / 98.00（均值 97.875）→ 变更后立即出现 **−0.29pp**
10-13～10-15：**96.95 / 96.95 / 96.95** → 相对前一档 **−0.93pp**，且**变更清单里没有任何 10-13 的事项**
→ 时间维拆开是：**约 23% 的降幅在 10-08 就发生了，约 74% 的降幅发生在 10-12→10-13 这一级台阶上，而这一级没有对应变更记录。**

→ **类根**：支付成功率不是一个「某一段坏了」的指标，而是**一条固定时间预算（客户端 SDK 800ms／网关→渠道超时）的余量的函数**；当这条预算的多个段可以在**同一分钟、无灰度、无对照流量、且原始报文不留存**的条件下被同时改动时，余量会被多段悄悄吃掉且侵蚀量不可归因——于是只能等「成功率」这个最钝的指标报警，而它报警时余量已经只剩 55ms。这一类在结构上必然可能发生，与本次换的是哪家 CDN 无关。
　└ **个例根 1（本次主因，必要背景条件）**：10-08 20:00 CDN A→B 全站接管（含 API 域名），把客户端→网关这条**串行**路径的 p95 抬高 +240ms。**必要条件**：没有它，余量还有 300ms，大促峰值即便叠加 240ms 排队也不至于击穿 800ms。
　└ **个例根 2（本次触发条件，充分性来源）**：10-13 起大促 +40% 的峰值在同一段路径上再叠加排队（网关 504 ×3 是渠道容量饱和的指纹），把 B 区 TTFB 顶到 420ms、总时延顶到 745ms。**充分条件**：只有在余量已被压到 55ms 时，这一档峰值才足以把客户端超时批量击穿。
　└ **个例根 3（共因，非超时通道）**：同一分钟的 v3.4（下单页样式改版 + BFF 优惠券校验重写）→ JS 错误 0.4%→2.1% → 「其他」族 +0.298pp（占总增量 23.8%）。优惠券校验在支付发起前是必经步骤，「没碰支付链路」这句话在结构上不成立。
　└ **个例根 4（未闭合）**：10-12→10-13 的 −0.93pp 台阶在变更清单里无对应项。最自然的解释是「大促 +40% × 周一峰值 → 渠道容量崖」，但「10-10 就已 +40%，10-10～10-12 却只降 0.29pp」与「单纯容量饱和」不吻合，除非放量是渐进爬坡——**而 data.md 没有按天放量曲线，这一格无法闭合**。这是整份数据里最该补的一格，也直接决定「先做哪件事」（见 L3）。

L3 双根

**处置根（修本次）＝ 接下来先做的唯一一件事：对「支付 API 域名」做一次单变量、带对照的链路上回退——把该域名的边缘→回源路径恢复到原 A 结构，先切 10% 流量作对照臂，静态资源留在 B、v3.4 保持不动。**

为什么是这一件（按 Share × Lever ÷ Cost）：
- Share＝主因之一（网关超时族占总增量 74.1%，是唯一有硬算术支撑的通道：745 vs 800）
- Lever＝改配置（DNS/CDN 路由，一动即生效）
- Cost＝**一次 CDN 路由配置，分钟级，无需发版，完全可逆**——在所有候选里唯一「成本≈0 且同时是诊断和修复」的
- 它同时回答了两个互相矛盾的时间/族切分：若回退臂的 800ms 超时率随 TTFB 同步回落（TTFB p95 → ~190ms、超时族回落 ≥50%），则 10-13 台阶也归客户端路径预算（个例根 1+2 合并）；若 TTFB 回落而失败率不回落、且网关 504 占比不降，则主因是渠道容量（个例根 4 成立），立刻改扩渠道并发——**一小时内就能把两条互斥假设分开，这是任何其他动作都做不到的**。
- 读数口径（属同一件事的度量，不是第二个动作）：按「小时 × 原因族 × 端 × CDN 区（A/B）」切，不要看日均值。

为什么**不**先做别的：回滚整个 v3.4 只解释 23.8%，且会把 CDN 这个最大变量重新埋在下面；把 SDK 超时抬到 1200ms 立刻有效但需发版（App 周级）、把失败推给渠道、且让探测器变钝——它只能作为并行应急项（见挂起表）。盲扩渠道在假设未分开前可能全无效。

**消解根（灭这一类）＝ 让「一条端到端时间预算的多个段，可以在无人对照的情况下被同时改动」这种结构不可能存在。**四条约束：
① 支付关键路径（API 域名/DNS · 支付 SDK · 支付网关 · 下单页/优惠券校验）纳入**变更冻解域，同窗口单变量**；
② 任何支付路径变更必须保留 **≥1% 对照流量 ≥24h**；
③ SLO 与告警改为看**预算余量**而不是绝对 p95——余量 <150ms 即告警；
④ 建立**分段聚合**观测面（CDN TTFB／网关处理／回程／渠道 504 分开），因为合规截断原始报文后，分段聚合是唯一还能定位的观测面。
- **不可发生判据**：若这四条当时生效——(a) 240ms 与 v3.4 不可能同分钟上线，二者不会互相掩盖，归因在结构上成立；(b) 余量从 300ms 掉到 55ms 会在**当天**触发余量告警被拦住，而不是等成功率把它顶出来（本次从 10-08 到 10-13 隔了 5 天）；(c)「其他」族 +0.298pp 会被 1% 对照臂在 JS 错误 ×5.25 的同一小时抓到。→ 本类「成功率掉了、查不出是哪一段、原始报文又没留存」在结构上**不可能发生**，而不只是变少见。
- **可执行首边（从现状出发的第一步，可以很小）**：今天在发布系统里给「CDN/域名/DNS」「支付 SDK」「支付网关」「优惠券/下单」四个目录加一条 required reviewer，并把「对照臂比例」做成发布单必填项；再建一条只有 1% 分流开关的空 canary 流水线模板。
- **成本量级**：组织＋配置级，**人日级**；分段 SLO 复用现有 JS 错误上报通道与网关日志，不需要新采集端；不做架构变更 ⇒ 不触发下节的重迁移。（定量留给定式图，此处只给量级）

L4 迁移出口（因消解根产生的新问题清单）
1) **合规 × 可观测的冲突**：原始报文不留存的前提下，要论证「分段聚合／trace 摘要」落在合规范围内 → 需法务评审（**本次问题降级为其中一项**）
2) **SDK 版本生命周期**：超时阈值改为服务端下发，并建各版本 SDK 分布看板，否则硬阈值永远改不动
3) **大促成为常态**：+40% 不是一次性，容量评审必须带「余量」口径，而不是「成功率 ≥98%」
4) **冻解域 vs 迭代速度**：必须有例外流程与审批 SLA，否则冻解域会被绕过（更大的风险是绕过之后没人知道）

结论（三句话）：
1. **根源不是某个组件坏了，是一条固定时间预算被先后吃光。** 10-08 20:00 同一分钟做的两件事里，CDN A→B 全站接管把「客户端→网关」这条串行路径的 p95 从 180ms 抬到 420ms（+240ms，总时延 p95 同步整段平移 +245ms，说明无任何吸收），客户端 SDK 的 800ms 硬阈值没变，余量从 300ms 掉到 55ms；10-13 起大促 +40% 的峰值在同一段路径上再叠加排队，把余量压穿 → 网关超时族 0.864%→1.790%（相对 +107%，占总降幅 **74.1%**）。同一分钟的 v3.4（下单页改版＋优惠券校验重写，JS 错误 0.4%→2.1%）贡献了「其他」族 0.162%→0.460pp 的 +0.298pp（**23.8%**）；风控绝对量只涨 3.4%，是分母效应，不是变量。**CDN 换轨是必要条件（没有它余量够用），大促峰值是触发条件（只有余量已薄到 55ms 才足以击穿）。**
2. **之所以两周才被发现、且现在仍说不清是哪一段，是因为结构上不允许归因**：两个不可分变量同一分钟生效、没有灰度、没有留对照流量、原始报文按合规不留存，只剩「成功率」这个最钝的指标和一张不能交叉的聚合表——所以时间维上 74% 的降幅发生在 10-12→10-13 这一级**没有变更记录的台阶**上，而族维上 74% 的增量在网关超时族，两者无法相加，因为缺「按天 × 原因族」这一格。
3. **只能做一件事，就先做这件：把「支付 API 域名」单独做单变量、带 10% 对照臂的链路上回退（静态资源留 B、v3.4 不动）。** 它成本最低（一次 CDN 路由、分钟级、无需发版、完全可逆）、动的正是那条唯一的「必要背景条件」，而且一小时内就能把「客户端预算」和「渠道容量」这两条互斥假设分开，决定后面是继续切 CDN 还是扩渠道并发。**不要先把 SDK 超时抬到 1200ms 当首选项**——它要发版、把失败推给渠道、让探测器变钝，只能作并行应急。数据侧顺带必做（属同一件事的读数口径，不是第二个动作）：把已有聚合指标按「小时 × 原因族 × 端 × CDN 区」重切。
