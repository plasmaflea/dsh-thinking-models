# 支付成功率 98.20% → 96.95% 根因回溯

[🌳 林状图] 选择理由：题问「根源是什么」，是典型的因果深度未知（不是选项广度、不是数量关系），且解题方向应由时间轴+链路恒等式生成，而非联想列举。故用林状分层分类回溯法，产出林状图 + 双根（处置根／消解根）+ 挂起表。

## L0 类别判定

**主类：网络/链路时延类（树外分支）**；**共因：软件类（前端发布 + 变更治理/观测结构）**。
判据：症状**随链路与地域变化**（海外相对劣化 1.97x，国内 1.59–1.67x；TTFB p95 同跳升），且**网关服务端 p95 持平 320→325ms**——失效点不在服务内部，而在请求到达服务之前的通路。
已排除的大类：①硬件（跨端跨地域同向、无随机性、DB 无重试）；②权限/账号体系（无 ACL/令牌类错误族，三端同向）；③纯组织流程（技术侧已有可测的 TTFB/504 信号，不是"技术全正常只剩人的问题"）。
保留但降权的大类：软件类（v3.4 前端发布）——见层1 判定，上界仅 24%。

## L2 逐层回溯

### 轴（生成源：一次支付请求的必经时序，一步一格）

| 格 | 必经时序 | 该格故障的可观测症状 |
|---|---|---|
| G1 | 客户端组装与 SDK 发起 | 只有特定端/版本劣化；JS 错误上报上升；SDK 版本分布变化 |
| G2 | DNS / 边缘接入（CDN、TLS、回源） | CDN 首字节 p95 抬升；失败率随地域 RTT 分级；边缘侧 5xx |
| G3 | 网关前置（连接池、限流、排队、超时） | 504 抬升**而**后端处理 p95 不变（连接/队列耗尽，不是服务慢） |
| G4 | 网关业务处理（支付服务本身） | 服务端 p95/p99 抬升；业务错误码族变化 |
| G5 | 上游渠道（银行/清算/渠道网关） | 渠道维度错误码；渠道超时率上升 |
| G6 | 结果回传与客户端校验/展示 | 网关侧成功但客户端报失败（"静默失败"，含重复扣款风险） |

三判据自检：**可生成**＝一次支付请求必然按此序经过六跳；**正交**＝每格的症状签名互不重叠（端维度／地域-RTT／504-且-p95平／服务端 p95／渠道维度／两端结果不一致）；**可观测**＝每格均有专属指标，且本次数据能填 5/6 格。

### 逐格判定（含为什么它必然存在）

**G1 客户端 —— 共因，非主根。**
JS 错误 0.4% → **2.1%**（10-08 20:00 之后立即出现）是 v3.4 前端改版的真实伤害。但它是"立即出现、幅度有限"，不是"台阶"：10-09（JS 错误已 2.1%）成功率 97.85%，仅比 10-08 的 98.05% 低 0.20pp，落在基线波动（98.05–98.20）之内。若 JS 错误真按 1.7pp 的规模转化成支付失败，10-09 就该掉到 ~97.0，事实没有。⇒ JS 错误主要在非支付路径（样式改版），v3.4 对支付成功的实际贡献 ≈ 0–0.2pp。

**G2 DNS/边缘 —— 主根落点。**
- TTFB p95：180 → **310ms**（原 A 节点区域残量）／**420ms**（B 节点区域）。切换后 **A 残量也涨了 130ms**——说明劣化不止于 B 的 POP，同源于回源/缓存命中率（A、B 共用的源站出口）。
- 失败率增量**按基线 RTT 单调分级**：海外 3.40→6.70（**1.97x**）＞ 华南 1.80→2.90（1.61x）≈ 华北 1.70→2.70（1.59x）≈ 华东 1.50→2.50（1.67x）。这是"固定延迟增量 + 固定阈值"的典型签名：Δ 平移整个时延分布，失败概率是尾部质量，基线越靠阈值越敏感。
- 失败率增量**跨端均匀**：Android +1.70、iOS +1.50、Web +0.70pp（加权 +0.646/+0.330/+0.280 = +1.256pp）。逻辑 bug 不会按端等比；共享边缘层会（API 域名全站接管）。
- 量级粗算（⚑ 量级校验，非精确模型）：baseline 端到端 ≈ 网关 325ms + 多跳 TTFB 180ms×2 ≈ 685ms < 800ms 阈值；切换后 325 + 420×2 ≈ 1165ms ≫ 800。即使按 A 残量 310ms 也 ≈ 945ms > 800。⇒ **所有地域都必然被推过阈值**，与"全局同向劣化"完全一致。

**G3 网关前置 —— 传导机制（不是根，但解释 504 的形态）。**
网关侧 504 占其响应 9% → **27%**（3x），而网关业务 p95 320 → **325ms**（+1.6%，持平）。若 504 来自后端慢，p95 必然同步上升；p95 不动而 504 涨 3 倍，只能解释为**前置层排队/连接耗尽后快速返回 504**。该层的输入压力来自 G2。⇒ 504 是 G2 在下游的显影，不是独立根。

**G4 网关业务处理 —— 排除。** 服务端 p95 325ms、DB 慢查询（>1s）与三周前持平。支付服务本身没坏。这一格同时**否证**了三份团队说法里的"后端没碰支付链路"之外的猜测——它证明"不是支付服务算得慢了"。

**G5 上游渠道 —— 挂起（数据缺）。** 无渠道维度指标。若 504 含上游超时，则服务端 p95 应上升；实际未上升，故降权但不排除（缺数据不等于无罪）。

**G6 结果回传 —— 数据缺口，且是最关键缺口。** 本次缺"网关侧成功 / 客户端侧报失败"的对照数。这是唯一能**直接**把失效点锁在 G2 的指标（两端结果不一致 ⇒ 差异发生在网关之前的通路上）。没有它，G2 的判定只能靠地域梯度 + TTFB 的推理，不能靠直接证据。

### 用恒等式切 G4/G5 的因子（第二层轴）

恒等式：`总失败率 = 风控拒绝 + 其他业务拒绝 + 技术超时`。代入：

| 因子 | 三周前 | 本周 | Δ | 占增量 |
|---|---|---|---|---|
| 网关超时 | 0.864% | **1.790%** | **+0.926pp** | **74.1%** |
| 风控拒绝 | 0.774% | 0.800% | +0.026pp | 2.1% |
| 其他（取消/余额/参数） | 0.162% | 0.460% | +0.298pp | 23.8% |
| 合计 | 1.800% | 3.050% | +1.250pp | 100% |

- 风控绝对失败率几乎不动（+3.4%），**在量 +40% 的情况下仍平** ⇒ 数据反过来验证了风控团队的说法（三份说法里唯一被数据支持的一条）。风控不是根。
- 网关超时一户独吞 74.1%，且**整族**都落在 G2/G3 上。
- "其他" +0.298pp 是混合项：延迟导致用户等不及取消（G2 派生）＋ v3.4 的 JS 错误（G1）。故 v3.4 的**上界 = 0.298/1.250 = 23.8%**，实际按 10-09 日曲线（仅 −0.20pp）更接近 0–5%。

| 区间 | 均值 | 相对 10-05~08 基线 98.14% |

| 10-05~10-08（变更前） | **98.14%** | — |

第二台阶 −0.93pp 无变更登记 ⇒ 只能由"①负载越过已被劣化的那道坎"或"②有未登记的变更"解释。10-11/10-12（周末大促）回升到 97.95/98.00，10-13（首个大促工作日峰值）塌到 96.95 ⇒ 指向①：**G2 已被劣化 → 大促 +40% 把前置层推过拐点**。②不能排除，因为「同期变更」表是人工汇总，不含 DNS/证书/限流阈值/活动开关。

### → 类根

**类根 A（技术结构）：支付成功率是"端到端固定阈值型"指标，而支付链路里挂着一个不在我方时延预算内的边缘缓冲层。**
客户端 SDK 阈值是**硬常数 800ms**（本周仍未变），所以在阈值之前引入的任何**固定延迟增量**都不会线性劣化成功率，而是以"阈值穿越"方式**台阶式**吃掉它，且放大倍数随地域基线 RTT 单调递增。这类变更一旦全量、无灰度、无对照地实施，**必然**能把成功率打成台阶——这就是本类问题结构上必然可能发生的原因。

**类根 B（治理/观测结构）：变更不可分辨 ＋ 观测被截断到聚合层。**
两个变更同一分钟全量生效、没有灰度、没有留对照流量；原始报文按合规不留存，只剩厂商聚合指标。**可分辨性**在这套结构下被结构性摧毁 ⇒ "成功率跌了但不知道是谁"这一类问题必然无法归因，只能二分试错。本次正是如此：手上有 3 个候选变量（CDN/v3.4/PG），却没有任何一条证据能把它们分开。

```
类根 A（边缘缓冲进入时延预算）
 └ 个例根 A1  CDN A→B 全站接管（含 API 域名），TTFB +130~+240ms，且 A 残量同源抬升
    └ 个例根 A2  网关前置连接/队列在大促 +40% 下耗尽 → 504 9%→27%（p95 不动）
       └ 个例根 A3  800ms 硬阈值把上述延迟增量放大成台阶（共因/放大系数）
类根 B（可分辨性被摧毁）
 └ 个例根 B1  10-08 20:00 双变更同分钟全量、无对照 → 归因不可行
    └ 个例根 B2  观测只有聚合层 → 无法从数据侧补证
    └ 个例根 B3  v3.4 前端改版 JS 错误 0.4%→2.1%（次要，≤24%，实测 0–5%）
```

## L3 双根

### 处置根（修本次）
**只回退一个变量：把「支付 API 域名」的边缘路由切回 A / 或回源直连，按地区或 POP 先切 10–20% 作处理组，保留 80–90% 作对照组。**
理由：它是份额 74.1–97.9% 的候选（网关超时整族 + "其他"的延迟派生部分），Lever = 改配置，Cost = 一次 DNS/路由变更（分钟级、可逆、不发版、不动代码）。**不做 100% 全量翻转**——A 残量 TTFB 已 310ms、且大促流量更高，一次性全切可能更糟；分割既止血又出证据。**不同时回滚 v3.4**：大促期间回滚优惠券逻辑的业务风险高于其收益（上界 24%），而且再叠一个变量就是重复 10-08 的原罪。

### 消解根（灭这一类）
**让支付 API 在结构上不再经由第三方边缘缓冲：把 `pay-api` 子域从 CDN 摘出，走独立入口（自建 SLB/专线直连），CDN 只承载静态资源。**

| 闸门 | 判定 |
|---|---|
| ① 不可发生判据 | **满足**。若采用，CDN 侧任何 TTFB 抬升/回源拥塞/边缘 504 都**不可能**出现在支付请求的时延分布里 ⇒ "边缘变更打穿支付成功率"这一类**结构上不可能发生**（不是"变少见"）。注意：它**不能**消灭"支付成功率下跌"本身，只消灭"边缘这一类原因"。 |
| ② 可执行首边 | **满足**。DNS 上把 `pay-api` 的 CNAME 从 CDN 改为自建 SLB 直连，先按地区 10% 灰度，观察 504 与成功率。一次配置，分钟级，可逆。 |
| ③ 成本量级 | 2–5 人日（DNS+证书+WAF/限流规则迁移＋一次联调）。**隐性成本在 L4 第 1 项（失去 CDN 的 DDoS/CC 防护）**，必须与安全团队一起量。 |

> 第二个候选消解根（**仅灭"不可归因"这一类，不灭"劣化"这一类**，故单列不计入主消解根）：变更治理闸门——单窗口只允许一个变更、支付链路变更必须带灰度+对照流量、必须留"请求 ID + 各跳结果码 + 各跳时间戳"三元组（不含报文，可与合规确认）。其不可发生判据：若采用，"跌了查不出是谁"结构上不可能发生；但"跌"仍可能发生。**诚实标注：这是另一个类，不要冒充本类的消解根。**

## L4 迁移出口（因消解根产生的新问题清单）

1. **防护能力**：摘掉 CDN 后支付入口失去 CDN 的 DDoS/CC 防护 → 需自建/采购高防或云 WAF 直连（**最大单笔成本与风险**）。
2. **凭据与证书**：TLS 证书、OCSP、HSTS 策略的归属与轮换流程从 CDN 侧迁回自建；证书过期将成为新的单点。
3. **可观测性**：入口 TTFB/504 指标落点从"厂商聚合"改为自有 Nginx/网关 Prometheus，**指标口径与看板需重做**——否则下一次事故依然只有聚合值。
4. **容量**：自建入口的连接数/带宽须按大促峰值 ×1.4 预留（本次 504 的机制就是连接/队列耗尽）。
5. **组织能力**：值班流程新增"单变量变更"闸门与灰度对照纪律；10-08 的双变更成为规程修订案例。

→ **本次问题降级为：第 3 项（可观测性）与第 4 项（容量）的一个子项**，且在迁移完成前仍需一次回退止血（处置根）。没有 L4，"不解决具体问题"就是遗漏而不是策略。

## 结论

### 一、根源

**一句话：不是支付系统变慢了，是支付请求的通路被换长了——10-08 20:00 把 CDN 从 A 全站切到 B（含 API 域名），首字节 p95 从 180ms 抬到 310/420ms；客户端 SDK 的 800ms 是硬阈值，这段固定延迟增量不是线性的"变慢"，而是把一部分请求直接推过阈值变成"网关超时"；10-10 大促 +40% 再把已被劣化的边缘前置层推过拐点，于是 10-13 出现第二个、也是主要的那级台阶。**

分层表述：
- **个例根**：CDN A→B（主因，可解释增量的 **74.1%–97.9%**）。机制链：TTFB +130~240ms → 端到端越过 800ms → 网关超时 0.864%→1.790%；同时网关前置连接/队列在大促下耗尽 → 504 9%→27%（因此 504 涨 3 倍而服务端 p95 只从 320 到 325ms）。
- **共因/次要**：v3.4 前端改版（JS 错误 0.4%→2.1%，上界 24%，按日曲线实测 0–5%）。它是 10-09 那 −0.26pp 第一台阶的一部分，不是 10-13 那 −0.93pp 第二台阶的来源。
- **被数据否掉的**：风控（绝对失败率几乎不动，量 +40% 仍平——三份团队说法里唯一被数据支持的一条）、DB（慢查询持平）、支付服务本身（p95 持平）。
- **类根**（这一大类在什么结构条件下才可能发生）：①**固定阈值型指标 + 阈值前挂第三方边缘缓冲** ⇒ 边缘的任何固定延迟增量必然以台阶方式吃掉成功率，且放大倍数随地域基线 RTT 单调递增；②**变更不可分辨 + 观测截断到聚合层** ⇒ 这类问题必然无法归因，只能二分试错。第二个类根比第一个更贵：它让本次的 3 个候选变量至今无法用数据分开。

### 二、只能做一件事，就先做这个

> **对「支付 API 域名」做一次单变量分割回退：把 10–20% 的支付 API 流量（按地区/POP 选海外 + 华南，劣化最重处）从 CDN B 切回 A 或回源直连，其余 80–90% 保持不动作对照；切换前把判据写死。**

**预登记判据（切换前写下来，不许事后改）**——观察窗 60 分钟，比较处理组 vs 对照组的**网关超时绝对失败率**：
- 处理组下降 ≥0.6pp 且对照组不变 ⇒ 边缘是主根，2 小时内按地区分批全量切回，止住 74–98% 的增量。
- 处理组无变化 ⇒ 边缘被排除（**净收益：一次操作消灭最大的候选**），立刻把同一套"单变量+对照"设计套到 v3.4 回滚上。
- 处理组变差 ⇒ A 也不干净（与 A 残量 310ms 一致），方向转为"API 域名直连源站 + 查 B 的回源/缓存命中率"。

**为什么是这件事**：它是唯一同时满足 ①份额最大（74–98%）②Lever 最高（改配置，可逆，不发版）③成本最低（分钟级）④**不制造第二个混淆变量**的动作。它一次动作完成两件事——**止血**和**归因**——而 10-08 的病根恰恰是"两个变量一起动、没有对照"。

**顺手要补的（不是"另一件事"，是同一次变更的度量件）**：在网关侧加一个"请求 ID + 各跳结果码 + 各跳时间戳"的三元组对账（**不含报文**，与合规确认后即可），专门统计"网关侧成功 / 客户端侧报失败"的比例。这是唯一能把失效点直接钉在边缘而不是推理出来的指标，也是本次数据里最贵的那个缺口。

### 三、反选清单（先别做这些）

| 别做 | 原因 |
|---|---|
| 同时回滚 v3.4 | 重复 10-08 的原罪：又是一个双变量变更，归因仍然不可行；且大促期回滚优惠券逻辑的业务风险 > 其 24% 的收益上界 |
| 调高客户端 800ms 阈值 | 掩盖而非修复（暴露面扩大），且拉长"客户端已超时、服务端已扣款"的窗口 → 重复扣款风险 |
| 先等 CDN 厂商 B 出报告 | 它已说"无异常"；而聚合指标里的 TTFB 180→420ms 本身就是对这句话的反驳 |
| 先加埋点/翻日志 | 报文按合规不留存，补不上；且不产生本周收入 |
| 查风控 | 绝对失败率 0.774→0.800，数据已经否掉了 |
| 100% 一键切回 A | A 残量 TTFB 已 310ms，大促峰值下全量翻转可能比现在更差 |

## ⚠️ 异常/矛盾/空白

1. ⚠️ **10-13/14/15 三天成功率完全相同（96.95%）**。若为真实逐日值，是极强的人为/口径痕迹；更可能是"本周"聚合值被重复填入按天表。**若为后者，"三天地板"不构成"平台期"证据，我的归因不依赖平坦性**（只依赖 10-05~08 vs 10-13~15 的均值差），但请核实。
2. ⚠️ **缺按小时成功率/发起量曲线**。文档只说"按小时形态与三周前一样"，但没给数字 ⇒ "大促 +40% 触发容量拐点"这一环只能推、不能证（这也是 A2 只能判为"传导机制"而非独立根的原因）。
3. ⚠️ **缺"网关成功 / 客户端失败"对照数**。这是本次最贵的缺口——有它，G2 就是直接证据；没它，G2 只能靠地域梯度推理。
4. ⚠️ **CDN A 残量区域 TTFB 也从 180 涨到 310ms**。只按"B 坏了、回 A 即可"处理会漏掉共同的上游（回源带宽/缓存命中率）。建议在分割回退的同时拉 B 的**缓存命中率与回源 QPS**——若命中率明显低于 A，则回退后仍需改缓存策略，否则源站出口依然是大促的瓶颈。
5. ⚠️ **基线口径不可比**：三周前用的是"周均"，本周只是 10-13~15 三个工作日（且是大促 + 工作日峰值）。周内构成不同，"98.20% → 96.95%"里含一部分口径差。本报告因此尽量用 10-05~08 这段同构成时期作基线（98.14%）。
6. ⚠️ **「同期变更」表不可当作变更全集**：它不含 DNS、证书、限流阈值下调、活动开关、云厂商侧操作。所以"10-13 没有变更"应读作"没登记变更"。
7. ⚠️ **运维那句"做完就都好了"** 与数据直接矛盾：变更后 10-09~12 均值 97.88% 已低于基线 98.14%，13 日起 96.95%。这是四份团队说法中唯一**被数据明确反驳**的一条。
8. ⚠️ **归因权重的证据等级差异**：CDN 的 74–98% 是"整族归属"，其内部 504 与 800ms 超时各占多少，现有聚合数据分不开——分割回退时请按"504 占比 / 客户端超时数"两路分别统计，不要只看总成功率。

## 💡 灵感备注

- 这次事故的真正成本不在那 1.25pp，而在**"可分辨性"被同分钟双变更摧毁**：3 个候选变量（CDN/v3.4/PG）在手，却没有任何一条证据能分开它们——这正是类根 B。若只能改一条规程，我选"变更窗口单变量 + 支付链路变更必须留对照流量"，因为它把"下次能不能查出来"从运气变成必然。
- 一个可复用的判据（建议进知识树 `network` 节点）：**故障率增量按"基线 RTT 高低"分层后呈单调阶梯 ⇒ 失效点几乎必在共享的时延通路上，而不在业务逻辑里**。逻辑 bug 的增量按功能/端/版本分层；时延 bug 的增量按距离分层。本次海外 1.97x vs 国内 1.59–1.67x 就是这个签名。
- 800ms 硬阈值是个结构性债务：它把"边缘延迟 +100ms"这种小事放大成"成功率 −1pp"。长期要么让阈值由服务端下发并随地域自适应，要么把支付 API 全链路时延预算变成显式契约（SLO 化），而不是一个写死在 SDK 里的常数。
