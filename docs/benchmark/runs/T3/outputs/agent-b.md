### 层 4 ＝ 链路时延恒等式（生成式：一次支付总耗时逐项相加，硬阈值固定在末端）

`T_total = T_dns + T_tcp + T_TTFB(CDN) + T_网关 + T_retry×N + T_客户端 < 800ms`

| 串行项 | 三周前 | 本周 | 是否移动 |
|---|---|---|---|
| CDN 首字节 p95（A 残留区） | 180 ms | **310 ms** | **+130ms** |
| CDN 首字节 p95（B 区） | 180 ms | **420 ms** | **+240ms** |
| 支付网关 API p95 | 320 ms | 325 ms | 不动（+5ms） |
| 网关 504 占其响应 | 9% | **27%** | 3×（见下） |
| DB 慢查询 >1s | — | 与三周前持平 | 不动 |
| 客户端 SDK 超时阈值 | 800 ms | 800 ms | 未变（硬阈值） |

**800ms 预算账**：

| 状态 | TTFB + 网关 | 余量 | 余量占比 |
|---|---|---|---|
| 三周前 | 180+320 = **500ms** | 300ms | **37.5%** |
| 本周 A 残留 | 310+325 = **635ms** | 165ms | 20.6% |
| 本周 B | 420+325 = **745ms** | **55ms** | **6.9%** |

**判定**：唯一有量级移动的**共享**时延项就是 CDN 边缘首字节，而它恰好是每一笔支付都必须先过的一项。+240ms 落在一个 800ms 的**不可协商**阈值上，余量从 37.5% 压到 6.9%——尾部请求成批跨阈值，超时失败率 0.864%→1.790%（2.07×）在量级上**不需要第二个原因**。

**反直觉但决定性的一条**：网关侧 504 占比 9%→27%（3×），可网关自身 p95 只从 320ms 到 325ms。**若 504 是"网关等上游等到超时"，p95 必然被这些慢响应拽高；它没被拽高 ⇒ 这些 504 是快速失败或被中断**——即客户端 800ms 先到点、主动断开，网关侧记账成 504/超时中断。所以 **504 是症状不是原因**；它比成功率跌幅大 8.85×（27% ÷ 3.05%），是因为绝大多数被重试救回（0.27 × ~89% 重试成功率 ≈ 3%）。
⚠️ 结论级提醒：**"网关超时"这个名字在指错方向**。它读起来像"网关坏了"，实际是"客户端预算被上游耗光"的统一记账口径——在没有原始报文的前提下，这是最容易集体误判的一格。

### → 类根

> **支付链路被部署在"距硬超时阈值的余量 < 任一单个共享组件的时延抖动"的状态，同时分段时延不可观测（合规不留报文、厂商只给聚合 p95）时，任何单一共享时延项（CDN / 边缘 / 回源 / 重试 / TLS 握手）的抬升，都会以同一个不可分辨的症状"网关超时"出现，并以断崖方式吃掉成功率。**

  └ **个例根（本次机制）**：10-08 20:00 CDN A→B 同窗口全量切换，把 TTFB p95 从 180ms 抬到 420ms（残留 A 310ms），吃掉 800ms 客户端预算里的 240ms（余量 300→55ms）→ ①10-09 起尾部少量跨阈值（−0.28pp）；②10-10 起 +40% 大促把并发推到 B 的边缘/跨境路径不经济区；③10-13 残留 A 流量消失 + 长连接/DNS 缓存重建，全部请求落到 420ms 的 B，尾部大面积跨阈值并进入**饱和平顶**（96.95%，三日零波动）。
  └ 挂在此根之下并被排除的并列枝：v3.4、PG 13.7、风控规则、大促流量本身——见挂起表。

## L3 双根

**处置根（修本次）**：把**支付 API 域名**的调度从 B 切回 A（静态资源继续留 B），保留 5~10% 走 B 作对照。预期余量 55ms→165ms；一个动作同时完成止血与因果判定——回切后回到 ~97.9% 则主假设成立，完全不回则主假设被推翻。

**消解根（灭这一类）**：把"800ms 预算"从**隐含事实**变成**被显式记账、且带发布门禁的资产**——支付链路时延拆五段（DNS / TCP / TTFB / 网关 / 重试次数）各自上报聚合分位，任何触及支付路径的**共享组件**变更必须附"分段 p99 对照"，无对照不得进生产。

- **不可发生判据**：若当时这条门禁存在，A→B 切换会因"TTFB p95 +240ms＝客户端预算的 30%"在发布前被拦下或强制灰度——本类问题（单一共享时延项抬升 ⇒ 成功率断崖且无法定位）在结构上**不可能发生**。对比之下，回切、调高超时、加日志都只让这一类**变少见**，属于缓解不是消解。
- **可执行首边**：在客户端支付 SDK 里加 5 个时间戳（发起 / 连接完成 / 首字节 / 网关响应 / 最终结果）与重试次数，只上报**本地聚合后的分位直方图**——不含任何报文内容，天然满足合规截断要求；先只采集、不告警。
- **成本量级**：1~2 人周（SDK 打点 + 埋点管道 + 一张分段时延看板），不改网关、不改 DB；对照流量成本近零。相对本次 1.25pp × 大促两周 GMV 的损失，量级可忽略（精确定量不在此图给，交 📐 公式图）。

## L4 迁移出口（消解根指向"可观测性 + 变更门禁"这一结构变更）

1) **数据与状态**：分段直方图的上报量与大促期采样率；本地聚合窗口与幂等去重（重试会重复计数）。
2) **运行与自启**：SDK 灰度与最低版本强制——旧版本无打点，看板必须按 SDK 版本切片，否则覆盖率长期缺角。
3) **可观测性**：合规边界下的聚合埋点口径（只留分位与计数、不落请求标识），并与 CDN/网关厂商聚合指标对齐口径（当前 504 口径不明，是本次最大的判断障碍）。
4) **凭据与权限**：CDN/DNS 切换权限与业务发布窗口**强制互斥**——本次两次变更同一分钟生效，直接摧毁了归因能力。
5) **组织能力**：值班与发布评审新增"时延预算"视角；厂商切换纳入支付链路变更评审。

→ **本次问题降级为第 3 项（口径不可分辨）与第 4 项（同窗口双变更）的直接后果**，不是孤立的偶发事故。

## 结论

**根源不是"某条链路坏了"，而是"余量被吃掉了，而吃掉余量的那一项恰好在前端、且症状名字指错了方向"。** 10-08 20:00 同一分钟生效的 CDN A→B 全量切换，把支付链路上唯一全局共享的时延项（边缘首字节 p95）从 180ms 抬到 420ms；这条链路此前一直靠"距客户端 800ms 硬超时还有 300ms 余量"活着（37.5%→6.9%），余量压到 55ms 后尾部请求成批跨阈值，超时失败率翻倍（0.864%→1.790%），占本次总增量 1.250pp 的 74.1%。大促 +40% 流量与 10-13 残留 A 流量消失把它从"两级暴露"推成"三日零波动平顶"（96.95%）。后端被排除（网关 p95 320→325ms、DB 慢查询持平）、风控被排除（绝对拒绝率 1.03×，占比下降纯属分母稀释）、v3.4 只能解释"其他"族的一小部分（0.298pp 里的一部分），都解释不了四端四区等比例抬升 + 超时族 2.07× 这个指纹。

**只做一件事：把"支付 API 域名"的调度切回 A（静态资源继续留 B），保留 5~10% 走 B 作对照。** 它是唯一同时满足四个条件的动作——可逆（分钟级）、止血（余量 55→165ms）、能因果判定（回切后是否回到 ~97.9% 就是主假设的判决书）、且不需要任何新数据（在合规拿不到原始报文的前提下，这是唯一还能给出答案的实验）。反过来说，此刻最不该先做的是：调高 SDK 超时（掩盖症状 + 重复扣款风险）、去要原始报文（合规拿不到）、回滚 v3.4（时序不支持，且会同时丢掉一个还在提供对照的变量）。

## ✅ 验证

- 三族增量分解精确闭合：0.926 + 0.026 + 0.298 = **1.250pp** ＝ 3.050 − 1.800。
- 四端加权：38%×2.20+22%×2.00+40%×1.30 = **1.796%→3.052%**（增量合计 1.256pp）；四区加权 = **1.800%→3.050%**（增量合计 1.250pp）。两套独立口径都回到总量，说明分解没有遗漏隐藏维度。
- 时序分段：10-05~10-08 均 **98.1375%**（波动 0.150pp，无拐点）／10-09~10-12 均 **97.8750%**（−0.325pp）／10-13~10-15 **96.9500%**（波动 0.000pp）。拐点精确落在 10-08 20:00，量级在 10-13 放大。

## ⚠️ 异常 / 矛盾 / 空白

1. ⚠️ **断崖在 10-13，变更表里 10-13 是空的**。这是本题最大的空白：要么存在未记录的变更，要么是"跨阈值饱和"——聚合指标无法区分，已进挂起表 #7。
2. ⚠️ **96.95% 连续三天完全相同（波动 0.000pp）**。真实流量在周一/周二/周三并不相同，成功率到 0.01pp 恒定极不寻常：更像"一个固定份额的流量整段失败"（1.25pp ÷ 100% ⇒ 1.25% 流量）或"指标口径平滑/采样"，而不是负载驱动的概率漂移。这条直接影响对"平顶=饱和"的解释，需先核口径（挂起 #8）。
3. ⚠️ **网关 504 占 27%，而成功率只跌 1.25pp，相差 8.85×**。要么重试把 89% 救回来了（那就还有一条"重试策略"的隐性风险没被治理），要么 504 口径把客户端主动中断也计入。两种都指向"网关侧口径不可用"，这是本次判断最大的障碍之一。
4. ⚠️ **网关 p95 只动 5ms，却报出 27% 的 504**。逻辑上这两个数字不可能同时是"网关等上游超时"——若是真超时，p95 必然被拽高。这条矛盾是整个推理的支点，也是"504 是症状"判断的唯一硬依据。建议把"504 的耗时分布"列为下一优先取数项。
5. ⚠️ **"CDN 首字节 p95（原 A 节点区域，切换后仍有一部分请求走 A）"——切换不彻底**。这句话是 10-13 断崖最可能的解释（残留流量消失 → 全部落 B），但手头没有 B 流量占比的按天曲线，无法证实。
6. ⚠️ **大促 10-10 起量，但 10-10（97.70%）是这一段最差的一天，10-11~10-12 反而回升到 98.00%**。"量↑ ⇒ 失败↑"在这三天里不成立，说明大促不是独立驱动项，必须与"哪个路径承载"结合才有解释力。
7. ⚠️ **口径陷阱**：题面"周"＝10-05 之前的周均，"本周"＝10-13~10-15 三天。10-05~10-12 这段按天数据不在两个"周"里，容易被跳过——而"两级暴露"的全部证据都在这段里。

## 💡 灵感备注

- 这个故障的真正形态是"**预算耗尽**"而非"组件故障"：它把 37.5% 的时延余量交给一个"没有 SLO 门禁的 CDN 切换"去消耗。任何"成功率掉了"的排查，若不先把 `Σ分段时延 / 硬超时` 算成一张预算表，就一定会掉进原因族命名的陷阱里。
- 元观察：本次四个团队的说法（风控没动、B 无异常、后端没碰支付、运维两个一起做都好了）**没有一句是假话**，但合起来指向了错误答案——因为每个人都在为自己那一格辩护，而故障发生在"格与格的接缝处"（余量）。这类故障的组织学特征值得单独记一笔。
