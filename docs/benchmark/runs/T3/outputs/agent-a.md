# 支付成功率 98.2% → 96.9%：根源与首动作

**类别：网络／入口链路类（端到端时延预算被入口层吃穿），不是软件内部逻辑缺陷。**

### 层1 选轴（生成式：用**时延恒等式**切，不用联想列举）

```
T_total = T_客户端预处理 + T_入口(DNS/连接) + T_首字节(CDN) + T_网关接入 + T_应用处理 + T_下游通道 + T_回程 + T_判定

|---|---|---|---|---|

### 层2 层内回溯（进入格3）

```
CDN 厂商 A → B 全量切换（10-08 20:00，含静态资源域名 + API 域名）
   └→ B 区边缘 TTFB p95 420ms（+240ms）
        └ 注意：A 残留区也涨到 310ms（+130ms）—— 说明恶化**不只是「B 比 A 差」**，
          切换动作把回源/预热配置也一起改了（这是回切后必须复核的点，见结论）
   └→ 客户端 800ms 预算余量：300ms → 165ms(A) / 55ms(B)   ← 见下方算账
        └→ 联合尾部（TTFB 高分位 ∩ 网关高分位）穿过 800ms
             └→ 「网关超时」族失败率 0.864% → 1.790%（**2.07×**，占全部增量 **74.1%**）

算账（p95 相加不是严格上界，但余量压到 55ms 的**量级**判定足够）：

| 情形 | TTFB | 网关 | 合计 | 800ms 余量 |
|---|---|---|---|---|
| 切换前 | 180 | 320 | 500ms | **300ms** |
| 切换后（A 残留） | 310 | 325 | 635ms | 165ms |
| 切换后（B 区） | 420 | 325 | 745ms | **55ms** |

余量从 300ms 压到 55ms，超时族翻 2.07 倍——量级自洽，不是凭空解释。

### 层3 交叉验证（三处独立证据指向同一格）

1. **份额分解**：增量 1.250pp 中，超时 +0.926pp（74.1%）、其他 +0.298pp（23.8%）、风控 +0.026pp（2.1%）。主增量就是超时。
2. **地区离群**：海外 3.40%→6.70%（**1.97×**），用 **10% 的量贡献 26.4% 的增量**；而华东/华北/华南增量均匀（+1.00/+1.00/+1.10pp，1.59~1.67×）。国内**无区域结构** ⇒ 排除单区域/单 ISP 故障；海外**恰好最翻倍** ⇒ 链路 RTT 越长被吃穿越狠。
3. **端分布反向排除 v3.4**：Web（BFF 优惠券校验的主要服务对象）增幅**最低**（1.30%→2.00%，1.54×），Android/iOS 均为 1.75~1.77×。若是 BFF 优惠券重写的锅，Web 应当最重。它最轻 ⇒ v3.4 不是主根。

### → 类根

**这一类在什么结构条件下才可能发生：支付成功率由端到端时延预算决定，而该预算的最短板位于「外部入口（CDN）」；入口是可被一次性整体替换、且替换时无灰度、无对照流量、无分跳观测的单点。** 一旦入口劣化，它不会表现为「某个接口报错」，而是直接转化为「超时」这一失败族，且事后无法与同期其他变更分离。

```
└ 个例根：10-08 20:00 CDN A→B 全量切换（静态 + API 域名同分钟生效）。
          B 区 TTFB p95 420ms（+240ms）吃掉 800ms 客户端预算的余量（300→55ms），
          超时族 0.864%→1.790%（占增量 74%）；大促满量（+40%）在 10-13 周一把余量彻底吃光

```

## L3 双根

### 处置根（修本次）

**把支付 API 域名从 CDN 厂商 B 回切到厂商 A；静态资源域名与 v3.4 全部冻结不动。** 观察 24 小时。

选这个而不是「整体回切」的理由：机制上被吃穿的是 **API 往返**那一跳（静态资源慢只会影响页面打开，落在「其他」族），只切 API 域名就保住了**单一变量**——这一次终于产生了对照组。

- 若失败率回落至 ~98% ⇒ 根确认且已止血，同时拿到「B 时期 vs A 时期」的前瞻对照。
- 若不回落 ⇒ CDN API 路径被排除，v3.4 与静态资源一致性升为并列待查（此时「静态还在 B」本身就是现成对照）。

### 消解根（灭这一类）

**消除「变更不可单独归因」与「分跳证据不可回查」这两个条件的同时成立。**

- **不可发生判据**：若每个变更各自独立发布并强制 5% 对照切片，则「两个变更同一分钟生效、无灰度、无对照」在**结构上不可能**，本次这类归因问题不存在的不是「变少见」而是「问不出来」；若链路观测按跳留存聚合（客户端上报的 TTFB / 网关耗时 / 结果码三元组），则合规截断原始报文**不会**消灭可归因性——**合规要求的是不留报文，不是不留分跳耗时**。这两条任取一条成立，本类问题即不可能发生。注意这不是「加监控」：现有 `CDN 首字节 p95` 只有**一个数**、A/B 两个区域混着，本身就不够用。
- **可执行首边**：①把 CDN 域名切换与代码发布拆成两条独立发布通道，下一次任一变更先放 5% 切片、观察 24h；②客户端支付 SDK 现有的 800ms 超时事件加一个枚举字段「超时发生在哪一跳」（`connect / ttfb / gateway / complete`）——一个字段的事。
- **成本量级**：均为**人日级**（发布流程改造 + 一个埋点字段），远低于 1.25pp × 支付量持续两周的代价。精确定量交 📐 公式图，此处只给量级。

三道闸门自检：①不可发生判据 ✅（见上，是结构性而非「变少见」）②可执行首边 ✅（两条都很小）③成本量级 ✅（人日级）。

## L4 迁移出口

消解根指向的是**流程 + 可观测性**变更，故必须列出迁移问题清单：

1. **数据与状态**：分跳聚合指标的留存策略（谁写、写哪、留多久），以及与合规口径的对齐——明确哪些字段属「报文」（不留）、哪些属「指标」（必须留）。

3. **可观测性**：①客户端 SDK 超时事件的「所处跳」枚举；②CDN 侧按域名/区域拆分的 TTFB 与 5xx **归因**（现在只有一个混着 A/B 的 p95）；③要求厂商 B 提供可自行核对的原始聚合，而非「已完成，无异常」这一句话。

## 结论

**根源：10-08 20:00 那次 CDN 从厂商 A 到厂商 B 的全量切换（含 API 域名）——不是 v3.4，不是风控，不是 DB，也不是大促。**

链条是：B 区边缘 TTFB p95 从 180ms 涨到 420ms，把客户端 800ms 超时预算的余量从 300ms 压到 55ms，联合尾部穿过超时线，于是「网关超时」族失败率从 0.864% 翻到 1.790%（2.07×），单独贡献了全部增量的 **74.1%**。后端完全无辜：网关 p95 只从 320 到 325ms，DB 慢查询持平——**失败不在应用内部，而在入口**。海外加倍（1.97×）与国内三区均匀（1.58~1.67×）这个组合，把「区域故障」排除掉、把「链路长度」钉死，是最有判别力的一格。大促（+40%）不是触发器，是放大器：它把 B 的余量在 10-13 周一彻底吃光，形成第二次台阶。v3.4 是并列共因，解释「其他」族那约 24%（且其证据与 CDN 静态资源一致性混淆未分离）。

而这一切之所以两周查不出来，是因为那两个变更在同一分钟生效、没有灰度、没有对照流量，同时原始报文被合规销毁——**根落在「不可归因」这个结构上，个案只是它的一个实例。**

**只能做一件事，就先做这个：把支付 API 域名从 CDN 厂商 B 回切到厂商 A，静态资源域名与 v3.4 全部冻结不动，观察 24 小时。**

- 为什么是这一件：方向由数据唯一支持（TTFB 是唯一确定恶化的链路指标，且 B 比 A 还差 110ms；后端全平）；它是**单变量**，其余全冻结，于是这一次终于有了对照；它**同时是止血与归因**——回落即根确认，不回落即把 CDN 路径干净排除、v3.4 升级为并列待查；成本一次配置变更 + 24h，完全可逆。
- **必须盯的一个点**：不要假定回切就回到 180ms。原 A 区域本周也是 **310ms**，说明这次切换动作把回源/预热配置也一起改了。回切后若 TTFB 不回落，下一步不是加带宽，而是查回源配置——这才是真正把余量还给客户端的动作。

## ⚠️ 异常/矛盾/空白

1. **⚠️ 10-13/10-14/10-15 三天成功率完全相同，都是 96.95%**，而汇总表「本周」也写 96.95%。在 +40% 量的真实分布下三日零波动（小数点后两位一致）在统计上不合理。怀疑：（a）按周口径统一回填、（b）四舍五入到 0.05 网格、（c）采集口径在 10-13 变更。**这直接影响 10-13 那个台阶的可信度**，建议先确认这三天的数是不是独立样本。
2. **⚠️「504 占其响应比例」的分母与记录方均未定义**（data.md 未给）。是 CDN 边缘记的 504，还是支付网关上游记的 504？两种读法都指向「入口层故障」这一结论，但强度差别很大，不能当直接证据用。
3. **⚠️「网关超时」这个原因族没有定义**。它可能是（a）客户端 SDK 800ms 超时、（b）网关自身 504、（c）下游通道超时。三者指向不同的根，而 59% 的失败被记在这个未定义标签上。本案按 (a) 解读（依据：`data.md` 特意给出「客户端支付 SDK 超时阈值 800ms 未变」这个数——若客户端超时不是判据，这个数没有存在理由），但这是**推断**，应显式确认。
4. **⚠️ 团队四条说法里有一条被数据直接推翻**：CDN 厂商 B 称「切换已完成，无异常」，而 B 区 TTFB p95 从 180 涨到 **420ms**。这不是「异常」，这是 2.3× 的劣化。同时「后端只动了前端和优惠券校验」被 Web 端增幅最低这一分布侧面支持，「风控没动过」被 1.03× 支持——四句话里三句与数据相容，只有厂商 B 那句与数据冲突。
5. **⚠️ 两个观测空白格**：`T_入口`（DNS/建连/TLS）与 `T_下游通道` 在本数据中**零观测**。这不是「此处没问题」，而是「查不到」。它们占据恒等式里两格，若回切后失败率不降，这两格就是下一站。
6. **⚠️ 最便宜的补证被浪费了**：`data.md` 的 TTFB 分列了「原 A 节点区域」与「B 节点区域」，说明**切换后仍有一部分流量走 A**——这是一份现成的自然对照。但没给这两部分各自的**支付失败率**。只要一个分组查询，归因当场闭合，成本比回切更低。之所以仍推荐回切：因为它同时止血，而分组查询不止血。

## 💡 灵感备注

- 这份数据里最锋利的一条是「客户端 SDK 超时阈值 800ms（未变）」与「网关 p95 325ms（未变）」**并存**。单看任一条都看不出问题；两条一起才说明：**超时不是后端变慢造成的，是预算被前端入口吃掉的**。「某个数字没变」往往比「某个数字变差」信息量更大。
- 「原 A 节点区域也是 310ms 而非 180ms」是整份数据里最容易被跳过、但最值钱的一行：它证明这次切换的伤害**不是「B 比 A 差」**这一层，而是切换动作本身改变了回源/预热行为。只看「B 最差」就会得出「回切到 A 即可」的错误自信。
