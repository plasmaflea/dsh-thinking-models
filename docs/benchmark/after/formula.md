# 3 人 × 6 个月做「类 Notion 块编辑器 MVP」需要多少人日

> 模式：📐 公式图（经验公式质点代入法）
> 选择理由：用户要的是「估算 / 大概多少」，属于定量收敛问题。先算清「工作量函数」，再反向校验「3 人 6 个月」这个容量约束装不装得下。

---

## 0. 定义前置：先钉死问的是哪一个「人日」

「需要多少人日」在这类问题里有两种读法，差 30% 以上，必须先分开：

| 读法 | 含义 | 是否含团队开销 | 典型值 |
|---|---|---|---|
| **A. 工作量人日（effort required）** | 把这件事做完本身需要的净工作量，与人多人少无关 | 否 | 较低 |
| **B. 投入人日（burn）** | 这 3 个人 6 个月实际会烧掉的人日 | 是（会议、联调、等待、返工） | 较高，约等于日历人力 |

本回答以 **A 为主**（这才是可迁移的估算），用 **B 反向校验容量**。两者的桥就是第 3 节的效率系数 α。

另外两个必须先定的边界：
- **「MVP」= 单人可用的块编辑器**，还是**多人实时协同的块编辑器**？这是本题最大的分岔，代价差 40–80 人日（见第 8 节第 1 行）。
- **「类 Notion」= 长得像（块 + 斜杠菜单 + 拖拽）**，还是**能力像（再加 database 多视图、权限、评论、AI）**？后者不是 MVP，是 V2。

本估算采用：**单人/弱协同 + 块编辑核心 + 斜杠菜单 + 拖拽 + 页面树 + 账号持久化**，不含实时协同与 database 视图。

## 1. 切出实体：核心变量清单

| 变量 | 符号 | 角色 |
|---|---|---|
| 功能模块基线工作量 | M_i | 第 i 个模块在「无摩擦」下的净人日 |
| 模块数 | n | 分解粒度 |
| 不确定性/难度放大 | R_i | 越靠近编辑器耦合核越大 |
| 集成与协作开销率 | O | 前后端联调、接口对齐、认知同步 |
| 缓冲率 | B | 需求漂移、返工、估错 |
| 有效率 | α | 8 小时里真正产出的小时占比 |
| 团队规模 | N | = 3 |
| 日历时长 | T | = 6 月 ≈ 126 工作日 |

## 2. 定语法：被代入的经验公式（含出处与适用条件）

**主公式（工作量）**

```
E = ( Σ M_i × R_i ) × (1 + O) × (1 + B)
```

- `Σ M_i × R_i` 的分解加权思路来自**功能点分析（IFPUG FPA）**：把系统拆成可独立交付的功能单元再求和。适用条件：分解粒度到「一个人能在 1–3 周内独立做完」的层级；粒度再细收益递减，再粗误差爆炸。
- `(1 + O)`、`(1 + B)` 的乘性结构来自 **COCOMO II**（Boehm）的成本驱动因子思路——规模对工作量的贡献是超线性的，且被一组乘性因子调节。这里**不引用 COCOMO 的绝对系数 a、b**（那是通用业务系统的均值，对编辑器这种「交互密集型」系统会严重低估），只借用其「乘性驱动因子」结构。
- `O` 随人数的增长依据 **Brooks 定律（《人月神话》）**：沟通通道数 ≈ n(n−1)/2。1 人 0 条，3 人 3 条。所以 O 不为 0 且不可压缩到 0。

**辅助公式（容量校验）**

```
C = N × T × α            （可用有效人日）
可行性判据：E / C ≤ 0.85   （留 ≥15% 缓冲）
```

**辅助公式（类比校验）**

```
E ≈ E_ref × S / S_ref × K
```

取同构系统为参照：一个「单用户块编辑器 + 周边应用壳」的成熟开源实现（BlockNote / Plate / Editor.js 一类）证明**编辑器壳本身可被复用，但产品化封装（持久化、账号、部署、健壮性）不可复用**。业界同类 MVP 的公开量级普遍落在 **6–18 人月**，取中位 **11 人月 ≈ 231 人日**作为参照点。适用条件：团队对该技术栈有 1 年以上经验；新手团队需乘 1.3–1.6。

## 3. 质点化：把 3 人团队压成一个质点

### 3.1 质点模型

> 把整个团队抽象为**一个效率系数 α 的聚合生产者**，忽略其内部结构，只保留「总有效人日」这一个自由度。

### 3.2 简化假设表（显式声明）

| # | 简化假设 | 取值/形式 | 依据 | 若被推翻的影响 |
|---|---|---|---|---|
| H1 | 团队对该技术栈「中等熟练」 | 1.0× | 题目未给经验水平，取行业中位 | 新手 ×1.3~1.6；资深 ×0.8 |
| H2 | 3 人可并行、无关键路径串行阻塞 | 并行度 ≈ 0.8 | 前端/后端天然可并行，但都等设计与接口 | 若串行，E 上浮 15–25% |
| H3 | 有效率 α = 0.65~0.80 | 中位 0.72 | 会议、沟通、上下文切换、非编码活动；工程管理常见区间，**属经验假设，非实测** | α 每降 0.05，日历需求 +7% |
| H4 | 集成开销 O = 0.20~0.35 | 中位 0.27 | 3 人 = 3 条沟通通道（Brooks），前后端需接口契约 | 若后端先行、契约冻结，O 可压到 0.15 |
| H5 | 缓冲 B = 0.15~0.25 | 中位 0.20 | 编辑器类需求「用起来才知道要什么」，漂移率高 | 若需求冻结且产品方全程在场，可压到 0.10 |
| H6 | 需求范围 = 第 0 节划定的窄 MVP | — | 见第 0 节 | 加入协同/database 视图直接推翻结论 |
| H7 | 不含招聘、上手、人员流动 | — | 假设 3 人已就位 | 每有 1 人中途换，+10~15 人日 |
| H8 | 不含运维/on-call/SLA | — | MVP 阶段 | 上线后每月 +3~5 人日 |
| H9 | 复用现成编辑器框架（ProseMirror/Lexical/Slate 一类） | 已计入 M_i | 不自研编辑器内核 | 若自研内核，M 全部 ×1.8~2.5 |

**质点化的代价**：H2/H3 把「谁等谁」抹平了。真实项目里全栈兼产品的那位大概率是关键路径（既出需求又写代码），这一点在 3.3 单独补回。

### 3.3 这个团队结构的特殊项（质点无法吸收，手动加回）

3 人配置 = 1 前端 + 1 后端 + 1 全栈兼产品。

- **产品角色寄生在开发者身上**：需求梳理、原型、验收没有独立人力，只能从编码时间里挤。这不是「加 10%」，而是**抬高了 B**（自己边做边改需求，返工率天然更高）。故 B 取 0.20 而非 0.15。
- **前端是瓶颈**：块编辑器的成本 70% 在前端。1 个前端扛编辑器耦合核，后端在中期就空闲。这意味着 O 的实际形态不是「沟通开销」而是「**前端排队**」。
- **判断**：这个配置对本题**不理想但不致命**——前提是让全栈那位把「编辑器耦合核」分担掉一部分，否则前端单点会顶穿 6 个月。

## 5. 迭代：三轮收敛

| 轮次 | 修正点 | 结果 |
|---|---|---|
| R1 | 直接用中位值 | 242 人日（≈11.5 人月），但区间 145–395 过宽，不适合当答复 |
| R2 | 收窄：`高`支路里 #2（26）、#7（18）、#15（32）三项叠加意味着「编辑器内核自研 + 块类型全做 + 零经验」，与 H9、H1 冲突，按假设剔除重叠尾部；`低`支路要求「粘贴清洗与 DnD 一稿过」，与 H5 的返工率冲突 | 收敛到 **170–340 人日** |
| R3 | 用类比公式校验：中位 242 人日 ≈ 11.5 人月，落在业界同类 MVP 6–18 人月区间中部偏上；与功能点分解的 242 一致，无系统性偏移 | **收敛判据满足（两独立估法差异 < 15%）** |

**收敛结论（工作量 A 口径）**

- **点估计：约 240 人日（≈11 人月）**
- **合理区间：170–340 人日（≈8–16 人月）**，P50≈240
- 若实时协同在范围内：**250–450 人日（≈12–21 人月）**

## 6. 反向校验：3 人 × 6 个月装得下吗（投入 B 口径）

```
C = N × T × α = 3 × 126 × 0.72 = 272 有效人日
可行性判据：E / C ≤ 0.85
```

- 若 E 取点估计 240：`240 / 272 = 0.88 > 0.85` → **超载，缓冲仅 32 人日（≈1.5 周）**
- 若 E 取区间上沿 340：`340 / 272 = 1.25` → **超载 25%，必然延期或砍功能**
- 若 E 取区间下沿 170：`170 / 272 = 0.63` → 有余量，可行

**这就是本题真正的答案**：

> 3 人 6 个月的总投入是 **378 毛人日 / 约 272 有效人日**。做「块编辑器 MVP」的净工作量中位是 240 人日——**数字上勉强装得下，但没有缓冲**。也就是说：**这套配置能交出「能用的块编辑器」，交不出「像 Notion 的 MVP」**。差的那部分不是人日不够，是**范围没砍到位**。

要把 `E/C` 压到 0.85 以下，需要把 E 压到 **230 人日以内**。从第 4 节的表里，最划算的砍法是：
- 砍 #7 块类型从 10 种到 6 种（−4~6）
- 砍 #12 搜索到 V2（−5）
- 砍 #8 外部粘贴清洗到「纯文本粘贴」（−5~7）
- 砍 #11 用第三方认证（−3）
- 合计 −17~21 人日，代价可控，体验不掉档

**反过来，最不该砍的是 #2 行内富文本编辑和 #4 撤销重做**——这两项砍出来的不是「少个功能」，是「产品不成立」。

## 7. 关键判断：成本不按模块分布，按「耦合核」分布

这是本题最容易被估错的地方，单独说清：

第 2、3、4、5 项（行内富文本 / 跨块选区 / 撤销重做 / 拖拽排序）**不是一个模块清单上的四行，是一个耦合核**。它们共享同一份「文档状态 + 选区状态 + 事务历史」，任何一项做浅了，其余三项全部表现为 bug：光标跳位、撤销撤销错了、拖拽后选区丢了。

所以：
- 按模块线性加总会**系统性低估 20–30%**（这就是为什么 R2 剔除了「低」支路）；
- 这个耦合核的工期**不随人力线性缩短**——加第 2 个前端到这块上，收益很低（Brooks 定律的微观版）。3 人团队里这块实际上是 **1 个人 + 1 个偶尔帮忙**。
- **风险集中在 #2**：IME（中文输入法）与跨节点光标是编辑器类项目最常见的「看起来 3 天、实际 3 周」项。这也是为什么中位给到 18 人日而非 12。

3. **产品/设计人力是寄生在开发者身上的**，第 4 节 #14 给的 15 人日远低于一个真产品的设计投入，差额以「返工」形式在 B 里付账。

## 9. 结论

| 口径 | 数值 |
|---|---|
| **净工作量（推荐引用）** | **约 240 人日，合理区间 170–340 人日（≈8–16 人月）** |
| 3 人 6 个月的实际投入 | 378 毛人日 ≈ **272 有效人日** |
| 负载比 E/C | 240/272 ≈ **0.88**（健康线 ≤0.85）→ **略超载，无缓冲** |
| 若包含实时协同 | 250–450 人日 → **该配置必延期** |
| 该配置的现实产出 | 能交付「单用户块编辑器 MVP」；「类 Notion」需砍掉协同与 database，或用 4–5 人 / 8 个月 |

**一句话答复**：粗估 **约 240 人日（8–16 人月区间，中位 11 人月）**；3 人 6 个月总量 378 毛人日 / 272 有效人日，数字上刚够、零缓冲——**够做块编辑器，不够做 Notion**。

**建议的实际排法**（若必须 3 人 6 个月交付）：
1. 第 1 个月只做 #1 + #2 的骨架（块模型 + 行内编辑的最小闭环），先把耦合核跑通，**不要并行铺功能**；
2. 第 2–3 个月铺 #3~#9，块类型只做 6 种；
3. 第 4 个月接后端 #10/#11，前后端接口契约在第 2 个月末冻结；
4. 第 5–6 个月全量 QA + 稳定化，**预留 20% 时间只修不加**；
5. 全程把产品决策集中在每周一次 30 分钟评审，避免「边做边改」把 B 从 0.20 推到 0.40。

## 10. 假设被推翻的条件（什么时候这个估算作废）

| 触发条件 | 后果 |
|---|---|
| 要求实时多人协同 | +40~80 人日且结构性返工，区间跳到 250–450 |
| 要求包含 database 多视图 | +50~90 人日，不再是 MVP |
| 使用自研编辑器内核或纯 contenteditable 裸写 | 第 4 节 #2~#8 全部 ×1.8~2.5 |
| 团队无编辑器/富文本经验 | 整体 ×1.3~1.6 |
| 需求在开发中途大改（B 实际 > 0.4） | 上部区间破 400 人日 |
