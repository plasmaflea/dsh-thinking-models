## 三、四条结论

1. **码位明确时方法饱和**：5/5 全部命中分水岭 F2、全部把 `0xC0000142` 那一族一次性排除。d 写得最狠：「G4 … `0xC0000142` … 且**进程已存在过**（会短暂出现在任务管理器、会有退出码）——**未到达**（G3 失败即返回）」。也就是说，只要症状里出现了 SxS 文案，`142` 家族（桌面堆、注入 DLL、受限令牌）就该被整族砍掉，五份都砍对了。
2. **结论高度同质**：五份的类根几乎同一句话（「可启动性被机器全局的程序集绑定命名空间裁决，应用只声明不携带依赖」），消解根也同一句（改自包含/私有程序集）。同质化=这一题的信息结构没有给林状图留出表现空间。
3. **异常报告机制稳定触发**：五份里有四份主动报出「SxS 失败本该在 Application 日志留 `SideBySide` 条目，题面说全空，与机制矛盾」。我去查了真实日志——**它们是对的，我的题面是错的**（真实注入产生 `SideBySide` 源 Event 33，直接把缺失的 identity 五个字段印出来）。见 `injection-sxs.md` 的「追加实测」。
4. **题面难度被我做低了**：真实场景里答案是白给的（Event 33 点名）。我的题面删掉了这条最强证据，反而把一个「有唯一解」的题变成了「靠机制互斥推唯一解」的题——五份仍然全对，说明这个方向也饱和了。

## 四、对论文的直接影响

- v2/v3/v4 用的 8 因子表含「⑦ SxS 配置错误」，注入证明它**不能直接产生 `0xC0000142`**。剔掉 ⑦ 后：v2 = 6/7、v3 = 7/7、裸机 = 7/7——**after 与裸机的真因覆盖率差距被抹平**。旧数字不能再用，必须在论文里如实更正。
- 真实且可复现的盲区只剩一条：`⑧ 受限令牌 / 低完整性级别`（v2、v3 两次全 0 命中，DSH 沙箱场景里它是真根因）。
- 本轮（G3-alt）不构成「林状图的缺陷证据」，构成的是「题面饱和证据」：当症状把失败层钉死在一个码位上时，五份产物无差异，方法不可被区分。

## 五、要把难度顶上去，得改题面的**信息结构**而不是加细节

本轮已验证「加细节无用」（五份都全对）。可用的三种抬压方式：

1. **矛盾共存**：保留 Event 33，但擦掉 `publicKeyToken` 与版本只留 `could not be found`，同时在 exe 同目录放一份 `app.exe.local\` 私有程序集（内容不全）。此时「供给侧缺失」与「私有优先已生效」两条同时为真，轴与排序必须打架。
2. **两个层同时留痕**：让进程真的被创建过、留下 `0xC0000142` 形态的 WER dump，但事件日志同时又有一条 SxS 失败——逼它在「G3 没到」与「G4 到了」之间做取舍，而不是二选一。
3. **没有唯一解**：给两条互相独立、都能完整解释观测的机制（例如「清单依赖被撤」与「AppCompat shim 注入了一份坏清单」），评分改成「两条都列出且给出区分实验」才算全中，而不是命中唯一根。
