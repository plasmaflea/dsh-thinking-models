## 1. 🌳 林状图／回溯法

**选择理由**：问的是「方向怎么判、根源在哪」——未知在**因果深度**（谁导致谁）与**必要条件归属**，不在选项广度或数量关系。按流程先读知识树。

### L0 类别判定

**类别**：分布式调用链的**因果定向**问题，落在 `software` 节点的 `concurrency`（并发与时序 → 重试风暴）子层。
**判据**：①行为来自代码/配置/环境姿态，换等价环境可复现；②两个指标的联动由确定性机制（排队、超时判定、重试回注）决定，属确定性竞争，不是随机位翻转。
**已排除的大类**：
- **硬件** —— 下游机器未动，且症状跨服务一致、与负载无随机相关（排除判据来自树节点表：随机性/校验错误/温度相关均无）。
- **权限／账号体系** —— 症状是延迟分布右移，不是拒绝访问类错误码族。
**未排除、已挂起的大类**：`network`（链路层，无重传/丢包/RTT 数据）、`data-consistency`（幂等与重复执行）、`org-process`（归因流程，作为"为什么工单方向发错"的根保留）。这三个在树中均为**待建节点**，本轮登记为**树外分支**。

- **命中节点**：`software` 的 `concurrency` 格（树内定义："锁、竞态、启动顺序、**重试风暴**"；典型根："依赖未被声明/缺健康检查"；典型症状："偶发、与启动时序强相关"）。
- **本次判为不适用**：`win-service`（Windows 服务进程初始化失败、Session 0、桌面堆、SxS）——与本题的服务间延迟无关；`init`、`dependency`（DLL/符号/位数）、`quota`（句柄/桌面堆）三格——本次症状不在进程启动段。
- **树外分支（不许静默丢弃，登记进挂起表）**：
  - `network`（待建节点）——本次含"链路/中间件是否变化"一支，但无数据。
  - `data-consistency`（待建节点）——本次核心机制是"同一逻辑请求被多次执行"，需要幂等/去重判据，树内无此分类。
  - `org-process`（待建节点）——本次"方向判错并发出错误工单"的组织根。
- **v2 候选登记**：需要在 `software` 下新增子层 `observability`（口径与测量点：延迟在哪个边界测、重试率分子分母是什么、均值 vs 瞬时），理由：本题中"下游负载没变"与"重试率 11%"两个断言**都是口径依赖的**，缺这一层则同类问题无法分类。

### L2 逐层回溯

#### 轴 1（生成源：必经时序 —— 一次逻辑请求的必经段，一步一格）

| 格 | 该段在管什么 | 该格故障的可观测症状（专属） |
|---|---|---|
| G1 客户端发起 | 并发度、超时预算 T、重试策略（上限/退避/抖动/预算）、连接池容量 | 客户端侧连接池 in-use 打满、获取连接等待时间上升；重试次数分布出现同步尖峰（多实例同一秒齐发） |
| G2 传输/中间件 | LB、DNS、连接复用、keep-alive、代理缓冲 | 只有跨 AZ/跨节点子集受影响；重传、RST、连接建立时间上升 |
| G3 下游排队 | 线程池队列、连接数上限、准入控制 | **排队时间 W 上升而服务时间 S 不变**；队列深度上升；CPU 未必打满（等锁/等 IO） |
| G4 下游处理 | 自身依赖、锁竞争、GC、缓存命中率、数据分布 | **S 上升**；GC 停顿、慢查询、缓存命中率下降；与到达率无关的自身耗时变化 |
| G5 下游响应回传 | 序列化、缓冲、内核发送队列 | 下游侧观测已完成但客户端未收到；尾部出现固定阶梯（如整秒/整百毫秒） |
| G6 客户端判定 | 超时判定、错误分类、是否计入重试 | 重试率与 P(L>T) 解耦；出现非超时类重试（连接失败、5xx、幂等冲突） |
| G7 重试回注 | 重试是否带抖动/预算/去重，是否回注到 G1 | **物理到达率 > 逻辑请求率**；按 request-id 去重后执行次数 > 1；尖峰而均值不变 |

**三判据自检**：
- **正交**：G1 的根（超时改小/并发提高）不能解释 G4 的 S 上升；G4 的根不能解释 G1 的连接池等待；G7 与 G3/G4 会互相解释——这不是正交性失败，而是**回路本身**，归入同一个类根（见下）。
- **可生成**：每一格都是一次调用必然经过的物理段，不靠联想列举。
- **可观测**：每格有专属症状，且**互不重叠**（W vs S 的分解是 G3/G4 的分水岭）。
- **全空列判据**：无空格，问题仍在（现象未解释），说明轴选对、只是尚未取值。

#### 轴 2（生成源：恒等式 —— 重试率不是自变量，是延迟分布的函数）

```
r = P(L_obs > T)  +  P(非超时类可重试失败)  +  P(策略性预重试)
A（物理尝试/逻辑请求） = 1/(1-r)  [无限重试上限]   或   1 + r  [只重试一次]
下游物理到达率 = 逻辑请求率 × A
```

这条恒等式给出本轮的**核心判定原则**：

> **r 与 p99 都不是独立观测量**。r 是"延迟分布叠在超时阈值 T 上"的导出量；p99 是分布的一个点。两个导出量同时变差，**在 H1（下游变慢）、H2（重试回路）、H3（共同原因）、H4（口径变化）下都会发生**，因此不具区分力。方向必须由**恒等式的另一侧**（A 的实际值、W/S 分解、时序先后、分布形状）来定，不能由这两个数本身来定。

#### 层 2 → 类根

```
→ 类根：重试是"各客户端私有的默认值"，不是"服务端声明的有预算契约"；
        且延迟的测量点没有统一定义（客户端观测延迟 ≠ 下游服务时间）。
        只要这两条同时成立，任何一次小抖动都会进入一个方向不明的正反馈：
        延迟↑ ⇒ 超时↑ ⇒ 重试↑ ⇒ 到达率与瞬时并发↑ ⇒ 排队↑ ⇒ 延迟↑，
        而两侧各自只看得见自己那一段的单向因果，于是"谁先变"在结构上不可判定。
```

**类根的结构条件（四条，缺一即本类不可能发生）**：
1. 重试**无预算上限**（retry 量不占总请求的比例约束），且**无抖动**（多实例共享同一超时值 ⇒ 超时同时发生 ⇒ 重试同时到达）；
2. 客户端超时预算 T 与下游尾延迟没有约束关系（T 落在下游尾部分布内部）；
3. 客户端观测延迟**包含客户端自身排队**（连接池等待、事件循环阻塞、GC），但被当作"下游延迟"上报；
4. 端到端**无贯穿的 request-id / deadline**，两侧无法把"同一逻辑请求的多次物理执行"对上账。

四条中任意一条被消除，本类（"重试率与延迟互相追高、双方各自归因于对方"）即失去结构条件。

```
     └ 个例根（本次具体机制，挂在类根下，待证，按先验概率排序）
        I2 无抖动重试的同步尖峰 + 无预算   ← 与"下游负载没变"完全兼容（均值不变、瞬时并发翻倍）
        I1 客户端侧排队占满观测延迟        ← 与"下游完全无辜"完全兼容（连接池被重试占满，自我放大）
        I4 口径变化（r 的定义/分母、p99 的采样点）← 可解释全部现象
        I3 下游内部长尾真变慢（S↑，非容量）← 被"资源/发布未变"降权，但未被排除（缓存命中率、数据分布、慢查询、锁都不需要发版）
        I5 共享故障域（同机/同 DB/同 LB）  ← 共因，需拓扑核对
```

**I3 为什么不能被"资源没变、发布没有"排除**：CPU 与版本不变，与"处理时间 S 不变"不是同一句话。缓存命中率下降、数据分布变化、依赖方变慢、慢查询计划漂移、锁等待增加，都可以在**零发布、零资源变化**下让 S 上升。所以下游那句话排除的是"H1 的资源型版本"，不排除 H1 的长尾型版本。

### L3 双根

**处置根（修本次）**——按顺序，前两步只是取证，后两步才动系统：
1. **上量不上的账**：给每个逻辑请求注入 request-id（重试时复用同一 id，另加 attempt 序号），在下游日志按 id 去重统计执行次数 M 与逻辑请求数 N，直接量出**真实放大因子** A_实际 = M/N，替换掉客户端自报的 3%/11%。
2. **把延迟拆开**：客户端 span 拆为「连接池等待 + 网络 + 下游服务 S + 响应处理」；下游 span 拆为「排队 W + 处理 S」。W↑S 平 ⇒ 输入侧（G1/G7）；S↑ ⇒ 下游内部（G4）。
3. **掐回路**：客户端重试加指数退避 + 抖动（full jitter）+ **重试预算**（retry 总量 ≤ 总请求 10%），并传播端到端 deadline（下游剩余预算 = deadline − 已耗时）。
4. **改工单方向**：把「请你们优化」改成「请提供按 request-id 去重的到达率、线程池队列深度、W/S 分解，以及秒级（非分钟均值）到达率曲线」——这是把一个不可证伪的归因争论，换成一次可对账的观测交换。

**消解根（灭这一类）**：**把"重试"从各端私有默认值，改造成服务端声明、客户端受限的契约，并把延迟的测量点定义成两边同一件事**——即同时落地：①重试预算（硬上限，如 ≤10% 总请求）；②强制抖动退避；③端到端 request-id + deadline 传播；④指标双口径（逻辑请求 vs 物理尝试；W 与 S 分离；客户端观测延迟与服务端服务时间分列）；⑤超时预算按调用链分配（T 必须小于该跳的下游 SLO 尾，而不是随手一个整数）。

- **① 不可发生判据**（若当时采用，本类问题在结构上不可能发生）：重试量被硬预算约束 ⇒ 回路增益 `g = (∂到达率/∂延迟) × (∂重试量/∂超时)` 被上限截断为 `g < 1` ⇒ 任何延迟扰动都被吸收而非指数放大，"重试率与延迟互相追高"在数学上不可能自持；request-id 贯穿 ⇒ 输入侧的增量在任何一方的看板上都**可见**，于是"双方各自归因于对方"这一整类方向争议**失去藏身处**。注意：这不是让问题变少见，而是让"方向不可判定"这个状态不可能出现。
- **② 可执行首边**（从现状出发的第一步，可以很小）：在客户端拦截器（或网关）加一个 retry budget counter，默认 10%，超预算直接返回首个错误而不重试；同一个拦截器里把 request-id/attempt 头写出去。**一处代码 + 一个配置**，不触碰下游。
- **③ 成本量级**：个位数人日（2–4 人日：拦截器 0.5–1 + 头部透传 0.5 + 双口径看板 0.5–1 + 灰度与回归 1）。端到端 deadline 传播改造为**双位数人日（2–4 人周）**，可后置。量级交给 📐 公式图收敛（见 §2.4），此处只给区间。

### L4 迁移出口（因消解根产生的新问题清单）

1. **超时/预算分配**：预算耗尽时首试失败率会上升，必须重新分配每跳的 T 与 deadline；否则把"重试风暴"换成"过早失败"。
2. **幂等与去重**：request-id 只是标签，服务端还需幂等键才能保证重试语义安全（否则重复扣款/重复写入）→ 落到 `data-consistency`（待建节点）。
3. **可观测性口径**：引入"逻辑请求 / 物理尝试"双分母后，所有历史看板与告警阈值失效，需重定基线（本次问题的"11%"在旧口径下也无法与新口径比较）。
4. **组织流程**：跨团队归因需要新工单模板（必须附守恒账：去重到达率、W/S 分解、时序对齐），否则同类归因错误会以"流程"形式复现 → `org-process`（待建节点）。
5. **容量与准入**：预算化之后，下游仍需准入控制与排队上限，否则下一次的放大源可能不是重试而是批处理或定时任务（同一类根的另一条入口）。
6. **告警语义**：从"p99 超阈值"改为"p99 变化率 + 重试率变化率 + 队列深度"三联动，单指标告警在回路里必然滞后。

→ **本次问题降级为其中一项**：第 3 项（可观测性口径）。本次"方向判不出"不是独立问题，它是"两侧口径未定义"的一个实例；把口径统一后，本题将退化为"某次尾部退化的归因"，不再是"谁先变"的争论。

### 候选根排序（`Share × Lever ÷ Cost`，上下级结构，不许平铺）

| 层 | 候选根 | Share（能解释已观测现象的比例） | Lever（能不能动它） | Cost（排除它要花多少） | 排序 |
|---|---|---|---|---|---|
| **类** | 重试无预算/无抖动 + 测量点未定义（⇒ 方向结构性不可判定） | 唯一（任何方向假设都在它的结构内） | 改配置 + 改架构 | 2–4 人日 | **1** |
| 个例 | I2 同步重试尖峰（均值掩盖） | 主因（可独立解释 r↑ 与 p99↑，且兼容"负载没变"） | 改配置 | 一次日志采样（M/N 比值） | **2** |
| 个例 | I1 客户端侧排队占满观测延迟 | 主因～共因 | 改配置 + 可观测 | 一次 span 采样 | **3** |
| 个例 | I4 口径变化（r 的分母/定义、p99 采样点） | 可解释全部（无上限） | 改配置（看板） | 一次指标定义核对 | **1'**（Cost 最低，与 1 并行做） |
| 个例 | I3 下游内部长尾变慢（S↑） | 次要～主因（未被排除） | **动不了**（须对方配合） | 一次 trace 交换 + 一次对方日志 | **4** |
| 个例 | I5 共享故障域 | 共因 | 换环境 / 动不了 | 一次拓扑与同机资源核对 | **5** |

> 排序是预算的函数：Cost=「一次采样」的先做（I4、I2、I1 三者共用一轮取证即可），Cost=「一次实验」的（canary 撤压）其次，Cost=「须对方配合」的（I3）最后。若把 Cost 设为 0（预算无限），排序会退化成清单——那正是团队犯的错：**只按"听起来最像"排序，而不是按"排除它要花多少"排序**。

### 挂起表（分支／判定／依据／恢复条件）——禁止用删除代替挂起

| 分支 | 判定 | 依据 | 恢复条件（什么观测会推翻本行） |
|---|---|---|---|
| 硬件故障 | ⊥ 非根 | 下游机器未动；症状是延迟分布右移而非随机/校验错误；跨服务一致 | 出现 CRC/ECC 错误、跨进程随机失败、与温度或负载无规律相关 |
| 网络链路（**树外分支 `network`**） | ⊥ 暂挂，未排除干净 | 无重传/丢包/RTT/连接建立时间数据；题面只字未提链路变更 | p99 抬升伴随重传率或 RTT 上升；只有跨 AZ/跨节点子集受影响；连接建立时间同步上升 |
| 权限/账号体系 | ⊥ 非根 | 症状是延迟，不是 401/403 类错误码族 | 出现拒绝访问类错误码，或换同一账号交互式登录即正常 |
| 「下游发版导致」 | ⊥ 已否 | 下游声明无发布，且资源未变 | 下游变更记录含同期配置开关、feature flag、依赖升级、数据迁移（**发布 ≠ 部署**，这一支口径要重核） |
| 「下游负载没变」作为**事实** | ⊥ 判定为**口径断言，不是观测** | 未说明统计的是 CPU / 平均 QPS / 完成请求数 / 并发数；重试造成的尖峰与幽灵请求恰好在这四个口径下都不可见 | 对方提供：去重后到达率、秒级到达率曲线、线程池队列深度、并发数、W/S 分解——若全部确实不变，本行升为事实，I2 出局 |
| 「重试是延迟的被动函数」（H1） | ⊥ 判定为**未通过自洽性检验** | 用 r=3% 与 p99=200ms 反解 T<200ms；若分布整体 4.5× 上移且 T 不变，r 会跳到远超 11%（见 §2.2）。因此 H1 至少在"纯被动"形式上不成立 | 若查到 T 在本周被改小，或实测 P(L>T) 与 r 在周内逐点吻合（误差 <1pp），则 H1 可行 |
| 「只有尾部动、p50 不动」 | **待证（低成本可证）** | 由 11%×900ms 反解需要 ~10% 请求落在慢模式带（见 §2.2），这是双峰签名 | 实测 p50 也按 ~4.5× 抬升 ⇒ 双峰假设死，转"全分布上移/容量型" |
| 重试率口径（3%/11% 的定义、分母、是否含非超时重试） | ⊥ 暂挂 | 指标定义未提供 | 拿到定义后重算：若分母是"调用次数"且含非超时重试，则 11% 与延迟无关，H2 权重需下调 |
| 数据一致性 / 重复执行（**树外分支 `data-consistency`**） | ⊥ 暂挂，且是 I2 的必要条件 | 树内无此分类，本次机制核心是"同一逻辑请求被多次执行" | 实测 M/N > 1.03 且存在副作用重复 ⇒ 升为主因分支，须先解决幂等再谈预算 |
| 组织与流程（**树外分支 `org-process`**） | ⊥ 不作技术根；**作为"工单方向发错"的根保留** | 技术手段尚未查清，故不能归入"技术全正常仍由人决定" | 四项取证全部完成且互相矛盾 ⇒ 归因流程升为根 |
| 共享故障域（同机/同 DB/同 LB/同批资源池） | ⊥ 暂挂 | 无部署拓扑信息 | 发现两侧共用 DB/中间件/宿主机，且该共享件同周有负载或配置变化 |

## 2. 📐 公式图 — 定量收敛（方向判定的定量判据）

**选择理由**：§1 已定因果骨架，剩下的关键分歧是"这 4.5× 到底能不能由 +9% 的重试流量解释"。这是一个数量关系问题，交给代入法收敛。

### 2.1 经验公式与质点模型

**被代入的公式（出处与适用条件）**：
1. **重试放大因子** `A = 1/(1-r)`（无限重试上限）或 `A = 1+r`（只重试一次）。出处：AWS Builders' Library《Timeouts, Retries, and Backoff with Jitter》、gRPC/Envoy retry budget 设计文档。适用条件：重试独立同分布、无去重、每次重试都真正送达下游。
2. **M/M/1 排队等待时间** `W = ρ/(1-ρ)`（以平均服务时间为单位），`ρ = λ/μ`。出处：标准排队论（Kleinrock）。适用条件：单队列单服务台、泊松到达、指数服务时间、稳态、FCFS。

**质点模型（简化假设，必须点名）**：
- 核心变量：ρ（下游利用率）、r（重试率）、A（放大因子）、T（客户端超时）、W（排队）、S（服务时间）。
- 质点化：把整个下游压缩成**一个队列 + 一个服务台 + 固定容量 μ**；把客户端压缩成**泊松到达源 + 一个固定超时阈值**。
- **被忽略的自由度（代价清单）**：多实例与负载均衡不均匀、连接池与客户端侧排队、重试的时间相关性（无抖动导致同步尖峰 ⇒ 实际到达不是泊松，而是脉冲）、服务时间的重尾、准入控制与熔断、G5 之外的传输段。**这份忽略清单正是 §1 里 I1/I2 的概率来源**，本轮不以模型排除它们。

### 2.2 代入（第一轮）：+9% 的重试流量能解释 4.5× 的 p99 吗？

**放大因子**：

| r | A=1/(1-r)（无限重试） | A=1+r（只重试 1 次） |
|---|---|---|
| 3% | 1.031 | 1.030 |
| 11% | 1.124 | 1.110 |
| **增量** | **+9.0%** | **+8.0%** |

⇒ 若重试全部真正送达且未被去重，下游物理请求量只增加 **约 +9%**（两种口径同量级，结论不敏感）。

**M/M/1 敏感度**（λ 增加 9%，μ 不变 ⇒ ρ' = 1.09·ρ）：

| 基线 ρ₀ | ρ' | W/W₀ |
|---|---|---|
| 0.50 | 0.545 | **1.20×** |
| 0.70 | 0.763 | **1.38×** |
| 0.80 | 0.872 | **1.70×** |
| 0.90 | 0.981 | **5.73×** |

**反解阈值**：令 `[ρ'/(1-ρ')] / [ρ/(1-ρ)] = 4.5`，`ρ'=1.09ρ` ⇒
```
4.5·ρ(1-1.09ρ) = 1.09ρ(1-ρ)  ⇒  3.41 = 3.815ρ  ⇒  ρ₀ ≈ 0.89
```

**第一轮结论**：**只有当下游基线利用率 ρ₀ ≳ 0.89（贴饱和、几乎无排队余量）时，+9% 的重试流量才能解释 4.5× 的尾部放大；若 ρ₀ ≲ 0.7，+9% 最多解释 1.4×，缺口 3 倍以上必须另找原因。**（M/M/1 对 p99 比均值更敏感，故 0.89 是**偏向"能解释"的宽松阈值**；真实阈值量级 ρ₀≈0.85–0.90，误差来源见 2.1 忽略清单。）

⇒ **这就是"方向怎么判"的第一个硬判据**：去要下游的 ρ（利用率或队列深度）。ρ≈0.9 ⇒ 重试/流量可以是主因，且真正的类根是"无排队余量"；ρ≈0.5 ⇒ 重试解释不了，H1 的长尾型或 H3 才是方向。

### 2.3 代入（第二轮）：用两个数字反解分布形状（**这是本题最省成本的一击**）

用恒等式 `r = P(L > T)`（假设重试只由超时触发）：

- r=3% ⇒ T 必须落在旧分布的 **q97**，而 q99=200ms ⇒ **T < 200ms**。
- 若下游整体变慢表现为"分布按 ~4.5× 等比上移"且 T 不变，则
  `r_new = P_new(L > T) = P_old(L > T/4.5) = P_old(L > q97/4.5)`，
  即超时阈值落到了旧分布的**很低分位**（举例：若 q50≈80ms、q97≈160ms，则 T/4.5≈35ms，P_old(L>35ms) 量级在 70%–90%）⇒ r 应跳到 **60%+**，而不是 11%。
- 反过来，要让 r 停在 **11%** 且 q99=**900ms** 同时成立，只能是：**T = 新分布的 q89，且约 10% 的请求落在 [T, 900ms) 这条"慢模式带"里，同时低分位基本不动**。

**第二轮结论（可一击证伪的预测）**：现有两个数字**不支持"全分布等比上移"**（即不支持"下游整体变慢"），而支持**双峰/长尾型退化**：~89% 请求照旧快，~10% 掉进慢模式，1% 超过 900ms。

> **待证预测 P1**：p50 基本不动（±20% 以内），p90 明显上移（2 倍以上），p99 上移 4.5 倍。
> **验证成本**：一次看板取样（Cost 最低）。**P1 成立 ⇒ "下游整体变慢"死；P1 不成立（p50 也 4.5×）⇒ 转容量型，回到 2.2 的 ρ 判据。**

长尾/双峰型的机制清单（全部不需要下游发版或改资源）：重试请求与首试争抢同一连接/线程/锁；幽灵请求（客户端已超时但下游仍在执行）；缓存击穿或热点 key；慢查询计划漂移；GC 停顿叠加；某个子集调用走了退化路径。**注意其中前两项的因果方向是"重试 → 慢"，与团队结论相反。**

### 2.4 代入（第三轮）：消解根的成本量级

| 项 | 单位成本 | 量级 |
|---|---|---|
| retry budget 拦截器（含抖动退避） | 0.5–1 人日 | **个位数人日**（合计 2–4 人日） |
| request-id / attempt 头透传 | 0.5 人日 | 同上 |
| 双口径看板（逻辑请求 vs 物理尝试、W/S 分离） | 0.5–1 人日 | 同上 |
| 灰度与回归 | 1 人日 | 同上 |
| 端到端 deadline 传播 | 2–4 人周 | **双位数人日**，可后置 |

**收敛判据**：2–4 人日 ≤ 一次跨团队工单往返的沟通成本量级 ⇒ 消解根的首边**比继续争论更便宜**，应当先做。这就是"消解优于解决"在这里的定量依据。

### 2.5 无关项／被切掉的关系（负边也是结论）

- 网络重传与 RTT（未代入，缺数据）——若存在，会把 ρ 的估计抬高，2.2 的阈值需上修。
- 客户端侧排队（I1）——模型里客户端是零延迟泊松源，**这是模型最大的一处失真**，也是 I1 不能被模型排除的原因。
- 重试的时间相关性（尖峰）——泊松假设直接抹掉了 I2 的核心机制，因此 **2.2 的结论"重试只能解释 1.2–1.7×"对 I2 不构成否证**：尖峰改变的是瞬时 ρ，不是平均 λ。这正是"下游负载没变"与"重试压垮下游"能同时为真的数学位置。
- 假设被推翻的条件：若实测 `M/N > 1.5`（真实放大因子远大于 1.124），则 2.2 的"只 +9%"前提整个失效，需重算——这也正说明**必须先量 M/N 再谈方向**。

## 3. 定向流程（怎么判断方向 —— 可直接执行的四步）

| 步 | 取什么证据 | 判读（谁先变 / 谁是真因） | Cost |
|---|---|---|---|
| **① 守恒账** | 按 request-id 统计 `M/N`（下游实际执行次数 ÷ 逻辑请求数） | `M/N ≈ 1.03` ⇒ 重试没有真正变成下游负载（H1/H3 权重升）；`M/N ≈ 1.12` ⇒ 重试是纯增量（H2 成立前提）；`M/N > 1.3` ⇒ 存在幽灵请求/超额重试（H2 强证据，且下游"完成请求数没变"可解释） | 一次日志采样 |
| **② 分布形状** | p50 / p90 / p99 三点 + 客户端 span 分解（连接池等待 / 网络 / S / 处理） | p50 不动、只尾部抬 ⇒ 长尾机制（重试自伤或子集退化），不是容量型；三点同倍率 ⇒ 容量/排队型，回到 §2.2 查 ρ；**连接池等待占比高 ⇒ 方向直接反转：延迟是客户端自己的** | 一次采样 |
| **③ 时序对齐** | r 与 p99 的 10 秒级曲线，同一时间轴；下游秒级（非分钟均值）到达率与队列深度 | p99 先动且 ρ 未变 ⇒ 下游内部真变慢（S↑），H1 成立；r 先动或 <10s 内同时 ⇒ 回路（H2）；下游秒级到达率出现尖峰而分钟均值平 ⇒ **I2 定案**，"负载没变"是口径假象 | 一次看板对齐 |
| **④ 干预实验** | 10% 流量 canary：关重试 / 加预算 / 加抖动，5–10 分钟 | p99 随之回落 ⇒ 重试在因果链上（H2）；**不回落也不能立刻否定回路**——metastable failure 的定义就是触发源撤除后故障仍持续（队列/连接/线程仍卡住）。此时做一次下游实例重启：重启后立即恢复 ⇒ 仍是回路；重启后依旧 ⇒ H1/I3 | 一次实验 + 少量流量风险 |

**四个判据的组合读法（本次最可能的落点）**：
- 若 ①`M/N≈1.1` + ②`p50 不动` + ③`秒级尖峰` + ④`撤压回落` ⇒ **方向反转：重试是首因**，下游是被打的。工单应撤回。
- 若 ①`M/N≈1.0` + ②`连接池等待高` + ④`撤压不回落`（重启也不回落）⇒ **两侧都不对，根在客户端自身**（I1）。工单应撤回并改自身的超时/连接池。
- 若 ①`M/N≈1.0` + ②`三点同倍率` + ③`p99 先动` + 下游 ρ 确实未变 ⇒ **H1 成立，下游确实变慢**，但根在长尾处理（S↑），工单应改为"请提供 S 的分解与依赖延迟"，而不是笼统的"优化"。

## 4. 结论

1. **方向现在不能判，而且用这两个数永远判不出来。** r 与 p99 都是延迟分布的导出量，"同时变差"在四个方向假设下都会成立，因此团队据以定案的两个数字**不具区分力**——这是确认性检验（走形 #2）的典型形式。真正的判据只有四类：**守恒账（M/N）、分布形状（p50/p90/p99 与 W/S 分解）、时序先后、干预实验**。
2. **现有数字已经否掉了一半的团队结论。** 若重试只由超时触发，r=3% 要求 T<200ms；而分布若整体 4.5× 上移、T 不变，r 会跳到 60%+ 而非 11%。所以"下游整体变慢 ⇒ 我们被动多重试"这个**单向被动叙事至少在一个环节上不自洽**；11%×900ms 的组合更像**约 10% 请求掉进慢模式的双峰退化**（待证预测 P1：p50 不动、p90 上移、p99 4.5×）。
3. **根源（类根）不在下游，也不在"重试率"这个数上，在结构里**：重试是各客户端私有默认值而非服务端声明的有预算契约；延迟的测量点在两侧没有统一定义。这两条同时存在时，"谁先变"在结构上不可判定，于是双方必然各自把对方的行为当原因——**这是一个会反复生产"错误工单"的结构，不是一个会反复变慢的下游**。
4. **本次最可能的机制（个例根，待证）**：无抖动、无预算的重试把超时同时发生在多实例上的请求**同步回注**（瞬时并发翻倍而分钟均值不变——这就是"下游负载没变"的全部解释），或客户端自身连接池被重试占满导致观测延迟虚高（下游完全无辜）。两者都与"机器没动、发布没有"完全兼容。
5. **该做的第一件事不是继续争论，也不是让对方优化**：花 2–4 人日上 retry budget + 抖动退避 + request-id 贯穿 + 双口径看板。它比一次跨团队工单往返更便宜，且一旦落地，"重试率与延迟互相追高、双方各自归因"这类问题在结构上不可能再发生（回路增益被硬上限截断为 g<1，输入侧增量对双方可见）。
6. **工单的改法**：从"请做性能优化"改为"请提供按 request-id 去重的到达率、秒级到达率曲线、线程池队列深度、W/S 分解"。这是一个可证伪的观测交换请求，不是一个归因判决。

⚠️ **异常/矛盾/空白**
- ⚠️ **矛盾**：团队结论要求"下游变慢"，下游自报"负载/机器/发布未变"——两者在"资源型变慢"上直接冲突，团队把反例解释成推责（走形 #3 反例豁免）。冲突未被解决，只是被搁置。
- ⚠️ **空白**：缺 p50/p90（只有 p99 一个点，无法判分布形状，也就无法区分容量型与长尾型——这是本题最关键的缺失数据）；缺下游 ρ / 队列深度；缺 r 的指标定义与分母；缺 W/S 分解；缺秒级到达率；缺两侧时序对齐。每一项都是 1 次采样级成本，全部未取。
- ⚠️ **口径陷阱**：题面「下游 p99」未说明是**下游自己测的服务时间**（S 或 W+S）还是**客户端测的端到端观测延迟**（含客户端排队、含超时后的重试叠加）。若后者，这个数根本不是下游的性能指标，整道题的归因基础就是错位的——这一条必须先钉死，否则后面全部判据都建在未声明的假设上。

💡 **灵感备注**
- 本题的判定核心可以压成一句话：**"慢"和"重试"都不是自变量；能当自变量的只有"到达率的瞬时形状"和"排队的余量"。** 谁把这两个量出来，方向就自己出来了。
- "下游说负载没变"这句话在重试类故障里几乎总为真，而故障几乎总为真——因为均值不变与瞬时并发翻倍可以同时成立。**这类"双方都诚实但结论相反"的局面，通常不是有人在说谎，而是没有人在同一个量纲上说话。**
- 可复用的组织级结论：任何"我方行为是反应、对方变化是原因"的归因，都默认了自己那一侧没有输入。**在分布式系统里，唯一的天然输入就是重试。** 这条不对称是这类争论的母体。
