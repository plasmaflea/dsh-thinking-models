# 二、🌳 林状图

## L0 类别判定

**类别 = `software`（子层 `concurrency`：重试与时序）**。
判据（引自树节点 `software` v1）：① 可复现性来自代码/配置/环境姿态而非物理介质；② 失败由确定性竞争导致（此处即重试与排队的时序竞争）。
**已排除的大类**：硬件（无跨进程随机性、无 CRC/ECC 类校验症状）；网络链路（无链路变更，且 200→900ms 是**连续尾部抬升**，而链路故障呈台阶/离散症状：超时、连接重置、RTT 阶跃、丢包重传）；权限/账号（无拒绝访问类症状）；组织与流程（技术手段尚未跑过任何一次测量，组织问题此刻只能是共因、不可能是根——但「先定责后定因」的习惯会作为 L4 迁移项保留）。

## L2 逐层回溯（轴＝恒等式，**生成**而非列举）

轴的生成源写清楚，否则后面全是猜：

- **恒等式①**：`L_obs = W_客户端排队 + RTT + W_服务端排队(ρ) + S_处理 + W_退避 + (k−1)·S_再处理`
- **恒等式②**：`ρ = λ_eff / μ`，`λ_eff = λ_biz · A`，`A = 1 + r + r² + …`（多层/嵌套重试时取乘积）
- **恒等式③**：`r = P(T > τ) + P(err)`

因为 λ_biz 与 μ 被声明不变，恒等式②把可能性压死：**ρ 上升只可能来自 `A`（放大倍数）或 `τ/err`（重试触发面）**。六格 = 恒等式右边六个可独立变动的因子，每格必然存在（少一格等式不成立），各有专属症状。

**层 1 · 真实业务量 λ_biz**
症状：按 logical request 去重后的 QPS 曲线。判定：下游报的是 **attempt 级 QPS**——重试请求在 QPS 上只 +11%，很容易被当成「负载没变」。此格若真不变，则 ρ 的分子只能从 A 走。

**层 2 · 放大倍数 A = attempts / logical（★方向被这一格钉死）**
症状：同一 `idempotency key` / `trace_id` 在服务端短时间内的**重复出现次数**；3%→11% 意味着表面 A 从 ≈1.03 到 ≈1.11，但若存在**多层级联重试**（client → gateway → service A → service B 各重试 k 次），尾部真实放大是 **k 的层数次幂**（2 层各 3 次 = 9×）。判定：**在 λ_biz 与 μ 都不变的条件下，A 是唯一还能把 ρ 推上去的因子**。这是恒等式给出的、不需要叙事的结论。

**层 3 · 有效容量 μ_eff（名义 μ 不变，有效 μ 会掉）**
症状：GC 暂停、连接 churn（重试反复建连/TLS 握手吃 CPU）、锁竞争、缓存命中率下降（重试打散分片热度、破坏结果缓存）、线程池被长尾请求占满（head-of-line blocking）。判定：**注意因果方向**——μ_eff 下降本身可能就是被 A 打出来的（重试风暴 → 连接风暴 → 缓存失效 → 有效容量下降），所以「μ_eff 掉了」不能自动赦免 A。

**层 4 · 重试触发面 τ 与错误分类（★3%→11% 的直接机制）**
症状：`P(T > τ)` 与 τ 的算术关系。判定（关键，全部用题面给的数，不需要任何新数据）：
- 若 τ = 1000ms 且下游 p99 = 900ms，则 `P(T > 1s)` 只在 **0.5%~1%** 量级——解释不了 11%。**⇒「下游变慢导致重试率到 11%」在算术上不成立**，剩下约 10% 的重试必然来自非超时触发面（连接失败、5xx/429、客户端本地失败、或更短的分层 timeout）。
- 若 τ ≈ 300ms（落在 p90 附近），则 `P(T > 300ms)` 从 ~3% 涨到 >10% 可以自洽——但这说明 **τ 本来就设在正常抖动的上半段内**，任何微扰都被判成失败 ⇒ 正反馈结构 ⇒ 仍是我方配置问题。
- **两个分支都指向我方。** 这一条是本题的判决性论据。

**层 5 · 观测口径（★可以单独制造「下游无辜」的假象）**
症状：p99 是谁测的（客户端含排队与重试等待／服务端 handler 时间）；失败与重试是否计入；是否只统计成功请求。判定：**幸存者偏差**——以前 3% 的超时请求被丢弃或记成错误，现在被重试救回，以「成功但很慢」的身份落进成功延迟分布，把 p99 直接抬上去。这一格可以在「下游一点没变」的前提下独立解释可观的涨幅。

**层 6 · 阻尼（给恒等式②加时间下标才生成的一格）**
`ρ_{n+1} = λ_biz · A(r(ρ_n)) / μ`。症状：有没有 retry budget、jitter+指数退避、断路器、deadline 传播、服务端取消执行。判定：**没有阻尼 ⇒ 回路增益 >1 ⇒ 系统多稳态**。这一格决定前五格是「一次性偏移」还是「自持的新工作点」。

## → 类根

**重试在分布式系统里被当作「一等可靠性机制」管理，而没有被当作「一等负载放大器」管理。** 只要同时缺三样东西——① retry budget（重试量相对成功量的硬上限）② deadline 传播与服务端主动放弃 ③ 阈值 τ 与容量准入（背压/熔断）——则「重试产生负载 → 负载抬升延迟 → 延迟触发更多重试」这个正反馈在结构上**必然可能**发生；此时任何一次微扰都能把系统从一个工作点推到另一个工作点，而「谁先动」只取决于那次微扰，与根因无关。

**└ 个例根（本次机制）**：τ 落在延迟分布尾部内部（或被非超时错误大面积触发）＋ 存在多点/多层放大**且**没有预算与 jitter 阻尼 ⇒ 某次微扰（一次 GC、一个批任务、一次网络抖动——下游确实「什么都没变」）把工作点从 `r≈3% / p99≈200ms` 推到 `r≈11% / p99≈900ms`，此后**重试自己维持这个新工作点**。下游的「三没变」是真的：变的是**工作点**，不是他们的机器。

# 三、L3 双根

## 3.1 处置根（修本次；按成本升序执行）

1. **改写工单**（0 成本）：从「要求下游优化」改成「联合定位重试流量，请提供与 QPS 无关的资源指标」——止损政治上已经跑偏的方向。
2. **一次反向实验（Cost = 一次采样，这是唯一能一次定方向的观测）**：挑单个分片或单个客户端，把 retry 上限降到 1（或直接 retry=0）跑 10 分钟，看下游 p99 是否立刻回落。回落 ⇒ 重试是原因，结案；不回落 ⇒ 才轮到审下游。
3. **修 τ**：τ 不得落在下游延迟分布的尾部内部；取 `τ ≥ max(下游 p99.9, 我方端到端预算的一份)`，并**强制 deadline 传播**（gRPC deadline / HTTP timeout budget），让服务端对超期请求主动停止执行。
4. **加阻尼**：指数退避 + full jitter，**禁止固定间隔重试**（固定间隔 = 同步重试风暴 = thundering herd）。
5. **收窄触发面**：只对可重试错误重试（连接类、5xx、429），禁 4xx 与业务错误；禁对非幂等请求重试。
6. **关掉/降级 hedging（对冲请求）**：对冲在下游饱和时会从「降 p99」变成「加剧饱和」，是隐性放大器。
7. **幂等键 + 服务端去重**：把重试从「重复执行」降级为「重复查询」。

## 3.2 消解根（灭这一类）

**让重试成为被预算约束的负载：每一次重试必须先从 per-downstream 的重试预算池取得许可（retry budget，重试量 ≤ 成功量的固定比例），并且每个请求携带并强制执行剩余 deadline。**

- **① 不可发生判据**：有预算池 ⇒ 放大倍数 A 被**硬顶**在 `1 + budget` 以内 ⇒ 回路增益 < 1 ⇒ 「重试自激 → 跳到高延迟稳态」在结构上**不可能发生**，而不只是变少见。只有预算能给出这个性质的硬顶；任何「更好的退避/更聪明的重试」都只是把临界点推远，属于缓解。
- **② 可执行首边**：在客户端 SDK 或边车（最可能是 mesh/Envoy 的 `retry_budget`）上开一个 per-cluster 预算 = 10%，超预算直接快速失败返回。**配置级改动，可今天做。**
- **③ 成本量级**：配置级（小时～天）；若需自研预算池 + deadline 传播 + 服务端取消，属中间件改动，**数人周量级**；**不需要架构迁移**。（具体数字交 📐 公式图，本图不凭空给。）

## 3.3 L4 迁移出口（走消解根后会带来的新问题）

1. **容量与准入**：预算化之后失败率会上升 ⇒ 必须同时定 SLO/错误预算、快速失败策略与降级路径（谁先失败、怎样失败最便宜）。
2. **可观测性（本次的结构性缺口）**：必须补四个现在都不存在的指标——① 每个 logical request 的**执行次数**（trace 级去重计数）② 「客户端已取消、服务端仍在执行」的请求占比与总时长 ③ 下游 ρ/饱和度（CPU run queue、连接 churn、池等待）④ 重试**按原因分类**打点。**没有第 ④ 项，本次这种方向之争会无限重复。**
3. **幂等与语义**：重复执行窗口变小但不归零 ⇒ 需要幂等键/去重表，否则重试策略收紧后仍会漏。
4. **客户端行为一致性**：多语言 SDK / 多团队客户端的重试策略必须**集中治理**，否则预算池会被绕过（各写各的 retry loop）。
5. **组织能力**：把「先定责后定因」改成「联合定因」，否则下一次同类问题仍以同样方式误判、同样方式发工单。
6. **容量规划**：饱和边缘的系统需要留出「抖动余量」，否则任何一次微扰都会重演。

**→ 本次问题降级为**：第 2 项（可观测性缺口）与第 1 项（容量准入）的一个具体子项——「下游 p99 涨了」从「一个待分责的事故」降级为「一次缺失的重试预算与容量准入的必然产物」。

# 四、候选根排序（Share × Lever ÷ Cost：预算就是排序）

| 序 | 根 | 层级 | Share（能解释已观测现象的比例） | Lever（能不能动） | Cost（证伪代价） |
|---|---|---|---|---|---|
| 1 | **观测口径污染**（p99 幸存者偏差 / 未声明口径） | 个例 | 可能解释大部分涨幅 | 改统计（我们能改） | 一次取数 |
| 2 | **τ 落在尾部内部 / 触发面错配** | 个例 | 主因（3%→11% 的直接机制） | 改配置 | 一次采样 |
| 3 | **放大倍数 A**（多层/嵌套重试、无 jitter、hedging） | 个例 | 主因或共因 | 改配置+中间件 | 一次反向实验 |
| 4 | **下游 μ_eff 下降**（GC/churn/缓存失效/长尾占用） | 个例 | 共因，且可能由 A 引发 | 需对方配合 | 一次联合取数 |
| 5 | **我方同周变更**（H3 双果同因） | 个例 | 共因 | 我们能查 | 一次变更审计 |
| 6 | **无 retry budget / 无 deadline 传播 / 无背压**（类根） | 类 | 唯一（结构性，解释「为什么会跳变并自持」） | 改架构（小） | 数人周 |

前 3 条成本都在「一次取数/一次采样/一次实验」的量级——**在花人周之前，用一天把它们全部判死或坐实。**

# 五、方向判决表（怎么判断方向：ρ 与 A 的二维裁决）

| 下游饱和度 ρ | 放大倍数 A（去重后实测量） | 裁决 | 动作 |
|---|---|---|---|
| 低（<0.5） | ≈1.1× | 我们不是原因，**方向成立**：下游有效容量 μ_eff 掉了（查 GC/锁/依赖/连接） | 工单继续追，但要追 μ_eff 而不是「变慢」 |
| 低（<0.5） | ≫1.1×（多层/嵌套） | 双因：我们放大了但没打出饱和，延迟涨另有因 | 两边同时查，别结案 |
| 高（>0.85） | ≈1.1× | **我方是扳机**：系统本已在饱和边缘，+11% 足以打穿；下游负荷结构脆弱是共因 | 撤工单，改我方预算+准入 |
| 高（>0.85） | ≫1.1× | **自激回路确认，我方是原因** | 撤工单，执行处置根 2→3→4 |

**这是唯一能一次性定方向的判决。** 缺 ρ、缺「去重后执行次数」这两个数，任何方向结论都只能是叙事。

# 六、怎么判断方向（可执行程序 + 每步的判死条件）

| 步 | 动作 | 若…则方向反了 | 若…则方向成立 |
|---|---|---|---|
| D1 | **先钉口径**：p99 是谁测的（客户端/服务端）、含不含重试等待与排队、失败是否计入；retry 率的分母是 logical 还是 attempt；时间窗从周级换到 1 分钟 | 口径一变涨幅消失 ⇒ 先前结论就是统计假象 | 口径澄清后涨幅仍在 ⇒ 现象为真 |
| D2 | **分钟级领先/滞后**：retry 与 p99 做 lag 交叉相关，找峰值 lag；把事件标记（我方发布/配置/灰度/流量切换）画在同一时间轴上 | retry 领先 p99 ⇒ 重试是因 | p99 领先 retry 且拐点对齐我方变更 ⇒ 下游或共同因 |
| D3 | **恒等式验算**：要下游给与 QPS 无关的资源指标（CPU 利用率、run queue、连接数/churn、池等待、GC、锁等待、cancelled-but-running 总时长） | QPS 不变而饱和度上升 ⇒ A 上升，我方是原因 | QPS 与饱和度同时不变 ⇒ 只有观测口径或他们未看到的维度 |
| D4 | **反向实验**（最省钱的一刀）：单分片 retry=0 或上限 1，跑 10 分钟 | p99 立刻回落 ⇒ 放大回路确认，**结案** | p99 纹丝不动 ⇒ 才轮到审下游 |
| D5 | **幽灵负载核查**：下游按幂等键/trace 统计「同一逻辑请求被执行了几次」，并统计「客户端超时后仍在执行」的时长总和 | >1.1× 或幽灵时长显著 ⇒ 重复执行的资源浪费被量化坐实 | ≈1× ⇒ 重试未造成实际重复执行 |
| D6 | **我方变更审计**：同周客户端版本、重试/超时配置、连接池、并发度、灰度/路由权重、批大小、新业务上线、SDK 升级 | 变更时刻与两个指标拐点重合 ⇒ 双果同因（H3），两个现象都是果 | 变更清单为空 ⇒ H3 死，回 H1/H2 判决表 |

**最短判据**：D4 是唯一一步就能结案的；D1 是唯一一步可能让整道题消失的。**先做 D1 和 D4，再讨论谁的锅。**

# 八、结论

**1. 方向上大概率是反的。** 不是「下游慢了所以我多重试」，而是「我多重试所以下游看起来慢了」——或者至少是**双果同因**，而不是单向因果。三条独立理由：
- **算术**：τ=1s 而 p99=900ms 时，超时只能解释 0.5%~1% 的重试，解释不了 11% ⇒ 「下游变慢」在数量上撑不起这个重试率。
- **恒等式**：λ_biz 与 μ 被声明不变时，`ρ = λ_biz·A/μ` 里只剩 A 能动 ⇒ 延迟上升必须由放大倍数或阈值触发面解释。
- **循环论证**：`r = P(T>τ)` 与 `p99 = Q(0.99)` 是同一分布的两个读数，天然同向，用它们互相证因果等于没说。

**2. 根源在哪。**
- **类根**：重试被当作「一等可靠性机制」管理，而没有被当作「一等负载放大器」管理——缺 retry budget、缺 deadline 传播、缺阈值与容量准入的联动，于是正反馈在结构上必然可能，系统多稳态。
- **个例根**：τ 落在延迟分布尾部内部（或被非超时错误大面积触发）＋ 存在多层/多点放大且无 jitter/预算阻尼 ⇒ 一次微扰把工作点从 `3% / 200ms` 推到 `11% / 900ms`，**此后重试自己维持这个新工作点**。
- **下游说自己「什么都没变」，很可能是真的**：他们的机器确实没动，变的是系统的工作点。

**3. 一句话归因**：这不是容量问题，是**反馈回路的增益问题**。修下游的机器不解决它；给重试装上预算和 deadline 才会让这一类问题在结构上不可能发生。

**4. 立刻要做的两件事**：D1（钉死 p99 口径，可能让整道题消失）＋ D4（单分片 retry=0 跑 10 分钟，一步结案）。在拿到 ρ 与「去重后执行次数」之前，不要再用这两个数互相证明因果。

**[✅ 验证]** 本结论只使用题面给出的四个数（3%、11%、200ms、900ms）与两条自述，所有推断均为恒等式推导与算术自洽检查，未引入任何未给出的外部数据；`τ=1s` 与 `τ≈300ms` 两个分支都做了显式讨论并给出各自的推论（结论同向）。

**[⚠️ 异常/矛盾/空白]** ⚠️ ①「同一周」是周级共现，**不足以支撑任何方向判断**，但已被写成工单——动作先于测量。②「负载没变」是自述且未定义维度（QPS≠资源占用），却是整条链上唯一未验证的输入。③ p99 的口径（谁测的、含不含重试等待、失败是否计入）完全缺失，这一项可以单独制造假象。④ 11% 与 p99=900ms 的算术不自洽，团队完全没做这个检查。⑤ 缺 ρ（饱和度）与「去重后执行次数」，这两个数缺失是本次无法定方向的结构性原因。⑥ 我方同周变更清单从未被列出，而这是「双果同因」唯一入口。⑦ 树里没有「跨服务重试反馈」这一支，`software/concurrency` 只覆盖本地时序——已登记 v2 候选。

**[💡 灵感备注]** ① 这是**工作点跳变**问题而不是斜率问题：两个稳态（3%/200ms 与 11%/900ms），中间不稳定，所以现象表现为「同一周突然变」，而不是「缓慢恶化」——这也是下游坚称「什么都没变」的原因。② 「客户端已放弃、服务端仍在算」的幽灵负载，是「QPS 不变但 CPU 利用率上升」的完美解释，成本极低但几乎没人统计。③ 工单本身会固化确认偏误：一旦把责任外化，团队就不会再做能判死自己的观测。④ 反过来，如果下游也开始重试，同样的回路会在他们的下游重演——**这类问题会沿着调用链向上游逐层复制**，值得作为一条通用判据。
