## L2 逐层回溯

**选轴（生成式，不列举）**

- 主轴＝**必经时序**：一次逻辑请求必然经过 客户端出口排队 → 路径 → 下游入队 → 下游服务 → 回程 → 超时判定与重试决策（后者回到第一步）。每一步都不可跳过，故可机械生成 6 格。
- 次轴＝**恒等式**：逻辑请求延迟 = Σ over attempts（每 attempt 的分段和）；放大系数 `A = attempts / logical_request`。用来区分"每一次更慢"与"次数更多"。

### 层1（分段归因：涨出来的 700ms 记在谁账上）

| 格 | 管什么 | 该格故障的可观测症状 | 对本题的判决力 |
|---|---|---|---|
| **C1** 客户端出口排队 | 连接池/并发信号量/线程池许可 | 客户端 span 中"等连接/等许可"占主导；**请求还没出门**，故下游 QPS 不涨 | **若成立，下游「负载没变」完全为真且无辜** |
| **C2** 路径 | DNS/TLS/LB 排队/网络重传 | 单次探针 RTT 正常而业务请求慢；DNS/TLS 耗时尖峰 | single-attempt 探针可一刀切开 |
| **C3** 下游入队等待 | 下游线程池/连接/限流器/锁 | 下游"总耗时"高但"handler 内耗时"不高 | **两方口径分歧正落在此格边界** |
| **C4** 下游服务时间 | 真实计算/DB/依赖 | per-caller p99、CPU、依赖耗时上升 | 他们说"没变"若指此格，则 900ms 不在下游 |
| **C5** 回程与客户端处理 | 反序列化/GC/日志 | GC pause、日志刷盘、尾包重传 | 只在 C1–C4 全清后才有分量 |
| **C6** 重试放大（次数格） | 一次逻辑请求的 attempt 次数 | attempt 分布右移；attempt p99 ≪ 逻辑请求 p99；超时重试占比高 | 本题主嫌 |

### 层2（次数归因：是"更慢"还是"更多"）

恒等式：`A = 1/(1-r)`（无递归上限）。r: 3% → 11% ⇒ `A`: 1.031 → 1.124，即**下游总工作量只多出约 9%**。

关键推论：9% 的负载增量**单独不足以**把 p99 从 200ms 拉到 900ms（4.5×）。它只在系统已处于非线性区时才够：M/M/1 量级 `Wq ∝ ρ/(1-ρ)`，ρ 0.90→0.95 约 ×1.9，0.95→0.98 约 ×2.6，0.90→0.98 约 ×5.4。**4.5× 正是 ρ 从 ≈0.9 被推到 ≈0.97–0.98 的量级特征**（粗算、单队列近似，精确值交 📐 公式图）。

⇒ 判决：这不像"下游坏了 4.5 倍"，更像"9% 的额外负载正好压在一个增益很大的点上"。增益旋钮就是**并发上限 c（连接池/线程池/信号量）**：`ρ=(λ/μ)/c`，c 越小，同样的 9% 越致命。

补充两条机制，它们解释"为什么小增量能有大振幅"：

1. 重试不是随机抽样——被重试的正是**越过超时阈值的重尾请求**，单次最贵，等于对最贵的请求重复计费。
2. 若缺 jitter，超时是**同步**的：一批客户端同时超时、同时重试，形成脉冲。同等均值负载下，脉冲的排队代价远高于均匀负载。

### 层3（账本检验：把"下游负载没变"逼到不可能三角）

Little's law：`L = λ·W`。下游称 λ（QPS）未变、机器未动、无发布，而其 p99 涨 4.5× ⇒ 三件事**必居其一**：

1. 他们的 `W`（含排队）确实涨了 ⇒ `L`（在途并发/线程占用）必涨约 4.5×——他们只是没看这个指标；
2. p99 的**口径不同**：他们量的是 handler 内 service time，我们量的是客户端端到端（含重试），两个数根本不是一个量；
3. 那个 900ms 的观测本身有问题（分位算法/采样/分母/聚合窗口）。

⇒ **"负载没变"不是反证，是在回答另一个问题。**

顺手查我们这一侧：`retry_rate = P(L > T)` 是延迟分布的**因变量**。健康态 p99=200ms 却有 3% 基线重试，本身就异常——说明超时阈值 T 被设在延迟分布的 p97~p99 附近，或另有错误码驱动的重试路径。由此得一条硬结论：**"重试率涨了"对因果方向不携带独立信息**——它与 p99 共享同一个隐藏变量，相关系数在这里没有判决力。团队的错误正是把因变量当证据。

→ **类根**：这条链路**没有一本双方共享的端到端时间账本，也没有对重试放大的任何上限**——时间预算（超时）是每端私有的常数，重试是无预算的正反馈元件，放大倍数无一方计量。结构后果有两条：①任一初始扰动都会被环放大成"双方都能各自解释"的事件；②"方向"是跨边界量，本地账本在结构上无法承载它，归因只能靠论证，而论证在这里必然僵持。

　└ **个例根（本次机制，挂在类根下）**：T 落在分布尾部（3% 基线即证据）→ 同周某扰动（流量/尾延迟/我们自己的超时或连接池变更/发布）使分布越过 T → 重试数↑ → 对重尾请求重复计费 ＋ 无 jitter 的同步脉冲 → C1/C3 并发占用↑，c 若偏紧则 ρ 越过临界 → 排队时间非线性上升 → 更多请求越过 T → 正反馈。**这条环不需要任何一方"变坏"。**

## L3 双根

### 处置根（修本次：都是"判方向"的动作，成本极低）

- **P1 口径对齐**（一次会议＋一次采样）：把四个数分开——客户端 attempt 级 p99、逻辑请求级 p99（含重试）、下游 handler 内 p99、下游入队 p99；并要求下游把"负载没变"落到 λ / L（在途并发）/ 队列深度 / 服务时间 四个**具体数**上。
- **P2 判决性实验**（唯一能定方向的操作；因为只有拔掉环里的一个元件，才不破坏环）：
  - a) **retry-off（或 budget=1）1–5% 分片**：若我们的逻辑请求 p99 回落、且**下游 p99 同步回到 200ms** ⇒ 我们就是他们 p99 的来源，工单方向反了；若关重试后我们仍 900ms ⇒ 慢在环外（C2/C4），工单方向对，但仍须继续分解。
  - b) **single-attempt 固定速率只读探针**（绕过重试层）：探针 200ms ⇒ 下游没坏；探针 900ms ⇒ 下游真的坏了，此时工单才有证据，并附 per-hop 分解。
- **P3 查同周内部变量**：超时阈值、连接池/并发上限、发布与灰度、流量结构、jitter/backoff 是否被关、幂等性（非幂等重试会造成写放大，属树外分支 `data-consistency`）。
- **P4 拆分重试率**：按 endpoint / shard / 客户端实例 / 错误码（超时 vs 连接重置 vs 5xx）。若高度集中 ⇒ 根是某个热点切片，不是全局下游变慢。

### 消解根（灭这一类）

**给「时间预算」与「放大」一个"有主、有上限、双方共账"的控制面**：端到端 deadline 逐跳传播（传**剩余预算**，而非每跳固定常数）＋ 重试预算 token bucket（重试量 ≤ 成功量的固定比例）＋ 拥塞错误 fast-fail（503/429 + Retry-After，客户端不重试）＋ 共享放大账本（每次逻辑请求的 attempts × 各段耗时，按 caller 可 join）。

- **不可发生判据**：若预算是端到端一个数并被逐跳扣减、且重试量受 token bucket 钳制，则 ①环的增益被钳到 <1，自激在结构上不可能；②重试无法把用户可感时长延伸超过预算；③账本只有一个，"双方各持一份本地真相"在结构上不可能——归因不再需要论证。它排除的是**自激放大与归因僵局**；不排除"下游真的变慢"（后者由探针直接观测，不需要推理）。
- **可执行首边**：在客户端公用库/出口网关加两个开关——retry budget（比例上限，先取保守值）＋ 每次逻辑请求的 attempt 与分段计时指标；同时把 jitter 打开。**不改下游、不需下游配合**，当天可灰度。
- **成本量级**：预算＋SDK 指标 ≈ 2 人日；deadline 传播（改 RPC 头、厘清幂等与部分成功语义）≈ 两周；若最终走网格化统一控制面 ≈ 一到两季（进 L4）。无数据迁移。收益：把 ρ 的增益旋钮从"事故触发点"变成"可调参数"。
- **反面（登记进挂起表）**：直接"取消重试/把重试降到 0"**不是**消解根——它把放大问题转成可用性问题，不满足不可发生判据；它只能在 P2 里作为短暂诊断分片使用。

## L4 迁移出口（走向统一控制面的代价）

1. **数据与状态**：放大账本需要请求打标（caller id / logical request id）并能把 attempt 与逻辑请求 join ⇒ 采样率与存储成本、trace 保留期。
2. **运行与自启**：SDK/网格升级的兼容矩阵与回滚窗口；旧客户端无法升级的长尾。
3. **可观测性**：三口径（attempt / logical / server）改造后，**历史 p99 目标与告警阈值全部要重算**，否则新旧口径混用会造出第二批"本地为真"的假数字。
4. **凭据与权限**：per-caller 拆分要求下游暴露按调用方维度的数据与配额隔离，牵动多租户边界。
5. **组织能力**：值班与复盘改成"以账本为准"，并明确谁拥有端到端预算、谁批准 retry budget 变更。

→ **本次问题降级为**：第 3 项（口径统一）的一个实例 ＋ 第 5 项（边界责任缺判据）的一个症状。也就是说，本次不是"两个服务谁慢"，而是"缺一个跨边界时间账本"这个更大问题的第一次显形。

## 结论

1. **方向不能靠这两个数定**：`retry_rate` 是延迟分布的因变量，二者共享同一个隐藏变量与同一个正反馈环，所以"下游慢→我们多重试"与"我们重试→下游更慢"在观测上同形；判决只能靠拔环实验（retry-off 1–5% 分片 ＋ single-attempt 探针），成本各是一次配置／一个脚本。
2. **数值上更像"重试放大"**：9% 的额外负载（A: 1.031→1.124）单独拉不动 4.5×，但若并发上限偏紧把 ρ 从 ≈0.9 推到 ≈0.98，4.5× 正是该区的量级特征；且 3% 的基线重试率在 p99=200ms 时本身就说明超时阈值压在分布尾部。
3. **根源不在任何一方的服务**：在于这条链路没有一本共享的端到端时间账本、也没有对重试放大的上限，于是"方向"这个跨边界量无人拥有、无人能算，双方的本地数字都为真；那张工单只是把一个尚无判据的结论转手给了下游。先做 P1＋P2（一天量级），再谈谁该优化。

[✅ 验证] 本题无本机数据可背书，全部结论为可执行/可证伪的推断；数值仅给量级（M/M/1 单队列近似、p99 与均值同向单调），精确值应交 📐 公式图。

[⚠️ 异常/矛盾/空白]
- 题面缺三个关键数：我们的超时阈值 T、重试上限（是否递归）、下游"负载"指标到底是 λ 还是 L。三者任一都能单独改变判决。
- 「同一周」被团队当作因果证据，但它同时符合"环被扰动"与"下游变慢"两个假设，**不具区分力**。
- 「下游负载没变」必须反问是哪个指标；不问清就接受，等于把判决权交出去。
- 团队结论已先行闭环（"所以发工单"），属"假设升格为事实"的走形风险：后续若只收集支持证据（例如只看我们这边的重试日志），会稳定复现该结论。必要时用 🧪 倒推图审计。
