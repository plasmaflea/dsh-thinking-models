## L0 类别判定

**类别**：`software`（分布式交互 / 重试放大子类）。
**判据**（两条同时满足才入本节点）：① 现象由代码与配置姿态产生——重试策略、超时阈值、连接池、SDK 版本，换一台等价机器可复现；② 失败是**确定性竞争**——给定相同输入与时序（重试 × 队列饱和）必然发生，不确定的部分可归因到外部输入的时序（谁先到达），而非物理介质随机性。
**已排除的大类**：硬件故障（无 CRC/ECC、无跨进程随机性、p99 是应用层分位数不是介质错误码）；权限/账号体系（无 ACL/令牌/组成员相关症状）。
**未排除但树中无节点**：网络类（分层可达性、超时形态）、组织流程类（决策与工单流转）。二者登记为树外分支进挂起表。

### L2-A 树轴六正交子层实例化（定位可动点）

| 子层 | 本题实例化（该层在管什么） | 该格故障的可观测症状 | 判定 |
|---|---|---|---|
| `lifecycle` 生命周期控制 | 谁决定**一次 attempt** 的存亡：客户端超时后，下游是否停止计算（有无 deadline 传播 / cancel） | 下游 CPU 与线程高位、但有效吞吐不涨；"我们早返回 504 了，它还在跑" | **疑似有根**（无 cancel ⇒ 被放弃的请求继续吃掉 μ） |
| `init` 初始化 | 每次 attempt 的必经步骤：TCP 建连 / TLS 握手 / 连接池借出 | 重试原因里 connect error、握手超时占比高；建连耗时 p99 上涨 | 待验（看原因分解） |
| `dependency` 依赖解析 | 我们的依赖 = 下游 + DNS + 配置中心 + 连接池实现版本 | 明确错误码族：503 / connection refused / pool exhausted / 握手失败 | 待验 |
| `quota` 资源配额 | 客户端连接池大小、每连接并发、线程池、服务端 accept backlog | `pool exhausted`；queue_time 上涨而 process_time 不变；连接数持续爬升 | **疑似有根**（重试开新连接 → 连接膨胀 → backlog 满 → refused → 再重试，自激） |
| `concurrency` 并发与时序 | **重试风暴**（树里点名的典型根）：无 jitter 的同步重试、多层叠加 `(1+r1)(1+r2)`、超时阈值与 p99 的相对位置 | 尖峰与某个时间点/版本强相关；下游队列深度呈锯齿；重试集中在同一毫秒簇 | **主疑** |
| `config` 配置与状态 | timeout 阈值 T、max_retries、backoff/jitter 参数、retry-on-error 的错误类集合 | "改配置有效但说不出为什么"——重试率在 p99 跨过 T 时阶跃 | **主疑** |

### L2-B 换轴（恒等式生成）：ρ 的四个乘子

生成源＝**恒等式**（不是联想列举）：下游排队系统的利用率恒等式

```
ρ = λ_user · M(p99) / μ     ，其中 M(p99) = 1 + r(p99)   （r = 重试率）
p99 = g(ρ)
```

依据 Little's law（L = λW）与到达率分解：**下游看到的到达率 = 用户意图到达率 × 每次意图的平均到达次数**。右侧即四个正交因子；而 M 是 p99 的函数、p99 是 ρ 的函数 ⇒ 式子本身含回路。**环的存在，就是"方向不可判定"的数学原因。**

- **层1｜单次用户意图**：首试成功/失败/超时 —— 决定是否产生第 2 次到达。
- **层2｜每次意图的到达次数 M**：由我们的重试策略、T 与 p99 的相对位置、层数叠加决定。
- **层3｜下游利用率 ρ 与分布**：由 λ_user、M、μ 决定，并且 ρ 是**分布**不是均值——均值不变也可以局部饱和。

| 乘子 | 格 | 该格为根时的专属症状（必须可观测） | 正交性（为什么不是别的格） |
|---|---|---|---|
| λ_user | **F1 入口需求变了** | 按 caller/接口/租户拆分的**首试**到达率同期上涨；下游按"用户意图去重"的 QPS 也涨 | 不能解释"重试原因全是 connect refused" |
| M(p99) | **F2 重试乘子变了**（阈值/上限/层数/错误类集合） | 重试率按**客户端版本/配置**强分层；第 2、3 次尝试占比**先于** p99 跳变；原因以 timeout 为主 | 不能解释"首试到达率上涨"，也不能解释"单分片打满" |
| μ | **F3 下游有效能力降了**（即使没发布、没动机器） | 下游 process_time 分位数上涨，或 GC/锁等待/CPU 上涨；其**依赖与共享资源**（DB、缓存、DNS、sidecar、同机邻居、扩缩容）有变更 | 不能解释"我们客户端版本分层" |
| ρ 的分布 | **F4 负载局部化**（均值没变、局部饱和） | 下游总量不变但**单分片/单副本/单热键/单连接池**打满；p99 涨而 p50 不动；错误集中在某 key/租户 | 不能解释"全局 QPS 上涨"（F1 才会）；且这正是"下游说负载没变"的合法解释 |

**关键对齐**：F4 ＋ **记账口径**，共同解释"下游说负载没变"**完全可能是真话**。重试在下游的账上不是"新负载"，而是**同一次用户意图的重复到达**：若他们按 request_id / 用户意图去重统计，QPS 一文不变；而真实的 attempt 数、连接数、线程占用、队列深度、锁竞争都在涨。所以这句话**既不证明下游无辜，也不证明他们有问题——它只是口径不同**。若双方继续用各自口径对话，这个工单会一直来回。

### 方向判定的三条独立证据链（对「你怎么判断方向」的正面回答）

一条曲线永远判不了方向：ρ 与 M 互为函数，两边都能自圆其说。必须拿**互相独立**的证据，**两条一致才下结论**：

**链 A｜数值自洽**（成本：一次查询，最便宜，先做）
只需回答一个问题：**我们自己的 timeout 阈值 T 是多少？**
- 若 **T > 900ms**：p99 = 900ms 根本碰不到超时线，"下游变慢 → 我们多重试"**在数值上自相矛盾**，8pp 的增量必有别的来源（5xx / 连接被拒 / 连接池耗尽 / retry-on-error 的错误类集合里含非超时项）→ 方向大概率反了，或另有根源。
- 若 **T ∈ [200, 900]ms**：重试率应随 p99 跨过 T 出现**阶跃平台**（几小时内从 3% 跳到接近 P(>T)），而不是平缓爬到 11%。平滑爬升更像策略/接口分布变了，或 T 本身被改过。
- 配套一刀：把重试按**触发原因**分解（timeout / connect error / 5xx / 本地错误如 pool exhausted / 客户端主动重试）。若 timeout 占比不高，H1 当场死。

**链 B｜剂量反应**（成本：一次切片查询）
- 按 caller / 接口 / SDK 版本 / 部署批次切重试率与 p99：若 p99 随重试率**梯度单调**、且下游"总容量口径"不变 ⇒ 存在本地放大（F2/F4）。
- 时间维：分钟级对齐、同期对照（上周同日同时刻，剔除周内季节性）看**先动者**与滞后方向。注意：滞后只能**排除**、不能确立——双稳态下噪声可以先于状态跳变。
- 版本维最锋利：某 caller 上 SDK/新配置的时间点若与 retry 率跳点重合 ⇒ 触发点在我们这边（F2），下游只是被推过临界点。

**链 C｜干预实验**（成本：一次灰度，**唯一决定性证据**）
取 5% 流量（或一个接口 / 一个 caller），把重试上限压到 0 或 1、打开满 jitter、timeout 改为"由上游剩余 deadline 决定"：
- 下游 p99 在数分钟内回落到 ~200ms（下游什么都没改）⇒ **方向反转**：我们的重试在制造下游的 p99。
- 重试归零后仍 900ms ⇒ F3/F4 成立：工单方向对，但**工单内容要换成证据项**（见下）。

这一步之所以决定性：它是**切断回路**的唯一手段。相关性分析与滞后分析在双稳态系统里原则上不可判定。

**工单该怎么写**（把"请优化"换成"请给证据"）：
① attempt 级 QPS / 连接数 / 队列深度 / 线程池占用（不是 request 级）；
② server-side latency 分解为 queue_time / process_time，并给出**超时后仍在执行**的请求比例；
③ 他们自己的依赖链与共享资源（DB、缓存、DNS、sidecar、同机邻居、扩缩容事件）当周有无变更——"没发布、机器没动"只覆盖镜像与实例，**不覆盖 μ 的全部输入**；
④ 单个分片 / 热键 / 副本的饱和度（F4）。

### → 类根

**这条链路上，「超时」与「重试」的控制权被每一层**各自代持**，没有任何一层持有全链路的 deadline 与重试预算。**（与 `software` 节点类根同构：本该由应用/链路掌握的控制权被外部机制代持。）于是 ρ 与 M 互为函数、系统具有**双稳态**：低延迟低重试 与 高延迟高重试 都是稳定解。在这一结构下，"变慢"和"多重试"不是因果链的两端，而是**同一个正反馈环上的两个观测量**——任何用两条聚合曲线做方向归因的做法在原理上不可判定。团队与下游的争吵是结构的必然产物，不是沟通问题、更不是谁在甩锅。

- └ **个例根（挂在类根下，不是平行清单）**：本周发生的是一次 **metastable flip**。一个平时就常态重试 3% 的系统，等价于长期把重试当成常规容量的一部分，已经停在临界点附近——3% 不是"正常"，而是"已站在悬崖边"。一次不够大的扰动就足以把它推过临界点，之后系统自己锁在高延迟分支上不回来。**这就是"两边都说没改、现象却持续"的机制**。
- └ 个例根的可疑触发点（待链 B 定死）：某 caller 的 SDK/配置变更；无 jitter 的同步重试在某分钟形成的簇；连接池膨胀撞上 accept backlog；某热分片/单副本局部饱和。

## L3 双根

### 处置根（修本次；不动结构也能做）
1. 立刻把重试上限临时压到 1、打开 jitter，5% → 100% 灰度，观察下游 p99 是否回落（＝链 C）。**成本 < 1 人日，且它同时是判定实验。**
2. timeout 与上游剩余 deadline 对齐（先只做"每跳 timeout < 上游 deadline"这一条）。
3. 重开工单，附证据清单（attempt 级指标、queue/process 分离、超时后仍在执行比例、局部饱和度、依赖链变更）。
4. 若链 C 证明是重试自激：处置到此为止——因为它在因果上同时是消解根的第一步。

### 消解根（灭这一类）
**在链路上引入三个结构性约束，使「重试 × 延迟」的正反馈获得硬上界：**
① **重试预算 retry budget**：重试总量按"成功请求数的固定比例"发 token（业界常见 10%），token 用完即拒绝重试并**快速失败**；
② **全链路 deadline 传播**：每跳 timeout 由"上游剩余 deadline"决定，服务端在 deadline 到期或客户端断开时**取消计算**（真正释放 μ）；
③ **jitter 退避 + 重试层收敛**：退避带随机抖动；全链路只允许一层重试（SDK / gateway / service 三层叠加收敛为一层）。

- **不可发生判据**：①一生效，任何时刻下游收到的 λ ≤ λ_user × (1 + b)（b 为预算上界，**硬上界**）。于是 ρ 有硬上界，队列不会进入自激饱和区，双稳态的那个高延迟稳定解**被结构性消除**。此时系统仍可能变慢（若 μ 降或 λ_user 涨），但只会慢，**不会锁死、不会雪崩**；更关键的是——放大系数被上界钉住后，任何 p99 上涨必然可归因到 λ_user 或 μ，**"方向不可判定"这件事本身也一起消失**。满足"若当时采用它，本类问题在结构上不可能发生"，而不只是变少见。
- **可执行首边（最小第一步）**：在网关加一个全局 retry token bucket，limit = 成功请求数的 10%；先只加这一个约束，5% 灰度，观察下游 p99。它**不依赖下游任何改动**（这是它能当天执行的原因）。
- **成本量级**（交 📐 公式图定量，此处只给量级）：token bucket + jitter = 1 人日量级；每跳 timeout 与 deadline 对齐 = 数人日；全链路 deadline 传播与取消 = 2–3 人周（跨客户端/网关/下游 SDK，唯一需要对方动手的一项）；重试层收敛 = 视层数 1–2 人周。总量**不入"重写架构"量级**。

## L4 迁移出口

采用消解根会暴露/新增的问题清单：
1. **幂等与重试安全边界**：预算内的重试也只能作用于幂等操作；写操作要靠幂等键，不能靠"重试上限"兜。→ 需要接口级幂等契约清单（树中 `data-consistency` 待建节点正是缺这块）。
2. **"被预算拒绝"的语义**：token 耗尽时上游收到什么？必须是可区分错误码（overload / retry-budget-exhausted），否则调用方会当普通错误再重试一次，抵消预算。
3. **可观测性口径重建**：attempt 级指标、deadline 剩余、queue/process 分离、超时后仍在执行比例。这是永久消除"方向争论"的基础设施。
4. **真实容量暴露**：过去被 3% 常态重试"代偿"掉的那部分 μ 会消失，容量规划要重算——这也解释了为什么这类系统一旦抖动就锁死：真实容量一直不够，靠重试兜着。
5. **组织与工单流程**：把"下结论 → 发工单"改成"证据清单 → 联合定位"；明确**谁持有全链路 deadline**（现状是没人坐在这个位置上，这正是类根的组织面）。
6. **客户端库版本治理**：多层 SDK 的重试配置统一版本 + 配置中心下发，否则收敛会被下一次依赖升级打破。
7. **超时值治理**：T 从"经验固定值"改为"由 SLO 与剩余 deadline 推导"，需要一份每跳超时预算表。
→ **本次问题降级为：第 3 项（可观测性口径）＋ 第 4 项（真实容量）的子项**；它的即时处置（压重试、对齐 deadline）由消解根首边顺带完成，不再作为独立任务。

## 结论

1. **方向现在判不了，而且不是数据不够——是结构上不可判定。** `ρ = λ_user · M(p99) / μ`，M 是 p99 的函数、p99 是 ρ 的函数，系统有双稳态；"下游慢→我们多重试"与"我们多重试→下游慢"在两条聚合曲线上等价。团队从相关性直接读出方向，命中走形 #1（单一假设）/#2（确认性检验）/#5（假设升格为事实），并用发工单处理了反例（#3）。
2. **判断方向只有三条合法手段，按成本排序**：① 数值自洽——**我们自己的 timeout 阈值 T 是多少？** 若 T > 900ms，H1 当场自相矛盾；再把重试按触发原因分解。② 剂量反应——按 caller / 接口 / SDK 版本切片看梯度与时差。③ **干预实验——5% 流量把重试压到 0/1 + jitter，看下游 p99 是否在几分钟内回到 ~200ms**。只有③能确立因果，而它只要一次灰度。**顺带纠正：**"下游说负载没变"既不证明他们无辜也不证明他们撒谎——重试在下游账上是"同一意图的重复到达"，去重统计后 QPS 可以一文不变。
3. **根源不在任何一侧**：`超时与重试的控制权被每一层各自代持，没有人持有全链路 deadline 与重试预算`。因此 3% 的常态重试早已把系统钉在临界点，本周只是一次 metastable flip——这解释了"两边都没改、现象却持续"。**消解根**＝retry budget（10%）＋ deadline 传播与服务端取消 ＋ jitter 与单层重试；**首边**＝在网关加一个全局 retry token bucket（1 人日、不需下游配合、且它本身就是判定实验）。
