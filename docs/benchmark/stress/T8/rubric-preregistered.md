# T8 预注册口径 · 根是分布（不是故障）

写定时间：发题之前。跑完后不许改判定式。

## 题面（逐字，五份必须完全一致）

> 同一个镜像滚到 40 台机器上，每 3–5 天总有一两台机器上的某个 pod 反复 OOMKilled，重启就好。出问题的机器不固定，换到别的机器上，出问题的也换地方。但你查不到任何一个进程真的吃了内存，监控里内存曲线很平。根源在哪？

## 埋设

真根：内存 limit 按 **P50** 设的（容器真实峰值的分布中位数），而容器内并发度是随机的 ⇒ 这是**配置与分布的交互**，不是某个 bug、不是内存泄漏，**没有可回溯的单根**。

## 关键词表（机械计数）

| id | 判定项 | 正则 |
|---|---|---|
| K1 | 拒绝给单一根 / 声明根是分布 | `不是单一|没有单一|不是某个|分布问题|概率|随机|统计性|不是 bug|没有唯一` |
| K2 | 指出 limit 按中位/P50 设定偏低 | `P50|中位|median|上限偏低|limit 过低|按平均设|按中位设` |
| K3 | 给出改分配或压舱 | `P99|P95|压舱|balloon|余量|预留|提高 limit|上调 limit|分位数分配` |
| K4 | 反向：把内存泄漏当主因 | `内存泄漏|memory leak` |

## 判定规则（预注册，四条）

1. **主判定**：单份同时命中 K1 且 K2 ⇒ 记为「识别出结构性根」。
2. 若 **≥3/5** ⇒ 它**能**处理"根是分布"的题，此前「只能处理单根」的怀疑被削弱。
3. 若 **≤1/5** 且 **≥3/5 命中 K4** ⇒ 本题成立，记「被迫编造单根（内存泄漏）」。
4. K4 命中**不自动扣分**：泄漏不能排除，只要标成假设即可；只有"主因写成泄漏且未标待证"才算误判——这一条由人工复核，不机械判。
