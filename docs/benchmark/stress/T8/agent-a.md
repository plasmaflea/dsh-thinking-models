## 0. 定义前置：这个"根源"问的是哪一件事

题面里其实叠着两个可分辨的问题，答案不是同一个：

- **Q1 为什么被 OOMKilled** —— 谁把 cgroup 的账本占满了？
- **Q2 为什么查不到是谁占的、曲线还平** —— 为什么这次故障不可观测？

现象 X ＝ Q1 ∧ Q2。**本篇主答 Q2**，理由是：OOMKilled 本身每天在全世界发生百万次，它不反常；"OOM 了却找不到吃过内存的进程、监控曲线还平"才是 X 里唯一反常的部分。而且 Q2 的答案不是"另一条线索"，它会把 Q1 的候选域**机械地压缩到三个格子**——因为"看不见"这件事本身就在告诉你占用者落在哪个域里。

⚠️ 不做这一步的代价是：直接答 Q1 会退化成一张"内存泄漏常见原因清单"，而那正是提问者已经排除过的方向。

## L2 逐层回溯

### 层 1｜轴 = **cgroup 记账恒等式**（生成源：恒等式，按等号右边机械切）

```
memory.current(cgroup) = anon + file(含脏页/回写中) + shmem + kernel(slab/sock) + 子 cgroup
```

为什么这一步必然存在：内核判定 OOM 用的就是等号左边这一个数，所以"占满账本"的东西**必然**落在右边某一项里，没有第五种可能。这四格彼此正交（一格涨不能解释另一格涨），且每格在 `memory.stat` 里都有专属计数器 → **可观测性由恒等式本身担保**。

| 格 | 这一格在管什么 | 触限时的专属可观测症状 | 会被"看进程"的手段看见吗 |
|---|---|---|---|
| **anon** | 进程堆/栈（RSS 主体） | RSS/工作集曲线会涨，`memory.stat.anon` 涨 | ✅ 会 → 与题面矛盾 |
| **file** | page cache（读放大、写日志/大文件），含 `file_dirty` / `file_writeback` | RSS 平，`memory.stat.file` 涨；脏页回写受阻时**不可回收** | ❌ 不会 |
| **shmem** | tmpfs：`/dev/shm`、`emptyDir{medium:Memory}`、`/tmp` 若是 tmpfs、`MAP_SHARED\|ANON` | RSS 平，`df -h /dev/shm` 涨、`memory.stat.shmem` 涨；**无 swap 时不可回收** | ❌ 不会 |
| **kernel** | slab、socket 缓冲、pagetables、kernel_stack | RSS 平，`memory.stat.slab/sock` 涨；重传/连接风暴时涨 | ❌ 不会 |
| *(边界项)* **记账归属** | limit 定给谁：容器级 vs pod 级 vs 节点级；LimitRange 注入；单位/换算 | 症状：**每个容器都不超，pod 超**；或每个 pod 都不超，节点超 | ❌ 不会（这一格连"哪个进程"这个问题都问错了） |

**判定**：`anon` 格与题面直接冲突（RSS 平），按挂起表处理（不是删除）；其余四格**全部存活**，且都具备"进程级观测看不见"这个共同性质。**全空列检查：四格都不空 → 轴有效，不需要换轴。**

### 层 2｜轴 = **差异载体恒等式**（生成源：题面已知条件"同一个镜像"）

```
现象差异 = 镜像内(≡ 0，因为 40 台同一镜像) + 随行状态 + 持久状态 + 宿主条件 + 时间点
```

为什么这一步必然存在：镜像相同 ⇒ 镜像内的一切（二进制、默认配置、依赖版本）都是**常量**，常量解释不了差异，所以差异必然落在"镜像之外、随 pod 或随宿主携带"的东西上。这一步是本题最强的剪枝刀，它把"代码有 bug"直接判成非充分条件。

| 格 | 内容 | 「为什么只有 1–2 个」的专属症状 |
|---|---|---|
| **随行状态** | 分片到的数据/租户/流量比例不同 | 出问题的总是**同一类负载特征**的副本；换个副本不出问题 |
| **持久状态** | emptyDir / PVC / 节点本地文件 / shm 段 | 容器重启能好、**pod 重建才好**（或反之）；`du` 能看到残留 |
| **宿主条件** | 节点内存水位、回写能力、邻居挤占 | 症状锚定**节点**而非 pod；同 pod 换节点即好、原节点上新 pod 又坏 |
| **时间点** | 稀有事件：定时任务、证书刷新、compaction、GC、限流放开、冷启动重放 | 事件时刻**在日志里**有对应条目；与"3–5 天"这个量级吻合 |
| **观测配置差异** | 各 pod 的 limit/request 来自不同来源（模板/手工/LimitRange） | 出事 pod 的 limit 与同类 pod **数值不同**（`kubectl describe` 一眼可见） |

**关键定量推论（可观测判据，不是估算数据）**：如果占用是"匀速泄漏 × 固定 limit"的确定性过程，40 个同镜像 pod 会**近似同时**触限（同期部署 ⇒ 同期越线）。观察到的是"任何时刻只有 1–2 个、且不同步、且位置会换"，因此触发的形态是**稀有事件驱动**而非匀速积累。题面给的"3–5 天"就是这个稀有事件的到达间隔；量级约 1.5 起 / 40 pod / 4 天 ≈ **每 100 pod·天 1 起**（数量级估算，非实测）。这条推论的价值在于：它把"泄漏速率"这个方向直接降权——匀速泄漏不需要 3–5 天的随机性，它只需要一个出发时间。

### 层 3｜轴 = **证据链必经时序**（生成源：必经时序，从分配到你去查，一步一格）

为什么这一步必然存在：要回答"为什么查不到"，只能沿"证据在哪一步被销毁"这条必经路径走，没有别的路。这一层直接产出 Q2 的答案。

| 步 | 这一格发生什么 | 证据在这一格怎么没的 |
|---|---|---|
| 1 分配 | 进程/内核替进程申请内存 | 尖峰可能只有几百毫秒，**短于 15–60s 的采样周期** → 曲线被平均成"平" |
| 2 记账 | 内存记到某个 cgroup 的账本上 | 账本粒度 ≠ 进程粒度：缓存、tmpfs、socket 缓冲**不属于任何进程的 RSS** → `ps/top/应用自报指标`结构性看不见 |
| 3 触限 | `memory.current` 触到 `memory.max` | 触限本身**不产生告警**，只产生一个事件计数（`memory.events`），很多人从不采它 |
| 4 回收失败 | 内核尝试回收（drop cache / swap） | 回收失败是**静默**的；没有 swap 时 shmem 根本不可回收，`anon` 也只能靠 OOM 收场 |
| 5 选 victim | 内核在**越限的那个 cgroup 内**挑一个进程杀 | **被杀者 ≠ 占用者**：victim 常是最末端的分配者/分数最高者，它可能只占了一小部分 → 你看到"被杀的进程没有大内存" |
| 6 kill + 重建 | SIGKILL（exit 137），kubelet 立刻重建容器 | **现场自毁**：等你去 `ps` 时，那个进程连同它占的内存**已经不存在了**。这一格是"查不到"的字面含义 |
| 7 你去查 | 事后取证 | 只剩 `lastState.reason=OOMKilled` 一个标签，和一条 1 分钟粒度的平均曲线 |

→ **类根**

退一步看层 1–3 的汇合：层 1 说"占满账本的东西不必是进程的内存"，层 3 说"就算它是，现场也在你去查之前被销毁"。两条边合起来给出一个不需要任何额外假设的结论。

## 类根

> **OOMKilled 的判据是 cgroup 记账总量，你的观测判据是「进程匿名内存 × 时间平均」。两个计量域不相交，且事件现场会在你去查之前被销毁。在这个结构下，"OOM 了但没人吃内存、曲线还平"不是异常，是必然的观测输出。**

再往上抽象一层（这是消解入口）：**内存的记账权、判定权、执法权（选 victim）、以及事后销毁现场的权力，全部被内核 cgroup + 容器运行时代持，应用只看到 137。** 这与 `software.md` 里那条类根同构——生命周期/配额被外部机制代持时，失败必然发生在应用能打日志之前，于是表现为"无堆栈、无输出、无嫌疑人"。

**个例根**（挂在类根下，是子节点，不是与类根平级的清单）。每条都标注它能解释三个指纹（位置随机 / 重启就好 / 曲线平）中的哪几个，**缺一个就降级**：

- **G1 · shmem/tmpfs 泄漏**（`/dev/shm`、`emptyDir{medium:Memory}`、tmpfs 的 `/tmp` 里被写出但从不 unlink 的文件/共享内存段）
  解释力：位置随机 ✅（per-pod 状态）｜重启就好 ✅（容器重建 ⇒ tmpfs 重挂载清空）｜曲线平 ✅✅（shmem 页**不属于任何进程的 RSS**，且无 swap 时**不可回收**）。**三指纹全中，且"反复 OOMKilled"也自洽**：每次重启重新执行一遍写入逻辑。→ **首位候选**
- **G2 · file page cache（写放大/读放大 + 脏页回写受阻）**
  位置随机 ✅｜重启就好 ✅（新容器新 cgroup，cache 归零）｜曲线平 ✅（缓存不进程内）。短板：page cache **本应可回收**，单靠它越限不成立，必须叠加"脏页回写受阻/回收跟不上分配速率"才致命 → 判为共因，需与节点侧 IO 状况联合成立。
- **G3 · kernel（sock/slab）**：连接/重传风暴时 `memory.stat.sock` 涨，RSS 平。位置随机 ✅｜重启就好 ✅（连接断掉）。短板：与"3–5 天"无天然对应，需要网络侧共因。
- **G4 · 节点级 OOM：本 pod 是被邻居的账本顶死的**（`oom_score_adj` 高的 Burstable pod 被内核当 victim）
  位置随机 ✅✅（锚定节点当时的拥挤程度，最贴合"位置会换"）｜重启就好 ✅（瞬时压力过去）｜曲线平 ✅✅（**看的是本 pod 的曲线，它当然平**）。这一条是唯一能解释"完全无内部增长却反复被杀"的候选 → **并列首位候选，且它把问题从"内存去哪了"翻转成"谁有权杀我"**。
- **G5 · anon 的观测盲区**：容器无感 JVM（老 JDK 按宿主机内存定堆）、Go 未向 OS 归还、sidecar 与 app 共用 pod 级账本、秒级尖峰。曲线"平"是因为你看的是**应用自报的 heap**而不是 RSS。解释力较弱（题面说"没有任何进程"），保留待证伪。
- **G6 · 记账边界错**：limit 定得比该 pod 正常足迹还小 / LimitRange 注入 / limit 单位写错。症状：`kubectl describe` 里 limit 与同类 pod 不同，且**一启动就贴着限**。解释力：重启就好 ❌（这一条通常重启也不好）→ 若观察到 crashloop 永不停，G1/G4 降权、G6 升权。

## L3 双根

**处置根（修本次）**——不动架构，只做三件事，成本都在一次事件窗口之内：
1. 把下一次事件的**现场**留下来：节点上临时拉起一个采集，2–5 秒一次把 `memory.current` + `memory.stat`（anon/file/file_dirty/file_writeback/shmem/slab/sock）+ `memory.events` 写进环形缓冲，OOM 时（`memory.events` 的 `oom_kill` 计数增加即触发）把前 60 秒落盘。
2. 分叉第一刀：`dmesg -T | grep -i oom`。看到 `Memory cgroup out of memory` ⇒ 容器级（G1/G2/G3/G5/G6）；看到 `Out of memory: Killed process ... oom_score_adj=` ⇒ 节点级（G4）。
3. 容器内四行取证：`cat /sys/fs/cgroup/memory.stat`、`du -sh /dev/shm`、`findmnt -t tmpfs`、`df -h /tmp`。

**消解根（灭这一类）**——把"记账域 = 观测域"做成结构约束，而不是下次再猜：

> 观测与限流一律建在 **cgroup 记账 + 事件驱动**上：每个可触限的内存域都有独立计数器并对 limit 建分级水位告警；OOM 由 `memory.events.oom_kill` **事件**触发而不是由采样报警；limit 的取值以该 pod 自身 `memory.current` 的实测分位数 + burst 余量为依据，而不是拍脑袋。

- **① 不可发生判据**：若当时采用它，则"OOM 了却查不到谁吃了内存"在结构上**不可能发生**——任何被记账的字节都必有一个归属域计数器（层 1 的恒等式保证穷尽），任何 OOM 都必然伴随一份 60 秒内的分解现场（层 3 的时序被打断在最后一步之前），任何 limit 都有分位数出处。注意这条只消解**"不可诊断"这一类**；"被占满"这件事不会被消灭，它会被降级成一个有名有姓的容量项。
- **② 可执行首边**：部署一个 DaemonSet，每 5 秒采一次 `memory.current` + `memory.stat` 五个域 + `memory.events`，OOM 事件触发落盘保留 7 天；同时把看板第一屏从"进程 RSS"换成"cgroup `memory.current` 分解堆叠图 + 每 pod limit 使用率"。**不需要等事故、不需要改业务代码、当天可上线。**
- **③ 成本量级**（估算，量化交 📐 公式图，本轮不展开）：40 节点 × 12 样/分 × ~1KB ≈ **每节点每天 10 MB 量级原始数据，压缩后 <1 MB**；CPU 亚毫核级；人力约半天 + 一次看板改版。**这是消解根里最便宜的一类：它买的是"以后每次都查得到"，而不是"这次的数"。**

## L4 迁移出口

消解根把问题从"内存去哪了"换成"我们把内存治理建在记账上"，由此产生的新问题清单：

1. **观测改造**：DaemonSet 的部署与生命周期、指标基数控制（40 节点 × 每 pod ~6 个域指标，label 基数会爆，需要采样分级）。
2. **限流基线**：limit 从"拍脑袋"改为"分位数 + burst 余量" ⇒ 需要容量基线与变更审批流程，以及防回归的校验（谁的 PR 把 limit 改回小值）。
3. **业务侧整改**：若根因落在 G1/G2，需要业务改 shm 清理策略、日志轮转、`--shm-size`、tmpfs 挂载方式 ⇒ 跨团队，需排期。
4. **节点侧共因**：若根因落在 G4/G2，需要节点资源配额、超卖比、Pod QoS 分级与污点隔离策略 ⇒ 属于容量规划。
5. **组织能力**：值班人员要会读 `memory.stat` 的五个域，而不是只看 RSS；告警文案要写清"这是哪一个域越限"。

→ **本次问题降级为：第 (3) 项里的一个子项**——"某微服务的 shmem/page-cache 累积越限"，从一桩玄学 OOM 变成一个有名有姓、可排期、可用基线卡住的容量工作项。

## 一页纸判别实验（下一刀切在哪）

按成本从低到高，前两步通常就能收敛：

| # | 动作 | 读什么 | 收敛到哪个 G |
|---|---|---|---|
| 1 | `kubectl describe pod` 看 `lastState.reason` / `exitCode` | 137 + OOMKilled | 确认标签本身（顺便排除"137 被误读成 OOM"） |
| 2 | 节点 `dmesg -T \| grep -i oom` | `Memory cgroup out of memory` vs `Out of memory: Killed process … oom_score_adj=` | 前者 → G1/G2/G3/G5/G6；后者 → **G4 确诊** |
| 3 | 容器内 `cat /sys/fs/cgroup/memory.stat` | `shmem` / `file` / `dirty` / `slab`/`sock` 谁是大头 | shmem→G1，file→G2，sock/slab→G3 |
| 4 | `du -sh /dev/shm`、`findmnt -t tmpfs`、`df -h /tmp` | tmpfs 里有没有不该存在的大文件 | G1 确诊（能直接看到残留文件） |
| 5 | 对同类 pod `kubectl get pod -o yaml` 比 limit | 出事 pod 的 limit 是否与同类不同 | G6 确诊 |

## 候选根排序（Share × Lever ÷ Cost，Cost 即预算）

排序规则：**Share（能解释已观测现象的比例）× Lever（能不能动）÷ Cost（排除它要花多少）**。这里把 Cost 压到最低的一批排在前面——因为本题的预算约束是"下一次事件之前必须收敛"，而不是"给我一份完整的内存学说"。

| 候选根 | Share | Lever | Cost | 排序 |
|---|---|---|---|---|
| **类根 · 记账域 ≠ 观测域** | 唯一（它解释了"反常"本身） | 改配置（改采集口径） | 一次采集改造（半天） | ① |
| G1 shmem/tmpfs | 主因 | 改配置 | 一次采样（`du /dev/shm`） | ② |
| G4 节点级 OOM / 邻居 | 主因 | 改架构（配额/隔离） | 一次 `dmesg` | ③ |
| G2 file page cache（+回写受阻） | 共因 | 改配置 | 一次采样（`memory.stat`） | ④ |
| G6 记账边界错 | 共因 | 改配置 | 一次 `describe` | ⑤ |
| G3 kernel sock/slab | 次要 | 改配置 | 一次采样 | ⑥ |
| G5 anon 观测盲区 | 次要 | 改配置 | 一次采样 + 读启动参数 | ⑦ |

（①②③ 的取证动作可在同一个事件窗口内一次做完，实际成本接近一次；④–⑦ 是免费搭车项。）

## 结论

1. **根源不在"某个进程吃内存"这条线上，在计量域的错配上**：OOMKilled 按 cgroup 记账总量判，而你看的是进程 RSS × 时间平均。缓存、tmpfs、socket 缓冲、以及邻居 pod 的内存，全都在账本里而不在任何进程的 RSS 里，且越限瞬间的事件现场会在容器重启时被销毁。所以"查不到谁吃了内存、曲线还平"不是线索缺失，是**观测工具与被观测对象不在同一个计量域**。
2. **最可能的个例**按三指纹（位置随机 / 重启就好 / 曲线平）排序：**G1 容器内 tmpfs（`/dev/shm`、`emptyDir{medium:Memory}`）泄漏** 与 **G4 节点级 OOM（本 pod 是被邻居顶死的无辜 victim）** 并列首位。两者的区别一刀就能切开：`dmesg` 里是 `Memory cgroup out of memory` 还是 `Out of memory: Killed process`。
3. **"同一个镜像 40 台"这句是本题最硬的约束**：镜像内是常量，常量解释不了差异，所以根因必然落在镜像之外（随行数据/持久状态/宿主/邻居/时间点）。这条推论顺手把"代码有内存 bug"降权了——匀速泄漏不会表现出"1–2 个、不同步、位置会换"这种稀有事件的形态。

## ⚠️ 异常/矛盾/空白

1. **⚠️ "换机器就好"与"重启就好"不可区分（混杂变量）**：换机器必然伴随重启，重启也重置了 pod。所以"问题跟着 pod 走"**不能**用来排除节点侧共因——G4（邻居顶死）完全可以在每次重启后恰好落在健康节点上而显得"跟着 pod 走"。本条直接削弱了题面的一个隐含排除项，已在 L0 里把硬件类降级为挂起。
2. **⚠️ "查不到 / 很平"的口径未声明**：是哪个指标（`usage`？`working_set`？应用自报 heap？）、多长采样间隔、什么聚合方式？——这恰恰是 Q2 的一部分，但也意味着"主因判断"依赖一个题面没给的口径。若口径是 `memory.usage_in_bytes` 且真平，则 G1/G2/G3 全部降权，只剩 G4/G5/G6 存活。
3. **⚠️ "反复 OOMKilled"与"重启就好"之间存在张力**：如果每次重启都被治好几天，说明杀伤状态可重置（支持 G1/G4）；如果 crashloop 持续不停，说明有持久状态或持续外部输入（支持 G2/G6 + 冷启动重放）。题面两句话同时成立时，指向的是"**某个稀有事件把 pod 推进了一个自维持的越限状态，而容器重建能把它拉出来**"——这个组合本身是一条额外线索，但题面信息不足以判定是哪个 G。
4. **⚠️ 空白**：题面没有给 limit 数值、没有给 pod 数量与副本关系、没有说"反复"的周期（是每次事件内循环，还是跨事件重复）。这三项任意一项都能把候选从 6 条压到 1 条。

## 💡 灵感备注

- 同一个"计量域 ≠ 观测域"的结构在别处也长一样：句柄/文件描述符泄漏、`conntrack` 表满、磁盘 inode 耗尽、cgroup `pids.max` 打满（pid 风暴常被误报成"资源不足"）、以及 Kafka/RabbitMQ 的"磁盘没满但被限流"。**凡是"执法方按账本判、观测方按进程看"的地方，都会长出同一朵花。**
- 一个反直觉的判据，值得记住：**把 limit 提升一倍后事件消失，并不能证明"内存不够"，只证明"越限被推后了"。** 要证明根因，必须看到 `memory.stat` 里**哪个域**在涨；否则你只是给同一个 bug 换了一个更长的引信。
