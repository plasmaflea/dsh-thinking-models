## L2 逐层回溯

### 层1 记账恒等式轴（生成源：恒等式，非列举）

判据量从来不是「某个进程用了多少」，而是：

```
memory.current = anon + file(含 dirty 与 mapped) + shmem + kernel(slab/sock/内核栈) + 跨容器与节点分摊
```

前四项对不上「任何单个进程的 RSS」，第五项连「本容器」都不是。这就是「查不到任何进程吃内存」的第一层结构性原因。

| 格 | 计入被杀阈值 | 计入进程 RSS | 该格故障的可观测症状 | 本题判定 |
|---|---|---|---|---|
| `anon` | 是 | **是**（直接可见） | 曲线抬高、top/ps 可查 | **空**（你看到的是平） |
| `file` page cache（dirty、mapped、不可回收部分） | 是 | 否 | 读大文件后 RSS 不动而 `memory.stat` 的 file/cache 抬升且不回落 | 候选 |
| `shmem`（tmpfs、`/dev/shm`、`emptyDir{medium:Memory}`、POSIX 共享段） | 是 | **否，任何进程都看不见** | `df -h /dev/shm` 高、`ipcs -m` 有段；进程退出后段可能仍在 | **候选，且最符合「无进程 + 重启即好」** |
| `kernel`（socket buffer、slab、conntrack） | 是 | 否 | 连接数/流量突增后 `memory.stat` 的 `sock`/`slab` 抬升，`ss -m` 可见 | 候选 |
| 跨容器与节点分摊 | 本 pod cgroup 只承担一部分 | 否 | 同 pod 其他容器（sidecar/init/ephemeral）用量高；或宿主邻居的 page cache 把节点压到低水位后，由 **node OOM** 选中本 pod | 候选（唯一能解释「被杀者用量正常」） |

### 层2 时序轴（生成源：必经时序，一步一格）

1. **常态平台** → 症状：一切正常、曲线平坦。这是观察起点，不是「没问题」的证据。
2. **慢变量累积** → 症状：`memory.stat` 分项缓慢单调抬升，而 RSS 完全不动。
3. **稀有触发** → 症状：只与特定数据／请求／时段／并发数相关，与宿主无关 → 这就是位置漂移。
4. **瞬时越界** → 症状：跨越发生在 1 个抓取间隔内，窗口平均后曲线看不出任何东西。
5. **内核判定 + 选 victim** → 症状：死的是 oom_score 最高的那一个（通常就是主容器），**不是真正占内存的对象**。
6. **容器重启、记账清零、pod 可能换节点** → 症状：曲线回到平坦，「重启就好」，且故障换个地方出现。

六格里只有第 1 格（anon）是空的 → **轴未全空，轴有效**（若五格全空则必须换轴重切）。

### 层3 归属轴（生成源：恒等式 `故障数 = 触发率 × 暴露面`，按「跟谁走」切）

- **跟镜像** → 若成立，40 台应同时崩；实测不是 → 降为共因/背景，不是根。
- **跟宿主**（邻居、内核版本、cgroup 版本）→ 部分兼容，但位置不该漂移得这么干净。
- **跟数据与请求** → 与「位置随负载漂移」「重启即好」最一致。
- **跟编排**（limit 定档与调度）→ 决定「为什么不是全崩、而是每周正好 1–2 台」。

### → 类根

**这个问题的根不是「谁吃了内存」，而是「内存的所有权与可观测性错位」，而且这个错位被两个放大器放大成必然：**

- **口径错位**：记账主体是 cgroup/内核，观测主体是进程 RSS 与按容器的均值曲线；两者交集只有 `anon`。
- **阈值与分布错位**：limit 按「稳态平台 + 一点余量」定档（等于按均值设计阈值），而真实用量是**重尾分布**；尾部事件概率再低，也会在 40 台 × 7×24 的暴露面上被必然命中——「每 3–5 天总有一两台」是算术，不是玄学。

└ **个例根**（必须挂在类根下，不许与类根平铺）：某一次具体是 shmem 峰值／内核 buffer／同 pod 邻居／节点级 OOM 中的哪一条，**题面信息不足以唯一确定**，只能给候选并排序，靠一次现场判别收敛（不编造）。

#### 个例根候选（全部挂在类根下）

- **A** `shmem/tmpfs//dev/shm` 峰值（并行查询、共享内存、解码器、Python 多进程、浏览器内核）
- **B** 内核态内存计入 pod cgroup（连接风暴下的 socket buffer、conntrack、slab）
- **C** 同 pod 其他容器（sidecar/init/ephemeral），或 pod 级 limit 被共享
- **D** **节点级 OOM**：被杀 pod 自身用量低，消费者是混部邻居的 page cache——唯一能同时解释「被杀者曲线平」＋「位置随调度漂移」
- **E** 真实 `anon` 稀有尖峰但采样过粗（大请求、批量导入、GC 峰值）
- **F** limit 定档过低（把「平台」当「上限」）

#### 候选根排序（预算：一次现场取证 + 一次采样 + 一次配置核对；不含迁移预算 ⇒ 换架构类候选一律留在挂起，不进前 N）

| 序 | 分支 | Share（份额） | Lever（可控性） | Cost（证伪代价） | 一条判别观测 |
|---|---|---|---|---|---|
| 1 | D 节点级 OOM | 唯一（同时解释两个反常） | 换环境/改调度 | 一次现场取证 | 内核日志是 `Out of memory: Killed process`（node 级）而非 `Memory cgroup out of memory`，且被杀 pod 的 `memory.current` 远低于其 `memory.max` |
| 2 | A shmem/tmpfs | 主因 | 改配置 | 一次采样 | `memory.stat` 的 `shmem` 分项出现尖峰，`df -h /dev/shm` 高 |
| 3 | F limit 定档过低 | 共因 | 改配置 | 一次配置核对 | 稳态平台值已到 limit 的 70%–90% |
| 4 | C 同 pod 其他容器 | 次要 | 改配置 | 一次用量对比 | pod 总量 ≫ 主容器之和 |
| 5 | B 内核态内存 | 共因 | 改配置 | 一次采样 | `sock`/`slab` 分项与连接数同相变化 |
| 6 | E 采样盲区下的 anon 尖峰 | 次要 | 改观测 | 一次改造（5–10s 采样） | 短间隔采样出现周期性尖峰 |

## L3 双根

**处置根（修本次，今晚能做）**：把「无痕重启」改掉——被 OOMKilled 的容器不要立刻被替换，先抓 `memory.stat` / `memory.peak` / `memory.events` + 节点 `dmesg` 的 OOM 行，判清是 **cgroup OOM 还是 node OOM**，再按实测尾部分位重定 limit。这是**止血，不是根**。

**消解根（灭这一类）**：**让「记账面」成为唯一的观测面与定档面**——三处必须同时对齐：

1. **观测面 ↔ 记账面**：容器级 `memory.stat` 分项（anon/file/shmem/sock/slab）+ `working_set` + `peak` + OOM 事件，间隔压到能分辨一次越界（5–10s 或事件驱动），而不是看均值曲线；
2. **定档 ↔ 尾部**：limit 不按「平台 + 余量」，而按「稳态 + 已知尾部事件上限 + 缓冲带」；并把硬杀（`memory.max`）前面那一段交给软限反压（`memory.high`／应用侧自管），让越界**先被看见**；
3. **所有权 ↔ 应用**：把会隐身的内存（`/dev/shm`、tmpfs、mmap、共享段、连接池）全部显式声明上限并自报，不再让内核替应用记账。

- **不可发生判据**：若当时 1+2+3 都已具备，本类问题在结构上**不可能发生**——因为「隐身」的前提（记账主体不可观测）已被消除，越界必然先落在可见的反压段，而不是直接落在硬杀上。不是「变少见」，是「看不见的越界不存在」。
- **可执行首边**（从现状出发的第一条边，可以很小）：挑 **1 个** pod，只对它把内存分项指标抓取间隔调到 5s（或旁挂一个 sidecar 导出 `memory.stat`），并在重启策略前留一条抓现场的命令。**一天内可完成**。
- **成本量级**（只给量级，定量交给 📐 公式图）：观测面改造 1–3 人天；limit 重定档需一次回放/压测 + 3–7 天观察；软限反压需确认运行时能力，天级到周级；把内存所有权收回应用自管是应用侧改造，周级到月级。**给不出量级就不能决策**，所以这里不下精确值。

## L4 迁移出口

消解根指向「观测/定档/所有权」三处结构性改动，必然带出这批新问题；本次问题降级为其中第 1 项的子项：

1. **可观测性**：5–10s 采样的存储与抓取成本、40 pod × 多项指标的基数爆炸、OOM 现场取证流程（必须在容器被替换前抓——cgroup 销毁后 `memory.peak`/`memory.events` 归零）；
2. **容量与调度**：limit 上调后装箱率下降、可能触发扩容；**requests 必须同步改**，否则 QoS 与 `oom_score` 语义再度失真（只改 limit 不改 requests，等于把这个 pod 改成「更容易被选中」）；
3. **反压语义与 SLO**：`memory.high` 节流会抬高 p99 延迟，需重定义 SLO 并要求应用能处理节流；
4. **数据与状态**：cache/shmem 纳入自管后，应用要给出清理策略与生命周期（日志轮转、mmap 释放、`/dev/shm` 配额）；
5. **组织能力**：值班 runbook 从「查进程」改成「查记账面 + 区分 cgroup OOM / node OOM」，否则下次仍会绕回「没有进程吃内存」的死胡同。

→ **本次问题降级为：第 1 项（可观测性）下的一个子项——「某 pod 的一次 OOMKilled 事件」。**

## 结论

① **被 OOMKilled 的不是「吃内存的那个」**——内存记在 cgroup/内核账上（page cache、tmpfs/共享段、socket/slab），或者干脆记在邻居身上，而你的观测面只有进程 RSS，所以必然「查不到进程、曲线很平」。
② **「每 3–5 天 1–2 台、位置漂移」不是随机玄学**——是重尾触发在 40 台暴露面上的必然命中率，叠加 limit 按平台（而非按尾部）定档。
③ **根既不在某个进程，也不在镜像的静态内容**，而在「内存所有权与可观测性错位 + 阈值按均值定档」这对结构条件下：处置是抓现场 + 按尾部重定档（止血），消解是把观测面、定档面、所有权三处一起对齐到记账面（灭类），代价是把「某 pod 的一次 OOMKilled」降级成「可观测性改造」的第一个子项。

## ⚠️ 异常/矛盾/空白

- ⚠️ **题面缺三项决定性信息**：cgroup 版本（v1/v2）、监控抓取间隔、pod 是否多容器/是否用 tmpfs·共享内存。这三项直接决定候选 **A** 与 **D** 谁主——缺哪一项，对应分支只能挂起，不许拍。
- ⚠️ **复盘预算陷阱**（最容易导致错误排除的一点）：按题面取「2 台 / 4 天 / 40 pod」估算，单 pod 单日故障概率 ≈ 2/(40×4) ≈ **1.25%**；则单 pod 观察 7 天一次都不出现的概率 ≈ (1−0.0125)⁷ ≈ **92%**。也就是说「我在测试环境跑一周没问题」几乎**必然**发生，**不能**用来排除任何候选——这正是这类问题被反复误判成「偶发/玄学」的原因。要排除，只能把观测面铺到同等暴露面，或把分辨率与现场保留做对。
- ⚠️ **取证窗口只有几秒到几分钟**：容器被替换后 cgroup 销毁，`memory.peak` / `memory.events` / `failcnt` 全部归零；不改重启策略，每一次 OOM 都是不可回收的证据损失。

## 💡 灵感备注

- **「被杀的不是消费者」（victim ≠ consumer）** 是这类问题最好用的识别特征：只要 OOMKilled 与「无进程吃内存」同时出现，第一动作就该是把观测面从 RSS 换到 `memory.stat` 分项，而不是去找泄漏。
- **40 台这个数字本身就是信息**：它把「单机永远看不到的尾部错误」变成「每周都发生的日常故障」，同时又小到不足以让人相信它是系统性问题。规模是放大器，不是噪声。
