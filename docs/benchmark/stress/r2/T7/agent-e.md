## L0 类别判定

**类别**：软件类问题 → 知识树 `concurrency` 子层（并发与时序，树内明确列出的典型根之一即「**重试风暴**」）为主层；`dependency`（客户端与下游共享依赖）与 `quota`（连接／accept 队列／并发配额）为并挂子层。
**判据**（按树的两条必满足项）：① 行为由代码／配置／环境姿态决定，不依赖物理介质（同一份客户端配置在等价环境可复现）；② 失败由确定性竞争导致，且能归因到外部输入的时序——本题两个指标都与「请求时序／重试时序」强相关。
**已排除的大类**：硬件故障（下游机器未动，无校验错误、无温度相关症状）；权限／账号体系（无 401/403 族、无「换账号即正常」症状）。
**未排除、已挂起的大类**：网络链路（客户端侧 DNS、LB 设备、证书轮换；题面无 traceroute／丢包／TCP 重传数据，不能用「没提」冒充「已排除」）；组织流程（不是技术根，是**归因方式**错，登记为 L4 迁移项而非分层根）。

## L2 逐层回溯

### L2.0 先处理「方向」本身：稳态反馈环里方向不可由观测识别

重试率与 p99 同时在涨，且两边都在证明「我没变」——这已经是**正反馈环自持**的典型形态（失败 → 重试 → 排队加深 → 时延上升 → 更多超时 → 更多重试）。环一旦自持，两个指标的同期相关**在数学上无法定向**：领先-滞后在环动力学会把相位锁定，领先者不再是原因。可定向的手段只有一种：**把环里某个增益节点置零，看残余**（identification by intervention）。

所以对「你怎么判断方向」的正面回答是：**不问「谁先」，问「把谁置零后现象消失」**。这个问题不需要实验就能先收窄一半，见 §5 的分解论证。

### 轴 A（生成源：计数恒等式）— 重试率这个**比值**从哪来

`观测重试率 R = F × k / D`
F = 首尝试失败暴露率；k = 每次失败的重试次数（含首次）；D = 分母口径因子（请求 / 调用 / 含不含连接层重试）。

| 格 | 该格在管什么 | 该格故障的可观测症状（专属） |
|---|---|---|
| A1 `F↑` 真失败更多 | 下游或链路真的更容易失败 | 首尝试错误率同步上升；错误码集中在超时／连接重置；**k 的分布不变** |
| A2 `k↑` 策略变了 | 超时缩短、可重试错误集放宽、退避无抖动、重试次数 1→3 | **首尝试错误率不变，R 涨**；重试次数分布直方图右移；R 的涨幅≈k 的倍数 |
| A3 `D↓` 口径变了 | 分母从「请求数」改成「调用数」、或把连接层重试计了进来 | R 跳变但**重试绝对次数不变**；变更点与某次配置／SDK 升级对齐 |

三格正交（各自有不同的可分离证据）、可生成（恒等式右边因子穷尽）、可观测（每格有专属症状）。**A2 是最容易被忽略的一格**：`R` 是比值，只要 k 从 1 变 3，失败率一点没变，R 也能从 3% 跳到 11%（3%×3.67）。

### 轴 B（生成源：单请求必经时序，一步一格）— 多出来的尝试**物理上落在哪**

一个逻辑请求从「判定要发」到「被记成一次重试」，必经五步：

| 格 | 必经步骤 | 该格故障的可观测症状（专属） |
|---|---|---|
| B1 客户端判定层 | 谁决定重试：超时阈值、可重试错误集、预算、退避曲线 | **下游业务 QPS 完全不变而 R 涨** → 重试根本没发出去，或被客户端熔断／去重吞掉 |
| B2 连接建立层 | DNS／TCP／TLS／连接池／网关／sidecar | 下游**业务 QPS 不变，但 accept 队列、TLS CPU、FD、SYN 重传上涨** → 重试死在连接层，永不计入下游业务指标 |
| B3 到达与准入 | LB 权重、限流器、队列、并发上限 | 下游**拒绝率／429／503 上涨而非请求量上涨**；排队时延吃掉 p99 的全部差额 |
| B4 执行 | 下游自身调 DB／缓存／下游的下游 | 下游的依赖侧 p99 同步上涨（共享资源）；或**同一份昂贵工作被执行多次**（非幂等重复） |
| B5 响应与超时判定 | 写回、客户端是否已放弃、取消处理 | 「已完成但无人接收」比例上涨；被取消的请求仍占资源；同一逻辑请求在下游出现多次 |

正交性：B1–B5 回答「多出的尝试停在哪一环」，与轴 A 的「比值为何变化」是两个独立问题。**B2 是本题最锋利的格**：它同时解释三件事——下游业务负载没变、下游 p99 变差、我们的重试率上升，且不需要任何一方说谎。

### 轴 C（生成源：聚合与口径恒等式）— 指标本身是不是幻觉

| 格 | 该格在管什么 | 该格故障的可观测症状（专属） |
|---|---|---|
| C1 聚合窗口 | 周粒度会把先后关系抹平 | 拉到分钟级后，某一指标其实是阶跃而非渐变 |
| C2 百分位可加性 | **p99 不可跨实例再加**，也不能「各实例 p99 取平均／取最大」 | 按单实例重算后差值缩小或消失 |
| C3 实例集合变化 | 扩缩容、权重调整、跨 AZ 聚合，会让样本群整体换人 | 同期有实例增减／权重调整记录，而「机器没动」仅指无硬件变更 |
| C4 样本口径 | 是否含超时与取消样本、是否只统计 2xx、直方图桶精度 | 把弃样本计入后 p99 抬升，剔除后回落 |

**全空列判据**：若 A、B、C 三轴所有格都无症状而问题仍在，则说明测的不是同一批请求（客户端与下游的「请求」不是同一个总体），换轴重切——重切方向为「逻辑请求 vs 物理尝试」的总体对齐轴。

## 5. 汇合层（不跨维度连边，只在此合并）+ 量级检验

三个维度在汇合层合成一句：**轴 A 解释「比值为何动」，轴 B 解释「多出的负载落在哪」，轴 C 解释「指标是否可信」。** 三者互不解释对方的格，满足正交。

题面给出的事实足够先做一个**纯逻辑的方向收窄**，不必等实验：

1. 下游的三项否认（负载没变、机器没动、没发布）在逻辑上等价于承认第四条：**每请求的工作量与执行环境没变 ⇒ 服务时间（handler 执行时间）没变**。他们否认的是「我怎么会被拖慢」，没有否认「我处理一个请求本身要多久」。
2. 端到端时延恒等式：`T = T_服务 + T_排队`（临界路径上可加）。服务项不变而 T 的 p99 涨了 4.5 倍（200ms → 900ms）⇒ **全部差额落在 T_排队**。
3. 排队项只由**到达过程**决定（到达率的瞬时峰值、并发度、连接复用度），不由被调方代码决定。而到达过程在这一周里唯一被已知改变的东西，就是重试。
4. ⇒ 差额在**到达侧**，即在我们这一侧。团队结论的因果箭头反了。

量级检验（📐 联动，仅作数量级、**不得当证明用**）：M/M/1 尾部近似 `T_p99 ≈ 4.605·S/(1-ρ)`。若 `S` 不变，`T_p99` 从 200ms 到 900ms（4.5×）对应 `ρ` 从约 0.78 抬到约 0.95（比值 4.40×），反解得 `S ≈ 9.6ms`——一个完全正常的服务时间。**也就是说：「下游变慢」根本不需要发生，只要利用率从 0.78 被推到 0.95，就足以产生 4.5× 的 p99 抬升**。而 0.78→0.95 需要的额外负载约 +22%，与「8 个百分点的请求被重试 × 每次约 3 次尝试」同一量级。⚠️ 这条吻合**不是证据**：M/M/1 是最粗的模型，真实系统有并发上限、批处理、GC，巧合概率不低。它只承担一个作用——**证明团队的推论不是唯一解释，且对立解释在数量级上完全站得住**。

补充一条常被漏掉的机理（轴 B2 与轴 C4 的交点）：**QPS 不是负载的充分统计量**。决定 p99 的是到达过程的二阶矩（突发性、并发度、连接复用度），而「负载没变」通常报的是均值 QPS。重试天然制造突发（同步重试、固定退避）与短连接，即使总量不变也能把瞬时 ρ 顶过 1。所以「负载没变」与「我们被重试搞慢了」**可以同时为真，且不需要任何人说谎**。这不是和稀泥，而是本题最容易被双方都漏掉的那个维度。

## 类根 / 个例根

**类根**：调用链上**缺少把「失败信号」转成「有界负载」的负反馈环节**——重试没有全局预算、被调方没有显式背压信号、重试不保证幂等、超时判据与被调方真实排队状态解耦。只要这四项缺位，「失败 → 重试 → 更慢 → 更多失败」这个环的**增益就 > 1**，于是任何一次轻微、短暂、甚至根本不属于故障的下游抖动，都会被放大成自持的雪崩，且事后无法从稳态数据里分辨谁先。这一类问题的判据是结构性的：**环里没有任何一处的增益被硬性固定在 < 1。**

  └ **个例根（本次具体机制，按 Share×Lever÷Cost 排，见排序表）**：
  - **个例根 ①**：客户端侧重试策略发生了「没人认为是变更」的变更（超时阈值缩短、重试次数上调、可重试错误集放宽、退避去掉抖动、连接池／DNS TTL 调整）。预期症状：首尝试错误率不变而 R 涨（轴 A2）、重试次数分布右移、变更时间点与某次配置热更新／SDK 版本／feature flag 对齐。**这是「下游什么都没变」的预期结果，不是它的反证。**
  - **个例根 ②**：重试在连接／网关注入层被吸收，不进下游业务 QPS 统计（轴 B2）。预期症状：下游业务 QPS 平，但 accept 队列／TLS CPU／FD／瞬时并发上涨。
  - **个例根 ③**：客户端与下游共享一个依赖（DB、缓存、DNS、证书链、消息队列），重试打的是这个共享物（轴 B4）。预期症状：DB 侧 QPS／连接数／慢查询与重试脉冲同相位。**这是唯一能让三方「我没变」全部为真的解释。**
  - **个例根 ④**（挂起，且**不改变处置**）：下游基线确实抬升。注意逻辑：即使它成立，一个增益 > 1 的客户端对任何下游波动都会自伤，处置动作不变——所以「下游是否也变慢」这件事对我们该做什么**不构成分歧**。它只影响工单的措辞，不影响我们的修复。

## L3 双根

**处置根（修本次，24 小时内）**：做一次**可逆的断环干预**，同时把工单改写。
干预：灰度把客户端重试预算／次数降到接近 0（或退避 ×4 并加满抖动），**同时**给发往下游的每个物理尝试打标（首尝试／第 N 次尝试、是否被取消），观测 30 分钟。
判定矩阵（这是本题「怎么判断方向」的可执行形式）：
| 观测结果 | 结论 | 动作 |
|---|---|---|
| p99 回落 ≈200ms，下游执行时间平 | 环在我们这边（个例根 ①②） | 按消解根治理；工单降级为信息共享 |
| p99 不回落，首尝试 p99 仍 900ms | 下游基线确实抬了（个例根 ④） | 工单成立，但**同时**必须修增益——否则下次波动照样雪崩 |
| p99 部分回落（如落到 400ms） | 混合：下游基线 200→400，我们放大 400→900 | 双重处置，先修我们（自伤优先） |
| p99 回落但下游业务 RPS 几乎没降 | 重试走的是连接／网关层（个例根 ②） | 修连接层重试与池化，业务侧无感 |

**消解根（灭这一类）**：把「失败 → 负载」的增益**硬性钉死 < 1**，四件事同时成立：① 全链路**全局重试预算**（重试量 ≤ 首尝试量的一定比例，例如 10%，且预留 headroom 使目标 ρ 有明显上界）；② 被调方**显式背压信号**（429 + Retry-After、自适应并发限制、队列深度反馈）被客户端真正遵守；③ **幂等键去重**，让重试不产生新的执行工作；④ **抖动退避 + 收窄可重试错误集**（只对幂等且可安全重试的错误重试）。
- **不可发生判据** ✓：若当时存在全局重试预算（放大有硬上界）+ 背压信号被遵守，则下游**永远进不了临界区**。任何单点变慢最多把负载推到预算上界，产生一次**有界且会衰减**的响应，排队项不会进入自持区。此时「两个指标联动 + 三方都声称没变」这一整类现象在结构上**不可能发生**——不是变少见，是存在硬上界。
- **可执行首边** ✓（从现状出发的第一步，很小）：在客户端统一出口（SDK 或网关）加 per-endpoint 重试预算令牌桶（默认开，灰度 1% → 100%），并把下游 429/503 的 `Retry-After` 透传遵守。**不需要下游配合，不需要架构改造，可当天上线。**
- **成本量级** ✓（联动 📐，此处只给量级）：工程量 **3–10 人日**（1–2 人）；运行成本 ≈ 0 甚至为负（重试减少反而省资源）；真实代价是**失败暴露度上升**，因此必须先有降级预案（缓存回退／静态页／降级开关），这是成本主体而非代码量；验证成本 = 一次 30 分钟灰度。**结论：低工程量、中风险、需要前置预案——不满足「无痛开关」条件，但远低于任何架构迁移。**

## L4 迁移出口

消解根指向的是「全链路重试治理」这个更大的工程。**本次问题降级为其中一项**：

1. **重试治理与配置一致性**：谁可重试、几次、退避曲线、超时阈值的统一登记与变更审计（消灭「没人认为是变更的变更」）。
2. **幂等性改造**：幂等键、去重表、重复投递检测，把「至少一次」的语义代价显式化（→ 树外节点 `data-consistency`，v2 候选的实体）。
3. **背压能力建设**：429/Retry-After、自适应并发、队列深度指标贯通到客户端决策。
4. **可观测性迁移**：trace 贯穿首尝试与所有重试、下游指标按「是否重试／第几次尝试」分维、p99 同时给 per-attempt 与 per-logical-request 两个口径、p99 禁止跨实例再加。**这一项是消解根的前置**——没有分维口径，连预算该设多少都无从谈起。
5. **组织能力与归因流程**：值班 playbook 从「先定位再断环」改为「**先断环再定位**」；跨团队归因以「守恒差额在哪」开场，而不是以「你变慢了」开场。
6. **容量与 headroom 目标**：把「没变却扛不住正常抖动」定义为容量缺陷（ρ 无上界 = 没有 headroom 预算），与 SLO 一起写进双方共担指标。

→ **本次问题降级为第 1、4 项的一个实例；本次的「方向之争」降级为第 5 项（归因流程缺失）的一个症状。**

## 结论

**方向判断**：箭头反了。不是「下游变慢 → 所以我们多重试」，而是「我们自己把失败的代价放大成了下游的负载 → 下游排队 → 更慢 → 更多重试」的正反馈环。题面事实已经足以走完大半推理：下游只否认了负载、机器、发布，**没有否认「每请求服务时间」**；而代码不变 + 机器不变 + 每请求工作量不变 ⇒ 服务时间不变；服务时间不变而 p99 涨 4.5 倍 ⇒ 全部差额落在**排队项**；排队项只由到达过程决定 ⇒ 差额在到达侧，也就是我们这一侧。严格说，在环自持之后「谁先」在稳态数据上**不可识别**，唯一能定向的是干预（把某个增益节点置零看残余），而不是继续取数争论。

**根源**：类根是**缺负反馈**——没有全局重试预算、没有背压信号贯通、没有幂等去重、超时判据与被调方真实排队状态解耦，于是环的增益 > 1，任何一次轻微抖动都会被放大成自持雪崩，事后还无法定向。个例根按排序是**客户端侧的「没人认为是变更的变更」**（超时缩短／重试次数上调／退避去抖动），其次才是连接层吸收（口径假象）与共享依赖被打穿。「下游变慢」即使为真，也只是把环点燃的火柴，不是环本身；而且**它是否为真不改变我们的动作**。

**下一步（按预算排序，从最便宜的开始）**：
1. 审计「重试率」的分子分母与重试次数分布直方图（分钟级）——分辨 A1/A2/A3，成本一次取数。
2. 把两边时间序列对齐到分钟级看领先-滞后——注意环自持后相位会被锁定，只能作辅助。
3. 查客户端这一周的**一切**变更，包括那些没人当变更的：超时阈值、重试库版本、可重试错误集、退避抖动、连接池、DNS TTL、证书轮换、feature flag、LB 权重。**「下游没变」的对偶命题是「系统变了」，只要两边都真没变，变的就是共享的那一层。**
4. 做断环实验（灰度关重试 30 分钟 + 按第 N 次尝试打标），按上面的判定矩阵落表。
5. 工单**不要撤回，改写**：从「你们变慢导致我们重试」改成「请给出你们 p99 的**服务时间／排队时间分解**，以及你们对 ρ 的 headroom 目标」。因为这个环能被点燃，说明下游本来就工作在临界区——那不是「被冤枉」，那是**缺少 headroom 的容量缺陷**，他们「什么都没变」正是问题的一部分。

**三句话版**：① 下游「负载没变、机器没动、没发布」这三句话如果为真，那么涨上去的 700ms 只可能是排队，而排队只由我们的到达过程造成——方向反了。② 根源不是谁慢，而是我们没有任何机制把「失败」限制成「有界的少量重试」，环的增益大于 1；③ 别再取证了，去做那个 30 分钟的置零实验，它一次能证伪四个假设，并且顺手上线重试预算。
