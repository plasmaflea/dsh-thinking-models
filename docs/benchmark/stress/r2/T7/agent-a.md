# 重试率 3%→11%、下游 p99 200ms→900ms：方向怎么判，根在哪

## 一、结论先行（三句话）

1. **"下游变慢 vs 我们重试变多"不是一个二选一问题。** 它们是同一个正反馈环路的两个端，题面把它们当竞争性解释，这个框架本身就错——在没有分钟级 lead-lag 和同 hop 计数之前，方向不可判；但方向的判据是可构造的，不用靠争论。
2. **数量级已经给出答案的一半。** 重试率 3%→11% 意味着到达下游的**尝试数**只涨了 `(1+11%)/(1+3%)−1 ≈ +7.8%`；而 p99 涨了 **4.5×**。线性容量通道下 +8% 到达量只能换来个位数百分比的延迟上升（除非利用率已贴到 ρ≈1 的刀刃上）。4.5× 不可能由"多了一点负载"解释——它只能是**到达过程的形状**（方差、集中度、热点同源）或**环路自维持**。这两条都指向"重试是放大器"，不是"下游是自变量"。
3. **根既不在下游，也不在"重试次数配置得太大"。根在：重试是开环的**——每请求独立决策、没有全局预算、没有抖动、没有熔断、与超时强耦合（超时越久→重试越多→越久）。这条结构一旦存在，**任何一次尾延迟扰动都会被翻译成一个持续更高的新稳态**。下游只是这个环路的受力面，不是根。**工单方向反了。**

> 补一条最容易被忽略的：**3% 的基线本身就是证据。** 健康 RPC 的重试率应在 1% 以下。3% 说明这个环路早就在跑、只是还没饱和；11% 不是"新出现的问题"，是**它越过临界点**的那一刻。团队把基线当正常，才会把 8pp 的增量当成外生冲击。

## 三、[🌳 林状图] 逐层回溯

### L0 类别判定

**类别**：分布式系统内的**排队—可靠性退化**（到达过程/队列/重试策略耦合导致的尾延迟抬升），归 `software` 节点下的 `concurrency`（重试风暴/时序）与 `quota`（连接池/线程池/队列）两个子层，并触及 index 中尚未核查的 `network` 待建分支。

**判据**：①现象随代码/配置/流量姿态变化，不随物理介质变化；②失败与延迟由确定性竞争（排队、超时、重试时序）导致，不是随机位翻转；③两个现象同周同向变化且与调用方行为相关。

**已排除的大类**：硬件故障（无 CRC/ECC/温度相关，两现象与调用方重试率同步）；权限/账号体系（与凭据、ACL 无关）；纯组织流程问题（组织因素无法产生 200ms→900ms 这一物理量；组织因素在 L4 出现，不作为本次根）。

> ⚠️ 如实登记：本类**不满足** `software` 节点判据 2 的严格形式（"给定相同输入与时序，失败可重现"）——排队退化是**统计性可复现**而非确定性可复现。这是一处树边界外的落点，下面登记为 v2 候选节点。

### L2 逐层回溯

**选轴（生成式，不列举）。** 本题的两个生成源：

- **恒等式源**：`到达下游的尝试数 = 请求数 × (1 + 重试率)`——给计数轴。
- **恒等式源（排队分解）**：`客户端观测延迟 = 服务时间 S × 排队放大(ρ) × 方差放大(Ca²,Cs²) + 重试与退避附加等待`——给延迟轴。右边四个因子**机械生成**四个格，不是联想出来的。

三个判据自检：**正交**（各格的根不能互相解释对方的症状：S 上升会让首次尝试也慢；ρ 上升会同时抬 p50；方差上升只抬尾；客户端附加项让下游看不到）｜**可生成**（恒等式右边因子）｜**可观测**（每格有专属症状，见下）。

| 层 | 轴格（恒等式因子） | 该格故障的可观测症状 | 本案判定 |
|---|---|---|---|
| 1 | **服务时间 S ↑**（下游单次真的变慢：慢查询、锁、GC、索引失效、数据增长） | server-side handler p99↑，**首次尝试也慢**，p50 同向动，per-shard 一致或集中于某分片 | **未验证**，下游自述"无发布"但"无发布≠无变化"（见 T3）。必须先看 handler 时间分解 |
| 2 | **利用率 ρ ↑**（真负载上升） | 下游 QPS/并发/连接数/CPU 同步↑，p50 也↑，p99/p50 比值基本不变 | **未验证**，与"负载没变"直接冲突——必须在**同一 hop** 上核 attempts 计数（见对照 1） |
| 3 | **到达方差 Ca² ↑（同平均负载，到达更突发/更集中）** | **平均 QPS 平、p50 平、p99 暴涨**，p99/p50 比值扩大；CPU 均值平但峰值尖；与重试的时间分布同步 | **最高嫌疑**。这一格是唯一能同时解释"下游负载没变"与"p99 涨 4.5×"的机制 |
| 4 | **重试与退避附加等待（客户端侧串联）** | 下游 server-side 时间正常，但客户端总时长超；客户端连接池/线程池排队时间↑；单请求 attempts>1 | **未验证**，但极可能贡献可观比例（客户端排队是自己造的） |

**四格无空格**（不许有"此处无症状"的空白）：四格全部给出了专属症状与判定。

**→ 类根：这一类在什么结构条件下必然可能发生**

> **类根：重试是开环的——它是一个正反馈环路，却被当成负反馈吸收器在用。**
> 具体结构条件五条同时成立：(a) 每请求独立决定是否重试，**没有全局重试预算**（放大倍数无上界）；(b) 退避**无抖动**，重试在时间上同步成波（把到达方差推高，命中格 3）；(c) **重试目标与故障目标同源**（打到同一分片/同一连接池/同一条慢队列），于是少量重试打在最稀缺的资源上；(d) 重试**与超时强耦合**（超时越长→重试越多→越慢→更多超时），是正反馈而非阻尼；(e) **无熔断/无负载感知**，环路没有出口条件。
> 只要这五条里有 (a)(d) 两条，任何一次尾延迟扰动都会被放大成一个**自维持的高延迟新稳态**（metastable failure）——这就是为什么它能跨周持续、而不是跟着扰动一起衰减。

**└ 个例根（挂在类根下，是子节点不是平行清单）：本次是哪一次变更/哪一类状态漂移把环路推过了临界点。**

| 个例根候选 | 机制 | 为什么它能解释"下游三不动" |
|---|---|---|
| **T1 客户端同周变更**（超时下调／重试次数上调／退避去掉抖动／SDK 升级／新调用方上线／重试条件从"只重试连接错误"扩大到"超时也重试"） | 直接抬高环路增益 | 下游什么都没动，是**你**动了增益。这是最便宜的一条，必须第一个查 |
| **T2 到达过程形状变化**（缓存命中率下降／TTL 改动／批任务与在线流量重叠／流量结构变化：请求变重、新租户） | 平均 QPS 不变、方差与单次成本上升 → 命中格 3 | 下游"负载"按均值衡量确实没变 |
| **T3 下游共享状态漂移**（数据量增长导致索引/工作集超出内存、连接数或句柄增长、统计信息过期、云配额限流、宿主邻居吵闹、证书/DNS/TLS、依赖版本被第三方升级） | 服务时间或排队资源悄悄变化 → 命中格 1/2 | "机器没动、没发布"≠"什么都没变"：**状态会漂移，共享基础设施会变** |
| **T4 重试目标同源**（重试打到同一热点分片/同一连接池/同一条慢队列） | 少量额外尝试集中在最稀缺资源上，局部 ρ→1 | 全局均值不变，局部爆炸 → 命中格 3/2 的交集 |
| **T5 多层重试叠加**（客户端 × 网关/LB × 服务内部重试） | 有效放大倍数 = 各层乘积，可远超 1.078 | 各层都"只加了一点点" |

### L3 双根

**处置根（修本次，小时级）：先把环路增益降到 <1，再谈谁慢。**

1. **可回退测试（一次开关，成本≈0，同时是方向判据）**：把重试降到接近 0（超时不重试、只保留连接类错误重试一次、退避加满抖动），或切一个不重试的 canary 分组，**10 分钟**内看下游 p99。回落 → 环路主导，方向定案；不回落 → 转查格 1/2。
2. **同一 hop 的计数与延迟分解**（见下"怎么判方向"三条对照），把双方数据放到同一坐标再谈因果。
3. **把工单改写成联合定位请求**：请下游给 server-side handler p99 分解（不含排队）、他们的**依赖** p99、入口 attempts 计数、排队时间（accept queue / 线程池 / 连接池等待）。要求他们"优化"是一份无法验收的工单；要这四个数是一份可验收的工单。

**消解根（灭这一类）：把重试从"每请求的局部策略"升级为"系统级的守恒资源 + 端到端 deadline 传递"。**

组合五项：①全局重试预算（如"重试尝试数 ≤ 成功请求数的 10%"，令牌桶实现，预算耗尽即自动停重试）；②指数退避 + full jitter；③只对**幂等且明确可重试**的错误码重试（超时不重试，或仅允许一次）；④端到端 deadline 传播，使嵌套重试共享同一预算而不是各层独立膨胀；⑤熔断 + 舱壁 + 重试目标去相关（换 host/换分片/带 token），使重试不落在故障点上。

**三道闸门：**

- **① 不可发生判据**：有全局预算时，任何单点尾延迟扰动对下游到达量的放大被**硬上界锁死在 ~1.1×**，且预算耗尽后重试自动关闭 → 本类（"一次扰动 → 自我维持的雪崩"）**在结构上不可能发生**，不是"变少见"。叠加 deadline 传播后，"多层重试相乘"这一类也归零（总预算守恒，与层数无关）。注意：这不消除扰动本身，而是消除**放大**——这正是"消解"与"缓解"的分界。
- **② 可执行首边**：在客户端 SDK/HTTP 客户端里把 `for (i=0;i<3;i++)` 重试循环换成**按成功数补充令牌的令牌桶**（比例 10%）+ full jitter，并把 `attempts/requests`、`重试预算消耗率` 打成指标。**一人日量级，配置+小改代码，一次可回滚发布。** 不需要架构变更就能迈出第一步。
- **③ 成本量级**：小（数人日 + 一次发布）。对照：不做的代价是"每次复发都要重新做一遍跨团队取证"，而取证的一次成本高于实施成本——这是本题真正的经济学颠倒。具体数字交 📐 公式图定量，此处不编造。

### L4 迁移出口（消解根带来的新问题清单）

1. **端到端 deadline 统一**：各 hop 超时必须从上游剩余预算推导，否则重试预算没有意义（预算管住了次数，管不住单次拖延）。
2. **幂等性审计**：11% 的重试率如果打在非幂等写接口上 = 重复扣款/重复下单/重复发消息。**这可能是比 900ms 更严重的问题**，且被"性能问题"叙事掩盖了。
3. **背压与降级承接**：重试被预算压住后，失败会**显性化**（原来被重试掩盖的 3% 会变成可见错误）。必须有排队/降级/限流/兜底来接住，否则"修好延迟、暴露错误"，会被误判为变更失败。
4. **调用方协同**：只要还有一方不设预算，单方退让无效（它会替你重试）。需要契约级约定。
5. **可观测性重构**：attempt 级 span（每跳重试单独成 span）、客户端排队时间、重试预算消耗率、per-shard/per-tenant p99 作为一等指标。没有这些，"下游变慢所以我们重试"这类方向误判在数据上**无法被反驳**。
6. **组织流程（方向判定举证责任）**：任何"某方变慢"的工单必须附**同 hop 计数 + 延迟分解 + 时间对齐**三件套，否则不予受理。

**→ 本次问题降级为**：清单第 5、6 项下的一个具体实例——"这次到底是哪一次变更把环路推过了临界点"变成治理落地后的一次**常规采样**，不再需要跨团队互相举证。第 2 项则是本题里被延迟叙事掩盖的第二个独立风险。

## 四、怎么写这个方向（三条对照 + 一次测试）

这是题面问的"你怎么判断方向"。**判方向不靠谁先抱怨，靠三个观测量必须在同一坐标上。**

**对照 1｜计数守恒（最硬、最便宜）。**
`尝试数 = 请求数 × (1 + 重试率)`。客户端请求数若持平，`+7.8%` 的尝试必须在下游**入口**的计数器上出现。两边同时取同一时间窗：
- 下游入口 attempts **涨了** → 他们说"负载没变"是**测在了错的层**（比如按业务 QPS、按去重后的 ID、按长窗口均值、或在 LB 之后聚合）→ 矛盾消解，方向指向放大器。
- 下游入口 attempts **没涨** → 你的重试**根本没发出去**（被本地熔断/连接失败/缓存挡住了），或重试率的口径是"遇到过重试的请求占比"而非"额外尝试"→ 那么 11% 与 p99 的关系完全是另一回事，先修口径。
> 这一条必须先做。**双方数据在计数上互相矛盾，任何因果结论都建在错坐标上。**

**对照 2｜延迟分解（决定"下游变慢"这句话的生死）。**
把客户端观测的 900ms 拆开：`连接建立/排队 + 网络 + 下游 server-side handler + 下游内部排队 + 重试/退避等待`。
- 若下游 **handler p99 仍是 200ms**，客户端却见 900ms → **"下游变慢"当场死亡**，多出的 700ms 在排队/网络/你的重试等待里。
- 若 handler 也是 900ms 但 **CPU 平** → 不是容量问题，是**排队资源**问题（连接池/线程池/锁/队列/单分片）。这时正确动作是"找那个排队资源"，而不是"要求优化"——"优化"对一个排队问题没有可执行含义。
- 若 handler 900ms 且 CPU 也↑ → 才轮到"容量/单次变慢"，进格 1/2。

**对照 3｜lead-lag + 外部对照（唯一能真正判"方向"的）。**
1 分钟粒度对齐两条曲线：
- 有明确 lead（重试率先动）→ 方向：你 → 下游。
- 同时刻动、无 lead → 这是**环路**，不能用"先动"判方向，只能判**增益**（关掉重试能压回多少）。
- 加一条外部对照：**同一下游的其他调用方**是否同时 p99 抬升。只有你涨 = 你的环；全都涨 = 下游或其共享依赖（这就把"无发布≠无变化"的排查推回到他们那边，但是用数据推，不是用嘴推）。

**一次测试｜可回退性（reversibility test）：这个环路有出口吗？**
把重试限流到接近 0，10 分钟内看下游 p99。
- 回落 → 环路的增益 >1，重试是放大器。**"下游变慢所以我们才重试"最多只对了一半：它解释了扰动，解释不了 4.5×。**
- 不回落 → 扰动源在下游/共享依赖，转查格 1/2，此时工单方向才对。

> 这三条对照 + 一次测试加起来不到一天工作量。**在拿到它们之前，「下游变慢」只是假设；拿到之后，无论哪个方向，都能给出可验收的动作。** 现在的工单是在用一个假设向另一个团队索要资源。

## 五、候选根排序（Share × Lever ÷ Cost）

排序是预算的函数。本题预算紧（跨团队、无对方内部数据），所以 Cost 权重高：**先做成本近乎为零的前置项，再按份额取前 N 条验证。**

| 层级 | 候选根 | Share 份额 | Lever 可控性 | Cost 证伪代价 | 排序 |
|---|---|---|---|---|---|
| **前置** | **C 观测口径错位**（"负载没变"与"重试 ×3.7"在计数上矛盾，必有一方测在错的层） | 共因（它是**解释两方数据矛盾**的唯一机制，不解释延迟本身） | 改口径 | 一次口径核对（对数） | **0（先做，否则后面全是错坐标）** |
| **类根 A** | **重试开环（无预算/无抖动/无熔断/与超时耦合）→ 正反馈无出口** | **唯一**（唯一能同时解释"负载平 + p99 4.5×"+"跨周自维持"的机制） | 改配置＋小改代码 | **一次开关** | **1** |
| 个例根 A-T1 | 客户端同周变更（超时/重试次数/退避/SDK/新调用方） | 主因（若查到即定案） | 改配置 | 查一次变更与配置历史（≈0） | **1'** |
| 个例根 A-T4 | 重试与故障目标同源（热点分片/同一连接池/同一条慢队列） | 共因 | 改路由/退避 | 一次 per-shard p99 采样 | 2 |
| 个例根 A-T5 | 多层重试叠加（客户端×网关×服务内部） | 共因 | 改架构 | 数放大器层数（读配置） | 3 |
| **类根 B** | **共享依赖/状态漂移**（"机器没动、没发布"≠"什么都没变"） | 主因或共因 | **动不了**（要对方上游） | 一次延迟分解＋对方取证 | 2 |
| 个例根 B-T2 | 到达过程形状变化（缓存命中率/TTL/批任务重叠/流量结构） | 主因 | 改调度 | 一次命中率采样 | 2' |
| 个例根 B-T3 | 下游共享状态（数据增长/索引失效/连接增长/配额限流/邻居吵闹/证书DNS） | 主因 | 动不了 | 一次分解＋对方取证 | 3 |

**取前 N 去验证：** 前置 C + 类根 A 的开关测试 + A-T1 的变更记录 → 三条加起来不到一天，可覆盖绝大概率。B 类不放弃，但排在"证明 A 不足以解释"之后——**先证明放大器，再追扰动源，顺序不能反**（反了就会像现在这样，向一个没有自变量证据的一方索要改动）。

## 七、结论

**方向怎么判：** 不是判"谁先坏"，是判三件事——①计数守恒（尝试数在同一 hop 上对账）；②延迟分解（下游 handler 时间 vs 客户端总时长，这一条能当场杀死或坐实"下游变慢"）；③分钟级 lead-lag 加外部调用方对照。再加一次**可回退测试**（把重试关掉看 p99 是否回落）当仲裁。这四件事一天内能做完，成本远低于一次跨团队工单拉扯。

**根源在哪：**
- **类根（结构）：重试是开环的**——没有全局预算、没有抖动、没有熔断、重试目标与故障目标同源、与超时强耦合。它本是用来吸收偶发抖动的负反馈，被部署成了增益 >1 的正反馈，**于是任何一次尾延迟扰动都能自维持成一个更高的延迟稳态**。这是"为什么它能持续一整周、而不是跟着扰动衰减"的答案。
- **个例根（本次触发源）：** 在 A-T1（客户端同周变更）→ A-T4（热点同源）→ B-T2/T3（到达形状或下游共享状态漂移）这个顺序里查，**用数据查，不用责任查**。
- **"下游变慢"最多是共因，不是根。** 而且题面给的数量级已经在反对它作为唯一解释：+7.8% 的尝试量换不来 4.5× 的 p99，除非那 +7.8% 全部砸在最稀缺的资源上、或者系统本就贴在 ρ≈1 的刀刃上——这两种情况都说明**问题在结构，不在对方的手艺**。
- **3% 的基线才是本案最被忽略的证据**：环路早就在跑，团队把它当正常，才会把 11% 读成"外生冲击"。

**给团队的一句话：** 在你能用一次开关把重试关掉、并看到 p99 回落（或不回落）之前，"下游变慢"是假设，不是结论；拿假设去开工单，换回来的一定是"我们没变"。

## ⚠️ 异常 / 矛盾 / 空白

1. **最硬的矛盾：** "下游负载没变"与"客户端重试率涨到 3.7 倍"在计数上**不可能同时为真**（除非重试没真正发出）。这是全案第一优先要消解的点——不消解它，方向判断建在两套不同坐标上。
2. **"同一周"是题面能提供的最弱时间分辨率。** 双向因果只能在分钟级 lead-lag 上判；用周级相关性判方向，等于用两个端态给因果排序。
3. **两个关键数缺失，必须立刻补**：下游 **server-side handler p99（不含排队）**，客户端 **连接池/线程池排队时间**。有这两个数 + attempts 计数，方向当天可定；没有它们，任何结论都是叙事。
4. **口径未定义**：重试率是"额外尝试/请求"还是"被重试过的请求占比"？下游"负载"是入口 QPS、业务 QPS、还是 avg CPU？口径差一层，结论差一个量级。
5. **被延迟叙事掩盖的第二风险**：11% 的重试打在非幂等接口上 = 重复写/重复扣款。它不表现为延迟，但可能是本案真正的资损项，且现在完全没人看。

## 💡 灵感备注

- **最强的指纹其实是一个比值**：有效放大倍数 `1.078` 与 p99 放大 `4.5×` 差了近两个数量级。凡是"小增量负载 → 大延迟跳变"的系统，几乎必然是**排队贴边 + 方差放大 + 热点集中**三者之一；这个比值本身就足以把排查从"谁的锅"切换到"哪个排队资源"。
- **3% 的基线值得单独立项**：它说明重试在这个系统里早就是常态路径而非异常路径。把重试当常态 → 它必然退化成隐藏的负载均衡器与负载放大器。
- **可回退测试是被严重低估的诊断工具**：它把"因果推断"降级为"开关实验"，成本一次配置变更，却能一次性证伪整份归因。任何"对方慢所以我们才做 X"的争论，都该先问"X 能关吗、关掉会怎样"。
