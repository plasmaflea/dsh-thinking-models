L0 类别判定：**软件/服务调用链问题（`software` 节点）** —— 判据：症状由代码与配置姿态决定（重试率是配置与超时判定的函数），不随物理介质随机；伴随现象是确定性竞争（重试与排队构成正反馈，同输入同时序可复现）。｜已排除：硬件（机器未动、无 CRC/温度相关、下游自测指标平）、权限/账号（无 ACL 变化，失败集中在延迟而非拒绝）。**未排除但也不整体划出：网络与组织** —— 网络的症状必须经由"连接/路由"格体现，故保留为 L1 的一个格；组织（工单互甩）是本次结论的产物，不是机制，登记为树外分支。

**【方向判定：先立判据，再谈结论】**

方向不是靠"谁先喊"定的，只能靠四条正交检验。团队结论的真实缺陷在于它**建立在一个无法区分方向的观测粒度上**：数据是"同一周"，而周的粒度里两条曲线必然同涨，"谁先动"在信息上等于缺失。

| 检验 | 做法 | 判读 |
|---|---|---|
| ① 先行性 | 把两条曲线降到 10s/1min 粒度做交叉相关，看重试率的上升沿是否早于 p99 的上升沿 | 重试率先动 ⇒ 重试是自变量（方向反转） |
| ② 分层重算 | 把 p99 按 `首试 attempt` / `重试 attempt` 分层重算，而不是合并口径 | 首试 p99 平、合并 p99 涨 ⇒ 700ms 是重试把右尾加权，不是服务变慢 |
| ③ 算术守恒 | 重试率 +8pp，在无缓存无熔断时应让下游入站请求 +≈8%（`0.11/0.03` 的调用量比 ≈1.078） | 下游"负载没变"与"重试率涨 8pp"**算术上不能同时为真**，除非重试没到达下游或被口径吞掉 |
| ④ 归因分解 | 把 11% 按触发原因拆开：超时触发 / 可重试错误码触发 / 主动策略触发 / 连接类错误触发 | 增量集中在某一类配置（阈值、分类、预算）⇒ 那是自变量，不是延迟的函数 |

其中 ③ 是这场争论的**唯一硬约束**：两边的说法在算术上互相排斥，先把这条钉死，方向就出来一半。而"下游说没变"是**三个具体维度的否认**（负载/机器/发布），不是"我没变"的全集——它不是证词，是排除三项的一份清单。

**【恒等式轴：团队的结论等价于一个未验证的单因子假设】**

`观测 p99 ≡ 客户端进程内排队 + 建连/路由 + 网络 + 下游入口排队 + 下游服务时间 + 超时判定延迟`
`观测重试率 ≡ f(超时阈值, 错误分类, 重试预算, 真实失败率)`

下游的"我们没变"实际只覆盖了右端**一项**（服务时间）。团队把它当成了整个等式，于是得到"下游变慢"。但这个观测同样完全相容于另一种解读：**700ms 的增量根本不在下游服务时间里，而在它前面的排队结构里**——而"重试"正是唯一能凭空抬高那一段的东西。这就是"下游自测没变"与"你看到 900ms"能同时为真的结构性原因，也是重试放大的签名，不是对它的反驳。

L2 逐层回溯（轴＝一次调用的必经时序，一步一格；正交：每格有专属症状）

| 格 | 该格故障的专属症状 | 本次判定 |
|---|---|---|
| G1 客户端发出前（进程内排队：GC/线程池/连接获取） | 客户端自测延迟升、下游自测延迟平；重试集中在特定实例或整点 | 待验，成本极低（一次看客户端 GC/线程池/连接池等待指标） |
| G2 建连与路由（DNS TTL、keepalive、LB/网格、TLS 握手） | 新连接比例升、错误码集中在 connect/EOF、按 AZ 分层后差异明显 | 待验（重试会放大建连次数，形成二级放大） |
| G3 网络链路（丢包/重传/RTT/MTU） | RTT 抖动、重传率升、跨区实例同时恶化 | 待验，优先级低于 G1/G4（下游"机器未动"削弱但不排除） |
| G4 下游入口准入（accept 队列、并发上限、限流器、连接数配额） | **下游 QPS 升而完成吞吐平/降、并发占用升、排队时间升、self-time 不变** | **本格与"下游自测没变"完全一致，是主嫌** |
| G5 下游处理（handler、慢查询、缓存命中率、下游的下游、批任务叠加、GC/证书轮换） | CPU/GC/命中率/p99 同步变化；同一接口分层后双峰 | 待验——这一格是"三没变"覆盖不到的盲区，不能因对方否认就挂起 |
| G6 返回与超时判定（阈值、错误分类、预算） | 延迟分布不变而重试率跳变；某错误码计数阶跃；SDK 版本变更日对齐 | 待验，成本最低（一次配置/SDK diff） |
| G7 观测与口径（分母、聚合窗口、p99 来源、attempt 是否重复计入） | 仪表盘定义变更、分母从"调用"变"请求"、p99 由服务端自测变端到端 | 必查——G7 单独就能解释全部现象，且不需要任何系统变化 |

→ **类根（个大类在什么结构条件下必然可能发生）**：这条调用链**没有把"尝试（attempt）"与"请求（request）"分成两级**——既没有分层计量，也没有准入隔离（无重试预算、无抖动退避、无熔断、attempt 不独立限流）。于是重试不是被约束的补偿动作，而是一个**无界的正反馈放大项**：任何初始扰动（正常抖动、一次慢查询、一次 GC）都会被"超时→重试→占位→排队→更多超时"闭环放大，且现象在结构上必然表现为"重试率与延迟同涨"，而现有观测**无法判定谁在前**。
　└ **个例根（本次具体机制）**：最可能是「G6 的一次超时/重试策略变化（或 SDK 默认值随升级变化）点燃了 G4 的占位闭环」——重试率 3%→11% 是配置的函数而非延迟的函数，下游服务逻辑确实没变，变的是**到达它的并发占用形态**（突发 + 长占位），所以它自测负载/机器/发布确实"没变"。并列备选个例根：G7 口径变化（能单独解释全部）、G5 盲区慢化（被"三没变"漏掉）、G1 客户端停顿（能解释重试率与客户端观测 p99，但要求下游自测 p99 平）。三条检验（①②④）在当前信息下无法区分，必须取证。

L3 双根

- **处置根（修本次）**：不要先发给下游，先在**本侧**做三件事：把重试策略立即改为抖动退避 + 重试预算上限（重试流量 ≤ 成功流量的固定比例）+ 按 attempt 分层上报；同时把 ①②③④ 四条检验跑一遍，把 11% 按触发原因拆开。判据：即使下游完全无辜，重试预算也能把放大闭环在结构上关掉，p99 会先回落 —— 这本身就是方向的**判决性实验**（一次配置灰度，成本 = 一次采样 + 一次重启级操作）。
- **消解根（灭这一类）**：**让"重试"在结构上不可能是放大器** —— 调用层统一施加 `retry budget + 抖动退避 + 熔断 + attempt/request 两级分层计量与准入隔离`，并把 p99 的 SLO 口径（服务端自测 vs 端到端）写进跨服务契约。
　· 不可发生判据：若当时有重试预算与抖动退避，则重试流量被硬性限制在"不改变下游排队状态"的量级内，重试率与 p99 的互相放大**在结构上不可能发生**（不是变少见）；同时 attempt 分层计量让"方向判定"从叙事变成可算，本类争论不会存在。
　· 可执行首边：把客户端 SDK 的重试计数从"按请求"改成"按 attempt"上报，并给退避加 10%~full jitter（一天，一次配置灰度，不需要下游配合）。
　· 成本量级：**改配置级（人天级）**；打点改造与契约统一是**人力周级**。精确量级交 📐 公式图，本轮不虚报数字；放大系数的量级可用 `Δ并发占用 = R × r_retry × T_wait`（Little's Law）代入实测估算，判据是"Δ占位 / 可用并发额度"是否越过 10%~20% —— 越过后在 U>0.8 的排队系统里 p99 抬升数倍是常态。

L4 迁移出口（消解根指向架构/契约变更，故必列）
1) 计量改造：attempt 级指标、首试/重试分层 p99、分母定义统一（打点全覆盖）。
2) 口径契约：与下游共同定义 p99 是服务端自测还是端到端、错误码"可重试/不可重试"的语义，否则重试预算无法判定。
3) 组织能力：重试策略从各客户端自行其是收归平台统一（否则每团队退避参数不同，预算形同虚设）。
4) 容量模型：把"重试放大系数"写进容量规划与压测脚本（压测必须带重试注入）。
5) 责任边界：把"互发工单"改成共担的放大系数上限与 SLO 口径。

**结论**

1. **方向大概率被弄反了，但更准确的说法是：现在的观测粒度不支持任何方向判断。** "同一周"里两条曲线同涨，是重试放大闭环的**典型同时性**，不是因果证据。
2. **先证伪算术**：重试率 +8pp 应带来下游入站 +≈8% 请求。若下游"负载没变"为真，则这批重试没到达下游（被熔断/丢弃/口径吞掉），"下游变慢导致重试"就更站不住；若下游请求数其实涨了 8%，则他们说的"负载没变"指的是 CPU/机器数 —— 而排队延迟对占用是超线性的，8% 的量在最敏感的工作点上足以造成数倍 p99。**两种情形的下一步都指向同一件事：先查重试是不是自变量。**
3. **根源（类根）不在下游，也不在"团队该少重试"**，而在调用链把"尝试"当成"请求"：没有 attempt 级计量、没有重试预算、没有抖动退避、没有准入隔离，于是重试是一个无界的正反馈项，任何一个初始扰动都会被放大成 p99 抬升，且现象上必然与重试率同涨。
4. **最省钱的判决性实验**：本侧加抖动退避 + 重试预算（一次配置灰度）。若 p99 随之回落，方向判定完成；若不回落，嫌疑立刻收缩到 G5/G7 两格，再去要那两张表（下游 handler self-time / 慢查询，以及仪表盘 p99 口径定义）。
5. 工单方向应从"请你优化"改成"**请给我服务时间与排队时间分开的 p99**"——把争论从责任归属改成可分摊的量。
