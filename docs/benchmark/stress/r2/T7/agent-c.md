[🌳 林状图／回溯法] 选择理由：题面问「根源在哪」，而且**已经有一个现成结论等着被检验**（"下游变慢，所以我们才多重试"）。这正是回溯法的靶心——先把因果关系定成骨架（谁是谁的必要/充分条件），再判"这条能不能解释"。它同时是"谁先动"的方向问题：方向问题在原图上就是一条边的方向，所以必须在同一张图里对两个方向都给出可证伪判据，而不是挑一个顺手的。末段用 🧪 倒推图对团队结论做一次负边审计。

L0 类别判定：**分布式系统的"闭环容量/反馈控制"问题（`software` 节点的 `concurrency` 子层）**
判据：两端各自声明"我这侧没动"，而两个指标同向、同量级变化（重试率 ×3.7、p99 ×4.5）——这是**系统结构**留下的签名，不是某一处变更留下的签名；可复现性来自代码/配置/环境姿态（重试策略、超时值、连接池、限流阈值、自动扩缩策略），符合 `software` 节点两条判据。
已排除：硬件（无跨进程随机性、无 CRC/ECC/温度相关，两侧均未动机器）；权限/账号（无 403／找不到资源的形态）；纯链路可达性（不是不通或重置，是系统性尾部上移，且"未动网络"）。
**未排除、必须并列**：组织流程（团队的结论本身可能就是被工单驱动的归因，见挂起表 H7）。
> 注意：这里"类别"判得准不准，直接决定后面在不在正确的坐标系里回溯。若本题实为纯粹的第三方容量事故（例如共享 DB 邻居打满），L2 的层3（饱和）会全空而症状仍在——那时按技能规则必须换轴，而不是继续往"重试"上归因。

## L2 逐层回溯

**选轴（生成式，不是列举）**：用**恒等式 + 必经时序**双源切。
恒等式（每个请求的时间与并发被这两条等式唯一分解）：

```
客户端观测延迟 = Σ_i(第 i 次尝试的服务时间) + 客户端排队 + 网络 RTT + 重试退避 + 连接建立(DNS/TLS)
并发 L = 到达率 λ × 持有时间 W        （Little's law：p99 由并发驱动，不是由均值 QPS 驱动）
排队 W ≈ S / (1 − ρ)                 （利用率 ρ 是唯一的放大器）
```

必经时序（一次扰动要变成风暴，必须**依次**经过这五格，缺一格环就断了）：
触发 → 放大 → 饱和 → 返回 → 观测。这五格就是本次的轴：它满足三判据——正交（各格根不互相解释对方症状）、可生成（环的每一步必然存在，缺一步正反馈不成立）、可观测（每格有专属症状，见下）。

| 层 | 轴格 | 这一格在管什么 | 该格故障的**可观测症状**（本题对应现象） |
|---|---|---|---|
| 层1 | **触发**：首次尝试为什么会失败 | 到底哪一类失败在喂重试 | 重试原因分布：timeout／connect 失败／5xx／429／reset。**若 timeout 占绝对多数 ⇒ 环是"延迟型"**；若是 5xx/429 ⇒ 下游在甩负载，"负载没变"立刻为假 |
| 层2 | **放大**：重试如何变成额外负载与被放弃的工作 | 重试系数、被放弃但仍在跑的服务端工作 | attempt≥2 的请求占比 ×3.7；服务端"已取消/客户端已断开仍在处理"的请求数上升；非幂等重复执行 |
| 层3 | **饱和**：额外负载落在哪个资源上 | 是带宽/CPU，还是并发/线程/连接池/队列 | **入口 QPS 平、但并发 in-flight、线程池、连接池水位、队列深度上升；下游 CPU 平、线程/连接全在等**——这就是"负载没变却变慢"的直接物理机制 |
| 层4 | **返回**：延迟如何变成更多重试 | 超时阈值与延迟分布的相对位置 | 重试率 r 不是独立观测量，它是 `r = P(延迟 > timeout) + P(错误)`：p99 从 200→900ms 跨越固定 timeout（1s 量级）时，r 会**阶跃式**从 3% 跳到 11%，而且分钟级上 retry 曲线应滞后 p99 约一个 timeout 窗口 |
| 层5 | **观测**：这个环如何被误读／被测量放大 | 两端 p99 是不是同一个东西 | 客户端 p99 含排队+退避+连接建立+重试，下游 p99 只是 handler 时间；P99 若按 per-host 平均或采样率不同则不可比；超时被放弃的请求在下游指标里可能根本没进统计（coordinated omission），使下游"看起来没变" |

全格检查：五格**都非空**，所以**坐标系没选错**——本题确实是一个自持环，不是一个单向因果链。

### → 类根（这一大类在什么结构条件下必然可能发生）

> **类根：重试的成本被外化到下游，而环路里没有任何负反馈闸门。**
> 上游做重试决策的边际成本 ≈ 0（它只多花一点自己的时间），代价（并发、队列、被放弃的工作）全由下游承担；同时下游的拥塞信号（429/Retry-After、队列深度、剩余并发）**没有通路回流到上游的重试决策**，deadline 与取消也不传播。
> 在这个结构下，**任何微小的尾部延迟扰动都必然被放大成正反馈**，而且一旦进环，"谁先动"在数学上不可辨识（两个方向产生完全相同的签名）。所以根不在"谁先变慢"，根在"**为什么一次微小扰动无法自愈**"——环路增益 ≥ 1。

### └ 个例根（本次具体机制，挂在类根之下，不是平行清单）

> **个例根：+9% 的平均负载，落在下游接近饱和的利用率余量上，被 1/(1−ρ) 放大成 4.5 倍的尾延迟。**
> 重试的几何级数：平均尝试次数 = 1/(1−r)。r=3% → 1.031；r=11% → 1.124。**平均负载只 +9%——所以下游"我们负载没变"在它自己的口径里可能完全诚实**（+9% 常常落在"没变"的噪声带里）。
> 但 p99 不是被平均负载驱动的：M/M/1 的 `W = S/(1−ρ)`。ρ=0.90 时，+9% 到达率把 ρ 推到 ≈0.98，`(1−ρ)` 从 0.10 掉到 0.019，**排队延迟放大 ≈5.3 倍**——你观测到的 4.5 倍，正好是这个量级。反过来算：要让尾延迟 ×4.5，只需要 ρ 从 0.90 挪到 0.978，**只需要极小的余量消耗**。（量级粗算，严格定量交给 📐 公式图；此处只用于判断"9% 够不够"这个问题——够。）
> 叠加项（同向、可叠加，不必二选一）：重试命中时恰好是拥塞窗口，且超时后**服务端仍在算**（无取消传播），持有时间 W 上升 → Little's law 下并发涨得比 9% 多得多（若基线均值 250ms、timeout 1s、r=11%，客户端侧持有时间约 250 + 0.11×800 ≈ 340ms，**并发 +35% 量级**）。并发才是队列的真正驱动量。
> **扣扳机的手（触发器，不是根）**：同一周里某个"没人认为是变更"的变化——客户端 timeout 或被下调/新增一层重试/去掉 jitter/连接池缩小、流量结构变化、下游某个依赖（缓存命中率、DB、DNS、证书轮换、LB 权重、mesh 配置漂移）、数据形状（热 key、payload 变大）、或自动扩缩按 QPS/CPU 定标因此**根本没触发扩容**。

**一句话方向结论**：团队把"重试率"当成对下游健康度的**独立观测**，其实它是延迟分布相对于超时阈值的**函数**——`r = F(timeout)`。两个数字不是两条证据，是同一条证据的两面。所以"下游慢 → 我们多试"和"我们多试 → 下游慢"**在相关性上完全等价**；用这两条数据判方向，判不出来，只能判出"这里有一个环"。方向必须靠**操纵**或**重试碰不到的不变量**来定。

## 判定方向的判定表（按成本从低到高，先便宜后昂贵）

| 步 | 动作 | 成本 | 读法（决策规则） |
|---|---|---|---|
| 0 | 先对齐口径：取**同一请求集**，两端同 percentile、同窗口、同采样；确认客户端 p99 是否含排队/退避/连接建立/重试 | 一次查询 | 若两边 p99 差一个量级 ⇒ 后面所有争论作废，先修测量 |
| 1 | 拆**重试原因分布**（timeout／connect／5xx／429／reset） | 一次查询 | timeout 为主 ⇒ 延迟型环；5xx/429 为主 ⇒ 下游在甩负载，"负载没变"当场为假 |
| 2 | 查下游的**利用率余量 ρ 与并发水位**（不是 QPS）：in-flight、线程池、连接池、队列深度 | 一次查询 | **这是判方向的支点**：ρ 高且并发涨 ⇒ 环在上游（重试是主因）；ρ 低且并发平 ⇒ 另有原因（中间段/测量/第三方/数据形状） |
| 3 | 查**重试碰不到的不变量**：下游 CPU per request、队列深度、取消/断开计数、重试免疫的对照组延迟 | 一次查询 | 这些平而 p99 涨 ⇒ 慢在"等待/并发/调度"，不在"计算"，也不是他们的发布 |
| 4 | 看**相位**：分钟级互相关，retry 率与 p99 谁领先 | 一次查询 | retry **滞后** ≈ 一个 timeout 窗口 ⇒ 重试是果；retry **领先** ⇒ 重试是因（自家客户端不会无端多试 ⇒ 一定有人在改策略或第三方在重试） |
| 5 | **操纵实验（决定性）**：1% 流量 retry budget = 0（或单可用区关重试），持续 1 小时 | 一次灰度，可逆 | 下游 p99 跟着回落到 200ms（而其总负载只变了 <1%）⇒ 重试就是因，环成立；下游 p99 仍 900ms、只是该 cohort 失败率上升 ⇒ 下游确实慢，工单方向成立 |
| 6 | **反向实验**：下游不动，用**固定平均 QPS、无重试**回放，看 p99 是否回落 | 一次压测 | 同一平均负载、p99 回落 ⇒ 是**负载形状/并发**在杀人，不是负载量 ⇒ 下游"负载没变"与技术事实不矛盾 |

判据级别的硬话：在没做第 5 或第 6 步之前，**任何一方对"方向"的断言都只是相关性叙事**；尤其团队的两条数据构成循环。第 2 步是性价比最高的支点（一次查询就能把方向劈成两半）。

## L3 双根

### 处置根（修本次，可逆、当班可做）

1. **立刻做判定+止损合一**：1% 流量 `retry budget = 0` 灰度（同时是上面第 5 步），拿到方向结论再决定放量。
2. **重试改成 full jitter 指数退避**，去掉同步重试（同步重试把重试变成脉冲，p99 峰值被自己抬高）。
3. **只用一层重试**：禁止 SDK／网关／业务各自重试相乘（n 层 × m 次 = mⁿ 倍最坏放大）。
4. **per-attempt timeout 改为"剩余 deadline 的分数"**，不再用固定 timeout；总预算封顶，重试不能延长总预算。
5. **打开取消传播**：客户端放弃即 cancel，别让下游继续替你算账（这条同时修掉"负载没变"的错觉）。
6. **给下游一张清单而不是一张工单**：请他们报 ρ／并发／队列／取消数／依赖与证书与 mesh 的变更审计，而不是请他们"优化"。

### 消解根（灭这一类）

> **把"重试"从上游的本地决定，变成共享容量上的全局预算 + 有反馈的闭环：**
> ① **retry budget**：重试总量 ≤ 总请求的固定比例（如 ≤10%），全局 token bucket 共享，预算耗尽即放弃并**快速失败上报**；
> ② **单层重试**（只有最外层可重试，内层直接失败上抛）；
> ③ **full jitter 退避** + 尊重 `429`／`Retry-After`（下游的拥塞信号必须能命令上游停手）；
> ④ **deadline 传播 + 取消传播**（超时即取消服务端工作）；
> ⑤ **容量定标量从"均值 QPS"换成"并发 + 尾部"**（按 Little's law 与 ρ 定容量，自动扩缩看 in-flight/队列/延迟而不是 CPU/QPS）。

- **不可发生判据**：若 ①②③④ 同时成立，重试量有**硬上界**且与瞬时失败解耦，超时**不再新增服务端工作** ⇒ 环路增益 < 1，正反馈在**结构上**无法自持。此时外部扰动仍然存在、延迟仍会上升，但只会是**有限的、可恢复的**上升，不会变成 4.5 倍的风暴。注意这是"消解"而非"缓解"：缓解是"我们少重试点"，消解是"重试不可能自我喂养"——即使明天有人又加了重试层，预算与单层约束也会把它夹住。
- **可执行首边**（从现状出发的第一步，可以很小）：**这就是上面的 1% 灰度**——它同时是判定边与止损边：一行配置（灰度标 + 预算 0）+ 一个计数器，人时 1~2 小时，完全可逆。第二步才是把 token bucket 写进客户端 SDK/网关的统一出口。
- **成本量级**（只给量级，严格数字交 📐 公式图）：若重试逻辑集中在统一 SDK 或网关，①~④ 约 **1 人周量级**；若散落在各业务调用点，按"调用点数 × 0.5 人日"估，10 个点约 **1~2 人周**。取消传播若已是 HTTP/2 或 gRPC，多为配置级（**1~2 人日**）；若是自研 HTTP/1.1 长连接，需要协议层改造（**数人周**）。⑤ 的扩缩指标替换是**配置级 + 1 人日**。

## L4 迁移出口（消解根是"换结构"，这是它合法性的来源）

1. **重试策略的所有权**：SDK／网关／业务三层谁负责重试、配置如何统一、如何防漂移（当前是"谁都能加一次重试"）。
2. **错误契约**：可重试 vs 不可重试错误码的划分、`429 + Retry-After` 语义、幂等键的强制位。
3. **deadline 传播**：跨语言/跨 mesh 的"剩余预算"语义（gRPC deadline、HTTP 超时链、网关裁剪）。
4. **可观测性重构**：按 attempt 拆分的指标（attempt=1 与 attempt≥2 分开看）、服务端取消/断开计数、in-flight 与队列深度、**两端同口径 p99**、重试免疫对照组。
5. **容量模型**：把重试计入容量（`λ_eff = λ/(1−r)`），自动扩缩的定标量换成并发与尾部延迟。
6. **组织**：谁拥有 retry budget 与 SLO 预算；上下游联合 SLO（"我们共同拥有这个 p99"）取代互发工单。
   → **本次问题降级为第 4 项 + 第 5 项**：本次"p99 涨 4.5 倍"其实只是"容量与可观测性没有把重试与并发计入模型"的一个子项。照此办理，下一次同类扰动会被预算夹住而不是变成风暴。

| 个例根 | ⑤ 观测口径不一致／coordinated omission（客户端 p99 ≠ 下游 p99） | 次要，但足以伪造"下游变慢" | 改配置 | 一次查询 | **必须最先排掉，否则后面全白做** |
| 个例根 | ⑥ 非幂等重试导致的重复执行/锁竞争抬高下游尾部 | 次要 | 改架构 | 一次查询（重复执行计数） | 与②同批查 |

排序的预算论证：①的 Cost 是"一次配置 diff"，⑤是"一次口径查询"，两者都在**分钟级**，所以排在最前；第 5 步灰度的 Cost 是"一次可逆灰度"，是唯一能把方向**闭合**的动作，所以它虽贵但不可省。**其余候选留在挂起，不删除。**

## 结论

1. **你无法用这两条数据判方向，因为它们是同一份证据**：重试率 ≈ P(延迟 > timeout)，是延迟分布对超时阈值的读数，不是独立观测。两个方向的因果产生完全相同的签名，所以这里存在的是**环**，不是箭头。
2. **判方向只有两条路**：(a) **操纵**——1% 流量 retry budget=0（或单可用区关重试），看下游 p99 是否跟着回落；(b) **重试碰不到的不变量**——下游的 ρ/并发/队列深度/取消数/CPU per request，以及两端同口径 p99。最便宜的支点是一次查询拿到"下游利用率余量 ρ 与并发水位"：**ρ 高且并发涨 ⇒ 主因在上游重试；ρ 平且客户端 p99 远高于服务端 handler p99 ⇒ 慢在中间段／测量／第三方，下游无辜**。
3. **数量上"9% 挡不住"这个辩护不成立**：重试系数 1/(1−r) 只把平均负载从 1.031 抬到 1.124（+9%），但 p99 由 `1/(1−ρ)` 驱动；ρ=0.90 时 +9% 就够把尾延迟放大 5 倍量级，正好是你观测到的 4.5 倍。**"我们只加了 9%"不是理由，它就是解释。** 而"下游负载没变"若只测均值 QPS，恰恰漏掉了真正的驱动量：并发与被放弃的工作。
4. **根源**（两个根，按技能要求分层）：
   - **类根**：重试的成本被外化到下游，环上没有负反馈闸门（retry budget / 429 尊重 / deadline 与取消传播），所以任何微小尾部扰动都必然被放大，且"谁先"不可辨识。
   - **个例根**：本次是"重试放大 ×(接近饱和的 ρ)"，触发器是同一周某次"没人认为是变更"的变化（客户端 timeout/重试策略、连接池、流量形状、下游依赖或邻居、扩缩未触发），触发器只是扣扳机的手，枪是类根。
5. **动作顺序**：先 1% 灰度关重试（判定+止损合一，1~2 人时，可逆）→ 同时一次性对齐口径、拆重试原因、取 ρ 与并发 → 再按结论走"预算+单层+jitter+deadline/取消"的消解根。给下游的请求应从"请优化"改成"请报 ρ/并发/队列/取消数 + 依赖与邻接变更审计"。
6. **三句话版**：这不是"谁慢谁错"，是"我们没有让重试为它消耗的共享容量付费"。方向上先用一次关重试的灰度定案，别再用相关性互相举证。根因是不可自愈的正反馈结构，不是某一次性能回退。

[✅ 验证] 本题为纯推理题，无外部数据可校验；已核对的两处内部一致性：①几何级数 1/(1−r)：r=3%→1.031、r=11%→1.124（平均负载 +9.0%）；②M/M/1 `W=S/(1−ρ)`：要让 W 放大 4.5 倍需 `(1−ρ₂)=0.10/4.5=0.0222`，即 ρ 从 0.90 → **0.978**，故"4.5 倍尾延迟"与"平均负载只涨 9%"在物理上完全兼容。技能前置工作已执行：知识树按序取到文件（见 L1 四元组路径），无静默降级。

[⚠️ 异常/矛盾/空白]
- ⚠️ **题面**「下游服务的 p99」未说明测量点：是下游自己的服务端 handler p99，还是我们客户端观测到的调用 p99？内容差别是定性级的（后者含排队/退避/连接建立/重试，且受 coordinated omission 影响）。建议：任何判方向之前先把这一条钉死，否则第 1 步就分叉。
- ⚠️ **题面**「下游自身负载没变」未说明测量量：均值 QPS？并发？CPU？入口还是 origin？内容差别决定这句话是事实还是盲区。建议：要求按秒的并发/in-flight/队列曲线，而不是日均 QPS。
- ⚠️ **题面**未给客户端的 timeout 值与重试次数。p99=900ms 与 timeout 的相对位置是"3%→11% 为何阶跃"的关键；缺此数只能给判定规则，不能给定量结论。
- ⚠️ **题面**未给"我们"在总流量中的占比。若我们只占下游 5%，则 11% 重试只对下游贡献 0.5% 额外负载，类根 A 的份额必须下调、H8（第三方）与 H10/H11 需上修。建议：这一条是分流第一优先。
- ⚠️ **技能侧**：现有知识树（v1）没有"跨服务反馈环"与"测量口径"两个层，本次两个关键分支都落在树外（H6 已登记 v2 候选）。这不是结论的问题，但意味着下一次同类题若照本树实例化，会**系统性漏掉这两层**。

[💡 灵感备注]
- 一句话判据可以固化成 SLO 条款：**"任何一次重试，都必须能说出它消耗了谁的哪一份余量"**。说不出来的重试就是无主债务。
- 有个便宜的常驻哨兵：**同一时刻对比 attempt=1 与 attempt≥2 的延迟分布**。若 attempt≥2 明显更快，说明下游没坏、是我们自己在排队/超时太紧；若 attempt≥2 也更慢，说明下游饱和或环已在跑。两行 SQL 级别的指标，比任何工单都先给出方向。
- 更根本的反问（可写进复盘）：如果重试是免费的、有效的，那为什么它会让 p99 从 200 涨到 900？——因为重试优化的是**单请求的成功率**，代价记在**系统的尾部**。这两者被同一个指标（成功率）掩盖，这是这类争论永远吵不完的结构性原因。
