[🌳 林状图] 选择理由：题面问的是「根源到底在哪」，且附带「怎么才能让它不再被打」——这是要消解整类事件，不是修本次单点，属于因果深度未知 → 林状图／回溯法。未知不在选项广度（不是「有哪些防守手段」），也不在数量关系（成本只要求量级），故本轮不并联网状图与公式图；成本只给量级，精确数字属 📐 公式图，不在本题范围内展开。

## L0 类别判定

**类别**：软件·安全（暴露面 × 供应链缺陷）——更精确地说，是「**同一大类事件按固定节律复现**」，不是「某个功能坏了」。

**判据**：
1. 可复现性来自代码／配置／环境姿态，不来自物理介质：每次入侵都能落到具体组件、入口或配置姿态（已停维护的运行时、公网可达的后台、无维护的第三方组件），换一台等价机器同样成立。
2. 失败是确定性的或由确定性竞争导致：给定同样的入口集合与版本号，利用可复现；「随机」的部分只来自攻击者何时来（外生时序），不是位翻转。

**已排除的大类**：
- **硬件故障**：无 CRC/ECC、无跨进程随机性；症状与具体 CVE／入口一一对应。
- **网络问题**：不是「到不了」，恰恰是「太到得了」；无丢包／超时／分层不可达形态。
- **权限／账号体系**：ACL、令牌、组成员关系不是根；凭据被滥用是入侵**之后**的现象，不是原因。
- **纯组织流程**：技术面上仍存在明确的可利用缺陷，尚未到「技术全正常、只剩人」的地步（该大类被推迟，未被否认，见挂起表第 9 行）。

## L2 逐层回溯

**轴（生成源＝恒等式，不是列举）**：一次攻击尝试要变成一次**成功**入侵，必须穿过五个因子，缺一即事件为 0。

```
月成功入侵次数 = F(攻击尝试) × E(可达入口) × D(入口上的可利用缺陷) × (1 − B 拦截) × (1 − R 检出清除)
```

- **可生成性**：这是乘法链，任一因子归零则乘积归零。
  → 由此得到本题唯一的解题方向：**要「不再被打」，数学上只有一种答法——把某一项打到 0，而不是把它压小。**
- **正交**：五个因子各自的失效不能互相解释（F 是外生、E 是网络姿态、D 是版本供应链、B 是拦截设备、R 是发现能力）。
- **可观测**：每格都能用一句话采到症状（见下）。

### 层1 — F 攻击尝试
症状：防守方根本看不见（你只看到每月成功的那一次，看不见每月数百万次扫描）。
判定：**外生**。防守方无杠杆。→ 不在此格找根（挂起表第 7 行）。

### 层2 — E 可达入口
症状：用一台外网机器能否直接 `curl` 到后台登录页。现状：**能**（否则不会被打）。
并且**从未被枚举**：现在没人能回答「我们一共有几个入口」（主后台／子站／旧接口／上传点／phpMyAdmin／旧测试目录／备份的 .sql 与 .zip／编辑器／图床／遗留 API）。
判定：该格有缺陷，且缺陷的形态是「**未知**」，不是「已知但没修」——这是它区别于其它四格的地方。

### 层3 — D 入口上的缺陷密度
症状：能否把所有组件（PHP／框架／CMS／插件／中间件／Web 服务器）列成版本清单并与 CVE 对照。现状：**不能**。
关键不在「版本旧」，而在**供给方**：PHP 5.6 的安全支持已于 **2018-12-31 结束**，第三方组件无人维护 → **D 由外部持续补充，不因你不改代码而下降**。
这是「补完这个月、下个月换个地方」的第一性来源：你不是在漏水，你在一艘持续下沉的船上。

### 层4 — B 拦截
症状：被利用的那个请求，有没有在到达应用之前被拒绝。现状：无 WAF／无虚拟补丁／后台无前置认证／无反代规则 → **B ≈ 0**。

### 层5 — R 检出与清除
症状：从 webshell／异常文件落地，到被发现的时间。现状：**≈ 一个月**（因为「被打」是你唯一的告警）→ **R ≈ 0**。
这一格同时解释了「**每月一次**」的**节律**：你的发现周期是「月」，事件的可见性由攻击者的下一步行动决定，不由你决定。

### → 类根

> **防守动作的粒度（个案：一个月补一个 CVE）低于攻击发生的粒度（类别：自动化扫描器穷举全部已公开 EXP）；同时 E 从未被枚举、B 与 R 接近 0、D 的供给方已经退役。**
> 在这样的结构里，任何单点修补都不可能收敛发生率——「换个地方再被打」是结构产物，不是运气差，也不是某个人手慢。

```
类根：防守粒度错配 ＋ 暴露面未枚举 ＋ 缺陷供给方已退役 ＋ 无拦截无检出
  └ 个例根①：本次的具体入口（某个上传点／某个旧插件／某个弱口令后台）
       —— 只解释「这次」，不解释「每月」；补掉它，类根原封不动。
  └ 个例根②：首次入侵留下的持久化残留是否从未被清除
       —— 这决定了「换地方」到底是「新洞」还是「同一个后门的另一个触发点」。
          必须先验证再动手（候选根排序第 1 位，Cost 最低）。
```

## L3 双根

### 处置根（修本次）——必须做，但不回答老板的问题

- **（a）先取证，再修补**：核心文件哈希对比官方发行包；查 crontab／计划任务／开机项；查上传目录与数据库中的可疑内容；查访问日志定位 webshell 首次落地的时间与来源 IP。
  **在确认「没有残留」之前，不要只补洞**——否则下个月的「新洞」可能是同一个后门的另一个触发点。
- **（b）清与换**：补掉本次入口；用官方包覆盖被改文件（不要手工删）；**轮换全部凭据**（数据库、后台账号、API key、SSH/FTP、第三方对接密钥）；核查数据是否被外带（合规与通知义务落在这里，不在技术里）。
- **（c）成本量级**：人日级。**但它只把 D 压低一点点，完全不改变「下个月」。**

### 消解根（灭这一类）

> **把乘法链里的 E 打到 0，把 D 的供给方退役，并把 B、R 从 0 抬到「小时级」。**

**① 收敛暴露面（唯一能实现「不再被打」的动作，也是第一条可执行边）**
后台与所有管理入口撤出公网：只经 VPN／零信任网关／堡垒机访问，源 IP 白名单落在反代或安全组上，并给后台加一道前置认证。
- **不可发生判据**：不可达的资产不可被枚举、不可被利用。只要「公网可达的管理入口数 = 0」，则「每月换个地方被打」在**结构上不可能发生**——注意判据是「结构性不可能」，不是「变少」。
  残留风险必须一并列出（否则这条判据是假的）：内部人员、供应链投毒、钓鱼取得的合法凭据、以及**已存在的持久化残留**（所以①必须与处置根（a）同时做）。
- **可执行首边**：本周在反代／安全组上加一条「仅允许公司出口 IP ＋ VPN 段访问 `/admin` 与后台端口」的规则——**不改 PHP 一行代码**；同日发出 VPN／白名单开通指引。
- **成本量级**：**1–3 人日 ＋ 一次跨部门协调**。
  → 这就是回答「18 人月业务不批」的钥匙：**消解根不需要重写，它是一次配置变更。**

**② 把「补洞」从个案升级为类别（抬 B 与 R）**
前置一道虚拟补丁层（WAF／反代规则，按 OWASP CRS 起步）＋ 文件完整性监控（FIM）＋ 访问日志集中与告警（后台登录、上传、异常 UA、非工作时段）。
- **不可发生判据：不成立**——这条只能把概率压小，是**缓解**而非消解。所以它是②，不是主根。诚实标注，不冒充根。
- **首边**：先只做一件事——把后台登录与上传的成功／失败日志集中到一处，并配一条告警。**一天。**
- **成本量级**：人日到人周。

**③ 退役已 EOL 的运行时（切断 D 的供给）**
PHP 5.6 → 受支持版本，但**不做 18 人月一次性重写**，而是**绞杀者模式（Strangler Fig）**：新功能／新接口走新栈，老页面按访问量排序逐个迁移；对外暴露面永久锁在①后面，让「迁移没做完」不再等于「随时被打」。
- **不可发生判据**：单独看不足（旧代码还在）；**与①组合后**才成立——①负责「打不到」，③负责「迟早不用打」。
- **首边**：先用容器化新栈跑一个只读报表页，验证会话／权限／数据库连通。
- **成本量级**：人月级、**可切片**（按页面／按接口），可放进正常迭代预算，不需要专项审批。

## L4 迁移出口

消解根（①收敛暴露面 ②拦截与检出 ③运行时退役）必然带出下列新问题；**本次问题降级为其中一项**：

1. **凭据与权限模型**：后台退出公网后，外包／驻场／远程办公／移动端怎么进？需要 VPN／零信任账号的发放、回收、双因素、最小权限——这是新模型，不是「关个端口」。
2. **运行时退役的兼容性清单**：`mysql_*` → `mysqli`/`PDO`、短标签、`ereg`、魔术引号、PHP 7 的严格类型与弃用告警、扩展缺失（mcrypt 等）→ 必须按文件／接口清点，工作量按清点结果定。
3. **数据与状态**：会话存储、上传目录、计划任务、定时导出在容器化后的落点；迁移时的一致性校验与回滚点。
4. **可观测性落点变化**：日志／审计／文件完整性基线放在哪、保留多久、谁看；「能回答谁在什么时候从哪个 IP 进了后台」成为新的验收项。
5. **组织能力**：每月补丁例会换成什么？需要一条 SLA（高危 CVE 公开后 N 天内必须处置）＋值班与审批链；否则①之后依然会因「忘了打」再出事——那时是内部横向，不是公网。
6. **业务连续性**：白名单误封导致外部合作方进不来的回滚预案与联系人。

→ **本次问题（这个月的这个洞）降级为第 2 项清单里的一行 CVE**：它从「事件」变成「退役清单上的一个待办」。

## 结论

1. **根源不在某个 PHP 文件，也不在「没重写」**，而在：**你在按个案补一个按类别发生的攻击**。管理入口从未被枚举（E 未知）、缺陷由已退役的运行时持续供给（D 不会自己下降）、拦截与检出都接近 0（B、R≈0）——所以「补一处、换一处」是结构必然，换人、加班、补得更快都不改变它。
2. **要「不再被打」，数学上只有一条路：把乘法链里的某一项打到 0。** 最便宜且唯一能做到的是 **E：把管理入口全部撤出公网**（VPN／零信任／IP 白名单 ＋ 前置认证）——**1–3 人日的配置变更，不需要 18 人月，也不需要业务批专项预算**。并行把 B、R 从 0 抬到「小时级」；PHP 5.6 的退役走绞杀者分片，进正常迭代，不进专项。
3. **但动手之前先花半天做一次鉴别诊断**：这个「换地方」到底是新洞，还是第一次进来后留下的后门从未清干净。若是后者，处置根是「从可信基线重建」——继续逐点补洞等于永远在补错的地方。
