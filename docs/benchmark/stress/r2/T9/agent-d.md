# 老 PHP 后台「每月被打一次」的根源回溯

[🌳 林状图]［选择理由］题面问的是「根源到底在哪」＋「怎么才能让它不再被打」——这是典型的**因果深度未知**，不是选项广度未知，也不是数量关系未知。且症状具有强周期性（每月一次），说明背后存在一个**稳定结构**而非偶发事件。故用林状图／回溯法，并以「消解根」而非「加固建议清单」作为交付物。

---

## L0 类别判定

**类别：`software`（软件问题）**
判据：① 失败来自代码/配置/环境姿态而非物理介质（同一套代码换台机器同样会漏）；② 失败是确定性的——漏洞在那里就一定可被利用，不确定的只是攻击者什么时候来。
**已排除的大类**：硬件故障（无跨进程随机症状、无校验错误族）；网络问题（链路可达性正常，问题不是「通不通」而是「通了以后能干什么」）。

⚠️ 同时**保留两个不得静默丢弃的旁支**：
- 「权限/账号体系」与「组织流程」在树里是 L0 排除项，但本题的排除只在**主因层**成立——技术层确实异常（EOL 栈、无防护），所以不落进「技术全正常但人被卡住」那一类；但「业务不批 18 人月」这一条是组织约束，必须回到**汇合层**处理（见 L3 消解根与挂起表），否则整个结论不可执行。
- 题面只有「被打」这一句，**没有任何取证结论**。所以本图的主线建立在「外部攻击、经公网入口」这一假设上，该假设在挂起表里单列一条，写明恢复条件。

## L2 逐层回溯

**选轴（生成式，非列举）**：轴取**「安全事故应答循环的必经时序」**——因为「每月一次」的周期本身就是该循环的转数，时序轴天然对齐症状的周期性。恒等式 `失守 = 可达入口 ∧ 可利用缺陷 ∧ 未阻断 ∧ 未发现` 作为每一相位的填充因子。三判据校验：**正交**（「入口开着」不解释「发现滞后」）；**可生成**（每一步都是应答流程的必经动作，跳过任何一步该流程就不成立）；**可观测**（每格有专属症状）。

### 层1｜暴露相位：入口从恢复完成的那一刻起就回到公网
- **该格故障的可观测症状**：攻击日志里出现境外 IP 直接命中登录页/上传接口/`?id=` 类参数，请求没有前置跳转、没有办公网来源；资产清单里有人答不出「这个后台为什么必须在公网」。
- 根：**暴露面没有所有者**。「这个后台该不该在公网」不是任何一个人的职责项，于是默认永远在公网。

### 层2｜缺陷供给相位：技术栈被冻结，缺陷按时间复利
- **症状**：PHP 5.6（2018-12 已终止安全支持，此后所有新 CVE 永不回补）；第三方组件版本号停在 2015–2018；代码里存在字符串拼接 SQL、`unserialize()`、`include($_GET)`、`eval`、上传白名单缺失、模板直接回显。「换地方再被打」正是这一格的指纹——补丁有效（补过的地方确实不漏了），但**供给速率恒为正**。
- 根：升级被「业务不批」锁死，于是技术债按复利计息，且利息以「每月一次事故」的形式支付。

### 层3｜发现相位：你们的漏洞扫描器就是攻击者本人
- **症状**：判断「有没有洞」的时机永远是「被打之后」；安全事件的第一发现渠道是业务异常/客户投诉/监管通报，而不是自己的告警；系统里没有依赖清单，答不出「我用了哪些组件、哪些有 CVE」。
- 根：**检测能力外包给了对手**。发现延迟 = 对手兴趣的延迟。这一格是「每月一次」而不是「每年一次」的直接原因之一：供给无限，而唯一的质量反馈来自入侵。

### 层4｜应急相位：收敛到「个例」而不是「类」
- **症状**：复盘纪要写的是「本次通过 XX.php 的 id 参数注入进入」，动作是「修补该文件该参数」；没有一条动作是「为什么这个文件本来就能被公网直接调用」。补丁单上是 1 个点，不是「这一类汇聚点的全集」。
- 根：修复的判据是「这次不漏了」，不是「这一类不可能了」。**个例根被当成类根处理**。

### 层5｜恢复相位：恢复的定义是「回到事故前的构型」
- **症状**：重装/回滚/换目录/删 webshell 之后，版本号、配置、口令、开放端口与事故前完全一致；数据库账号、`APP_KEY`/会话密钥、第三方凭据**未轮换**；恢复验收标准是「业务能跑」。
- 根：**恢复的安全判据被定义为「与事故前一致」，而不是「与已知不安全构型不同」**。而被攻破的构型本身就是「含有未知可利用缺陷」的构型——**于是每次恢复都精确复位到一个已知不安全的状态，循环的重置点是不安全基线，不是安全基线。**
- ⚠️ 这是本图中**唯一能解释「周期性」的格**：层1–4 任何一格都可能「这次运气好」，唯有层5 保证下一次必然重来。**不轮换凭据（尤其数据库口令与密钥）是最常见的「下个月换个地方再被打」的前因**——打掉 webshell 但口令没换，攻击者手里留的是一把钥匙，不是一次机会。

### → 类根（面对整个大类）

> **这套系统没有一个「独立于业务代码、且被强制经过」的安全边界。**
> 直接后果是四个量同时成立且都是常量：① 攻击面**不可枚举**（没人能列出它的入口全集，更列不出缺陷全集）；② 缺陷**供给恒为正**（EOL 栈 + 冻结组件）；③ 发现权在**对手**手里；④ 恢复动作**复位到不安全基线**。
> 这四者叠加，使「每月失守一次」不是失误、不是运气差，而是一个**稳态**——补丁不改变「有多少洞」，只改变「洞在哪」。老板看到的「每月一次」，就是这个稳态的特征频率。

### → 个例根（挂在类根之下，是子节点，不是平行清单）
本月经某具体入口被利用的那个具体缺陷（注入点／上传绕过／反序列化／弱口令／组件 CVE）。它解释**这一次**为什么会失守，不解释**为什么每月都有一次**。

## L3 双根

### 处置根（修本次——治标，但必须做对）
不要只删 webshell。按序：① 从外到内定位真实入口（不是第一个被写入的 webshell，是第一个被利用的请求）；② 清除驻留（计划任务、启动项、`.user.ini`/`auto_prepend_file`、`php.ini` 篡改、后台新增管理员账号）；③ **轮换全部凭据**（数据库口令、`APP_KEY`/盐、会话密钥、第三方接口密钥、SSH/面板口令）——**这一条不做，前面全白做**；④ 从可信介质重建而非就地清理；⑤ 补掉本次利用点，并**顺手把同类汇聚点全部扫一遍**（把个例升级成类，否则层4 的根没动）。
判据：修复不是「网站能访问了」，而是「攻击者手里的东西全部失效」。

### 消解根（灭这一类）
> **把防守对象从「无穷的漏洞」换成「有限的入口」。**

漏洞不可枚举，入口是可枚举的。当前所有资源都投在「枚举漏洞」这一侧（每月补一个），而那一侧的完备性要求「知道所有洞」——结构上做不到。改投「枚举入口」这一侧，完备性要求降为「列出所有入口」——一天的盘点工作量。

具体形态：在业务代码**之外**建立一个强制的、白名单化的收口层——
- **网络位置**：后台从公网摘除，只经反代/VPN/办公网可达，公网侧只放行枚举过的路径与方法；
- **请求形态**：反代层做路径/方法/参数形态白名单，不依赖业务代码自身校验；
- **运行权限**：Web 进程以最小权限运行，数据库账号只授该库该表，禁止 DDL/文件读写；
- **出网方向**：默认禁止服务器主动出网（后门回连、数据外带、反弹 shell 全部失效）；
- **公共观测**：收口层落全量请求审计——这是全站唯一一个「必定经过」的观测点，也顺手把层3 的「发现权」从对手手里拿回来。

**① 不可发生判据**：完备性不再依赖「知道所有漏洞」，而依赖「枚举所有入口」。当所有不可信输入只能以被枚举过的形态到达业务代码，「未知缺陷被不可信网络直接利用」这**一整类**在结构上不成立——攻击者能触达的请求集合是一个有限子集。
⚠️ **诚实标注（否则这条会被高估）**：三条边必须**同时**成立才算消解——「入口不可达」∧「内网不默认可信」∧「发现权在自己手里」。只做第一条（网络隔离）时，类别**没有消失，只是被推远**：攻击者需要先拿到内网立足点（钓鱼、员工终端、第三方运维），向量从「公网扫描」变成「内网横向」。因此单做网络隔离→**降级为缓解**，写明；三条合起来→消解成立。

**② 可执行首边**（从现状出发，可以很小）：
> 第一条边 = **把后台从公网摘到一层只放行「已枚举路径+方法」的反代后面**，同一天把数据库口令改为最小权限账号、把服务器出网默认关掉。
> 不需要改一行业务代码，不需要业务批 18 人月，也不需要等「下个月再被打一次」来立项。

**③ 成本量级**：**人日～人周**量级（粗估，未经公式图核算；关键假设：业务代码零改造，仅在外部收口 + 配置调整，不含后续技术债处置）。对照项是 18 人月——**低两个数量级**。

### 顺带说破一件事：老板嘴巴里那个二选一是假的
「继续被打」vs「18 人月重写」不是全集。第三个选项（在旧的、烂的、不可枚举的系统外面套一个可枚举的边界）成本是前者的百分之一量级，而且**它恰好是唯一一个能让这一类问题消失的动作**——重写不消除「不可枚举攻击面」这个属性，用 PHP 8 写三十万行无框架代码，照样每月被打，只是洞的种类换了名字。**这就是为什么「全站重写」在本轮不是消解根，而是 L4 里的一项。**

## L4 迁移出口

消解根一旦采用，会引出下面这些新问题。本次问题**降级为第 5 项中的一次具体补丁**：

1. **交付与发布**：收口层成为单点与变更瓶颈。「临时放行」会腐化成永久放行——必须一开始就定「放行条目的有效期与审批人」，否则半年后收口层形同虚设。
2. **可观测性**：收口层成为唯一公共观测点，日志落点、保留期、告警阈值要一并设计。有了告警没人看等于没有。
3. **凭据与权限模型**：数据库最小权限、禁止出网，会打断现有定时任务、批处理、图片外链、第三方回调——必须先在低峰期用「观察模式」跑一段，收集真实依赖。
4. **组织能力**：告警响应需要值班与升级路径；否则新加的检测只是多了一个没人看的日志文件。
5. **技术债退出路线**（不重写，切片）：把「不可枚举的部分」包在收口层后面不动，把「可枚举的部分」（认证、上传、查询、文件读取、对外接口）按域逐步替换。18 人月被拆成可分批申请的小额预算——**这才是对「业务不批」的正确回应：不是说服老板批 18 人月，是把 18 人月拆成他肯批的形状。**

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 全站重写 / 换技术栈 | 挂起，非本轮消解根 | 18 人月业务不批；且它**不消除**「攻击面不可枚举」这一属性——换语言不换结构，同样每月失守，只是洞换个名字。根落在类，不能靠换实例解决 | 若收口层上线后仍有大量缺陷**穿越**收口层得手，说明缺陷位于「入口之后的业务逻辑内部」，此时按域切片重写升格为必要，且预算论证成立 |
| 内部人员 / 第三方运维 / 供应链 | 挂起，**未排除** | 题面只说「被打」，未给任何取证结论；「换地方」若每次都发生在内网路径或同一第三方账号下，指向内部而非公网 | 拿到两次以上事件的**入口 IP 与成功账号**。若入口均为内网或同一第三方，改判为内部风险类，消解根转为权限与审计分离 |
| 弱口令 / 凭据复用 | 挂起，疑为共因 | 老后台月度失守的高频真因，但题面无信息 | 日志若显示「登录成功」而非「注入成功」，此项立即升为处置根首项，并成为消解根第四条边的优先项 |
| 业务侧必须公网可达的接口（支付回调/上传/分享页/API） | 挂起 | 收口会打断对外业务，不能一刀切 | 若存在此类接口，则收口只覆盖后台管理面；公网接口需单独做接口级白名单与参数校验，成本上浮一档 |
| 数据外泄 / 合规通报义务是否已触发 | 挂起 | 题面未提，但决定处置根是否要并入法务与通知流程 | 一旦取证显示数据被读取或外带，处置根须加「外泄影响评估」一支 |
| 权限/账号体系（树 L0 排除项） | 部分回挂汇合层 | L0 排除只在「主因」层成立；入侵后的横向移动与提权确实依赖目录 ACL 与服务账号 | 取证显示提权路径依赖 ACL/服务账号，则本支升为消解根第五边 |
| 组织流程（树待建节点 `org-process`） | 汇合层纳入，不作主线 | L0 已判 `software`（技术层确实异常，不属「技术全正常而问题由人产生」那一类）；但「业务不批预算」是真实约束 | 若收口方案仍被预算否决，主线必须整体转到 `org-process` 节点——届时问题从「技术根」变成「风险定价与成本叙事根」 |
| 树外分支：`security-exposure` 节点缺失 | 登记 v2 候选 | 现有 `software` 六子层全是「进程起不来」的轴，无安全暴露轴；本次被迫自建轴 | 下次做同类题前补齐该节点（判据／典型根／典型症状／核查日期），并升版本 |
| 「每月一次」的周期稳定性 | 未验证假设 | 题面为转述，未给事件时间序列 | 取事件时间序列表。若间隔无规律，则类根不变，但「稳态」表述改为「暴露常开 + 偶发得手」，排序中第 2 项的份额下调 |

## 结论

**根源在哪（三句话）**：
1. 不在 PHP 5.6，也不在补丁打得慢。根源是**这套系统没有一个独立于业务代码、且被强制经过的安全边界**——于是它的攻击面不可枚举，漏洞只能一个个补，而漏洞供给无穷、发现权在对手手里、恢复动作又把自己精确复位回事故前那个不安全构型。
2. 这四件事叠加，「每月被打一次」就不是失误，是**稳态**：补丁改变的是「洞在哪」，不改变「有多少洞」。你这个月的修复动作的终点，就是下个月受害周期的起点。
3. 更直白一点：**你们真正的漏洞扫描器是攻击者本人。只要这个分工不变，补丁永远追不上。**

**怎么才能让它不再被打（一条动作）**：
**把防守对象从「无穷的漏洞」换成「有限的入口」**——在业务代码外面套一层强制的、白名单化的收口（不可达 + 请求形态限定 + 最小权限 + 禁止出网 + 公共审计），让「未知缺陷被不可信网络直接利用」这一整类在结构上不成立。
第一条边今天就能走：**把后台从公网摘到只放行已枚举路径的反代后面，同时换掉数据库口令、关掉服务器出网。** 人日量级，不需要业务批 18 人月。
重写不是被否掉的方案，是被**降级**的方案——它不消除这个结构，只更换实例，所以它排在挂起表里，等收口层证明「缺陷藏在入口之后的业务逻辑内部」那一天再升格。

> 一句话给老板：**别再买补丁了，买边界。补丁是按洞付费，边界是按入口付费——洞数不清，入口数得清。**
