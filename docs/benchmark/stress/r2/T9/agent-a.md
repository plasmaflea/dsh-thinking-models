## L0 类别判定

类别＝**「反复失守的存量系统」**（安全姿态 × 组织流程复合类）。
判据：① 存在一次成功入侵的**必经时序**，可机械生成、不靠联想列举；② 失败不是确定性代码缺陷，而是「可达性 × 可利用性 × 扩散性 × 可检测性」四因子的乘积，所以表现为概率性、周期性、换位复现；③ 单点修复对**单个漏洞**有效、对**整体失守率**无效（速率比较失衡）——这正是题面的观测。
已排除：硬件故障（无校验错误、无随机症状）；网络问题（无分层不可达证据，且链路故障不产生 webshell）；纯软件缺陷类（`software` 节点判据②不满足：修好一个洞并不消除本类现象，故不能把根放在"代码有 bug"上）；纯权限/账号体系（题面无 ACL、令牌症状；账号问题只会放大后果，不产生入口）。
`software` 节点本次判为**部分适用**（借用 `config` 暴露姿态、`dependency` 依赖补丁源两格）；`win-service` 节点不适用。

## L2 逐层回溯

两条**必经时序**各自生成一棵子树，结构上隔离维度，只在汇合层合并（不跨维度跳边）。

**子树 A · 攻击侧**（攻击者必须逐格满足，缺一格攻击不成立）
| 格 | 该格在管什么 | 故障的可观测症状 |
|---|---|---|
| A1 定位 | 目标与指纹是否可达可见 | 访问日志里大量陌生 IP 探测 `/admin`、`/phpmyadmin`、`/.env`、`/.git`；响应头带 `X-Powered-By: PHP/5.6.x`；搜索引擎/测绘平台能搜到登录页 |
| A2 入口 | 是否存在可利用弱点（EOL 组件洞／弱口令／上传／反序列化／配置错） | web 目录新增陌生 `.php`；上传目录可执行；access log 有 POST 到非常规脚本 |
| A3 立足 | 弱点是否兑现为代码执行 | 文件 mtime 异常、可疑子进程、crontab 被追加、`/tmp` 有陌生 ELF |
| A4 扩散 | 单点失守是否等于全站失守（后台直连生产库／共享凭据／内网漫游） | DB 账号从 web 主机登录；同一口令出现在多个配置文件；跨主机 SSH |
| A5 外传 | 数据/持久化是否被拦 | 出站到陌生 IP:端口、DNS 隧道、单次响应体异常大、无出站审计记录 |
判定：**A1–A5 每月全链走通**。不是某一格坏了，是**全链没有一格被结构性拦住**——所以"补完这个洞"只关掉 A2 的某一个取值，A1、A3、A4、A5 原封不动，下月换 A2 的另一个取值即复现。

**子树 B · 防守侧**（一次修复闭环的必经时序）
| 格 | 该格在管什么 | 故障的可观测症状 |
|---|---|---|
| B1 发现 | 资产台账 + 漏洞/入侵检测 | 只有"被打之后"才知道；说不出后台有几个域名几个端口几个副本；无外部扫描、无文件完整性监控 |
| B2 定级排期 | 谁能批、SLA 与预算 | 无补丁 SLA；平时无安全工时，只有事故才排期；优先级由谁喊得响决定 |
| B3 修复执行 | 补丁/配置/下线，含回滚与变更记录 | 改的是症状不是清单项；无变更记录；修完不清点"还有多少同类" |
| B4 复测与基线 | 验证 + 收敛为基线（重建后配置可复现） | 修完不复测；重建后配置与上次不同；同一个洞二次出现；补丁记录与资产清单对不上 |
判定：**B1、B4 结构性断裂，B2 半断**（无 SLA，纯事件驱动；18 人月不批就是 B2 断裂的直接后果）。整条反馈环因此**不闭合**，只能靠"下一次被打"重新触发。

**汇合层 → 类根**
> **修复闭环的周期（月）严格大于弱点产生与暴露被发现的周期（周），而在这个系统里没有任何机制去拉平这个比较。**

更直白：这个后台的安全性从来没有被"管理"过，只被"应急"过——**应急的节律由攻击者的扫描器决定，不由你决定**。两条结构条件使它必然成立：
- (i) **上游补丁流已断**：PHP 5.6 官方安全支持已于 2018-12-31 结束，题面中同代第三方组件同样 EOL。于是"补"的对象只能是自己发现的洞，新披露的洞没有上游补丁可消费——修补速率的上限被上游锁死。
- (ii) **攻击面存量从不收敛**：后台可达公网（A1）、单点失守即全站失守（A4）。攻击者每月只需在同一个存量里挑一个还没补的，成本恒定；而防守方要堵全部，成本线性增长。这是攻守不对称的教科书形态。
- 个例根（挂在类根下，不与之平行）：**本次入侵的具体入口**（某上传点／反序列化／弱口令／插件洞／配置错）。题面未给，见 ⚠️。它解释"这一次"，不解释"每月"——把它当根就会得到"再补一次下月再被打"的循环。

## L3 双根

**处置根（修本次）**——顺序不可颠倒，先隔离后取证，不要在不可信主机上"删 webshell"：
1. 摘除可达性（同时是取证保护）：先把后台从公网入口摘掉/白名单化；
2. 保全证据：web 与网关日志、文件 mtime 清单、进程、crontab、出站连接，定位 A2 入口；
3. 从干净基线重建，不在被入侵主机上清理；
4. 全量轮换凭据：DB、SSH、后台账号、支付/短信 API key、CI 凭据，**含硬编码在代码里的那些**（这类最容易漏、也最常被复用）；
5. 临时加固：上传目录禁执行、出站白名单、后台前置认证。

**消解根（灭这一类）**：把安全边界从**应用内部**搬到**应用外部**，让"有漏洞"不再等于"可被利用、可扩散、不可见"。
- **S1 可达性收敛**：后台不再是公网资产，只在堡垒机/VPN/零信任网关之后；公网只保留无管理功能的回调端点。
- **S2 扩散性收敛**：后台不再直连生产库、不再有内网漫游权限（经中间层 + 最小权限账套 + 出站白名单 + 只读根文件系统）。
- **S3 可检测性收敛**：文件完整性监控 + 网关/WAF 日志 + 资产台账 + 月度外部扫描 + 到期强制升级（把补丁从"事件驱动"改成"SLA 驱动"）。

三闸门：
- **不可发生判据**：若当时已采用 S1+S2（哪怕 S3 未做），"外部攻击者每月打穿一次"这一类在**结构上不可能**发生——A1 不成立（摸不到入口），A3 即便兑现也拿不到可直接外传的全站权限（A4 被切断）。注意这是**可达性消解而非漏洞消解**：洞还在，只是不再是入口。S3 的作用是把"已发生"从月级发现压到小时级发现，使 B1/B4 闭合。诚实边界：内部人员、供应链、钓鱼不在此消解范围内，进 L4 与挂起表。
- **可执行首边**：**本周末把后台管理入口从公网摘掉**（Nginx `allow` 内网段 + 撤公网解析，或前置于零信任网关）。1–3 人日，**不改任何业务功能，因此不需要 18 人月那种审批**——这是全题唯一"结构有效 × 不需业务批"的切口。
- **成本量级**（量级估计，精算须交给 📐 公式图，此处不凭空给数字）：S1 = 人日级（1–3 人日）；S2 = 人周级（约 2–6 人周）；S3 = 人周级（约 2–4 人周建基线，之后每月固定少量工时）；对照全站重写 18 人月。**差距约两个数量级**。

关键判断：**18 人月重写不是消解根，它是"恢复上游补丁流"（S0，长期正确方向），但它完全不改变 A1/A4 与 B1–B4 的结构**——不配 S1/S2/S3，重写出来的系统五年后一样 EOL、一样每月被打一次。所以"重写"应被剥离出应急预算，变成独立的技术债决策；而"不再被打"用 S1 就能当月兑现。

## L4 迁移出口（消解根引发的新问题清单）

1. **公网回调面**：支付/短信/第三方回调必须公网可达 → 拆出独立公网端点（无管理功能、独立域名、限流、IP 白名单、独立凭据）。这是 S1 最先卡住的地方。
2. **数据与状态**：只读根文件系统会破掉老代码写本地路径（上传/session/缓存/日志）→ 需可写卷白名单 + 迁移方案。
3. **运行与自启**：容器化/收容后 PHP 5.6 的扩展、cron、绝对路径、SELinux/AppArmor 语义差异。
4. **凭据与权限模型**：硬编码凭据改为注入；后台账号与运维账号分离；退出共享账号；外包/驻场权限回收与审计。
5. **可观测性落点**：日志/指标/转储从"应用本地"迁到网关与集中平台，谁看、看什么、告警给谁。
6. **组织能力**：S3 谁值守、补丁 SLA 谁批、月度复测谁做；移动办公/异地/外包人员走不通 VPN 怎么办（S1 落地最常见的反对理由）。

→ **本次问题降级为第 1、6 项下的子项**（"公网回调面拆分"与"值守/SLA 落地"）。它不再是"安全问题"，而是"边界工程 + 运维机制"里的一条待办。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| "是某个具体漏洞没修干净" | 不是类根，只是**个例根** | 每次都能定位并修好，且攻击形态换了位置而非重现——修干净过的东西不会以另一形态每月再来 | 若下一次入侵复用**同一入口/同一 payload** → 升级为主根，回到补丁管理而非暴露面 |
| "代码写得烂" | 不是根（相关项，非必要） | 烂代码 + 不可达 ≠ 被打；好代码 + 公网暴露 + EOL 运行时照样被打。A1–A5 无一格由代码质量决定 | 若有证据显示历次入侵**全部**源于自研业务逻辑漏洞（不含框架/组件/配置/弱口令）→ 升级，重写才转为消解根 |
| "上 WAF 就能挡" | 缓解，非消解 → 挂起 | WAF 是概率拦截，绕过成本低于补洞成本；且只覆盖 HTTP 面 | 若有证据显示历次入侵均为 HTTP 已知签名 → 可降级替代首边（但 S1 仍更便宜） |
| "打补丁打到 EOL 运行时上" | 结构性缺口，但**不是本轮首边** | 自研补丁覆盖不了未披露/未修的洞；但补丁成本低，不应停 | 出现社区 LTS fork（如第三方 PHP 5.6 安全支持）→ 重新评估，"补"这条路重新打开 |
| "内部人员/凭据泄露" | 挂起 | 题面无内部威胁迹象 | 日志显示登录来自合法凭据 + 非常用地点/时间/设备 → 转主根 |
| "被定向针对（APT），不是扫描" | 挂起 | "补完停一个月再被打"的**节律**更像自动化扫描器按指纹周期扫 EOL 系统；定向攻击不会给你一个月安静 | 访问日志中 UA/IP 批次高度重叠、或出现社工/钓鱼前置迹象 → 升级为主根，S1 之后仍需事件响应 |
| "硬件/网络层" | 排除 | 无校验错误、无分层不可达证据，链路故障不产生 webshell | 出现 DDoS、链路侧注入、BGP/DNS 劫持证据 |
| "18 人月重写是唯一解 / 不批就不安全" | 挂起（且非消解根） | 重写买的是"上游补丁流恢复"，不改 A1/A4/B1–B4；18 人月买到的是时间不是结构 | 消解根三条全部实施后仍每月被打 → 说明入口在自研业务逻辑内部，此时才轮到重写 |
| **树外分支**：`org-process`（组织流程类，索引中为待建节点） | 判定为根的**上游**（元根） | "18 人月不批"把修补路径锁死在事件驱动上；预算口径决定了 B2 断裂 | 预算口径改为"季度安全工时包"或"改造成本可分期" → 重新评估 B2 是否仍断 |
| **树外分支**：`security-posture` 节点缺失 | 登记 | 树只有 `software`／`win-service`，无安全姿态类判据，本轮四因子判据为临时构造 | 树升 v2 时补节点（判据：可达性×可利用性×扩散性×可检测性），并复核本结论 |

## 结论

1. **根源不在某个漏洞，在"修复速率被上游锁死、而攻击面从不收敛"这个结构**：PHP 5.6 官方安全支持 2018-12-31 已结束，新洞没有上游补丁可消费；后台又直连公网、单点失守即全站失守。所以"每月补一个、下月换一个"不是手气差，是这套结构的稳定输出。
2. **让它不再被打的最短路径不是重写，是把后台从公网摘掉**（1–3 人日，不改功能，因此不需要走 18 人月的审批）：洞还在，但不再可达；再有 S2 切断"一跳全站"，单点失守也不再等于全站失守。
3. **18 人月重写买的是"恢复上游补丁流"，不是"不再被打"**。它是长期正确方向，应剥离出应急预算；不配 S1/S2/S3，五年后同一道题会再问一次。

[✅ 验证] 未做外部核查，本回答只基于题面四项事实（PHP 5.6、老后台、月度被打且补后换位、18 人月）+ PHP 5.6 安全支持于 2018-12-31 结束这一公开事实。树已实读，路径与版本见 L1。成本为量级估计，非精算。

[⚠️ 异常/矛盾/空白]
- **空白（不改变结论形状，但改变首边做法）**：本次入口未知；是否已暴露公网；有无 WAF/日志/文件完整性监控；PHP 5.6 是官方包还是自研补丁；是否存在必须公网可达的回调；外包/驻场是否持有后台权限。
- **题面给的节律本身是证据**：定向攻击不会在你补完后安静一个月，这种周期最符合自动化扫描器按指纹扫 EOL 系统 → 若能确认是扫描驱动，则"抹指纹（版本头、后台路径、报错页）+ 收进网关"的边际收益显著高于继续补洞。
- **题面矛盾风险**："补完下月换个地方再被打"未说明是同一攻击批次 → 若日志显示 UA/IP 高度重叠，则存在"被盯上"的定向分支，需从挂起转主根。
- **18 人月与"不再被打"的因果被默认绑定**：这是全题最容易被接受却最不成立的隐含假设（重写不等于安全姿态改变），本图已在挂起表第 8 行显式挂起。

[💡 灵感备注] 老板要的"不再被打"实际是一个**可达性问题**，不是一个**代码质量问题**——这是全题唯一同时满足"不改功能、不批 18 人月、结构上消解"的切口。把 S1 包装成"变更可达性"而不是"安全改造"，审批阻力会小一个量级；同时把 18 人月从应急叙事里剥离，它才有机会被真正批准。
