[🌳 林状图／回溯法] [选择理由：题面问的是「根源在哪」＋「为什么查不到」，是典型的因果定位题，不是选项穷举也不是定量估算。且现象里出现「查不到凶手」这种反常——正好命中回溯法的类根形态：某个本该由应用/运维掌握的控制权被外部机制代持（此处是内核的 charge 记账与 OOM victim 裁决），失败发生在应用能记录之前。]

## L0 类别判定

**类别**：软件类 · `quota`（资源配额／记账口径）为主，`lifecycle`（谁裁决存亡）为辅的资源记账故障。

**判据（两条须同时满足，均满足）**：
1. 可复现性来自环境姿态而非物理介质——同一镜像在 40 台等价机器上以同一统计率复现，且**症状不跟机器走**（若是坏内存条／坏主板，坏的会固定是那几台，而不是"换机器问题也换地方"）。
2. 失败是确定性的或由确定性竞争导致——存在稳定周期（3–5 天）与稳定恢复手段（重启即愈），说明有可归因的累积速率，而不是随机位翻转。

**已排除的大类**：

| 排除大类 | 排除依据 |
|---|---|
| 硬件故障 | 症状随 placement 迁移而非固定于机器；无 ECC/CRC/温度/负载相关性；重启可愈（硬件劣化不会因数秒重启归零） |
| 网络问题 | 无超时／连接重置／DNS 解析失败形态；OOMKilled 是内核的 kill 语义，不是链路的可达性语义 |
| 权限／账号体系 | 权限失败是 deny 语义并带明确错误码；本题是 kill 语义，且重启同一身份即恢复 |
| 组织流程 | **不排除**，作为残余项挂起（见挂起表末行）："重启就好"这一处置习惯本身在毁灭证据 |

> 说明：L0 在此压缩为一行结论 + 排除表。省略大类判定等于让后面全部回溯建在未声明的假设上（倒推法走形 #1）。

**命中子层**：

## L2 逐层回溯

### 选轴（生成式，不是列举）

轴由**恒等式**生成，不用联想列举。两条恒等式：

```
触发式：OOMKilled ⟺ memcg.charge ≥ limit  ∧  reclaim(charge) 失败
记账式：memcg.charge = anon(本 cgroup 内进程匿名页)
                     + file(page cache / mmap 文件 / overlayfs 上层写)
                     + shmem(tmpfs / /dev/shm / memory emptyDir)
                     + kernel(slab / socket buffer / page table / kernel stack / percpu)
```

而监控侧看到的是另一个量：

```
observed = f(RSS)  或  working_set = usage − inactive_file
```

于是定义**差额 Δ = charge − observed**。本题的全部自由度只有两个：**Δ 落在哪个账户**、**为什么 reclaim 失败**。轴由此机械生成，无需灵感。

三判据自检：
- 正交：四类账户互不重叠（anon / file / shmem / kernel 在 memory.stat 里就是四个不同键），任一格能独立解释"RSS 平而 charge 涨"。
- 可生成：恒等式右边只有这四个加项，为什么这格必然存在不需要论证——它是加法项。
- 可观测：每格有专属键名与专属曲线（下逐格写出）。

---

### 层1 · 判据层：谁在判这次 OOM？

这是全题**最低成本的分叉点**，一条 dmesg 就能定，先做。

| 格 | 机制 | 该格的可观测症状 |
|---|---|---|
| 1a cgroup OOM | 容器 memcg 的 charge 撞到自己的 limit | pod 事件 `OOMKilled=true`、`restartCount++`；节点 dmesg 出现 `Memory cgroup out of memory: Killed process <pid> (<name>) total-vm:... anon-rss:... file-rss:...`；节点整体内存可能健康 |
| 1b node OOM | 节点物理内存耗尽，内核在节点范围内选 victim | dmesg 出现 `Out of memory: Killed process ...`（无 "Memory cgroup" 前缀）；同一节点上其他 pod 也被杀或被驱逐；节点出现 MemoryPressure/eviction 记录 |

两者症状不同、修法完全不同（1a 改配额/改账户，1b 改节点容量与调度）。**先看这一行，别先看进程。**

---

### 层2 · 记账口径层：Δ 落在哪个账户（正交四格）

| 格 | 账户 | 为什么 RSS 查不到 | 该格的可观测症状（专属） |
|---|---|---|---|
| 2a | **file page cache**（日志/临时文件/overlayfs 上层写/mmap 文件） | page cache 不是任何进程的 RSS；且 `working_set = usage − inactive_file` 会把可回收的那部分**扣掉**，所以曲线看起来完全平 | `container_memory_cache` 单调涨；`container_memory_usage_bytes` 涨而 `container_memory_working_set_bytes` 平；`memory.stat` 的 `file`/`active_file`/`dirty`/`writeback` 涨 |
| 2b | **shmem / tmpfs**（/dev/shm、memory 型 emptyDir、/tmp 映射） | tmpfs 页记在 shmem 账户，不落在写它的进程 RSS 上（尤其写入由内核路径完成、或写者已退出时） | `memory.stat` 的 `shmem` 涨而进程 RSS 平；`df` 看 /dev/shm 用量涨；默认 /dev/shm=64Mi 被挂在大容量 tmpfs 上时尤甚 |
| 2c | **kernel memory**（slab / socket buffer / page table / kernel stack / percpu） | 内核对象根本不属于任何用户态进程，RSS 无一字节，多数监控面板**连指标都没有** | `memory.stat` 的 `kernel`/`kernel_stack`/`slab`/`sock`/`percpu` 涨；节点 `slabtop` 有异常增长项；大量短连接 pod 的 `sock` 账户持续涨；连接池/长连接泄漏时尤其贴合"3–5 天单调涨" |
| 2d | **非本容器的 anon**（fork 出的短命子进程、sidecar、init 容器、`kubectl exec` 进去的进程、cgroup v1 下同 pod 多容器共享 cgroup） | 进程已经退出或不在这个容器的 PID 视图里，`ps` 排不到它，charge 却还挂在同一个 cgroup 上 | `cgroup.procs` 里的 PID 集合与 pod spec 里的容器数**对不上**；`ps` 看到的 task 数与被杀进程名不一致；被杀进程名不是你预期的那个 |

四格正交性检验：2a/2b 是"用户态写出去但记在缓存/共享内存上的量"，2c 是"内核自己持有的量"，2d 是"用户态持有但归属错位"——任一句都不同时解释另一格的症状。

---

### 层3 · 归因层：为什么每次是"不同的 pod、不同的机器"？

这一层是本题**最容易被误读成"问题在迁移"**的地方，必须单独切格。

| 格 | 机制 | 该格的可观测症状 |
|---|---|---|
| 3a | **随机 victim**：cgroup OOM 在组内按 badness（≈ 匿名页占用 + `oom_score_adj`）选杀对象，节点 OOM 在全节点按 `oom_score` 选杀对象——**选的是"最好杀"，不是"吃最多的"** | 同一 pod 反复被杀但每次死的进程/容器不一样；`oom_score_adj` 为 0 的无辜 pod 被选；真正的消费者毫发无伤 |
| 3b | **采样稀疏造成的错觉**：40 台 × 每 3–5 天 1–2 次 ⇒ 单台约 **100–200 天**才轮到一次。命中率极低时，"哪台"这个变量的分布看起来就是随机的 | 把 40 台按事件数画帕累托图，会看到**没有任何一台显著出头**——即"机器"不携带信息；按时间画，事件率近似平稳（泊松） |
| 3c | **同源底座**：同一镜像、同一调度器、同一节点池、同一 limit ⇒ 40 台在统计上是同一个系统的 40 个独立重复试验 | 任一单台都能复现，只是要等足够久；把任一 pod 手动挪到任意机器，长期看该机器也会出 |

三格互不解释对方：3a 解释"凶手与被杀者的错位"，3b 解释"为什么看起来漂移"，3c 解释"为什么机器不是解释变量"。**关键判据纠偏：题面里其实没有"迁移"这个事实，只有"低事件率 + 无归因"这个事实。**

---

### 层4 · 累积层：为什么是 3–5 天，为什么重启就好

| 格 | 机制 | 该格的可观测症状 |
|---|---|---|
| 4a | **单调累积账户（不回落）**：连接/`sock`、conntrack、slab 对象、direct buffer、dirty page、未 trim 的 arena。增长速率 r，阈值 L ⇒ 周期 T = L / r，稳定可预测 | 3–5 天**稳定周期**；重启把 charge 归零（T 从重启时刻重新计时）；把 limit 调大 → 周期按比例变长（**这是可做的最强判别试验**） |
| 4b | **自愈型账户（会回落）**：普通匿名页分配、GC 可回收堆、有上限的缓存 | 不会有稳定周期，而是"偶发""活动高峰后出现"；重启只是碰巧赶上窗口 |

**用周期性反推账户性质**：既然观察到稳定周期 + 重启即愈，就必然存在一个"只增不减"或"回落速度 < 增长速度"的 charged 账户。这一格把候选从"内存泄漏"（进程级）直接改判成"**记账账户级单调累积**"——而账户可能根本没有一个对应的进程。

### → 类根（面对整个大类）

> **这一类问题之所以必然可能发生，结构条件是：内存的记账单位是 cgroup（charge），观测单位是进程（RSS），两者之间存在一个没有监控面的差额 Δ（file cache / shmem / kernel / 归属错位的 anon）；而 OOM 的判据只用 charge 口径。只要有一个"只增不减"的账户落在 Δ 里，系统就会在"没有任何进程内存异常"的前提下，周期性地杀掉一个与它因果无关的对象——因为 victim 是按 badness 选出来的，不是按因果选出来的。**

这条类根同时解释了题面的三个反常，且每个反常各有一个独立机制支撑：
- "查不到任何进程吃内存" → Δ 不在任何进程的 RSS 里（层2）。
- "内存曲线很平" → `working_set = usage − inactive_file` 把 Δ 里最容易被误判的那部分扣掉了（层2 格2a）。
- "机器/pod 不固定" → 低事件率 + 随机 victim（层3 格3a/3b）。
- "重启就好、3–5 天复发" → 单调累积账户被清零后重新开始（层4 格4a）。

### └ 个例根（挂在类根下，不是平行清单）

按 `Share × Lever ÷ Cost` 排序。**排序即预算**：Cost 全部压到"一次采样"，所以这里给的是**验证顺序**，不是信口猜概率。

| 序 | 个例根 | Share（能解释已观测现象的比例） | Lever | Cost |
|---|---|---|---|---|
| A | **kernel 账户（socket buffer / slab / page table）单调涨** | 主因：RSS 零字节、监控几乎无指标、周期与连接数/句柄数强相关 | 改配置＋改代码 | 一次 `memory.stat` 采样 |
| B | **file page cache（日志/临时文件/overlay 上层）dirty 不可回收** | 主因/共因：perfect fit "usage 涨而 working_set 平" | 改配置（rotation/noatime/落盘策略） | 一次采样 |
| C | **shmem/tmpfs**（/dev/shm、memory emptyDir、/tmp 映射） | 共因：RSS 完全看不到 | 改配置 | 一次采样 |
| D | **运行时堆外**（JVM direct buffer / metaspace / 线程栈 / glibc arena 未 trim；cgroup 未感知导致 MaxRAMPercentage 按宿主算） | 主因（若负载是 JVM/Go 大堆）：监控只看 heap_used 就会"查不到" | 改配置＋改代码 | 一次 `jcmd VM.native_memory` / `GODEBUG` 采样 |
| E | **节点级 OOM 误杀（邻居/系统进程是真正消费者）** | 次要–主因：取决于层1 分叉 | 改架构（配额分层） | 一次 dmesg |
| F | **归属错位的进程**（sidecar/init/exec/未回收的子进程共享 cgroup） | 次要：`cgroup.procs` 一比就现形 | 改配置 | 一次 `cgroup.procs` 对比 |

> A–D 的共同点必须写清：**它们都不是"某个进程泄漏"，所以"查哪个进程"这个提问方式本身就把答案排除了。** 这是本题真正的陷阱。

## L3 双根

### 处置根（修本次，最短路径）

四步，全部是"一次采样"级成本，按顺序做，第二步就能把 A–F 收敛到一格：

1. **定分叉（1 分钟）**：`dmesg -T | grep -i "killed process"` —— 有没有 `Memory cgroup out of memory` 前缀？有＝走 1a（limit 问题），无＝走 1b（节点问题）。
2. **定账户（10 分钟）**：在被杀容器**活着时**（或下一周期复现前）取
   `cat /sys/fs/cgroup/memory.stat`（v2；v1 为 `/sys/fs/cgroup/memory/<cid>/memory.stat`），
   与 `memory.current`（v1: `memory.usage_in_bytes`）对齐，逐键核对：`anon / file / shmem / kernel / slab / sock / pagetables`。哪一格的数值 ≈ 差额 Δ，就是哪一格。
3. **一眼命中 2a 的判别**：把 `container_memory_usage_bytes`、`container_memory_working_set_bytes`、`container_memory_cache` 三条画同一张图。**usage 涨而 working_set 平 ⇒ 确认 2a（cache 型 charge）**，这是本题最省事的单条判据。
4. **临时止血（不要用"提高 limit"当结论）**：limit 调大只是把周期按比例拉长（`T = L / r`），不是修复，而且会误导下一轮排查。真正的止血是给"不回落账户"封顶：日志 rotation + `noatime`、连接池/超时上限、direct buffer 上限、定期 drop 临时文件。
5. **取证纪律**：**下一次复发时，先取证再重启**——把 `memory.stat`、`cgroup.procs`、`dmesg`、`/proc/<pid>/smaps_rollup` 抓完再重启。现在"重启就好"这个习惯，本身就是这轮查不到的直接原因之一（重启把 charge 和证据一起清零了）。

### 消解根（灭这一类）

> **把监控与配额的口径从"进程内存"整体迁移到"cgroup 全字段记账"：任何 charge 增量都必须落在一个有名字、有指标、有上限的账户上；同时把 OOM victim 的选择从随机改成显式（`oom_score_adj` 分层 + `memory.high` 软限流先 reclaim 再杀）。**

- **不可发生判据**：若每个 charge 加项都有专属指标与显式上限，则"charge 撞到 limit 却查不到谁吃的"在**结构上不可能**——因为 Δ 定义为 charge − Σ(已命名账户) ≡ 0，不存在无主内存；即使仍被 OOM，诊断路径也不再依赖"猜受害者"，也不需要重启清场来恢复。注意：这不是"让它变少见"（调大 limit 就是变少见），而是让"无主的 charged 内存"这个对象消失。
- **可执行首边（第一条可执行边，很小）**：在现有 cAdvisor/agent 上，把 `container_memory_working_set_bytes / usage_bytes / cache / rss` 与 `memory.stat` 的 `file / shmem / kernel / slab / sock` 落库（cAdvisor 多数版本已采集，只是没画、没告警），告警从"绝对量阈值"改成"**charge 增速**阈值"。**小时级、无架构变更、不动业务代码。**
- **成本量级**：10⁰–10¹ 人日；存储与 series 线性增长（每容器约 +10–20 条 series）。联动 📐 公式图：周期 `T = L / r`，成本主要在"给每个不回落账户找到所有者并封顶"这一项，量级 10¹ 人日／账户。

## L4 迁移出口

消解根把问题从"查凶手"换成"补记账口径"，因此必然带来下列新问题清单：

1. **可观测性**：series 基数上升（每容器 10–20 条 × 40 节点上的 pod 数），采集与存储开销上升；告警模型要从静态阈值改成增速/趋势模型，误报会先上升一阵。
2. **配额模型**：引入 `memory.high` 软限流后，症状从"被杀"变成"被 throttle 变慢"——需要应用能承受 reclaim 抖动，`request/limit` 必须重算，否则会用"更隐蔽的慢"换掉"显式的死"。
3. **运行时改造**：每一个不回落账户都要找到所有者并封顶——谁在写日志、谁在建连接、谁在 mmap、哪个库在用 direct buffer。这一项是真正的工作量所在。
4. **组织能力**：值班流程从"重启大法"改成"先取证后重启"，需要 runbook + 采集脚本 + 一条硬约束（重启前必须落盘 memory.stat）。
5. **调度口径**：从"按 request 调度"走向"按真实 charged 用量调度"（memory-aware scheduling），否则 Σ limit 超卖导致的节点级 OOM（层1 格1b）会继续存在。

→ **本次问题降级为第 1 项"可观测性口径缺失"的一个具体实例**：它不是"某个 pod 有 bug"，而是"这套平台没有定义 Δ 这个量"。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 硬件故障（坏内存条/坏主板） | ⊥ 非根 | 症状不跟机器走；重启即愈（硬件劣化不会因数秒重启归零）；无 ECC/CRC 日志 | 若帕累托图显示某 1–2 台机器事件数显著高于其他（如 >3σ），或 dmesg 出现 MCE/EDAC/`Machine Check`，则恢复为候选根 |
| 网络问题（超时/链路抖动） | ⊥ 非根 | 失败是 kill 语义，非可达性语义；无 DNS/超时形态 | 若 `sock` 账户增长被证实由重传队列/连接泄漏驱动，则网络从"被排除大类"降级为"格 2c 的上游触发条件"重新纳入 |
| 权限/账号体系 | ⊥ 非根 | deny 语义 vs kill 语义不同；同身份重启即恢复 | 若出现 RBAC/PSP/SA 令牌导致的采集缺失（查不到是因为没权限查），则恢复 |
| "某个进程内存泄漏"（最直觉的假设） | ⊥ 非根（**这是本题要否定的主假设**） | RSS/曲线皆平；且见层3 格3a——victim ≠ 消费者 | 若 `memory.stat` 的 `anon` 项≈Δ 且 `cgroup.procs` 能定位到某 PID 的 `smaps_rollup` 异常，则恢复为"进程级泄漏"，走常规 heap/leak 分析 |
| JVM/运行时堆内泄漏 | ⊥ 非根（若为 JVM 负载） | 堆指标平；3–5 天周期 + 重启即愈更像堆外/账户累积 | 若 `jcmd GC.heap_info` 显示老年代持续增长且 Full GC 不回落，则恢复 |
| 调度不均 / 单机超卖 | ⊥ 暂挂 | 目前无法区分"调度问题"与"3b 采样错觉"，两者都表现为机器不固定 | 若某节点 Σ(request)/capacity 显著高于均值且该节点事件率随之偏高，则升级为共因 |
| **内核 memcg 统计自身 bug**（charge 泄漏） | ⊥ 暂挂（树外分支） | 无法排除，但**不应优先假设**：先证 Δ 落在哪个正常账户，再谈内核 bug。若真的 `memory.current` − Σ(memory.stat 各键) 显著 > 0，才是内核记账 bug 的判据 | 当出现 `memory.current − Σ(memory.stat 明细) 明显为正且可复现`，或已知内核版本的 memcg charge 泄漏 CVE/回归，则升级为首要根 |
| 组织流程（"重启就好"毁灭证据） | **不挂起，已升为共因** | 题面"重启就好"直接消灭了 charge 现场；这是"查不到"的第二重原因（第一重是 Δ 本身无监控面） | —（已经是处置根第 5 步的输入） |

树外分支登记：`v2 候选` 建议在 `software` 节点下新增子层 **`accounting` 记账口径**（与 lifecycle/init/dependency/quota/concurrency/config 并列，因为 quota 讲的是"配额多大"，不覆盖"记账单位与观测单位不等"这一类）。理由：本次问题的根不在"配额设错"，而在"配额与观测的口径不等"，现有六子层没有格能干净承载它。

## 结论

1. **根源不在任何进程里，在"记账口径 ≠ 观测口径"这个结构缺口**：OOM 的判据是 cgroup 的 charge（含 page cache／shmem／内核内存），你看的是进程 RSS 或 `working_set = usage − inactive_file`，两者之差 Δ 没有任何监控面，于是"没有任何进程吃内存，但容器被 OOMKilled"是**完全自洽的正常输出**，不是矛盾。
2. **"机器/pod 不固定"是低事件率造成的采样错觉，不是问题在迁移**：40 台 × 每 3–5 天 1–2 次 ≈ 单台 100–200 天一次，命中率低到无法归因；再叠加 OOM killer 按 badness（不是按因果）选 victim，所以"被杀的"和"真吃内存的"本来就错位。追被杀的那个 pod 必然扑空。
3. **3–5 天周期 + 重启即愈，指向一个"只增不减"的 charged 账户**（`T = L / r`，重启把 charge 清零）。所以第一步不是查进程，是**读一次 `memory.stat` 把 Δ 归到 `file / shmem / kernel(slab,sock) / anon` 的哪一格**，并用 `usage 涨而 working_set 平` 这一条单判据直接命中最常见的 cache 型 charge；消解则要把监控与配额整体搬到 cgroup 全字段口径（首边：把已采集的 memory.stat 全字段落库 + 告警改成"charge 增速"）。

## 💡 灵感备注

1. **把 40 台读成"一台机器的 40 次重复实验"，这道题的随机性立刻消失**——"机器不固定"不是现象，是样本量不足。这类"低事件率被误读为高随机性"的模式在分布式排障里反复出现，值得做成一条常驻判据：**先算单机事件间隔，再谈"随机"**。
2. **"重启就好"是排障中最危险的成功**：它同时清掉了 charge 现场、kernel 计数器、连接状态和内存碎片——修复动作与证据销毁动作完全重合。一个团队如果长期只有"重启"这一条路径，它就等价于**放弃了这个类问题的可诊断性**，这是比本次 OOM 更贵的债务。
3. **本题真正的提问陷阱**：现象里嵌了一个未经验证的因果假设——"有某个进程吃了内存"。"查不到任何进程吃内存"被当作**谜题**来问，其实它是**答案**：memory 的判据本来就不是进程。识别"提问里夹带的假设"这一步，比后续任何一次采样都值钱（这也是倒推法的用武之地：本题若有人坚持"一定有进程泄漏、只是监控不准"，就落入了单一假设走形）。
