# 每月被打一次的老后台：根源与消解

[🌳 林状图] 选择理由：问的是「根源到底在哪」，且附带「怎么才能让它不再被打」＝要**类根 + 消解根**，因果深度未知而非选项广度未知，故用林状图（回溯法）而不是网状图；本轮不需要定量，所有成本只给**量级**并注明交给 📐 公式图，不在林状图里凭空造数字。

**定义前置**（元规则：边界模糊先明确）：本轮把「被打」定义为**攻击者取得未授权能力并造成业务影响**（入侵、越权、脱库、篡改、挂马、勒索）。若老板口中的「被打」其实只是「被扫描/被爆破尝试」，类根与处置会完全不同——该分支已挂起（挂起表 #3）。

## L0 类别判定

**类别：对抗性安全类（`security`，树外大类）**
（判据：失败既不是随机位翻转，也不是我方输入的确定性复现，而是**由有意图的对手按「成本/收益」主动择时选择**；证据形态＝有日历节奏的周期性、修复后攻击位置迁移、我方不改任何输入也会发生。
｜已排除的大类：**硬件**——无 CRC/ECC、无温度负载相关、无跨进程随机性，但有日历节奏，不符合；**网络**——分层可达性正常，被打是「利用成功」而非「连不通」；**权限/账号体系**——攻击者不持有合法账号，换账号不改变结果；**纯组织流程**——技术结构先行，流程因子下沉到 L2 与 L4，不作 L0）

## L2 逐层回溯

### 层1（轴＝速率恒等式 · 生成源：恒等式）

恒等式：`每月一次成功入侵 ⇔ 对手月新增可用入口速率 ÷ 我方月消除速率 ≥ 1`，其中
`新增可用入口速率 = 暴露面 × 缺陷生成速率 × (1 − 拦截率)`，`消除速率 = 补丁吞吐 × 覆盖面 × 发现速度`。
按等号右侧因子切格（三判据：正交＝各格不互相解释对方症状；可生成＝能说出为何该格必然存在；可观测＝每格有专属症状）。

| 格 | 该格为何必然存在 | 该格故障的可观测症状 | 本案现状判定 |
|---|---|---|---|
| **格1 暴露面**（管理面可达性） | 管理面必须被某条网络路径可达，才可能被打 | 后台登录页可从公网直接打开；每月固定时点出现成批扫描/爆破，且**总能扫到新的路径** | 后台与业务同域、直接挂公网，前置无身份边界 ⇒ **暴露面 ≈ 全代码面**，一个 URL 就是一个候选入口 |
| **格2 缺陷生成**（运行时/依赖/代码模式） | 可达之后必须存在可利用缺陷，才叫被打 | 补丁只修了被利用的那一个点，**兄弟文件里的同族写法仍在**；插件停更后再无版本可升 | PHP 5.6 已于 **2018-12-31 终止安全支持**（[php.net/eol](https://static.php.net/eol.php)），运行时层 CVE 永久不修；框架/插件无依赖更新通道 ⇒ **缺陷生成器常开**，「每月」≈ 公开 exploit 的发布与扫荡节奏 |
| **格3 拦截率**（缺陷→影响之间的必经层） | 从缺陷到影响之间必然有若干可设防的层，否则该层为 0 | 日志里只有「被成功」，没有「被拦截」；同一个 payload 变体下次仍然通 | 无 WAF、无 RASP、无前置鉴权、无网络分段 ⇒ **拦截率 ≈ 0**，必要条件链被压成一步：**任一代码缺陷 = 被打** |
| **格4 发现与消除**（可见性 × 补丁吞吐） | 消除必须发生在利用之前才有效，所以可见性必然在分母上 | 发现靠事后（业务异常、客户投诉、监管通报）；修完不知道还有没有别的 | 无资产/接口清单、无文件完整性监控、无漏洞巡检、无变更窗口 ⇒ **发现权在对手手里**，消除速度由对手的出拳节奏决定 |

### 层2（轴＝一次入侵的必经时序 · 生成源：必经时序）

用来解释题面真正的怪现象：「**补完下个月换个地方再被打**」。

1. **侦察定位入口** → 症状：出手的总是「没登记过的入口」（备份文件、遗留调试页、编辑器上传、导入导出、旧接口）。判定：入口集合未登记，**补丁覆盖面＝被通报的那一个 URL**。
2. **寻找可利用缺陷** → 症状：只在被报的那个文件上补，同族模板（upload/sql/include）不动。判定：**点补而非批量消同类**，生成器未动。
3. **穿越到达执行点** → 症状：请求直接命中应用代码，中间无任何一层能记录或阻断。判定：无隔离层 ⇒ 第2步任一缺陷**直接等于**第3步完成。
4. **取得能力（执行/越权/读库）** → 症状：一次漏洞即拿到数据库凭据与全量用户数据（后台与业务同库同账号、应用账号权限过大）。判定：**应用自身是唯一身份边界**，垂直/水平越权无第二道闸。
5. **造成业务影响** → 症状：数据集中且高价值，攻击收益高，所以对手会回来。判定：这是「**每月**」的**动机侧**成因——清掉一个洞只是抬高对手成本，不改变「值得再来」。

### → 类根

> **这一类（周期性被打）在结构上必然可能发生，是因为这套系统把「安全」实现成「一个个入口的补丁集合」，而没有实现成「入口生成机制的约束」。** 四个结构条件同时成立：
> ① **管理面由业务代码自己守门**（代码正确性＝身份边界）；② **运行时与依赖不可升级**（缺陷生成器永动）；③ **缺陷到影响之间没有必经隔离层**（必要条件链被压成一步）；④ **入口与缺陷存量不可见**（发现权在对手手里）。
> 四条件并存时，「补丁」只能删样本、删不掉生成器，所以攻击必然在别处重来；「每月一次」是攻击方扫荡与 exploit 节奏，不是巧合，也不是运气差。

**└ 个例根**：本月那个具体入口（某个插件/上传点/注入参数/越权接口）。它只是这个生成器本月吐出的**一个样本**，挂在类根之下——不与类根并列，也不能反过来用它的特征去解释「为什么是每月」。

## L3 双根

### 处置根（修本次）
**顺序必须是「先取证、再补洞」**：① 保全现场并判断是否已植入 webshell/后门、是否已建立持久化账号、是否已脱库（这决定要不要走通报与合规流程）；② 补本次入口；③ **强制轮换全部后台与数据库凭据**（打过一次就必须假定凭据已泄）；④ 关停不用的高危模块（上传、富文本编辑器、导入导出）。
Share=**唯一**（解释本次）；Lever=改配置；Cost=一次采样 + 一次应急。
**它的作用是止血，不改变下个月。**

### 消解根（灭这一类）
> **把管理面的可达性交给网络与身份边界，把缺陷的生成速率交给可升级的供应链——即「管理面不可从公网直达」＋「运行时/依赖有升级通道」两条同时成立。**

- **闸门① 不可发生判据**：当管理面**不在公网可达集合内**（只能经 VPN／零信任网关／固定出口 IP + mTLS 到达）时，攻击者连层2第3步都进不来，「任意代码级缺陷」不再等价于「被打」——本类问题在结构上**不可能发生**，只退化为「被探测」。**单加 WAF 过不了这道闸**：WAF 是概率不是结构（挂起表 #1）。同时闸门要求第二条：若运行时仍不可升级，则「洞变少但仍在」，类别未灭。
- **闸门② 可执行首边**（很小、不动业务代码、当天可回滚）：在现有 Web 服务器前加一层访问控制——**`/admin` 等管理路径只允许办公/VPN 出口 IP，其余一律 403**，同一层挂虚拟补丁规则集。这是从现状出发的**第一条边**，不是终点。
- **闸门③ 成本量级**（定量交给 📐 公式图，此处只给量级）：首边＝**人日级**；中期（运行时容器化 + 依赖锁定 + 每月重建镜像 + 凭据分权）＝**个位数量级人月**；对照全站重写 18 人月＝**两位数量级人月**。
  **关键论证**：18 人月买的是「换掉生成器」，但生成器里真正必须换的只有**不可升级的运行时 + 无升级通道的依赖**这两项，它们可以**单独买**，不必连业务逻辑一起买。反过来，**只重写而不装隔离层与升级通道，新系统下个月照样被打**——重写不是消解根，容器化运行时才是那两根柱子之一。

## L4 迁移出口

消解根指向「管理面撤出公网 + 运行时容器化 + 依赖可升级」，于是产生以下新问题清单：

1. **数据与状态**：容器化后的会话、上传、临时目录落点；老代码对 `register_globals`/`magic_quotes`/短标签的隐式假设在新镜像下行为变化；数据库连接与字符集。
2. **运行与自启**：从裸机/面板部署改为编排，进程生命周期由谁代持（树 `software.lifecycle` 子层原样适用：控制权换人代持，失败会发生在能打日志之前）。
3. **可观测性**：前置网关的「被探测」日志成为主证据源；补文件完整性监控与后台登录审计；告警阈值、值班归属要重新定义。
4. **凭据与权限模型**：网关身份与后台账号的映射（否则出现双份账号）；数据库账号分权，应用账号去掉 DDL 与跨库权限。
5. **组织能力**：从「被打→救火」改为「每月资产与依赖巡检 + 固定变更窗口」；必须有人对**入口清单**负责，否则格4 永远为 0。
6. **老功能裁剪**：下线长期不用的上传/富文本/导入导出模块（高频入口），需业务确认。
7. **预算法务**：网关/WAF 归属谁的预算；老运行时若已无受支持框架，需要「运行时迁移」立项而不是「全站重写」立项。

→ **本次问题降级为**：第 3、4 两项交界处「入口可见性 + 身份边界」工程里的一个 ticket。它不再是一场独立战役，也不是「重写 18 人月 vs 继续挨打」的二选一。

## 候选根排序（`Share × Lever ÷ Cost`，类根在上、个例根在下，排序带预算）

| 层级 | 候选根 | Share | Lever | Cost | 处置 |
|---|---|---|---|---|---|
| 类根 A | 代码正确性＝身份边界（管理面公网自守） | 主因 | 改架构（可低成本前置） | 一次网关规则配置 | **先做首边** |
| 类根 B | 运行时/依赖不可升级（缺陷生成器永动） | 主因（唯一解释「每月」节奏） | 换环境/改架构 | 一次迁移 | 并行立项，不阻塞 A |
| 类根 C | 无必经隔离层（缺陷直接=被打） | 主因 | 改架构 | 一次网关规则配置 | 并入 A（同一层同时解决） |
| 类根 D | 入口与缺陷不可见（发现权在对手） | 共因 | 改流程 | 一次盘点 | 立即起步，与 A 并行 |
| 个例根 a | 本月那个具体入口 | 唯一（解释本次） | 改配置 | 一次采样 | **立刻止血** |
| 个例根 b | 点补未批量（同族写法未清） | 共因 | 改流程 | 一次代码扫描 | 与补丁同批做 |

排序理由（一句话）：A/C 的 Cost 是一次配置、Lever 是架构级，故最先做；B 是**唯一**解释「每月」的根但 Cost 是迁移，故并行立项而非阻塞；个例根 a 是止血，不是答案。**预算有限 ⇒ 先买 Cost 最低、Lever 最高的那两行，而不是先买最彻底的那一行。**

## 结论

1. **根源不是「PHP 5.6 这个版本号」，而是四个结构条件同时成立**：管理面由业务代码自己守门（任意代码缺陷＝被打）、运行时与依赖不可升级（缺陷每月新增）、缺陷到影响之间没有必经隔离层（必要条件链被压成一步）、入口与缺陷存量不可见（发现权在对手手里）。补丁只能删样本、删不掉生成器，于是每月换个地方重来。
2. **所以「不再被打」的可达版本不是「零漏洞」，而是**：管理面撤出公网直达（只经身份边界到达）＋ 运行时/依赖装上升级通道。这两条成立后，即使本月这个洞没修，攻击者也进不来——这才是本类问题的结构条件；同时要接受「被探测」不会消失，消失的是「每月一次成功入侵」。
3. **代价不必是 18 人月**：首边是网关/ACL 的一天级配置，中期是容器化 + 依赖锁定 + 凭据分权的个位数量级人月。18 人月只在「运行时已无法承载任何受支持框架」时才成为必要项，而那时它也只是**迁移容器**，不是全站重写；**只重写不装隔离层，下个月同样挨打。**
