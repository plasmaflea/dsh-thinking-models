## L2 逐层回溯

**选轴（生成式，非列举）**：由恒等式生成 —— `一次失陷事件 = 可达入口 × 可利用缺陷 × 失陷后驻留能力`。三个因子都是**必要条件**（任一为 0，本类事件不发生），因此可以机械切格，不靠联想。三判据自检：**正交**（「换地方再打」归因到某格时不会同时解释别格的症状）、**可生成**（说得出为什么这一格必然存在：任何一次外部利用都要经过「能到达 → 有缺陷可用 → 用完能留下东西」）、**可观测**（每格有专属取证物，见下）。

**层1 · 可达入口**（必要条件：不可达则本类事件不可能）
症状/取证：防火墙或 NAT 上存在 `0.0.0.0/0 → 80/443/管理端口` 的放通；后台登录页、上传接口、phpMyAdmin、调试/运维端口在公网可访问；DNS 里后台域名解析到公网 IP。
判定：老后台是**单体应用直接对公网暴露**，没有身份感知网关、没有网段分段、没有「匿名可达路径清单」。可达面只随需求增加而增加（加一个导出、加一个回调、加一个上传），从不回收。

**层2 · 可利用缺陷**（必要条件：无缺陷则可达也打不穿）
症状/取证：被利用点集中在 **EOL 之后的运行时与组件**（PHP 5.6 的上游安全修复在 2018 年底已停止）、第三方 CMS/插件、手写 SQL/文件上传/反序列化/越权逻辑；把本月补的那个洞和上月那个洞放在一起看，**没有共享补丁**。
判定：漏洞的**产生速率**由「老代码模式 + 停更运行时」决定，是一条约恒定的正速率；而修补是**人工按个处理**，速率由值班人手与「有没有上游补丁」决定。**两条速率倒挂**——这不是这个月运气差，而是结构性赤字。所以「补完下个月换个地方」是这套结构的正常输出，不是意外。

**层3 · 失陷后驻留能力**（必要条件：无驻留则每次只是短暂事件，不构成「反复被同一个系统打」）
症状/取证：web 目录里出现 webshell 且**文件时间戳早于发现时间数周**；代码目录对 web 用户可写；会话/上传目录/代码/配置同层同盘；无文件完整性监控（FIM）、无不可变基础设施、没有「删掉重建」的脚本；数据库与服务账号长期不轮换。
判定：一次成功利用从「一次性事件」升级为**持续据点**——攻击者下次不必重新找洞，因为上次的据点（或从中拿到的凭据、内网映射）还在。这是「每月换个地方再打」的**机制性解释**：换地方的不是攻击者，是**你发现的位置**。
⚠️ 取证缺口：题面没有时间线、没有 webshell 落点、没有账号与出网记录，所以「本次是否已有驻留」**只能给判据不能给结论**。判定判据：把 webshell/后门文件时间戳与上一次补丁日期比对——早于补丁日期 ⇒ 上次失陷从未清除，你在给一个已经被占的房子换门锁。

**「检测与响应」折叠进层3**（跳步规则：格不可省，链可省）：MTTD 以周计 ⇒ 驻留窗口 = 周；MTTR 以天计 ⇒ 每次应急都在重建同一套手工动作。

**→ 类根**（面对整个大类，不是本次这个洞）：
**漏洞产生速率长期高于修补速率（赤字），叠加信任边界为零（无隔离、无不可变性），使任何一个洞都能直达数据并留下据点。**
换成一句人话：这台系统的**安全状态不可维护**——它要求的修补速度超过任何小团队的手工能力，同时又不提供任何「被打进来也无所谓」的隔离与可重建性。于是每次补洞只是把下一次事件的日期推迟大约一个月。

**全空列检验**：三格各有专属症状与专属取证物，无空格；若三格全空而「每月仍被打」，说明坐标错，须改为按攻击链时序切（侦察→入口→利用→持久化→横向→外带）——已列为挂起项，条件见挂起表末行。

**└ 个例根（挂在类根下，不许与类根平级）**：本月被利用的那一个具体入口（题面未给取证：入口请求、落点、账号、出网）。它**不是根**——把它当根，就是过去 N 个月一直在犯的错：处理个例根只能买到约 30 天，因为下个月的洞**本来就已存在于这条赤字结构里**。

## L3 双根

**处置根（修本次）** —— 按此顺序，顺序错了会浪费窗口：
1. **先保全**：日志、容器/主机镜像、数据库快照、访问日志时间线。先重装会毁掉时间线，下一个月的判断从此无据。
2. **先断可达，再补洞**：把后台、上传、phpMyAdmin、运维端口从公网摘掉（或前置身份网关）。先补洞后断可达 ⇒ 攻击者在窗口期内继续可用。
3. **清驻留面**：webshell 与可疑上传、计划任务/自启、SSH 授权 key 与新增账号、数据库账户与存储过程、可写目录内一切非源码文件、出网连接。
4. **最后才补那个具体的洞**，并把它记成流水线上的一次执行记录，不是一个战役的终点。

**消解根（灭这一类）** ——
> 把老后台从「公网可达 + 代码与状态同一可写空间 + 手工按个补洞」改造成「**不可达**（经身份感知网关）+ **不可驻留**（只读根文件系统、状态全外置、失陷即销毁重建）+ **可重建**（幂等部署、一键重建）的计算核」，并给补丁装上**流水线**（SBOM 组件清单 + 每周自动重建）。

- **① 不可发生判据**：本类问题的定义不是「存在漏洞」，而是「漏洞被反复利用**并留下据点**」。若入口需强身份且最小化 ⇒ 未认证攻击者没有路径可利用缺陷（因子1→0）；若根文件系统只读、状态全外置、失陷即销毁重建 ⇒ 利用成功也无法转为据点（因子3→0）；因子2（缺陷）**依然存在**，但它已不能单独生成本类事件。⇒ 「每月换个地方被打」在结构上不可能发生，剩下的只是**需认证的、可自动回滚的利用尝试**。
- **② 可执行首边**（从现状出发的第一步，很小）：不改一行业务代码，**在公网与老后台之间插一层身份感知反代**（Cloudflare Access／Tailscale／WireGuard，或 nginx + IP 白名单 + 强口令 + 二次认证皆可），把后台、上传、phpMyAdmin、调试端口全部摘出公网，只留真正必须匿名的少量路径，并**写出一张「匿名可达路径清单」**（这张清单就是以后每次评审的对照表）。小时级、可回滚，单独这一条就能打掉「未认证被打」这一大类的大半。
- **③ 成本量级**（量级估算，须交 📐 公式图复核，不在林状图里凭空给数字）：网关层 1–3 人日；容器化 + 状态外置 3–6 人周（取决于上传/会话/计划任务的外置量）；SBOM + 每周自动重建 2–4 人周 + 持续每周少量维护。**对比全站重写的 18 人月，量级差约 1–1.5 个数量级，且可分月交付、可停在任一层。**

## L4 迁移出口

消解根指向环境/架构变更，因此必须列出它自己会带来的新问题清单——**本次那个洞降级为其中一项**：

1. **状态与数据外置**：PHP session → Redis、上传目录 → 对象存储、日志、计划任务 → 外部调度。风险：老代码常把 `$_SESSION`、本地路径、`/tmp` 硬编码，外置会把**隐式本地状态清单**一次性暴露出来（这是好事，但要人周级预算）。
2. **运行与自启**：从「宿主机 + 手工 php-fpm」迁到容器 + 只读根 + 健康检查。语义差异（时区、上传大小、扩展、opcache、文件权限）会带来一波新故障。
3. **可观测性**：日志/审计落点由本地文件改为集中采集。**这条必须排在容器化之前**——否则「失陷即焚」会把证据和容器一起焚掉。
4. **凭据与权限模型**：DB 账户、SMTP、第三方 key 从 `config.php` 类明文里拔出，改为注入 + 可轮换。否则重建出来的容器仍带着同一把钥匙。
5. **组织能力**：发布流程、值班、以及**每季度真做一次「删了重建」演练**——这是维持消解根的唯一手段，缺它半年后必然回退。

→ **本次问题（本月那个洞）降级为**：第 1)/4) 项里的「外围网关规则 + 组件版本升级」这一条，属于流水线的一次常规执行，而不再是需要全员拉起来的应急战役。

## 结论（三句话）

1. **根不在「某个洞」**，在于这套结构**漏洞产生速率长期高于修补速率（赤字），且信任边界为零**——所以每次补洞只是把下一次事件的日期推迟约 30 天；老板看到的「每月一次」是这种结构的节拍，不是运气问题。
2. **让它不再被打，不靠「补得更多」，靠取消前提**：后台不可达（身份感知网关 + 匿名可达路径清单）、失陷不可驻留（只读容器 + 状态外置 + 一键重建）、补丁流水线化（SBOM + 每周重建）。三条落地后，「每月换个地方被打」在结构上不可能发生，只剩需认证、可回滚的尝试。
3. **全站重写 18 人月不是这道题的答案**——它解决「代码老」，不解决「可达 + 可驻留」。先花 1–3 人日把后台从公网摘掉，再按人周量级做容器化与流水线，收益/成本比高一个数量级；重写只在业务要新功能时按功能预算立项。
