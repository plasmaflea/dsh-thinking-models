# T9 预注册口径 · 消解根不可行

写定时间：发题之前。跑完后不许改判定式。

## 题面（逐字，五份必须完全一致）

> 我们有个 PHP 5.6 的老后台，每个月都要被打一次，补完下个月换个地方再被打。全站重写要 18 人月，业务不批。老板问：根源到底在哪，怎么才能让它不再被打？

## 埋设

- 技术真根：**没有统一的入参边界 + 上传功能与业务代码同权**，漏洞面是结构的，不是某个版本的。
- 消解根：重写/换栈——**正确但不可行**（18 人月，业务不批）。
- 本题测的是：**双根机制在消解根不可行时会不会退化成废话**。

## 关键词表（机械计数）

| id | 判定项 | 正则 |
|---|---|---|
| K1 | 显式标注消解根不可行/降级 | `不可行|不现实|降级|成本闸门|不可执行|18 人月|业务不批|暂不|不具备条件` |
| K2 | 给出减面路径（结构性缓解） | `统一入参|入参边界|统一入口|上传.{0,6}剥离|独立服务|WAF|权限分离|最小权限|参数化|框架` |
| K3 | 指出每月补丁是在治症状 | `治标|症状|打补丁|补丁循环|救火|每个月|反复` |
| K4 | 结论只给"重写" | 反向项：结论段落里唯一根治建议是重写/换栈 |

## 判定规则（预注册，四条）

1. **主判定**：单份同时命中 K1 且 K2 ⇒ 记为「双根机制正常（不可行→降级+减面）」。
2. 若 **≥4/5** ⇒ 该机制在这一型上站得住，写「饱和」。
3. 若 **≥3/5 命中 K4 而未命中 K1** ⇒ 本题成立，记「为了有消解根而给不可执行建议」。
4. 只报命中份数，不报答对率。
