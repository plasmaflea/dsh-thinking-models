[🌳 林状图] 选择理由：题面是「根源到底在哪」＋「怎么才能让它不再被打」——要的是纵向因果的根，不是选项清单，也不是数值估算。用回溯法的双根结构正好把「每月被打」拆成两个必须分别回答的问题：为什么打得进（可达性×可执行性），为什么下个月换个地方还是打得进（复发性）。消解根落在「类」（这一整类问题在什么结构条件下才可能发生），本次事件降级为其子项。

L0 类别判定：**软件类问题中的「安全姿态」子类**（判据：入侵是否成功由代码/依赖版本/环境姿态决定，换一台配置等价的机器同样可复现；已被利用的入口有确定性 PoC，不依赖硬件随机性或链路抖动｜已排除：硬件故障——无 CRC/ECC 报错、无随负载无规律的症状；网络故障大类——丢包/DNS/链路可达性不是本问题的变量，网络在这里是**暴露面**而不是**故障源**；权限/账号体系问题——ACL/令牌层面的「拒绝访问」不是症状，弱口令只占其中一格；纯组织流程问题——技术面确实有可用的洞，所以不能把它整类推给「预算不批」）。
⚠️ 判据里的「被打」按**入侵成功**理解；若题面的「被打」其实指 DDoS／流量压垮，则本图第 3、4 层选轴错误，须换轴重切（见异常栏）。

L1 树实例化：树 = `software`（L0 类别判定节点）· **v1** · 核查 2026-10-18 · 路径 `C:\Users\Administrator\.dsh\skills\forest-hierarchical-backtracking\tree\software.md`（索引：`…\tree\index.md`）。
- 本次**判为不适用**的节点：`software` 的六个正交子层（lifecycle／init／dependency／quota／concurrency／config）是给「进程起来了但行为不对」这一支用的；本问题的现象是「被成功入侵」，失败发生在应用之外（攻击者侧），六子层里只有 `dependency`（组件版本＝EOL 运行时与旧插件）勉强映射到第 2 层一格，其余不适用——**不用它作主轴**，改按入侵必经时序切。
- 本次**判为不适用**的候选节点：`win-service`（Windows 服务形态，无关）。
- **树外分支登记**：本问题的主干「攻击链＋暴露面＋检测响应」在 v1 树里没有节点，登记为 `v2 候选` 节点 `security`（理由：现有树只覆盖「程序自己出故障」，不覆盖「程序被对手利用」；这两类的判据、典型根、可观测症状完全不同，不能塞进 `software` 的六子层）。未建之前按临时轴 v0 切，已在挂起表留档。

L2 逐层回溯
**轴＝入侵必经时序**（生成源：任何一次成功入侵在结构上都必须依次经过这几格，少一格则入侵不成立；不是联想列举）。

| 层 | 轴格（必经时序） | 该格故障的可观测症状 |
|---|---|---|
| 1 | **暴露面**：哪个入口从公网可达 | 访问日志里有大量境外 IP 扫 `/admin`、`/phpmyadmin`、`.git/config`、`*.php.bak`；后台域名能在外网直接打开 |
| 2 | **入口点**：某个输入被送进危险解析/拼接 | 把公开 CVE 的 PoC 打过去，返回 200 并在上传目录出现新文件；同一 URL 在打了补丁的等价环境里不出现 |
| 3 | **落地与权限**：拿到执行权后能做什么 | 上传目录出现 `.php`；`www-data` 能写代码目录、能读 `config.php` 明文库密码、进程能主动出网 |
| 4 | **持久化**：怎么活到下一次 | 清除后 2–6 周复发；crontab／计划任务／SSH authorized_keys／数据库里存的 PHP／`.htaccess` 里出现陌生条目 |
| 5 | **利用与暴露**：为什么这次才被发现 | 出网流量异常、CPU 跑满（挖矿）、被监管/客户/云厂商通知、`/tmp` 有陌生二进制 |
| 6 | **检测与响应**：发现得有多晚、清得有多干净 | 从入侵到发现 > 数十天；清除靠手工翻目录；无文件基线、无日志外送、无复盘闭环；下个月同一入口再中 |

逐层判定（因果边，标必要/充分）：
- 层1 + 层2 → 入侵成功：**两个都是必要条件，合起来才充分**。缺层1（不可达）或缺层2（无可用输入）任一个，成功入侵不成立。
- 层3 → 「被打」升级为「全站失守」：**充分**。代码目录可写 + 库凭据明文 + 无出网限制 = 一次 RCE 直接等于数据与内网全拿。**这是「补完一个又换一个」为什么每次都这么疼的真正来源**——不是漏洞多，是每个漏洞的赔付上限都顶到天花板。
- 层4 → 复发周期：**必要条件**。没有持久化就只能利用一次；有持久化则「补完」不等于「清完」。
- 层6 → 发现滞后与复发：**必要条件**。无检测 ⇒ 攻击者有无限时间；清除不彻底 ⇒ 上一轮的立足点直接变成下一轮的入口。
- 全空列判据检查：六格全部有症状、且每格都能单独解释一个已观测现象（层1 解释"为什么总能被找到"、层4 解释"为什么下个月又来"、层6 解释"为什么每月才发现"），坐标未失效。

→ **类根（宏观，面 1）**：**这套系统的安全性，被维持在「每一个已知漏洞都被及时修补且每一处代码都没有洞」这个条件上，而它不具备维持该条件的结构能力**——运行时已停止安全支持（PHP 5.6 自 2018-12-31 起无上游安全修复）、第三方组件无补丁通道、自研代码无安全基线、无边界收敛、无检测。当一个系统的安全等价于「不出任何差错」，它的正常产出就是**按漏洞公开节奏被周期性攻破**；「每月一次」不是运气差，是这套结构的稳定输出频率。
→ **类根（宏观，面 2）**：**它是「单点全失守」结构**——一个 web 进程同时持有代码写权限、数据库明文凭据与内网可达性。于是漏洞的**数量**不重要，任意一个就够；修补的**速度**也不重要，因为攻方的成本是「找到一个」而守方的成本是「找全所有＋比 CVE 快」。这是攻守成本的不对称，不是勤勉问题。

   └ **个例根（本次）**：本月被利用的是某一处公网可达入口上未修补的输入解析缺陷（旧插件/上传/文件包含/SQLi 之中之一）→ 落 webshell → 因 `www-data` 可写 web 根、凭据在文件里、无出网限制，直接升级为全站控制；又因无文件基线且旧 webshell／计划任务未清干净，下个月的入口其实已经预置好了。
   个例根挂在两个类根之下（不是平行清单）：它之所以能发生＝面 1 允许「未修补的洞」长期存在；它之所以能一次打穿＋反复发生＝面 2 的权限集中 + 层4/层6 的缺失。

L3 双根
**处置根（修本次，48 小时内）**：按「假定已被完全控制」处置，而不是按「清掉那个文件」处置——
1) 先**收边界**（断掉公网入口，把后台挂到内网/白名单后面），止住继续被利用；2) 取证留存（进程、`/tmp`、crontab、`authorized_keys`、web 根与上传目录全量快照、访问日志外送）；3) **凭据全换**（DB、SSH、后台账号、API key、云 AK，含代码里硬编码的）；4) 清持久化点（webshell、计划任务、`.htaccess`、DB 里存的 PHP、被改的 `index.php`）；5) 从**已知干净基线**重装一份代码比对差异，而不是在原机上删文件；6) 定发现时间与影响面（外发了什么），决定是否需上报。

**消解根（灭这一类）**：**把「单个漏洞」与「全站失守」解耦——让代码执行权限拿不到写权限、拿不到明文凭据、出不了网，且运行实例可随时从不可变镜像重建。**
- ① 不可发生判据：若当时采用它，攻击者在层3 上来就会撞墙——无代码目录写权限 ⇒ 无法落 webshell（层4 的持久化形态被结构性删除，不是被清理得更快）；无明文凭据 ⇒ 拿到的进程换不来数据库与内网；无出网 ⇒ 拿不到工具也送不出数据；实例可重建 ⇒ 任何未被察觉的篡改在下次重建时归零。于是「每月一次成功入侵并造成全站失守」这个结果**在结构上无法达成**，只剩「一次被拦下或被重建清零的尝试」。注意它消灭的是**结果**而不是**尝试**：扫描和打洞还会继续（那是攻方成本决定的），本篇的判据只保证不再有「成功」这一状态。
- ② 可执行首边（可以很小，今天就做）：把上传/附件目录改成 `noexec` 且与代码目录分开挂载，同时收紧 `www-data` 对代码目录的写权限——0.5～1 人日，先堵住「漏洞 ⇒ 落文件」这条最短路径；第二步把 `config` 里的库账号换成只有该库 DML 权限、且不可读其他库、且来源限本机的账号（1 人日）。**不需要等全站重写。**
- ③ 成本量级：首边 1–2 人日；把 web 层容器化／只读根文件系统／出网白名单／日志外送做全，量级在 **2–6 人周**；与全站重写 18 人月差一个数量级以上，且可分批、可回滚、与业务代码改动解耦（这是它能在「业务不批 18 人月」的前提下仍然可决策的原因）。
- 补充：**入口收窄（IP 白名单/VPN）是这条消解根的必要前置边**，但它**单独**不构成消解根——见挂起表第 4 行的降级判定。

L4 迁移出口（因消解根产生的新问题清单，本次问题降级为其中一项）
1) **访问方式**：后台不再公网可达 ⇒ 需要 VPN／零信任网关的账号体系与审批流程，外包与远程办公要重排。
2) **文件与状态**（最容易被低估）：代码目录只读 ⇒ 上传落对象存储、`session`/临时目录/缓存外置，旧 PHP 代码里写死路径的地方要改——这部分**是真实的代码工作量**，但它按需改、按月付，不是 18 人月一次性。
3) **部署与运行**：不可变镜像 ⇒ 发布流程、配置注入方式、回滚策略全变；数据库迁移与数据一致性校验要单独排期。
4) **可观测性**：日志/指标从「本机文件」变成「集中采集」，文件完整性基线的维护归谁。
5) **凭据与权限模型**：最小权限库账号、密钥进配置中心/密钥管理，硬编码凭据清理需要盘一遍历史代码（有存量清单）。
6) **组织能力**：谁值班看告警、谁批白名单、补丁窗口怎么排、应急响应按什么清单跑。
→ **本次问题降级为**：第 6 项里的**一行应急响应条目**（按标准处置清单执行），不再是需要单独立项、单独立预算的独立事故。这正是「不解决具体问题」的合法性来源：它被吸收进一个更大的、可一次买断的结构里。

结论（三句话）
1. 根源不是「哪个漏洞没补」，而是**这套系统的安全被设计成「靠不出错」来维持**——跑在没有安全补丁的运行时上、正对公网、而且一次 RCE 就等于全站（代码可写＋库密码在文件里＋能出网）。在这样的结构里，每月被打一次是**正常产出**，不是运气差；补完这个、下个月换个地方，是它的固有节奏。
2. 所以「让它不再被打」的正确目标不是「零次尝试」（做不到，扫描是免费的），而是**零次成功**：入口不再公网直达、打进来也拿不到写权限/凭据/网络、被改动也能靠重建归零。这三件事加起来，把「每月一次全站失守」变成「每月若干次被拦下的尝试」。
3. 预算上它不需要 18 人月：首边（后台撤出公网＋上传目录 `noexec`＋库账号最小权限）是 **1–2 人日**，做全是 **2–6 人周**，与业务代码改动解耦、可分批、可回滚。如果连这个量级也不批，那答案就变成一句必须写进会议纪要的话：**这是业务侧已决策接受的风险**，技术侧唯一还能做的就是把它隔离到独立网段/独立域名，确保它被打时不波及主站——而不是继续每月做一次清除。
