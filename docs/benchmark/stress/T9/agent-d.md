## L0 类别判定

**类别**：安全运维类 —— 主类挂在 `software` 大类的 **`dependency`（不可维护底座）+ `config`（配置姿态：暴露面/权限/目录可写）** 两个子层；另有两条**树外**子域必须显式并入：`security`（对抗性外部输入与利用链）、`org-process`（预算与响应模式）。

**判据**：
- 满足 software 判据①：同一份代码在等价机器上「是否被攻破」可复现——攻击者的成功取决于代码与配置姿态，不取决于物理介质。
- **弱满足** software 判据②：这里的失败不是「确定性失败」，而是「外部输入驱动的确定可利用性」。这个弱满足本身就是关键信号——**它说明根不在 software 六子层的任何单格里**，所以每月「补一个洞」永远补不完。
- 决策者要的是「不再被打」，主体是**对抗性外部输入**，而 v1 树只有「故障形态」维度，没有对抗维度 → 见 L1 树外分支。

**已排除的大类**：
| 被排除 | 判据 | 依据 |
|---|---|---|
| 硬件故障 | 无 CRC/ECC、无温度或负载相关随机性 | 症状有明确利用链，不是随机 |
| 网络问题 | 不是可达性不足，而是可达性**过多** | 攻击者能到达，恰恰说明链路正常 |
| 权限/账号体系问题（作为主类） | 不是「换同账号交互式登录即正常」的形态 | 主体是外部未授权者；但**若为内部凭据泄露则本行恢复**，见挂起表 #4 |
| 组织与流程（作为主类） | 「技术手段已全部正常，问题仍由人产生」不成立 | 技术面明确有洞、有暴露面，不能先归因到人 |

## L2 逐层回溯

**选轴（生成式，非列举）**：轴 = **一次外部入侵事件的必经时序**。任何一次「被打」都必然依次经过五步并回到第一步，一步不可省，故可机械切格：

> 可达 → 可利用 → 利用成功（权限姿态） → 后果与被发现 → 响应与修补 → 回到「可达」

五格 + 一格闭环＝六格。每格给出「该格故障的可观测症状」与判定：

| 格 | 该格在管什么 | 该格出问题时的可观测症状 | 判定 |
|---|---|---|---|
| **G1 可达性（暴露面）** | 攻击者能否到达入口 | 后台 admin 域名/端口在公网可直连，无 IP 白名单、无网关认证、账号共享；扫描器每月扫到 | 必要条件成立。**且这是六格中唯一能被守方单方面关掉的格** |
| **G2 可利用点（漏洞产出率）** | 从「能到达」到「有洞可用」 | 每次洞出现在不同文件：老代码每页自拼 SQL、自处理上传、自 `include`；PHP 5.6 已于 2018-12-31 停止安全支持（末版 5.6.40），底座不再有人替你修 | 产出方**不在你的控制域**，且产出率随时间**单调不减**（新公开的 5.6 生态 CVE 与攻击技术只增不减） |
| **G3 利用成功的权限姿态（爆炸半径）** | 一个洞能炸多大 | 一个洞=全站：单 DB 账号全库权限 / web 目录可写**且可执行** / 主机可出网 / 后台账号共享 | 这条边把「洞」放大成「事故」；是「每月一次**事故**」而非「每月一个洞」的必要条件 |
| **G4 后果与被发现（可观测性）** | 多久知道 | 发现靠外部（客户投诉、监管通报、云厂商、挂马被搜索引擎标记）；发现延迟以「月」计 | 发现延迟直接**定义了这个节拍**——「每月一次」的周期长度由它决定 |
| **G5 响应与修补（修补率）** | 多久补上、补多少 | 补丁以「洞」为单位计价、以「事故」为触发；业务驳回 18 人月重写；补完即验收 | 修补率被钉死为常数 ≈ 1 洞/月 |
| **G6 闭环** | 补完回到 G1 | 「补完下个月换个地方再打」 | **六格不是六个并列原因，是一个闭环**；周期 = min(G4 延迟, 1/μ) |

**跨格校验**：六格症状互不重叠（G1 是可达性、G2 是代码与版本、G3 是权限、G4 是日志、G5 是预算）→ 正交成立；每格都能一句话说出「为什么这步必然存在」→ 可生成成立；每格有专属症状 → 可观测成立。**无空格**，故不需要换轴。

### → 类根（根落在整个大类上）

> **漏洞的「产出率」与「修补率」分属两个控制域：产出一侧（G1 暴露面 × G2 不可维护底座 × 无统一输入边界）不在你的控制域内，且随时间单调上升；修补一侧（G5 事故驱动的预算 + 人肉补丁）由你控制但产能固定。**

写成恒等式（这是轴的第二个合法生成源）：

```
剩余风险 R(t) = ∫₀ᵗ [ λ_产出(τ) − μ_修补(τ) ] dτ
λ_产出 = f(EOL 底座, 输入边界缺失, 公网暴露面)  且  dλ/dt ≥ 0
μ_修补 ≈ 常数（1 洞 / 月，事故触发）
```

**只要 λ ≥ μ，R 不收敛——「每月一个新的洞」是这个恒等式的必然输出，不是运气差，也不是某个人不努力。** 过去 12 个月的全部动作都是在减小「已实现的 R」，一次都没有动过 λ/μ 的关系，所以下个月必然复现。这就是「补完下个月换个地方」的机理。

### └ 个例根（挂在类根之下，是子节点，不是平行清单）

- **个例根 A：本次那个具体洞**（某个页面的 SQL 注入／文件上传／反序列化／`include` 路径穿越）。它只解释「这一次是哪儿」，**不能解释「为什么还有下一次」**。
- **个例根 B：本次未清场的持久化**（若存在残留 webshell／计划任务／`php.ini auto_prepend_file`／DB 内异常账号）。若成立，则「下月换个地方」可能不是新洞，而是同一个入侵者的新动作 —— 见挂起表 #1。

> ⚠️ 过去 12 个月的修补策略犯的是一个**类别错误**：**把个例根当类根用**。这解释了为什么每次「修好了」都真的修好了那一个洞，而问题依然按月复发。

## L3 双根

### 处置根（修本次，量级：1–2 周）

1. **清场先于堵洞**：全量取证——webshell 扫描、进程/定时任务/启动项、`authorized_keys`、`php.ini auto_prepend_file`、DB 内异常账号与 UDF、后台账号表。
2. **轮换全部凭据**：DB、后台账号、API key、云 AK、证书。
3. **堵本次洞**。
4. **回捞日志**，确定入口、驻留时长、外泄数据范围——这一步决定本次是「事故」还是「合规事件」，不能事后补。

> 处置根里**不写「加固」**：加固属于消解根，混进来就会重演「补完即验收」。

### 消解根（灭这一类）：三条并列结构条件 + 一条保鲜条件

同时成立则「每月被外部打一次」**在结构上不可能发生**（不是变少见）。

**S1 暴露面收口** —— 管理后台不在公网可达，只经固定出口／VPN／零信任网关。
- 不可发生判据：攻击者**够不到入口**，则 G1 归零，G2 的洞再多也无法被外部触发，「被外部每月打一次」这一整类**结构上不可能**。
- 可执行首边：今晚把 admin 的 DNS 记录摘掉或前置一层强制 IP 白名单/网关认证；**随后观察一周残余访问日志**（残余访问者＝你不知道的自动化、外包、监控，直接进迁移清单）。
- 成本量级：**周级**（1 周内可上线），不触碰业务代码，不需要业务批预算。
- 三道闸门：①通过 ②通过 ③周级 ✔

**S2 爆炸半径切断** —— 洞存在也拿不到全站：上传目录**不可执行** + DB 分账号最小权限 + 应用**不出网**（出网走白名单代理）+ 后台个人账号 + 关键操作二次认证。
- 不可发生判据：「一个洞 → 全站失守/数据外泄」这条因果链（G3）被物理断开。此时洞依然会出现，但**事件降级为告警** —— 「被打」从一个「事故类」降级为「噪声类」，这才是可承受的终态（对不可维护底座尤其重要）。
- 可执行首边：web 目录挂 `noexec`、DB 应用账号降到只读＋必要写、加出网白名单。
- 成本量级：**周级**。
- 三道闸门：①通过（它不消灭洞，但消灭「洞=事故」，判据表述必须写清是后者）②通过 ③周级 ✔

**S3 底座可维护** —— 运行时与组件回到**有补丁可打**的状态。
- 不可发生判据：λ_产出 回到「社区与你共同承担」，则「补丁追不上产出」这一支消失。
- **手段不是 18 人月重写**，是绞杀者模式（strangler）：新功能/新页面只写在新运行时（PHP 8.x）或现成受维护框架上，老页面按**访问量 × 风险**分片迁移，一次一片；在迁完之前，把不可维护的 5.6 关进 S1+S2 的笼子里。
- 可执行首边：选 1 个「高风险 × 高访问」页面在 8.x 上重做，跑通构建与部署流水线。
- 成本量级：**分片、每片周级；总量仍是人月级，但可分摊、可按季度批，不需要一次性立 18 人月项目**。
- 三道闸门：①通过 ②通过 ③分片周级 ✔

**S4 预算与响应机制（组织层，树外分支；判定：消解根的保鲜条件，不独立成根）** —— 安全预算的触发条件从「事故」改为「边界与资产」（公网可访问的管理端点清单、EOL 组件清单、权限清单）。它**不过第①道闸门**（不直接使问题不可发生，只防止消解退化），故按规则登记为保鲜条件而非并列根。
- 首边：把「公网可访问的管理端点清单」变成每月固定评审的一项。

## L4 迁移出口

因 S1–S3 产生的新问题清单（消解根一旦执行，这些问题必然出现）：

1. **数据与状态**：5.6 → 8.x 的字符集（`utf8` → `utf8mb4`）、`mysql_*` → PDO、`ereg`/`mcrypt` 移除、magic quotes 遗留转义、会话存储迁移。
2. **运行与自启**：裸机/面板 → 容器化；php-fpm 版本与扩展清单（openssl 替 mcrypt 等）。
3. **可观测性**：日志集中化、WAF 告警接值班、文件完整性监控、管理操作审计留痕。
4. **凭据与权限模型**：共享后台账号 → 个人账号 + SSO + 最小权限 DB 账号 + 密钥轮换。
5. **组织能力**：值班与变更流程、外包/第三方组件的准入与台账、EOL 组件清单纳入例行评审。

→ **本次问题降级为清单第 3) 项的一个输入**（可观测性缺位导致发现延迟以「月」计，从而定义了复发节拍），以及第 5) 项台账的一条记录。

> 没有这一层，「不解决具体问题」就是遗漏，不是策略。

## 候选根排序（`Share × Lever ÷ Cost`，带预算；上下级结构，不平铺）

| 层级 | 候选根 | Share | Lever | Cost | 序 |
|---|---|---|---|---|---|
| **类根** | λ_产出 ≥ μ_修补（速率失衡） | 唯一（解释全部 12 次复发） | 不可直接动——只能通过其子节点改 | 一次迁移（人月级，可分摊） | 1（它决定动作**顺序**，不是一次操作） |
| 类根之子 | **S1 暴露面收口** | 主因（覆盖「为什么外部每月能打进来」） | 改配置／改架构 | **一次采样**（1 天可验证残余访问） | **2 ← 先做** |
| 类根之子 | S2 爆炸半径切断 | 共因（覆盖「为什么一个洞=一次事故」） | 改配置 | 一次权限变更/重启 | 3 |
| 类根之子 | S3 底座可维护 | 主因（长期） | 换环境 | 一次迁移（分片） | 4（预算最大，排在前两条之后） |
| 个例根 | 本次那个洞 | 唯一，但只解释本次 | 改代码 | 一次补丁 | 5（先做，但**不算根**） |
| 个例根 | 未清场的持久化 | 次要（若成立升为唯一） | 清场/重建主机 | 一次重建 | 6（先做，不算根） |

**预算说明**：Cost 最小的两条是 S1（一次采样）与个例根（一次补丁），所以它们必须在本周内做完；S3 的 Cost 是人月，故只能进「按季度分片」而不是「本月立项」——**排序是预算的函数，无预算约束的清单不是答案**。

## 挂起表

| # | 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|---|
| 1 | 同一攻击者 + 残留持久化（后门/webshell 未清干净） | 非根，但可能升为主线 | 「补完下月换个地方」也可由同一 C2 的新动作造成，题面没有清场证据 | 任一月事件日志出现同一源 IP 段／C2 域名／webshell 家族／同一上传路径模式 → 恢复为主线，根改为「事件响应只堵洞不清场」，S1 顺序后移 |
| 2 | 洞来自第三方组件（老 CMS 插件、富文本编辑器、统计脚本） | 个例根的来源分支 | 题面未给出洞的分布 | 修补记录集中在某几个第三方组件 → 恢复为「供应链台账缺失」，S3 首边改为组件清单与替换 |
| 3 | 「被打」实为流量型攻击（DDoS/CC）而非入侵 | 挂起，不属本类 | 题面无数据外泄/后门证据，也未排除 | 无后门、无异常登录、无外泄，仅带宽/CPU 打满 → 换轴至 `network`／`quota` 支，本图不适用 |

| 5 | 已有 WAF/防护但被绕过 | 挂起 | 题面未提现有防护 | 有 WAF 且日志有拦截记录 → S1 从「新建边界」降级为「核对绕行路径」（源站 IP 直连是最常见绕行，必须查） |
| 6 | 18 人月估算正确且不可压缩 | 挂起，**不影响结论** | S1/S2 的量级与重写完全无关 | 若 S1/S2 上线后仍每月被内部利用 → 底座迁移不可再分摊，必须一次性立项 |
| 7 | **树外分支 `security`**（Web 攻击面/利用链） | 树外，登记 **v2 候选** | v1 树只有故障形态维度，缺对抗性外部输入维度 | 树升 v2 并补 `security` 节点后重跑本图 L1 |
| 8 | **树外分支 `org-process`**（预算与响应模式） | 树外，索引已列为待建 | 同上，社会分类维度缺失 | 补节点后重跑 L1 |
| 9 | 合规/审计口径把「扫描告警」计为「被打」 | 挂起 | 口径可能放大频次，使「每月一次」变成统计假象 | 核对事件定义（是否含未成功扫描）→ 若为口径问题，则 μ 实际远大于 1/月，只需修 G4 |
| 10 | 业务逻辑漏洞（越权/支付）而非技术注入 | 挂起 | S1/S2 对它无效，需要独立风控支 | 洞集中在业务逻辑而非输入处理 → 另立业务风控子树，不进本图 |

**折叠说明（本表未删除任何分支，只做折叠）**：G2 的「无统一输入边界」与「EOL 底座」折叠为同一节点「产出率不可控」，因为二者对 λ 的作用方向相同（都使 λ 不减），拆开不增加独立性，属纯开销。

## 结论

1. **根源**：不在某个洞，也不只是「PHP 5.6 老」。根源是**漏洞产出率长期 ≥ 修补率**——产出一侧（公网暴露的入口 × 不可维护的 5.6 底座 × 无统一输入边界）不在你的控制域且随时间上升；修补一侧（事故触发、人肉补丁）被钉死为约每月一个洞。恒等式不收敛，所以「补完下个月换个地方」是必然，不是运气。
2. **停止被打**：继续补——速率不够；等 18 人月重写——期间旧系统仍在挨打，且把安全变成一个需要业务批准的立项＝预算博弈必输。真正的动作是把问题从「消灭洞」换成「消灭洞的可达性与危害」：**S1 后台摘出公网**（G1 归零，外部触发在结构上不可能）、**S2 切断一个洞到全站的传导**（洞从事故降级为告警）、**S3 绞杀者分片换底座**（λ 回到可维护状态）。
3. **给老板的一句话**：现在要的不是 18 人月，是 **1–2 周**把后台从公网摘掉并把权限收窄；这两条做完，「每月被打一次」这个节拍在结构上就不再成立，剩下的才是「要不要继续投资底座」的决策。
