# 月刊式被打的 PHP 5.6 老后台：根源在哪，怎么才能不再被打

**[🌳 林状图] 选择理由**：提问是「根源到底在哪 + 怎么才能不再被打」，是根因定位题，不是选项目枚举（网状图）也不是定量预估（公式图）；未知在**因果深度**（为什么按月复发、为什么换个地方还能被打），不在广度。按技能边界，消解根的成本量级本轮只给**量级**，不凭空出数字，定量交给 📐 公式图。

---

## L0 类别判定

**类别**：软件类 · **对抗性子类**（攻击者驱动的重复性入侵）。
**判据**：①可复现性来自代码/配置/环境姿态——同一套代码 + 同一暴露姿态下，攻击可稳定复现 ✓；②但**不满足** `software` 节点第 2 条判据——本题的失败不是「给定相同输入与时序可重现的确定性竞争」，而是由**对手的意图与经济动机**驱动的：同一份代码，对手换工具就打穿不同点，防守方改变了的是概率而非法定性结果。⇒ 本节点需扩展出对抗性子类，不能直接套。
**已排除的大类**：硬件故障（症状随攻击而非随机、跨系统不随机）、网络问题（可达性可测、症状不随链路变化）、账号权限体系（不是单账号特例，是多入口被利用）。**组织流程类：不排除，挂起**（见挂起表第 2 行）——技术面尚未收紧，组织问题无法与结构问题分离测量。

## L2 逐层回溯

**选轴**：一次成功入侵的**必经时序**（生成式：任何入侵不可能跳过其中任一步，故六格必然存在，非列举）。三判据自检：正交 ✓（各格症状不互相解释）、可生成 ✓（每格能说出为何必然）、可观测 ✓（每格有专属症状）。

### 层1 暴露面（攻击者能不能碰到）
- 该格在管：PHP 进程是否对**不可信网络**存在可达入口。
- 故障**可观测症状**：外网 `curl` 后台登录页返回 200/302（未认证即可触达登录页）；access log 出现批量扫描器特征（`/phpmyadmin`、`/.env`、`/wp-login.php`、异常 UA）；后台路径被搜索引擎收录；同一 IP 段反复探测。
- 本题判定：**没有这一格的控制**（不是守不住，是无人负责）→ **主因**。
- 为何必然存在：没有触达就没有入侵，这一步任何攻击链无法跳过。

### 层2 初始访问（某个入口的输入被当成代码/命令/路径执行）
- 症状：单条请求参数超长或含 `union` / `base64` / `<?php` / `${`；上传目录出现新 `.php`；错误日志出现 `eval()'d code`；文件名含 `%00`。
- 判定：**每次真实发生**，但这是**个例根层**（本次是哪个洞）。**真正的问题不在这一层**——因为能补的点是有限的，能产出的洞不是（见层1、层6）。
- 为何必然存在：入口是攻击者与代码的唯一接触面。

### 层3 立足与持久化（进来之后能不能活下来、能不能再回来）
- 症状：web 根目录出现**时间戳异常**的新 `.php`（尤其混在 `images/`、`upload/` 之类目录）；`.htaccess` 被改；crontab / 计划任务新增；`/tmp` 下有可执行文件；文件属主变成 web 运行用户。
- 判定：**「每个月回来」的机制嫌疑第一位**（见诊断分支 D1）——月度复发+换位置，也可由「旧锚点复用」完美解释，不必是新洞。
- 为何必然存在：一次入侵要被**重复利用**，必须留下可再进入的锚点；反之若每次都是全新洞，恰恰说明锚点被清干净了。**两者可观测区分**。

### 层4 凭据与提权（能拿多深、能拿多久）
- 症状：后台管理员账号/口令被改；DB 出现陌生账号或 `FILE` 权限被开；`authorized_keys` 新增；同一 DB 口令出现在多个系统；`config.php` 可被 web 直接下载。
- 判定：**典型存在且从未被处置**——老后台常见「一个 admin 口令走天下」，DB 凭据硬编码在 web 可达目录。
- 为何必然存在：提权是扩大战果的必经环节；没有它，攻击收益撑不起「每月来一次」的投入。

### 层5 影响（对手为什么要来）
- 症状：出网连接异常（拖库 / 挖矿 / C2 心跳）；被挂马做跳板；被勒索留信；站点权重异常；带宽账单突增。
- 判定：**题面缺失**，但「每月稳定来一次」本身就是证据：**收益在持续变现**（数据 / 算力 / 流量 / 信誉至少一项）。这是**经济学根**，不是技术根。
- 为何必然存在：无收益的重复入侵不可持续——对手的成本也要回收。

### 层6 发现与响应（守方闭环）
- 症状：发现延迟 ≈ 一个月（「每个月」是对手周期，不是防守节奏）；处置清单里**只有「补洞」**，没有清除、没有凭据轮换、没有检测、没有复盘。
- 判定：**这是「按月循环」的引擎**——响应动作只覆盖层2 的**一个点**，完全不覆盖层3、层4、层6 自身。
- 为何必然存在：任何防守都必须有「发现→处置」闭环；缺环时，**对手的周期就成了你的周期**。

### → 类根

> **这套系统同时满足四个条件：(a) 补丁供给无上游（PHP 5.6 的安全支持已于 2018-12-31 结束，此后无官方安全补丁）；(b) 不可维护的代码直连不可信网络、中间无中介层；(c) 入侵后不清持久化锚点、不轮换凭据；(d) 无检测能力，发现延迟以月计。四者同时成立时，「被反复入侵」是这套结构的稳定态，不是偶发事故。**

一句话类根：**「把无法维护的代码，放在敌人能直接碰到的地方，并且不打算知道自己被碰过。」**
三件里掐掉任意一件，本类问题即不成立；三件全在，补多少洞都只是**延长下一次的间隔**——这正是「补完下个月换个地方」。

**└ 个例根（挂在类根下，不是平行项）**
- **个例根 A（本次）**：本轮被利用的那个具体入口（未审计的参数/上传/包含），叠加**上次处置可能未清除的锚点**（由 D1 判定）。
- **个例根 B（机制，最要命）**：防守方把「根」取在个例上——每次只补**被打的那一个点**，不补**这一类**代码缺陷，所以每个月从零开始。这一条与本题主旨同构：**用个例根冒充类根，就是按月循环的引擎。**

## 诊断分支（必须先判，不能默认）

- **D1：每月是「新洞」还是「同一批人复用旧锚点」？**
  判据：查层3/层4 锚点的时间戳是否**早于上次处置时间**（webshell mtime、crontab 创建时间、DB 账号创建时间、`authorized_keys` mtime）。
  - 早于 ⇒ 上次没清干净 / 凭据没换 ⇒ 处置根第一条是「重建 + 全量轮换」，「补洞」居后。
  - 晚于且每次入口不同 ⇒ 供给无限（类根 a+b 生效）⇒ 消解根必须掐暴露面。
  代价：一次日志与文件时间取证（人日级）。

- **D2：后台是否真的对公网可达？** 判据不是「能不能登」，而是**未认证时是否返回 200/302 到登录页**。这一条决定消解根是否成立。

## L3 双根

### 处置根（修本次，天级；顺序不可换）
1. **止血**：先把后台入口从公网摘掉（安全组 / 网关白名单）。**先断通路，再谈清理**——否则清理期间对手仍在里面。
2. **取证（最小集）**：`access.log` 异常请求、web 根目录新增文件 mtime、crontab、DB 账号表、`authorized_keys`、出网连接（`ss -tp`）。
3. **重建而非清理**：代码从版本库按已知好提交重新部署并比对文件哈希。清干净的概率远低于重装。
4. **全量凭据轮换**：后台账号口令、DB 账号、SSH key、API/云 AK、第三方对接密钥——**一个不漏**。
5. **补洞放到最后，且按「类」补不按「点」补**：对 SQL 注入 / 任意文件上传 / 文件包含 / 命令执行 / 反序列化 / 弱口令六类各做一次全量排查，把这一类**所有实例**列成表，一次清完。
   - ⚠️ 这一步仍然只是**缓解**：它把「每月一次」变成「每季一次」，不改变类问题结构。**不许把它当消解根**（见挂起表第 6 行）。

### 消解根（灭这一类）

> **让攻击者与 PHP 5.6 进程之间不再存在无人看守的通路**：暴露面收敛 + 入口层有主 + 补丁供给有上游。

**三道闸门**：

1. **不可发生判据**：本类问题的必要条件是「攻击者能**直接**触达 PHP 应用进程」。若后台仅经办公网 / VPN / 零信任网关可达，则公网扫描器与批量利用工具**结构上无法命中任何入口**——不论代码里还剩多少洞。这不是「变少见」，是**必要条件被移除**。
   残留：内部人与凭据泄露属于**另一个类**，登记为挂起（挂起表第 3 行），不混入本结论。

2. **可执行首边**（从现状出发的第一步，可以很小）：
   - **第 1 天**：在现有网关/安全组上加一条规则——`/admin` 及后台全部真实路径仅允许办公网出口 IP 段与 VPN 段访问，其余 403。**不改一行代码**，当天上线，可回滚。
   - **第 1 周**：给 PHP 5.6 上**虚拟补丁**（WAF / ModSecurity 规则集）。因为 5.6 已无官方安全补丁，这是唯一能把「上游」补回来的替代品——把补丁供给从「人工追洞」换成「规则覆盖类别」。
   - **第 1 月**：产出**暴露面清单**（哪些路径/端口对公网开放、谁负责、上次审计时间），纳入变更流程。
   - **第 1 季度起**：以「容器内只升不改业务逻辑」的方式推进运行时升级（5.6 → 仍在支持的 7.4/8.x）。它**不等于** 18 人月全站重写，兼容风险集中在 `mysql_*` 扩展、短标签 `<?`、已废弃 API、旧第三方 SDK。**具体工时本轮不给数字**（实测依赖树与 `mysql_*` 调用点数后再估，交公式图）。

3. **成本量级**（只给量级，不编数字）：
   - 首边（访问控制）：**人日级**、配置变更、可回滚
   - 虚拟补丁：**人日级** + 订阅费
   - 暴露面清单：**人日级**
   - 运行时升级：**人月级**，工作量与风险须实测
   - 全站重写：**18 人月**（题面给定）
   → 结论：**「不再被打」不需要 18 人月。** 三件里最便宜的一件（掐暴露面）就足以让本类不成立。

## L4 迁移出口

消解根一旦指向结构变更，必然产生新问题（缺这层，「不解决具体问题」就是遗漏而非策略）：

1. **访问路径与例外**：VPN / 零信任引入后，远程办公、外包、第三方对接怎么进；紧急破窗（break-glass）账号怎么管、怎么留痕、多久轮换。
2. **凭据与权限模型**：从「一个 admin 口令」到「个人身份 + 最小权限 + 可审计」；谁在何时改了什么要能查。
3. **可观测性**：日志必须**移出 web 根目录**（否则日志本身就是攻击者的地图）；加文件完整性基线（web 目录新增 `.php` 即告警）；出网连接白名单。
4. **数据与运行时**：5.6 → 7/8 的兼容改造（`mysql_*`、短标签、废弃 API）、容器化后会话与上传目录的落点。
5. **组织能力**：谁负责漏洞订阅与 WAF 规则更新；变更窗口怎么和业务谈；把「被打一次补一次」的例会改成「每月看暴露面与检测告警」的例会。
6. **发布与回滚**：老系统常见的「FTP 手工上传」式部署 ⇒ 至少建立最小可回滚发布（版本标签 + 一次性全量部署），否则处置根第 3 条「重建而非清理」**根本执行不了**。

→ **本次问题降级为**：L4 第 1 项（访问路径与例外）下的子项「后台入口访问控制」，以及 L4 第 3 项（可观测性）下的子项「文件完整性监控」。
→ 即：本题从「要不要花 18 人月重写的决策」，降级为「**一张访问控制规则表 + 一个告警项 + 一个按月复盘流程**」。

## 候选根排序（Share × Lever ÷ Cost，上下级结构）

| 层 | 候选根 | 份额 Share | 可控性 Lever | 证伪代价 Cost | 排序 |
|---|---|---|---|---|---|
| 类根 | 暴露面收敛缺失（无中介直达 PHP 进程） | **唯一**（必要条件） | 改配置 | 一次配置变更 | **1 · 先做** |
| 类根 | 补丁供给无上游（5.6 已 EOL） | 主因（决定时间窗长度） | 换环境 / 加虚拟补丁 | 人日级（虚拟补丁） | 2 |
| 类根 | 无检测响应（发现延迟 ≈ 30 天） | 共因（决定复发周期） | 改架构（加监控） | 人日级 | 3 |
| 个例根 | 上次清除不彻底 / 凭据未轮换 | 主因（若是，则完美解释「换地方」） | 改流程 | 一次取证 | **0 · 先判 D1** |
| 个例根 | 本次那个入口的代码缺陷 | 次要（补了也只堵一点） | 改代码 | 一次改代码 | 4 |
| 放大器 | 「PHP 5.6 太老」本身 | 共因，**不是根** | 换环境 | 人月级 | 5（挂起） |

**为什么「PHP 版本老」被降为放大器而不是根**：即便升到受支持的 8.x，只要「代码直连公网 + 无检测」仍成立，被打仍会发生，只是单洞利用窗口变短、成本变高。按必要条件分层，它提高的是攻击成本，不是把类问题的必要条件掐掉。**排序里 Cost 就是预算**：预算只有 18 人月的零头时，排序自动把配置级动作顶到第一位。

## 挂起表

| # | 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|---|
| 1 | 硬件 / 网络 / 账号权限为根 | ⊥ 非根 | 症状随攻击变化而非随机器/链路变化；同一入口可稳定复现利用 | 换机换网换账号后仍按月复发 → 回升重判 |
| 2 | 组织流程（无人负责、预算不批）为根 | ⊥ **挂起，非排除** | 当前技术面**尚未收紧**（暴露面未收敛），组织问题无法与结构问题分离测量 | 暴露面收敛 + 虚拟补丁 + 凭据轮换全部执行后仍按月复发 → 根转 `org-process`（树已有该待建节点） |
| 3 | 内部人 / 凭据泄露 | ⊥ 不在本类 | 本类判据是「外部批量利用」；题面无内部迹象 | 收紧暴露面后仍出现只从内网发起的异常登录 → 单独立类 |
| 4 | 勒索 / 竞争性打击 / 纯 DDoS | ⊥ 非根 | 经济学只解释「为什么有对手」，不解释「为什么能进来」 | 若已无可利用入口而对手改用 DDoS / 社工 → 另属非入侵类 |
| 5 | 18 人月全站重写是唯一解 | ⊥ 否 | 消解根只需掐掉一个**配置级**必要条件；重写完全不改变「暴露面无主」这一条 | 若业务要求后台对公网自助开放且无法加网关 → 重写权重上升，但仍先做 WAF + MFA |
| 6 | 「按类补漏洞」作为消解根 | ⊥ **仅缓解** | 漏洞供给无限，补类只降低频率；代码缺陷的自然产生速度不因一次性清理归零 | 若实测 6 个月无新增可利用入口 → 可重估为充分条件 |
| 7 | **树外分支** `security-adversarial` | 登记，未入树 | 树索引「待建节点」无安全节点；六子层无法表达暴露面/补丁供给/检测响应 | 建为 v2 节点（必须补判据列，否则是标签不是分类） |
| 8 | 「后台必须对公网开放」（客户/代理商自助） | 未确认（题面无） | 题面未说明后台的服务对象 | 若确认必须开放 → 消解根退化为「入口层有维护 + 虚拟补丁 + 强制 MFA」组合，成本升到人月级，首边改为 WAF 规则 + MFA |
| 9 | 用户所谓「被打」的具体形态 | 未确认 | 题面只说「被打」，可能是扫描噪声 / 挂马 / 拖库 / 勒索，四者响应优先级不同 | 取证后若仅为扫描噪声 → 层3–层5 症状不成立，坐标需重切 |

## 结论

1. **根源不在「哪个洞」，而在三件事同时成立**：补丁供给无上游（PHP 5.6 安全支持已于 2018-12-31 结束）+ 不可维护的代码直连公网、中间无中介层 + 无检测与清理闭环。三者叠加时，按月被打是这套结构的**稳定态**，不是事故；「补完下个月换个地方」是这个结构的正常输出。
2. **让它不再被打的最小解不是 18 人月重写**，而是掐掉三件里的第一件：**把后台从公网撤到网关/白名单后面**（人日级、可回滚、当天可上线）；再用虚拟补丁把「上游」补回来，用文件完整性监控把发现延迟从「月」压到「小时」。按 Share×Lever÷Cost，这三条排在最前，成本比 18 人月低两个量级。
3. **重写不是必需项，但它换来的东西要说清楚**：只有升级运行时/重构，才能让「代码里还剩多少洞」这件事本身**变得可维护**。这件事应该发生在暴露面收敛**之后**，作为 L4 迁移清单里的一项，而不是被月度事件逼出来的紧急决策。
4. 给老板一句话：**先花一天把门关上，再用一个月把锁换掉，最后再谈要不要换房子。**

## 💡 灵感备注

- **「每月一次」这个周期本身就是证据**：它等于对手的扫描/批量利用周期，也等于守方的发现延迟。守方节奏被对手定义，这是「无检测能力」的**可观测代理指标**——不用看一行代码就能判防守成熟度。
