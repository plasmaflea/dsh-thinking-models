## L0 类别判定

**软件类**（判据：① 同一份二进制在另一台机器上行为可复现 ⇒ 失败来源是环境姿态而非物理介质；② 失败是确定性的、每次双击都一样 ⇒ 不是随机位翻转｜已排除：硬件故障〔无 CRC/温度/负载相关性、另一台机器同一文件夹稳定〕、网络〔全程无网络参与〕、组织流程〔技术失败已确定存在〕）。
**权限类先不排除、留作子分支**（ACL 也能让激活上下文生成失败并返回同一错误码），但主导解释权归软件类。

> 本行不能省：省略大类判定＝把后续全部回溯建在「这肯定是软件问题」这个未声明假设上。

## 解码：那一句话本身就是最硬的证据

命令行那一行是 Win32 **错误码 14001 `ERROR_SXS_CANT_GEN_ACTCTX`** 的文本形式。三个直接推论，全部可推导、不靠猜：

1. **它是 `CreateProcess` 的返回值**，由调用方（cmd/PowerShell）打印，不是 exe 自己打印的。exe 自己打印不了任何东西——它根本没被创建。
2. 失败点在**激活上下文（activation context）生成**阶段，即加载器读清单、解析 `dependentAssembly`、去程序集绑定命名空间里找身份并生成激活上下文——**在 CLR 之前、在 `main` 之前、在任何用户态日志组件能够记录之前**。
3. 因此"任务管理器里没有进程"不是巧合：`NtCreateUserProcess` 阶段就整体失败，**不存在进程**，自然没有 WER 记录、没有 .NET Runtime 事件、没有 Application Error。**「日志全空」不是线索缺失，它就是 14001 的指纹**——WER 没有对象可记。（SxS 自己的记录走 `Microsoft-Windows-SideBySide` ETW 通道，默认关闭，所以"应用程序"日志为空是预期结果，不是异常。）

## L2 逐层回溯（轴：一次双击的必经时序，六格机械生成）

生成源＝**必经时序**（不是列举）：双击到进程存在，这六步一步不可省。每格给出「该格故障的可观测症状」，再看本题观测集落在哪一格。

| 格 | 该格在管什么 | 该格故障的专属症状 | 本题判定 |
|---|---|---|---|
| G1 外壳发起 | explorer/cmd 调 `ShellExecute`/`CreateProcessW` | 外壳自己报错（找不到文件、拒绝访问 5、策略拦截）；exe 未被触碰 | ✗ 错误文本是 14001，不是 2/5/1260 |
| G2 内核创建进程与映射映像 | `NtCreateUserProcess` 分配进程对象、section、PEB、映射 PE | 映像无效 → 0xC000007B /「不是有效的 Win32 应用程序」/ 位数不符 | ✗ 文本不符；PE 在另一台机器上可正常映射 |
| **G3 加载器建立激活上下文** | 读 exe 清单 → 解析 import table 与 `dependentAssembly` → 在程序集绑定命名空间里解析身份 → 生成 activation context | **`CreateProcess` 返回 FALSE，`GetLastError()=14001`（14001 = ERROR_SXS_CANT_GEN_ACTCTX）；进程从未被创建；Application 日志无 .NET Runtime／无 Application Error；`SideBySide` ETW 通道有记录（默认关闭）** | ✓ **唯一吻合** |
| G4 依赖模块初始化 | ntdll→kernel32→`mscoree.dll`→CLR 初始化 | 0xC0000142（DllMain 失败）/ 0xC0000135（缺 DLL）/ 0xC0000139（导出缺失）/ .NET Runtime 事件 1025/1026 | ✗ 全空且无进程 |
| G5 进入托管 main | 业务代码、窗口创建、App.config、注册表 | 有窗口，或有 Application Error（.NET Runtime 1000/1026，含堆栈） | ✗ 无窗口、无堆栈 |
| G6 失败上报 | WER、事件日志、退出码回传父进程 | 只改变"看见什么"，不产生故障本身 | — 本题观测正是"它没有产出任何东西" |

**"所有格都空而问题仍在"没有发生**：G3 一格就把全部观测吃掉了。全空列判据不触发，坐标系不需要换轴。

### G3 内部的搜索空间收缩（关键一步）

失败身份来自哪份清单？一个 .NET exe 的**静态导入**基本只有 `mscoree.dll`（`_CorExeMain` 宿主），而 `mscoree.dll` 不带 SxS 依赖。所以：

> **在"这是 .NET exe"的前提下，能提供 `dependentAssembly` 的清单只有 exe 自己（内嵌资源或同目录 `app.exe.manifest`）。** 搜索空间被压到"读这一份清单、看它声明了哪个身份"。

（条件分支：若该 exe 实为混合模式 C++/CLI，静态导入里可能还有 VC 运行库，则失败身份也可能来自那份 DLL 的清单。此支不影响类根，登记进挂起表。）

### 证据链逐条消费

| 观测 | 它排除了什么 | 它指向什么 |
|---|---|---|
| exe 三个月没改、编译机没换 | 构建侧漂移（新加清单、新依赖 redist、Debug 版误发） | 变更发生在**那台机器**上，不是产物上 |
| 同一文件夹拷到另一台机器昨天还能跑 | 产物损坏、拷贝不全、清单语法错误、应用目录内私有程序集缺失（私有探测先于 WinSxS，随目录走，两台机器等价） | 差异在**机器全局状态**，且**声明的身份本身是可满足的** |
| 报错但无窗口、无进程 | 程序内任何代码路径（含 .NET 启动配置、App.config、权限、端口） | 失败在 CLR 之前，在 `main` 之前，在 `CreateProcess` 内部 |
| Application／System 日志全空 | 用户态崩溃、CLR 异常、服务控制管理器事件 | 进程从未存在；WER 无对象可记 |
| 「前两天开始」 | — | 事故窗口内那台机器上有变更（Windows Update / 装了或卸了带运行库的软件 / 清理工具 / EDRA 策略下发）——这是**取样窗口**，不是原因 |

### 类根（面对整个大类）

> **可执行文件的"可启动性"被一个机器全局、第三方可改写的程序集绑定命名空间（WinSxS ＋ publisher policy ＋ SxS 策略）所裁决；而应用只"声明"依赖、不"携带"依赖，于是依赖解析权被加载器代持。**

这条结构一旦成立，下面这个症状包就是它的必然签名——**二进制在源码、版本库、编译机、exe 字节里都看不到这个依赖**；它只在运行那台机器的全局命名空间里存在；它被别的软件单方面改动；改动之后失败发生在应用能打任何日志之前，错误只回传给**调用者**而不是写进任何日志。这就是"没窗口、没报错弹窗、没进程、没日志、只有一行从命令行漏出来的加载器文案"的同源解释。

```
类根：依赖解析权由加载器 + 机器全局程序集绑定命名空间代持（声明而非携带）
  └ 个例根：在那台机器上，exe 自身清单声明的那个 assembly identity 不可解析
```

### 个例根（本次具体机制，三选一，同一层不并列成答案）

身份"不可解析"只有三种形态，注意**它们不是三个平行的猜想，是同一个节点的三个子项**：

| 子项 | 机制 | 时间窗吻合度 |
|---|---|---|
| C1 身份缺失 | 共享运行库被卸载/清理（卸载 redist、清理工具删"旧版运行库"、某安装器的反安装脚本移除共享运行库） | 高（"前两天"） |
| C2 身份在但解析失败 | 较新 redist／Windows Update 覆盖后，publisher policy 指向一个已不存在的版本，policy 链断裂 → 文件还在，激活上下文仍生成失败 | 高（"前两天"、Windows Update 时间点） |
| C3 身份在但清单不可读/损坏 | WinSxS 存储损坏或更新半应用（CBS 事务未完成）；或 ACL／受控文件夹访问／EDR 拦住了清单或程序集目录的读取 → 读取失败同样返回 14001 | 中（新装安全软件、更新中断） |

**这三种机制给出的错误文本、进程缺失、日志全空完全一致，只用题面信息无法再切分。** 硬要再切就必须做一次取证——这正是预算问题，见下面的排序与处置根。诚实的答案是：**类根已定死，个例根落在 C1/C2/C3 上，用一条零风险命令收敛**，而不是在三个里挑一个讲成事实。

## L3 双根

### 处置根（修本次）

按 `Share × Lever ÷ Cost` 排序执行，前两步都不改任何东西：

1. **读出身份**（零风险，分钟级）：`sxstrace Trace -logfile:sxs.etl` → 复现 → `sxstrace Parse -logfile:sxs.etl -outfile:sxs.txt`；或开启 `事件查看器 → 应用程序和服务日志 → Microsoft → Windows → SideBySide`。日志会直接写出**缺的是哪个 assembly identity、要哪个版本、哪个架构、从哪份清单来的**。这是把 C1/C2/C3 三者分开的唯一判据，先做它，别先重装。
2. **按 trace 结论对号入座**：C1 → 装回被声明的那一个特定版本运行库（不是"装最新"）；C2 → 重装同一版本 redist 让它把 publisher policy 一并写回（或按 trace 修 policy 链）；C3 的 ACL 支 → 把该目录从受控文件夹访问/EDR 拦截里放行；C3 的存储支 → `DISM /Online /Cleanup-Image /RestoreHealth` ＋ `sfc /scannow`。
3. **兜底（不依赖全局状态，立即恢复）**：把该 assembly 作为**私有 side-by-side 程序集**放到 exe 同目录（`<exe 目录>\<AssemblyName>\<AssemblyName>.manifest` ＋ DLL）；私有探测先于 WinSxS，同 identity 时私有胜出，一步就能让程序跑起来，且不用管理员去全局装东西。
4. **不必做**：重装 .NET Framework、重装本程序、重新编译、换机器——按上面的证据链，这些都在错误格之外。

### 消解根（灭这一类）

> **把「声明依赖」改成「携带依赖」：交付形态改为自包含，使 exe 的启动不再经过机器全局程序集绑定命名空间。**

- **不可发生判据**：私有程序集在**应用目录内**解析且先于 WinSxS；第三方卸载/升级全局运行库、publisher policy 被改写、CBS 半应用，都不在解析路径上。于是"启动被全局程序集状态打断"**在结构上不可能发生**，不是"变少见"。清单里若还留着对全局 assembly 的 `<dependency>`（典型如只想要视觉样式的 `Microsoft.Windows.Common-Controls`），就把该依赖删掉或改为可选。
- **可执行首边**：`mt.exe -inputresource:app.exe;#1 -out:app.manifest`（或直接打开同目录的 `app.exe.manifest`）——**第一步只是把清单导出来看一眼**，零风险、5 分钟，就能确认到底声明了哪几个身份。确认之后的第一条改造边：把对应 assembly 目录随包发布并从清单里删掉该依赖；.NET 侧改自包含/单文件发布；native 依赖能静态链接就静态链接 CRT。
- **成本量级**：**一次构建管线改动，半天到两天量级**（取决于是否需要重编 native 依赖），运行期零成本、零性能损失；代价是包体变大与发布粒度变粗。三道闸门全过 ⇒ 消解根成立，不降级为挂起。
- **覆盖边界（必须写清）**：C3 的 ACL/EDR 支不在本消解根覆盖内——那是权限类，属另一个类根，已挂起。

## L4 迁移出口

消解根指向交付形态变更，按技能要求列出后续问题清单，并声明本次问题降级为其中一项：

1. **构建产物完整性**：私有程序集成为构建产物的一部分 → CI 必须校验私有目录/清单完整（缺一个文件就复现同一类故障，只是原因从"机器被改"变成"包被打漏"）。
2. **分发与签名**：包体变大、更新粒度变粗；私有 DLL 也要进签名与哈希清单。
3. **安装与权限**：装到 `Program Files` 下时，私有程序集目录需要正确的 ACL，否则"携带依赖"会被"读不到依赖"替代。
4. **可观测性**：清单不再依赖全局命名空间，但"启动失败无任何日志"这一类**没有一起消失** → 需另外固化 SxS ETW 通道与启动面包屑（这是另一类的消解，不在本条）。
5. **组织能力**：谁负责运行库升级？职责从"用户机器上装 redist"变成"重新出包/发版"，发布流程与回滚责任要跟着改。

**本次问题降级为上面第 1 项（构建产物完整性）下的一个具体 case。**

## 候选根排序（预算＝证伪代价）

| 层级 | 候选根 | Share 份额 | Lever 可控性 | Cost 证伪代价 | 排序 |
|---|---|---|---|---|---|
| 类根 | 依赖解析由机器全局命名空间代持 | 唯一（同时解释：无进程／无窗口／无日志／二进制不变／跨机不同 全部 5 条） | 改架构 | 半天改包 | ①（唯一能解释全套现象） |
| 个例根 C1 | 共享运行库被卸载/清理 → 身份缺失 | 主因 | 改配置（装回） | 一次 trace ＋ 一次重装 | ② |
| 个例根 C2 | 被新 redist/更新覆盖，policy 链断 | 主因 | 改配置（重装同版本） | 一次 trace ＋ 一次重装 | ③ |
| 个例根 C3-ACL | ACL/EDR 拦住清单读取 | 次要 | 改配置（放行） | 一次 trace（trace 会写出"访问被拒"） | ④ |
| 个例根 C3-store | WinSxS 损坏／更新半应用 | 次要 | 改环境（DISM/sfc） | 一次 DISM（30 分钟） | ⑤ |

排序的预算约束：①②③④共享同一次 trace（一次采样即同时证伪三条），所以真实账是**一次零风险采样**，而不是五次重装。这就是为什么处置根第 1 步是取证而不是动手。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 应用目录内的私有 side-by-side 程序集缺失 | ⊥ 不是根 | 私有探测相对 exe 目录、随目录走；整目录拷到另一台机器可正常运行 ⇒ 目录内容完整且有效 | 若另一台机器其实是**从别处启动**或私有目录没被一起拷贝，此判定推翻 |
| 清单语法错误／身份版本写错 | ⊥ 不是根 | 同一份清单在另一台机器上解析成功 | 若两台机器上的清单并非同一份（外部 `.manifest` 未随包拷贝） |
| 缺 .NET Framework／运行库版本不对 | ⊥ 不是根 | 那会是 CLR 加载失败，报"unable to find a version of the runtime"并写 .NET Runtime 事件；本题无进程、无事件，且失败点更早 | 若命令行那句话其实来自 exe 之后弹的对话框（需确认文案来源是 shell 的 CreateProcess 报错） |
| 「装个 VC++ 运行库就完事」式的盲目归因 | ⊥ 不成立（作为结论） | 缺 DLL 是 0xC0000135、导出过旧是 0xC0000139、DllMain 失败是 0xC0000142，都不是 14001；14001 只说明"激活上下文生成失败"，可能是缺、可能是 policy 断链、可能是清单读不到。**装最新版 redist 甚至可能让 C2 更糟**（又写进一套新 policy） | 若 sxstrace 明确写出缺失的正是某个运行库身份，则"装回**该特定版本**"才成立（注意是钉版本，不是装最新） |
| 文件被 SmartScreen／Mark-of-the-Web／杀软拦 | ⊥ 不是根 | 那些给出的是"已被系统管理员阻止"/0xC0000428/"无法验证发布者"，或干脆静默删除文件且提示形态不同；本题给的是 SxS 专属错误码，且另一台机器同一文件夹可运行 | 若命令行文案实际是策略拦截提示、或 exe 在那台机器上已被删除（需 `Get-Item` 核对文件仍在） |
| 权限/账号体系（UAC、组策略、AppLocker/WDAC 的一般拦截） | ⊥ 不是根（**但 ACL 子支保留为 C3**） | 一般权限拒绝是错误码 5；AppLocker/WDAC 拦截是 0xC0000428 或"已被策略阻止" | 若 trace 显示清单/程序集读取被拒绝，则 ACL 子支由"次要"升为该机实际根 |
| 位数不符／WOW64 重定向导致身份在某视图不可见 | ⊥ 挂起（同症状的第二机制） | 位数不符通常是 0xC000007B；但 WOW64 下 32 位进程只看 32 位视图，理论上可造出"身份不可见"，且换机器可解 | trace 若写出身份存在但架构不匹配，则升为个例根 |
| 「调 SharedSection 窗口堆配额」 | ⊥ 不是根（流行误归因） | 那是服务态 Session 0 桌面堆的 0xC0000142 主因，本题交互式桌面、且未到 DllMain | 若最终发现进程确实起来过（有进程 evidence），此条重新评估 |
| 树外分支：exe 清单依赖的是**公司自研**的自定义 side-by-side 程序集（由安装器注册进 WinSxS） | ⊥ 挂起（树里无此节点） | 软件树 v1 缺「程序集绑定命名空间」支；该机制与全部观测相容，且会让"覆写/清理"这类动作直接命中 | 若 `mt.exe` 导出的清单里出现的不是微软运行库身份而是自有 assembly 名，此支升为个例根；同时登记 `v2 候选`：`software / sxs-binding` 节点（判据：错误码 ∈ {14001,14002,14003}；典型根：清单声明的全局身份不可解析；典型症状：无进程＋日志全空＋调用方收到 14001） |
| 树外分支：混合模式 C++/CLI，失败身份来自被静态导入 DLL 的清单 | ⊥ 挂起 | 题面称".NET 编译的单个 exe"，默认静态导入仅 mscoree.dll | 若 `dumpbin /imports` 显示还有 VC 运行库导入，则搜索空间从"只看 exe 清单"扩到"看各 DLL 清单" |

## 结论

**根源不在那个 exe，而在它的依赖形态：它只"声明"依赖、不"携带"依赖，于是能不能启动由那台机器的全局程序集绑定命名空间（WinSxS ＋ publisher policy ＋ SxS 策略）单方面裁决，而这个命名空间是任何安装器、卸载脚本、Windows Update、清理工具都能改写的共享可变状态。**

本次的具体扳机是：那台机器在这两天里被改动了，导致 exe 自身清单里声明的那个 assembly identity 不再可解析。**程序集身份缺失（C1）、policy 链断裂（C2）、清单/程序集读不到或存储损坏（C3）三者给出的错误文本、进程缺失与日志全空完全一致，题面信息到此为止不能再切分**——一次 `sxstrace` 就能把三者分开，重装 .NET Framework／重装本程序／重新编译都在错误格里，不必做。

三句话版：失败发生在 `CreateProcess` 内部、CLR 之前，`14001` 就是"激活上下文生成失败"；进程从未被创建，所以"没有进程、没有日志"是必然而非异常；产物没变、机器变了——变的是那台机器上全局程序集命名空间里被声明的那个身份。**观测上的"什么都没有"，本身就是答案的一部分。**

## ⚠️ 异常／矛盾／空白

1. ⚠️ **题面自带的观测缺口**：`GetLastError()` 的实际数值未给出，我是从错误文本反推 14001。文本与 14001 的系统默认文案逐字对应（"The application has failed to start because its side-by-side configuration is incorrect."），这一反推可靠；但若实际是 14002/14003（同样关于 side-by-side，语义不同），个例根排序需微调。建议：下次遇到同类现场直接记 `$LASTEXITCODE`／`GetLastError` 数值，而不是只抄文案。
2. ⚠️ **"事件查看器什么都没有"是本题最容易被当成"无迹可查"的误读点**：SxS 的默认记录在 `应用程序和服务日志 → Microsoft → Windows → SideBySide`，**不在**"应用程序"日志。取证时如果只翻"应用程序"日志就会得出"机器上什么都没发生"的错误结论。
3. ⚠️ **"同一文件夹拷过去能跑"这条控制实验的效力依赖一个未声明前提**：拷贝是全目录、且两台机器的清单是同一份。若当年只拷了 exe（外部 `.manifest` 留在原目录），这条就同时否掉了它本该排除的东西——这是本题唯一可能让整个回溯偏移的隐含假设。
4. 空白：`知识树` 缺「程序集绑定命名空间」节点（本次以树外分支处理，已登记 `v2 候选`）；按题目第 3 条约束未读工作区 `knowledge-tree/index.md`（是否存在未知），L1 只能实例化技能自带的 `software` v1。

## 💡 灵感备注

「无进程、无日志、二进制不变、跨机不同」这个四元组，是一类**加载器代持型失败**的通用指纹（SxS 14001、DLL 重定向、AppLocker 哈希策略、EDR 注入时机）。它的判据价值在于：只要这四条同时成立，就可以立刻把调查焦点从"程序做了什么"整体移到"在程序诞生之前是谁拦了它"，省掉整个业务代码方向的排查。这四元组值得作为独立节点进树，而不是每次靠经验临场拼。
