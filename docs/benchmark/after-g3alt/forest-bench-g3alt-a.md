# 根源回溯：双击无反应 + `side-by-side configuration is incorrect`

[🌳 林状图] 选择理由：题面是「根源在哪」的追根因题，且已给出成组观测（无进程／无弹窗／事件日志全空／换机可跑），未知在**因果深度**，不在选项广度，故用林状分层分类回溯法，不用穷举法铺选项。

---

## L0 类别判定

**类别**：`software` —— Windows **进程创建阶段的加载器失败**（PE 加载 + SxS 激活上下文解析），不是「应用程序运行期异常」类。
**判据**：①同目录拷到另一台机器可复现"正常"，失败只与本机环境姿态绑定（software 判据 1 成立）；②失败 100% 确定性、无随机成分（判据 2 成立）；③故障发生在任何应用代码执行之前（无进程遗留、无托管事件）。
**已排除的大类**：`hardware`（无校验错误、无随机性、无温度/负载相关）｜`network`（与链路无关）｜`权限/账号体系`（错误码族不对，见挂起表）｜`组织流程`（技术层尚未收敛，不能甩给人）。
**本次判为不适用的树节点**：`software/win-service` 的**判据**不满足（该节点要求进程由 SCM 创建、跑在 Session 0 非交互桌面；本题是双击/命令行启动的交互式桌面 exe），但其**格 3（SxS 激活上下文）与状态码族可直接复用**——故按"部分实例化"使用，另登记 v2 候选节点（见挂起表）。

## L2 逐层回溯

**轴 = 必经时序**（生成源：一次 `CreateProcess` 到出窗口的必经步骤，一步一格，机械生成，非联想列举）。三判据：正交（各格症状不互相解释）｜可生成（每一步都是"不起它进程就到不了下一步"）｜可观测（每格有专属症状）。

| 格 | 该格管什么 | 若此格故障 → 专属症状 | 本题判定 |
|---|---|---|---|
| **1** 调用方发起 `CreateProcess`（外壳双击 / cmd / 快捷方式：参数、工作目录、**错误如何呈现**） | 谁创建进程、失败信息以何种形态暴露 | 进程从不出现，但**错误呈现可以静默**（双击经 Explorer，硬错误被吞；cmd 有控制台承接文本） | **非根**：只能解释"为什么双击看不到报错"，解释不了错误本身 |
| **2** 内核创建进程对象 + 映像映射（PE 格式、位数、签名/AppLocker 策略） | 映像本身能不能被接受 | `0xC000007B`／`0xC0000428`／"不是有效的 Win32 应用程序"／被策略拦截 | **非根**：错误文本不是码族里的任何一条 |
| **3** **加载器构建激活上下文：解析 exe 清单里的 `<dependentAssembly>`（SxS）** | 清单声明的程序集能否在 machine store 解析到 | **硬错误文本 `side-by-side configuration is incorrect`（= ERROR_SXS_CANT_GEN_ACTCTX / 14001）、`CreateProcess` 直接返回 FALSE、进程对象即刻消失、无 WER 1000、无 .NET Runtime 事件、`sxstrace` 可抓到缺失的 assemblyIdentity** | **✅ 命中格** |
| **4** 静态导入解析 + 各 DLL 的 `DllMain` | DLL 能否全部初始化成功 | `0xC0000135`（缺 DLL）／`0xC0000139`（导出缺失）／`0xC0000142`（DllMain 返回 FALSE） | 非根：SxS 失败在格 3，**根本到不了 DllMain** |
| **5** CLR 初始化（挂 .NET Framework、构造 `AppDomain`） | 托管运行时能不能起来 | Application 日志出现 **`.NET Runtime` 源（Event 1026/1022）** 或 "requires .NET Framework" 提示 | 非根：事件日志里**没有 .NET Runtime 条目**，正是"没走到这一格"的证据 |
| **6** 托管入口 → 建窗 → 消息循环 | 窗口为何不可见 | 进程存在但无窗（句柄/桌面/`ShowWindow` 问题）或进程崩溃 | 非根：**任务管理器里连进程都没有** |

**格 3 的落点不是"exe 坏了"，而是"exe ⊕ 机器的联合解析失败"**：

```
→ 类根：桌面 exe 的"依赖解析"控制权被 Windows 加载器（PE loader + SxS machine store）
        代持，而不是由应用自己掌握。
        推论（这一类在什么结构条件下必然可能发生）：
        ①"能跑"从来不是 exe 的属性，而是「exe 内嵌清单声明」×「本机 SxS 仓库/策略/注册表」的联合函数；
        ②任一机器侧因子被改，同一份 exe 就从"能跑"变"不能跑"，且失败必然发生在应用能写日志之前
          → 于是表现为"无窗口、无进程、无堆栈、无事件"；
        ③编译机没换过 ⇒ 验证样本量恒为 1 ⇒ 该类问题对"换机/系统更新/装卸软件"完全没有免疫力。
     └ 个例根：这台机器在近两天内，被清单引用的那个 SxS 程序集（或它的版本策略）在机器侧
        消失/被改版本，加载器在激活上下文阶段就退出。
        高概率具象（按概率降序，均需 sxstrace 定案，不许猜着装）：
        A. 清单依赖的 VC 运行库（`Microsoft.VC80.CRT` / `Microsoft.VC90.CRT` 一类）
           被别的安装/卸载程序带走或被换了版本 → 引用解析为空；
        B. 清单依赖 `Microsoft.Windows.Common-Controls` 6.0（WinForms 默认清单几乎必带）
           的 WinSxS 条目/注册项损坏或被"精简版系统/清理工具"删掉；
        C. `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\SideBySide\Winners`
           或 `C:\Windows\WinSxS\Manifests` 被"深度清理/优化"动过。
        判别性推理：若是 C（整库损坏），故障面会远超本程序（资源管理器/系统组件/其他
        带清单的软件会一起异常），题面没有这些现象 ⇒ **更可能是 A/B 这种"单点程序集被卸/被换"**。
```

**为什么另外三条观测都不构成反证**：

- "没进程" = 格 3 的**必然**结果（14001 在 `CreateProcess` 层返回，进程未成型）。
- "Application 日志全空" = 格 3/5 的**结构性必然**（WER 的 1000 事件需要进程真的崩；CLR 事件需要 CLR 起来；SxS 失败两者都不发生），是坐标，不是死胡同。
- "换台机器昨天还能跑" = 类根的直接推论（被换掉的是机器侧的契约，被拷走的是 exe）。**注意它同时是个陷阱**：那台机器也只是"还没被改"，明天同样会坏。

## L3 双根

**处置根（修本次）**：先定案再动手 —— 用 `sxstrace` 把"缺的是哪个程序集"变成一行事实，再按事实补回。

1. `sxstrace.exe Trace -logfile:C:\temp\sxs.etl` → 双击/命令行启动该 exe → `sxstrace.exe Parse -logfile:C:\temp\sxs.etl -outfile:C:\temp\sxs.txt`
2. 读 `sxs.txt` 的 `ERROR` 行：它直接打印解析失败的 `assemblyIdentity`（name / version / publicKeyToken / processorArchitecture）——这就是个例根的**判决书**。
3. 交叉核对：`wevtutil qe Application /q:"*[System[Provider[@Name='SideBySide']]]" /c:20 /rd:true /f:text`（确认是"没记录"还是"只看了 .NET Runtime/Application Error 两个源"）；再看 `C:\Windows\WinSxS\Manifests` 与 Winners 注册表里对应条目是否还在。
4. 按判决书补回：VC 系 → 装回对应版本 redist（**先卸新装旧，别同装两版**）；Common-Controls/系统组件系 → `DISM /Online /Cleanup-Image /RestoreHealth` + `sfc /scannow`，再不行从同版本健康机对照条目。
5. 顺手验证题面前提：比对两台机器上该 exe 的哈希 + `mt.exe -inputresource:app.exe;#1 -out:app.manifest` 导出内嵌清单，确认"exe 三个月没改"为真（前提本身也要被证据背书）。

**消解根（灭这一类）**：**把这条 exe 的清单依赖从"机器级 SxS 契约"上摘下来，改成不依赖激活上下文解析的形态**（app-local 私有程序集 / 静态链接 CRT / 视觉样式改用 `Application.EnableVisualStyles()` 运行时启用 / self-contained 发布）。

- **不可发生判据**：清单里没有 `<dependentAssembly>` 声明 ⇒ 激活上下文为空 ⇒ 加载器无可解析之物 ⇒ 14001 这一类**在结构上不可能发生**（不是变少见，是入口消失）。
- **可执行首边**（很小）：删掉/清空 `app.manifest` 里的 `<dependency>/<dependentAssembly>` 节点（WinForms 保留 `EnableVisualStyles` 调用即可；原生依赖改 `Copy Local` 随包分发），重编译，在一台"没装过任何 VC 运行库"的干净机上双击验证。
- **成本量级**：一次编译 + 一轮"干净机冒烟"（分钟～小时级；若转 self-contained 分发，体积 +几十 MB、构建时间 +分钟级）。

## L4 迁移出口

摘掉 SxS 依赖后，新问题清单（本次问题降级为其中一项）：

1. **安全更新责任转移**：app-local 携带的运行时不再随 Windows 更新，须自己跟 CVE 与版本节奏。
2. **分发一致性**：不能再"只拷一个 exe"，每台机器必须整目录/整包拷贝并校验（这正是题面"同文件夹拷走"这个动作暴露的隐患）。
3. **可观测性**：加载期失败从此有明确日志（应用自己打的），但要新增"启动面包屑"落点。
4. **视觉/DPI 退化**：去掉清单里的 Common-Controls 与 dpiAware 声明后，视觉样式与高 DPI 表现可能回退，需要重新以私有方式声明。
5. **测试矩阵**：必须覆盖"无 VC 运行库 / 无对应 WinSxS 条目 / 不同 Windows 版本"三类干净机。
6. → **本次问题降级为第 2 项（分发一致性）+ 第 5 项（测试矩阵）的一项**。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件（什么证据会推翻本行） |
|---|---|---|---|
| 应用代码 bug / 业务逻辑 | 排除 | 运行期异常必有进程、必有堆栈，且会留 `.NET Runtime`/WER 事件；本次两者皆无 | 若 `sxstrace` 显示无激活失败、而进程曾起来过 |
| 缺 .NET Framework / CLR 绑定失败 | 排除 | 缺框架报的是另一条消息（"requires .NET Framework"）；SxS 与 CLR 绑定是两条独立链路；Application 日志无 CLR 事件 | 若 `sxstrace` 的 ERROR 行指向 `.NET` 相关 `assemblyIdentity` |
| 权限 / ACL / UAC | 排除 | 错误码族不对（权限是 5/1260，ACL 是拒绝访问），且不会给出 SxS 文本 | 若 `CreateProcess` 返回 5/1260 且 `sxstrace` 无失败 |
| 杀软 / AppLocker / WDAC / SRP 拦截 | 挂起 | 拦截典型结果是 `0xC0000428` 或静默拦截+策略事件，与 14001 不同族 | 若错误码实为 `0xC0000428`，或安全软件日志有拦截记录 |
| exe 文件损坏 / 被误改 | 挂起 | 另一台机器用同目录同文件能跑 ⇒ 文件不是变量；但"没改过"三字尚无哈希背书 | 若两台机器 exe 哈希不一致，或内嵌清单被外部 `.manifest` 覆盖 |
| 目录里多了外部 `foo.exe.manifest` 或同名 `.local` 目录 | 挂起 | 整目录拷到另一台机器能跑 ⇒ 目录内容在两机是同一集合，不构成差异变量 | 若两机目录内容清单不一致，或 `mt.exe` 导出显示用了外部清单 |
| 机器级 WinSxS 整体损坏（C） | 挂起（低概率） | 全库损坏会连带系统组件/其他带清单软件异常，题面未报 | 若 `sfc/DISM` 报 `CORRUPT` 或他应用同时报同一错误 |
| 编译机 / 工具链 / SDK 更新 | 挂起 | 题面明示编译机未换；且此类变化无法解释"本机两天内变坏" | 若发现最近一次构建产物与三个月前的构建不一致 |
| 父进程激活上下文继承（无清单进程继承调用方） | 挂起 | 双击（Explorer）与命令行（cmd）两条**不同的父进程**都失败 ⇒ 与调用方无关，指向机器侧 | 若换一个明确带清单的宿主进程启动它即可成功 |
| **树外分支**：SxS 事件记录被关（Application 日志"全空"） | 挂起 | 若 SxS 确实解析失败，正常应有 `source=SideBySide`（33/59/80）；"什么都没有"与机制矛盾 | 若 `wevtutil` 按 SideBySide 源查询能查到事件 ⇒ 本行作废，转为"用户只看了两个源" |
| **树外分支**：操作系统版本/补丁级在两机不同 | 挂起 | "昨天还能跑"指向**时间点变化**而非机器固有差异 | 若两台机器 Windows 版本/补丁级不同且回滚补丁后恢复正常 |

## 结论

1. **根源是一句"加载器在激活上下文阶段就失败"**——`side-by-side configuration is incorrect`（ERROR_SXS_CANT_GEN_ACTCTX / 14001）是 `CreateProcess` 阶段的错误，`DllMain`、CLR、`main()` 全都还没开始，所以「无窗口、无进程、无 .NET Runtime 事件、无 Application Error」不是没线索，而是这条故障的**专属指纹**。
2. **类根**：桌面 exe 的依赖解析权被 Windows 的 SxS machine store 代持 —— "能跑"是 exe 清单 ⊕ 本机契约的联合函数，不是 exe 的属性；只在编译机上验证（样本量 1）就必然吃这一击。
3. **个例根**：这台机器近两天把清单所引用的那个程序集在机器侧弄丢了（最可能：VC 运行库被别的装卸程序带走/换版，或 Common-Controls 6.0 的 WinSxS/注册条目被"精简/清理"动过）。**别靠猜着装运行库**，用 `sxstrace` 一行定案再补。
4. **消解**：把清单依赖摘掉（app-local / 静态 CRT / 运行时启用视觉样式 / self-contained），让 14001 在结构上无处发生；代价是把"分发一致性"和"测试矩阵"变成自己的常设工作。

[✅ 验证] 本题为纯推理题（题面第 3 条禁止读文件、禁止复现），故无本机实测。可复核的硬锚点仅两处文本级事实：错误串是加载器对 14001 的本地化文案；该码族属于 `CreateProcess` 失败而非进程崩溃——这两条决定"事件日志为空"是结构必然。L1 的树版本与核查日期取自技能自带树文件（software.md / win-service.md，均 v1，核查 2026-10-18）；工作区知识树按题面要求**未读取**，用前须复核。

[⚠️ 异常/矛盾/空白]
1. ⚠️ **Application 日志"什么都没有"与机制矛盾**：SxS 解析失败正常会写 `source=SideBySide`（Event 33/59/80）。要么只查了 `.NET Runtime`/`Application Error` 两个源，要么 SxS 事件记录被关。**这不是可忽略项**——它决定 `sxstrace` 是不是唯一可靠证据源。建议：先按 SideBySide 源精确查询一次。
2. ⚠️ **双击不弹窗 vs 命令行有文本**的不对称：说明错误呈现路径不同（外壳吞掉硬错误），是**观测缺陷**，不是两套故障。把它当"两个问题"会分叉诊断。
3. ⚠️ **"另一台机器昨天还能跑"极易被误读为"exe 是好的所以不是依赖问题"**：恰恰相反，它证明的是"依赖契约是机器级的"。该机器同样暴露在同类风险下，不可作为长期验证环境。
