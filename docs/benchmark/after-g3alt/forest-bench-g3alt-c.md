# SxS 启动失败：根源判定

[🌳 林状图／回溯法] [选择理由：提问落在「根源在哪」——未知在**因果深度**而非选项广度或数量关系；且题面给的是"零改动 + 跨机器差异"的确定性故障，正适合用必经时序轴把"哪一步死的"切出来，再沿恒等式上溯到类根。]

---

## L0 类别判定

**类别**：`software`（软件/运行时姿态类）。
**判据**：(1) 失败按机器姿态确定性复现、不随物理介质或随机性变化；(2) 同一份程序在另一台机器上可正常运行 ⇒ 可复现性来自环境姿态而非位翻转。
**已排除的大类**（按 `software` 节点排除表逐条走）：

| 被排除大类 | 判据命中情况 |
|---|---|
| 硬件故障 | 无随机性、无校验错误、跨机器差异由姿态而非介质解释 ⇒ 排除 |
| 网络问题 | 双击即死，未进入任何网络调用；无超时/重置形态 ⇒ 排除 |
| 权限/账号体系 | 报错文案不是"拒绝访问"族（0xC0000022），且换交互式登录未改变 ⇒ 排除 |
| 组织与流程 | 技术层已有明确的加载器文案 ⇒ 不属此支 |

**L1 子层定位**（`software` 六正交子层中本次命中的）：`lifecycle`（进程创建权由 OS 加载器代持）+ `dependency`（Win32 side-by-side 程序集解析）+ `init`（失败点在 main 之前）。`quota`／`concurrency`／`config` 见挂起表第 9–11 行。

## L2 逐层回溯

### 层1 轴：一次"双击启动"的必经时序（生成源＝必经过程，一步一格）

| 格 | 该格在管什么 | 本格失败能否产生题面四个现象 | 该格故障的专属症状 |
|---|---|---|---|
| 1 前端发起（Explorer ShellExecute / cmd CreateProcess） | 由谁来创建进程 | ✗ 不能（本格失败连文案都没有） | 无进程创建；ShellExecuteEx 返回失败码，Explorer 无提示 |
| 2 内核创建进程 + 映射映像 | 拿到进程对象、映像就位 | ✗ 不能（文案来自加载器，本格还没到） | 访问拒绝／映像无效族（0xC0000022 等），WER 无记录 |
| **3 加载器建立激活上下文（解析 exe 清单里的 SxS 依赖）** | manifest 声明的程序集 identity 能否在机器侧解析到 | **✓ 会，且只有本格同时产生全部四个现象** | 加载器文案 "side-by-side configuration is incorrect"；退出码 `0xC0150002`（`STATUS_SXS_CANT_GEN_ACTCTX`）；进程毫秒级被 `TerminateProcess`，任务管理器采样不到；`sxstrace` 报 `ERROR: Cannot resolve` 具体 identity |
| 4 解析静态导入（DLL 加载与 DllMain） | 各 DLL 能否映射并初始化 | 半会（同为静默死，但文案不同） | `0xC0000135` / `0xC0000139` / `0xC000007B` / `0xC0000142`，文案不是 SxS 那句 |
| 5 CLR 启动（mscoree → clr） | .NET 运行时初始化 | ✗ 不能静默到此 | Application 日志出现 `.NET Runtime` 源；`0x8013170x` 族 CLR 专属码 |
| 6 托管 Main 与窗口 | 业务代码 | ✗ 完全不能 | 有窗口／抛异常／`Application Error`＋WER 报告 |

**全空列判据检验**：六格里只有格 3 同时满足题面四个约束（无窗口、无进程残留、无 `.NET Runtime`/`Application Error`/系统日志、只有加载器一句 SxS 文案）⇒ 坐标系有效，**不必也不许再往格 5（.NET）猜**。格 5 之空是判据不是巧合：CLR 根本没被加载，`.NET Framework` 侧不可能留下任何事件。

### 层2 轴：恒等式的右边（生成源＝恒等式，按因子切，因子缺一不可）

> 激活上下文解析结果 ≡ f（**A** 清单声明的 identity 画像，**B** 机器侧实际可解析到的程序集集合与解析缓存，**C** 解析规则／重定向／架构视图）

| 格 | 本次取值 | 判定 |
|---|---|---|
| **A 声明侧**（exe 内嵌/同名 manifest 的 `<dependency>` 要求的 name·version·arch·publicKeyToken·language） | 三个月未改、编译机未换、同一份文件夹在另一台机器可运行 ⇒ **A 在这台机器上是常量且可满足** | A ⊥ 本次根（挂起）。但它是必要的另一半：A 若没声明任何 Win32 程序集，B 怎么烂都不会出 SxS 错 |
| **B 供给侧**（WinSxS 中该精确版本的可用性、同目录私有程序集、`...\SideBySide\Winners` 等解析缓存） | 唯一"前两天"可能变化、且跨机器必然不同的因子 | **★ 本次根所在** |
| **C 规则侧**（`.local` 私有重定向、AppCompat shim 替入的 manifest、x86/x64 架构视图、SxS 策略键） | 可被安全软件／"优化清理"工具／组策略改动；但"拷走就能跑"把其中的 `.local` 一支压到接近零 | 次要／部分挂起 |

**A 与 B 之间那条最硬的判别**（本题的核心证据链，值得单独记下来）：
> 「**同一个文件夹**拷到另一台机器能跑」⇒ 该文件夹自洽：exe、内嵌 manifest、以及任何随目录携带的私有依赖与 `.local` 都是完整且可满足的 ⇒ **故障的全部责任在故障机"文件夹之外"的机器级状态**。
> 这一步同时排掉了"exe 被改坏""拷贝时丢了依赖""清单写错""编译产物问题"——而"exe 三个月没改、编译机没换"是同一结论的第二个独立证词。
> 一句话：**程序没变，世界变了。**

### 层3 上溯到类根 → 个例根挂其下

**类根（这一类在什么结构条件下必然可能发生）**：
> 当程序对 Win32 side-by-side 程序集的引用是**"借来的"**——不由程序自带、而由机器级供给（WinSxS／其他产品捎带的 redistributable）提供时，**"机器侧可用集合 ⊇ 清单要求的精确 identity"就成了它能否启动的必要条件**。而这个必要条件不写在程序里、不受程序控制、也不随程序发布而固定；机器侧任何一次增删（卸载、升级、servicing、清理、还原、策略变更）都能在程序零改动的前提下把它从"能跑"改成"跑不起来"。又因为失败发生在加载器里、在任何应用代码（含 CLR）执行之前，其可观测面被压缩成"没有窗口、没有进程、没有日志、只有加载器一句话"。

**└ 个例根（本次具体机制，按 Share 降序，全部挂在上面的类根之下）**：

- **G1（主因）借来的供给被撤走**：故障机"前两天"某产品被卸载／升级，顺带把它提供给 exe 的那个精确版本的 redist 程序集（最典型：某版本 `Microsoft.VC*.CRT`，其次 `Microsoft.Windows.Common-Controls` 6.0.0.0）从 WinSxS／策略条目里撤掉了。exe 依赖的从来不是"VC++ 运行库"这个类别，而是**某一个精确 version**；借出者走了，声明就悬空。
- **G2（共因）解析状态损坏**：`WinSxS` 清单目录或 `Winners` 解析缓存被 `DISM /StartComponentCleanup` 式清理、第三方"优化"工具、失败的系统更新或系统还原回滚破坏，导致解析指向不存在的版本。
- **G3（次因）C 规则侧被改**：安全软件／AppCompat shim 替入了另一份 manifest，或架构视图错配（x86 exe 在只有 x64 视图的解析路径上找不到对应架构的程序集）。
- **G4（次要）策略拦截**：WDAC/AppLocker 类策略介入——但通常报自己的码（`0xC0000428` 等）且不产生 SxS 文案。
- **G5（已被排除，非根）exe／清单／私有依赖损坏**：被"拷走能跑"直接排除。

## L3 双根

**处置根（修本次）**：在故障机上按"先取证后动手"的顺序做一次定点修复——
1. `sxstrace trace -logfile:sxs.etl` → 复现 → `sxstrace parse -logfile:sxs.etl -outfile:sxs.txt`，从输出里读出**那一个**解析不到的 `assemblyIdentity`（写死版本号），这一步把"猜"换成"证"，5 分钟量级；退一步可用 `cmd /c app.exe & echo %errorlevel%` 确认退出码是不是 `0xC0150002`。
2. 按 identity 分派：缺 `Microsoft.VC*.CRT` → 装回**对应精确版本**的 redist（x86/x64 都要对）；缺 `Microsoft.Windows.Common-Controls` 6.0.0.0 或 `Winners` 键异常 → `sfc /scannow` + `DISM /Online /Cleanup-Image /RestoreHealth` 修机器级供给与缓存，重启复测。
3. 顺手查"前两天"：Setup/MSI 安装卸载记录与 servicing 记录（注意题面只说**系统日志**没新东西，Setup/MSI 日志属未观测区）。

**消解根（灭这一类）**：**把 SxS 依赖从"借来的"改成"自带的"或"不需要的"**——清单里引用的 Win32 程序集以私有程序集形式随程序发布（同目录 DLL + 私有 assembly manifest／`.local`），或消除该引用（.NET 侧改 self-contained 发布／静态链接，或去掉对 Common-Controls v6 的 `<dependency>`）。
- **① 不可发生判据**：若依赖由程序自带或静态链接，则启动所需的程序集集合是**程序自身属性的函数**，与机器上任何 redist 的安装、卸载、servicing、清理、策略变更无关 ⇒ 本题这一类"程序零改动、突然不能启动"在结构上不可能发生（不是变少见，是不成立）。
- **② 可执行首边**：把当前 exe 的 manifest（`mt.exe -inputresource:app.exe;#1` 或同目录 `.manifest`）里 `<dependency>` 逐条列出，逐条判"能否自带"；第一条可落地的边＝把 CRT 私有化或整包改 self-contained 发布，再在干净 VM 上做一次冷启动冒烟。
- **③ 成本量级**：构建改动小时级～1 人日（一次性），CI 冷启动冒烟分钟级/次；对照一次跨部门排查的人日级成本，回本一次即够。量级应交 📐 公式图定量，此处只给量级。

## L4 迁移出口（消解根带来的新问题清单；本次问题降级为其中一项）

1. **包体与完整性**：私有程序集/self-contained 让产物从"单 exe"变成"exe＋若干 DLL"或体积显著变大，签名与哈希校验要随之覆盖新文件（WDAC 策略可能需放行）。
2. **更新责任转移**：安全补丁不再由 Windows servicing 代劳，CRT/运行时 CVE 要自己跟（这是把"别人管"换成"自己管"的代价）。
3. **冷启动可观测性**：需要一台干净 VM 与一条冒烟用例进 CI，否则下一次同类故障仍只能靠 `sxstrace` 事后取证。
4. **分发形态**：若坚持"双击就用"的单文件，需要打包/自解压或单文件发布器，启动时间与首次解压行为要重测。
5. **回退路径的自我约束**：任何"为了省体积回退去借系统 redist"的决定，会原样复现这一类——须写进发布检查单。
→ **本次问题降级为第 2/3 项的子项**："借来的依赖会随世界消失"这一条，在这份清单里只是一个需要管理的版本责任，而不是一次不可解释的线上停机。

## 候选根排序（Share × Lever ÷ Cost）

**预算声明**：本次取证预算＝1 台机器 × 约 2 小时 + 允许一次重启。Cost 就是预算，无预算则排序退化成清单。

| 层级 | 候选根 | Share（能解释已观测现象） | Lever（能不能动） | Cost（排除要花多少） | 排序 |
|---|---|---|---|---|---|
| 类根 | 启动期程序集解析权由 OS 代持、且匹配是精确匹配 | 唯一（唯一能同时解释"零改动＋跨机器差异＋死在加载器＋无日志"） | 改架构 | 一次采样（确认）+ 一次迁移（消除） | 1（骨架，必取） |
| 个例 | **G1 借来的 redist 供给被撤** | 主因 | 改配置（装回）/ 改架构（私有化） | 一次采样（`sxstrace`） | **2（首选验证）** |
| 个例 | G2 WinSxS/Winners 解析状态损坏 | 共因 | 改环境（sfc/DISM） | 一次采样 + 一次重启 | 3 |
| 个例 | G3 C 规则侧被改（shim/架构视图） | 次要 | 改配置 | 一次采样（比对清单与 WinSxS 架构目录） | 4 |
| 个例 | G4 策略拦截 | 次要 | 改配置 | 一次策略导出 | 5 |
| 个例 | G5 exe/清单/私有依赖损坏 | **无**（已被排除） | — | 一次比对（已由"拷走能跑"付清） | 末位 |
| 个例 | 「重装/修复 .NET Framework」 | **无**（CLR 从未加载，文案不是 CLR 的） | — | 小时级且零信息量 | 不入排序 |

## 挂起表（分支｜判定｜依据｜恢复条件）

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| A 声明侧（exe manifest 的 identity 也是变量） | 判非根（挂起） | 三个月未改、编译机未换；拷贝件可运行 | 若发现 exe 内嵌 manifest 与发布包内的不一致，或被 shim 替入过另一份 manifest |
| G5 exe/清单/随目录私有依赖在传输中损坏 | 判非根 | 同一文件夹在另一台机器可运行 ⇒ 目录内容自洽 | 若"另一台能跑"的那份与本机不是逐字节同一份（例如另拷过/另装过别的东西） |
| `.local` 私有程序集被拷走或缺失 | 判非根 | 同上；若原机缺文件，拷出版本亦应缺 | 若本机目录里存在 `.local` 而拷贝时被排除（拷贝工具过滤了隐藏/特定扩展名） |
| 位数/架构视图错配 | **挂起（未排除）** | 需看 exe 的 PE 架构与 manifest 的 `processorArchitecture`，并与 WinSxS 的 x86/x64 视图比对；跨机器差异可能由"另一台恰好同架构补丁态"解释 | 若 `dumpbin /headers` 的机器类型与清单声明架构不一致，或原机 WinSxS 缺少对应架构的该程序集 |
| SxS 本该在 Application 日志留条目却全空 | **挂起（观测通道缺口）** | `SideBySide` 源可能未注册/被策略关闭/日志已满，或失败上报发生在事件写入之前；"日志空"不能反证 SxS | `wevtutil gp Application` 查源与日志状态；用 `sxstrace` 取证（不依赖事件日志）。若 `sxstrace` 也干净，则回到格 1/2 重切 |
| 双击完全无弹窗 vs 命令行有文本 | 挂起（判定为**上报通道差异**，不是第二根） | 该文案出自加载器；有控制台父进程时文本落到控制台，GUI 侧走 CSRSS 硬错误对话框。GUI 侧无弹窗可能因交互桌面不可用、`SEM_FAILCRITICALERRORS`/ErrorMode 或策略静默 | 若 GUI 侧本应有对话框却确实没有，则"弹窗被抑制"是一个**独立缺陷**（ErrorMode/组策略/Explorer 会话），须单列，不并入本根 |
| quota（句柄/桌面堆配额） | 判非根 | 交互式桌面、单次启动、非开机并发场景；且配额类不给 SxS 文案 | 若只在开机自启/高并发登录时失败 |
| concurrency（启动顺序/重试） | 判非根 | 失败是确定性的、每次双击必现 | 若出现"重试 N 次有一次能起"的形态 |
| config（环境变量/注册表业务配置） | 判非根（但注册表中的 SxS 项已计入 G2） | 失败在读取业务配置之前（CLR 未加载） | 若 `sxstrace` 显示解析成功而程序仍不出窗口 |
| 系统日志为空 ⇒ 前两天什么都没发生 | 判**不可推**（取证缺口） | 题面只覆盖系统日志；MSI/Setup 日志、servicing 记录、第三方安装器日志均未观测 | 查 Setup 与 MSI 日志、`Get-WinEvent` 的 Setup 通道；若确实无任何增删，则 G2（自发损坏/清理）权重上调，G1 下调 |
| 杀软/EDR 拦截 | 判非根 | 拦截通常报 `0xC0000022`/`0xC0000428` 并留 WER 或 AV 事件，且不产生 SxS 文案；题面无任何日志 | 若出现访问拒绝族退出码或 AV 拦截事件 |
| 树外分支：`deployment-supply`（依赖供给形态） | 登记为 `v2 候选` 节点，未入树 | 见 L1：现有 `dependency` 层无"供给方消失"格 | 待该节点入树并核查后，把 G1 从个例根提升为该节点下的标准格 |

## 结论

1. **根不在 exe，也不在 .NET。** 它死在 Windows 加载器建立 **side-by-side 激活上下文**的那一步（格 3），此时任何应用代码、包括 CLR，都还没有机会执行——所以没有窗口、任务管理器看不到进程（毫秒级被 `TerminateProcess`）、`.NET Runtime`／`Application Error`／系统日志一个都不会有，能开口说话的只剩加载器自己那一句。**去修 .NET Framework 是零信息的动作。**
2. **责任全在故障机的机器级 SxS 供给。** 「同一个文件夹拷到另一台能跑」是本题最硬的一刀：它证明 exe、内嵌清单、随目录的私有依赖全部自洽且可满足 ⇒ 变的只能是"文件夹之外"的东西。exe 清单里 `<dependency>` 要的是**某一个精确 identity** 的 Win32 程序集（最典型：某精确版本的 `Microsoft.VC*.CRT`，其次 `Microsoft.Windows.Common-Controls` 6.0.0.0）；那台机器上前两天有东西把它撤走了或把解析状态搞坏了——最可能是**某产品被卸载/升级，顺带撤掉了它一直在替这个 exe 提供的 redist**。程序没变，世界变了。
3. **取证一句话，修法两句话**：`sxstrace` 抓出来的那个解析不到的 identity 就是答案；**处置**＝按该 identity 装回精确版本的 redist（或 `sfc`/`DISM` 修 WinSxS 与解析缓存）；**消解**＝把依赖从"借来的"改成"自带的"（私有程序集/静态链接/self-contained 发布），此后机器侧怎么增删都与它无关——这一类"零改动突然不能启动"在结构上不再可能发生。

本题最值钱的可复用判别不是"SxS"这个词，而是一条通用探针：**当"程序零改动 + 单机失败 + 换机正常"同时出现时，把"程序的属性"与"世界的属性"切开——凡是拷走就好、留在此地就坏的，根必然在"文件夹之外"的机器级代持状态里**（依赖供给、许可、策略、解析缓存都属这一类）。同类结构还有：证书链、字体/区域设置、`PATH` 顺序、文件关联、`%TEMP%` 权限、时区与 locale 依赖的默认值。
