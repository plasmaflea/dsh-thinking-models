### 为什么失效 —— 一句话

**副本代码是可读的，真根是被「读」出来的，不是被「推」出来的。**

5/5 都直接引用了字面常量：

- `lab-t1\front.js:11` `UPSTREAM_TIMEOUT = 800`
- `lab-t1\upstream.js:5` `DELAY = 300`、`upstream.js:6` `MAX_ACTIVE = 4`

只要读到这三个数，`C_max = A × ⌊T/D⌋ = 8`、`N_crit = 9` 就是算术，不需要判断力。我上一轮预告的捷径，五份全部走了。⇒ **这道题测的不是「假证据能不能被识破」，测的是「代码能不能被读」**。

## 四、五条实打实的发现（仍然有价值）

### 1. 假证据的识破理由高度一致，且都不是「猜」

五份给的是同一个机制：`client intended to send too large body` 属 nginx 的**请求体准入阶段**（`$upstream_addr = "-"`），产出 413；502 属**等待上游响应阶段**。两阶段由构造互斥，所以「改限额 → 502 消失」这条链在结构上不成立。

三条旁证被 4/5 独立提出（b/c/d/e）：
- nginx 判定是**严格大于**，日志值 `4194304` 恰等于 `4m` ⇒ 若生效限额真是 4m，这行**根本不该出现** ⇒ 实际生效值 < 4MiB（很可能是默认 1m 或 4m 写在没 reload/别的 location）。
- 频次量级不匹配：体积违例是确定性失败（重传永远 413），而 502 只有「十几条/天」。
- 「刷新一下就好」只有瞬态拥塞能解释，静态阈值给不出这个行为。

### 2. 数值指纹五份一致

| 观测 | 五份的一致结论 |
|---|---|
| 拐点 | `N=9` 出现第 1 条 502（`⌈9/4⌉×300 = 900 > 800`） |
| 数量律 | `502 条数 = max(0, N − 8)`，N=10→2、12→4、16→8 逐点吻合 |
| 502 延迟 | 钉在 800ms 附近（实测 818–842ms），是**截断**不是长尾 |
| 成功延迟 | 300ms 的整数倍台阶（≈320 / 630 / 820） |
| 上限 | N=32 / 40 时 100% 502（e：32→32/32；b：40→40/40） |

「延迟被钉在常量上」被 b 和 d 各自独立点成**常量超时的指纹**，d 还补了一句更狠的：这种形态在 Grafana 上看起来像「p99 很稳」，极易被误读成后端健康。

### 3. 三处设计时没预料的机制被挖出来了

- **超订**（c/d/e）：`front.js:8 maxSockets: 32` 对上 4 个槽位 = **8× 超卖**；e 算出代理自己制造的最坏排队 `(32/4−1)×300 = 2100ms`，是它愿意等的 800ms 的 2.6 倍。
- **作废请求仍占槽**（d 实测）：`up.destroy()` 不撤销上游已排队的工作。32 并发突发刚结束立刻发 1 个 → 502 @814ms；等 3s 再发 → 200 @312ms。**这就是「刷新一下就好」的机制**（约 1.8s 残留窗口），不是修好了，是积压排空了。
- **模型失准区间被两方独立报出**（a、e）：a 报 N=24 偏离（预测 8/16，实测 4/20）；e 报 K≥16 失准（16 实测 11 条，20 两次跑 12 与 19）。⇒ 公式只在 `K ∈ [9,15]` 精确，超过后受请求到达时刻摊开影响，只能当**乐观下界**。两方各自把它写进了 ⚠️ 异常而不是藏起来。

### 4. 四条「本能级」判断都出现了

五份全部给出：**处置根**（对齐超时与容量、加背压/503）、**消解根**（时延契约：超时由 p99.9 派生 + 后端先于代理拒绝 + 准入 ≤ A×⌊T/D⌋）、**挂起表**（各 5–10 行，带恢复条件）、**成本排序**（先取证后改配置）。

### 5. 三处只有个别 agent 越想越狠

- b：指出放宽 body 限额会让 D 变大 ⇒ 排队更深 ⇒ **502 反而更多**（方向性风险）。
- d：把 4m→10m 判为「份额为零但 Cost 极小，于是在 `Share × Lever ÷ Cost` 里挤掉了份额唯一的正确候选」，并归纳出「先按同一条请求 join 日志，再谈频次」——这条是全组最锋利的一句。
- c：指出「看着像 4m」本身不可信，要 `nginx -T` 全量 dump 看 location 匹配顺序。

## 五、D5'（真正的盲测）要怎么改

T1 的教训只有一条：**只要实现可读，假证据就必然失效**。所以 D5' 必须把「读实现」这条捷径掐死：

| 要素 | T1（本轮） | D5'（下一版） |
|---|---|---|
| 实现代码 | 可读 | **不可读**——只给 `access.log` / `error.log` 摘录、监控截图数据、配置文件片段 |
| 真根 | 可直接读常量 | 只能从「502 延迟钉在某值上」「502 数与并发线性」这类**行为指纹**反推 |
| 假证据 | 一条 413 日志 | 一条 413 日志 **+** 一条真的 `upstream timed out`（两者都真，只有时间戳能分开） |
| 判分新增 | — | 「是否提出按 `$request_id`/同秒 join 日志」成了关键判据 |

D5' 的题面里必须同时存在两类真日志，让「频次最高」和「同一请求」这两个选择器**给出不同答案**——这才是 D5 真正要压的地方。
