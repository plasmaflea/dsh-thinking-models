# windows-latest 上「同 commit 约 1/7 红、立即重跑转绿」的根源回溯

[🌳 林状图／回溯法] 选择理由：题面问的是「根源在哪」，属于典型根因定位；且要求给出可执行的判别路径而非选项清单，命中林状图的触发词与适用域（根因分析／故障诊断）。本题不需要先穷举选项（无未知广度），也不需要定量建模（无需先算数），故不联用网状图／公式图。

---

## L0 类别判定

**类别：`software`（软件类·环境姿态子类）**
判据（树 `software` 节点两条必要条件）：① 可复现性来自代码/配置/**环境姿态**，而非物理介质 —— 同一 commit 逐次运行结果不同，说明差异在每次运行的环境姿态，不在被测代码；② 失败是**由确定性竞争导致**的 —— 不是位翻转，而是"某条断言的值 = 环境时序的函数，时序偶尔越过阈值"。

已排除的大类：
- **硬件故障**：1/7 的稳定并发率 + 立即重跑转绿 + 本地 200 次全绿，指向统计性而非物理性；硬件受害应跨软件随机出现且伴校验/重试错误。
- **网络问题**：题面直给排除。
- **磁盘空间**：题面直给排除（但"空间"与"IO/句柄竞争"是两件事，见 ⚠️）。
- **权限/账号体系**：本地与 CI 都能跑到测试主体，无 ACL/令牌类症状。
- **组织与流程**：同 commit 即时重跑即绿，与人的决策/交接无关。

**本次判为不适用的节点**：
- `win-service`（L1 节点，覆盖 Session 0／桌面堆／注入 DLL／SxS）—— 该类机制只在**服务形态**下进入；CI 测试是交互式 Session 1 的普通进程，无 SCM 参与。判为不适用，但其中"桌面堆/配额受限"的**机制**在 `quota` 层仍被复用。

**树外分支（不许静默丢弃，登记 v2 候选）**：
- `ci-runner-environment`（CI 托管 runner 的环境姿态：共享宿主 CPU steal、镜像滚动、Defender 默认开启、卷冷缓存）—— 树里没有这一支，但本次它是主嫌疑维度。**v2 候选节点**，理由：`software` 的六个子层都以"应用/进程"为中心，缺少以"托管运行环境"为中心的节点，而这一类 flake 恰恰由环境代持控制权产生。

## L2 逐层回溯

### 轴一（判据轴，恒等式生成）：失败的必要条件分解

生成源：恒等式。任何一次测试运行：

```
观测值  =  F(测试显式输入, 环境隐式输入)
红 ⟺ 观测值 ∉ 断言容差
```

按等号右边逐项切，失败的必要条件只可能落在三格，三格**正交、可生成、可观测**：

| 格 | 该格在管什么 | 该格故障的可观测症状 | 本题判定 |
|---|---|---|---|
| **① 环境隐式输入改变** | 未写进测试输入的那部分环境（调度延迟、CPU 份额、并行度、共享命名空间、宿主缓存） | 同一 commit、同一日志里"没有代码差异却结果不同"；失败用例耗时贴近阈值 | **活跃·必要** |
| **② 容差贴边（margin < 环境波动）** | 测试侧的阈值/超时/sleep 预算相对真实波动没有余量 | 断言值离阈值只差几个百分点；把超时 ×10 就不再红 | **活跃·必要** |
| **③ 观测丢失** | 日志/结果没被采集，或进程被杀导致无断言失败 | 红但无失败用例名、或 job 崩在采集之前 | **活跃（管道侧）** |

**关键结论（这是本题的结构性答案）**：① 与 ② **必须同时成立**才可能红。
- 本地：① 恒假（本地那台机器把调度/并行/命名空间钉在容差内）⇒ **② 从未被检验过**。所以"本地 200 次全绿"不是反证，而是"② 的缺陷没被触发"。
- CI：① 以约 1/7 的概率为真 ⇒ **② 一旦贴边就红**。
- 推论：**任何只改 ① 的动作（换更快的 runner、加机器、重跑）都是缓解，不可能消解**；同理只改 ② 而不改 ① 也只是把概率推小。这直接决定了下面双根的形态。

### 轴二（来源轴，必经时序 + 树六子层）：自由度从哪来

轴由树 `software` 的六个正交子层实例化（裁剪但不漏格）。每格用**两个必须同时解释的现象**验收：**(a) 为什么本地 200 次测不出**、**(b) 为什么 CI 约 1/7 且立即重跑常绿**。只解释其中一个的，判为不是根。

| 层 | 该层管的自由度 | 该格故障的可观测症状 | 能否解释 (a) 本地绿 | 能否解释 (b) 1/7 且重跑绿 | 判定 |
|---|---|---|---|---|---|
| **`concurrency` 并发与时序** | 并行度、共享命名空间、启动顺序 | 偶发；只在并行度/核数不同的机器上出现；失败形态为端口占用、临时文件被占用、静态单例被改写、`CurrentDirectory` 被并行测试改写 | ✅ 本地核数 ≠ runner 核数 ⇒ **并行拓扑不同**，本地结构性挡在门外 | ✅ 共调度是概率事件 | **活跃（主因候选 A）** |
| **`quota` 资源配额** | CPU 份额、内存、句柄、线程池 | 长跑后失败；4 核上线程池爬升慢 + 同步阻塞 ⇒ `TimeoutException`/`TaskCanceledException`；失败用例耗时贴阈值 | ✅ 本地核多、内存足、无限配额 | ✅ 宿主 steal 是概率的 | **活跃（共因候选 C）** |
| **`init` 初始化** | 进程启动必经步骤（加载、首写、绑定） | 死在第一行日志之前；`Process.Start` 后立刻连接被拒；`WaitForExit(timeout)` 返回 false | ✅ 本地文件已热、二进制已被 AV 排除 | ✅ Defender 首扫新 exe/dll 的尾延迟是概率的 | **活跃（共因候选 B）** |
| **`config` 配置与状态** | 环境变量、区域/时区、持久残留 | 区域相关断言（日期/小数/排序）；`%TEMP%`/缓存/上次运行残留被复用 | 部分（culture 差异） | 仅"持久残留"这一小支能解释 1/7；culture 在 runner 上是**恒定**的 ⇒ 应必红 | **收窄为活跃·弱（候选 D）** |
| **`dependency` 依赖解析** | 静态/动态依赖、版本、架构、符号 | `BadImageFormatException`、0xC0000135、MSB 版本漂移 | 部分 | ❌ 依赖漂移是**时间阶跃**（某天起必红），不是 1/7 的概率；同一镜像内重跑不该变 | **挂起** |
| **`lifecycle` 生命周期控制** | 谁创建/杀死测试进程 | 整 job 崩、退出码来自加载器（0xC000013A、137、258）、无断言失败 | 部分 | ❌ 宿主 kill 不产生"某条断言红"，且应伴内存单调增长 | **挂起** |

**为什么 1/7 这个数值本身就是证据**：14% 的稳定失败率对**离散 interleaving（真实数据竞态）偏高**——真竞态通常在 10⁻³ 量级，且随重跑次数呈现不稳定分布；14% 恰好是**连续量（延迟/份额）越过阈值的尾概率**量级（即 `P(延迟 > 阈值) ≈ 0.14`）。这不排除并发类（并发类里"端口/文件占用"也是连续延迟驱动的），但把**调查优先级从"找执行顺序"改成"找耗时贴阈值的断言"**。这是一个可以立刻验证的推论：读失败 run 的 `.trx` 里失败用例的 `duration`，若它接近（而非等于）超时值，本推论成立。

### 为什么"本地 200 次全绿"不是反证（(a) 的机制表）

本地与 `windows-latest` 在以下量上**系统性不同**，每一个都是 ① 格的自由度：

| 自由度 | 本地开发机（典型） | windows-latest runner | 差异后果 |
|---|---|---|---|
| 逻辑核数 | 8–32 | 公开仓 4 vCPU（私有仓历史上更少，**需按你的仓库类型核对**） | xUnit 默认按 collection 并行、并发度 = `ProcessorCount` ⇒ **并行拓扑完全不同** |
| CPU 独占性 | 独占 | 与共租户共享，存在 steal | 尾延迟抬到 100 ms–s 级 |
| Defender | 开发目录常已排除/编译器路径不扫 | 实时扫描新生成的 exe/dll/zip | 首次启动与首写阻塞句柄 |
| 全局 timer resolution | 常有 GUI/音频/浏览器把全局 timer 提到 1 ms | 无 ⇒ 默认 **15.625 ms** | `Thread.Sleep(1)`/`Task.Delay(1)` 实际 ≈15 ms；本地测出的"1 ms 级"时序假设在 CI 上不成立 |
| 卷状态 | NTFS + 已热缓存 | 全新卷、冷缓存 | 首写/首读延迟 |
| 区域/时区 | 常见 zh-CN | en-US | 格式类断言**恒红**（因此不是 1/7 的来源，见挂起表） |

## L3 双根

### 类根（面向整个大类）

> **测试把「环境自由度」当成了常量：断言的表达式里含有未被固定的环境量（调度延迟、CPU 份额、并行度、共享命名空间、宿主缓存状态），这些量在开发机上稳定落在容差内，在托管 runner 上以约 1/7 的概率落到容差外。也就是说，测试的确定性控制权被代持给了运行环境——与 `software` 节点的类根同构：本该由应用掌握的控制权被外部机制代持。**

个例根挂在类根之下（候选，按 Share 排序，尚不能收敛为单条——原因见 ⚠️）：

```
类根：确定性控制权被环境代持
├─ 个例根 A（主因候选）并发/共享命名空间
│    xUnit 并行度 = ProcessorCount，本地高核 vs runner 4 核 → 并行拓扑不同；
│    共享资源（固定端口、固定临时文件名、静态单例、Environment.CurrentDirectory）
│    在重跑时以概率被并发触达。症状：端口占用 / 文件被占用 / 断言读到别人的状态。
├─ 个例根 B（共因候选）启动延迟 × 固定超时
│    Process.Start 新生成的 exe 首次被 Defender 扫描，尾延迟 100 ms–数秒；
│    测试用固定 WaitForExit/WaitOne 预算等待 → 超时。症状：连接被拒 / 等待返回 false。
├─ 个例根 C（共因候选）4 核上的线程池饥饿
│    同步阻塞占用 worker，4 核上 ThreadPool 注入速率不足 → 异步断言超时。
│    症状：TimeoutException / TaskCanceledException，失败用例耗时贴阈值。
└─ 个例根 D（次要）持久残留复用
     %TEMP%/缓存/上次运行残留被复用；与"立即重跑常绿"部分不符，故降权。
```

### 处置根（修本次）

**用一次成本最低的实验把 A/B/C 三支切开，而不是先猜。**
1. 打开最近一次红的 run，下载 `TestResults/*.trx`（或 `--blame` 产出的 `Sequence.xml`）——需要失败**用例名 + duration + 该次并行上下文**。若没上传 artifact，这本身就是 ③ 格（观测丢失），先补 `actions/upload-artifact`。
2. **决定性判别实验（性价比最高的一步，成本 ≈ 30 次重跑）**：把测试并行度固定为 1（xUnit：`-parallel none` 或 `maxParallelThreads: 1`；`dotnet test` 加 `-- RunConfiguration.MaxCpuCount=1`），再连跑 30 次：
   - **仍约 1/7 红** ⇒ 排除并发调度，锁定 **B/C（延迟与配额）**：去查"耗时贴阈值的断言"，并把该断言的预算从"固定超时"改成"事件驱动 + 宽容差"。
   - **转为全绿** ⇒ 锁定 **A（并发/共享命名空间）**：逐项隔离端口（bind `:0` 由 OS 分配）、临时目录（每测试独占）、`CurrentDirectory`/环境变量（禁改）。
3. 同时建立本地"CI 等价档"：限核（进程亲和性绑到 1–2 核）+ 保持 Defender 实时扫描开启 + 不运行任何会抬高全局 timer resolution 的 GUI/音频进程，在同一档位上跑 200 次。**"本地 200 次全绿"只有在等价档上成立才算证据。**

### 消解根（灭这一类）

> **把时间、命名空间、并行度、配额四项自由度从环境手里收回测试自己手里：断言只依赖测试自己设定的输入（虚拟时钟推进、独占资源、显式声明的并行度、自建配额），而不是依赖运行环境恰好够快、恰好不撞、恰好几核。**

三道闸门：
- **不可发生判据**：若每条断言的求值只依赖测试自己设定的输入，则"环境变慢/变脏/变少核"无法改变断言结果 ⇒ 本类问题在**结构上**不可能发生（不是"变少见"）。自检判据：**同一 commit 在"限 1 核 + Defender 开启 + 并行度 1 + 冷 `%TEMP%`"的机器上跑 200 次仍全绿**；达不到，就说明还有自由量没收回来。
- **可执行首边**（从现状出发的第一步，可以很小）：
  1. CI 默认产出 `TestResults/*.trx` + 逐测试耗时，并 `upload-artifact`（半天）；
  2. 并行度从 `ProcessorCount` 改为显式常量（1 行配置）；
  3. 落地上面第 3 步的"CI 等价本地档"脚本（半天）。
- **成本量级**：首边 ≤1 人日；时间源抽象全量替换与全仓 `DateTime.*` / `Task.Delay` / `Stopwatch` / `Thread.Sleep` 的调用点数成正比，量级 **1–3 人周**（需按实际点数用 📐 公式图定量，此处只给量级）；命名空间隔离 2–5 人日；换 `ubuntu-latest` 1–2 人日——**但换 OS 只消解 Windows 特有子类，不消解类根**（见 L4 第 6 项）。

### 候选根排序（Share × Lever ÷ Cost）

| 层级 | 候选根 | Share 份额 | Lever 可控性 | Cost 证伪代价 | 排序 |
|---|---|---|---|---|---|
| 类根 | 确定性控制权被环境代持 | 唯一 | 改架构 | 读一次失败 run 的 trx | **1** |
| 个例 | A 并发/共享命名空间 | 主因 | 改配置 | 关并行跑 30 次 | **2** |
| 个例 | B 启动延迟 × 固定超时 | 共因 | 改配置 | 读失败用例 duration | **3** |
| 个例 | C 4 核线程池饥饿 | 共因 | 改配置 | 同上 + 核数曲线 | **4** |
| 个例 | D 持久残留复用 | 次要 | 改配置 | 清 `%TEMP%` 后跑 30 次 | **5** |
| 树外 | `ci-runner-environment` 姿态 | 共因 | 换环境/动不了 | 对比失败 run 的镜像版本 | 6 |

排第一的不是"最可能的机制"，而是"信息量/成本比最高的动作"——因为现在**连失败的是哪条断言都不知道**（③ 格），任何机制判断都还只是先验。

## L4 迁移出口

消解根指向测试基建的结构变更，故必须列出迁移清单，并把本次问题降级为其中一项：

1. **时间源抽象**：引入可注入的时间源（.NET 8 的 `TimeProvider`，或自定义 `IClock`），全仓 `DateTime.Now` / `Stopwatch` / `Task.Delay` / `Thread.Sleep` 替换为注入；测试支持"真实时钟 + 虚拟时钟"双跑。迁移期风险：虚拟时钟掩盖真实性能回归，需保留一条真实时钟的 smoke 通道。
2. **命名空间隔离**：每测试独占临时目录、端口由 OS 分配（bind `:0`）、禁止测试改写 `CurrentDirectory` 与进程级环境变量；清理策略显式化。
3. **并行度治理**：把并行度从 `ProcessorCount` 改为显式声明；共享资源的测试归入同一 collection/fixture；写入"哪些测试互斥"的声明表。
4. **可观测性**：`trx` + `--blame-hang-timeout` + 逐测试耗时基线 + 失败自动上传 artifact/dump。**没有这一项，同类问题在任何架构下都不可定位。**
5. **环境等价**：本地"CI 等价档"脚本（限核、开 Defender、并行度 1、冷 temp）；或迁到 self-hosted / 容器。注意：Windows 容器仍共享内核与宿主 Defender，**不等价**，不能当成消解手段。
6. **决策：是否必须用 Windows runner**：若无 Windows 特有依赖，换 `ubuntu-latest` 可结构性消除一个**子类**（Defender 句柄竞争、NTFS 锁、15.625 ms timer、桌面堆），但**不消除**时序/配额类——因此它是子类消解，不是类根消解。

→ **本次问题降级为：第 4 项（可观测性缺失）下暴露出的一个未命名断言。** 即"本次到底哪条红、红了多少毫秒"在产品化之前不可得，所以本轮只能给到按 Share 排序的候选集与一次成本 30 次重跑的决定性判别实验。

## 挂起表

| 分支 | 判定 | 依据 | 恢复条件 |
|---|---|---|---|
| 测试代码随机数 | 非根 | 题面已确认排除 | 若红/绿与 seed 相关，或失败用例名随 seed 变化则恢复 |
| 网络请求 | 非根 | 题面排除；且网络抖动应表现为 DNS/socket 错误族，不会稳定在 1/7 | 失败日志出现 socket/DNS/TLS 错误则恢复 |
| 磁盘空间 | 非根 | 题面排除；空间耗尽是单调恶化，不会"立即重跑就绿" | runner 报 `No space left`/`ENOSPC` 则恢复 |
| 磁盘 IO / 文件句柄竞争（≠ 空间） | **未排除，需澄清** | 题面只说"不是磁盘空间"；文件被占用属 `concurrency` 子类，是活跃候选 A 的一部分 | 若用户确实已排除句柄/IO，则本行降为挂起 |
| 硬件（树外大类 `hardware`·待建节点） | 非根 | 1/7 稳定并发率 + 立即重跑绿 + 本地 200 绿；硬件受害应跨软件随机且伴校验/重试错误 | 出现 ECC/CRC/磁盘重试日志，或换宿主后同率出现则恢复 |
| `lifecycle`（进程被宿主杀） | 挂起 | 失败应表现为整 job 崩、无断言失败，且伴内存单调增长 | 失败 run 退出码为 0xC000013A/137/258 等加载器或信号类且无断言失败 |
| `dependency`（依赖/镜像版本漂移） | 挂起 | 依赖漂移是**时间阶跃**（某日起必红），不是 1/7 的概率；同一镜像内重跑不该变 | 出现 `BadImageFormatException`/0xC0000135，或"某天起全红" |
| `config`-区域/时区/文化 | 挂起 | runner 的 culture 恒定 ⇒ 应**必红**；无法解释 1/7，也无法解释重跑转绿 | 失败与日期/小数/排序断言同时出现，且本地切 en-US 也复现 |
| `config`-持久残留（`%TEMP%`/缓存） | 活跃·弱（候选 D） | 能解释 1/7（复用上次残留），但与"立即重跑往往就绿"不完全相符 | 清空 `%TEMP%` 与缓存后仍 1/7，则降为挂起 |
| `ci-runner-environment` 环境姿态（树外分支，v2 候选节点） | 活跃 | 共享宿主 CPU steal、镜像滚动、Defender 默认开启，是 ① 格的直接来源 | 对比失败 run 的 runner 名/镜像版本/核数，若无差异则降权 |
| 组织流程（`windows-latest` 镜像滚动节奏，树外大类） | 挂起 | 同 commit 即时重跑即绿，与时间点无关 | 出现"某镜像版本起才红、换回旧镜像即绿" |
| **"本地 200 次全绿"作为反证** | **判定为不成立的反证** | 本地并行度（核数）、Defender 配置、全局 timer resolution 都与 runner 不同 ⇒ 本地把 ① 格结构性钉住，② 格的缺陷从未被检验 | 只有在"限 1–2 核 + Defender 开启 + 并行度 1 + 冷 temp"的等价档上跑 200 次全绿，才构成排除 |
| 换 `ubuntu-latest` 作为消解根 | 降级为**子类消解**（候选） | 只消除 Windows 特有的 Defender/NTFS/15.625 ms timer/桌面堆子类，不消除时序与配额类 | 换后仍偶发，即确认类根未被消解 |

## 结论

根源不在测试逻辑里的"随机性"，而在**测试把环境自由度当成了常量**：本地那台机器恰好把调度延迟、并行度、共享命名空间的稳定性钉在容差内，`windows-latest` 把同一批量以约 1/7 的概率推过容差——所以"本地 200 次全绿"不是反证，而是"容差从来没被检验过"的证据。**1/7 这个数值本身偏向尾延迟（连续量越阈值），而不是真实数据竞态（离散 interleaving 通常低两个量级）**，因此调查优先级应从"找执行顺序"改为"找耗时贴阈值的断言"。最高性价比的一步不是猜机制，而是做一次判别实验：**把 CI 并行度固定为 1 再跑 30 次**——仍红则锁定启动延迟/4 核线程池饥饿（Defender 首扫、配额），转全绿则锁定共享命名空间（端口、临时文件、静态单例、`CurrentDirectory`）；同时先把"逐测试耗时 + 失败 artifact"变成默认产出，否则同类问题在任何架构下都无法定位。永久解法只有一条：把时间、命名空间、并行度、配额四项自由度从环境手里收回测试自己手里，判据是"限 1 核 + 开 Defender + 并行度 1 下跑 200 次仍全绿"。
