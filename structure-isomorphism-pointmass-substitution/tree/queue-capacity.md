# 排队-容量（`queue-capacity`）

**边型**：`L = λW`（Little's law，守恒型恒等式）；`吞吐 = min(λ, C/S)`

**变量集**
- `λ`：到达率；`C`：并发槽位/服务台数；`S`：单请求服务时间
- `L`：系统内数量（排队 + 在服务）；`W`：系统内停留时间
- 派生：`C_max = C · ⌊T_timeout / S⌋`（超时窗内最多能处理多少）

**边界条件（缺一即非本模式）**
- **稳态**：观测窗足够长，`λ` 与 `W` 不同时漂移
- **守恒**：请求不会凭空消失（超时丢弃会让守恒破裂，见下）
- 服务台同质（异构池要分层算）
- 时间窗足够覆盖排队长度（否则算不出 `W`）

**已知同构问题**
- 线程池/连接池饱和：`L` 排队导致超时
- 客服工单积压：工单数 = 到达率 × 平均停留
- 上游代理超时：`C_max < λ·S` 时必然 502/504
- 服务重启节流：重启间隔 < 服务启动时间 ⇒ 永远起不来

**该类的典型处置动作**
1. **先算 `C_max` 再谈优化**：`C_max = C × ⌊timeout/S⌋`，一旦 `λ > C_max`，超时是算术必然而不是「偶发」。
2. **用 `L = λW` 反解**：观测到 `L`（队列深度）和 `W`（延迟），就能反推 `λ`，不需要额外埋点。
3. 瓶颈在 `min` 的那一项：要么提 `C`，要么降 `S`，要么降 `λ`（限流/削峰）。
4. 结论形式：`C_max 与 λ 的比较 + 剩余余量 + 越过它之后是排队还是丢弃`。

**越界后退化成什么**
- 有超时丢弃 → 守恒破裂，`L=λW` 里被丢弃的那部分不可见 ⇒ 只能给上界，且必须说明「真实延迟比观测更长」。
- 有重试 → 有效 `λ_eff = λ × 平均尝试次数`，必须代入放大后再算。
- 有限队列 + 满即拒 → `queue-capacity` 与 `saturation` 联用：拒绝率由 `max(0, λ − C/S)` 决定。

**反例（别把它当本模式）**
- 把人力当服务台：人力超载不会「排队等待」，而是加班、降质或延迟交付——机制不同，不能迁移结论。
- 「加机器就能解决」：若瓶颈在 `S`（单请求更慢，例如加了跨机房调用），加 `C` 无效甚至更糟。
