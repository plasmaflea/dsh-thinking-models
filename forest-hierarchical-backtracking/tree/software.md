# 节点 `software` · L0 类别判定

**父节点**：无（顶层）　**版本**：v1　**核查**：2026-10-18

## 判据（怎么判定「这是软件问题」）

必须同时满足两条，否则不属于本节点：

1. **可复现性来自代码/配置/环境姿态，而不是物理介质**：同一份程序在另一台等价机器上行为可复现（或明确只在某种环境姿态下复现）。
2. **失败是确定性的或由确定性竞争导致**：给定相同输入与时序，失败可重现；不确定的部分能被归因到某个外部输入的时序，而不是随机的位翻转。

**排除项**（必须先排除，再进入本节点）：

| 被排除的大类 | 判据 | 典型症状 |
|---|---|---|
| 硬件故障 | 症状跨软件、跨进程随机出现；有校验错误（CRC/ECC）、温度/负载相关 | 随机蓝屏、内存校验失败、磁盘重试、同一程序时快时慢无规律 |
| 网络问题 | 分层可达性可测（ping/telnet/traceroute）；症状随链路变化 | 超时、连接被重置、DNS 解析失败 |
| 权限/账号体系问题 | 换同一账号的交互式登录即正常/异常；ACL、令牌、组成员关系可查 | 拒绝访问、找不到资源、服务账户特有失败 |
| 组织与流程问题 | 技术手段已全部正常，问题仍由人的决策/交接/优先级产生 | 决策不落地、工单在人间滞留 |

> 类别判定允许**一行完成**，但不许省略。省略大类判定＝让后续回溯建在未声明假设上。

## 六个正交子层（L1 轴候选，可按需裁剪但不可漏格）

| 子层 | 该层在管什么 | 典型根 | 典型症状 |
|---|---|---|---|
| `lifecycle` 生命周期控制 | 谁创建进程、谁决定它的存亡 | 由外部管理器（SCM/容器/监督进程）而非应用自身控制 | 无堆栈的猝死、退出码来自加载器而非程序 |
| `init` 初始化 | 进程起来的必经步骤（加载、绑定、读取配置） | 初始化阶段某一步返回失败 | 死在日志第一行之前 |
| `dependency` 依赖解析 | 静态/动态依赖、版本、架构、符号 | 缺失/过旧/位数不符/符号缺失 | 明确的不同错误码族（见 win-service 节点的码表） |
| `quota` 资源配额 | 内存、句柄、桌面堆、线程、文件描述符 | 非交互/受限上下文的配额比交互式小 | 开机并发时失败、平时成功 |
| `concurrency` 并发与时序 | 锁、竞态、启动顺序、重试风暴 | 依赖未被声明（缺 DependOnService、缺健康检查） | 偶发、与启动时序强相关 |
| `config` 配置与状态 | 环境变量、注册表、配置文件、持久状态 | 配置在错误的阶段被读取 | 改配置有效但说不出为什么 |

## 本节点的类根（往上一层）

软件问题的类根通常是：**某个本该由应用掌握的控制权，被外部机制代持**——生命周期、配额、依赖解析、启动顺序，其中任何一项被代持，失败就会发生在应用能打日志之前，于是表现为「无堆栈、无输出」。

这条类根是消解路径的入口：把控制权交还应用（前台守护/容器/自管启动），或换到把这些语义显式化的环境（如 Linux + systemd）。
